# 自动化测试提示词 — 分布式系统与微服务架构（V01–V10）

> 使用说明见同目录 `README.md`。每条提示词在同一 Session 内按轮次顺序喂入。

## 维度说明

本维度考察 Agent 在**服务发现、负载均衡、分布式事务、消息队列、
一致性算法、分布式缓存、服务网格、容错机制、分布式追踪、
事件驱动架构**等"分布式系统"垂直领域中的实战表现，
与 J 维度（网络协议基础）和 K 维度（综合场景）互补：
J 考察"单机网络协议"，K 考察"综合工程实践"，
本维度考察"多节点协作的分布式系统设计与实现"。
所有主题都以"动手写分布式代码或设计架构方案"为核心，强调分布式工程能力。

### V01 服务发现：Consul 与 etcd 实战
- **预期档位**: hard
- **考察维度**: 服务注册 + 健康检查 + 配置中心
- **对话脚本**:
  1. 解释服务发现（Service Discovery）的两种模式：客户端发现 vs 服务端发现，各有什么优劣。
  2. 用 Rust 实现一个最小服务注册客户端：服务启动时向 etcd 注册自己的地址和端口，定期发送心跳续约。
  3. 加上健康检查：实现一个 `/health` HTTP 端点，etcd 通过它判断服务是否健康。
  4. 讨论：etcd 和 Consul 在一致性协议上有什么不同（Raft vs Raft+Gossip）？各自的适用场景？

### V02 负载均衡算法与实现
- **预期档位**: medium
- **考察维度**: 负载均衡 + 算法选择 + 健康感知
- **对话脚本**:
  1. 解释 5 种负载均衡算法：轮询（Round Robin）、加权轮询、最少连接（Least Connections）、一致性哈希、随机。
  2. 用 Rust 实现一个最小负载均衡器：监听 8080 端口，把请求转发到 3 个后端服务，支持轮询和最少连接两种策略。
  3. 加上健康检查：定期探测后端服务，不健康的节点自动从池中移除，恢复后自动加回。
  4. 讨论：一致性哈希在什么场景下比轮询更好？"虚拟节点"解决了什么问题？

### V03 分布式事务：两阶段提交与 Saga 模式
- **预期档位**: hard
- **考察维度**: 分布式事务 + 一致性保证 + 补偿机制
- **对话脚本**:
  1. 解释分布式事务的难点：为什么单机 ACID 在分布式环境下难以实现？CAP 定理是什么？
  2. 解释两阶段提交（2PC）的流程：准备阶段和提交阶段，为什么它在协调者故障时会阻塞？
  3. 用 Saga 模式实现一个"下单"流程：扣库存 → 扣款 → 创建订单，任一步失败时执行补偿操作（回滚）。
  4. 讨论：Saga 的"编排（Choreography）"和"编排（Orchestration）"两种风格各有什么优劣？

### V04 消息队列：Kafka 与 RabbitMQ 对比
- **预期档位**: medium
- **考察维度**: 消息系统 + 发布-订阅 + 消息可靠性
- **对话脚本**:
  1. 解释消息队列的核心概念：Producer、Consumer、Topic、Partition、Offset、Consumer Group。
  2. 对比 Kafka 和 RabbitMQ：吞吐量、消息持久化、顺序保证、消费模型各有什么差异？
  3. 用 Rust 的 `rdkafka` crate 实现一个最小生产者-消费者：生产者发送 100 条消息，消费者按顺序消费并确认。
  4. 讨论：消息队列的"至少一次/至多一次/恰好一次"三种语义怎么实现？Kafka 的幂等生产者是怎么工作的？

### V05 一致性算法：Raft 协议深入
- **预期档位**: hard
- **考察维度**: 共识算法 + 领导者选举 + 日志复制
- **对话脚本**:
  1. 解释 Raft 协议的核心概念：Leader、Follower、Candidate、Term、Log Entry。
  2. 描述 Raft 的领导者选举过程：什么时候触发选举？怎么保证一个 Term 只有一个 Leader？
  3. 描述日志复制过程：Leader 怎么把日志同步到 Follower？什么情况下提交？
  4. 讨论：Raft 和 Paxos 哪个更容易理解？为什么 etcd/ZooKeeper 都选了 Raft 类协议？

### V06 分布式缓存：Redis 集群与缓存策略
- **预期档位**: medium
- **考察维度**: 缓存架构 + 一致性哈希 + 缓存模式
- **对话脚本**:
  1. 解释缓存的两种模式：Cache-Aside（旁路缓存）和 Read-Through/Write-Through，各有什么优劣。
  2. 用 Rust 的 `redis` crate 实现一个分布式缓存层：先查缓存，缓存未命中时查数据库并回填。
  3. 处理缓存穿透、缓存击穿、缓存雪崩三个问题：分别给出防护方案（布隆过滤器、互斥锁、随机过期时间）。
  4. 讨论：Redis Cluster 的一致性哈希是怎么工作的？"虚拟槽位（Hash Slot）"和传统一致性哈希有什么区别？

### V07 服务网格：Istio 与 Envoy 原理
- **预期档位**: hard
- **考察维度**: 服务网格 + 流量管理 + 可观测性
- **对话脚本**:
  1. 解释服务网格（Service Mesh）的核心概念：数据平面（Envoy）和控制平面（Istio）。
  2. 描述 Envoy 的流量管理能力：路由、重试、超时、熔断、灰度发布是怎么实现的。
  3. 设计一个"金丝雀发布"方案：新版本先接收 5% 流量，观察 10 分钟无错误后逐步放量到 100%。
  4. 讨论：服务网格的性能开销在哪（Sidecar 代理）？什么规模的服务才值得引入服务网格？

### V08 容错机制：熔断、限流、降级
- **预期档位**: medium
- **考察维度**: 容错模式 + 稳定性保障 + 自适应保护
- **对话脚本**:
  1. 解释三种容错模式：熔断器（Circuit Breaker）、限流（Rate Limiting）、降级（Fallback）。
  2. 用 Rust 实现一个三态熔断器：Closed（正常）→ Open（熔断）→ Half-Open（探测），状态转换条件是什么？
  3. 加上令牌桶限流：每秒最多 N 个请求，超出返回 429。
  4. 讨论：熔断器的"失败阈值"和"熔断时长"怎么调？太敏感和太迟钝各有什么风险？

### V09 分布式追踪：OpenTelemetry 与链路追踪
- **预期档位**: hard
- **考察维度**: 可观测性 + 链路追踪 + 性能分析
- **对话脚本**:
  1. 解释分布式追踪的核心概念：Trace、Span、Parent Span、Trace Context（traceparent 头）。
  2. 用 Rust 的 `opentelemetry` crate 为一个 HTTP 服务加追踪：记录每个请求的处理时间和子调用。
  3. 实现跨服务追踪：服务 A 调用服务 B 时，Trace Context 怎么传递？
  4. 讨论：采样率怎么设？100% 采样在生产环境可行吗？"尾部采样（Tail-based Sampling）"解决了什么问题？

### V10 事件驱动架构：Event Sourcing 与 CQRS
- **预期档位**: hard
- **考察维度**: 事件溯源 + 读写分离 + 最终一致性
- **对话脚本**:
  1. 解释 Event Sourcing 的核心思想：不存储当前状态，存储所有导致状态变化的事件，通过重放事件重建状态。
  2. 用 Rust 实现一个最小 Event Sourcing 系统：一个"银行账户"聚合，支持存款、取款、查询余额。
  3. 加上 CQRS（命令查询职责分离）：写模型处理命令生成事件，读模型从事件投影出查询视图。
  4. 讨论：Event Sourcing 的"事件版本升级"怎么处理？旧事件 Schema 变了怎么办？
