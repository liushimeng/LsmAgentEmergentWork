### BC01 技术写作基础：金字塔原理与受众分析
- **预期档位**: simple
- **考察维度**: 写作结构 + 受众适配
- **对话脚本**:
  1. 巴巴拉·明托的金字塔原理在技术写作中的应用：结论先行 + MECE 分组 + 归纳演绎，三段式结构在 RFC 与设计文档中的具体体现。
  2. 技术文档的三大受众分层：决策者（高管/PM，要 ROI + 风险）→ 实现者（开发，要接口 + 边界）→ 维护者（未来自己，要原因 + 陷阱），给每类受众写同一主题的开头段。
  3. 「对程序员友好的文档」十大原则：示例驱动、Show me the code 先于讲原理、版本对齐、可复制粘贴、错误码可定位、API 与教程分离。
  4. 改写一段糟糕的技术说明（堆砌名词/缺主语/无结构）为合格版本，对比前后差异并逐条说明改写理由。

### BC02 ADR（架构决策记录）深度实践
- **预期档位**: medium
- **考察维度**: ADR 模板 + 决策生命周期
- **对话脚本**:
  1. 主流 ADR 模板对比：MADR / Nygard Template / Y-statements / Planguage / AlexBuck 的 6 段式，每种模板的适用场景与最小必填字段。
  2. ADR 编号规则：`0001-record-architecture-decisions.md` → `0042-use-postgres-for-analytics.md`，命名规范如何承载检索与版本语义。
  3. ADR 的生命周期：Proposed → Accepted → Deprecated → Superseded，状态机迁移规则与回退决策的写法。
  4. 给 laew 写一份真实 ADR：决策「在 Agent 循环中引入 ContextMaxSize 800K + 三档自动压缩」，按 MADR 模板写完整 Context/Decision/Consequences。

### BC03 API 文档工程：从 OpenAPI 到 Reference Doc
- **预期档位**: medium
- **考察维度**: API 文档标准 + 自动化生成
- **对话脚本**:
  1. API 文档三大形态：Reference（接口字典）/ Tutorial（手把手）/ Guide（概念体系）的写作目标与读者路径设计。
  2. OpenAPI / AsyncAPI / GraphQL SDL / gRPC ProtoDoc 四种 IDL 的文档生成链路：swagger-ui / Redoc / Stoplight / GraphiQL / Buf Schema Registry。
  3. API 文档的「可调试性」：内置 Try It、Code Sample 多语言、错误码示例、Rate Limit 文档、版本切换器（v1/v2/v3 共存），给 Stripe / Twilio 的最佳实践拆解。
  4. 给 laew 的 `-debug` 模式生成 API 文档：用 utoipa 从 Rust 类型自动推导 OpenAPI 3.1，含 Agent 调用端点、Request/Response schema、错误码、示例 curl。

### BC04 Runbook 与故障响应手册
- **预期档位**: medium
- **考察维度**: Runbook 模板 + 应急剧本
- **对话脚本**:
  1. Runbook vs Playbook vs SOP 的差异：Runbook 是步骤化操作手册、Playbook 是战术决策树、SOP 是流程规范文档，三者在 SRE 体系中的角色。
  2. Runbook 的标准结构：触发条件 → 影响范围 → 应急止血 → 根因排查 → 修复步骤 → 验证方法 → 回滚方案 → 沟通模板，每节必填字段清单。
  3. 「可执行的 Runbook」三要素：命令可复制粘贴、参数可配置、输出可解读。给一段故意写错/写模糊的 Runbook 反例与修复对照。
  4. 为 laew 写一份真实 Runbook：「`LsmAgentEmergentWork.db` 损坏导致启动失败」——给出 SQLite 修复命令（PRAGMA integrity_check + .recover）、备份回滚路径、对外沟通文案。

### BC05 Engineering Wiki 与团队知识资产
- **预期档位**: medium
- **考察维度**: 知识库结构 + 长期维护
- **对话脚本**:
  1. 团队知识资产的三层架构：日常笔记（Slack/钉钉）→ 沉淀文档（Confluence/语雀）→ 长期资产（GitHub/BookStack），三层如何转化与归档。
  2. Wiki 工具对比：Confluence / Notion / GitBook / Outline / 语雀 / BookStack / Docusaurus，编辑体验、检索质量、版本控制、权限模型的差异。
  3. 知识库的「僵尸化」问题：写完没人看、链接断裂、版本过期。给一个季度知识库审计 SOP（含死链扫描、阅读量统计、定期 review）。
  4. 设计 laew 团队的 Engineering Wiki 目录树：Onboarding / Architecture / Runbook / ADR / Postmortem / RFC 五类，给出每类的最小内容模板。

### BC06 RFC 与设计文档：从提案到落地
- **预期档位**: medium
- **考察维度**: RFC 流程 + 设计评审
- **对话脚本**:
  1. 主流 RFC 流程对比：IETF（互联网标准）/ Google Design Doc / Apache Project / Rust Lang RFC / GitHub Issue-based，五种流程的相同点与差异。
  2. 设计文档的十段标准模板：Context / Goals / Non-Goals / Design / Alternatives Considered / Risks / Open Questions / Test Plan / Rollout / Open Questions。
  3. 设计评审的常见反模式：过早定细节、过早讨论实现、文档先行于需求讨论。给一份有效的设计评审会议议程模板（含时间盒）。

### BC09 注释即文档：代码内的技术写作
- **预期档位**: simple
- **考察维度**: 注释原则 + 文档生成
- **对话脚本**:
  1. 注释的「该写与不该写」边界：解释 why（动机/约束/陷阱）不写 what（语法翻译/机械重复），给正反两组对比示例。
  2. Rustdoc / JSDoc / Go doc / Python docstring 四种文档注释的风格对比：参数类型、返回值、示例、链接、交叉引用的最佳实践。
  3. doc test（文档即测试）：Rust 的 `///` 注释中的可执行示例、`assert_eq!` 内嵌、`?` 错误传递，给 laew 的工具注册模块写一段 doc test。
  4. 审计 laew 现有代码注释质量：找出 5 处「Bad 注释」（机械翻译、过期信息、错误解释）并给出修复版本，讨论「注释负债」如何累积。

### BC10 技术写作的工具链与发布流水线
- **预期档位**: medium
- **考察维度**: 写作工具 + 自动化发布
- **对话脚本**:
  1. Markdown 写作工具对比：VS Code + Markdown All in One / Typora / Obsidian / iA Writer / MarkText / HackMD，编辑体验、所见即所得、协作能力差异。
  2. 静态站点生成器选型：Docusaurus（Meta）/ VitePress（Vue.js）/ Astro / Hugo / Jekyll / MkDocs，主题生态、MDX 支持、搜索、版本切换的对比。
  3. 内容发布的「CI/CD」：Git 提交 → Lint（markdownlint + textlint）→ 拼写检查（cspell）→ 死链扫描（lychee）→ 自动部署（Vercel/Cloudflare Pages/GitHub Pages）。
  4. 给 laew 的 docs/ 目录搭建一条文档自动化：每次 push 跑 markdownlint + cspell + lychee + mermaid 校验，产出覆盖率报告与 doc broken-link 看板。
