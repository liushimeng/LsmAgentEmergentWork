# 自动化测试提示词 — 测试自动化与质量工程（T01–T10）

> 使用说明见同目录 `README.md`。每条提示词在同一 Session 内按轮次顺序喂入。

## 维度说明

本维度考察 Agent 在**测试框架使用、测试策略设计、Mock 与桩、
测试驱动开发（TDD）、契约测试、混沌工程、测试覆盖率、
可视化测试、测试报告生成、质量门禁**等"测试工程"垂直领域中的实战表现，
与 E 维度（通用编码调试）互补：E 考察"写代码与修 bug"，
本维度考察"验证代码正确性与保障工程质量"。
所有主题都以"动手写测试代码或设计测试方案"为核心，强调测试工程实战能力。

---

### T01 单元测试框架实战：Rust 的 #[test] 与断言宏
- **预期档位**: medium
- **考察维度**: 测试框架 + 断言设计 + 边界覆盖
- **对话脚本**:
  1. 用 Rust 为一个"用户注册函数"编写单元测试：函数签名是 `fn register(email: &str, password: &str) -> Result<User, RegisterError>`，先列出需要覆盖的测试用例清单。
  2. 实现测试：覆盖正常注册、邮箱格式错误、密码过短、邮箱已存在四种场景，使用 `assert_eq!` / `assert_matches!` 宏。
  3. 加上参数化测试：用 `rstest` crate 的 `#[rstest]` + `#[case]` 宏，把上面的 4 个场景改成参数化形式。
  4. 讨论：单元测试的 FIRST 原则（Fast/Independent/Repeatable/Self-Validating/Timely）是什么？你的测试违反了哪一条？

### T02 Mock 与 Stub：用 mockall 隔离依赖
- **预期档位**: medium
- **考察维度**: Mock 框架 + 依赖隔离 + 行为验证
- **对话脚本**:
  1. 解释 Mock、Stub、Fake、Spy 四者的区别，各举一个适用场景。
  2. 用 Rust 的 `mockall` crate 为一个"发送邮件"的函数写测试：`EmailSender` trait 有一个 `send` 方法，业务函数依赖它，测试时 mock 掉。
  3. 验证行为：不仅验证返回值，还要验证 `send` 方法被调用了恰好一次（`times(1)`），且参数符合预期。
  4. 讨论：过度使用 Mock 的风险是什么？什么时候该用真实依赖（集成测试）而不是 Mock？

### T03 测试驱动开发（TDD）：红-绿-重构循环
- **预期档位**: medium
- **考察维度**: TDD 方法论 + 测试先行 + 小步迭代
- **对话脚本**:
  1. 解释 TDD 的"红-绿-重构"三步循环，为什么"先写测试"能改善设计？
  2. 用 TDD 实现一个"括号匹配"函数：先写失败的测试（红），再写最少代码让它通过（绿），最后重构。演示完整三轮。
  3. 加上新需求"支持多种括号类型（()[]{}）"，用 TDD 方式增量实现。
  4. 讨论：TDD 在哪类场景下效果最好（算法/业务逻辑/API），在哪类场景下成本过高（UI/数据库/并发）？

### T04 集成测试与测试夹具（Fixture）
- **预期档位**: medium
- **考察维度**: 集成测试 + 测试数据准备 + 环境搭建
- **对话脚本**:
  1. 单元测试和集成测试的边界在哪？为什么集成测试需要"测试夹具（Fixture）"？
  2. 为 laew 的 `provider add` 功能写一个集成测试：测试前创建一个临时 SQLite 数据库，测试后自动清理。用 Rust 的 `tempfile` crate 实现。
  3. 加上测试数据工厂（Test Data Builder 模式）：构建一个 `ProviderRecord::builder()` 让测试代码更简洁。
  4. 讨论：集成测试的"测试数据库"应该用内存 SQLite 还是临时文件？各自的优劣？

### T05 契约测试：服务间接口的兼容性保障
- **预期档位**: hard
- **考察维度**: 契约测试 + 消费者驱动 + 版本兼容
- **对话脚本**:
  1. 什么是契约测试（Contract Testing）？它和单元测试、集成测试、E2E 测试的关系是什么？
  2. 用 Pact（Rust 版 `pact_consumer` / `pact_provider`）实现一个最小契约测试：消费者（Agent 客户端）期望 Provider（LLM API）返回特定 JSON 结构。
  3. 模拟 Provider 端验证：用 `pact_provider` 验证真实 API 响应是否符合契约。
  4. 讨论：契约测试在微服务架构中的价值是什么？什么时候该用契约测试而不是 Mock？

### T06 混沌工程：主动注入故障
- **预期档位**: hard
- **考察维度**: 混沌工程 + 故障注入 + 系统韧性
- **对话脚本**:
  1. 什么是混沌工程？它和"故意搞破坏"有什么区别？解释"实验 vs 混乱"的关键差异。
  2. 设计一个针对 laew 的混沌实验：模拟 LLM API 返回 5xx 错误，观察系统的重试和降级行为。给出实验假设、爆炸半径、终止条件。
  3. 用 Rust 实现一个简单的故障注入代理：在本地起一个 HTTP 代理，按 30% 概率返回 503，其余请求转发到真实 API。
  4. 讨论：混沌工程在什么阶段引入合适（开发/预发/生产）？"在生产环境做混沌实验"需要哪些前提条件？

### T07 测试覆盖率：度量与提升策略
- **预期档位**: medium
- **考察维度**: 覆盖率工具 + 度量指标 + 提升方法
- **对话脚本**:
  1. 解释行覆盖率、分支覆盖率、条件覆盖率的区别，哪个最有价值？
  2. 用 `cargo-tarpaulin` 或 `cargo-llvm-cov` 为 laew 项目生成覆盖率报告，解读输出。
  3. 找出覆盖率最低的 3 个模块，分析原因（是死代码、还是难以测试的边界情况？）。
  4. 讨论：100% 覆盖率等于"没有 bug"吗？覆盖率的"边际收益递减"拐点通常在哪？

### T08 可视化测试与快照测试
- **预期档位**: medium
- **考察维度**: 快照测试 + UI 回归 + 视觉对比
- **对话脚本**:
  1. 什么是快照测试（Snapshot Testing）？它适合什么场景，不适合什么场景？
  2. 用 `insta` crate 为 laew 的"多 Agent 架构图生成"功能写快照测试：每次运行都和上一次输出对比，变化时人工确认。
  3. 讨论"快照膨胀"问题：当快照文件变得很大时，怎么维护？什么时候该用快照测试而不是精确断言？
  4. 如果要为 laew 的 TUI 做"视觉回归测试"，设计一个方案：截图 → 对比像素 → 标记差异。

### T09 测试报告与质量看板
- **预期档位**: medium
- **考察维度**: 报告生成 + 质量度量 + 可视化
- **对话脚本**:
  1. 一份好的测试报告应该包含哪些要素（通过率、失败原因、耗时趋势、覆盖率）？
  2. 用 Rust 实现一个最小测试报告生成器：解析 `cargo test` 的 JSON 输出，生成 HTML 报告。
  3. 加上趋势分析：对比最近 5 次测试的通过率和耗时，用 ASCII 折线图展示趋势。
  4. 讨论：质量看板（Quality Dashboard）在团队中的价值是什么？哪些指标最该放上看板？

### T10 质量门禁与 CI 流水线集成
- **预期档位**: hard
- **考察维度**: 质量门禁 + CI 集成 + 自动化决策
- **对话脚本**:
  1. 什么是质量门禁（Quality Gate）？它在 CI 流水线中起什么作用？
  2. 为 laew 设计一套质量门禁规则：单元测试通过率 ≥95%、覆盖率 ≥70%、clippy 无 warning、构建成功，任一不通过则 PR 不能合并。
  3. 用 GitHub Actions 实现这个门禁：写一个 workflow 文件，在 PR 时自动跑检查并报告结果。
  4. 讨论：质量门禁太严（阻碍交付）太松（形同虚设）怎么平衡？"门禁豁免"机制应该怎么设计？
