### DB01 长连接网关与心跳保活

- **预期档位**: medium~hard
- **考察维度**: 长连接生命周期 / 心跳设计 / 网关水平扩展
- **对话脚本**:
  1. IM 为什么不用 HTTP 轮询而用长连接：实时性（服务端主动推送）与资源消耗（轮询空转）的对比；WebSocket / TCP 自定义协议 / QUIC 三种长连接选型各自的适用场景。
  2. 心跳保活设计：NAT 超时（运营商 5~15 分钟回收空闲映射）决定心跳间隔；智能心跳（网络好拉长、弱网缩短）省流量；服务端怎么检测假死连接（连续 3 次心跳缺失踢下线）。
  3. 基于上面的心跳机制，讨论网关层水平扩展：100 万长连接怎么分摊——单机能撑多少连接（C10M 问题、epoll、内存每连接开销），连接状态（user→连接→网关节点）存哪（Redis）。
  4. 动手：用 Python asyncio 写一个 100 行的 WebSocket echo 服务，加 30 秒心跳超时踢人逻辑，用两个浏览器标签页验证。

### DB02 消息可靠投递：ACK、重传与去重

- **预期档位**: medium~hard
- **考察维度**: 可靠投递协议 / 超时重传 / 幂等去重
- **对话脚本**:
  1. 消息不能丢也不能重：TCP 只保证链路层可靠，应用层还要自己 ACK。设计一个最小可靠投递协议：client 发消息带 client_msg_id → server 入库后回 ACK → client 收到 ACK 前超时重发。
  2. 基于上面的协议，讨论重发必然导致重复——服务端用 client_msg_id 幂等去重（唯一索引）；服务端推给接收方同理（接收方 ACK + 本地按 msg_id 去重）；画出「发送方-服务端-接收方」三段 ACK 时序图。
  3. 边界场景：ACK 在回传路上丢了怎么办（发送方重发，服务端靠幂等识别）；用户杀进程导致 ACK 丢失（下次上线拉离线消息兜底，引出 DB04）。
  4. 动手：给 DB01 的 echo 服务加 client_msg_id + ACK + 3 秒重传逻辑，用 tcpkill 或手动断网模拟丢包，验证不丢不重。

### DB03 消息序号与会话内排序

- **预期档位**: medium
- **考察维度**: 序号生成 / 会话内有序 / 时钟问题
- **对话脚本**:
  1. 消息为什么需要时间戳之外的序号：两个用户同时发消息时间戳相同，服务器收到顺序才是「真相」；全局递增 seqid（Snowflake / DB 自增）vs 会话内递增 seqid 的差异。
  2. 会话内 seqid（每个会话一个递增序列）是 IM 主流：客户端按 seqid 排序渲染、按 seqid 断点续拉（「我本地到 seq=100，拉 100 之后的」）；讨论为什么不需要全局有序。
  3. 基于上面的 seqid 设计，讨论时钟问题：客户端本地时间不可信（用户改系统时间），所有排序必须以服务端分配的 seqid 为准，客户端时间只用于展示。
  4. 动手：用 SQLite 实现 seqid 分配器（`UPDATE counter SET v=v+1 WHERE session_id=? RETURNING v`），模拟 3 个会话并发发消息验证各自递增且互不干扰。

### DB04 离线消息与多端漫游

- **预期档位**: medium~hard
- **考察维度**: 离线拉取 / 多端同步 / 同步协议
- **对话脚本**:
  1. 用户手机关机 3 天，开机后要收到这 3 天的消息——离线消息两种模型：离线队列（消息存到「待投递队列」，上线全量推）vs  Timeline 拉取（消息存会话 timeline，上线按 seqid 差量拉）；后者为什么成为主流。
  2. 基于上面的拉取模型，讨论多端漫游：同一账号手机+平板+PC，每个端记录自己同步到的 seqid（同步位点），各端独立差量拉取；删除消息多端怎么一致（删除也是一条「同步指令」）。
  3. 同步位点与服务端 seqid 构成一个简单的同步协议：`sync(session_id, from_seq) -> messages[] + latest_seq`；讨论大差量（3 天 1 万条）怎么分页、压缩。
  4. 动手：在 DB03 的 SQLite 基础上实现 sync 接口——给每个设备存 sync_point，写个脚本模拟「端 A 发 5 条，端 B 上线拉取，端 C 再上线拉取」全流程。

### DB05 已读回执与未读数计算

- **预期档位**: medium
- **考察维度**: 已读模型 / 未读数一致性 / 群聊回执
- **对话脚本**:
  1. 单聊已读回执实现：接收方上报「已读到 seq=105」，发送方渲染「已读」标记；已读位点存服务端还是 P2P 透传，各自的隐私与可靠性权衡。
  2. 未读数计算：未读数 = 会话 latest_seq − 我的已读位点，不必逐条数；讨论未读数清零时机（进会话清零 vs 逐条已读），以及小红点角标的一致性维护。
  3. 群聊已读回执为什么难：500 人群每人一个已读位点，「已读 325 人」要聚合 500 个位点；微信的简化——群聊不做单条已读，只做「已读人数」快照；讨论存储与聚合成本。
  4. 动手：给 DB04 的模型加 read_point 表，实现「上报已读 → 计算对方视角未读数」的查询 SQL，模拟两个会话验证数字正确。

### DB06 群聊：写扩散与读扩散选型

- **预期档位**: medium~hard
- **考察维度**: 扩散模型 / 存储放大 / 大群优化
- **对话脚本**:
  1. 群消息两种投递模型：写扩散（消息写入每个成员的收件箱——读时直接读自己收件箱，微信模式）vs 读扩散（消息只存会话一份——读时按会话拉，钉钉/Slack 大群模式）；存储放大倍数与读放大倍数的对比。
  2. 基于上面的对比，讨论选型依据：群小且活跃 → 写扩散（读快）；群大（万人群）→ 读扩散（写只写一份，否则 1 条消息写 1 万次）；混合模式（单聊写扩散、大群读扩散）。
  3. 大群的附加优化：消息聚合下发（100ms 内 10 条合一个包）、不活跃成员不实时推（上线再拉）、@消息单独走强提醒通道。
  4. 动手：用 SQLite 模拟两种模型——50 人群发 100 条消息，统计写扩散的总行数 vs 读扩散的总行数，量化存储放大差异。

### DB07 消息存储与历史记录分页拉取

- **预期档位**: medium
- **考察维度**: 存储模型 / 分页游标 / 冷热分层
- **对话脚本**:
  1. 消息表设计：按什么分区（按会话 hash 分库分表）、单行存什么（msg_id / session_id / seq / sender / 类型 / 内容 / 时间）；为什么内容字段通常单独放（列表查询不加载大字段）。
  2. 历史分页拉取的游标设计：「向上翻」用 `WHERE seq < ? ORDER BY seq DESC LIMIT 20`，游标就是最小已加载 seq；讨论为什么不用 offset 分页（新消息插入导致 offset 漂移）。
  3. 冷热分层：3 个月内的热消息在 SSD 在线库，历史消息归档到对象存储；拉取跨越冷热边界时的「先查在线库，不足再查归档」合并逻辑。
  4. 动手：在 DB05 基础上实现 pull_history(session_id, before_seq, limit) 接口，造 200 条消息连续翻页验证不重不漏。

### DB08 消息撤回、编辑与内容安全

- **预期档位**: medium
- **考察维度**: 状态消息 / 内容审核 / 合规要求
- **对话脚本**:
  1. 撤回实现：撤回不是删除，是把消息标记为 revoked 并下发一条「撤回指令」让所有端更新渲染（显示「对方撤回了一条消息」）；讨论撤回时限（2 分钟）怎么在校验端做。
  2. 消息编辑与撤回的区别：编辑要保留历史版本吗（Slack 保留 edit history、微信不支持编辑）；编辑后的「已编辑」标记与审计需求。
  3. 内容安全：文本敏感词（AC 自动机多模匹配）、图片鉴黄（异步审核先放行后拦截 vs 同步审核延迟发送）、垃圾消息频控（同内容 1 分钟发 5 群触发拦截）；讨论审核误判的申诉与人工复审通道。
  4. 动手：给 DB07 的存储加 status 字段（normal/revoked/edited），实现撤回接口 + 同步指令广播，并用 AC 自动机（或简单关键词）加一道发送前敏感词拦截。

### DB09 端到端加密：Signal 协议简化实现

- **预期档位**: hard
- **考察维度**: E2EE / 密钥交换 / 前向保密
- **对话脚本**:
  1. E2EE 的目标：服务器存密文，只有通信双方能解密；先讲最小可行方案——双方用 X25519 做 ECDH 密钥交换得到共享密钥，AES-GCM 加密消息；服务器只能看到收发关系（元数据）看不到内容。
  2. 前向保密（Forward Secrecy）：长期使用同一密钥，泄露一次全部历史遭殃；Signal 的双棘轮（Double Ratchet）——每发一条消息密钥「棘轮」前进一步，旧密钥立即销毁；用对称棘轮（KDF 链）讲清基本原理。
  3. 基于上面的棘轮，讨论乱序与离线难题：消息乱序到达怎么解密（每消息带序号 + 暂存跳过的链密钥）、离线消息怎么交换初始密钥（服务器预存一次性预密钥 bundle）。
  4. 动手：用 Python cryptography 库实现简化版——X25519 交换 + HKDF 派生消息密钥 + AES-GCM 加解密，模拟 A 发 3 条消息（中间乱序到达）B 全部解出。
