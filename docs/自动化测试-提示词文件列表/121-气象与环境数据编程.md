### DM01 气象数据格式总览：GRIB2 / BUFR / NetCDF / 站点文本

- **预期档位**: simple~medium
- **考察维度**: 格式选型 / 自描述数据 / 开放数据入口
- **对话脚本**:
  1. 气象数据四大格式各管一段：GRIB2（格点预报/再分析，紧凑二进制）、BUFR（观测报文，站点+垂直廓线）、NetCDF（科学数组，自描述+多维）、CSV/文本（台站日值，人读友好）；按"格点 vs 站点、预报 vs 观测、体积 vs 可读性"三轴给四者定位。
  2. 针对上面的定位，拆"自描述"的含义：GRIB2 头部把要素代码（如 2t = 2 米气温）、层次（地面/850hPa）、预报时效（+24h）、网格定义全编进码表（Code Table 编号体系）；解释为什么"同一个文件里 500 条消息、每条一个时效一片区域"是多消息设计的由来。
  3. 基于上面的格式地图，盘点开放数据入口：NOAA GFS（全球预报，逐 6h）、ERA5 再分析（历史"最优回顾"）、中国气象数据网台站日值、Open-Meteo 免费 API；说明"再分析"与"预报"的数据质量语义差别（为什么算历史统计要用再分析而不是存档的旧预报）。
  4. 动手：写一个格式嗅探器 `wx_sniff <file>`：读文件头魔数判别 GRIB2/NetCDF/BUFR/CSV，GRIB2 数出消息条数，NetCDF 用 ncdump 头信息提取维度与变量清单，CSV 自动猜测分隔符与表头；对三个真实样例文件输出统一的结构摘要 JSON。

### DM02 GRIB2 解析实战：eccodes 与网格模板

- **预期档位**: medium~hard
- **考察维度**: 二进制解析 / 码表语义 / 工具链
- **对话脚本**:
  1. GRIB2 的分节结构：Indicator(魔数+总长) → Identification(中心/日期) → Grid Definition(网格模板) → Product Definition(要素+层次+时效) → Data Representation(打包方式) → Data(压缩数据) → End；解释"模板（Template）"机制——网格模板 3.0（经纬格点）与 3.1（旋转经纬）等的编号分支。
  2. 针对上面的结构，用 eccodes 的消息迭代模型解析：`codes_grib_new_from_file` 逐消息读、`codes_get` 按键取 `shortName`/`validityTime`/`level`、`codes_get_array('values')` 取数值数组与 missing 值标记；说明 GRIB 的"缺测"用位图节+特定填充值的实现。
  3. 基于上面的键值访问，做提取管道："从 GFS 文件抽出 2 米温度 +24h 时效、按经纬度索引取出北京格点值"；处理三个现实坑：经度从 0-360 起（要减 360 换 -180-180）、位势与气温的单位（K→℃）、扫描模式决定数组是行优先还是蛇形。
  4. 动手：实现 `grib2csv`：输入 GFS GRIB2，输出 `date,step,lat,lon,element,value` 长表 CSV（只取用户指定的要素与时效列表、bbox 裁剪）；对一份 500KB 样例跑通后统计解包耗时，并讨论 eccodes 绑定（Python eccodes / Rust 的 eccodes-sys）在分发型工具里的部署代价。

### DM03 站点时序与缺测治理

- **预期档位**: medium
- **考察维度**: 时序清洗 / 缺测插补 / 聚合规则
- **对话脚本**:
  1. 台站数据的第一课是缺测：仪器故障、报文丢失、迁站断档；写出缺测的三种形态——孤立缺（单点）、连续缺（一段）、边界缺（序列开头结尾），说明它们分别适用什么插补策略（线性内插/日气候值平移/放弃）。
  2. 针对上面的形态，定聚合规则：逐时→日值的"最多缺 3 小时且无连续 2 小时缺才算有效日值"这类业务约束（气象行业标准惯例），日平均用 02/08/14/20 四次定时 vs 24 时平均的差异；说明为什么"先定有效规则再聚合"能避免脏均值污染下游。
  3. 基于上面的规则，处理单位与符号坑：降水 0.1mm 编码（R01 报文放大 10 倍）、微量降水（"T"/trace：有降水不足 0.05mm）、气温放十倍整数存储；写单位归一化层（入口统一转标准单位：℃/mm/m/s），出口再按需转换。
  4. 动手：实现 `station_qc.py`：读台站 CSV（含缺测标记 999999/空串）→ 缺测分类统计 → 按规则插补或置 NaN → 输出日值表与质量报告（每站缺测率/插补率/无效日数）；对一份人工注入三类缺测的样例验证分类正确。

### DM04 气候统计：气候态、距平与极端指数

- **预期档位**: medium
- **考察维度**: 气候态基线 / 距平分析 / 极端阈值
- **对话脚本**:
  1. "今年偏热 1.3℃"的算法基础是气候态（climatology）：以 1991-2020 三十年窗口内逐日（或逐月）均值/方差为基线；解释为什么 WMO 每十年滚动更新标准气候态基线，以及"拿 1951-1980 基线说话"与"拿 1991-2020 基线说话"结论观感差异的原因。
  2. 针对上面的基线，算距平（anomaly）：当日值 − 同日气候态 = 距平；处理两个细节——年内样本用前后各 15 天滑动窗增稳（避免单日样本太少）、闰年 2 月 29 日的归并策略；距平序列为什么能直接做趋势分析（滤掉了季节周期）。
  3. 基于上面的距平，定义极端事件指数：百分位阈值法（日最高温 > 第 95 百分位即"热日"）、持续热浪指数（连续 ≥3 个热日）、标准化降水指数 SPI 的简化思路（月降水拟合 Γ 分布后取标准正态分位数）；说明 SPI 的"干旱等级表"（-1.0 轻旱 / -1.5 中旱 / -2.0 重旱）如何从指数映射。
  4. 动手：用任一城市 30 年日值数据实现 `climate_report`：输出年气温距平折线（附趋势线斜率：℃/10年）、热日数逐年柱状数据、SPI-3 月序列；交叉验证距平趋势与逐年均值趋势的一致性，并解释二者什么时候会背离（方差变化时）。

### DM05 台风路径数据处理：BEST TRACK 与影响分析

- **预期档位**: medium
- **考察维度**: 专有格式 / 路径插值 / 地理计算
- **对话脚本**:
  1. 台风"最佳路径"（BEST TRACK）数据：事后订正的逐 6h 中心位置、强度（中心气压/近中心最大风速）、强度分级（热带低压/台风/强台风/超强台风）；解析 CMA 与 JTWC 两种文本格式的字段差异（分隔符、风速单位 knot vs m/s、时间制式）。
  2. 针对上面的解析，做路径工程：6h 离散点 → 线性插值到 1h（经纬度小段可近似线性）、七级风圈半径缓冲区（buffer）生成、移速计算（相邻点大圆距离/时差）；解释为什么缓冲区要用米制投影距离而不是纯经纬度差。
  3. 基于上面的路径，做影响分析：判断某城市"是否在台风 100km 影响圈内"的逐小时命中序列、首次/最后一次进入时间、最近距离与对应强度；把结果导出 GeoJSON（LineString 路径 + Point 城市 + Polygon 圈），说明与通用 GIS 工具链（CR 维）的衔接点。
  4. 动手：实现 `typhoon_track.py`：读 CMA 年鉴文本 → 标准化记录结构 → 对某台风输出逐小时插值路径表、某指定城市的影响摘要（进出时间/最近距离/当时强度）；对两个真实台风验证插值平滑度与圈命中逻辑，输出可直接画图的 GeoJSON。

### DM06 雷达回波与定量降水估计

- **预期档位**: medium~hard
- **考察维度**: 雷达数据模型 / Z-R 关系 / 坐标处理
- **对话脚本**:
  1. 天气雷达怎么"看见"雨：以固定仰角发射脉冲，接收反射率因子 Z（mm⁶/m³），一次体扫（volume scan）含多个仰角层；解释极坐标存储模型（方位角 360 × 距离库 km × 层数）与常见的 CAPPI（等高面）合成概念。
  2. 针对上面的模型，讲 dBZ 与 Z-R 关系：Z 量级跨度 1~10⁶ 所以工程上用 dBZ = 10·log10(Z)；经典马歇尔-帕尔默公式 Z = 200·R^1.6 反解雨强 R；说明同一 dBZ 在层状云（稳雨）与对流云（暴雨）下的误差来源，以及为什么业务上要本地化订正系数。
  3. 基于上面的公式，做格点合成：极坐标（方位/距离）→ 经纬度格点的重采样（最近邻 vs 双线性）、多层拼图取最大值/最接近目标高度层的策略；处理两个坑——距离越远波束越高（1.5° 仰角在 200km 处已探到 4km+ 高空，不能代表地面）、遮挡（山体挡波束造成固定扇形弱区）。
  4. 动手：实现 `radar_qpe`：输入一份模拟体扫（极坐标 dBZ 数组 + 站点坐标），输出 1km 网格雨强图与区域 1 小时估测雨量（假设回波稳定）；对 dBZ=45 的强回波单点验证 R 值量级（约 50mm/h 级），并做"忽略波束高度"与"高度衰减订正"两版对比说明误差量级。

### DM07 空气质量 AQI 计算：从浓度到指数

- **预期档位**: simple~medium
- **考察维度**: 分段线性 / 业务规则 / 逐时 vs 日值
- **对话脚本**:
  1. AQI 不是浓度是指数：六项污染物（PM2.5/PM10/SO₂/NO₂/O₃/CO）各自浓度经**分段线性插值**得到 IAQI，取最大者为 AQI、对应污染物为首要污染物；解释为什么用"分段"（各级别斜率不同）而不是全局线性（高浓度区间必须放大区分度）。
  2. 针对上面的算法，写出 IAQI 公式：`IAQI = (I_hi − I_lo)/(C_hi − C_lo) × (C − C_lo) + I_lo`，注意浓度限值表按日均与小时均两套、O₃ 还有 8 小时滑动均值；说明"浓度超表上限时 IAQI 封顶计算"的惯例。
  3. 基于上面的公式，处理日值规则：PM2.5 日均要求至少 20 个有效小时浓度、O₃ 日最大 8 小时滑动（每日滚动算 17 个窗口取最大）的取整规则；讨论逐时 AQI 与日 AQI 数值差异的解读陷阱（"小时 AQI 500 日 AQI 200"意味着短时脉冲污染）。
  4. 动手：实现 `aqi.py`：输入小时浓度 CSV，输出逐时 AQI + 首要污染物 + 级别中文名（优/良/轻度…严重），再按有效规则算日值；构造边界用例（恰好等于限值、超上限封顶、有效小时数不足）断言输出，并跑一份真实城市历史数据统计全年各级别天数。

### DM08 预报检验：MAE、RMSE 与分级技巧评分

- **预期档位**: medium~hard
- **考察维度**: 检验体系 / 事件分类 / 技巧评分
- **对话脚本**:
  1. 预报准不准要有数学答案：连续量检验三件套 MAE（平均绝对误差）/ RMSE（放大极端误差惩罚）/ Bias（系统性偏冷偏暖）；解释为什么"温度预报 bias = -1℃"比"MAE = 2℃"更能指导改进方向（先修系统偏差再修离散度）。
  2. 针对上面的连续量，进入事件检验：预报"明天有雨"（≥0.1mm）与实况构成 2×2 列联表（命中/空报/漏报/正确否定）；推出 POD（命中率）、FAR（空报率）、TS 评分（threat score，`= 命中/(命中+空报+漏报)`）；解释 TS 为什么是降水检验的核心指标而不用准确率（"无雨"气候概率太高会虚高）。
  3. 基于上面的列联表，讲技巧评分与分级检验：TS 相对气候概率的技巧评分、分级检验（小雨/中雨/大雨分别算 TS——小雨高 TS 大雨低 TS 是常态）、邻域法（容许 10km 位移误差的尺度化检验）解决"预报对了雨但位置偏 20km 被判全错"的问题。
  4. 动手：实现 `fcst_verify.py`：输入预报与实况的站点/格点配对文件，输出连续量报告（MAE/RMSE/Bias 分要素）与分级 TS 表（雨量三档 + 温度 ±2℃ 命中率）；构造"完美预报/全错/气候基准（一律报无雨）"三组对照数据验证各指标的方向性正确。

### DM09 多源天气 API 聚合：缓存、限流与单位陷阱

- **预期档位**: medium
- **考察维度**: API 集成 / 数据归一 / 缓存策略
- **对话脚本**:
  1. 单一数据源有单点风险，聚合 Open-Meteo / OpenWeatherMap / 和风天气三家：设计聚合层架构——统一 `Observation`/`Forecast` 内部模型 + 各源 adapter + 择优/合并策略（主源失败切备源、同源同字段不一致时的优先级）；说明为什么不直接透传各家的 JSON 结构。
  2. 针对上面的架构，处理字段归一的地狱细节：温度 ℃/℉/K、风速 m/s / km/h / mph / knot、时间戳 UTC vs 当地时区 vs 毫秒、天气现象码各家自定义（晴/多云/雨的编码表完全不同）——建一张映射表并留 `raw` 字段存原始值以便审计。
  3. 基于上面的归一层，加缓存与限流：API 配额宝贵，预报数据本身 15 分钟级更新——设计 TTL 缓存（当前天气 10min / 逐日预报 6h）与请求合并（同城市并发请求只打一次上游）；再讲退避重试与"上游 5xx 时用过期缓存 + stale 标记"的降级策略。
  4. 动手：实现 `wxproxy`：一个本地 HTTP 聚合服务（或 CLI），端点 `/weather?city=xxx` 返回归一化 JSON（含数据源、更新时间、stale 标记）；写并发压测脚本验证请求合并生效（上游计数器只有 1 次），并注入"主源 500"场景验证备源切换与 stale 降级链路。

### DM10 气象可视化：站点填图、风羽与时序面板

- **预期档位**: medium
- **考察维度**: 专业图形语法 / CLI 出图 / 视觉编码
- **对话脚本**:
  1. 气象图有自己的视觉语法：站点填图（station plot）——一个圆圈 + 周围固定方位放气温/露点/气压/天气符号，风向杆从站心指向风的来向、羽线数量表风速；解释这套"百年电报码遗产"为什么至今没被点/色块完全替代（单图信息密度极高）。
  2. 针对上面的语法，实现风羽（wind barb）：风速按 50/10/5 knot 三档符号组合（旗/长杆/短杆）映射，风向决定旋转角；在 SVG 或 canvas 坐标系里写出绘制函数与图例，说明北半球"羽在杆左侧"的约定。
  3. 基于上面的元素，做色斑图与时序：气温/降水的分级填色（色带必须与级别语义绑定：AQI 级别色不可乱序）、时序面板的"距平着色"（距平为正暖色为负冷色）；讨论无障碍问题（红绿配色对色盲用户失效，改用蓝橙或加纹理）。
  4. 动手：实现 `wxplot`：输入站点观测 CSV，输出一张 SVG 站点填图（含气温/风羽/天气符号与图例、比例尺、标题时间），另输出该站 30 天温度时序 SVG（含气候态参考带：气候态 ±1σ 的半透明带）；不依赖重型绘图库、手写 SVG 生成，验证浏览器打开渲染正确。
