### BN01 为什么 0.1 加 0.2 不等于 0.3
- **预期档位**: simple
- **考察维度**: IEEE 754 浮点表示 + 工程应对
- **对话脚本**:
  1. 解释 IEEE 754 双精度浮点数为何无法精确表示 0.1 和 0.2，用二进制小数展开 `0.1 = 0.0001100110011...`（无限循环）说明存储时被截断到 52 位尾数。
  2. 那为什么 0.5 + 0.25 能精确等于 0.75？引出「能精确表示的小数 = 分母为 2 的幂次的有理数」的判定规则，列出 0.1/0.2/0.3/0.7 这些二进制无法精确的常见小数。
  3. 实际工程里怎么应对：金融系统为什么用定点数或整数（以「分」为单位）、科学计算怎么控制误差累积、UI 展示时 `Math.abs(a-b) < 1e-9` 的容差比较。
  4. 给 laew 的 Token 计量模块提个建议：累计 `input_tokens + output_tokens` 做总额判断时，要避免浮点累加误差，建议用 `u64` 或 `Decimal` 类型。

### BN02 为什么 UTF-8 要这样设计
- **预期档位**: simple
- **考察维度**: 字符编码历史 + UTF-8 变长设计
- **对话脚本**:
  1. ASCII（7 bit，128 字符）为何无法覆盖欧洲重音字符和东亚象形文字？Latin-1 / GBK / Big5 等「扩展编码」的乱码根源（同字节不同解码）。
  2. UTF-8 变长编码的精妙之处：1-4 字节、首字节前缀模式（`0xxxxxxx` / `110xxxxx 10xxxxxx` / `1110xxxx 10xxxxxx 10xxxxxx` / `11110xxx 10xxxxxx 10xxxxxx 10xxxxxx`）、自同步（任意位置向后扫描必能找到字符边界）、与 ASCII 兼容。
  3. 为什么不用 UTF-16 当默认？UTF-16 对 BMP 字符固定 2 字节但需要 BOM、emoji 和生僻字需要 4 字节（surrogate pair），UTF-8 在 ASCII 为主的英文场景更省空间。
  4. laew 的 TUI 渲染英文文案时用 ASCII 直接通过，遇到中文/emoji 时按 UTF-8 多字节切片；用同样的思路审视 Provider API 返回的多语言 JSON，按 `str::chars()` 而非按字节索引。

### BN03 为什么处理时间这么难
- **预期档位**: medium
- **考察维度**: 时区 / 夏令时 / 闰秒 / 历法
- **对话脚本**:
  1. 同一时刻不同时区显示不同：UTC / 本地时间 / Unix 时间戳（自 1970-01-01 00:00:00 UTC 起的秒数）三者的关系与转换，给一段 Python/Rust 把本地时间转 UTC 的代码。
  2. 夏令时（DST）的坑：纽约时区一年有 23/24/25 小时不等的「某一天」，跨区会议、cron 定时任务、机票预订系统历史上踩过的真实 bug。
  3. 闰秒为什么被引入又要废除：原子时与地球自转的偏差、2015 年闰秒导致 Cloudflare DNS 故障、Google 「leap smear」平滑抹除 1 秒的工程实践。
  4. laew 的 `SessionContext` 摘要写入 `session_memory` 表时，建议全部用 UTC + ISO 8601（`2026-09-10T12:34:56Z`）存储，展示时再按用户时区转换，避免跨时区用户的会话历史错位。

### BN04 大小端从哪里来，什么时候会咬人
- **预期档位**: simple
- **考察维度**: 字节序 + 网络协议与二进制文件
- **对话脚本**:
  1. 大端（Big-Endian）vs 小端（Little-Endian）：大端高位字节在前（人类阅读顺序）、小端低位字节在前（x86/ARM 默认），用 `0x12345678` 在内存中 `12 34 56 78` vs `78 56 34 12` 的对比说明。
  2. 网络字节序为什么统一为 big-endian（RFC 1700）：跨平台通信时用 `htonl/htons` 转换，IP 头、TCP 头的端口号都遵循大端；给一段 Rust 用 `to_be_bytes()` 转换的代码。
  3. 真实咬人案例：BMP 图片头读取忘换字节序导致图像红蓝翻转、PE 可执行文件解析、Magic Number 判断（`PNG: 89 50 4E 47` 大端 vs `GIF: 47 49 46 38` 看起来都是 magic 但顺序敏感）。
  4. laew 读取 SQLite 文件或外部 LLM 协议返回的多字节整数（tool_call id、token count）时，统一用 `u32::from_be_bytes` / `u64::from_be_bytes` 解析，避免在跨架构（x86 ↔ ARM Mac）开发时遇到神秘数据错位。

### BN05 随机数为什么不随机，UUID 会重复吗
- **预期档位**: simple
- **考察维度**: PRNG / 真随机 / 碰撞概率
- **对话脚本**:
  1. 计算机为什么无法「真随机」：`Math.random()` / `rand()` 都是伪随机（PRNG，线性同余 / Mersenne Twister），给定种子序列完全可预测；对比 `/dev/urandom`（Linux 内核熵池）、`getrandom()` 系统调用、`Intel RDRAND` 指令的随机性来源。
  2. UUID v4 的随机性保障：122 bit 随机空间，约 5.3 × 10^36 种可能，「生日悖论」下生成 2^61 个才有 50% 碰撞概率（约 23 亿亿），但 v1/v2 基于时间戳的 UUID 在多机器同时生成时可能撞车。
  3. 安全敏感场景为什么不能用 UUID：会话 token、密码重置链接必须用密码学安全 RNG（`crypto/random_bytes` / `rand::rngs::OsRng`），避免被预测。
  4. laew 的 Session ID 用什么生成？建议改成 `Uuid::new_v4()` + `OsRng` 双重保险，并在生成后立刻写入 SQLite 持久化（防止进程崩溃后 ID 复用）。

### BN06 为什么排序需要「稳定」
- **预期档位**: simple
- **考察维度**: 排序稳定性 + 多级排序
- **对话脚本**:
  1. 排序稳定性的定义：相等键的元素在排序后保持原相对顺序。举例学生列表按成绩排序后，成绩相同的还按原本的名字顺序，那就是稳定排序。
  2. 常见排序算法的对比表：冒泡/插入/归并是稳定（O(n²)/O(n log n)），快排/堆排/希尔是不稳定；为什么数据库和编程语言标准库的 `sort` 默认用 Timsort（稳定 + 实际最快）。
  3. 多级排序的优雅实现：先按部门排序、再按薪资排序时，稳定的二级排序保留一级排序结果；如果用不稳定排序，要么一次写复合键（部门 × 1e9 + 薪资），要么两次排序但顺序相反。
  4. laew 的 TUI 命令历史展示按「时间倒序」排列时，相同时间的命令应保持输入顺序，建议用 Rust 的 `slice::sort_by_key` 配合稳定比较器。

### BN07 为什么数组下标从 0 开始
- **预期档位**: simple
- **考察维度**: 索引历史 + 偏移量语义
- **对话脚本**:
  1. C 语言和后续语言的 `a[i]` 等价于 `*(a + i)`：从 0 开始是「偏移量」语义（首元素相对首地址偏移 0）；从 1 开始则要么浪费一个存储单元，要么每次计算 `*(a + i - 1)` 多减一次。
  2. Fortran / MATLAB / Lua / R 等从 1 开始的语言：数学公式直接对齐（矩阵 A[i][j]、第 i 个元素）、但内存模型和指针转换更复杂；Julia 官方论文论证了为何选 1-based。
  3. 边界检查的 off-by-one（差一错误）：`<` vs `<=` 差一个循环次数、数组长度 `n` 时合法下标 `[0, n)` vs `[1, n]`、二分查找易错点（mid = (left + right) / 2 vs left + (right-left)/2 防溢出）。
  4. laew 的 TUI Frame 在计算光标位置、字符宽度累加、Tab 切换索引时，统一用半开区间 `[0, n)` 表达，避开 1-based 的边界换算陷阱。

### BN08 空指针、null 与 Option：十亿美元的错误
- **预期档位**: medium
- **考察维度**: null 引用危害 + 类型系统应对
- **对话脚本**:
  1. Tony Hoare 1965 年发明的 null 引用的自白：「十亿美元的错误」。Java/Python/JS 的 `null` / `None` / `undefined` 在未检查时导致 NullPointerException、AttributeError、TypeError，是无数线上事故的根源。
  2. 类型系统的应对：Rust 的 `Option<T>`（编译期强制 `match`）、Haskell 的 `Maybe`（Monad）、Kotlin 的可空类型 `String?` vs `String`（编译期区分），对比 C++17 `std::optional<T>`、Python `Optional[Type]` 注解但运行时仍可能 None。
  3. 防御性编程三件套：默认值（empty string / 0 / 空对象）、Null Object Pattern（`User.anonymous()`）、异常 vs 返回值的语言哲学分歧（Java checked exception、Go `err != nil`、Rust `Result<T, E>`）。
  4. laew 的 LlmClient 调用结果用 `Result<Response, AgentError>` 返回，避免到处 `if response != null` 检查；Provider 列表查找时用 `Option<&Provider>` 显式表达「可能不存在」，杜绝 NPE。

### BN09 为什么删除文件很快，磁盘空间却没变
- **预期档位**: simple
- **考察维度**: 文件系统 unlink + 块释放时机
- **对话脚本**:
  1. `rm file` 只是删了目录项（inode 引用计数 -1），实际数据块在引用计数归零前不会被回收；「正在写入的日志文件被删除但 `du -sh` 看不到释放」就是这个原因（写入进程还持有 fd）。
  2. SSD 的 TRIM / 磁盘块回收：机械硬盘删除后数据其实还在（可恢复），SSD 需要主动 TRIM 让控制器擦除块，否则未来写入会先擦后写速度下降。
  3. 大文件删除 vs 大量小文件删除：ext4 单个大目录 `rm -rf` 可能慢在 dentry 失效上，XFS / Btrfs 表现不同；`rsync --delete` 先重命名再删除避免 race condition。
  4. laew 的 DebugReport 写到 `DebugReport/debug_report_*.md`（已 gitignore），删除旧报告时建议用 `truncate -s 0` 或 `mv` 到回收目录而非直接 `rm`，避免误删后无法追溯；同时保留最近 30 天的报告做兜底。

### BN10 为什么「在我机器上能跑」
- **预期档位**: medium
- **考察维度**: 环境差异 + 容器化与可复现构建
- **对话脚本**:
  1. 经典「在我机器上能跑」的原因清单：OS 版本（glibc 2.31 vs 2.35）、CPU 架构（x86 vs ARM）、Python/Rust/Node 版本（不同 ABI）、时区与 locale（中文 vs UTF-8）、PATH 环境变量、依赖版本（libssl 1.1 vs 3.0）、文件路径分隔符、文件权限（root vs 普通用户）。
  2. 工程化应对三板斧：Docker 镜像（`FROM rust:1.78-slim` 锁定 glibc + CPU）、版本锁文件（`Cargo.lock` / `package-lock.json` / `poetry.lock` 必须入库）、CI 多环境测试矩阵（Ubuntu/macOS/Windows × x86/ARM）。
  3. Nix / Guix 的可复现哲学：纯函数式包管理、每次构建产出位级别相同的二进制；与 Docker 的「以镜像为单位」的区别。
  4. laew 作为发布到根目录的 Rust CLI，建议在 CI 中至少跑 `cargo test` × `cargo build --release` × `./laew --version` 三步，并附上 `rebuild_restart_app.sh` 脚本和具体 `rustc --version` 输出，便于跨机器排查「我这里编出来不一样」的问题。
