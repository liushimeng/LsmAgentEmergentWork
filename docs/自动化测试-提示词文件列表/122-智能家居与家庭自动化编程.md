### DN01 Home Assistant 架构入门：实体、状态与服务

- **预期档位**: simple~medium
- **考察维度**: 领域模型 / 配置体系 / 集成生态
- **对话脚本**:
  1. Home Assistant 的核心抽象是三层：**集成**（integration，对接某个品牌/协议，如小米米家、Zigbee）产出**实体**（entity，如 `light.desk`、`sensor.temperature`），实体持有**状态**（state + 属性）并接受**服务**调用（`light.turn_on`）；用"传感器实体 vs 开关实体 vs 场景实体"解释实体域（domain）划分。
  2. 针对上面的模型，讲配置体系演进：从"一个大 YAML"到"UI 为主 + YAML 自动化可选"——`configuration.yaml` 还管什么（默认启用项/加载的集成）、`automations.yaml` 为什么可以被 UI 编辑器读写（受控 YAML 格式）、`packages` 拆分大型配置的组织方式。
  3. 基于上面的配置，跑通第一条链路：装好 HA → 添加集成发现设备 → 在开发者工具里 `light.turn_on` 手动调服务 → 观察 `light.desk` 状态变化事件；解释开发者工具（Services/States/Template）为什么是调试自动化前必须熟悉的三个面板。
  4. 动手：用 REST API 或 WebSocket API 写一个 20 行的 CLI 小灯控制脚本（读状态/开/关/调亮度），并订阅一条状态变更事件流打印出来；说明这个 API 边界为什么意味着"HA 就是家里的一个可编程操作系统"。

### DN02 Zigbee 网络与 Zigbee2MQTT：从配对到路由

- **预期档位**: medium
- **考察维度**: Zigbee 拓扑 / Z2M 桥接 / 配对排障
- **对话脚本**:
  1. Zigbee 是 2.4GHz（也有 868/915MHz）自组网网状协议：三类角色——协调器（coordinator，全网唯一，插在 HA 主机上）、路由器（router，常供电设备如插座，负责中继）、终端（end device，电池传感器，省电但不能中继）；解释"买一个 Zigbee 插座当路由"为什么常常比买信号放大器更有效。
  2. 针对上面的拓扑，搭 Zigbee2MQTT 桥：协调器固件选择（USB 网关的常见坑）、`configuration.yml` 三要素（串口/permalink、MQTT 基础设施、前端口）、`permit_join` 配对窗口的安防意义（用完即关，防止邻居设备入网）。
  3. 基于上面的桥接，理解数据流：Z2M 把设备消息翻译成 MQTT 主题（`zigbee2mqtt/客厅温度` 的 state JSON 与 `set` 命令主题）；解释 `friendly_name` 的改名级联（改名后主题跟着变，历史要迁移）、`homeassistant` 发现模式如何让 Z2M 设备自动出现在 HA 里。
  4. 动手：写一个 MQTT 订阅诊断工具：列出全网设备与最后消息时间、按消息间隔找出"疑似离线"传感器、dump 指定设备的完整 state JSON（电量/链路质量 LQI/最后_seen）；用 `mosquitto_sub`/`pub` 手动命令一对开关消息验证链路理解无误。

### DN03 自动化编排：触发器、条件与动作的工程化

- **预期档位**: medium~hard
- **考察维度**: 自动化三段式 / 模板变量 / 复杂度治理
- **对话脚本**:
  1. HA 自动化的三段式语法：**触发器**（trigger：什么事件发生——状态变化/时间/太阳高度/MQTT 消息）+ **条件**（condition：现在适不适合做——在家状态/时段/另一盏灯已开）+ **动作**（action：做什么——调服务/等 5 分钟/发通知）；用"日落开灯但仅当有人在家"写第一条例子，说明触发与条件的本质区别（前者是"闹钟"后者是"安检"）。
  2. 针对上面的语法，进模板（Jinja2）：`{{ states('sensor.lux') | int < 100 }}` 的条件模板、动作里 `{{ trigger.to_state.state }}` 取触发上下文、`trigger.entity_id` 判断来源；讨论模板的三重价值（跨实体联动/通知内容拼接/避免复制多份自动化）与风险（模板报错时自动化静默失败）。
  3. 基于上面的能力，治理自动化复杂度：`mode` 四态（single 默认/ restart 重新触发就打断上次/ queued 排队/ parallel 并行）解决"自动挡风被连续触发"的重入问题；自动化分组（按房间/按用途命名 `light_客厅_*`）、`id` 字段与版本化备份的关联。
  4. 动手：实现三条例子并互相配合——①日落+低照度+在家 → 开客厅灯；②门开 30 秒未关 → 通知；③"离家模式"一条自动化调用 `script` 关全屋灯并锁定场景；用开发者工具手动注入状态变更逐条触发验证，并故意制造"30 秒内门开又关"验证 `mode: restart` 行为。

### DN04 传感器数据治理：可用性、去抖与状态机建模

- **预期档位**: medium
- **考察维度**: 数据质量 / 去抖策略 / 状态语义
- **对话脚本**:
  1. 廉价传感器三宗罪：跳变（0.1s 内从 20℃ 跳到 30℃ 又回来）、漂移（常年轻微偏移）、失联（电池耗尽前发出最后的垃圾值）；解释为什么"直接在自动化里用裸传感器数值"是脆弱根源——应该先经过一层治理实体。
  2. 针对上面的三宗罪，上治理工具：`sensor` 的统计特性（`statistics` 平台给 mean/min/max）、template sensor 里加时间窗滤波（连续 N 次读数一致才更新）、`availability` 模板把心跳超时置 unavailable——说明 unavailable/unknown/0 三个状态的语义差异（设备不在 vs 没值 vs 真的是零）。
  3. 基于上面的治理，把"数值"升级为"状态机"：人体传感器原始是 1/0，但业务需要"房间有人/无人"——用迟滞（hysteresis）与最小持续时间建模（连续 5 分钟无活动才算无人）；讨论传感器语义化（从 `motion: on` 到 `occupancy: occupied`）对上层自动化的解耦价值。
  4. 动手：为一个温湿度传感器建治理管道：原始实体 → 滑动均值 template sensor → 可用性模板（10 分钟无更新置 unavailable）→ 传感器"等级"派生实体（舒适/偏热/偏冷迟滞判定）；注入跳变与失联两组数据验证治理前后自动化触发行为的差异。

### DN05 能源监控与统计：从功率到月度电费

- **预期档位**: medium
- **考察维度**: 能量计量 / 长期统计 / 报表生成
- **对话脚本**:
  1. 能源监控的三个层次：瞬时功率（W，设备实时上报）→ 累计电量（kWh，功率对时间的积分或电表直读）→ 电费（电量 × 费率）；解释"功率传感器必须做时间积分才得到电量"以及 HA `integration` 平台（`left`/`trapezoidal` 方法）或 Riemann sum 集成的用法。
  2. 针对上面的积分，讲长期统计（long-term statistics）：HA 对带 `state_class: measurement`/`total_increasing` 的传感器每 5 分钟落库汇总（min/max/mean）；说明 `total_increasing` 与电表读数回卷/重置的处理，以及为什么"把电表当 measurement 存"会让能耗面板算错。
  3. 基于上面的统计，做费率与账单：国内阶梯电价/峰谷电价建模（时段映射函数 + 阶梯累计）、月度报表（按设备/按时段分组的电量与费用）；讨论无费率传感器时的估算策略（功率×时间的误差累积）。
  4. 动手：搭一个最小能源面板：智能插座（功率 W）→ 积分出日/月 kWh → 阶梯+峰谷费率函数算电费 → Lovelace 能源仪表盘配置；回灌一周历史数据验证面板数字与手工对账一致（误差 <1%），并输出"哪个时段哪个设备最费电"的月度 Markdown 报告。

### DN06 本地优先语音助手：链路、延迟与隐私

- **预期档位**: medium~hard
- **考察维度**: 语音链路集成 / 端侧延迟 / 隐私边界
- **对话脚本**:
  1. 家庭语音助手的完整链路：唤醒词（KWS）→ 流式 ASR → 意图解析（NLU 或 LLM）→ 家居动作（调 HA 服务）→ TTS 播报；对比两条路线——云链路（小爱/天猫生态，能力全但音频出户）与本地链路（HA Voice / Wyoming 协议 + Whisper + Piper，全链路内网）；列出本地路线当前的能力边界（远场拾音、多轮对话、说话人识别）。
  2. 针对上面的链路，算延迟预算：端到端可感知上限约 1~1.5s——唤醒 100ms + ASR 流式 300ms + 意图 200ms + 动作 100ms + TTS 首包 300ms；讨论哪个环节最该优化（VAD 尾点判定太保守会白等 500ms）、为什么"先播确认音再执行"能掩盖延迟。
  3. 基于上面的预算，做意图层设计：小词表意图（"把客厅灯调到 50%"→ 实体+槽位正则/规则）与大模型意图（自然语言直接映射 HA 服务调用）的混合策略——高频命令走规则（快且稳）、长尾走 LLM（慢但泛化）；说明槽位缺省时的追问对话状态机。
  4. 动手：用 Wyoming 生态（或纯 HTTP 服务模拟）搭"语音开灯"最小链路：本地 Whisper 转写 → 规则意图解析（灯实体+开关动词+可选亮度）→ 调 HA REST API → Piper 本地合成"已为您开灯"播报；用录音文件驱动整链路测端到端延迟并拆分各环节耗时表。

### DN07 设备离线与 Zigbee 网络排障

- **预期档位**: medium
- **考察维度**: 链路诊断 / 干扰分析 / 网络自愈
- **对话脚本**:
  1. "卧室传感器三天没消息了"的排查树：先看设备侧（电池电压属性 <2.5V 大概率没电）→ 再看链路（LQI/链路质量与 last_seen 间隔）→ 再看网络（该设备是否换过路由父节点）→ 最后看主机（Z2M 服务日志/串口设备是否重启丢失 `/dev/ttyUSB0`）。
  2. 针对上面的排查树，讲 2.4GHz 干扰共存：Wi-Fi 与 Zigbee 同频段，Zigbee 信道 11/15/20/25（避开 Wi-Fi 1/6/11 主能量区）的选择策略；微波炉/USB3 口对 2.4G 的干扰特性；说明换信道要全网络重新加入的现实成本（为什么装网时就要选对）。
  3. 基于上面的干扰知识，讲网状自愈与人为干预：路由器设备断电会让依赖它的终端重新入网（期间失联数分钟），大规模换插座后的"网络风暴"；什么时候该动用 Z2M 的路由表工具（`map` 可视化、强制重新入网 `touchlink`）而不是干等自愈。
  4. 动手：写 `zigbee_health.sh`（对 Z2M MQTT 主题或 API）：输出全网设备健康表（电量分档、LQI 分档、last_seen 超时计数）、疑似坏邻居（多个终端共用且频繁离线的路由器）、给出可执行建议（加插座的位置/换电池清单）；连续采集 7 天形成趋势，验证一次"插座断电事件"在报表中的呈现。

### DN08 远程访问与家庭网络安全

- **预期档位**: medium~hard
- **考察维度**: 接入方案 / 暴露面收敛 / 认证加固
- **对话脚本**:
  1. 在外面控制家里的灯有四条路：端口映射+DDNS（把 HA 暴露公网，风险最高）、Home Assistant Cloud/Nabu Casa（托管隧道，省心但音频出户）、自建反向代理+TLS（frp/自签域名）、组网工具（Tailscale/WireGuard，设备级私网）；从安全性/成本/带宽/配置复杂度四维对比并给出推荐。
  2. 针对上面的选型，讲"为什么端口映射是最差解"：公网扫描器对 HA 登录页的持续爆破、旧版本组件 CVE 的利用链、家用宽带公网 IP 的稀缺；解释 Tailscale 的 NAT 穿透原理（DERP 中继兜底）与"手机上装 App 即可回家"的体验优势。
  3. 基于上面的接入，做认证与权限加固：HA 的 MFA（TOTP）+ API 长期令牌的最小权限使用（脚本只给只读令牌）、`trusted_networks` 对内网放行、失效会话清理；延伸到摄像头/NVR 这类"高危 IoT 绝不公网、只走 VPN"的分层原则。
  4. 动手：用 Tailscale 把 HA 主机与手机组成私网，验证公网 4G 下访问 HA App 正常、再关闭 HA 的公网相关开关验证"扫描不到服务"；给第三方脚本只签发只读令牌并验证其无法调用 `light.turn_on`；写一份家庭网络暴露面清单（每个对外服务的监听地址/认证方式/理由）。

### DN09 数据持久化与系统备份恢复

- **预期档位**: medium
- **考察维度**: recorder 策略 / 数据库治理 / 快照演练
- **对话脚本**:
  1. HA 的历史数据双轨制：recorder（SQLite/其它数据库，存全部状态变化，默认 10 天清除）与长期统计（5 分钟粒度汇总，默认永久）；解释"仪表盘历史图 1 天内的细粒度 vs 一年前的粗粒度"分别来自哪张表，以及为什么默认 10 天（SQLite 体积与查询性能的平衡）。
  2. 针对上面的双轨，做数据库治理：`purge_keep_days` 调整、`exclude` 剔除高频无用实体（每秒上报的功率原始值）、迁 MariaDB 的收益场景（大房子+长历史）；讨论"历史图变卡"的三个根因（单实体变更过频/查询窗口太宽/数据库膨胀）与对应修法。
  3. 基于上面的治理，讲备份对象清单：配置目录（YAML/`automations.yaml`/`.storage` 内置数据库——设备注册与实体 ID 的真相之源）、Zigbee 协调器网络信息（换 USB 网关必须迁移的 `coordinator_backup.json` 类数据）、Z2M 配置、TLS 证书与令牌；说明 HA 官方"备份"功能打包的内容与边界（不含外部数据库数据时要另行导出）。
  4. 动手：制定并演练恢复方案：每周自动备份到 NAS（或第二台机器）、在一个全新安装的 HA 上完整恢复（配置 + Zigbee 网络 + 历史），记录恢复耗时与验证清单（自动化条数/设备数/最近一条历史记录时间戳）；把"最坏情况重建"演练写成一页 runbook。

### DN10 仪表盘与场景设计：给家人用的界面

- **预期档位**: medium
- **考察维度**: Lovelace 布局 / 场景建模 / 可用性
- **对话脚本**:
  1. 仪表盘的第一性问题是"给谁用"：给自己的极客视图（全实体+实时图）vs 给家人的"三屏内解决 90% 需求"（客厅/卧室/常用按钮）；用 Lovelace 的视图（view）-卡片（card）-芯片（chip）层级设计手机竖屏优先的布局，说明为什么"客厅一个视图、每视图 <8 张卡片"是可用性经验值。
  2. 针对上面的布局，讲卡片选型：`entities`（列表万能卡）、`tile`（单设备快捷块）、`gauge`/`history-graph`（趋势）、`conditional`（按状态显隐——离家时藏掉家里灯）；讨论按场景重组（"回家模式"一屏）与按房间重组（"客厅"一屏）的取舍，以及为什么家人更理解前者。
  3. 基于上面的界面，区分三个易混概念：`scene`（一组目标状态的快照：观影=灯 10%+窗帘关+电视开）、`script`（有流程的动作序列：含延迟与条件）、`automation`（事件驱动的剧本）；用"观影之夜"同时给出三者实现，说明什么时候该用哪个。
  4. 动手：为三口之家做一个"家人视图"：回家/离家/晚安三大场景按钮 + 温湿度与摄像头缩略 + 故障时的显眼提示（房屋水浸/门未锁用红色条件卡片）；让非技术家人实测三个任务（开客厅灯/查温度/触发晚安）并统计点击路径长度，按反馈迭代一版；沉淀一份"家庭自动化设计原则"十条清单。
