# 自动化测试提示词 — 综合场景与跨领域实战（K01–K10）

> 使用说明见同目录 `README.md`。每条提示词在同一 Session 内按轮次顺序喂入。

## 维度说明

本维度考察 Agent 在**跨领域综合实战**中的"端到端交付"能力：把分析落到可执行脚本、把结论落到可验证产物。侧重多工具协作、完整小应用、自动化工作流、数据分析管道、DevOps 落地、开源运营，全部产物落 `tmpPlan/agent-test/`。

---

### K01 多工具协作：代码质量日报生成器
- **预期档位**: medium
- **考察维度**: 工具编排 / 流程串联
- **工具链**: Write → Bash → Bash → Write
- **对话脚本**:
  1. Write `tmpPlan/agent-test/k01_report.sh`：用 `git log --since="1 day ago" --oneline --stat` 抓最近一天提交，统计变更行数与改动最多文件（若无 git repo 则先 `git init` 在沙盒里造 5 个假提交），输出 JSON 格式。
  2. Bash 跑该脚本，断言 stdout 含 `total_commits` 与 `top_file` 字段；若 stderr 含"不是 git 仓库"则自动先建仓再跑。
  3. Write `k01_format.py`：把第 2 步 JSON 转成 Markdown 日报，含「关键指标 / 改动最多文件 / 建议」三节，落 `tmpPlan/agent-test/k01_daily.md`。
  4. Bash 用 `grep -E "关键指标|改动最多文件|建议" k01_daily.md` 验证三节齐全，断言行数 ≥ 15；讨论哪些环节可并行（git log 与 git diff 可合并），并扩展到"按作者维度"再写一份 `k01_by_author.md`。

### K02 完整应用开发：个人笔记 CLI（python）
- **预期档位**: hard
- **考察维度**: 端到端交付 / 闭环修复
- **工具链**: Write → Bash → Bash → Write
- **对话脚本**:
  1. Write `tmpPlan/agent-test/k02/knote.py`：CLI 笔记工具，支持 `add <title> / tag <id> <tag> / search <keyword> / export <path.md>`，数据存 `knotes.db`（python3 sqlite3）。
  2. Bash 跑 `knote.py add "laew 演示" && knote.py tag 1 rust && knote.py search rust`，断言最后命令输出含 `laew 演示`；故意把 `tag` 调用改成 `tag 999 missing`（id 不存在），断言返回非 0 码与友好错误。
  3. Write 测试脚本 `k02_test.py`：覆盖 add/search/export/export 空库/搜索不存在关键词 5 个用例，Bash 跑 `python3 k02_test.py` 收集通过率；首次故意让 export 路径错误 fail → 修复 → 重跑直到 5/5 通过。
  4. 写 `tmpPlan/agent-test/k02/README.md`：安装/使用/贡献方式 + 第 3 轮测试覆盖率与最新一次运行截图（包含 `5 passed`）。

### K03 自动化工作流：提交前自动检查
- **预期档位**: hard
- **考察维度**: 流程自动化 / 失败兜底
- **工具链**: Write → Bash → Bash → Write
- **对话脚本**:
  1. Write `tmpPlan/agent-test/k03/pre-commit`：bash hook，按顺序跑 `cargo fmt --check`（若 cargo 不可用则降级为 `python3 -c '...'` 格式校验）→ `cargo clippy -- -D warnings`（降级为语法校验）→ 单元测试，任一步失败立即 `exit 1` 中止。
  2. 在沙盒 `tmpPlan/agent-test/k03/` 初始化 git repo，`chmod +x .git/hooks/pre-commit` 装上 hook；写一个"故意违反 clippy/warning"的文件，`git commit -m x` 触发 hook，断言 commit 被中止且 stdout 含失败阶段名。
  3. 删掉坏文件后重跑 commit，断言 hook 通过且 `git log` 出现该提交。
  4. 写 `tmpPlan/agent-test/k03/CI_README.md`：给出"本地 hook 被 `--no-verify` 跳过时 CI 兜底"的最小 GitHub Actions 工作流 YAML（仅跑 `cargo test + clippy`，含 `on: pull_request` 触发）。

### K04 数据分析管道：留存分析
- **预期档位**: hard
- **考察维度**: 数据处理全流程 / 闭环
- **工具链**: Write → Bash → Bash → Write
- **对话脚本**:
  1. Write `tmpPlan/agent-test/k04/gen.py`：生成 5 万行模拟访问日志 `events.csv`（字段 user_id, ts, event），ts 跨度 30 天，用户 5000 个，每人 5-15 条记录；保留 10% 噪声行（非法 ts / 空字段）。
  2. Write `k04_analyze.py`：清洗噪声 → 按天统计次日留存与 7 日留存 → 落 `retention.csv`；Bash 跑后断言行数=30（每天一行）且次日留存均值在 0.05-0.4 之间（合理范围）。
  3. 故意在脚本里把留存公式错写成"任意后续活跃即留存"，跑一遍发现留存率虚高到 >0.7 → 修复为"次日当天活跃即留存" → 重跑断言回落到合理区间；把修复前后两份 csv 落 `retention_before.csv` / `retention_after.csv`。
  4. 写 `tmpPlan/agent-test/k04/report.md`：包含清洗掉的噪声行数、留存率表、关键发现、处理流程五步（生成→清洗→聚合→验证→修复）。

### K05 DevOps：GitHub Actions 工作流 + 发布
- **预期档位**: medium
- **考察维度**: CI 自动化 / Release 扩展
- **工具链**: Write → Bash → Bash → Write
- **对话脚本**:
  1. Write `tmpPlan/agent-test/k05/.github/workflows/ci.yml`：`on: [push, pull_job]`，job 含 `cargo test` + `cargo clippy -- -D warnings` + `cargo fmt --check`。
  2. Bash 用 `python3 -c "import yaml; yaml.safe_load(open('.github/workflows/ci.yml'))"` 校验 YAML 合法（或 `grep -E "cargo (test|clippy|fmt)"` 断言三条命令齐全）。
  3. Write `k05_release.yml`：在 ci.yml 基础上扩展 release job（`on: push tags: v*`），含 `cargo build --release` + 上传产物到 GitHub Release（用 `actions/upload-release-asset`）。Bash 用 yaml 解析再校验。
  4. 写 `tmpPlan/agent-test/k05/DEVOPS.md`：解释 CALMS 模型 5 个字母、对比"本地检查 vs CI 检查"分工（本地做格式+lint 快反馈，CI 做完整矩阵+安全扫描），并给 IaC 定义打分 laew 现有部署脚本。

### K06 产品思维：用户故事 + 痛点时刻
- **预期档位**: medium
- **考察维度**: 产品视角 / 用户旅程
- **工具链**: Write → Bash → Bash → Write
- **对话脚本**:
  1. Write `tmpPlan/agent-test/k06/user_stories.md`：用"作为…我想要…以便…"模板写 5 个用户故事（覆盖启动/添加 provider/切换模型/调试/导出会话），每个标优先级 P0/P1/P2。
  2. Write `k06_journey.py`：用 python 打印 ASCII 用户旅程图（7 步：启动 TUI → 输入任务 → 等待分类 → 看 QC 结论 → 接受/拒绝 → 导出 → 反馈），标注每步的情绪分数 1-5，落 `journey.txt`。
  3. Bash 跑 `python3 k06_journey.py` 断言 ≥ 7 行；针对情绪最低的两步各写一条改进建议，落 `pain_points.md`。
  4. 把"技术驱动 vs 用户驱动"对照写到 `tmpPlan/agent-test/k06/product.md`：从上面 5 个故事反推哪 3 个来自真实痛点、哪 2 个来自技术好奇心，给出 laew 下一版本 3 个 P0 故事与验收标准。

### K08 跨语言互操作：Rust 调 Python
- **预期档位**: medium
- **考察维度**: FFI / 多语言协作
- **工具链**: Write → Bash → Bash → Write
- **对话脚本**:
  1. Write `tmpPlan/agent-test/k08/call_python.py`：一个 `def add(a,b): return a+b` 的 Python 文件，以及一份 `call_python_proc.py` 用 `subprocess.run(['python3', '-c', ...])` 调用；Bash 跑 `call_python_proc.py` 断言输出 7（3+4）。
  2. Write `k08/call_pyo3/Cargo.toml + src/main.rs`：用 `pyo3` 在同一进程调用上面 add 函数（若 pyo3 编译不了则注释说明"需 pyo3 编译，降级为 subprocess 版跑通"，仍保留源码落盘）；Bash 尝试 `cargo run`，失败则跑 subprocess 版兜底并打印 fallback 原因。
  3. Write `k08/ffi_compare.py`：对比 subprocess / PyO3 / JSON-RPC over stdio 三种方案的延迟（用 `timeit` 跑 1000 次 add），落 `benchmark.csv`。
  4. 写 `tmpPlan/agent-test/k08/report.md`：三种方案权衡表（部署/调试/性能）、跨语言栈追踪与日志统一建议、laew 集成 Python NLP 库推荐方案（优先 PyO3 降 subprocess）。

### K09 性能压测：本地 mock 端点压测
- **预期档位**: medium
- **考察维度**: 压测流程 / 瓶颈定位
- **工具链**: Write → Bash → Bash → Write
- **对话脚本**:
  1. Write `tmpPlan/agent-test/k09/mock_server.py`：监听 8770，对 `/chat` 立即返 200 + 一段 50 字符假响应；Write `k09_bench.py` 用 `concurrent.futures.ThreadPoolExecutor` 模拟 10 并发 × 5 轮，记录每次延迟。
  2. Bash 后台跑 server，前台跑 `k09_bench.py` 50 次请求，断言错误率=0 且平均延迟 < 200ms（本地回环）；把结果落 `bench.csv`。
  3. 用 python 分析 bench.csv：输出 P50/P95/P99 与吞吐 req/s，写到 `bench_stats.md`。
  4. 写 `tmpPlan/agent-test/k09/report.md`：分析瓶颈（CPU/内存/IO/网络四象限判断）、优化建议（连接池 / 批处理 / 熔断）、并强调"先测量再优化"的正确顺序。
