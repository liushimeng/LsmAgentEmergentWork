### BF01 终端俄罗斯方块：SRS 旋转系统与消行判定
- **预期档位**: hard
- **考察维度**: SRS Wall Kick + 消行检测 + 7-bag 随机
- **对话脚本**:
  1. 用 Rust 写一个终端版俄罗斯方块（crossterm 字符画）：核心数据结构是 10x20 的 `[[u8; 10]; 20]` 二维数组，0 空、1-7 表示 7 种方块颜色；先实现基础下落与左右移动。
  2. 加上 SRS（Super Rotation System）旋转：方块绕中心旋转时若新位置与已有方块冲突，要按「Wall Kick 表」尝试 5 个偏移位置（如 JL-piece 顺时针从 (0,0) 试到 (1,0)、(1,-1) 等），这是 Tetris Guideline 的硬性规范。
  3. 消行判定：每帧下落锁定后扫描每行，若全 1 则删除该行并把上方所有行下移；多行同时消除（Tetris 4 行）要给额外奖励；锁定延迟（Lock Delay）机制：触底后给 500ms 缓冲，让玩家微调。
  4. 7-bag 随机生成器：经典 Tetris 用「7 个方块打乱顺序抽完」的 bag 算法（不会出现连续 6 个 S/Z），避免玩家被「长旱」搞崩；同样思路可以给 laew 的 Yolo 任务分类器用——保证任务分布均衡，不让某类任务「连旱」。

### BF02 扫雷：随机布雷、首点保护与洪水填充展开
- **预期档位**: medium
- **考察维度**: 邻域 BFS + 状态机 + 首点安全保证
- **对话脚本**:
  1. 用 Rust 写扫雷：数据结构 `enum Cell { Hidden, Revealed, Flagged }` + 周围雷数 u8；布雷算法先生成全 0 网格，遍历每个格子用「周围 8 邻域」统计雷数（不要预先放置雷后再算，否则要二次扫描）。
  2. 首点保护：玩家第一次点击必须是雷的概率为 0——经典做法是首次点击后才布雷，确保第一次点击位置与周围 8 格都不是雷；或者先布雷后判定，若是雷则把雷挪到别处。
  3. 洪水填充展开：玩家点击空白格时递归展开所有相邻非雷格（8 邻域 BFS），直到遇到数字格停下；用栈/队列避免递归爆栈，大盘（30x16）迭代版更稳。
  4. 给 laew 的 Quality-Check Agent 加「首点保护」思路：QC 第一次检测某个 SubAgent 的输出时不直接判失败，而是「保证至少看到一次成功样本」再下结论，避免「第一次任务失败就误判模型有问题」。

### BF03 2048：滑动合并算法与撤销栈
- **预期档位**: medium
- **考察维度**: 4 向滑动 + 状态持久化 + 输入去抖
- **对话脚本**:
  1. 用 Rust 写 2048 的核心：4x4 棋盘，玩家按方向键时所有方块沿该方向「贴边 + 同值合并」；先写左滑：扫描每行，找非零块向左推，遇到同值且未合并过则合并（一次滑动每个块最多合并一次，用 `merged: bool` 标记）。
  2. 右滑/上滑/下滑都是左滑的旋转结果：把棋盘转 90 度（顺时针）/ 翻转后复用左滑逻辑，再转回去；用「矩阵旋转 helper 函数」避免 4 倍代码重复。
  3. 加撤销栈：每次玩家操作前把棋盘状态 `clone()` 进 `Vec<Board>`（深拷贝，~64 字节），按 `u` 键 pop 一份恢复；这是 2048 经典实现的核心交互，比单纯难度递增好玩得多。
  4. 给 laew 的 SubAgent-Work 加「滑动窗口式任务回滚」：每个 SubAgent 在执行期间维护一个 micro-undo 栈，记录每步的 BashTool 输出，按 `Ctrl+Z` 让 Agent 撤回上一步再换方案（比整轮重试省 token）。

### BF04 推箱子 Sokoban：关卡格式与死锁检测
- **预期档位**: hard
- **考察维度**: XSB 格式 + 死锁判定 + BFS 求解
- **对话脚本**:
  1. 用 Rust 解析经典 Sokoban XSB 关卡格式：`##### / #  $@ #` 字符画（`#` 墙、空地、`.` 目标、`$` 箱子、`@` 玩家、`+` 玩家在目标），把 8x8 小关卡文件读成 `Board` 结构。
  2. 死锁检测：玩家无解的死锁状态有 4 类——角死锁（箱子推到墙角且墙边无目标）、边死锁（沿墙推后无法再动）、冻结死锁（目标被箱子封死出口）；移动前要预判，避免玩家进入必败状态。
  3. BFS 求解：从初始状态出发，状态 = (玩家位置, 所有箱子位置)，每步 4 个方向推箱子（玩家要先能走到箱子背后）；用 HashSet 去重，统计最优步数；中型关卡状态空间 ~10^7，必要时用 IDA* 剪枝。
  4. 给 laew 的 Plan Agent 加「死锁预演」：在生成 hard 任务方案前用 BFS 模拟 Workflow 拓扑是否可解（避免「SubAgent 顺序死锁」），参考 Sokoban 死锁检测的逻辑预判 Plan 是否能执行。

### BF05 五子棋 AI：极小化极大与 α-β 剪枝
- **预期档位**: hard
- **考察维度**: Minimax + α-β 剪枝 + 启发式评估
- **对话脚本**:
  1. 用 Rust 写五子棋游戏循环：15x15 棋盘，黑白轮流落子，胜负判定是「最后落点」的横/竖/左斜/右斜四条线上是否有连续 5 个同色棋子（不需要全盘扫描，落点局部检测即可）。
  2. 极小化极大算法（Minimax）：递归深度 4-6 层，每层评估函数计算双方棋型分（活三 +100、冲四 +1000、活四 +10000、五连 +100000）；α-β 剪枝把搜索节点从 O(b^d) 降到 O(b^(d/2))。
  3. 启发式优化：只对「已有棋子周围 2 格内」的候选点展开搜索（剪掉 95% 的空位），加上迭代加深（IDDFS）+ 置换表（Zobrist 哈希），让 6 层搜索在 1 秒内出解。
  4. 把 Minimax 思路给 laew 的 Yolo 任务分类器：任务分类本质是「选最大概率档位」的极小极大问题（考虑「分类错误的代价 vs 调度的成本」），用 α-β 思想在 multi-class 场景剪枝减少 Yolo LLM 调用次数。

### BF06 康威生命游戏：无限网格与 HashLife 优化
- **预期档位**: hard
- **考察维度**: 无限网格 + 哈希去重 + 四叉树缓存
- **对话脚本**:
  1. 用 Rust 写经典生命游戏：固定 100x100 网格（边界外视为死），每帧按「8 邻居活细胞数 = 3 复活、= 2 保持、否则死亡」规则生成下一代；朴素版用两个 `Vec<bool>` 切换即可。
  2. 扩展到无限网格：用 `HashMap<(i64, i64), bool>` 只存活细胞位置，计算邻居时只扫活细胞周围 8 格；这个数据结构能处理任意大宇宙，但哈希开销大。
  3. HashLife 算法（Bill Gosper 1984）：四叉树结构存 2^n x 2^n 子方块，每块缓存「进化 k 代后的结果」，重复状态直接查表；理论上 N 代复杂度可降到 O(N log N)，能模拟宇宙尺度的图案。
  4. 给 laew 的 Session 主上下文做 HashLife 思想：把历史消息按 2^n 分块（例如 4/8/16/32 条一组），每组缓存 Compact Agent 压缩后的摘要，重复内容（比如反复粘贴同一文件）查表复用，省 LLM token。

### BF07 打砖块：反弹角度、道具与关卡编辑器
- **预期档位**: medium
- **考察维度**: 物理碰撞 + 关卡格式 + 道具状态机
- **对话脚本**:
  1. 用 Rust 写打砖块（Breakout）核心循环：球的位置/速度 `(x, y, vx, vy)`，每帧 `x += vx; y += vy`；与挡板、砖块、墙碰撞时按「入射角 = 反射角」翻转速度分量（碰到垂直墙翻 vx，碰到水平墙翻 vy）。
  2. 球与砖块碰撞的精确判定：球是圆、砖块是矩形，用「球心到砖块最近点」距离与球半径比较；避免「隧穿」（球速过快穿过砖块）要把步长拆细（每帧分多次子步）。
  3. 道具系统：砖块销毁时按概率掉落（加长挡板 / 多球 / 激光），用有限状态机管理道具状态（掉落 → 在挡板 → 生效 → 消失），玩家接住触发效果；关卡用 JSON 描述砖块布局，加一个简单的关卡编辑器。
  4. 给 laew 的 SubAgent-Work 复用打砖块的「隧穿防护」：BashTool 输出过快（连续大段 stdout）时要做子步拆分（每 1KB 切一段），避免 Compact Agent 一次性拿到超长输出导致上下文溢出。

### BF08 文字冒险 MUD：剧情状态机与存档
- **预期档位**: medium
- **考察维度**: 房间图 + 物品状态机 + 序列化存档
- **对话脚本**:
  1. 用 Rust 写经典 MUD：核心数据结构是房间 `struct Room { name: String, description: String, exits: HashMap<Direction, RoomId>, items: Vec<ItemId> }`，玩家 `Player { current_room, inventory, hp }`。
  2. 命令解析：`north` / `take sword` / `use potion` / `inventory` 等动词用模式匹配分发到对应处理函数；剧情用状态机推进（如 `talk_to_npc` 触发对话分支 → 派任务 → 完成 → 改变房间状态）。
  3. 存档：把玩家与全局可变房间状态序列化成 JSON 存盘（serde_json），读档还原；注意物品已拿走、门已开等「持久状态」要存在房间对象里，不能存在玩家身上。
  4. 给 laew 的 TUI 加 `/mud` 彩蛋命令：玩家输入「north」「take」「use」等指令，Yolo Agent 解析成 BashTool 调用（cd / 读文件 / 跑命令），把当前工作目录建模为 MUD 房间，让 TUI 变可玩。

### BF09 数独：生成、唯一解校验与求解器
- **预期档位**: medium
- **考察维度**: DLX 精确覆盖 + 回溯 + 难度梯度
- **对话脚本**:
  1. 用 Rust 写数独求解器：用 Donald Knuth 的 Dancing Links（DLX）算法把数独建模为「81 格 × 324 列约束」的精确覆盖问题（每格位置 1 个数 → 4 个约束：单元格、行、列、宫），求解速度 ~毫秒级。
  2. 数独生成：从满盘解出发，逐个挖空（每挖一个空验证是否仍有唯一解）；用 DLX 跑两次（挖空前 + 挖空后）比对解集数量，只保留唯一解的挖法；难度梯度对应挖空数（30 简单 / 50 中等 / 60 困难）。
  3. 玩家交互：实现键盘上下左右选格 + 数字键填数 + 候选数标记（pencil mark）；错误高亮（与初始盘数字冲突时变红），完成时全盘校验。
  4. 给 laew 的 Plan Agent 加「唯一性校验」：hard 任务的 Plan 方案生成后用 DLX 思想验证「是否有多种等效方案」（避免下游 SubAgent 选错路径），规划阶段就消歧。

### BF10 塔防原型：波次调度、路径与升级树
- **预期档位**: hard
- **考察维度**: A* 寻路 + 状态机 + 经济平衡
- **对话脚本**:
  1. 用 Rust 写塔防核心：地图是网格，每个塔位有「射程 / 伤害 / 攻速」三属性；敌人沿固定路径从起点走到终点，用 A* 或「预设 waypoint 列表」移动；敌人按波次刷新。
  2. 目标选择：每个塔每帧选一个敌人攻击，策略有「最近」「最远」「最低血」「最高血」「首个将到终点」5 种；用 priority_queue 按 (优先级, 敌人 ID) 排序，同帧内打同一目标。
  3. 升级树：每个塔 3 级升级分支（如箭塔 → 火焰塔 / 冰霜塔），升级成本指数增长；经济平衡是核心体验——出怪收益 ≈ 玩家 70% 的建塔开销，难 30%，玩家有挑战感又不至于崩盘。
  4. 给 laew 的 MultiAgentOrchestrator 加「波次调度」：把用户任务流建模成塔防波次（每条任务是一个敌人），SubAgent 是塔，根据历史成功率动态升级（高频成功任务 → 升级为 fast-path 直接 SubAgent 处理；低成功率 → 升级为 Plan 路径加 QC）。
