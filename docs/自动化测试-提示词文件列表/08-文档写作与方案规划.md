# 自动化测试提示词 — 文档写作与方案规划（H01–H10）

> 使用说明见同目录 `README.md`。每条提示词在同一 Session 内按轮次顺序喂入。

## 维度说明

本维度考察 Agent 在**文档写作、方案设计、技术规划、知识沉淀**等场景中的表现，
涵盖技术文档撰写、架构方案设计、API 文档、变更日志、调研报告、白皮书、
演讲提纲、培训材料、决策记录、技术选型等主题。

---

### H01 技术方案文档撰写
- **预期档位**: medium
- **考察维度**: 长文结构化输出 + 方案完整性
- **对话脚本**:
  1. 我要给团队写一份"laew 接入 OpenAI 兼容协议"的技术方案，请列出文档大纲（至少 6 节）。
  2. 把"背景与目标"和"方案设计"两节展开成完整正文，要求有图（用 ASCII 或 Mermaid）。
  3. 补充"风险评估"和"回滚方案"节，列出至少 5 个风险点及应对措施。
  4. 把完整方案保存到 `tmpPlan/接入OpenAI兼容协议方案.md`，检查目录锚点是否都能跳转。

### H02 API 接口文档生成
- **预期档位**: medium
- **考察维度**: 接口描述规范 + 示例完整性
- **对话脚本**:
  1. 为 laew 的 `/provider` 系列斜杠命令写一份面向用户的 API 风格文档（命令/参数/示例）。
  2. 每个命令补充"典型使用场景"和"常见错误"两段。
  3. 设计一个"快速上手"章节，从零开始到完成首个 provider 配置，给出 5 步命令序列。
  4. 把文档保存到 `tmpPlan/provider命令参考.md`，要求格式统一、示例可复制即执行。

### H03 架构决策记录（ADR）
- **预期档位**: medium
- **考察维度**: 决策文档方法论 + 权衡表达
- **对话脚本**:
  1. 什么是架构决策记录（ADR）？它的核心结构是什么？
  2. 用 ADR 格式记录 laew 的一个真实决策："为什么选择 SQLite 而不是 PostgreSQL 作为存储层"。
  3. 在 ADR 中补充"被否决的替代方案"章节，至少列两个并说明否决理由。
  4. 把 ADR 保存到 `tmpPlan/ADR-001-SQLite选型.md`，检查是否符合"背景→决策→后果"三段式。

### H04 调研报告撰写
- **预期档位**: hard
- **考察维度**: 信息综合 + 对比分析
- **对话脚本**:
  1. 我要调研"主流 CLI Agent 工具的 TUI 实现方案"，请设计调研维度和对比表结构。
  2. 基于 laew 知识库（`docs/Agent源码调研/`）中已有的 15 个项目信息，填充对比表。
  3. 从调研中提炼出 3 条对 laew 的启示，按优先级排序并说明落地难度。
  4. 把完整调研报告保存到 `tmpPlan/CLI_Agent_TUI调研.md`，含摘要、正文、参考三部分。

### H05 变更日志（Changelog）撰写
- **预期档位**: simple
- **考察维度**: 版本管理 + 变更分类
- **对话脚本**:
  1. 什么是 Keep a Changelog 规范？它的核心原则是什么？
  2. 假设 laew 从 0.1.2 升级到 0.2.0，包含 5 个新功能、3 个修复、1 个破坏性变更，写一份 Changelog 片段。
  3. 破坏性变更应该怎么写，才能让用户快速理解影响并知道怎么迁移？
  4. 对比"按时间排序"和"按重要性排序"两种 Changelog 组织方式的优劣。

### H06 技术白皮书大纲
- **预期档位**: hard
- **考察维度**: 宏观叙事 + 逻辑链条
- **对话脚本**:
  1. 为 laew 写一份技术白皮书的大纲，目标读者是"考虑采用 Agent CLI 的 CTO"。
  2. 展开"行业背景与痛点"章节，用数据化表达（可合理假设）说明为什么需要多 Agent 架构。
  3. 展开"laew 的核心竞争力"章节，提炼 3 个差异化卖点并各给出论据。
  4. 讨论白皮书和 README 在内容、语气、篇幅上的区别，各适合什么传播场景。

### H07 演讲提纲与幻灯片
- **预期档位**: medium
- **考察维度**: 口头表达设计 + 信息节奏
- **对话脚本**:
  1. 我要在组内做一场 15 分钟的"laew 多 Agent 架构分享"，请设计演讲提纲（含时间分配）。
  2. 把"架构总览"那一页的要点展开成 3 个关键信息，每点不超过 20 字。
  3. 设计一个"现场演示"环节：从启动到完成一个 medium 任务，写出要执行的命令和预期输出。
  4. 为演讲准备 3 个可能的 Q&A 及回答口径，覆盖"为什么不用 Python""性能如何""生产可用吗"。

### H08 培训材料设计
- **预期档位**: medium
- **考察维度**: 教学设计 + 知识传递
- **对话脚本**:
  1. 设计一份面向新贡献者的"laew 上手培训"大纲，包含 4 个模块，每个模块有学习目标。
  2. 把"模块一：项目结构与编译运行"展开成详细讲义，含命令示例和预期输出。
  3. 设计 3 个动手练习，难度递进（跑起来→加日志→改功能），每个练习给出验收标准。
  4. 讨论"文档驱动培训"和"导师驱动培训"各自优劣，给出适合开源项目的混合方案。

### H09 技术选型报告
- **预期档位**: hard
- **考察维度**: 多方案对比 + 决策框架
- **对话脚本**:
  1. laew 要选一个 TUI 框架（自研 vs ratatui vs cursive），请设计选型评估维度（至少 5 个）。
  2. 按维度给三个方案打分（1-5），说明打分理由，最后给出加权总分。
  3. 分析"自研"方案的技术债务风险，给出 3 年内可能面临的维护成本估算思路。
  4. 把选型报告保存到 `tmpPlan/TUI框架选型.md`，含推荐结论和风险提示。

### H10 项目 README 重构
- **预期档位**: medium
- **考察维度**: 门面文档设计 + 信息层级
- **对话脚本**:
  1. 读 laew 当前的 `README.md`（如果有），分析它的信息架构是否合理。
  2. 设计一个理想 README 的章节顺序：从"一句话定位"到"贡献指南"，说明每节的作用。
  3. 重写"快速开始"章节，要求新用户能在 3 分钟内跑起来第一个命令。
  4. 讨论 README 中"徽章（badge）"的作用，为 laew 设计一组合理的徽章（版本/构建/文档/许可）。
