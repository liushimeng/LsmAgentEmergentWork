### CU01 RLE 与 Delta：最简单的两把刀

- **预期档位**: simple~medium
- **考察维度**: 游程编码 / 差分编码 / 适用数据画像
- **对话脚本**:
  1. 用 Python 实现 RLE：`aaabbbcc → (a,3)(b,3)(c,2)`，处理「连续重复少」时的膨胀问题（每字符 +1 字节开销，最坏翻倍）；给出 RLE 适合的数据画像（大面积纯色位图 / 屏幕差分 / 时序常量段）。
  2. Delta 编码：`[100, 101, 105, 104] → [100, +1, +4, -1]`，配合 ZigZag 变换（`n << 1 ^ n >> 31`）把有符号小差值映射为无符号小整数，再配合 varint 存储；写 delta+zigzag+varint 三连管线并统计单调递增时间戳序列的压缩比（通常 8 字节 → 1 字节）。
  3. 组合实战：帧间差分（游戏画面 / 屏幕共享只传变化矩形 + RLE 压缩变化区）——写「上一帧 + 当前帧 → 变化矩形列表 → RLE 序列化」的屏幕差分管线；讨论为什么这对高频小变化的场景极有效。
  4. laew 借鉴：帧间差分对照 Session 上下文的「轮间差分」——多轮对话里相邻两轮的消息高度重叠（系统提示词 + 历史 + 新一轮），讨论 transcript 落盘时用「追加 + 差分」而不是每轮全量快照（联动 `/rewind` 的三处一致截断如何配合）。

### CU02 Huffman 编码实现

- **预期档位**: hard
- **考察维度**: 频率统计建树 / 规范码 / 编解码对称
- **对话脚本**:
  1. 经典 Huffman：统计字节频率 → 小顶堆每次取两个最小合成父节点 → 树叶路径（左 0 右 1）即前缀码；用 Python 实现 `compress(bytes) -> (tree, bits)` 并验证「频率高的字符码短」与前缀无歧义性质。
  2. 规范 Huffman（Canonical）：只存「每个码长的最小符号」即可重建整棵树（码长数组 → 按字典序分配码字），把树存储从几百字节压到几十字节；实现规范码的编码端与「码长表重建」的解码端，这 deflate 实际在用。
  3. 解码的工程化：逐位走树慢——规范码下「首 bit 前缀 → 数值比较」查表解码（按码长分桶 + 基址偏移）；写查表版解码器并对 1MB 英文文本测吞吐，对比朴素版 3~10 倍提速。
  4. laew 借鉴：Huffman「按频率分配资源」对照 Compact Agent 的压缩策略——上下文里各段按「信息频率」定保留度（高频引用的接口定义保留原文、低频的示例压成一句），讨论实现「内容热度统计」需要的埋点。

### CU03 LZ77 / LZSS 滑动窗口匹配

- **预期档位**: hard
- **考察维度**: 三元组 / 滑动窗口查找 / 最长匹配贪婪
- **对话脚本**:
  1. LZ77 核心：输出 `(偏移, 长度, 下一字符)` 三元组，解码器从已解出的历史里按偏移回拷长度——解码极简（无任何表）但编码要找「当前位置往回 32KB 窗口内的最长匹配」；用 Python 写朴素 O(n×w) 匹配版跑通小样例。
  2. 哈希链加速：窗口匹配用「3 字节前缀哈希 → 候选位置链表」把匹配复杂度降到近似 O(n)；实现哈希链并限制每位置最多回溯 16 个候选（速度/压缩比平衡），这是 zlib 的实际做法。
  3. LZSS 改进：三元组太胖（不足 3 字节的匹配亏本）——加一个「控制位图」标记每个 token 是字面量还是匹配，短匹配不发「下一字符」字段；实现 LZSS 并对比 LZ77 在文本上的压缩比提升。
  4. laew 借鉴：LZ 的「历史窗口内重复引用」对照上下文中的重复引用（同一文件被 Read 多次、同一报错反复出现）——讨论把 tool_result 的重复内容替换成「回指标记」（如 `↩同上轮第 3 块`），LLM 能否正确消费这类指针（注意与 96-CN01 调色板思想的呼应与差异）。

### CU04 LZW 词典编码

- **预期档位**: hard
- **考察维度**: 词典增长 / 编解码同步 / GIF 与 PDF 的遗产
- **对话脚本**:
  1. LZW 编码：动态词典从单字符初始化，编码端每读到「词典里最长可匹配前缀」输出其码字并把「前缀+下一字符」插入新词条（码字递增）；用 Python 实现编码器并手跑 `ABABABC` 的词典演化过程（表格逐步推演）。
  2. 解码器同步：解码端不需要传词典——利用「已解出的码字序列」同样重建词典；唯一坑是「码字刚生成立即被引用」（KwKwK 情形），解码端此时要用「上一词条 + 上一词条首字符」补齐；写出这个特殊分支并构造测试用例覆盖它。
  3. 工程细节：码字位宽动态增长（9bit → 10bit → …，词典满后清空重置）、早期变体（clear code / EOD 码）；解释 LZW 在 GIF（1987）与 PDF（Flate 出现前）的历史地位，以及 Unisys 专利诉讼如何把 PNG + zlib 推上历史舞台。
  4. laew 借鉴：编解码「两端独立重建同一状态」的同步思想对照多 Agent 的共享心智——Yolo / Plan / SubAgent 各自的 Agent-Context 独立，但要靠「共享输入（任务描述 + 注入产物）」重建一致认知，讨论哪些信息必须显式传递否则各端状态漂移（如工作目录路径）。

### CU05 算术编码与区间编码

- **预期档位**: hard
- **考察维度**: 区间缩进 / 整数实现 / 与 Huffman 的本质差异
- **对话脚本**:
  1. 算术编码直觉：把整个消息编码成「0~1 区间内一个小数」——按符号概率反复切分区间取子区间，最终区间内任取一点（位越少越好）表示全部信息；手推两个符号（P(a)=0.6, P(b)=0.4）编码 `aab` 的区间演化，对比 Huffman 在「概率非 2^-k」时的编码浪费。
  2. 有限精度整数实现：用 32/64 位整数区间 `[low, high)` 的缩放——每步重归一化（区间变小时左移输出确定高位 bit、下溢时 E1/E3 映射处理 0.5 附近的粘连）；用 Rust 实现整数区间编码器并测试浮点版结果一致。
  3. 自适应模型：概率表随编码过程动态更新（每见一个符号其概率 +1），编解码端同步更新即无需传频率表；实现自适应二阶模型（以上一符号为条件）并对比静态模型的压缩比。
  4. laew 借鉴：自适应模型「边运行边学习统计」对照 Yolo 的任务画像积累——分类器不需要离线重训，每轮任务结果（成功档位 / 失败回流）在线更新「任务类型 → 档位」的先验，讨论这种在线学习的收敛与遗忘（概率表的衰减因子）。

### CU06 CRC 校验：多项式除法与查表

- **预期档位**: medium~hard
- **考察维度**: CRC 原理 / 查表优化 / 多项式选型
- **对话脚本**:
  1. CRC 原理：把数据看作大二进制数，对生成多项式做模 2 除法（异或代替减法），余数即校验码——接收端重算比对；用 Python 手写逐 bit 版 CRC-32（多项式 0xEDB88320 反射形式）并解释「检错能力」：奇数位翻转必检出、≤32bit 突发错误必检出。
  2. 查表加速：逐 bit 太慢——预生成 256 项表（每个字节值预先算好它对余数的影响），主循环变成 `crc = table[(crc ^ byte) & 0xFF] ^ (crc >> 8)`；实现查表版并验证与逐 bit 版结果一致，再实现按 8 字节切分的切片表（slicing-by-8）思路说明。
  3. 多项式与标准：CRC-32（以太网/zip）、CRC-32C（iSCSI，硬件 SSE4.2 指令支持）、CRC-16-CCITT（蓝牙/HDLC）；讨论「不同领域选不同多项式」的原因（针对各自信道误码模型优化），以及 CRC 为什么只能检错不能纠错、为什么不能当密码学哈希用（碰撞可构造）。
  4. laew 借鉴：CRC「附加在数据尾随发」对照 laew 的 trace 完整性——Debug 模式采集的各 Agent 输入输出若落盘归档，加内容校验（CRC 或 xxHash）能检测「报告被事后手改」，与 CM04 状态哈希链呼应。

### CU07 Base64 与传输编码家族

- **预期档位**: simple~medium
- **考察维度**: 位重组 / padding / 变体与误用
- **对话脚本**:
  1. Base64 原理：3 字节（24 bit）重组成 4 个 6bit 符号查 64 字符表（A-Z a-z 0-9 + /），末尾不足 3 字节补零 + `=` padding；用 Python 不调库实现 `b64encode/decode` 并处理 padding 的两种残留长度（1 字节 → 2 符号 + ==，2 字节 → 3 符号 + =）。
  2. 变体：URL-safe（`+ /` → `- _`，URL 与文件名安全）、无 padding 形态（接收端按长度推断）、Base32（8 字符块、大小写不敏感场景）、Base58（Bitcoin，去易混字符 0/O/I/l）；各写一个适用场景判断题。
  3. 误用警示：Base64 不是加密（已知变换无密钥）、体积膨胀 33%（图片内嵌 JSON 的内存代价）、双重编码事故（已编码数据再被框架自动编码产生 `PT09` 类特征串）；写一个检测「疑似双重编码」的启发式（解码结果可打印比例 + 再编码还原比对）。
  4. laew 借鉴：误用检测的启发式对照 Debug Agent 的「问题报告」——讨论给 laew 加「常见误用体检」：API Key 贴成了 Base64、把 JSON 当 Markdown 存、编码错误的中文（GBK/UTF-8 混淆），P2 级提醒而非报错。

### CU08 现代压缩：zstd / LZ4 / Snappy 选型

- **预期档位**: medium
- **考察维度**: 算法结构对比 / 等级与字典 / 基准测试方法
- **对话脚本**:
  1. 三剑客定位：LZ4（只做 LZ 匹配不做熵编码，解压 5GB/s，压缩比 ~2）、Snappy（同类定位的历史选择）、zstd（LZ + FSE 熵编码，分级 1~22，比拼 gzip 高 30%+ 速度还更快）；给「RPC 消息 / 日志归档 / 数据库页 / 冷备份」四个场景各选一个并说明取舍。
  2. zstd 深入：压缩等级语义（1 快糙 / 19 慢精 / 22 超长窗口）、训练字典（小数据集如 JSON 日志用 100KB 样本训练 dict 后小消息压缩比翻数倍）、长距离匹配模式（--long，窗口 128MB 适合大文件内部重复）；用 zstd crate 做等级 × 数据集的压缩比/耗时矩阵实验。
  3. 基准测试方法学：用真实数据（不要用随机数——不可压；不要用全零——过度可压）、区分「压缩耗时 / 解压耗时 / 压缩比」三指标、报告 p50/p99 而不是均值；写一个简陋 bench 框架并跑出你机器上的选型表。
  4. laew 借鉴：zstd 字典「领域小样本定制」对照 laew 的系统提示词——通用提示词像无字典压缩，针对「本工程任务」的领域提示词等于训练了字典；讨论用历史任务日志「训练」一个项目级提示词附录的可行性与风险（过拟合到旧代码风格）。

### CU09 非密码学哈希：FNV / xxHash / 滚动哈希

- **预期档位**: medium
- **考察维度**: 哈希用途分层 / 滚动哈希 / 一致性哈希预备
- **对话脚本**:
  1. 分层认知：非密码学哈希追求「快 + 分布均匀」（FNV-1a 32/64、xxHash3 内存带宽级、Adler-32 弱但免费附赠于 zlib）vs 密码学哈希追求「不可逆 + 抗碰撞」（联动 BU 维）；用 Rust criterion 微基准对比 FNV vs xxHash vs SHA-256 在 1KB 块上的吞吐（预期 100 倍量级差）。
  2. 滚动哈希：Rabin-Karp 的窗口滑动 `H' = (H - a_out × b^(m-1)) × b + a_in` 允许 O(1) 移动窗口重算；实现滚动哈希并用于「文本重复行检测」（联动文档查重 CW04 预留呼应）与内容分块（content-defined chunking：按哈希低 N 位为 0 的边界切文件，得到「插入位移不变」的分块，rsync/restic 的核心）。
  3. 简单一致性哈希入门：节点哈希到环上、键顺时针找节点——实现一个 200 行内的哈希环（含虚拟节点 150 个/物理节点）并统计节点增删时的键迁移率（期望 ~1/N vs 取模法的全迁移）。
  4. laew 借鉴：内容定义分块（CDC）「按内容切而非按位置切」对照上下文的稳定分块——Compact Agent 若按「消息边界 + 内容哈希」分块（而不是固定条数），编辑某轮后其余块的缓存摘要仍可复用，讨论实现收益。

### CU10 列存编码：字典 / RLE / Bitmap / Delta

- **预期档位**: hard
- **考察维度**: 列内编码组合 / Parquet 编码栈 / 压缩比分析
- **对话脚本**:
  1. 为什么列存先编码再压缩：同列数据同质（性别列只有 2 个值、ID 列单调递增、状态列低基数）——字典编码（值 → 小整数）+ RLE（连续相同跑长）+ Delta（单调数值差分）各自吃掉一类模式；用 Python 把一列 100 万行的「城市名」做 字典+RLE 后再 zstd，统计总压缩比。
  2. Parquet 的编码栈：每列chunk独立选编码（字典基数超阈值 fallback 明文 / BOOLEAN 走 bitmap / 时间戳走 DELTA_BINARY_PACKED / 字符串走 DELTA_BYTE_ARRAY），页级统计（min/max/null 计数）下推谓词跳过整块；用 pyarrow 读一个 Parquet 文件的 per-column encoding 元数据并解读。
  3. Bitmap 索引编码：Roaring Bitmap 的分桶思想（高 16 位分桶、稀疏桶存数组、稠密桶存位图）兼顾空间与 AND/OR 速度；实现一个简化版 roaring（两种桶型）并对比 naÏve bitmap 在稀疏列上的空间差。
  4. laew 借鉴：列存「按访问模式组织存储」对照 laew 的 DB 设计——`providers` 表按行存配置没问题，但若未来存「每轮任务的 trace」（角色 / 耗时 / token / 状态），按列组织（或至少建好索引 + 分区）对 Debug 报告的聚合查询更友好，讨论 schema 演进路径。
