### CZ01 Conway 定律与反向组织设计

- **预期档位**: medium
- **考察维度**: Conway 定律 / 逆康威 / 团队边界设计
- **对话脚本**:
  1. 定律原文：「设计系统的组织……其设计的系统结构会复制该组织的沟通结构」——例证：分布式团队产出的代码天然按地理分模块；用三个真实公司架构图（Amazon / Netflix / Uber）与团队拓扑图对比，验证「微服务边界 = 团队边界」。
  2. 反向康威（Inverse Conway Maneuver）：先设计目标系统结构（微服务 / 模块化），再调整组织结构匹配它——通过合并 / 拆分团队 + 调整汇报关系；给出「从单体到微服务」的组织转型三步走（业务能力切分 → 团队重组 → 服务化推进）。
  3. 沟通开销公式：n 个团队的沟通渠道数 = n(n-1)/2；10 个团队就有 45 条沟通路径；亚马逊的「两个披萨团队」（6~8 人）规则就是「让 n 保持小」；讨论跨团队依赖管理（service catalog / internal API 规范 / 数据契约）。
  4. laew 借鉴：Conway 定律对照多 Agent 架构——Yolo/Plan/Main/Sub/QC/SessionContext 六角色就是「按能力切分的虚拟团队」，每个角色有独立 system prompt 与工具集；可类比微服务边界设计思路，让角色职责清晰、跨角色消息协议明确（当前已有）。

### CZ02 Team Topologies 四类团队与交互模式

- **预期档位**: medium~hard
- **考察维度**: 四类团队 / 三种交互 / 认知负载
- **对话脚本**:
  1. 四类团队：Stream-aligned（业务交付主力，对齐业务价值流）/ Enabling（能力赋能，帮助其他团队掌握新技术）/ Complicated-Subsystem（复杂子系统专家，如 ML 引擎 / 风控引擎）/ Platform（内部平台，减少业务团队认知负担）；每个团队 5~9 人，目标 / 失败模式 / 与其他团队的边界不同。
  2. 三种交互模式：Collaboration（紧密协作——共建新系统）/ X-as-a-Service（服务消费——稳定后转入）/ Facilitating（赋能——Enabling 团队的典型行为）；讨论何时切换（Collaboration 通常是临时的，迁就稳定后转 X-as-a-Service，否则长期协作吞噬团队精力）。
  3. 认知负载三型：Intrinsic（领域本质复杂度，无法削减）/ Extraneous（工具 / 流程造成的——应该削减）/ Germane（学习新事物必须的——应该支持）；平台团队的核心使命就是「消灭 Extraneous 认知」——把构建部署、测试、监控从业务团队剥离出去。
  4. laew 借鉴：Platform 团队使命对照 laew 自身——laew 试图把 LLM Provider 切换 / 协议适配 / Session 管理从用户业务中剥离（用户只关心「提任务拿结果」），这就是一种 Platform 化；讨论 laew 还可以进一步消减哪些 Extraneous 认知（如多 Agent 编排细节对用户透明）。

### CZ03 DORA 与 SPACE：度量什么与怎么度量

- **预期档位**: medium~hard
- **考察维度**: DORA 四指标 / SPACE 五维度 / 指标陷阱
- **对话脚本**:
  1. DORA 四指标：部署频率（Deployment Frequency——精英团队按需多次）/ 变更前置时间（Lead Time for Changes——从提交到生产的小时数）/ 变更失败率（Change Failure Rate——失败部署比例）/ 平均恢复时间（MTTR——失败到恢复）；自评问卷定位 Elite / High / Medium / Low 四档；讨论 Google DORA 团队的 STALE 报告方法论。
  2. SPACE 五维度：Satisfaction & well-being（满意度与福祉）/ Performance（绩效——非单维）/ Activity（活动量——代码行数陷阱）/ Communication & collaboration（沟通协作）/ Efficiency & flow（效率与流）；SPACE 反对单一指标，强调问卷与系统数据结合。
  3. 度量陷阱：Goodhart 定律（「指标一旦成为目标就不再是好指标」——代码行数指标导致刷 commit）；DORA 四指标的「反向博弈」（小 commit → 频繁部署但低价值）；SPACE 强调满意度与福祉（防止「高产但疲惫」的伪优秀）。
  4. laew 借鉴：DORA 对照 laew 的 Session 主上下文连续性指标——可度量「平均多少轮后用户完成主任务」「SessionContext 摘要注入后的主任务成功率」作为 SPACE 中的 Efficiency & Flow 维度；讨论避免把 Session 数本身当指标（刷 Session 次数无意义）。

### CZ04 知识管理：第二大脑与组织记忆飞轮

- **预期档位**: medium
- **考察维度**: 个人 PKM / 团队知识共享 / 知识衰减
- **对话脚本**:
  1. 个人 PKM 三派：卡片派（Zettelkasten——卢曼 9 万张卡片，强调原子化与链接）/ 收集派（Logseq / Obsidian——先收再说）/ 输出派（Building in Public——以教代学）；三个派系在「输入即整理 vs 整理是输出环节」的根本差异；推荐「三派融合」工作流（输入用 Zotero / 整理用 Obsidian / 输出用博客）。
  2. 团队知识资产：Wiki（静态结构化）/ ADR（架构决策记录）/ Runbook（运维剧本）/ Engineering Handbook（新人手册）/ Confluence 评论历史；讨论「组织记忆飞轮」——决策→记录→回顾→改进决策；知识孤岛识别（同一问题被三个团队各自解决三次）。
  3. 知识衰减与保鲜：文档的「保质期」——架构图 6 个月、ADR 1 年、Runbook 1 季度；定期刷新机制（季度 wiki 健康检查 / ADR 年度评审 / Runbook GameDay 后修订）；讨论「文档所有权」——写入者不是所有者，使用者才是所有者（实践反转）。
  4. laew 借鉴：组织记忆飞轮对照 session_memory 表——当前是 SessionContext 单向写入，可考虑「回看 → 反哺」回路（用户删除某条历史摘要时记录原因，模型下次注入避免同类噪声）；讨论让 laew 的 SessionContext 输出结构化 ADR 模板供团队参考。

### CZ05 远程异步协作：writing-first 文化

- **预期档位**: medium
- **考察维度**: 异步协议 / 文档先行 / 时区工程
- **对话脚本**:
  1. writing-first 文化：GitLab 极端示例——所有决策必须有「议题文档」（issue / MR 描述），所有讨论必须可被新员工 6 个月后回溯理解；写作好处（思考清晰 + 信息共享 + 决策可审查）vs 写作成本（速度慢 / 即时反馈缺失）；讨论如何培养 writing-first 习惯（把会议改成 RFC review、把口头决策改成 MR 提交）。
  2. 时区工程：全球分布式团队的「时区加权中心」计算（团队成员地理分布 → 最优会议时区）；异步友好会议节奏（每周固定 1~2 个全员会议 + 大量异步 RFC）；On-call 轮值时区公平（不让某地区永远承担深夜值班）。
  3. 工具栈与协议：默认公开（Default to Public——GitLab 公开所有内部讨论）+ 透明决策日志（决策 → 链接 → 后续执行可追溯）；具体工具（Notion / Linear / GitLab / Slack 频道归档）；讨论「沟通渠道分层」（紧急同步用电话 / 重要决策用文档 / 日常同步用 IM）。
  4. laew 借鉴：writing-first 对照 laew 的 SessionContext 摘要——目前摘要偏「任务结论」缺少「决策理由」；可让摘要模板加「为什么这么处理」字段，让 Session 回看时能理解 Agent 当时的判断逻辑，类比 ADR 角色。

### CZ06 会议税与会议效率治理

- **预期档位**: simple~medium
- **考察维度**: 会议成本计算 / 会议分类 / 替代方案
- **对话脚本**:
  1. 会议成本公式：参会人数 × 时长 × 时薪——10 人 1 小时会 = 10 小时人工；用这个公式审计你团队一周的会议总开销（很多团队花在会议的时间 > 30%）；识别「最贵的会议」（决策会 / 评审会）vs「最没用的会议」（无议程同步会 / 状态汇报会）。
  2. 会议分类与替代：决策会 → RFC 评审（异步）+ 投票窗口（24 小时）；评审会 → PR/MR 评论（异步）+ 同步讨论仅限阻塞问题；状态会 → 看板（Asana / Jira 自动同步）+ 周报；一对一 → 异步清单（互相丢问题清单）；培训 → 录播视频 + 答疑 office hour。
  3. 会议纪律：必须议程（提前 24 小时发）、必须主持人（控时间 + 控话题）、必须决议（5 分钟结束前明确「下一步谁做什么」）、必须纪要（决议 + 行动项 + 截止时间）；给出「坏会议信号清单」——经常超时 / 经常跑题 / 经常没有决议 / 经常同一拨人重复讨论同一议题。
  4. laew 借鉴：会议成本公式对照 laew 用户与 LLM 交互——一次 prompt 调优往往要 3~5 轮（成本 = 5 × tokens × 单价）；让 laew 提供「精简版结论」自动总结前几轮对话，类比「会议纪要自动生成」——把交互成本降到单轮级别。

### CZ07 决策机制：共识 vs 咨询 vs 一人决策

- **预期档位**: medium~hard
- **考察维度**: 决策模式 / DACI 框架 / 决策日志
- **对话脚本**:
  1. 三种决策模式：Consensus（共识——所有人同意，速度慢但执行顺）/ Consultative（咨询——决策者参考意见后自决）/ Directive（指令——决策者直接拍板，参考信息但不必然接受意见）；决策模式选择 = 决策成本 × 可逆性 × 重要性。重要 × 不可逆 → Consensus；不重要 × 可逆 → Directive；中间 → Consultative。
  2. DACI 框架：Driver（推动者——执行协调）/ Approver（最终决策者——一人）/ Contributors（贡献意见——多领域）/ Informed（被告知者——利益相关方）；与 RACI 的区别是 DACI 明确「一个 Approver」，避免委员会主席制；写一份选型决策的 DACI 示例（前端框架选 React vs Vue）。
  3. 决策日志与可追溯：每项重要决策必须有记录——背景（为什么现在决策）/ 选项（考虑了哪些）/ 决策（最终选了什么）/ 理由（为什么）/ 风险（可能错的地方）/ 复盘日期（多久后回头看）；这就是 ADR 模板的核心；讨论决策反悔成本（技术决策可逆性低，反悔成本高——应该更慎重）。
  4. laew 借鉴：DACI 对照 laew 的 Agent 决策——当前 Plan Agent 独断决策「WorkFlow 拆解」，可加一个「决策可追溯」——记录「为什么把任务拆为 3 个 WorkFlow、为什么按此依赖排序」，让用户能在 QC 阶段质疑；类似企业决策的「Approver 透明度」。

### CZ08 远程团队信任建设与文化

- **预期档位**: simple~medium
- **考察维度**: 信任类型 / 文化载体 / 团队健康度
- **对话脚本**:
  1. 信任的两种：认知信任（Competence-based——相信你能做）+ 情感信任（Benevolence-based——相信你为我好）；远程团队天然缺乏情感信任（缺少共处 / 午餐 / 闲聊）；给三种建立方法：1-on-1 非工作话题 10 分钟 / 全员线下季度聚会 / 跨团队兴趣小组（读书 / 游戏）。
  2. 文化载体：传统公司靠物理环境（办公室标语 / 团队合影 / 节日装饰），远程公司必须主动制造「文化载体」——周会开场分享（轮流 5 分钟）/ 团队播客 / 内部 newsletter / 「荣誉墙」（每月表彰）；讨论 Slack emoji 反应作为微文化的形成路径。
  3. 团队健康度信号：好信号——会议有人主动反对 / 离职者愿意回来 / 新人敢在第一周提改进 / 失败被公开讨论；坏信号——会议室政治 / 离职率高且集中 / 文档只敢写到「老板视角」/ 周末 IM 必回；给出季度「团队健康度自评问卷」模板（10 题匿名）。
  4. laew 借鉴：文化载体对照 laew 的 TUI 体验——TUI 横幅的「项目说明」也是一种文化载体（让用户感受到 laew 主动关注自己的工作上下文）；讨论给 laew 加「工作日常关怀」细节（长时间无响应时提示休息 / 连续失败时鼓励重试而非沉默）。

### CZ09 技术债治理：四象限与雷达图

- **预期档位**: medium~hard
- **考察维度**: 技术债分类 / 度量 / 治理节奏
- **对话脚本**:
  1. 技术债四象限：Mart Fowler 四象限——Reckless/Deliberate（明知故犯——「没时间重构」）vs Prudent/Deliberate（明知且规划——「先发布，后续有 ticket」）；Prudent/Reckless 是最坏的（明知却不规划）；讨论如何识别——「我现在打的 hack，未来会用 ticket 跟进吗？」。
  2. 度量技术债：SonarQube 的「技术债比」（修复时间 / 开发时间）/ Sigrid 的架构指标 / 自研「代码异味」统计（重复行数 / 圈复杂度 / 测试覆盖率 / 长函数占比）；讨论「软指标」如「新人 onboarding 时间」也能反映债务严重程度。
  3. 治理节奏：Boy Scout Rule（每次提交让代码比之前好一点——最低成本持续治理）/ 集中重构日（每月 1~2 天专门还债）/ 季度技术债清理 sprint（10%~20% 时间固定投入）；讨论「停下来还债」vs「边做边还」——前者一次性投入大、后者容易被业务挤掉。
  4. laew 借鉴：技术债治理对照 laew 自身的演进——CLAUDE.md 中「CLAUDE.md 提到的设计意图是 X，但当前代码是 Y」就是技术债；建议给 laew 加「内部 ADR」模块，记录每次架构决策与变更理由，让后续重构有迹可循，避免重构后丢失原始设计意图。

### CZ10 工程文化与人才留任：OKR 与晋升机制

- **预期档位**: medium
- **考察维度**: OKR 落地 / 晋升通道设计 / 离职成本
- **对话脚本**:
  1. OKR 落地：O（Objective，定性目标）/ KR（Key Result，可度量结果）的「60 分万岁」原则（KR 完成 0.7 是优秀、1.0 是超额）；OKR 与 KPI 的差异（OKR 是牵引、KPI 是考核）；讨论 OKR 失败模式——把 KR 当 KPI 100% 完成（失去牵引意义）/ O 太多（每季度 5 个目标等于没目标）。
  2. 晋升通道设计：双轨制（管理序列 + 技术序列——避免「优秀工程师被迫转管理」）/ 级别能力模型（IC1~IC6 / M1~M6 各有明确能力定义）；避免「年度绩效排名强制分布」（损害协作文化）；讨论「成长叙事」——晋升答辩要讲「我从 X 到 Y 发生了什么」。
  3. 离职成本与留任：替换成本估算（3~6 个月新人上手期）；离职信号识别（沉默 / 态度变化 / 缺勤增加）；离职面谈（blameless exit interview——问「哪个环节让你失望」而非「为什么走」）；re-hire 友好（让离职成为可能的归处而非决裂）。
  4. laew 借鉴：OKR 对照 laew 的功能演进——CLAUDE.md 中「第 18 轮新增 8 维度 18 个 gap」就是 KR，可量化「已实现 gap 数 / 总 gap 数」作为版本进度仪表，让用户直观看到 laew 在变强；这种「公开进度」是工程文化的核心——让用户信任产品演进。
