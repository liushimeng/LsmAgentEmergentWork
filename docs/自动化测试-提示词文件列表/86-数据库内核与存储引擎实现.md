### CD01 B+ 树：数据库索引的经典数据结构

- **预期档位**: hard
- **考察维度**: B+ 树原理 + 插入删除 + 数据库应用
- **对话脚本**:
  1. B+ 树是关系型数据库最经典的索引结构。核心特性：(a) 所有数据在叶子节点（内部节点只存键）；(b) 叶子节点链表连接（支持范围查询）；(c) 节点大小 = 磁盘页大小（4KB / 16KB）；(d) 自平衡（所有叶子在同一层）。请解释为什么 B+ 树比 B 树更适合数据库（叶子链表 + 内部节点更胖 + 磁盘 I/O 更少）。
  2. B+ 树操作：(a) 查找（从根到叶，每层二分）；(b) 插入（找到叶子，满则分裂）；(c) 删除（找到叶子，不足则借位或合并）；(d) 分裂与合并的触发条件。请描述插入导致节点分裂的完整过程：叶子满 → 分裂成两个 → 中间键上提到父节点 → 父节点满则继续分裂。
  3. B+ 树在数据库中的工程优化：(a) 填充因子（Fill Factor，预留空间减少分裂）；(b) 前缀压缩（键的前缀共享）；(c) 批量加载（Bulk Loading，自底向上构建）；(d) 部分索引（只索引满足条件的行）；(e) 覆盖索引（索引包含所有查询列，避免回表）。请解释为什么「覆盖索引」能显著减少 I/O（索引即数据，无需访问表）。
  4. laew 的 B+ 树应用：laew 的 `session_memory` 表如果数据量增长到百万行，如何设计索引：(a) 按 `session_id` 查询 → B+ 树索引；(b) 按 `created_at` 范围查询 → B+ 树索引（叶子链表）；(c) 按 `agent_name + created_at` 联合查询 → 联合索引。讨论 SQLite 的 B+ 树实现与手动实现 B+ 树的权衡。

### CD02 LSM 树：写优化的存储引擎设计

- **预期档位**: hard
- **考察维度**: LSM 树原理 + Compaction + RocksDB
- **对话脚本**:
  1. LSM 树（Log-Structured Merge Tree）是写优化存储引擎的核心数据结构（RocksDB / LevelDB / Cassandra / HBase）。核心思想：(a) 写入先到内存表（MemTable）；(b) 内存表满后刷到磁盘（SSTable，Sorted String Table）；(c) 后台 Compaction 合并 SSTable；(d) 读取从 MemTable → 新 SSTable → 旧 SSTable。请解释为什么 LSM 树写性能远优于 B+ 树（顺序写 vs 随机写）。
  2. Compaction 策略：(a) Size-Tiered Compaction（大小分层，同大小 SSTable 合并）；(b) Leveled Compaction（按层合并，每层有序）；(c) 两种策略的读写放大权衡（Size-Tiered 写放大低读放大高，Leveled 反之）。请描述 RocksDB 的 Leveled Compaction：L0 允许重叠 → L1 及以下每层有序 → 每层大小是上一层的 10 倍。
  3. LSM 树的读取优化：(a) 布隆过滤器（Bloom Filter，快速判断键不存在）；(b) 块缓存（Block Cache，缓存热点数据块）；(c) 索引（SSTable 内置稀疏索引）；(d) 布隆过滤器的误判率与内存开销权衡。请计算 100 万元素、1% 误判率的布隆过滤器需要多少内存（约 1.2 MB）。
  4. laew 的存储引擎选择：laew 当前用 SQLite（B+ 树），如果改为 LSM 树（RocksDB）：(a) 写入性能提升（日志类数据顺序写）；(b) 读取性能可能下降（需要查多层）；(c) 存储压缩更好（SSTable 可压缩）。讨论 laew 的 `agent_memory` 表是否适合 LSM 树（写多读少 vs 读多写少）。

### CD03 MVCC：多版本并发控制的工程实现

- **预期档位**: hard
- **考察维度**: MVCC 原理 + 快照隔离 + PostgreSQL 实现
- **对话脚本**:
  1. MVCC（Multi-Version Concurrency Control）是主流数据库（PostgreSQL / MySQL InnoDB / Oracle）的并发控制机制。核心思想：(a) 每个事务看到数据库的一个快照；(b) 写操作创建新版本而非覆盖旧版本；(c) 读不阻塞写、写不阻塞读；(d) 版本链 + 可见性判断。请解释为什么 MVCC 比两阶段锁（2PL）更适合读多写少场景（读写不冲突）。
  2. PostgreSQL 的 MVCC 实现：(a) 每行有 `xmin`（创建事务 ID）和 `xmax`（删除事务 ID）；(b) 快照记录当前活跃事务列表；(c) 可见性判断：`xmin` 已提交且不在活跃列表中 → 可见；(d) VACUUM 清理不可见版本。请描述一个事务读取时的可见性判断逻辑：哪些版本对当前事务可见？
  3. 隔离级别与 MVCC：(a) 读已提交（Read Committed，每条语句新快照）；(b) 可重复读（Repeatable Read，事务开始快照）；(c) 快照隔离（Snapshot Isolation，PostgreSQL 的「可重复读」实际是快照隔离）；(d) 写偏斜（Write Skew）问题（快照隔离无法防止）。请用「医生排班」例子说明写偏斜：两个事务同时检查「至少一个医生在岗」然后同时请假。
  4. laew 的 MVCC 启示：laew 的会话历史如果支持「时间旅行」（查看历史版本）：(a) 每条消息有 `created_at` 和 `deleted_at`；(b) 删除是软删除（设置 `deleted_at`）；(c) 用户可以回滚到任意时间点。讨论这种「会话 MVCC」对调试和审计的价值。

### CD04 WAL 与恢复：数据库如何保证不丢数据

- **预期档位**: hard
- **考察维度**: WAL 原理 + ARIES + 崩溃恢复
- **对话脚本**:
  1. WAL（Write-Ahead Logging）是数据库持久性的基石：(a) 先写日志再写数据（Log before Data）；(b) 日志顺序写（快）；(c) 数据随机写（慢）；(d) 崩溃后通过日志恢复。请解释为什么 WAL 能保证「已提交事务不丢」（Commit 前日志已落盘）和「未提交事务不回滚」（通过 Undo 日志回滚）。
  2. ARIES 恢复算法：(a) Analysis 阶段（确定崩溃时的活跃事务和脏页）；(b) Redo 阶段（重做所有操作，包括未提交的）；(c) Undo 阶段（回滚未提交事务）；(d) LSN（Log Sequence Number）贯穿始终。请描述 ARIES 的 Redo 历史（History Redo）为什么需要重做已提交和未提交的操作（简化恢复逻辑）。
  3. WAL 的工程优化：(a) 组提交（Group Commit，多个事务一起 fsync）；(b) 双写缓冲（Double Write Buffer，防止部分页写入）；(c) 检查点（Checkpoint，定期刷脏页减少恢复时间）；(d) WAL 分段（PostgreSQL 的 WAL 段文件）。请解释为什么「组提交」能显著提升高并发写入性能（摊薄 fsync 开销）。
  4. laew 的 WAL 设计：laew 的 SQLite 已内置 WAL 模式，但 `agent_memory` 表如果需要更强的持久性：(a) 每次工具执行前写 WAL；(b) 崩溃后自动恢复到最后一致状态；(c) 支持「操作重放」（重放 WAL 重现问题）。讨论 laew 是否需要超越 SQLite 默认持久性的机制。

### CD05 查询优化器：SQL 如何被翻译成执行计划

- **预期档位**: hard
- **考察维度**: 查询优化 + 代价模型 + 执行计划
- **对话脚本**:
  1. 查询优化器是数据库的「大脑」，把 SQL 转成最优执行计划。流程：(a) SQL 解析 → AST；(b) 语义检查（表 / 列是否存在）；(c) 逻辑优化（谓词下推 / 子查询展开 / 连接顺序）；(d) 物理优化（选择算法：Hash Join vs Nested Loop vs Merge Join）；(e) 代价估算（基于统计信息）。请解释为什么「连接顺序」对性能影响巨大（3 张表有 12 种连接顺序，10 张表有上亿种）。
  2. 基于代价的优化（CBO）：(a) 统计信息（行数 / 唯一值 / 直方图 / 相关性）；(b) 代价模型（CPU + I/O + 内存）；(c) 选择率估算（`WHERE age > 30` 选择率约 50%）；(d) 直方图（等宽 / 等高 / 顶部频率）。请描述优化器如何估算 `SELECT * FROM users WHERE age > 30 AND city = 'Beijing'` 的选择率。
  3. 执行计划阅读：(a) `EXPLAIN` 查看执行计划；(b) `EXPLAIN ANALYZE` 查看实际执行；(c) 关键指标（rows / actual rows / loops / time）；(d) 常见性能问题（全表扫描 / 嵌套循环 / 排序溢出）。请分析一个慢查询的执行计划：`Seq Scan on users (cost=0..1000 rows=10000)` → 问题是什么？如何优化？
  4. laew 的查询优化：laew 的 `session_memory` 表如果支持复杂查询（如「最近 7 天 Yolo 分类为 hard 的任务」）：(a) 需要索引（`created_at` + `task_level`）；(b) 需要统计信息（ANALYZE）；(c) 需要查询计划验证（EXPLAIN）。讨论 laew 是否需要引入查询优化器的概念（即使底层是 SQLite）。

### CD06 火山模型与向量化执行：查询引擎的执行架构

- **预期档位**: medium
- **考察维度**: 火山模型 + 向量化 + 执行引擎对比
- **对话脚本**:
  1. 火山模型（Volcano Model / Iterator Model）是经典查询执行架构：(a) 每个算子实现 `open()` / `next()` / `close()`；(b) `next()` 每次返回一行；(c) 算子通过 `next()` 链式调用；(d) 优点：实现简单、内存友好；缺点：虚函数开销大、CPU 缓存不友好。请解释为什么火山模型的「每行一次虚函数调用」在现代 CPU 上性能差（分支预测失败 + 指令缓存未命中）。
  2. 向量化执行（Vectorized Execution）：(a) 每次 `next()` 返回一批行（如 1024 行）；(b) 算子内部用 SIMD 处理；(c) CPU 缓存友好（数据连续）；(d) 代表系统（DuckDB / ClickHouse / Vertica / MonetDB）。请解释为什么向量化执行比火山模型快 3-10 倍（减少虚函数调用 + 利用 SIMD + 缓存友好）。
  3. 两种模型的工程权衡：(a) 火山模型适合 OLTP（行数少、延迟敏感）；(b) 向量化适合 OLAP（行数多、吞吐敏感）；(c) 混合执行（HyPer / Umbra 自适应切换）；(d) 编译执行（Code Generation，把查询编译成机器码）。请讨论为什么 DuckDB 选择向量化执行（嵌入式 OLAP 场景）。
  4. laew 的执行引擎启示：laew 如果要做「会话数据分析」（如统计每个 Agent 的调用次数）：(a) 用 SQLite 的火山模型（简单）；(b) 用 DuckDB 向量化执行（高性能）；(c) 用 DataFusion（Rust 原生查询引擎）。讨论 laew 是否需要内置 OLAP 能力。

### CD07 列式存储：OLAP 场景的性能密码

- **预期档位**: medium
- **考察维度**: 列存原理 + 压缩 + 分析场景
- **对话脚本**:
  1. 列式存储（Columnar Storage）把同一列的数据连续存储（而非行存储的同一行连续）。优势：(a) 分析查询只读需要的列（减少 I/O）；(b) 同列数据类型相同（压缩率高）；(c) 向量化执行友好（数据连续）。请解释为什么「SELECT avg(age) FROM users」在列存上比行存快 10 倍以上（只读 age 列 vs 读所有列）。
  2. 列存压缩技术：(a) 字典压缩（字符串 → 整数 ID）；(b) 行程编码（RLE，连续相同值）；(c) 位图压缩（低基数列）；(d) Delta 压缩（有序数值）；(e) LZ4 / ZSTD 通用压缩。请描述字典压缩的完整过程：原始数据 `["Beijing","Shanghai","Beijing"]` → 字典 `{0:"Beijing",1:"Shanghai"}` → 编码 `[0,1,0]`。
  3. 列存 vs 行存选型：(a) OLTP（点查 / 单行读写）→ 行存（MySQL / PostgreSQL）；(b) OLAP（聚合 / 分析）→ 列存（ClickHouse / DuckDB / Snowflake）；(c) HTAP（混合）→ TiDB / OceanBase；(d) 列存不适合频繁单行更新（写放大）。请讨论 laew 的会话数据分析是否适合列存。
  4. laew 的列存应用：laew 如果要做「Agent 性能分析」（统计每个 Agent 的调用次数 / 平均耗时 / token 用量）：(a) 导出为 Parquet 格式（列存）；(b) 用 DuckDB 分析；(c) 生成可视化报告。设计一个 laew 的 `/analyze` 命令：自动把会话数据导出为 Parquet 并用 DuckDB 生成分析报告。

### CD08 两阶段提交与分布式事务

- **预期档位**: hard
- **考察维度**: 2PC + 3PC + 分布式一致性
- **对话脚本**:
  1. 两阶段提交（2PC）是分布式事务的经典协议：(a) Phase 1（Prepare）：协调者问所有参与者「能否提交」，参与者锁定资源并回复 Yes/No；(b) Phase 2（Commit/Rollback）：全部 Yes 则发 Commit，否则发 Rollback。请解释为什么 2PC 是阻塞协议（协调者故障时参与者一直锁定资源）。
  2. 2PC 的故障场景：(a) 参与者故障（协调者超时后回滚）；(b) 协调者故障（参与者阻塞等待）；(c) 网络分区（部分参与者收到 Commit 部分未收到）；(d) 解决：3PC（三阶段提交，引入 CanCommit 阶段减少阻塞）、Paxos Commit（用共识算法替代协调者）。请描述 3PC 如何减少阻塞（PreCommit 阶段后参与者可自主决定）。
  3. 分布式事务的工程实践：(a) Saga 模式（长事务拆成小事务 + 补偿操作）；(b) TCC（Try-Confirm-Cancel）；(c) 本地消息表（最终一致性）；(d) Seata 框架（AT / TCC / Saga / XA 四种模式）。请用「转账」例子说明 Saga 模式：A 扣款 → B 入账 → 失败则补偿（A 退款）。
  4. laew 的分布式事务启示：如果 laew 部署为多节点（多个 Agent 服务协同）：(a) 会话状态一致性（哪个节点处理哪个会话）；(b) 工具执行幂等性（同一命令不重复执行）；(c) 失败补偿（SubAgent 失败后的回滚策略）。讨论 laew 是否需要分布式事务（当前单节点不需要，但多节点部署时必需）。
