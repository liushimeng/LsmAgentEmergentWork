### DP01 逻辑编程范式：Prolog 的事实、规则与查询

- **预期档位**: medium
- **考察维度**: 声明式语义 / 统一 / 回溯 / 闭世界
- **对话脚本**:
  1. Prolog 程序 = 数据库 + 推理规则：事实 `parent(tom, bob).` 规则 `grandparent(X,Z) :- parent(X,Y), parent(Y,Z).`，查询 `?- grandparent(tom, W).`；解释"程序不是被执行而是被询问"的范式反转，以及变量的大写约定与匿名变量 `_`。
  2. 针对上面的查询语义，讲**统一**（unification）：`parent(tom, X)` 与事实 `parent(tom, bob)` 可统一（X=bob）；统一不是赋值而是双向模式匹配——`f(X,a)` 与 `f(b,Y)` 统一出 X=b, Y=a；再用 `append/3` 的三行递归定义（`append([],L,L). append([H|T],L,[H|R]) :- append(T,L,R).`）展示"一个关系既是谓词又是数据构造器"。
  3. 基于上面的统一，看**回溯**与搜索顺序：Prolog 按子句书写序与左到右目标序做深度优先搜索；用"找出 tom 的所有孙辈"演示多解回吐（`;` 逐个要答案）；讲**闭世界假设**——没写的事实即为假（不像数据库的 NULL 语义），以及 `not` 的"失败即否定"（negation as failure）为什么要求目标无绑定变量才安全。
  4. 动手：用 SWI-Prolog（或在线解释器）建一个 15 条事实的家谱：定义 `sibling/2`（并排除自己）、`ancestor/2`（递归）；查询验证后再写 `path/2`（图上的可达关系）用于一个小型地铁换乘图，解释为什么同一个 `path` 谓词既能查"能否到"又能枚举所有路线。

### DP02 自制迷你 Prolog：统一算法与回溯机

- **预期档位**: hard
- **考察维度**: 统一实现 / occurs check / 深度栈与选择点
- **对话脚本**:
  1. 术语（term）的数据表示：`Var(id)` / `Atom(name)` / `Struct(functor, [args])` 三节点；统一算法 `unify(a,b,subst)` 的四象限分派（Var-Var / Var-NonVar / Struct-Struct 逐参 / 其余失败），其中关键操作是**走绑定**（walk：变量可能已绑定到另一个变量，要解到底）。
  2. 针对上面的算法，处理 occurs check：`unify(X, f(X))` 若不检查自指会构造无限项——标准 Proloc 出于性能默认关掉 occurs check 的历史原因；用"出现检查失败→抛 unify 错"的实验说明什么时候必须开。
  3. 基于上面的统一，实现求解机：目标栈（goal list）+ 选择点（choice point：记录已试到第几个子句）+ 深度优先主循环——取栈顶目标、遍历可统一子句、压入子句体；失败时回溯到最近选择点换下一子句；解释"变量替换要跟随回溯撤销"的两种实现（trail 尾迹记录 vs 不可变替换表传递）的性能取舍。
  4. 动手：用任意语言实现 300 行内的 mini-Prolog：解析 `p(X) :- q(X), r(X).` 语法、统一器、求解器；跑通 DP01 的家谱与 append/3；实现 `solve_all` 枚举全部解并去重（同一变量绑定集合）；用"左递归规则 `p(X) :- p(X).`"验证你的实现会死循环，讨论真实 Prolog 的深度限制/tabling（表格化）如何救它。

### DP03 Datalog 与递归推理：把事实算到不动点

- **预期档位**: medium~hard
- **考察维度**: Datalog 语义 / 不动点求值 / 与 Rete 的对偶
- **对话脚本**:
  1. Datalog = Prolog 的受限子集：无函数项（保证有限解空间）、纯声明式（无副作用）、面向关系的集合语义；规则 `path(X,Y) :- edge(X,Y).` `path(X,Y) :- edge(X,Z), path(Z,Y).` 求**不动点**（一直应用规则直到不再产生新事实）；解释为什么"没有函数项"保证了迭代必然终止。
  2. 针对上面的语义，实现朴素与半朴素（semi-naive）求值：朴素法每轮全量重算所有规则（重复爆炸），半朴素法只"用上一轮新产生的事实"做增量推导（delta 关系）；用 1000 条边的链图对比两者求 `path` 的迭代轮数与总工作量差异。
  3. 基于上面的求值，做经典应用：传递闭包（组织架构的"所有下属"）、 Same-generation（同代亲属）、可达性分析（静态调用图）；对比 Datalog（反向链/集合查询）与 Rete（前向链/流式事件，DG 维的规则引擎）的适用场景——批量推理 vs 每秒千条事件的增量决策。
  4. 动手：实现 mini-Datalog：规则解析 → 关系存储（HashSet）→ 半朴素不动点引擎；编码"edge 图 + reach 规则"与"某人所有祖先"两例验证；再实现一个实用小工具——从 `depends_on` 事实推出模块的传递依赖并检测循环依赖（提示：`cycle(X) :- reach(X,X)` 的妙用），对 laew 的 docs 目录结构抽象一个例子跑通。

### DP04 CSP 建模：八皇后与地图着色

- **预期档位**: medium
- **考察维度**: 建模三要素 / 约束表达 / 建模陷阱
- **对话脚本**:
  1. 约束满足问题的三要素：**变量**（每行一个皇后 `q1..q8`）、**域**（每变量 1-8 列）、**约束**（两两不同列 `qi≠qj`、不同对角线 `|qi-qj|≠i-j`）；把八皇后从"回溯算法题"翻译成"声明式模型"，讨论另一建模选择（64 个 0/1 变量 + 每行恰一个的约束）为什么明显更差（对称性爆炸）。
  2. 针对上面的对比，讲建模四象限：变量多 vs 域大、二元约束 vs 全局约束（alldifferent 一个顶 n² 个二元不等式——传播力更强）、冗余约束（加"皇后总数=8"这种被蕴含的约束反而提速）；用"表达力 vs 求解效率"解释为什么建模是一门手艺。
  3. 基于上面的手艺，做地图着色：邻接表 → 变量=区域、域={红绿蓝}、约束=相邻不同色；扩展到时间表着色（考试排期：一门课一变量、同学生选的课互斥）；说明为什么"四色定理"保证了平面图总能 4 色解，而求"最少用几色"就变成优化问题（要加二分尝试或目标函数）。
  4. 动手：写 `cspsolve(model)` 通用回溯求解器（model = vars/domains/constraints 三元组，约束为谓词函数）：跑通 8 皇后（数出 92 解）、中国 34 省级行政区 4 色着色（给定邻接表）、以及"把 1-8 填入 3×3 魔方使行列和相等"三例；统计各例的节点数与剪枝前后的对比（为 DP05 埋点）。

### DP05 搜索启发式与传播：MRV、前向检查与弧一致

- **预期档位**: hard
- **考察维度**: 变量/值排序启发式 / 约束传播 / 一致性强度
- **对话脚本**:
  1. 盲目回溯的两大加速器：**变量排序**——MRV（最少剩余值优先：先约束最紧的变量，失败早暴露）与度启发式（作为并列时的 tie-breaker，先选约束别人最多的）；**值排序**——LCV（最少约束值优先：先试给后续留下最多余地的值）；解释为什么 MRV 影响的是搜索树形状而 LCV 影响的是"首选解质量"。
  2. 针对上面的排序，上约束传播两级：**前向检查**（FC，赋值后立即删去邻变量域中的冲突值，域空即回溯）与**弧一致**（AC-3：队列维护待检弧 (Xi,Xj)，Xi 的每个值若在 Xj 域中无支持则删除，删了就重新入队 Xi 的其它邻弧）；说明 AC-3 在赋值前跑一次 = 把"注定失败的分支"提前整支砍掉。
  3. 基于上面的两级传播，量化收益：用 8 皇后与随机生成的 n 皇后（n=12~20）做对照实验——朴素回溯 / +MRV / +FC / +AC3 四档，记录赋值次数与总耗时；解释为什么传播越强单节点越贵但节点数越少，存在"传播强度性价比拐点"。
  4. 动手：给 DP04 的求解器插上这些插件（策略模式：`Heuristic`/`Propagator` 接口），输出统一对比表与搜索树规模曲线；再实现"求解数独的通用 CSP 前端"（27 个 alldifferent 约束的建模）验证 AC-3 版能秒解困难盘面，而朴素版在某个构造盘面上跑不出来。

### DP06 SAT 求解：CNF、DPLL 与单元传播

- **预期档位**: hard
- **考察维度**: 命题编码 / DPLL 框架 / 冲突驱动思想
- **对话脚本**:
  1. SAT 是约束求解的"汇编语言"：输入是 CNF（合取范式，子句=文字的或，公式=子句的与）；把三色地图着色编码成 CNF（每区域三个布尔变量"r 是红色"……+ 每区域至少一色 + 相邻不同色两个方向），体会"任何有限域 CSP 都能归约到 SAT"的通用性（代价是变量爆炸）。
  2. 针对上面的编码，实现 DPLL：`dpll(clauses)` = 单元传播（只有一个文字的子句直接赋真并化简）→ 纯文字规则（可省略）→ 选一个变量分支 `x=true` 递归、失败则 `x=false`；用可视化追踪在 8 皇后的 CNF 上跑 20 层，标注单元传播连续触发的"连锁化简"效果。
  3. 基于上面的基础版，讲工业求解器的跃迁——CDCL（冲突驱动子句学习）：冲突时分析出**冲突子句**（记录"这样走会矛盾"的浓缩教训）加入子句库、非时序回跳（回到冲突子句的第二新决策层）、VSIDS 活动度决策（冲突中出现的变量优先再决策）；说明为什么这些机制让 SAT 从玩具变成能解百万子句的工业引擎（芯片验证、依赖解析背后都是它）。
  4. 动手：实现带单元传播与简单学习的 mini-SAT（CDCL 完整实现为选做）；用"鸽笼问题 n+1 只鸽子 n 个笼"做压力测试（已知不可满足的难例族），画出你的求解耗时随 n 的增长曲线；对比把同一问题交给 Z3/minisat 求解的耗时，体会工业级实现的数量级差距。

### DP07 SMT 与 Z3 实战：让求解器懂算术与逻辑

- **预期档位**: medium~hard
- **考察维度**: SMT 分层 / 建模实战 / 优化目标
- **对话脚本**:
  1. SAT 只懂布尔，SMT（Satisfiability Modulo Theories）让文字带理论：线性算术 `x + y ≤ 10`、位向量 `(a & mask) == 0xff`、数组与未解释函数；架构 = SAT 骨架 + 理论求解器按需仲裁（DPLL(T)）；说明"理论组合"（QF_LIA/QF_BV 等片段名）为什么决定求解器选型与速度。
  2. 针对上面的认识，用 Z3 (Python API) 建第一个模型：排班问题——5 个班次 3 名员工，每人每周 ≥2 次 ≤3 次、不能连班、A 不上周末；变量=Int（员工×班次 0/1）、约束=布尔与算术混写；`check()` 返回 sat 后 `model()` 读出排班表，体会"声明约束→拿答案"与手写贪心的开发效率差距。
  3. 基于上面的模型，加**软约束与优化**：`Optimize` 接口——员工偏好表量化为代价（周日晚班罚 5 分、连班罚 3 分），`minimize(total_cost)` 求全局最优；讨论"软约束加权打分"与"硬约束不可违反"的组合表达力，以及为什么小规模（<万级变量）排班类问题 Z3 通常是性价比最高的选择。
  4. 动手：完整实现"三人值班周排班器"：输入偏好矩阵输出最优排班 + 总罚分；做三个变体实验——(a) 去掉连班约束看罚分降多少（量化约束的代价）、(b) 把人数改成 2（unsat，请求解出 unsat core 哪些约束冲突）、(c) 扩到 4 周（测试求解时间增长）；最后用 `Z3_print` 导出约束集做交接文档。

### DP08 实战一：会议排课系统——约束建模到违约解释

- **预期档位**: hard
- **考察维度**: 组合调度建模 / 组合爆炸控制 / UNSAT 诊断
- **对话脚本**:
  1. 场景：某机构 30 门课、8 个教室、5 天×6 时段、教师 15 人；约束清单三层——硬约束（教师同时段唯一、教室同时段唯一、教师不可用时段、连堂课必须相邻）、软约束（上午优先、同年级分散、教室容量偏好）、容量约束（选课人数 ≤ 教室座位）；写出变量设计的两个候选（课×时段布尔矩阵 vs 每门课一个时段整数变量）并论证后者在传播上更优。
  2. 针对上面的模型，处理课与课之间的对称性：同一年级同科目的两个平行班完全对称会造成解空间翻倍搜索——对称破缺约束（给平行班的时段变量强制 ≤ 序）；连堂课用"时段对"合枚举（{1,2},{3,4},{5,6}）建模替代相邻算术约束；说明这类"建模技巧"对求解时间的影响常常大于求解器调参。
  3. 基于上面的技巧，处理无解情况（UNSAT）：当约束过紧时 Z3 返回 unsat——用 unsat core 提取"最小冲突约束集"，把它翻译成人话（"张老师周二全天不可用 + 两门课只有周二有教室"）；讨论面向教务的交付物为什么必须包含"哪条约束卡死了"而不是空手而归。
  4. 动手：生成随机但有结构的测试数据（教师负荷 80%、10% 冲突注入），实现 `timetable_solve(input) -> Schedule | ConflictReport`：可解时输出按天分组的课表 + 软约束达成率统计，冲突时输出 unsat core 的中文解释；跑 10 组数据统计可解率、平均求解时长、最大冲突集大小，并给出"教师负荷降到多少就能全解"的敏感性分析。

### DP09 实战二：配送任务分配——时间窗、能力与软约束

- **预期档位**: hard
- **考察维度**: 分配类建模 / 时间窗约束 / 加权目标与松弛
- **对话脚本**:
  1. 场景：20 个配送单、6 名骑手；每单有取货点/送达点、时间窗（最早/最晚送达）、重量；骑手有位置、载重上限、工作时段；目标是"全部送达前提下总超时罚分最小"；建模第一步分解：**指派层**（哪个骑手接哪些单）与**排序层**（每骑手内部的访问顺序）耦合，先写混合整数模型（骑手×订单 0/1 + 位置顺序变量 + 到达时间传播约束），说明它是 VRP（车辆路径问题）的最小化版本。
  2. 针对上面的耦合，做解耦降维：固定指派 → 每骑手内部变成"带时间窗的 TSP"（可交给求解器或启发式）→ 外层用约束求解或局部搜索调整指派；讨论"精确解（Z3/MIP）在 20 单规模可行、200 单必须启发式"的规模分界与工程上常见的"分层求解"架构。
  3. 基于上面的分层，处理软约束与松弛：某些单时间窗冲突不可避免——引入 slack 变量（每单允许迟到分钟数，进目标函数罚分）让问题恒有解；再实现"最小牺牲集合"诊断（哪些单最值得外包/加人：固定其余约束后 minimize 该子集的 slack）；对比硬性 unsat 报错与软性给出可执行方案的交付差异。
  4. 动手：实现 `dispatch(input) -> PlanReport`：随机生成骑手与订单（注入 15% 时间窗紧张率），输出每骑手路线（按序站点 + 预计到达 + 超时标记）+ 总罚分 + 三个"运营建议"（加一个骑手可省多少罚分/哪些单建议改约/哪条路线载重贴上限）；对照贪心基线（最近单优先）量化约束求解方案的罚分改善幅度。
