### CE01 个人知识管理（PKM）：程序员的「第二大脑」

- **预期档位**: medium
- **考察维度**: PKM 方法论 + 工具选型 + 知识体系构建
- **对话脚本**:
  1. 个人知识管理（Personal Knowledge Management, PKM）是「系统地收集、组织、检索、分享知识」的方法论。经典框架：(a) Zettelkasten（卡片笔记法，Luhmann 发明，原子化 + 链接）；(b) PARA（Projects / Areas / Resources / Archives，Tiago Forte 提出）；(c) Building a Second Brain（CASSETTE → CODE 方法）；(d) Linking Your Thinking（LYT 框架）。请解释为什么「原子化笔记」（一条笔记一个想法）比「长文档」更容易复用。
  2. PKM 工具生态：(a) Obsidian（本地 Markdown + 双向链接 + 图谱视图）；(b) Notion（数据库 + 协作 + 云端）；(c) Logseq（开源 + 大纲 + 双向链接）；(d) Roam Research（双向链接先驱）；(e) 思源笔记（国产 + 块引用）。请对比 Obsidian 与 Notion 的优劣（Obsidian 本地优先 + 插件丰富 vs Notion 协作强 + 数据库灵活）。
  3. 程序员的 PKM 实践：(a) 代码片段库（按语言 / 场景分类）；(b) 错误解决方案库（错误信息 → 解决方案）；(c) 架构决策记录（ADR）；(d) 学习笔记（技术书 / 课程 / 文章）；(e) 会议纪要（行动项 + 决策）。请设计一个程序员的 Obsidian vault 目录结构：`00-Inbox / 01-Projects / 02-Areas / 03-Resources / 04-Archives / Templates`。
  4. laew 的 PKM 集成：laew 如何帮助用户管理知识：(a) `/save` 命令把对话中的关键结论保存到 Obsidian vault；(b) `/link` 命令自动发现相关笔记并建立链接；(c) `/review` 命令定期回顾笔记（间隔重复）；(d) `/search` 命令语义搜索笔记。讨论 laew 作为「知识管理助手」的设计哲学。

### CE02 Zettelkasten 卡片笔记法：从输入到创造的闭环

- **预期档位**: medium
- **考察维度**: Zettelkasten 方法 + 原子化 + 链接思维
- **对话脚本**:
  1. Zettelkasten（卡片笔记法）由德国社会学家 Niklas Luhmann 发明，核心原则：(a) 原子化（一条笔记一个想法）；(b) 用自己的话重述（不是摘抄）；(c) 链接相关笔记（建立知识网络）；(d) 定期回顾与演化。请解释为什么「用自己的话重述」比「复制粘贴」更能促进理解（强制加工 → 深度编码）。
  2. Zettelkasten 的三类笔记：(a) 闪念笔记（Fleeting Notes，临时想法，快速记录）；(b) 文献笔记（Literature Notes，阅读时用自己的话记录）；(c) 永久笔记（Permanent Notes，深思熟虑后写入知识库）。请描述从「闪念笔记」到「永久笔记」的完整流程：闪念 → 文献 → 永久 → 链接。
  3. 链接的艺术：(a) 显式链接（`[[相关笔记]]`）；(b) 隐式链接（通过标签 / 查询发现）；(c) 链接类型（支持 / 反对 / 扩展 / 类比）；(d) 链接描述（不只链接，说明为什么链接）。请用 Obsidian 的双向链接举例：写一条「B+ 树」笔记，链接到「数据库索引」「磁盘 I/O」「LSM 树」并说明链接关系。
  4. laew 的 Zettelkasten 支持：laew 如何帮助用户实践 Zettelkasten：(a) 对话中自动识别「可原子化的想法」并建议创建笔记；(b) 自动发现相关笔记（基于语义相似度）；(c) 定期提醒回顾（间隔重复算法）；(d) 生成「笔记链」可视化（知识图谱）。讨论 laew 作为「笔记助手」如何降低 Zettelkasten 的实践门槛。

### CE03 工具链自动化：让机器做重复的事

- **预期档位**: medium
- **考察维度**: 自动化策略 + 工具链 + 效率倍增
- **对话脚本**:
  1. 工具链自动化是「把重复性手动操作交给脚本执行」的工程实践。自动化层次：(a) 命令别名（`alias ll='ls -la'`）；(b) 脚本封装（`build.sh` 替代长命令链）；(c) 任务运行器（Make / Just / Task）；(d) CI/CD 流水线（GitHub Actions / GitLab CI）。请解释为什么「自动化」是开发者最重要的杠杆（一次投入，无限次复用）。
  2. 常见自动化场景：(a) 项目初始化（`cargo new` / `create-react-app` / 自定义模板）；(b) 代码格式化（`pre-commit` 钩子自动 `cargo fmt`）；(c) 测试运行（文件保存自动运行相关测试）；(d) 部署发布（`git tag` 自动触发发布流水线）；(e) 依赖更新（Dependabot / Renovate）。请设计一个「项目初始化」脚本：输入项目名 → 创建目录 → 初始化 Git → 创建 README → 创建 .gitignore → 首次提交。
  3. 自动化反模式：(a) 过度自动化（自动化脚本比手动操作还复杂）；(b) 脆弱自动化（环境变化就失效）；(c) 黑箱自动化（只有作者会用）；(d) 自动化债务（脚本堆积无人维护）。请讨论如何避免这些反模式：文档化、测试自动化脚本、定期清理。
  4. laew 的自动化能力：laew 如何帮助用户自动化：(a) `/automate` 命令把多步操作录制为可复用脚本；(b) `/schedule` 命令定时执行任务（如每天备份数据库）；(c) `/template` 命令管理项目模板；(d) `/hook` 命令管理 Git 钩子。讨论 laew 作为「自动化中心」的定位。

### CE04 环境复现：让开发环境「一键搭建」

- **预期档位**: medium
- **考察维度**: 环境管理 + 容器化 + 可复现性
- **对话脚本**:
  1. 环境复现（Environment Reproducibility）是「在任何机器上快速搭建相同开发环境」的能力。痛点：(a) 「我机器上能跑」；(b) 新成员 onboarding 慢；(c) 依赖版本冲突；(d) 系统差异（macOS vs Linux vs Windows）。请解释为什么「环境复现」是团队协作的基础（消除环境差异）。
  2. 环境复现工具链：(a) 版本管理器（`rustup` / `nvm` / `pyenv` / `asdf`）；(b) 虚拟环境（`venv` / `virtualenv` / `conda`）；(c) 容器（Docker / DevContainer）；(d) Nix（声明式包管理 + 可复现构建）；(e) dotfiles（配置文件版本管理）。请对比 Docker 与 Nix 的优劣（Docker 隔离强 vs Nix 更轻量 + 可组合）。
  3. DevContainer 实战：(a) `.devcontainer/devcontainer.json` 定义环境；(b) `Dockerfile` 定义基础镜像；(c) `features` 添加工具（Git / SSH / Rust）；(d) `postCreateCommand` 初始化项目；(e) VSCode 直接连接容器开发。请写一个 Rust 项目的 DevContainer 配置：基础镜像 `mcr.microsoft.com/devcontainers/rust` + 安装 `cargo-watch` + 初始化命令 `cargo build`。
  4. laew 的环境复现：laew 如何帮助用户：(a) `/init` 命令自动生成项目的 DevContainer 配置；(b) `/env` 命令检查当前环境（Rust 版本 / 依赖状态）；(c) `/sync` 命令同步环境配置到团队；(d) `/doctor` 命令诊断环境问题。讨论 laew 作为「环境管理助手」的价值。

### CE05 键盘流：高效编辑的肌肉记忆

- **预期档位**: simple
- **考察维度**: 快捷键 + 编辑效率 + 工具设计
- **对话脚本**:
  1. 键盘流（Keyboard Flow）是「用快捷键替代鼠标」的高效工作方式。核心理念：(a) 手不离键盘（减少上下文切换）；(b) 肌肉记忆（快捷键变本能反应）；(c) 组合键（`Ctrl/Alt/Shift` + 字母）；(d) 模式编辑（Vim 的 Normal / Insert / Visual）。请解释为什么「键盘流」比「鼠标流」快 3-5 倍（减少手移动 + 批量操作）。
  2. 编辑器快捷键体系：(a) 导航（`hjkl` / `Ctrl+f/b` / `gg/G`）；(b) 编辑（`dd` / `yy` / `p` / `u` / `Ctrl+r`）；(c) 搜索（`/` / `?` / `n/N` / `*`）；(d) 多光标（`Ctrl+d` / `Alt+Click`）；(e) 重构（`F2` 重命名 / `Ctrl+Shift+R`）。请描述 Vim 的「文本对象」概念：`ci"`（修改引号内内容）/ `dap`（删除整个段落）。
  3. 终端快捷键：(a) 行编辑（`Ctrl+a/e/w/u/k`）；(b) 历史（`Ctrl+r` 搜索 / `!!` 上一条）；(c) 进程控制（`Ctrl+c/z/s/q`）；(d) tmux 快捷键（`Ctrl+b` 前缀 + `c/d/%/"`）。请解释为什么 tmux 的 `Ctrl+b` 前缀与 Emacs 快捷键冲突（终端快捷键设计的命名空间问题）。
  4. laew 的键盘流设计：laew 的 TUI 如何优化键盘体验：(a) Vim 模式（Normal / Insert / Visual）；(b) 快捷键自定义（用户可重映射）；(c) 命令面板（`Ctrl+P` 快速执行命令）；(d) 多光标编辑（同时编辑多处）。讨论 laew 的 TUI 是否应该支持 Vim 模式（学习成本 vs 效率收益）。

- **预期档位**: medium
- **考察维度**: Wiki 设计 + 知识组织 + 团队协作
- **对话脚本**:
  1. 个人 Wiki 是「个人知识的中枢系统」，把零散笔记组织成可检索的知识库。设计原则：(a) 低摩擦记录（随时记录，不中断思路）；(b) 多维度组织（标签 / 链接 / 目录 / 时间线）；(c) 渐进式完善（先记录后整理）；(d) 可检索（全文搜索 + 语义搜索）。请解释为什么「低摩擦」是个人 Wiki 成功的关键（记录成本高于整理成本）。
  2. 个人 Wiki 工具：(a) Obsidian（本地 Markdown + 插件）；(b) Notion（数据库 + 协作）；(c) TiddlyWiki（单文件 Wiki）；(d) DokuWiki（轻量 PHP Wiki）；(e) MediaWiki（维基百科同款）。请对比 Obsidian 与 TiddlyWiki 的优劣（Obsidian 生态丰富 vs TiddlyWiki 单文件便携）。
  3. 个人 Wiki 的组织方法：(a) MOC（Map of Content，内容地图页）；(b) 标签体系（`#topic` / `#status` / `#type`）；(c) 链接网络（双向链接 + 反向链接）；(d) 模板（会议纪要 / 读书笔记 / 项目文档）。请设计一个程序员的个人 Wiki 首页：包含哪些 MOC 页？如何组织？
  4. laew 的 Wiki 集成：laew 如何与个人 Wiki 协同：(a) `/wiki` 命令把对话内容保存到 Wiki；(b) `/link` 命令自动发现 Wiki 中的相关页面；(c) `/moc` 命令生成内容地图；(d) `/sync` 命令同步 Wiki 与 laew 的会话记录。讨论 laew 作为「Wiki 助手」如何降低知识管理门槛。
