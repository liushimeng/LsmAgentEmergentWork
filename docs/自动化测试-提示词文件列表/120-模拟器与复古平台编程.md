### DL01 模拟器原理地图：模拟、虚拟机与高级仿真

- **预期档位**: medium
- **考察维度**: 仿真分层 / 精度光谱 / 技术选型
- **对话脚本**:
  1. 三个常被混淆的概念：模拟器（emulator，模仿另一台机器的硬件行为让原版程序无改动运行）、虚拟机（virtual machine，定义一套新指令集让同一程序跨平台）、高级仿真（HLE，不模仿硬件只重实现系统调用/API 层）；用 Wine、QEMU、Docker、RPCS3 各归一类。
  2. 针对上面的分类，讲精度光谱：指令集级（只保证指令结果对）→ 指令周期级（每条指令消耗正确周期数）→ 子周期/门级（信号级仿真）；解释为什么 NES 上某些游戏（依赖禁止组合的奇异行为）逼着模拟器走向周期精确；再说明前端-核心分离架构（libretro 模式）：核心只负责仿真机器状态、前端负责音频/视频/输入/存档——这一分层为什么让一个前端能跑几十种机器核心。
  3. 基于上面的分层与精度光谱，评估工作量：CHIP-8（周末级）→ GB（月级）→ NES（月级但周期陷阱多）→ PS1（年级团队）；解释精度要求与"游戏兼容率"的成本曲线，说明为什么商业复刻迷你主机普遍选 HLE 而非周期精确。
  4. 动手：写一个 100 行的"寄存器机"玩具模拟器（4 个寄存器 + 8 条指令 + 程序计数器），实现取指-译码-执行主循环与停机条件；它是后续 DL02~DL09 的脚手架，讨论把这个循环写对的关键点（PC 自增时机、指令副作用顺序）。

### DL02 CHIP-8：35 条指令与最小可玩模拟器

- **预期档位**: medium~hard
- **考察维度**: 指令译码 / 外设接口 / 完整闭环
- **对话脚本**:
  1. CHIP-8 是模拟器的"Hello World"：1977 年的解释型语言，35 条指令、4KB 内存、16 个 8 位寄存器、64×32 单色屏；画出它的内存布局（0x000-0x1FF 解释器区保留 / 0x200 起加载 ROM / 字体数据）与寄存器组（V0-VF、I、PC、栈、延时/声音定时器）。
  2. 针对上面的结构，实现译码：CHIP-8 指令是 2 字节大端，按最高 4 位分派再逐段拆位（`nnn`/`nn`/`n`/`x`/`y`）；实现 DXYN 绘图指令的 XOR 写屏 + VF 碰撞标志（精灵覆盖处像素 0→1 时置 1），说明这条指令为什么是 CHIP-8 的灵魂。
  3. 基于上面的核心，接外设：定时器按 60Hz 递减（与现代 CPU 主频解耦的定时器线程或帧内补偿）、16 键小键盘映射到 QWERTY 的 1234/QWER/ASDF/ZXCV 布局；讨论主循环用"每帧执行 N 条指令再刷屏"的节流策略（原始机器约 500 条/秒，现代机器裸跑会快 1000 倍）。
  4. 动手：实现完整 CHIP-8 并跑通测试 ROM（如 test_opcode.ch8 全指令自检）与一个公开游戏（如 PONG）；实现带消隐的 DXYN 修正（真实硬件绘制期间屏幕有闪，多数模拟器忽略它），记录你在哪个指令上踩了最深的坑。

### DL03 6502 指令集：寻址模式与周期表

- **预期档位**: hard
- **考察维度**: 寻址模式 / 标志位 / 指令实现
- **对话脚本**:
  1. 6502 是 NES/Apple II/C64 的心脏：8 位数据、16 位地址、A/X/Y 三个寄存器、六类指令（load/store/算术/移位/跳转/栈）；解释它"寄存器少但寻址模式丰富"的设计哲学——13 种寻址模式（立即/零页/零页X/绝对/绝对X/间接/间接Y……）才是表达力的来源。
  2. 针对上面的寻址模式，逐个实现地址计算函数并注意页边界惩罚：`LDA $1234,X` 若 `0x1234+X` 跨页则多耗 1 周期；给出官方 6502 周期表里"基础周期 + 跨页加成 + 分支跳转加成"的三级结构，说明为什么仿真周期数是后续时序正确的基础。
  3. 基于上面的实现，处理标志位的隐蔽规则：ADC/SBC 受十进制模式 D 标志影响（NES 的 6502 焊死了无 BCD，C64 有）；溢出标志 V 的计算（有符号溢出 vs 进位 C 的区别）；非法指令（illegal opcodes）如 LAX/SAX 为什么部分真实芯片会执行且部分游戏依赖它们。
  4. 动手：实现完整的 6502 核（合法指令集 + 标志位 + 周期计数），跑 nestest.nes 的自动化对比：把你的执行 trace（PC/指令/A/X/Y/P/SP/周期）与标准参考 log 逐行 diff，修正到前 500 行完全一致。

### DL04 内存映射与 MMIO：地址空间即总线

- **预期档位**: medium~hard
- **考察维度**: 地址空间布局 / 镜像 / 总线抽象
- **对话脚本**:
  1. 真实机器没有"内存"只有"地址空间"：CPU 地址线连着 RAM、ROM、PPU 寄存器、手柄，读 `0x2002` 不是读内存而是读 PPU 状态寄存器；画出 NES 的 CPU 地址图（$0000-$07FF 内存 + 2KB 三镜像 / $2000-$3FFF PPU 寄存器 + 每 8 字节镜像 / $4000-$401F APU+输入 / $4020-$FFFF 卡带区）。
  2. 针对上面的布局，实现总线抽象：`fn read(addr) -> u8` / `fn write(addr, val)` 内按区间分派到不同设备；解释镜像（mirroring）的含义——`$0800-$1FFF` 访问物理上同一块 2KB RAM，地址低 11 位有效——以及为什么正确实现镜像比"宽线性数组"更能通过怪游戏的测试。
  3. 基于上面的总线，讲设备间副作用：读 `0x2002` 会清除其中的 vblank 标志位、写 `0x4014` 触发 OAM DMA（暂停 CPU 513 周期）；说明这类"读写自带动作"正是 MMIO 与普通内存的本质差异，也是仿真 bug 高发区。
  4. 动手：实现 `Bus` 结构：CPU RAM + 镜像、PPU 寄存器占位、手柄移位寄存器（`$4016` 写 1 锁存/写 0 释放、读时逐位吐出 8 键状态）；写单元测试验证镜像地址等价性与"读清标志"副作用。

### DL05 卡带与 Mapper：bank 切换的艺术

- **预期档位**: hard
- **考察维度**: PRG/CHR 结构 / bank 切换 / Mapper 家族
- **对话脚本**:
  1. NES 卡带不只是 ROM：CPU 侧 PRG-ROM（16KB 单位）+ PPU 侧 CHR-ROM/RAM（图案表）+ 可能的额外 RAM 与电池；解释 iNES 文件格式（16 字节头：PRG/CHR bank 数、Mapper 号低 4 位、镜像方式、电池标志）的解析。
  2. 针对上面的格式，讲 Mapper 存在的理由：CPU 地址线只有 16 位（64KB）而大游戏 512KB，靠卡带上的开关电路把不同 16KB 窗口映射进 CPU 视野；以 Mapper 0（NROM 固定映射）、Mapper 1（MMC1：写 `$8000-$FFFF` 特定序列切 bank、5 位锁存器移位装载）、Mapper 2（UxROM：只切低位窗口）为例说明映射策略差异。
  3. 基于上面的映射，实现 Mapper 1（MMC1）：写地址触发的锁存器状态机（前 4 次写收集位、第 5 次写生效并复位）、控制寄存器决定 PRG bank 大小与 CHR 模式（4KB/8KB 粒度）、镜像方式可动态切换（水平/垂直/单屏/四屏）；说明为什么 MMC1 的"连续写同一地址 4 次再写 0"是复位惯用法。
  4. 动手：把 Bus 的卡带区改成 Mapper trait（`read_prg/write_prg/read_chr`），实现 NROM 与 MMC1 两个实现并运行分别使用这两种 Mapper 的公开 ROM；用"读 CHR 侧验证图案表确实随 bank 切换变化"的测试锚定行为。

### DL06 PPU 扫描线渲染：背景、精灵与滚动

- **预期档位**: hard
- **考察维度**: 渲染时序 / 精灵求值 / 视口滚动
- **对话脚本**:
  1. NES PPU 不是 framebuffer 而是逐扫描线实时合成：一帧 262 线（可见 240 + vblank 22 + 过扫描），每线 341 PPU 周期；背景渲染三级流水——命名表（tile 索引）+ 属性表（调色板组）+ 图案表（像素位平面 0/1）合成 2 位色号再查调色板。
  2. 针对上面的流水，实现精灵：OAM 256 字节存 64 个精灵（y/tile/attr/x），每扫描线"求值"出 y 范围命中的前 8 个（第 9 个置溢出标志，模拟真实的硬件 bug 才能过某些游戏）；绘制时 8x8/8x16 两种模式、水平/垂直翻转、优先级位（精灵0 与背景碰撞标志是《超级马里奥》计分栏的关键）。
  3. 基于上面的渲染，实现滚动：`PPUSCROLL` 两寄存器 + 写 `$2006` 的地址复用（先做指针后做滚动临时值），细粒度滚动产生的"每行换命名表"效应与 coarse/fine X/Y 的位拆分；解释为什么"状态栏固定 + 世界滚动"的游戏要在渲染中段写 `$2005/$2006` 实现分屏（raster effect）。
  4. 动手：实现完整 PPU 渲染管线输出 RGB framebuffer，运行任一经典平台跳跃游戏验证：背景滚动、精灵动画、精灵0命中中断三者同时工作；抓一帧与参考截图逐像素对比，统计不匹配像素数作为回归指标。

### DL07 APU 声音通道：方波、三角与噪声

- **预期档位**: hard
- **考察维度**: 波形合成 / 定时器与序列 / 采样输出
- **对话脚本**:
  1. NES APU 五通道：两个方波（旋律主声部）、三角（低音）、噪声（打击乐/音效）、DMC（采样回放）；每个通道都是"定时器驱动的状态机"——定时器按 CPU 时钟分频推进相位，相位查波形表输出；解释为什么方波有 4 种占空比（12.5%/25%/50%/75%）而音色各不相同。
  2. 针对上面的状态机，实现包络与扫频：音量包络（起音量 + 衰减速率或恒定）、长度计数器（查表 32 档，到 0 静音）、扫频单元（周期性调整通道频率，含"禁止扫到 <8 的边界规则"防止过扫描破音）；说明这些单元都挂在帧计数器的半帧/ quarter-frame 节拍上。
  3. 基于上面的通道，合成输出：所有通道线性混合（可加简单非线性混音近似真实硬件）→ 以 44.1kHz 重采样（APU 原生速率不是音频标准速率）→ 缓冲区策略（环形缓冲 + 下溢填充静音 vs 时域拉伸）；讨论为什么"音频驱动主循环"（以音频缓冲需求反推模拟推进量）是消除爆音的常用架构。
  4. 动手：实现方波×2 + 三角 + 噪声四通道（DMC 可选），运行任一游戏的标题画面听 BGM 是否音高正确；实现"帧计数器中断标志读清"语义，用《超级马里奥》的开场音乐做听感验收（跑调通常= 定时器分频错）。

### DL08 周期精确与同步陷阱：CPU、PPU 与 DMA 的三人舞

- **预期档位**: hard
- **考察维度**: 时序耦合 / 竞态 / 死循环保护
- **对话脚本**:
  1. NES 主时钟 21.47MHz 分频出 CPU（1/12）与 PPU（1/4），三者速率比 3:1；解释为什么"先跑完一整帧 CPU 再渲染一帧 PPU"的粗放架构会挂掉依赖精确定时的游戏——vblank 标志置位/清除的时机、sprite 0 命中在扫描线中点的位置，CPU 必须能"赶得上"。
  2. 针对上面的耦合，实现交错推进：主循环每步进 CPU 一条指令（获得周期 c），再把 PPU 推进 3c 周期、APU 推进 c 周期；说明这种"指令粒度交错"已能通过绝大多数游戏，以及哪些现象（如精确到周期的 raster 特效）仍需子指令粒度。
  3. 基于上面的交错，处理 OAM DMA 与竞态：`STA $4014` 触发 DMA 期间 CPU 停摆 513/514 周期（奇偶对齐差异）；vblank 读写竞态（`$2002` 在置位同一周期被读则读到 0 且标志被抑制）——这类"官方文档标注 TBD、靠测试 ROM 反推"的行为清单如何沉淀为回归用例。
  4. 动手：重构 DL02~DL07 的成果为交错主循环（CPU 一指令 → PPU 3 周期 → 每帧末换帧缓冲），实现 runaway 保护（同一 PC 连续执行超过 1e7 周期无中断则报错，防止"卡死在死循环而 UI 假死"）；用三个经典机型的测试 ROM（cpu_timing / ppu_vbl_nmi / sprite_hit）跑分并记录通过率。

### DL09 即时存档与确定性回放

- **预期档位**: medium~hard
- **考察维度**: 全状态序列化 / 确定性 / 回放格式
- **对话脚本**:
  1. 即时存档（savestate）= 把机器全部状态序列化：CPU 寄存器 + RAM + PPU 全部寄存器与 FIFO + APU 相位 + 卡带 bank 状态 + 手柄锁存；列出"最容易漏存"的五处状态（PPU 娄/移位寄存器/开放总线滞留值/wram 镜像脏位/DMA 对齐奇偶），说明为什么漏一个就会出现"读档后画面撕裂一帧"这类灵异现象。
  2. 针对上面的清单，设计序列化框架：versioned format（头部魔数+版本+各块长度）、每个设备实现 `save<W>`/`load<R>` trait、向前兼容（未知块跳过）；对比"整块 memcpy 结构体"（快但移植性差、含 padding 陷阱）与逐字段序列化的取舍。
  3. 基于上面的存档，实现电影回放（movie）：录制 = 存初始状态 + 每帧手柄输入序列；确定性回放要求模拟器无浮点非确定（禁用宿主时间/随机源）、输入序列驱动逐帧推进；解释"回放从第 N 帧失步"的排查思路（通常是某设备漏入了状态）。
  4. 动手：给模拟器加 savestate 与 movie：验证"存档→玩 100 帧→读档→重放同样输入，状态哈希逐帧一致"；实现"从回放任意帧分叉继续玩"（把回放输入段作为前缀）；用状态哈希（对全部设备状态做 FNV）作为每帧断言工具。

### DL10 调试器、trace 与图形查看器

- **预期档位**: medium~hard
- **考察维度**: 断点与跟踪 / 状态可视化 / 诊断工具链
- **对话脚本**:
  1. 模拟器是最好的开发工具：实现 CPU 级调试原语——单步/步过（遇到 JSR 先跑完子程序）、断点（PC 地址读写）、观察点（watchpoint：某地址被写入时断下）、寄存器窗口实时刷新；说明这些原语对"逆向原版游戏"与"自研 demo 开发"的双重价值。

  3. 基于上面的 CPU 层，做 PPU 可视化：命名表查看器（4 屏布局与当前镜像）、图案表查看器（512 tile 网格着色）、调色板查看器、OAM 精灵叠加视图；解释"打开图案表看一眼字体 tile 是否加载成功"如何把两小时的渲染 bug 定位缩短到一分钟。
  4. 动手：实现一个 TUI 调试面板（可复用 laew 的 CLI 渲染思路）：左 trace 滚动区 + 右寄存器/断点列表 + 底部命令行（`b $C000`/`watch $07`/`n 16`），接入 DL08 的模拟器；用它定位一个故意注入的渲染 bug（交换了图案表低位面 plane0/plane1 的顺序），记录从现象到根因的推理链。
