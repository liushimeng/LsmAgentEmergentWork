### BI01 VS Code 扩展开发：命令、视图与配置项
- **预期档位**: medium
- **考察维度**: Extension API + 命令注册 + 视图贡献
- **对话脚本**:
  1. VS Code 扩展的四大核心贡献点：`commands`、`menus`、`views`（TreeView/Webview）、`configuration`（package.json contributes）。先讲清它们在 activationEvents 触发后的生命周期和内存开销。
  2. 基于上面的贡献点，写一个最小扩展：注册一个命令 `laew.ask` 弹出输入框、把内容塞进剪贴板并提示「已复制到 laew」，同时在左侧 TreeView 显示最近 10 条历史。
  3. Webview 与 TreeView 的选型：TreeView 适合结构化只读数据、Webview 适合富交互（HTML/iframe）。给一个把 laew 的 SessionContext 摘要用 Webview 渲染成可折叠 Markdown 视图的最小实现。
  4. laew 的 Provider 管理 TUI 已经支持 list/add/use/del 五种操作。基于 BI01 讲的扩展 API，给 laew 实现一个 VS Code 扩展 `laew-vscode`：命令面板里直接调用 laew 的 provider CLI 并回填结果。

### BI02 VS Code 语言支持：语法高亮与 LSP 接入
- **预期档位**: hard
- **考察维度**: TextMate 语法 + LSP 客户端 + Semantic Tokens
- **对话脚本**:
  1. VS Code 的语言支持三层模型：TextMate 语法（.tmLanguage.json，仅 tokenize 着色）→ Language Server（LSP，语义分析）+ LSP 客户端（vscode-languageclient）→ Semantic Tokens（增量语义高亮）。先讲清三者职责边界。
  2. 基于 TextMate 语法，给一门自定义迷你语言 `mylang` 写语法高亮：支持 `fn`/`let`/`if` 关键字、`//` 单行注释、字符串字面量三部分。给出关键正则片段。
  3. 接入一个 LSP 服务器（如 rust-analyzer 或 pyright）的关键步骤：启动外部进程、传递 `initialize`/`didOpen`/`didChange`、处理 `completion`/`hover`/`definition` 响应，给最小可工作扩展代码。
  4. laew 的 Debug Agent 输出 `DebugReport/debug_report_*.md`，如果想给它做专门的 VS Code 语法高亮（识别「P0/P1/P2 问题报告」「优化建议」章节），给一个 TextMate 语法 + 一个本地 LSP 服务器（用 Rust 写 mini-lsp）的完整方案。

### BI03 Neovim 配置工程：Lua、lazy.nvim 与插件治理
- **预期档位**: medium
- **考察维度**: Lua 配置 + 懒加载 + LSP/Tree-sitter 集成
- **对话脚本**:
  1. Neovim 的 Lua 配置哲学：从 `init.vim` 迁移到 `init.lua` 后，模块化（`require('modules.lsp')`）、`vim.api.nvim_create_autocmd` 自动命令、`vim.keymap.set` 键位成为标配。先讲清这套机制的内存与启动开销。
  2. lazy.nvim 的「懒加载（lazy-loading）」机制：为什么不是所有插件都要在启动时加载？事件触发（`VeryLazy`/`BufRead`/`CmdUndefined`）、按键触发（`keys`）、函数触发（`ft`/`require`）三档策略差异。
  3. 基于 lazy.nvim 写一个最小配置：装 5 个核心插件（telescope / treesitter / lspconfig / nvim-cmp / gitsigns），每个都走懒加载，并给 telescope 绑定 `<leader>ff` 为模糊搜索文件。
  4. 把 laew 的 TUI 体验搬进 Neovim：写一个插件 `laew.nvim`，在浮动窗口里跑 `laew -p "..."`，接收输出并按流式响应回填到 Neovim buffer，给出 RPC 通信与回显机制的设计。

### BI06 dotfiles 工程：跨机同步与幂等安装
- **预期档位**: medium
- **考察维度**: 幂等脚本 + Git 追踪 + 跨平台兼容
- **对话脚本**:
  1. dotfiles 的两个核心原则：幂等（运行 10 次与运行 1 次结果一致）和无副作用（不污染用户未指定的配置）。先讲清 `stow`/`chezmoi`/`yadm` 三个工具的能力边界。
  2. 基于幂等原则，写一个 bootstrap.sh：检测 macOS vs Linux、备份现有 .zshrc、用 stow 软链 ~/dotfiles/zsh 到 ~/.zshrc，安装 Homebrew（macOS）/ apt 包（Linux）并跳过已安装的，给出关键片段。
  3. dotfiles 的「敏感信息」隔离：API key 不能入 Git。讲清三种模式——`.gitignore` + 手动拷贝、age/GPG 加密的 `git-crypt`、专用 secret 管理（`pass`/`Bitwarden CLI`）。
  4. laew 作为 dotfiles 的一部分被安装进 `~/.local/bin`，它的 SQLite 数据库却默认落在「根目录」（`current_exe()` 父目录）。基于 BI06 的幂等原则，给一份安装脚本设计：如何让 dotfiles 在多机上保持 laew 配置一致但数据库按机器隔离。

### BI07 Shell 定制：zsh 与 fish 的提示符、补全与钩子
- **预期档位**: medium
- **考察维度**: zsh 补全 + 提示符 + 钩子系统
- **对话脚本**:
  1. zsh 的「补全系统（Completion System）」：从 `_git`/`_docker` 等函数补全到 compsys 的 `_arguments`/`_describe` 语法。讲清「上下文补全（context-sensitive）」与「组补全（group）」的工程价值。
  2. 基于 compsys，给 laew 写一个 zsh 补全插件 `~/.zsh/completions/_laew`：补全 `-p`/`-f`/`-debug`/`--help` 选项、`/provider` 后接 `add|list|use|del` 子命令、`/provider use <id>` 后接数字 ID，给出关键代码。
  3. zsh 的 `precmd`/`preexec`/`chpwd` 三类钩子：在提示符渲染前、命令执行前、目录切换时各做什么？给一个 `preexec` 钩子：命令超过 30 秒执行就发通知的小示例。
  4. fish 与 zsh 的本质差异：fish 默认无 dotfiles 配置（web UI 配置）、所有补全是「即取即用」、不支持 POSIX 语法。基于 BI07 的钩子系统，laew 的 TUI 在 fish 下有没有兼容性问题？给一份测试矩阵。

### BI08 终端与字体工程：Nerd Font、连字与字形渲染
- **预期档位**: medium
- **考察维度**: Nerd Font 补丁 + 连字 + 终端渲染管线
- **对话脚本**:
  1. Nerd Font 是什么：把 Powerline 三角、Font Awesome 图标、Devicons 等图标合并进开源字体（Hack/JetBrainsMono/FiraCode）供终端用。讲清它通过 `Private Use Area (PUA)` Unicode 区段避免与标准文本冲突的设计。
  2. FiraCode / Iosevka 等「编程连字（Ligatures）」字体：把 `->`/`=>`/`!=`/`>=`/`===` 等多字符运算符合并成单个字形。讲清连字只在 IDE/终端启用时生效、对普通文本编辑器不影响。
  3. 终端的「字形渲染管线」：文本 → 字体查找（fallback chain）→ shaping（连字/合字/Kerning）→ rasterization。CJK 字符宽度（半角/全角）和 emoji 宽度（VS16）在终端里如何由 `unicode-width` 类算法决定。
  4. laew 的 TUI 用 crossterm 自绘渲染引擎，CJK 显示在历史 Bug（`6eea88e Provider List 按钮截断`）里被重点修复过。基于 BI08 的字体工程，给一份 laew TUI 字体兼容清单：测试矩阵、Nerd Font 图标在按钮文本里的位置规则、CJK 宽度预算算法。

### BI10 键位重映射与输入效率工程
- **预期档位**: medium
- **考察维度**: 系统层键位 + 应用层键位 + 输入法冲突
- **对话脚本**:
  1. 系统层键位重映射工具链：macOS 的 Karabiner-Elements（JSON 配置）、Linux 的 `xmodmap`/`sxhkd`、Windows 的 PowerToys Keyboard Manager。它们的能力边界（能否区分应用窗口、能否模拟组合键）。
  2. 基于 Karabiner-Elements，写一个把 Caps Lock 改造成 Hyper（Ctrl+Shift+Alt+Cmd）的复杂映射：单击 Caps Lock 直通 Esc、长按 200ms 切换大小写、Shift+Caps Lock 切换输入法。
  3. 应用层键位的「模态编辑（Modal Editing）」：Vim 的 Normal/Insert 模式、Kakoune 的 Selection-as-First-Class、Helix 的现代实现。对比它们的键位设计哲学：Vim 偏手不动、Kakoune 偏语义选择。
  4. laew 的 TUI 主屏是单行 `InputHandler` + 斜杠命令补全，键位是标准 Readline 风格（Ctrl+A/E/K/N/P/F/B）。基于 BI10 的键位重映射，给一份 laew TUI 键位优化建议：是否引入 Modal 编辑（Vim-like Normal/Insert 模式）？给可行性评估。
