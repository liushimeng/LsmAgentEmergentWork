### CA31 离线优先（Offline-First）设计哲学

- **预期档位**: medium
- **考察维度**: 设计理念 + 与传统云优先的差异
- **对话脚本**:
  1. 传统「云优先」架构假设网络永远在线，离线是异常状态；「离线优先」架构假设网络不可靠，离线是默认状态，云端是增强。请用对比表列出两种架构在「数据流向」「冲突解决」「用户体验」「网络假设」「开发复杂度」五个维度的差异。
  2. 离线优先的核心原则：本地优先（local-first / local source of truth）、同步为辅（sync as enhancement）、无网络也能用（fully functional offline）、乐观更新（optimistic UI）。请用 Notion / Figma / Linear 这类「离线优先」SaaS 产品举例说明每个原则的体现（无网络打开 Notion 仍能看到完整内容、编辑实时落本地、后台上传同步）。
  3. 离线优先的工程挑战：写冲突（两个设备离线编辑同一记录）、读陈旧（设备 A 看到的是几小时前的版本）、容量限制（本地存储有限）。请分析这三个挑战分别需要哪些技术解决（CRDT / 版本向量 / 分级缓存）。
  4. laew 的天然离线特性：所有 SQLite + 文件系统都在本机，无网络也能跑（仅 LLM 调用需要网络）。请评估 laew 在离线场景下的可用范围：完全离线下哪些功能可用（/help / 编辑历史 / 查看本地文件 / /export 纯本地数据）/ 哪些功能不可用（Yolo 任务分类 / Plan 方案生成 / SubAgent LLM 调用）。

### CA34 CRDT：Conflict-free Replicated Data Types

- **预期档位**: hard
- **考察维度**: CRDT 数学原理 + 工程实现
- **对话脚本**:
  1. CRDT 是一类保证「多个副本独立修改 + 自动合并 + 无冲突」的数据结构。请解释 CRDT 的两大类：(a) 基于状态的 CvRDT（Convergent Replicated Data Type，如 G-Counter / PN-Counter / OR-Set）；(b) 基于操作的 CmRDT（Operation-based Replicated Data Type，如 Operation-based OR-Set）。用 G-Counter（每个节点独立计数、查询时取最大值）举例说明「无冲突合并」。
  2. 实际应用最广的 CRDT 是 Yjs（基于 Y.Array / Y.Map / Y.Text）。请设计一个协同文档编辑场景：用户 A 在位置 5 插入「你好」、用户 B 在位置 5 插入「Hello」，最终两份副本合并后都能正确包含两段文本（顺序由时间戳决定）。说明为什么 Yjs 能做到这点（用 RGA / YATA 算法保证插入位置稳定）。
  3. Automerge 是另一款主流 CRDT 库（基于 JSON 文档），特点是数据模型可序列化（每次变更生成不可变 snapshot）。请对比 Yjs vs Automerge：性能（Yjs 更快）、API（Automerge 更接近 JSON）、生态（Yjs 更广泛）。讨论在协同编辑器 / 协同表格 / 协同白板三种场景下的选型。
  4. CRDT 的局限性：「无冲突」≠「符合用户意图」。两个用户同时删除同一行的不同字段，CRDT 能自动合并，但合并结果可能违反用户意图。请设计「冲突可视化 + 用户裁决」方案：当 CRDT 合并结果检测到可能违反意图时，弹出 UI 让用户选择「保留 A 版本 / 保留 B 版本 / 合并 / 自定义」。讨论在 laew 的 Session 上下文同步（同一用户多设备）是否需要 CRDT。

### CA35 Operational Transformation：OT 算法与实时协同

- **预期档位**: hard
- **考察维度**: OT 算法原理 + 与 CRDT 的对比
- **对话脚本**:
  1. Operational Transformation（OT）是另一种协同编辑算法，Google Docs 用 OT 实现。请解释 OT 的核心思想：每个操作是一个转换函数，把「在文档 X 上执行 op_a」转换为「在文档 X（已被 op_b 修改）上执行 transform(op_a, op_b)」。用「两个用户同时在位置 5 插入字符」的经典案例说明 OT 如何保证最终一致。
  2. OT vs CRDT 对比：OT 需要中央服务器协调（服务器接收 op、转换、广播）；CRDT 无需服务器（各副本独立合并）。OT 的优势是「意图保留」更好（可以理解操作语义）；CRDT 的优势是「去中心化」与「P2P 友好」。请设计场景：5 人团队协同编辑（需要中央协调）→ OT 更合适；100 人分布式 P2P 笔记 → CRDT 更合适。
  3. OT 的实现复杂度：变换函数必须满足「TP1」「TP2」两个性质（变换的对称性与幂等性），写错一个就会导致数据丢失。请分析为什么 OT 算法的测试覆盖率要求极高（>95%），以及 Google 在 Google Docs 中维护 OT 算法的工程经验（数千个测试用例 + 形式化验证）。
  4. 在 laew 中的 OT / CRDT 应用：当前 laew 是单进程单用户，无需协同。但若未来支持「多设备同步同一 Session」（笔记本 + 手机），需要保证两端的 Session 状态最终一致。请评估：Session 上下文（消息流）适合用 CRDT（append-only）；配置（provider 设置）适合用 LWW CRDT；任务历史（agent_memory）适合用 OR-Set CRDT（添加 + 删除两操作）。

### CA36 Edge Runtime：Cloudflare Workers / Deno Deploy / Vercel Edge

- **预期档位**: medium
- **考察维度**: Edge Runtime 架构 + 与传统 Serverless 的差异
- **对话脚本**:
  1. Edge Runtime 是部署在全球边缘节点（CDN POP）的运行时，请求就近处理（无需回源）。请对比 Cloudflare Workers（V8 隔离 + 30ms CPU 限制）/ Deno Deploy（Deno 内核 + 无冷启动）/ Vercel Edge（基于 Vercel 边缘 + Next.js 集成）三者的运行时差异、性能特点、生态成熟度。
  2. Edge Runtime 的限制：CPU 时间限制（Workers 30ms 免费版、300ms 付费版）、无 Node.js API（无 fs / 无 TCP socket / 无原生模块）、冷启动不可控。请分析这些限制带来的工程影响：长任务必须切片（如流式响应）、不能用 npm 包假设 Node.js API、数据访问必须通过 fetch。
  3. Edge Runtime 的优势：地理分布（200+ POP 点）、低延迟（< 50ms 到全球用户）、抗 DDoS（边缘节点吸收流量）。请设计一个「全球部署的实时 API」架构：用户请求落到最近 POP → 在 POP 上做身份校验 + 鉴权 + 简单逻辑 → 需要重操作时转发到中心 Region。这种「边缘入口 + 中心处理」是当前主流 SaaS 架构。
  4. Edge Runtime 与 laew 的潜在结合：laew 本身是本地 CLI，不需要 Edge 部署；但 laew 的「Provider 接入层」（调用 Anthropic / OpenAI API）可以在 Edge Runtime 上做一层「智能路由」：在边缘 POP 上缓存用户常用的 system prompt + 历史 context，做请求合并 + 重试 + 路由选择。讨论这种架构对延迟与成本的优化空间。

### CA37 边缘 AI 推理：ONNX Runtime / TF.js / 模型量化

- **预期档位**: hard
- **考察维度**: 端侧推理引擎 + 模型量化 + 性能优化
- **对话脚本**:
  1. 边缘 AI 推理指在终端设备（手机 / 浏览器 / IoT）运行 ML 模型，无需云端往返。请对比三大主流端侧推理框架：ONNX Runtime（跨平台、支持 100+ 模型格式）、TensorFlow.js（浏览器原生、GPU 加速）、Core ML（Apple 平台专属、ANE 硬件加速）的性能、模型兼容性、生态成熟度。
  2. 模型量化（Quantization）：把 FP32 模型压缩为 INT8 / FP16 / INT4，模型大小缩到 1/4 - 1/8、推理速度提升 2-4 倍，但精度损失 1-3%。请设计一个量化的 LLM 边缘部署方案：基础模型 FP16（~30GB）→ 量化 INT4（~4GB）→ 在手机/笔记本上用 llama.cpp / GGUF 加载。讨论量化后质量下降的可接受范围。
  3. WebGPU 是浏览器调用 GPU 的新标准（Chrome 113+ / Safari 17+），让端侧 AI 推理获得 GPU 加速。请对比 WebGPU vs WebGL vs WASM SIMD：WebGPU 是真正的通用计算 API（支持 compute shader）、WebGL 只能图形计算、WASM SIMD 是 CPU 指令级并行。设计一个「浏览器端 LLM 推理」演示：在 Chrome 中用 WebGPU 加载 GGUF 模型、流式输出。
  4. laew 的本地小模型集成：当前 laew 只能用云端 LLM Provider；如果集成 llama.cpp 本地推理，可在完全离线场景下做 Yolo 任务分类。请设计一个「云端 + 端侧」混合架构：默认走云端 Provider（强模型）；检测到无网络时自动降级到本地小模型（如 Qwen 1.5B INT4 / Llama 3.2 1B INT4）；用户在 TUI 中看到「当前使用本地模型」的提示。

### CA38 网络弹性设计：断网降级 / 重连同步 / 乐观更新

- **预期档位**: medium
- **考察维度**: 网络异常处理 + 弹性工程模式
- **对话脚本**:
  1. 网络弹性的核心是「网络随时可能断、应用必须持续工作」。请设计五种网络异常场景下的降级策略：网络全断（功能受限但核心可用）、网络抖动（重试 + 抖动退避）、高延迟（超时延长 + 流式响应）、丢包严重（多路复用 + 前向纠错）、IP 变化（连接迁移 + 状态恢复）。每种给出工程实现要点。
  2. 乐观更新（Optimistic Update）的核心思想：用户操作立即在 UI 上生效，后台异步同步到服务器。请设计一个「乐观更新」实现：用户编辑文档 → 立即在本地显示新内容 → 后台 PUT 到服务器 → 失败时回滚（保留原版本）+ 提示用户「同步失败，是否重试？」。讨论乐观更新在金融场景（转账）的高风险性（必须先确认服务器再展示）。
  3. 重连同步（Reconnection Sync）策略：网络恢复后需要把本地未同步变更全部上传。设计一个「增量同步」方案：本地维护一个 `pending_changes` 队列（每条变更带 ID + 时间戳 + 操作），网络恢复时按顺序上传 + 冲突检测 + 服务器确认。讨论为什么必须用「顺序队列」而不是并发上传（避免冲突）。
  4. laew 的网络弹性升级：当前 laew 的 LLM 请求失败时直接报错；可升级为「弹性请求」：失败自动重试（指数退避 + 抖动）+ 切换备选 Provider（用户配置了多个 Provider 时）+ 本地降级（无网络时使用本地缓存的历史回复）。请设计「/provider failover」配置命令：用户预设主备 Provider + 触发条件。

### CA39 同步协议：ETag / If-Match / 增量同步

- **预期档位**: medium
- **考察维度**: HTTP 同步原语 + 增量同步算法
- **对话脚本**:
  1. HTTP 提供几种同步原语：ETag（资源指纹，标识资源版本）、If-Match（条件请求，要求服务器资源 ETag 匹配才执行）、If-None-Match（缓存验证，本地副本与服务端一致则用本地）。请用代码示例说明「乐观锁并发控制」：客户端 GET 资源拿 ETag → 本地修改 → PUT 时带 `If-Match: <etag>` → 服务器检查 ETag 一致才接受，否则返回 412 Precondition Failed。
  2. 增量同步三方案：基于时间戳（`updated_at > last_sync_time`）、基于版本号（`version > last_version`）、基于游标（`WHERE id > last_id ORDER BY id LIMIT 100`）。请对比三者在「漏同步风险」「实现复杂度」「乱序容忍度」上的差异，推荐用版本号（递增整数最稳）。
  3. Change Data Capture（CDC）是数据库层面的增量同步：监听 binlog / WAL 捕获所有变更，发布到消息队列供下游订阅。请设计一个 SQLite CDC 方案：用 `sqlite3_preupdate_hook` 监听所有变更 → 序列化为 JSON → 写入本地变更队列（SQLite 或文件）→ 上传到云端。讨论 SQLite WAL 模式的 CDC 实现细节。
  4. laew 的多设备同步：当前 SQLite 是单设备本地文件，无同步机制。请设计一个「laew Cloud Sync」原型：本地 SQLite 写操作触发 CDC → 加密上传到 laew Cloud（用户账户下）→ 其他设备定期拉取 + 合并 + 写本地。讨论 SQLite 单文件跨设备同步的工程难点（文件锁 / 冲突解决 / 大文件传输）与替代方案（用 laew Cloud 作为 source of truth，本地 SQLite 作为缓存）。
