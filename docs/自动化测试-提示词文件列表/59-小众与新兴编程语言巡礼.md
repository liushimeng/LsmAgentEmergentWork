### BH01 Nim：Python 语法编译到 C 的系统语言
- **预期档位**: medium
- **考察维度**: 元编程 + 编译到 C + 静态分析
- **对话脚本**:
  1. Nim 的设计哲学是什么？为什么说它有 Python 的可读性却能编译成高效 C 代码？先讲清它的三种编译后端（C/C++/JS）和内存管理选项（GC/ARC/orc）各自适用什么场景。
  2. 基于上面的对比，用 Nim 写一个命令行 JSON 解析工具：输入一个 JSON 文件，统计顶层键的数量并打印。用 ARC 模式管理内存，给出完整可编译代码。
  3. Nim 的宏系统跟 Rust 宏的本质差异：Nim 宏是普通函数返回 AST，给一个用宏自动为结构体生成 `toJson`/`fromJson` 的示例。
  4. 如果把 Nim 当作 laew 的某个实验性模块的实现语言（譬如一个独立的代码分析脚本工具），编译产物和分发方式要怎么设计才能嵌入到 Cargo 构建流程里？

### BH02 Crystal：Ruby 手感加静态类型推导

- **对话脚本**:

  2. 基于上面的类型推导机制，用 Crystal 写一个 HTTP 服务：监听 8080，提供 `/health` 和 `/sum?a=1&b=2` 两个端点，用标准库的 `HTTP::Server` 实现。
  3. Crystal 的生态短板：很多 Ruby gem 没有原生绑定（Crystal 不能直接 require 一个 .rb 文件运行）。讨论用 `crystal-compatibility-layer` 包装 Ruby gem 的可行性和边界。

### BH05 Scala 3：given/using 与类型类编程

  3. Scala 3 的「扩展方法（extension methods）」和「类型 lambda」两个新特性给生产代码带来的好处：给一个用扩展方法给标准库的 `List[T]` 增加 `firstOption` 之外的 `secondOption` 的示例。

### BH10 Odin、V 与 Gleam：新生代语言的设计取舍
- **预期档位**: medium
- **考察维度**: 新生代语言定位 + 语言设计权衡
- **对话脚本**:
  1. 三种新生代语言的设计动机差异：Odin 想做「C 的现代替代品」（明确分配器 + 绑定时多态）、V 想做「比 Go 更简单比 Rust 更易上手」（30 秒编译 + nil safety）、Gleam 想做「Erlang VM 上的类型安全 ML」。先讲清三者的定位。
  2. 基于 Odin 的「明确分配器」哲学，写一个游戏粒子系统：用 `context.allocator = context.temp_allocator` 替代 C 的 malloc/free 配对，对比 Odin 的 `defer { ... }` 写法和 C++ RAII 的边界。
  3. V 的「nil safety」和 Rust 的 Option/Result 在编译器层面的差异：V 在编译期强制所有可能为 nil 的类型显式声明 `?int`，不允许悄悄解引用；这是更严格的工程约束还是更繁琐的形式？
  4. Gleam 跑在 BEAM（Erlang 虚拟机）上、与 Erlang 进程无缝互操作，这对 laew 想做的「长会话热升级」有什么启发？给一份 Gleam 替代 Erlang OTP 关键模块的可行性分析。
