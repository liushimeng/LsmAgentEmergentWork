# 38 代码审查与团队协作工程

> 编号段 AM01–AM10 · 聚焦 Code Review、Git 工作流、团队协作与工程文化

### AM01 Git 工作流：从 Git Flow 到 Trunk-Based
- **预期档位**: medium
- **考察维度**: 分支策略 + 发布管理
- **对话脚本**:
  1. 讲清 Git Flow 的 master/develop/feature/release/hotfix 五类分支各自的生命周期与适用场景。
  2. GitHub Flow 和 Git Flow 比做了哪些简化？为什么小团队更适合 GitHub Flow？
  3. Trunk-Based Development 的核心实践是什么？短生命周期分支 + 特性开关怎么配合？
  4. 为一个 10 人团队选型：从上面三种工作流里选一种，给出理由与落地计划。

### AM02 Pull Request 写作：让审查更高效
- **预期档位**: simple
- **考察维度**: PR 规范 + 沟通效率
- **对话脚本**:
  1. 一个好的 PR 描述应该包含哪些要素？给出一个模板（背景、变更、测试、截图、风险）。
  2. PR 大小对审查质量的影响：为什么建议 < 400 行变更？大 PR 怎么拆？
  3. 自审查（Self-review）的习惯：提交 PR 前自己先看一遍 diff，列出你通常会检查的 5 个点。
  4. 对比 GitHub、GitLab、Bitbucket 的 PR/MR 体验差异：审查流程、CI 集成、合并策略。

### AM03 Code Review 实战：建设性反馈
- **预期档位**: medium
- **考察维度**: 审查技巧 + 反馈文化
- **对话脚本**:
  1. 审查一段有性能问题的代码（如 N+1 查询），怎么写反馈既指出问题又不打击积极性？
  2. 区分"必须改"（阻塞合并）和"建议改"（nit:）的标准是什么？给出 5 个典型例子。
  3. 审查者 vs 作者的权力动态：怎么避免"审查变成挑刺"？建立团队审查文化的 3 个实践。
  4. 用 Danger 或 GitHub Actions 自动化审查：lint、测试覆盖率、PR 大小检查，写出配置。

### AM04 合并冲突：预防与解决
- **预期档位**: simple
- **考察维度**: 冲突解决 + 分支同步
- **对话脚本**:
  1. Git 合并冲突的根本原因是什么？用三方合并（ours/theirs/base）解释冲突是如何产生的。
  2. 解决一个实际冲突：用 VS Code 的合并编辑器或命令行，逐步展示解决过程。
  3. rebase 和 merge 在冲突处理上有什么差异？为什么 rebase 的冲突可能反复出现？
  4. 预防冲突的团队实践：频繁同步主干、小 PR、模块化代码、沟通机制，给出具体建议。

### AM05 提交信息规范：Conventional Commits
- **预期档位**: simple
- **考察维度**: 提交规范 + 自动化
- **对话脚本**:
  1. Conventional Commits 的 `type(scope): subject` 格式怎么用？列出常见 type（feat/fix/refactor/docs …）的含义。
  2. 提交信息里的"BREAKING CHANGE"标记有什么用？和语义化版本（SemVer）怎么联动？
  3. 用 commitlint + husky 在提交时强制校验信息格式，写出配置。
  4. 用 standard-version 或 semantic-release 根据提交历史自动生成 CHANGELOG 与版本号。

### AM06 代码风格与 lint 工程
- **预期档位**: medium
- **考察维度**: 代码质量 + 自动化
- **对话脚本**:
  1. 为什么团队需要统一的代码风格？从可读性、审查效率、减少无意义争论三个角度说明。
  2. 为 Python 项目配置 Ruff：替代 flake8 + isort + black，写出 pyproject.toml 配置。
  3. 为 TypeScript 项目配置 ESLint + Prettier：解决两者的规则冲突，写出 .eslintrc 与 .prettierrc。
  4. 用 pre-commit 框架在提交前自动运行 lint：写出 .pre-commit-config.yaml，包含多种语言钩子。

### AM07 结对编程与集体代码所有权
- **预期档位**: simple
- **考察维度**: 协作模式 + 知识共享
- **对话脚本**:
  1. 结对编程的 Driver/Navigator 模式怎么运作？各自的角色与禁忌是什么？
  2. 什么任务适合结对（复杂逻辑、新人 onboarding、关键模块），什么任务不适合（简单 CRUD、探索性 spike）？
  3. 远程结对用什么工具？对比 VS Code Live Share、Tuple、Pop 的体验差异。
  4. 集体代码所有权（Collective Code Ownership）和"代码禁区"文化怎么平衡？给出团队公约示例。

### AM08 技术债务管理：识别与偿还
- **预期档位**: medium
- **考察维度**: 债务量化 + 偿还策略
- **对话脚本**:
  1. 技术债务的四类（故意/无意、鲁莽/谨慎）怎么区分？各举一个代码示例。
  2. 用 SonarQube 或 CodeClimate 扫描一个项目，解读"技术债务比率"指标的含义。
  3. "20% 时间还债"和"每次 PR 顺手重构"两种策略各适合什么团队？
  4. 用架构决策记录（ADR）记录一个技术债务决策：背景、决策、后果，写出完整 ADR。

### AM09 团队工程文化：心理安全与持续改进
- **预期档位**: simple
- **考察维度**: 团队文化 + 工程实践
- **对话脚本**:
  1. 心理安全（Psychological Safety）在工程团队里为什么重要？给出 3 个提升心理安全的实践。
  2. 复盘（Retrospective）会议怎么开才不走过场？对比 Start/Stop/Continue、4Ls、Sailboat 三种格式。
  3.  blameless postmortem（无责任复盘）怎么写？给出一个模板（时间线、根因、改进项、跟进）。
  4. 用 DORA 指标（部署频率、变更前置时间、故障恢复时间、变更失败率）评估团队效能，怎么采集？

### AM10 开源协作：从贡献者到维护者
- **预期档位**: medium
- **考察维度**: 开源流程 + 社区运营
- **对话脚本**:
  1. 给一个开源项目提 PR 的完整流程：Fork → Clone → Branch → Commit → PR → Review → Merge。
  2. 怎么写好一个开源项目的 Issue 报告？给出模板（环境、复现步骤、预期 vs 实际、最小复现仓库）。
  3. 维护者怎么处理社区贡献：快速响应、友善反馈、合并标准、冲突处理，给出 SOP。
  4. 用 All Contributors 规范认可各类贡献（代码、文档、设计、翻译），写出配置与自动化流程。
