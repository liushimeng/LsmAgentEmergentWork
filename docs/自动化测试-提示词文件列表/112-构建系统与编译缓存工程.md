### DD01 Makefile 依赖图与增量构建

- **预期档位**: medium
- **考察维度**: Makefile 机制 / 依赖推导 / mtime 增量
- **对话脚本**:
  1. Makefile 的本质是「目标 ← 依赖」的 DAG：`a.o: a.c a.h` 表示 a.o 依赖两者，任一更新则重建；make 靠文件 mtime 比较决定重不重新编译；手写一个 3 个 C 文件项目的 Makefile 验证增量（改一个 .c 只重编一个）。
  2. 头文件依赖的坑：`a.c` include 了 `b.h`，改了 b.h 但 Makefile 没写依赖 → 不重建 → 诡异 bug；gcc `-MMD -MP` 自动生成 .d 依赖文件的机制。
  3. 基于上面的项目，讨论伪目标（.PHONY: clean）、隐式规则（`%.o: %.c` 模式匹配）、变量与函数（`$(wildcard)`、`$(patsubst)`）；Makefile 的时间戳误判场景（checkout 旧分支 mtime 回退）。
  4. 动手：在 /tmp 建一个 hello 项目（main.c / util.c / util.h），写带自动头依赖（-MMD）的 Makefile，依次验证：全量构建 → 改 util.h 两个文件都重编 → 只改 main.c 只重编它。

### DD02 Ninja 与构建并行调度

- **预期档位**: medium
- **考察维度**: Ninja 设计哲学 / 并行调度 / 依赖发现
- **对话脚本**:
  1. Ninja 为什么比 Make 快：Make 是「通用构建语言」（每次解析所有规则、递归调用），Ninja 是「构建汇编」（由 CMake/Meson 生成、语法极简、解析毫秒级）；对比同一项目 make 与 ninja 的空构建时间（no-op build，ninja 通常快 10 倍+）。
  2. 并行调度：Ninja 按 CPU 核数默认开 N+2 并发任务；调度本质是 DAG 拓扑序上的贪心——一个任务的所有依赖完成就立即调度；讨论链接阶段为何成为瓶颈（单任务无法并行）。
  3. 基于上面的调度模型，讨论 Ninja 的 deps log（.ninja_deps 记录上次构建发现的真实头依赖，加速下次增量）与 restat（输出 mtime 没变就不触发下游重建，省联锁重建）。
  4. 动手：用 CMake 生成同一小项目的 Unix Makefiles 与 Ninja 两套构建文件，`time` 对比全量构建与空构建耗时，观察 ninja 的 `[3/10]` 进度输出格式。

### DD03 构建缓存：内容寻址存储 CAS

- **预期档位**: medium~hard
- **考察维度**: CAS 原理 / 哈希指纹 / 缓存命中率
- **对话脚本**:
  1. ccache 的核心思想：编译输出 = f(预处理后源码 + 编译参数 + 编译器版本)，对这个输入算 SHA256 作 key，输出存缓存；命中就直接吐 .o 不跑编译器；为什么必须哈希预处理后的源码（宏展开后才公平）。
  2. 内容寻址存储（CAS）：key 就是内容哈希，天然去重、天然防篡改（哈希对不上就是坏了）；Bazel/Nix 的整个产物仓库都是 CAS；讨论 CAS 的 GC 问题（无限增长，需要 LRU 淘汰）。
  3. 基于上面的指纹模型，讨论缓存中毒与正确性：环境变量、绝对路径、时间戳宏（`__DATE__`）混进输入会导致缓存污染或命中率暴跌；ccache 的 direct mode 与 preprocessor mode 差异。
  4. 动手：安装 ccache，给 DD01 的项目套 `CC="ccache gcc"`，清空后构建两次，用 `ccache -s` 看第二次的命中率；再改一个注释观察是否仍命中（预处理后注释消失）。

### DD04 远程缓存与分布式编译

- **预期档位**: medium~hard
- **考察维度**: 远程缓存协议 / 分布式编译 / 带宽 vs 算力
- **对话脚本**:
  1. 团队场景：10 个开发者的机器各自编译相同代码是浪费——远程缓存把 CAS 搬到共享服务器（HTTP 简单存取或 REAPI gRPC 协议），一人编译全组命中；估算 1000 个目标文件的项目全命中时能省多少时间。
  2. 分布式编译更进一步：不只共享结果，还把编译任务分发到别人的空闲机器——distcc/icecc 把预处理后的源码发给远端编译；讨论分发粒度（按编译单元）与网络带宽的关系（源码 100KB vs 编译 5 秒，带宽够就划算）。
  3. 基于上面的分发模型，讨论正确性前提：远端编译器版本/头文件必须与本地一致，否则产物不同——这就是 hermetic 构建要解决的（引出 DD05）；Bazel remote execution 怎么打包「输入根」。
  4. 动手：两台机器（或本机+容器）搭 distcc：配置 DISTCC_HOSTS，给项目并行编译 `-j16`，观察任务分发日志；再讨论如果远端是不同 glibc 版本会发生什么。

### DD05 Hermetic 构建与 Bazel 沙箱

- **预期档位**: medium~hard
- **考察维度**: hermeticity / 沙箱执行 / 可复现性
- **对话脚本**:
  1. hermetic（密封）构建的定义：构建结果只依赖显式声明的输入，不依赖本机环境（/usr/include、环境变量、已装库）；为什么 Google 级别必须 hermetic——否则「我机器能编过」无法消除，缓存也不可信。
  2. Bazel 的沙箱实现：每个编译 action 在受限目录执行（Linux 用 mount namespace + bind mount 只暴露声明的输入文件）、网络默认禁用、时间戳归一化；验证方法：两次构建产物哈希应逐字节相同。
  3. 基于上面的沙箱，讨论真实工程的妥协：完全 hermetic 要求把编译器/系统库都纳入输入（toolchain 仓库化），迁移成本高；渐进路线——先禁网络、再锁编译器版本、最后容器化 toolchain。
  4. 动手：写一个小 Bazel/Meson 项目（或用 docker --network=none 模拟），验证断网构建是否成功；故意让某编译步骤偷偷读 /etc/hostname，看沙箱如何让它失败。

### DD06 交叉编译：sysroot 与工具链文件

- **预期档位**: medium
- **考察维度**: 交叉编译概念 / sysroot / CMake toolchain
- **对话脚本**:
  1. 交叉编译场景：x86 开发机编译 ARM 路由器固件；三要素——交叉编译器（aarch64-linux-gnu-gcc）、sysroot（目标平台的头文件与库副本）、目标三元组（arch-vendor-os-abi）。
  2. sysroot 是什么：目标系统根目录的只读拷贝（/usr/include、/lib），编译器用 `--sysroot` 把 #include 和链接指向它而非本机；为什么不能用本机 /usr/include（glibc 版本不匹配运行即崩）。
  3. 基于上面的概念，写一份 CMake toolchain 文件：指定 CMAKE_SYSTEM_NAME、C/C++ 编译器路径、CMAKE_SYSROOT、find_root_path 模式；讨论 pkg-config 在交叉编译下的坑（要用目标的 .pc 文件）。
  4. 动手：装 gcc-aarch64-linux-gnu，交叉编译一个 hello.c 生成 ARM64 可执行文件，用 `file` 验证架构，用 qemu-aarch64 或静态编译后在 x86 上跑通。

### DD07 Linux 打包实战：deb 与 rpm 包构建

- **预期档位**: medium
- **考察维度**: 包格式 / 打包工具链 / 运维分发
- **对话脚本**:
  1. deb 包解剖：本质是 ar 归档内含 control.tar.gz（元数据：包名/版本/依赖/维护脚本）+ data.tar.gz（文件树）；用 `dpkg-deb -R` 解开一个现成 deb 看结构。
  2. 手写 deb：建目录树（usr/bin/我的程序 + DEBIAN/control），写 control 文件（Package/Version/Depends/Description 字段），`dpkg-deb --build` 出包，`dpkg -i` 安装验证；postinst/prerm 维护脚本能干什么（建用户、注册 systemd 服务）。
  3. rpm 对照：spec 文件分段（%prep/%build/%install/%files）的「构建脚本即打包脚本」哲学 vs deb 的「先装到暂存目录再打包」哲学；rpmbuild 的 BUILDROOT 机制。
  4. 动手：把 DD06 编译的 hello 打成 deb 包（含 postinst 打印欢迎语），安装、运行、`dpkg -L` 列出文件、`apt remove` 卸载，走完完整生命周期。

### DD08 构建性能分析：找瓶颈再优化

- **预期档位**: medium
- **考察维度**: 构建剖析 / 关键路径 / 瓶颈分类
- **对话脚本**:
  1. 构建慢的四种病根：CPU 不足（编译任务排队）、IO 不足（小文件随机读）、单任务过大（链接超大二进制）、依赖串行（DAG 关键路径太长）；各用什么工具观测（htop / iostat / ninja log）。
  2. Ninja 构建剖析：`ninja -t graph` 导出依赖图找关键路径（最长依赖链决定最短构建时间）；Chrome 的 ninjatracing 把 .ninja_log 转成 Chrome trace 火焰图看时间线。
  3. 基于上面的分析，讨论优化手段的对应关系：关键路径长 → 拆库减依赖层级；单文件编译慢 → 拆文件/预编译头；IO 慢 → tmpfs/ssd；链接慢 → lld/mold 链接器、拆分动态库。
  4. 动手：给一个多文件 C++ 项目分别用 GNU ld 与 mold/lld 链接，`time` 对比；再用 `ninja -t commands` 找出编译最慢的 3 个文件并解释为什么（模板重/头文件大）。

### DD09 用 bash + inotify 手写 watch 构建脚本

- **预期档位**: simple~medium
- **考察维度**: inotify / bash 脚本 / 防抖
- **对话脚本**:
  1. watch 构建的需求：保存文件自动重新编译+测试；核心工具 inotifywait——`inotifywait -m -e modify,create,delete src/` 阻塞监听文件事件；写一个最简循环：事件来了就跑 make。
  2. 防抖（debounce）：编辑器保存常触发多个事件（write+rename），连跑 5 次构建浪费；加防抖——事件后等 300ms 收静默期，期间来新事件就重置计时。
  3. 基于上面的脚本，讨论健壮性：构建期间来的新变更要排队（不能丢）、构建失败不清屏（保留错误上下文）、Ctrl+C 要同时杀 inotifywait 子进程（trap EXIT）。
  4. 动手：写出完整 watch.sh（监听 → 防抖 → make → 终端通知成功/失败），对着项目改文件实测；对比现成工具（watchexec/entr）看它们多解决了什么。

### DD10 手写迷你构建系统：DAG + 指纹增量

- **预期档位**: hard
- **考察维度**: 构建系统内核 / 拓扑调度 / 内容指纹
- **对话脚本**:
  1. 项目目标：用 Python 写一个 100 行的迷你构建系统——配置文件声明任务（名字/输入文件/输出文件/命令），构建系统算 DAG、拓扑排序、并行执行、增量跳过。先设计任务文件格式（JSON/YAML）。
  2. 增量判定升级：不用 mtime 改用内容指纹（输入文件 SHA256 + 命令文本），指纹存 .build_state.json；为什么内容指纹优于 mtime（git checkout 回退 mtime 时不错误重建、也不漏重建）。
  3. 并行调度：就绪任务（依赖全完成）放进线程池，完成一个解锁下游；失败的 fail-fast 语义——立即停新任务、等已运行的结束、打印失败命令。
  4. 完整测试：造一个「gen → compile × 3 → link」的项目，依次验证：首次全量 → 改一个输入只重建一条链 → 并发数 >1 时总时间下降 → 失败任务正确中断。对照 DD01 的 Make 与 DD02 的 Ninja，说清你的迷你系统各抄了它们什么设计。
