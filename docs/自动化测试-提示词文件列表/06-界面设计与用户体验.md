# 自动化测试提示词 — 界面设计与用户体验（F01–F10）

> 使用说明见同目录 `README.md`。每条提示词在同一 Session 内按轮次顺序喂入。

## 维度说明

本维度考察 Agent 在**界面设计、TUI/CLI 设计、交互设计、用户体验**等方面的表现，
涵盖布局设计、配色方案、表格展示、错误文案、进度条、ASCII 架构图、Web 原型等主题。

---

### F01 TUI 布局设计
- **预期档位**: hard
- **考察维度**: 触发 Plan Agent 的设计类任务
- **对话脚本**:
  1. laew 的 TUI 目前是全量重绘的单行输入主屏。如果要加"左侧会话列表 + 右侧对话区"的双栏布局，你会怎么设计？先出方案。
  2. 双栏之间焦点怎么切换（Tab 键语义）？窄终端（<100 列）下怎么降级？
  3. 这个设计对现有 `src/tui/engine.rs` 的 Screen/Frame 抽象冲击大吗？给出改造点清单。
  4. 把最终设计写成 Markdown 方案文档，保存到 `tmpPlan/TUI双栏布局设计.md`。

### F02 CLI 帮助排版设计
- **预期档位**: medium
- **考察维度**: 信息层级设计
- **对话脚本**:
  1. 评价 `./laew --help`（实际跑一下）当前的排版：信息层级、分组、示例是否清晰？
  2. 参考 git/docker 等成熟 CLI 的帮助设计，提出三条具体改进。
  3. 设计一版新的帮助文案（含 EXAMPLES 段落），用 Markdown 代码块完整给出。
  4. clap derive 模式下实现 EXAMPLES 段落和彩色标题的要点是什么？

### F03 表单交互设计评审
- **预期档位**: medium
- **考察维度**: 交互细节评审（对照既有设计文档）
- **对话脚本**:
  1. 读 `docs/TUI界面与CLI渲染引擎/03-Tab表单与Provider操作设计.md`，总结 ProviderForm 的 5+1 Tab 交互模型。
  2. 从可用性角度评审这个设计：新用户最可能在哪一步困惑？给出两条改进建议。
  3. API Key"浏览态脱敏、编辑态明文"的约定合理吗？有没有更安全的替代交互？
  4. 如果要给表单加"字段校验（如 end_point 必须是合法 URL）"，设计校验触发时机和错误提示样式。

### F04 终端配色方案设计
- **预期档位**: medium
- **考察维度**: 视觉设计 + 可访问性
- **对话脚本**:
  1. 读 `src/tui/theme.rs`，梳理 laew 当前的颜色使用规范。
  2. 设计一套"成功/警告/错误/信息/强调"五色语义体系，给出具体 ANSI 色码选择及理由。
  3. 色盲用户（红绿色盲约占男性 8%）使用这个配色会有什么问题？怎么通过"颜色+符号"双通道解决？
  4. 终端不支持 256 色时怎么优雅降级？NO_COLOR 环境变量约定是什么？

### F05 进度条与加载态设计
- **预期档位**: medium
- **考察维度**: 等待体验的交互设计
- **对话脚本**:
  1. CLI 程序在等待 LLM 响应时，常见的加载态方案有哪些（spinner/打点/流式回显）？各有什么心理感受差异？
  2. laew 等待 LLM 时的当前表现是什么？（读代码或实际体验）有什么可改进的？
  3. 设计一个 spinner：要求显示已等待秒数，超过 30 秒提示"响应较慢"。给出实现思路。
  4. 流式输出（SSE）相比 spinner 为什么是更好的方案？改造代价主要在哪？

### F06 表格数据展示设计
- **预期档位**: medium
- **考察维度**: 数据可视化 + 宽度自适应
- **对话脚本**:
  1. 终端表格展示的核心难点是什么（对齐/宽字符/窄终端）？中英文混排对齐为什么容易崩？
  2. laew 的 `/provider list` 展示多条接入记录，设计一个表格布局：五列字段 + 当前激活标记。
  3. 当终端宽度不足容纳所有列时，设计三种降级策略（截断/换行/省略列）并选择其一说明理由。
  4. unicode-width 这类 crate 解决什么问题？没有它时中文字符宽度会被算错成多少？

### F07 错误提示文案设计
- **预期档位**: medium
- **考察维度**: 文案工程 + 用户心理
- **对话脚本**:
  1. 好的 CLI 错误提示三要素是什么（发生了什么/为什么/怎么办）？给一个反面教材改写示例。
  2. 为 laew 的"API Key 错误（401）"场景设计一条错误提示文案，要引导用户去 `/provider` 修复。
  3. 为"网络超时"和"模型返回格式解析失败"各设计一条文案，语气保持统一。
  4. 错误码体系要不要引入（如 LAEW-E1001）？分析利弊，并给出适合 laew 当前阶段的结论。

### F08 ASCII 架构图设计
- **预期档位**: medium
- **考察维度**: 纯文本视觉表达
- **对话脚本**:
  1. 用 ASCII 字符画一张 laew 六 Agent 编排架构图（Yolo→Plan/Main→SubAgent→QC→SessionContext）。
  2. 改进第一版：加上数据流方向（哪些写 SQLite、哪些只读）和各 Agent 持有的工具标注。
  3. 画图工具选择上，纯 ASCII、box-drawing 字符（┌─┐）、mermaid 三种方案各自适合什么场景？

### F09 Web 落地页原型
- **预期档位**: hard
- **考察维度**: 跨介质设计（CLI 工程做 Web 原型）
- **对话脚本**:
  1. 为 laew 设计一个单页产品介绍落地页的信息架构：首屏主张、特性矩阵、架构亮点、快速开始、文档导航。
  2. 写出完整的单文件 HTML 原型（内联 CSS，深色主题，终端美学风格），保存到 `tmpPlan/laew_landing.html`。
  3. 给页面加一个"模拟终端"区块：用打字机效果逐行展示一段 laew 多 Agent 协作的示例对话（纯 CSS/JS）。
  4. 检查无障碍：语义化标签、对比度、键盘可达性各做一轮自查并修复明显问题。

### F10 终端动效设计
- **预期档位**: medium
- **考察维度**: ANSI 控制序列 + 节制美学
- **对话脚本**:
  1. 终端里的光标移动、清屏、隐藏光标分别对应什么 ANSI 转义序列？各写出一个。
  2. 用 bash 写一个 10 帧的"进度扫描线"小动画（写入 `tmpPlan/anim.sh`），要求退出时恢复光标。
  3. 动效在管道/重定向环境下为什么要禁用？检测方法是什么（对照 laew 的 atty 分流）？
  4. 讨论：CLI 工具里动效的"节制原则"——哪些场景加动效提升体验，哪些场景是打扰？
