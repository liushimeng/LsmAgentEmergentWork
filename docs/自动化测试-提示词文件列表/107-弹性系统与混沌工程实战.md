### CY01 韧性模式全景：从重试到舱壁

- **预期档位**: medium
- **考察维度**: 六大韧性模式语义 / 选型决策树 / 组合使用
- **对话脚本**:
  1. 六模式概览：Retry（重试）/ Circuit Breaker（熔断）/ Bulkhead（舱壁隔离）/ Timeout（超时）/ Rate Limiter（限流）/ Fallback（降级）——每模式解决一类故障（瞬时 vs 持续 / 单请求 vs 全局 / 调用方 vs 被调方）；用一张矩阵表达「故障类型 × 应对模式」的覆盖关系，讨论为什么「重试 + 熔断 + 舱壁」是分布式调用最常见三件套。
  2. 选型决策树：先超时（避免无限等待）→ 再重试（仅对幂等操作）→ 再熔断（避免下游雪崩）→ 再舱壁（隔离资源耗尽）→ 最后降级（保证核心可用）；以「外部支付网关调用」为例走完决策树，画出最终组合的代码骨架（Rust 实现 trait `ResiliencePolicy` 装载六模式）。
  3. 模式组合的反模式：「重试 + 超时 + 熔断」三种同时开启会放大故障——重试放大流量、熔断切断请求、超时决定何时熔断；解释顺序与参数的耦合关系（重试超时 ≤ 熔断超时），并用单元测试验证「超时不重试时整体降级链路仍可控」。
  4. laew 借鉴：六模式对照 Compact Agent 的三级恢复（排水 → 折叠 → 暴露，详见 `agent/overflow.rs`）——都是「渐进降级、最后兜底」思路，讨论把舱壁思想引入 laew（SubAgent 并行度 3 即舱壁上限，避免单个重任务占满所有并发位）。

### CY02 指数退避与抖动四式

- **预期档位**: medium
- **考察维度**: 重试退避算法 / 抖动必要性 / 工程实现
- **对话脚本**:
  1. 基础公式：固定间隔（100ms × n）造成同步重试雪崩；线性退避（base × n）只是稍好；指数退避 `base × 2^n` 是工业界默认（AWS SDK / gRPC 默认行为）；手推 n=0..5 的延迟序列并解释为什么 n 通常封顶 6~8（再大也没意义）。
  2. 四种抖动：完全抖动（[0, cap] 随机）、等抖动（cap/2 + [0, cap/2] 随机）、截断指数抖动（min(cap, base × 2^n × rand)）、装饰器抖动（base × 2^n + rand × base × 2^n）；用 Python 实现四种并仿真 1000 次重试的分布直方图，对比「尖刺 vs 平铺」——抖动消除了同步尖峰。
  3. 工程细节：jitter cap 与 base 的取舍（base=100ms cap=30s vs base=1s cap=60s 的恢复时间差）、重试预算（每分钟最多 N 次防滥用）、幂等键（保证重试安全——同一请求 id 不会扣两次款）；用 Rust 写 `RetryPolicy::next_delay(attempt) -> Duration` 并附单元测试覆盖四式。
  4. laew 借鉴：重试预算对照 Agent 调用 LLM 的失败回流——Yolo 失败回流不应无限重试同一条提示（设 N=3），超过后建议「换写法」（拆分任务、降档、降 Provider）；讨论用抖动分散并发请求避免 Provider 端同时尖峰。

### CY03 熔断器三态机：从 Closed 到 Open 再到 Half-Open

- **预期档位**: medium~hard
- **考察维度**: 状态机设计 / 滑动窗口 / 半开探测
- **对话脚本**:
  1. 三态语义：Closed（正常计数失败）/ Open（直接拒绝 fast-fail）/ Half-Open（放少量请求探测）；状态转移条件—— Closed 阈值到 → Open，Open 冷却期到 → Half-Open，Half-Open 探测成功 → Closed，探测失败 → Open；画 ASCII 状态机图并标注每条边的触发条件。
  2. 计数器设计：朴素计数（固定窗口突刺问题：窗口边界成功率高掩盖窗口内失败率）；滑动窗口分桶（10 个 1 秒桶轮转——计算窗口内总失败率）；滑动窗口对数（按请求时间戳存环形数组，O(1) 滚动）；用 Rust 实现「滑动窗口对数 + 三态机」并测「持续失败」「突发恢复」「间歇失败」三种流量形态。
  3. 半开探测的陷阱：探测请求放多少（1 个太谨慎、10 个太激进——业界多取 5~10）、探测期间其他请求是放行还是拒绝（多数实现拒绝防止雪崩回流）、探测成功后多久完全恢复（直接 Closed vs 渐进 Closed——后者按比例逐步放开流量）；讨论 Netflix Hystrix 与 resilience4j 的设计差异。
  4. laew 借鉴：熔断器三态对照 Agent 编排的失败处理——某 Provider 连续失败可触发「熔断该 Provider」，冷却期后 Half-Open「试探一次」再决定是否切回；讨论 Provider 层熔断 vs Agent 层熔断的区别（粒度：单模型 vs 单会话链）。

### CY04 Bulkhead 舱壁：资源隔离的工程实现

- **预期档位**: medium~hard
- **考察维度**: 隔离维度 / 资源耗尽防御 / 监控与自适应
- **对话脚本**:
  1. 隔离维度：线程池舱壁（每个被调方独立线程池——Tomcat 默认）、连接池舱壁（数据库连接按业务分池）、信号量舱壁（轻量隔离——Semaphore N 限制并发）、进程舱壁（容器/微服务——最重也最彻底）；四种隔离粒度与开销对比（信号量 < 线程池 < 进程）。
  2. 资源耗尽防御：共享线程池的「慢调用拖垮快调用」问题——某慢查询占住所有线程，其他正常请求排队到超时；用 Rust 写 `BulkheadGuard::acquire(semaphore)` RAII 守卫实现「信号量舱壁」，演示「舱壁 A 被占满不影响舱壁 B」。
  3. 舱壁容量规划：静态分配（按预估最大 QPS × 平均延迟算容量——简单刚性）vs 弹性分配（队列动态伸缩——复杂但高效）；给出「舱壁溢出」的处理——溢出立即拒绝（fail fast）还是排队（queue with timeout）；讨论拒绝时的用户感知（429 + Retry-After 头）。
  4. laew 借鉴：舱壁对照 WorkFlow 并行 Semaphore 上限 3——这是天然的进程内舱壁；讨论跨任务的舱壁（同时跑多个 SubAgent 任务时，Yolo 与 Main-Work 各自一个舱壁，防止元任务占用过多资源）。

### CY05 故障注入：从 Chaos Monkey 到 Chaos Mesh

- **预期档位**: hard
- **考察维度**: 注入维度 / 爆炸半径 / 实验设计
- **对话脚本**:
  1. 注入维度矩阵：基础设施层（关机 / 断网 / CPU 满载 / 磁盘满 / 时钟偏移）→ 平台层（进程 kill / OOM / DNS 污染）→ 应用层（延迟 / 异常 / 状态污染）→ 业务层（脏数据 / 并发竞争）；每一层的注入工具（Chaos Monkey / Toxiproxy / Chaos Blade / Chaos Mesh）的覆盖范围对比。
  2. 爆炸半径控制：稳态假设必须先建立（否则注入无法判断「是否破坏了稳态」）；爆炸半径从「单实例 1% 流量」开始逐步扩大；稳态检测 = SLI 指标在窗口内方差 < 阈值；用 Rust 写 `SteadyStateHypothesis { metric, window, threshold }` 并用 Prometheus 指标验证注入前后偏离。
  3. 实验设计四步：1) 假设（Hypothesis：「数据库主从切换应在 30 秒内完成且 RPO=0」）→ 2) 注入（kill 主库）→ 3) 测量（自动恢复时长 + 数据丢失量）→ 4) 验证 / 修复（不达预期就修直到过为止）；给一个完整实验报告模板。
  4. laew 借鉴：稳态假设对照 SessionContext 摘要质量——注入「故意混乱的对话历史」看 Yolo 摘要能否保持主题不漂；把 laew 的多轮对话当作被试，注入干扰轮（中间插入无关话题）测主任务记忆稳健性。

- **预期档位**: medium
- **考察维度**: GameDay 流程 / 红蓝分工 / 演练剧本
- **对话脚本**:
  1. GameDay 流程：目标设定（演练哪个故障剧本）→ 邀请参与方（蓝队：业务运维 / 红队：注入者 / 观察员）→ 预演（所有人在场前阅读剧本）→ 注入 → 实时观察 → 即时复盘（hot wash）→ 正式 postmortem；与「真故障」的区别是「可预期、可回滚、可学习」。

  4. laew 借鉴：GameDay 对照 laew 的 provider 故障恢复——主动制造 Provider 故障（断网 / 改 end_point 为不存在的域）观察 Yolo 的回流行为（熔断 Provider？降档到 SubAgent？建议用户换 Provider？），记录真实恢复路径与文档承诺的差距。

### CY07 blameless postmortem 五段论

- **预期档位**: simple~medium
- **考察维度**: 复盘文化 / 根因分析 / 改进项跟踪
- **对话脚本**:
  1. 五段结构：1) 时间线（精确到分钟的事件序列）→ 2) 影响面（受影响的用户数 / 业务 / 收入 / 信任）→ 3) 根因（不止技术根因——包含触发因素 / 检测延迟 / 升级路径 / 沟通问题 / 流程缺口）→ 4) 修复（短期止血 + 长期预防）→ 5) 行动项（责任人 / 截止日 / 跟踪机制）；给一个真实事故（如 Cloudflare 2019 年全球宕机 30 分钟）的复盘骨架填充示例。
  2. blameless 的真正含义：不追责个人 ≠ 不追责流程——追责对象是「系统的弱点」而非「操作者的失误」；写「人因」（human error）时要继续追问「为什么人在那种情况下会犯错」（流程设计 / UI 反馈 / 培训是否充分）；讨论 blameless 不是「放过」而是「追到机制层」。
  3. 5 Whys 根因法：表面原因 → 第一层 Why → 第二层 Why……直到触及流程/系统层；举例「订单重复扣款」5 层追溯（用户连点 → 客户端未防抖 → 后端未做幂等校验 → 没有幂等键规范 → 架构评审 checklist 缺失）。
  4. laew 借鉴：blameless postmortem 对照 Debug Agent 输出——Debug Report 报告应避免「某 SubAgent 错了」的归因，改写为「失败发生在 X 条件下，触发 Y 设计假设不成立，建议改为 Z」；建议给 laew 加一份「自我事故复盘」模板（见 P01 边界测试对照）。

### CY08 优雅降级：从核心功能到开关矩阵

- **预期档位**: medium~hard
- **考察维度**: 降级策略 / 开关设计 / 用户感知控制
- **对话脚本**:
  1. 降级金字塔：核心功能保留（必须）→ 体验降级（能跑但慢/丑）→ 增值功能关闭（不影响核心）→ 完全失败（兜底文案）；写一份「电商大促降级清单」示例（核心：下单 + 支付；体验：商品图降级 + 推荐关闭；增值：评论 / 收藏 / 优惠券关闭；兜底：「服务繁忙，请稍后」）。
  2. 开关设计：每个降级点是独立开关（开关粒度：功能级 vs 接口级 vs 字段级）；开关状态三态（强制开 / 强制关 / 自动）；动态降级触发（错误率阈值 / QPS 阈值 / 资源指标——三者联动）；用 Rust 写 `FeatureFlag { name, default, override, auto_rule }` 的开关模型并配 Redis 持久化与 Admin UI 热更新。
  3. 用户感知控制：降级要让用户「知道但不焦虑」——静默降级（图片加载失败 placeholder）+ 显式降级（顶部黄色横幅 + 推荐兜底文案）；如何让用户主动选择降级（高级设置勾选「省流量模式」）；不要把降级文案写得过分悲观（让用户觉得快完蛋了）。
  4. laew 借鉴：降级金字塔对照 Compact Agent 的三档压缩（Light/Medium/Aggressive，详见 `docs/Context设置与自动压缩设计/`）——就是上下文溢出的优雅降级；讨论把降级策略扩展到更多资源（Provider 不可用 → 自动降级到本地模型 / SubAgent 单 Agent 模式）。

### CY09 自适应弹性：让系统自己学

- **预期档位**: hard
- **考察维度**: 自适应参数 / 反馈控制 / 策略学习
- **对话脚本**:
  1. 自适应参数：静态阈值（「错误率 > 50% 就熔断」）的局限（业务高峰低谷阈值不同）；动态阈值（基于历史 P95 + 3σ 的统计阈值）；平滑窗口（指数加权移动平均 EWMA 跟踪延迟）；用 Rust 写 `AdaptiveThreshold { p95_history, sigma, factor }` 计算动态阈值并画出 24 小时阈值曲线与真实错误的贴合度。
  2. 反馈控制环：经典控制理论借鉴——熔断器就是「误差信号」（失败率）→「控制器」（熔断器状态机）→「执行器」（拒绝请求）；讨论 PID 控制（比例 P+ 积分 I+ 微分 D）在自适应重试上的应用（P=当前错误、I=历史累积、D=错误变化率），以及稳定性（不震荡）的工程调试方法。
  3. 策略学习：A/B 实验框架是策略学习的原始形态；多臂老虎机（Multi-Armed Bandit）做策略选择（探索 vs 利用）；强化学习的现实边界（训练成本 / 安全护栏 / 离线评估）；举例某大厂的「自动参数调优系统」架构（实验平台 + 评估流水线 + 灰度发布）。
  4. laew 借鉴：自适应阈值对照 Yolo 任务档位分类——历史分类准确率作为反馈信号，调整 simple/medium/hard 边界（例如某类任务历史 hard 分类实际 medium 占比 80%，就降低该类任务的硬档阈值）；讨论「自动档位漂移」的可行性与人因审查必要性。

### CY10 灾难恢复：DR 演练与跨地域切换

- **预期档位**: medium~hard
- **考察维度**: RTO/RPO / 演练级别 / 切换决策
- **对话脚本**:
  1. RTO/RPO 定义：RTO（Recovery Time Objective——从故障到恢复允许多长时间）/ RPO（Recovery Point Objective——允许多少数据丢失）；按业务分级——支付核心 RTO 5 分钟 RPO 0 / 电商浏览 RTO 1 小时 RPO 5 分钟 / 内部 BI RTO 24 小时 RPO 1 小时；写一份业务影响分析 BIA 模板。
  2. DR 演练级别：L1 单机恢复演练（重启 / 切换主从——无业务影响）→ L2 数据中心级别切换（同城主备切换——影响部分用户）→ L3 地域级别切换（异地多活切换——影响全量用户）；每级演练频率（季度 / 半年 / 年度）与业务影响成反比。
  3. 切换决策：自动切换（速度快但风险高——可能脑裂）vs 人工决策（慢但可控——往往 too late）；折中：监控触发 + 人工确认的「5 分钟超时自动切换」机制；DNS 切换 vs IP 任播 vs 数据库流量切换的工程实现差异。
  4. laew 借鉴：DR 演练对照 laew 数据库迁移（CLAUDE.md 提到的「存量库打开时自动迁移」）——自动迁移本身是高风险操作（数据损坏可能），建议加「迁移前快照 + 二次确认 + 回滚预案」，让「数据库升级」像 L3 演练一样有标准剧本。
