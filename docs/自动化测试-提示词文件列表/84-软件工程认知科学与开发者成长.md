### CB01 认知负荷理论：程序员大脑的带宽管理

- **预期档位**: medium
- **考察维度**: 认知负荷三类型 + 工程实践 + 工具设计启示
- **对话脚本**:
  1. 认知负荷理论（Cognitive Load Theory, CLT）由 John Sweller 提出，把工作记忆的负荷分成三类：(a) 内在负荷（Intrinsic Load）由任务本身的复杂度决定，无法削减只能分摊；(b) 外在负荷（Extraneous Load）由信息呈现方式引入，是设计的敌人；(c) 相关负荷（Germane Load）是构建图式（Schema）时真正有益的认知投入。解释为什么「一次学太多」会让程序员崩溃（内在负荷 + 外在负荷同时爆表），为什么「好的 IDE」能省认知资源（减少外在负荷）。
  2. 编程任务中三类负荷的具体表现：(a) 内在负荷例子：理解一个分布式共识算法（Raft 涉及选举 / 日志复制 / 快照 / 成员变更）；(b) 外在负荷例子：命名糟糕的变量（`x` / `tmp` / `data1` 强迫大脑做映射）、不一致的目录结构、过深的嵌套回调；(c) 相关负荷例子：把「事务的 ACID」图式套用到理解分布式事务。请评估你最近写的一段代码里三类负荷的占比。
  3. 削减外在负荷的工程实践：(a) 命名规范（自解释优先）；(b) 函数单一职责（一次只需理解一件事）；(c) 一致性（项目内风格统一，减少切换成本）；(d) 渐进式披露（Progressive Disclosure，把复杂 API 拆成简单层）。举例说明 laew 当前 TUI 是否符合这些原则：TUI 的 banner / 主屏 / 子屏切换是否让用户每次只需关注一层？
  4. 内在负荷的分摊策略：(a) 任务分解（把大任务拆成可独立验证的小任务）；(b) 分块（Chunking）练习（反复做相似任务形成图式）；(c) 双重编码（Dual Coding，文字 + 图示同时呈现，强化记忆）。设计一个 laew 的「认知友好」交互模式：用户输入复杂任务时，Yolo 自动拆解为 3-5 步并在 TUI 显示「任务地图」，每步有清晰边界，让用户逐步确认而非一次看全。

### CB02 心流（Flow）：程序员最佳状态的神经科学

- **预期档位**: medium
- **考察维度**: 心流条件 + 工程环境设计 + 中断恢复
- **对话脚本**:
  1. 心流（Flow）由 Mihaly Csikszentmihalyi 提出，是「全神贯注 + 内在驱动 + 时间感消失」的巅峰状态。心流的核心条件：(a) 明确目标（知道在做什么）；(b) 即时反馈（做对做错立刻知道）；(c) 技能-挑战平衡（挑战略高于当前技能 5-10%）。解释为什么「难到崩溃」或「简单到无聊」都无法进入心流（缺少挑战或缺少成长感），为什么「心流编程」时解决 bug 的速度能达到平时的 3-5 倍（注意力全部聚焦 + 没有切换损耗）。
  2. 工程环境如何诱发心流：(a) IDE 的即时反馈（保存即编译、测试即运行）；(b) 任务规模合适（不接 1 个月才能完成的大任务）；(c) 干扰最小化（关 Slack / 邮件 / 通知）；(d) 工具流畅（命令直达、快捷键肌肉记忆）。请诊断你自己的开发环境：你当前 IDE / 编辑器 / 终端是否最大化心流条件？评分（1-10）并给出 3 个改进项。
  3. 心流杀手（Flow Killers）：(a) 中断（一次中断平均需要 23 分钟恢复深度工作，研究来自 Gloria Mark）；(b) 多任务并行（大脑根本无法真正并行，只是快速切换，认知成本陡增）；(c) 不确定性（不知道要做什么就一直焦虑）；(d) 反馈延迟（写完代码 10 分钟才能看到运行结果）。设计 laew 的「心流保护」机制：用户进入 `/focus` 模式后，Yolo 主动屏蔽无关提示（不打断 + 静默执行后台维护任务），任务完成才通知。
  4. 团队级别的心流文化：(a) 「无会议日」或「无会议下午」（保护深度工作时间）；(b) 异步优先（Slack 替代会议，但需明确响应时间预期）；(c) 减少跨时区同步会议（默认异步 + 录播）；(d) 给 senior 工程师「不被打扰时间」权限（核心时间窗）。请你为一个 5 人小组设计「心流保护章程」：具体规则 + 失败应对 + 度量方式（如 GitHub 提交时间分布、会议占比、Wakatime 深度工作时间）。

### CB03 深度工作（Deep Work）：在分心时代的核心竞争力

- **预期档位**: medium
- **考察维度**: 深度工作方法论 + 时间块管理 + 工具支持
- **对话脚本**:
  1. Cal Newport 在《Deep Work》中把工作分为深度工作（Deep Work，创造新价值、难复制）和浮浅工作（Shallow Work，重复性、易外包）。请对比三类工作：(a) 写新算法 / 设计架构（深度，价值极高）；(b) 写常规 CRUD（中等深度）；(c) 回答邮件 / 填表（浮浅，可自动化）。解释为什么深度工作在分心时代反而是稀缺资源（能深度工作的人越来越少），为什么能深度工作的人收入增长更快（高价值工作越来越集中到能深度的人手中）。
  2. 深度工作的四个哲学：(a) 禁欲主义哲学（完全隔离，如隐士）；(b) 双峰哲学（每天 4 小时深度 + 剩余浮浅）；(c) 节奏哲学（每天固定时间深度工作，形成节奏）；(d) 记者哲学（随时切换到深度状态，需要长期训练）。评估哪种最适合软件工程师（节奏哲学最现实 / 双峰哲学最高效），并为你自己设计一周的深度工作时间表。
  3. 浮浅工作最小化的具体方法：(a) 时间块（Time Blocking，把每天切成 90 分钟块，每块明确一个目标）；(b) 邮件批处理（每天 2-3 次集中处理而非实时响应）；(c) 任务看板（Kanban：Todo / Doing / Done，可视化进度）；(d) 「两分钟规则」（能在 2 分钟内完成的立刻做，否则排入看板）。请你为自己设计一个「每日时间块模板」：早晨 / 上午 / 下午 / 晚上各做什么。
  4. laew 的深度工作支持：(a) `/focus` 命令开启番茄钟（25 分钟深度 + 5 分钟休息）；(b) 番茄钟期间自动屏蔽所有非关键通知；(c) 完成后显示「本时段你完成了 3 个 SubAgent 任务 + 1 次提交」；(d) 日报统计：今日深度工作时长 / 完成度 / 最高产时段。讨论这种「Agent 当工作教练」的设计哲学：Agent 不只是执行工具，也是用户工作节奏的元认知伙伴。

### CB04 调试心智模型：从「为什么报错」到「找到根因」

- **预期档位**: medium
- **考察维度**: 调试方法论 + 心智模型构建 + 工具辅助
- **对话脚本**:
  1. 调试的核心是构建「程序实际行为」与「心智模型」之间的差异图。心智模型错误分三类：(a) 知识错误（不知道某个 API 的行为）；(b) 假设错误（以为某事会发生但其实不会）；(c) 路径错误（知道每一步但推断出错的执行路径）。请用一个真实案例说明每类：知识错误（以为 JavaScript `==` 会比较类型其实会强转）/ 假设错误（以为 Promise 同步执行其实微任务异步）/ 路径错误（递归出口正确但调用栈错）。
  2. 调试五步法（基于经典调试教材）：(a) 复现（Reproduce，找到稳定触发条件）；(b) 定位（Isolate，二分法 / 反证法缩小范围）；(c) 理解（Understand，读代码 + 看日志 + 设断点）；(d) 修复（Fix，最小改动解决问题）；(e) 验证（Verify，写回归测试确保不复发）。请你描述最近一次调试经历，对照五步法评估哪一步最耗时（往往定位占 80% 时间）。
  3. 高效调试的工具与技术：(a) 二分定位（git bisect 找到引入 bug 的提交）；(b) 打印调试（printf debugging，最朴素但有效）；(c) 断点 + 单步 + 变量观察（IDE 调试器）；(d) 静态分析（类型系统 + lint 提前发现）；(e) 故障注入（Chaos Engineering，主动制造失败）。请你为一个常见 bug 场景（生产环境偶发 500）设计排查方案：哪些工具组合使用？预期多久定位？
  4. laew 调试能力的扩展方向：(a) 自动 bisect：当用户报告「昨天还正常今天坏了」，SubAgent 自动运行 `git bisect` 找到引入问题的提交；(b) 失败模式库：把常见错误（OOM / 段错误 / 死锁）的排查步骤模板化，用户报错时自动匹配；(c) 「陪伴调试」模式：SubAgent 不只给最终答案，把思考过程外化（"我先排除 X，因为...；再检查 Y..."），让用户跟着学。讨论这种「调试教练」相比「直接给答案」的长期价值。

### CB05 技能习得曲线：从新手到专家的认知跃迁

- **预期档位**: medium
- **考察维度**: 技能习得阶段 + 刻意练习 + 成长型思维
- **对话脚本**:
  1. Dreyfus 模型把技能习得分为五阶段：(a) 新手（Novice，依赖规则，不知道情境）；(b) 高级初学者（Advanced Beginner，能识别可识别情境）；(c) 胜任者（Competence，能规划 + 自我修正）；(d) 精通者（Proficiency，凭直觉但能反思）；(e) 专家（Expert，无意识反应 + 模式识别）。请用真实案例对照每个阶段：新手写代码（照抄教程）、高级初学者（在熟悉场景能独立完成）、胜任者（能拆解中等复杂任务）、精通者（能看清大型系统的设计取舍）、专家（看一眼代码就知道 bug 在哪 + 怎么修）。
  2. 刻意练习（Deliberate Practice, Anders Ericsson）三大要素：(a) 跳出舒适区（练习略高于当前能力的任务）；(b) 即时反馈（练习结果能立刻评估）；(c) 高重复（重复练习同一类问题直到形成图式）。对比三类常见但低效的练习：(a) 重复做已经会的事（无成长）；(b) 做太难的事（一直挫败，无法形成图式）；(c) 看书不练（输入未转化为图式）。请你为自己设计一个「下一季度刻意练习计划」：3 个刻意练习目标 + 每周投入时间 + 反馈来源。
  3. 学习曲线曲度差异：(a) 陡峭曲线（语法、命令、API 调用等规则性知识，1-2 周入门）；(b) 平缓曲线（架构设计、性能调优、分布式系统等需要长期实践）；(c) 永久曲线（业务理解、行业知识、用户心理，永远在积累）。解释为什么「学会 Python 语法」≠「会用 Python」（前者陡峭曲线，后者平缓曲线），为什么 5 年经验 ≠ 5 次 1 年经验（重复陡峭曲线 vs 持续平缓曲线）。
  4. laew 作为「技能加速器」：当用户尝试 laew 不擅长的任务时（如系统级内核调试），laew 应该：(a) 老实承认能力边界（不是假装能做）；(b) 提供学习路径（推荐「先读这本书第 X 章」）；(c) 设计渐进任务（从简单引导到复杂）；(d) 观察用户操作模式（用户反复查文档 → 提示「要不要我把这步骤记下来？」）。讨论这种「Agent 当陪练」的设计 vs 「Agent 直接代劳」的差异：前者加速用户成长，后者可能让用户停滞。

### CB06 源码阅读方法论：从面对 100 万行代码到胸有成竹

- **预期档位**: hard
- **考察维度**: 源码阅读策略 + 工具辅助 + 学习效率
- **对话脚本**:
  1. 面对一个陌生的大型开源项目（如 Redis 30 万行 / PostgreSQL 100 万行），新人往往不知从何入手。源码阅读三层次：(a) 鸟瞰层（Bird's-eye，看 README / 架构图 / 目录结构 / 模块划分）；(b) 入口层（Entry Point，找到 main / 初始化函数 / 第一个被调用的核心函数）；(c) 深入层（Deep Dive，沿一个具体功能走完整链路）。请你描述你最近读过的最大项目，你用了哪个层次？平均每个层次花多久？
  2. 鸟瞰层工具与技术：(a) README + 官方文档（先读官方设计理念）；(b) 目录结构（`tree -L 2` 看模块划分）；(c) 关键文件统计（`cloc` 看代码量分布）；(d) 依赖图（`cargo tree` / `npm ls` 看模块依赖）；(e) GitHub Insights（看贡献者分布 + 提交频率 + Issue 类型）。请你为 Redis 5.0 设计一个鸟瞰层学习路径：先看什么 / 后看什么 / 关键文件清单。
  3. 入口层技巧：(a) 从最小可执行例子入手（找官方 example / test）；(b) 调试器打断点（设置断点看实际调用栈）；(c) 关键函数搜索（grep 核心 API 找所有调用点）；(d) 写一个 toy 复刻（用最简实现替代核心功能，理解原理）。请你为理解 laew 的 `MultiAgentOrchestrator` 设计一个入口层学习路径：从哪个文件读起 / 哪些函数值得深读 / 怎么画架构图？
  4. laew 辅助源码阅读：(a) `/arch <repo>` 命令：分析任意仓库输出鸟瞰层报告（README 摘要 + 模块图 + 依赖关系 + 关键文件）；(b) `/explain <file:line>`：解释一段代码的「为什么」（不是「做什么」而是「为什么这么写」）；(c) `/trace <symbol>`：追踪一个函数 / 变量的所有引用 + 调用链；(d) 渐进式注释：用户读代码时自动在关键位置补充「为什么」注释（基于 git blame + Issue 历史）。讨论这种「AI 阅读伙伴」相比「自己硬读」的效率提升（预估提升多少 %）。

### CB07 工程判断力（Engineering Judgment）：在不确定中做技术决策

- **预期档位**: hard
- **考察维度**: 工程决策框架 + 权衡分析 + 长期主义
- **对话脚本**:
  1. 工程判断力（Engineering Judgment）是在「没有标准答案」时做出合理技术决策的能力。它不同于算法题（算法有最优解，工程没有），不同于知识题（知识有事实答案，工程要看场景）。典型决策场景：(a) 自研 vs 用第三方库（短期快 vs 长期可控）；(b) 微服务 vs 单体（独立扩展 vs 复杂度爆炸）；(c) 新技术 vs 稳定技术（学习收益 vs 维护风险）。请你用一个最近的实际决策说明：你做了哪个选择？依据是什么？事后看对不对？
  2. 工程决策的四维框架：(a) 短期成本（开发时间 / 学习曲线）；(b) 长期成本（维护负担 / 技术债）；(c) 业务价值（功能上线速度 / 用户体验）；(d) 风险（人才流失 / 安全漏洞 / 供应商绑定）。用这个框架评估：「把数据从 MySQL 迁到 PostgreSQL」是合理决策吗？什么场景合理？什么场景不合理？
  3. 常见决策陷阱：(a) 沉没成本（已经投入 3 个月，再坚持半年 vs 放弃换方向）；(b) 光环效应（某技术在大厂成功 = 我们也该用）；(c) 群体思维（团队都同意时缺乏反对意见）；(d) 锚定效应（第一个方案成为参照系，后续都被它绑架）。请你描述一个你见过的真实决策陷阱，结果如何？
  4. laew 辅助工程决策：(a) `/decide` 命令：用户描述决策场景 → Yolo 输出四维评估表（短期 / 长期 / 价值 / 风险）+ 利弊清单 + 历史类似决策案例；(b) 反向论证：自动列出「不选这个方案的 5 个理由」，强制用户考虑反对意见；(c) 决策日志：把决策过程记入 `decision_log` 表（含当时考虑的因素 + 最终选择），未来 review 时可回顾；(d) 一致性检查：检测当前决策是否与项目过往决策冲突（如一直选 A 技术，这次突然选 B，提醒用户「这是新方向？」）。讨论这种「AI 决策伙伴」相比「PR Review」的补充价值：前者是决策前辅助，后者是决策后审查。

### CB08 技术领导力：从「写最好代码」到「让团队写出最好代码」

- **预期档位**: hard
- **考察维度**: 技术领导力模型 + 团队赋能 + 工程文化建设
- **对话脚本**:
  1. 技术领导力 ≠ 管理（Manager），更不等于「最厉害的程序员」。技术领导力的核心是「让团队的产出 > 每个人产出之和」，手段包括：(a) 设定技术愿景（让团队知道往哪走）；(b) 关键决策拍板（解决团队卡住的争议）；(c) 知识传播（Code Review / 技术分享 / 结对编程）；(d) 工程文化建设（让「质量」「自动化」「文档」成为团队共识）。请对比三类技术 Leader：(a) 1-on-1 教学型（花 50% 时间带人）；(b) 架构设计型（花 50% 时间画架构）；(c) 流程优化型（花 50% 时间改进工程流程）。
  2. 「10x 工程师」的真相：研究显示个体差异没那么大，真正决定产出的是：(a) 团队规模（5 人团队产出 vs 20 人团队，不是个体能力差距）；(b) 工程效率（CI/CD 自动化节省的时间）；(c) 协作质量（沟通成本）。一个 10x 工程师的 5 倍效率，可能源于：(a) 5 倍减少返工（写好测试 + 评审到位）；(b) 5 倍减少等待（自动化部署 + 快速反馈）；(c) 5 倍减少沟通（一目了然的代码 + 清晰的文档）。请你诚实评估自己：是「真 10x」还是「环境 10x」？
  3. 工程师的「影响力杠杆」分四档：(a) 个人贡献者（Individual Contributor，杠杆 = 个人产出）；(b) Tech Lead（杠杆 = 小组产出，5-10 人）；(c) 架构师（杠杆 = 跨团队产出，几十人）；(d) CTO（杠杆 = 整个公司技术产出，几百到几千人）。每一档的核心能力不同：IC 重深度 / Tech Lead 重广度 / 架构师重远见 / CTO 重战略。请你评估自己当前在哪一档，下一档需要什么能力跃迁？
  4. laew 协助技术领导力建设：(a) 自动生成项目架构图（`/arch` 输出可分享给团队的图）；(b) 自动生成技术决策记录（ADR 模板，把决策过程结构化）；(c) 自动识别技术债（重复代码 / 缺失测试 / 文档空白 → 输出技术债清单）；(d) 团队工程效率仪表盘（提交频率 / 代码审查时长 / 部署频率 / 故障率）。讨论这种「AI 团队助理」相比传统 BI 工具的优势：实时 + 自动化 + 与代码联动。

### CB09 反脆弱职业：构建越变越强的工程师之路

- **预期档位**: medium
- **考察维度**: 反脆弱原理 + 职业多元化 + 持续成长策略
- **对话脚本**:
  1. Nassim Taleb《反脆弱》提出三类系统：(a) 脆弱（Fragile，波动下崩溃，如玻璃）；(b) 强韧（Robust，波动下不变，如塑料）；(c) 反脆弱（Antifragile，波动下变强，如肌肉）。工程师职业的反脆弱策略：(a) 技能 T 型化（一专多能，深度 + 广度都有）；(b) 跨领域经验（在不同行业 / 公司 / 技术栈积累）；(c) 写作 + 开源（建立个人品牌，让机会主动找你）；(d) 教学相长（带新人 / 写博客 / 演讲，倒逼自己精进）。请你用反脆弱框架评估自己当前职业：哪些地方脆弱？哪些地方反脆弱？
  2. 工程师的「可迁移技能」清单：(a) 技术能力（编程 / 架构 / 调试 / 性能优化）；(b) 工程能力（Code Review / 测试 / 部署 / 监控）；(c) 软技能（沟通 / 文档 / 时间管理）；(d) 元能力（学习能力 / 抽象思维 / 系统思维）。其中「技术能力」贬值最快（5 年换一波），「软技能 + 元能力」增值越久。请你为自己设计「抗贬值学习计划」：每年重点投资哪些能力？
  3. 工程师常见的「职业天花板」与突破：(a) 技术深度瓶颈（专家级往上需要原创贡献）；(b) 管理转还是不转（个人贡献者路径在国内不成熟）；(c) 跨行业转型（35 岁焦虑）；(d) 副业 / 创业 vs 全职稳定（机会成本）。请你诚实评估：你 5 年后想成为什么？现在每天做的事是否在朝那个方向走？
  4. laew 作为「反脆弱职业伙伴」：(a) 技能评估：定期（每季度）询问用户「你这季度学了哪些新东西？」并自动生成技能雷达图；(b) 风险预警：检测用户技能单一化（90% 时间只用一种语言 / 一个框架）→ 提示「考虑拓宽技术栈」；(c) 个人品牌建设：自动把用户的优秀 SubAgent 任务产出整理成博客草稿（用户只需编辑即可发布）；(d) 职业教练对话模式：`/career <问题>` 用户问职业困惑，Yolo 不给标准答案而是问「你的核心价值观是什么？」/「你愿意为深度牺牲广度吗？」引导用户自己想清楚。讨论这种「AI 不替你做人生决策，但帮你厘清思路」的设计哲学。

### CB10 工程师的「为什么」：在 AI 时代守住思考的深度

- **预期档位**: hard
- **考察维度**: 第一性原理 + 长期主义 + 人机协作哲学
- **对话脚本**:
  1. 在 AI 越来越能写代码的时代，工程师的核心价值正在从「写代码」转向「想清楚做什么 + 为什么做」。第一性原理（First Principles Thinking）是回到问题本质，不被现有方案束缚的能力。举例：(a)「为什么需要数据库？」→ 因为有持久化 + 高并发查询需求；(b)「为什么需要微服务？」→ 因为团队独立扩展 + 部署隔离的需求。AI 工具擅长「已有方案的快速实现」，但不擅长「第一性原理的重新定义」。请你思考：你现在做的项目里，有哪些问题是用「惯性方案」解决的（因为大家都这么做）？如果重头设计，会不同吗？
  2. 「写代码 vs 想清楚」的时间分配变化：(a) 1990 年代：80% 写代码 + 20% 想清楚（IDE 弱）；(b) 2010 年代：50% 写代码 + 50% 想清楚（IDE + Stack Overflow）；(c) 2020 年代（AI 时代）：20% 写代码 + 80% 想清楚（AI 写代码，人写规格）。预测 2030 年代会如何？5% 写代码 + 95% 想清楚？还是 AI 强到人连想都不用想？讨论对工程师的要求变化。
  3. AI 时代的工程师核心能力（Marco Rogers 提出的「AI 增强工程师」模型）：(a) 问题定义能力（Problem Framing，把模糊需求转化为可执行任务）；(b) 规格撰写能力（Spec Writing，写出 AI 能理解的详细规格）；(c) 评审能力（Code Review，评估 AI 输出的质量与边界）；(d) 系统思维（Systems Thinking，理解组件如何组合而非单点实现）。这四项都不是 AI 能轻易替代的（AI 强的是单点实现，弱的是全局判断）。请你为自己设计「AI 时代能力升级计划」：每项如何训练？多久见效？
  4. laew 作为「思考伙伴」而非「代码代写」：(a) 默认要求用户先写规格（Spec）再写代码：SubAgent 拒绝执行「帮我写个 XX」这种模糊任务，必须先有 acceptance criteria + edge cases；(b) 「不写代码」模式：用户描述需求，laew 不生成代码而是输出「问题分析 + 设计选项 + 权衡 + 推荐方案」，把决策权留给用户；(c) 「思考可视化」：把 AI 推理过程外化（"为什么选 A 不选 B？""有哪些假设？"），让用户跟着推理而非只看结论；(d) 故意留白：laew 在关键决策点停下来问用户（"这里我看到两个方案 A 和 B，你倾向哪个？"），而不是自作主张。讨论这种「AI 陪练而非 AI 代工」对用户长期成长的价值（用户思考能力不被替代 vs 被替代）。
