### CV01 闰年规则：从儒略历到格里高利历

- **预期档位**: simple
- **考察维度**: 闰年算法 + 历法史 + 边界测试
- **对话脚本**:
  1. 写闰年函数：`year % 4 == 0 && (year % 100 != 0 || year % 400 == 0)`——4 年一闰、百年不闰、400 年再闰；用 Rust 实现并对 1600/1700/1900/2000/2100 逐个断言，解释平均年长 365.2425 天与回归年 365.2422 的残差（约 3300 年差一天）。
  2. 历法史：儒略历（纯 4 年一闰，年平均长 0.0078 天）到 1582 年已漂移 10 天——格里高利改历直接删除 10 月 4 日到 10 月 15 日；解释「十月革命发生在公历 11 月」这类历史日期换算问题（俄国 1918 年才改历）。
  3. 边界测试集：写出你会在 PR 里附上的闰年测试用例表（含负年份约定 / 0 年 / 大数年份溢出 `i32::MAX`），以及「1752 年 9 月英国改历少了 11 天」这种真实历史边界为什么是绝佳的测试样本（很多手写日期库在这里翻车）。
  4. laew 借鉴：历法迁移的「历史包袱兼容」对照 laew 的 SQLite 存量库自动迁移（补列回填默认值）——两者共同原则：新规则只管新数据、旧数据带版本标记、跨版本的换算逻辑要显式且可测。

### CV02 儒略日与日期序数运算

- **预期档位**: medium
- **考察维度**: JD/MJD 换算 / 日期差算法 / 天文纪元
- **对话脚本**:
  1. 儒略日（JD）：从公元前 4713 年 1 月 1 日起连续计日的天文纪元，任何历法的日期都先换算成 JD 再互转；实现 `date_to_jdn(y, m, d) -> i64` 的经典整数算法（a = (14-m)/12, y+4800-a, m+12a-3, jdn = day + (153m+2)/5 + 365y + y/4 - y/100 + y/400 - 32045）并验证 2000-01-01 = 2451545。
  2. MJD 与工程用途：MJD = JD - 2400000.5（去掉 0.5 是让一天从午夜而非正午开始），fits 科学数据 / 航天 / GPS 时间常用；实现往返（date → JD → MJD → date）并做 10 万组随机日期的自洽测试。
  3. 日期差与星期：两日期差 = JDN 相减（O(1) 无循环）；星期 = (JDN + 1) % 7（0=周日）的零表推导；实现「某人活了 10000 天是哪天」与「下个周五十三号」两个趣味查询。
  4. laew 借鉴：JD「用一个连续标量统一所有历法」对照统一消息模型——laew 把两种协议消息统一为内部模型再转换，讨论「中间标量表示」的设计威力（新历法/新协议只需两端的换算器）。

### CV03 农历转换：查表与天文两条路

- **预期档位**: hard
- **考察维度**: 农历规则 / 查表法 / 天文算法法
- **对话脚本**:
  1. 农历规则：以朔日（新月）定初一、以中气定月序（无中气月为闰月）、冬至所在月为十一月、年首为寅月——「规则 astronomically defined」意味着转换本质需要天文计算；解释为什么「19 年 7 闰」只是统计近似不能用于实现。
  2. 查表法实现：每年存「农历年大小月位图 + 春节公历日期 + 闰月位置」紧凑元数据（一年约 4 字节），用 Rust 实现公历 ↔ 农历的双向换算（先定位年再逐月推）；覆盖 1900-2100 的数据约 800 字节，这是多数开源库的做法。
  3. 天文算法法：用 VSOP87 简化版或 ELP2000 月亮位置模型直接算朔时刻（精度秒级）+ 时区换算（北京时间东经 120°）；说明天文法能外推任意年份但要小心「时刻接近午夜时朔日跨日」与历史时区（1949 前各地用时）的坑。
  4. laew 借鉴：查表 vs 计算的取舍（嵌入式预算 / 精度需求 / 数据维护成本）对照 laew 的 mock LLM 脚本（按角色分流的静态表）vs 真实调用——「表驱动换算」胜在确定性与低成本，败在覆盖边界，讨论何时必须切换到「真算」。

### CV04 二十四节气：太阳黄经计算

- **预期档位**: hard
- **考察维度**: 黄道坐标 / 节气时刻 / 简化算法
- **对话脚本**:
  1. 节气本质：地球公转到黄经每 15° 整数倍的时刻——立春是黄经 315°、春分 0°、清明 15°…；解释为什么节气在公历上「日期基本固定（±1 天）」而农历日期乱飘（节气是太阳历属性）。
  2. 简化太阳位置：用低阶 Fourier 级数（VSOP87 截断或 Jean Meeus《Astronomical Algorithms》的公式）计算给定时刻的太阳黄经（精度 0.01° 足够节气）；用 Python 实现并验证 2026 年春分在 3 月 20 日附近。
  3. 求节气时刻：黄经是时间的单调（近似）增函数——牛顿迭代 `t = t - (λ(t) - target) / dλ/dt` 几步收敛；实现「给定年份返回 24 节气的精确到小时的时刻表」，并处理黄经 360° 环绕（冬月到春月跨 0° 的迭代初值选择）。
  4. laew 借鉴：牛顿迭代「初值差也能收敛、但好初值少迭代」对照 Yolo 分类——用轻量启发（关键词 / 长度）做初值、LLM 做精化，讨论两段式分类的成本/准确率权衡。

### CV05 月相与潮汐：朔望周期计算

- **预期档位**: medium
- **考察维度**: 朔望月 / 月相名 / 农历日期反推
- **对话脚本**:
  1. 朔望月：平均 29.530588 天（新月到新月），用「已知某个新月纪元时刻 + 周期外推」估算任意日期月相 `age = (date - epoch) mod 29.53`；实现月龄计算并映射到八相名（新月/娥眉/上弦/盈凸/满月/亏凸/下弦/残月），误差累积说明（一年漂移 ~1 天，需修正项）。
  2. 精化：加「太阳不均匀运动修正」（地球轨道椭圆，月相速度随季节 ±0.6 天摆动）的两组正弦修正项；实现精化版并用 2026 年几个满月（农历十五/十六）验证在 ±1 天内。
  3. 潮汐关联：潮汐周期 ≈ 半个太阴日 12 小时 25 分（月球主导），大潮在朔望（日月引潮力叠加）、小潮在上下弦；用 Python 算「给定农历日期的潮汐强弱」并解释「钱塘江大潮在农历八月十八」的天文学原因（朔望大潮 + 地形放大）。
  4. laew 借鉴：周期外推「模型会漂、需要修正项」对照 token 估算模型（字符/4 + 10% 对 CJK 系统性低估）——讨论给估算加「按语言/内容类型的分段修正系数」的标定方法（用历史会话实测回归）。

### CV06 ISO 8601 与 RFC 3339：手写时间解析器

- **预期档位**: medium
- **考察维度**: 格式规范 / 手写解析 / 互操作陷阱
- **对话脚本**:
  1. 规范对比：ISO 8601 允许 `20260910`（基本格式）/ `2026-09-10T08:30+08:00` / `2026-W37-4`（周年）/ `2026-253`（年积日）；RFC 3339 是其互联网子集（必须有 `T` 分隔、必须有偏移或 Z、禁止基本格式）；写一个支持 RFC 3339 全量 + ISO 扩展格式的手写解析器（不调 chrono），返回 `(本地时间, 偏移秒)`。
  2. 解析器工程：状态机或手写游标逐段切（年-月-日 T 时:分:秒.小数 偏移）；处理逗号/点两种小数秒、`-00:00` 的语义（RFC 3339 里表示「偏移未知」≠ UTC）、24:00 表示次日零点；写 15 个边界用例的测试表。
  3. 互操作陷阱：不同库对 `2026-09-10`（无时间的日期）与瞬时（Instant）的类型区分、序列化时 Z vs +00:00 的不一致、数据库存「不带时区 timestamp」导致的多区部署事故；总结「内部一律 UTC 瞬时 + 出口才格式化」的原则及其例外（未来预约时间要存本地时间 + 时区，因 DST 规则可能变）。
  4. laew 借鉴：手写解析器 vs 调库的边界对照 laew 「不引入新 crate」约定——本次手写的价值是掌握格式语义（之后用 chrono 时知道它替你处理了什么），laew 自研 TUI 引擎同理（理解渲染语义后才有资格谈引入 ratatui）。

### CV07 tzdata 与 DST：时区规则的编程实现

- **预期档位**: medium~hard
- **考察维度**: tzdata 结构 / 转换区段 / DST 判定
- **对话脚本**:
  1. tzdata 结构：IANA 时区数据库按区（如 Asia/Shanghai）存「历史转换记录链」（UTC 时间戳 + 偏移 + 是否 DST + 缩写），中国 1986-1991 曾实行夏令时的历史都在链里；解析 TZif 二进制格式（v2/v3 的 header + transitions 数组 + POSIX 尾缀）并用 Python 读出上海区的全部转换点。
  2. 任意时刻偏移：二分查找「不大于 t 的最后一条 transition」得到生效偏移；实现 `offset_at(zone, utc_ts)` 与反向 `local_to_utc`（本地时间在 DST 回拨的重叠段有两个候选——返回两者并让调用方选择；跳变空洞段无解——报错或前推）。
  3. 未来规则外推：tzdata 尾部的 POSIX TZ 规则（如 `EST5EDT,M3.2.0/2,M11.1.0/2` = 3 月第二个周日 2 点到 11 月第一个周日）用于预测未来转换；解析这个规则字符串并实现「给定年份的 DST 起止日计算」（第 N 个星期几的算法：`1 + (7 - (wd_of_first + 7 - target_wd) % 7) + 7*(n-1)`）。
  4. laew 借鉴：本地时间反解的「重叠段双候选」对照 `/rewind` 的轮次歧义——回退目标轮次若有多个同名匹配（合成消息不计轮），必须显式消歧而不是静默取第一个；对照讨论「报错优于猜」的 API 设计原则。

### CV08 RRule：RFC 5545 重复规则引擎

- **预期档位**: hard
- **考察维度**: 重复语义 / 边界条件 / 实现策略
- **对话脚本**:
  1. RRule 语法：`FREQ=MONTHLY;BYDAY=2TU` = 每月第二个周二（日历应用「每两周周五」「每月最后一个工作日」的后端）；解析器把规则字符串解析成结构体（FREQ / INTERVAL / BYDAY / BYMONTHDAY / UNTIL / COUNT / BYSETPOS）。
  2. 枚举引擎：从 DTSTART 开始按 FREQ 步进生成候选集 → 应用 BYxxx 过滤器链（BYMONTH → BYDAY → BYMONTHDAY → …）→ BYSETPOS 取第 N 个（`BYDAY=MO,TU,WE,TH,FR;BYSETPOS=-1` = 每月最后一个工作日）；实现这个管线并跑通「每月最后一个周五」与「每 2 周的周二周四」。
  3. 边界地狱：2 月 30 日跳过还是顺延到 3 月？（RRule 跳过）；COUNT 与 UNTIL 互斥；时区 DST 跳变日的发生时刻保持本地钟面；无限规则必须配 `until` 或惰性迭代器（`take_while`）；写这四个边界的测试并对照 dateutil.rrule 的行为校验你的实现。
  4. laew 借鉴：过滤器链 + 集合位置选择的管线结构对照 MultiAgentOrchestrator 的编排管线（项目上下文注入 → Yolo 分类 → 档位路由 → QC）——讨论「可组合规则链 + 显式中间结果」让每一步可单测（RRule 的每个 BYxxx 都能独立测试）。

### CV09 cron 表达式解析与下次触发计算

- **预期档位**: medium~hard
- **考察维度**: 五域语法 / 语义匹配 / next 算法
- **对话脚本**:
  1. 五域解析：`分 时 日 月 周` 每域支持 `*`、`,`、`-`、`/`（`*/5`、`10-30/2`）、星期名与月份名缩写；用 Rust 写解析器输出每域的 bitset（60/24/31/12/7 位），非法输入（`61` 分、`0` 日）显式报错。
  2. 语义陷阱：日域与周域同时非 `*` 是 OR 不是 AND（cron 的历史反直觉）；`0 0 31 * *` 一个月只有大月触发；周日的 0 和 7 都合法；写这三个陷阱的测试用例并在文档里显式声明语义。
  3. next 触发计算：从给定时刻逐分钟递增匹配五域——慢版 O(分钟数)；快版「按域进位」（分钟域取下一个置位位、溢出进小时…再处理日月周 OR 联合判定与月末回退）；实现进位版并对比逐分钟版在 `0 0 29 2 *`（四年一触发）下的性能（快版毫秒、慢版遍历数十万分钟）。
  4. laew 借鉴：cron「小语言大语义」（五个域的隐式组合规则）对照 laew 自定义斜杠命令的 frontmatter 设计——讨论小 DSL 的语义必须「显式文档化 + 拒绝歧义输入」（cron 的日周 OR 反例），laew 的 `argument-hint` 与占位符 `$1-$9` 如何避免同类歧义。

### CV10 月历生成、节假日调休与 iCal 导出

- **预期档位**: medium
- **考察维度**: 月历矩阵 / 调休规则 / iCalendar 格式
- **对话脚本**:
  1. 月历矩阵：任意年月生成 6×7 网格（周一或周日开头，含前后月补格）；实现 `calendar_matrix(y, m) -> [[Date; 7]; 6]` 并决定补格的归属标记（显示但不属于本月）；讨论为什么固定 6 行（跨度最长的月 + 周首偏移是 6 行）。
  2. 节假日与调休：中国节假日 = 法定节日（部分按农历，联动 CV03）+ 周末 + 调休补班日（国务院每年发布，规则不可推导只能数据化）；设计 `holidays(year)` 数据层（节日表 / 补班表）与 `is_workday(date)` 判定链（补班 → 节假日 → 周末 → 工作日），并实现「下一个工作日跳过长假」的计算。
  3. iCal 导出：RFC 5545 的 VCALENDAR/VEVENT 结构（UID / DTSTART / DTEND 或 DURATION / RRULE 联动 CV08 / VALARM 提醒）；写生成器注意文本转义（逗号分号换行）、行折叠（75 字节软换行 CRLF + 空格续行）、以及 `X-WR-CALNAME` 这类扩展字段的兼容面；导出「个人节假日日历」并在 Google Calendar / 系统日历导入验证。
  4. laew 借鉴：节假日「规则 + 每年人工数据」的混合模式对照 laew 的内置命令 + 自定义命令（`.laew/commands/` 动态加载）——「代码管规则、数据管例外」的架构让运营性内容（每年变化的调休 / 用户自定义命令）无需发版即可更新，讨论 laew 还有哪些硬编码文案应该数据化。
