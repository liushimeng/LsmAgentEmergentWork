# 64 文件格式解析与序列化编程

> 编号段 BM01–BM10 · 聚焦 文件格式手写解析：PNG / ZIP / WAV / xlsx / Protobuf / CBOR / SQLite / CSV / 配置格式 / 自定义二进制协议
> 与现有 AD01「ELF 文件结构」等专题互补：AD 偏**可执行文件**结构（ELF / Mach-O / PE）；64 偏**数据文件**解析（图像 / 归档 / 表格 / 协议）
> 与现有 10 维「网络协议与安全基础」互补：10 写协议（HTTP / TLS / WebSocket）；64 写**磁盘文件**（字节流 + 容器 + 字段编码）

---

### BM01 PNG 解码：chunk、CRC 与 zlib 解压
- **预期档位**: medium
- **考察维度**: PNG chunk 解析 + CRC32 校验 + zlib 流式解压
- **对话脚本**:
  1. 手写一个 PNG 解码器（用 `flate2` 解 zlib，不用 `image` crate）：文件头 8 字节 `89 50 4E 47 0D 0A 1A 0A` + 一系列 chunk，每个 chunk 结构 `[length:4][type:4][data:length][crc:4]`，先解析 IHDR（图像宽 / 高 / 位深 / 颜色类型 / 压缩方法 / 滤镜 / 交错）。
  2. 基于上面的 chunk 解析，校验 CRC32（`crc32fast::hash` 对 type+data 计算），错误时给出精确的 chunk 偏移与类型。解析 PLTE 调色板（颜色类型 3 才有）、IDAT 图像数据（多个 IDAT 顺序拼接再 zlib 解压）、IEND 结束。
  3. 解压后处理 PNG 滤镜：每个 scanline 前有 1 字节滤镜类型（0 None / 1 Sub / 2 Up / 3 Average / 4 Paeth），逐行重建原始 RGBA，给出 Paeth 预测器算法实现。
  4. 交错（interlace）模式 1（Adam7）要按 7 个子图 pass 重采样到完整图像，每 pass 子图尺寸是 `ceil((w - x) / 7)` 形式。最后给 laew 加一个 Read 工具选项 `--png-info`，只解析 IHDR + 校验 CRC 不解像素，快速拿尺寸 / DPI。

### BM02 ZIP 归档：中央目录、压缩与流式解包
- **预期档位**: medium
- **考察维度**: ZIP End of Central Directory + Local File Header + DEFLATE
- **对话脚本**:
  1. 手写 ZIP 解析器：先在文件末尾找到 End of Central Directory Record（魔数 `50 4B 05 06`，可前移 65557 字节扫描），从中拿到中央目录偏移与条目数。ZIP 支持从任意条目位置开始读（不必从头扫描），这是它相对 TAR 的优势。
  2. 基于上面的 EOCD，读取中央目录条目（CDFH）：压缩方法（0 Store / 8 DEFLATE / 99 AES）、压缩大小 / 未压缩大小、CRC32、文件名 + extra 字段。给出校验：CRC 必须等于未压缩数据的 CRC32。
  3. 按需解压单个文件：从对应 Local File Header 开始读（注意文件名可能与中央目录不一致，**以中央目录为准**），用 `flate2` 流式 DEFLATE 解压到 `Vec<u8>` 或 `Write` sink，避免一次性加载整个 ZIP。
  4. 加密 ZIP（传统 PKZIP / AES-256）：传统加密用 ZIPCrypto 流密码（已知有已知明文攻击，不安全）；AES 用 WinZip 规范（AES-CTR + HMAC-SHA1）。给 laew 加一个 ZIP 读取工具作为 Bash 工具的补充（避免每次 `unzip` 调用子进程）。

### BM03 WAV 与 PCM：采样率、位深与音频写入
- **预期档位**: simple
- **考察维度**: RIFF 容器 + fmt chunk + data chunk
- **对话脚本**:
  1. 手写 WAV 解析器（RIFF 格式）：文件头 `RIFF<size>WAVE` + chunks，至少有 `fmt `（格式：采样率、声道数、位深、编码格式 PCM=1 / IEEE_FLOAT=3 / EXTENSIBLE=0xFFFE）和 `data`（原始 PCM）。给出 chunk 解析通用代码（4 字节类型 + 4 字节大小 + 填充到偶数）。
  2. 基于上面的 fmt chunk 计算音频时长：`duration_seconds = data_size / (sample_rate * channels * bits_per_sample / 8)`。注意 `data_size` 可能为 0（live streaming），要用 `data` chunk 实际字节数 / 帧大小迭代。
  3. WAV 写入：构造 RIFF 头 + fmt chunk + data chunk（PCM 16-bit 小端），位深支持 8/16/24/32，多声道用交错存储 LRLRLR...。给出把麦克风 PCM 流实时写入 WAV 文件的代码（每 100ms flush 一次更新 RIFF 头大小）。
  4. 浮点 PCM（IEEE 754）：范围 [-1.0, 1.0]，24-bit 整数按符号扩展到 32-bit 处理。给 laew 的 TUI 提示音 / 通知音效加一个 WAV 生成器（用 `hound` 或手写），避免打包 MP3 文件。

### BM04 xlsx 解析：OOXML 结构与共享字符串表
- **预期档位**: hard
- **考察维度**: ZIP 容器 + XML 解析 + 共享字符串 + 单元格类型
- **对话脚本**:
  1. xlsx 本质是 ZIP 套 XML（OOXML）：`xl/workbook.xml` 工作簿 + `xl/worksheets/sheet1.xml` 数据 + `xl/sharedStrings.xml` 共享字符串 + `xl/styles.xml` 样式。把 xlsx 当 ZIP 打开后先列条目，再用上一节的 ZIP 解析器读每个 part。
  2. 基于上面的结构，解析 sheet1.xml：行 `<row r="1">` + 单元格 `<c r="A1" t="s"><v>0</v></c>`，`t="s"` 表示值是 sharedStrings 索引、`t="str"` 表示 inline string、`t="n"`（默认）是数字；日期是数字 + numFmtId 标识（numFmtId 14 起为日期格式）。
  3. 共享字符串表（`sharedStrings.xml`）解析：`<si><t>文本</t></si>` 或带 `<r>` 富文本片段；`<si>` 总数超过 10000 时考虑用字典索引而非数组。合并单元格在 `<mergeCells>` 节点，公式在 `<f>` 子节点。
  4. 大文件优化：xlsx 可能 100MB+，不要一次性 XML parse，用 `quick-xml` 的流式 Reader（`read_text` / `read_resolved`）逐行处理；可只解析第一个 sheet。最后给 laew 的 Plan Agent 加一个「读取 xlsx 表格统计指标」的工作流用例。

### BM05 Protobuf 编解码：varint 与 wire type 手写
- **预期档位**: hard
- **考察维度**: varint 编码 + wire type 6 种 + 字段标签
- **对话脚本**:
  1. 手写 Protobuf 编码器（不依赖 `prost`）：每个字段 = field_number << 3 | wire_type（varint 0 / 64-bit 1 / length-delimited 2 / 32-bit 5）；varint 每个字节 7 位有效 + 最高位 continuation（`buf.push_back((b & 0x7F) | 0x80); b >>= 7;`）。
  2. 基于上面的编码，length-delimited 类型（wire_type=2）先写 varint 长度再写字节；message 嵌套（写 0x0A 长度前缀的子消息）；string / bytes 类型同理。给出 `encode_varint` 与 `encode_tag` 的 Rust 函数。
  3. 解码器：循环读 varint tag → 判断 wire_type → 读对应长度 / 值；嵌套消息读完后回到父字段位置（保存 offset）；packed repeated 字段（`repeated int32 foo = 1` 旧版需 packed=true，新版默认 packed）一次读完整个 length-delimited 块再循环解 varint。
  4. unknown 字段保留：跳过未知字段不报错（兼容性核心），编码时把 unknown 原样写回。给 laew 的 agent_memory 表加一个 Protobuf 二进制 blob 字段（比 JSON 紧凑 30%），给个真实 proto schema：`Task { id: u64, level: enum, workflows: repeated Workflow, context: bytes }`。

### BM06 CBOR 与 MessagePack：紧凑二进制与严格子集
- **预期档位**: medium
- **考察维度**: CBOR 主类型表 + strict 模式 + Schema
- **对话脚本**:
  1. CBOR（RFC 8949）编码规则：每个数据项 = 主类型（高 3 位）+ 附加信息（低 5 位）。主类型 0 unsigned / 1 negative / 2 byte string / 3 text string / 4 array / 5 map / 6 tagged / 7 floats/simple。附加信息 0-23 直接带值，24-27 接 1/2/4/8 字节扩展。
  2. 基于上面的主类型，手写 CBOR 编码整数（直接 varint 类似）/ 字符串（先长度后 UTF-8 字节）/ 数组 / map（按顺序 key1 value1 key2 value2）；tagged 类型用主类型 6 + 后续数据（如 0xC0 0x74 = tag(0) 标准时间，0xC2 = tag(2) 自定义 bigint）。
  3. 严格子集（CTAP2 / WebAuthn / pi Agent 用）：限制 map 键必须按规范排序、禁用 indefinite-length、字符串必须规范化（UTF-8 NFC）、禁止 tag 漂浮。Rust 实现 `ciborium` 支持 strict 模式 + `is_human_readable()` 控制编码差异。
  4. vs MessagePack：MessagePack 结构相似但更紧凑（`fixstr` 0-31 字节内嵌长度），CBOR 更标准化（IETF RFC + 自描述 + 二进制 JSON 语义）。给 laew 的 Debug Agent trace 序列化选 CBOR（自描述 + 比 JSON 紧凑 40%），用 `ciborium::ser::into_writer` 写入二进制文件。

### BM07 SQLite 文件格式：页头、B 树与只读解析
- **预期档位**: hard
- **考察维度**: 页类型 + varint cell + B 树遍历 + schema 表
- **对话脚本**:
  1. SQLite 文件 = 固定 4096 字节页（默认）的链表，前 100 页固定为 header（含 page_size / text_encoding / freelist / schema_cookie 等），从 page 1 开始 B 树存储。手写只读解析器：读 page_size 字段 + 文件总长度 / page_size = 总页数。
  2. 基于上面的 header，每页开头 8/12 字节（看版本）页头：`page_type`（13 leaf table / 5 interior table / 10 leaf index / 5 interior index / 2 freelist / 1 lock-byte），freeblock 偏移，cell 数量，cell content 区起始偏移，右 sibling 指针（interior）。
  3. cell 结构：`payload_length`（varint）+ `rowid`（varint，leaf table）+ `payload` + overflow（payload > page_size 时链到 overflow page）；table b-tree cell 用 record format（header 长度 + 字段类型数组 + 字段值）。
  4. 从 sqlite_schema 表读元数据：每个表 / 索引是一行，type/name/tbl_name/rootpage/sql；按 rootpage 走 B 树根，遍历 cell 解 record 格式。给出用 `rusqlite::Connection::query_row` 配合 `PRAGMA page_count` 校验手写解析器输出。给 laew 加一个 `inspect-db` 子命令（基于自研解析器）快速浏览 agent_memory 表前 10 行。

### BM08 CSV 与 TSV 的边界：引号、换行与方言
- **预期档位**: simple
- **考察维度**: RFC 4180 + 引号转义 + 嵌入换行 + UTF-8 BOM
- **对话脚本**:
  1. CSV 看起来简单但有方言：RFC 4180 规定字段含 `,` / `"` / `\n` 时用 `"` 包裹，内部 `"` 转义为 `""`，换行可用 `\r\n` 或 `\n`。手写解析器：状态机 `InField / InQuotedField / AfterQuote` 处理引号内换行（直接吃掉）和结尾引号后可能是下一个字段（逗号）或行尾。
  2. 基于上面的状态机，加 TSV 支持（`\t` 分隔 + 通常无引号，Excel 导出常用），自动嗅探分隔符：读首行，按 `,` / `\t` / `;` 计数取最大（且每列数量一致的那个）。UTF-8 BOM（`EF BB BF`）跳过；GBK / Big5 CSV 用 `chardetng` 识别。
  3. 写出 CSV：把字段按 RFC 4180 转义（仅含特殊字符才加引号），用 `csv` crate 的 `WriterBuilder::terminator(Terminator::CRLF)` 保证行尾。Excel 兼容：在文件最开头写 UTF-8 BOM。
  4. 大 CSV 处理：100MB+ 文件别一次 parse 用 `csv::ReaderBuilder::has_headers(true)` 流式迭代；行内 cell 包含 HTML / JSON 时单独存表关联。给 laew 加一个 Read 工具支持 CSV 预览（前 100 行 markdown 表格化输出）。

### BM09 YAML、TOML 与 INI：配置格式的坑与取舍
- **预期档位**: medium
- **考察维度**: YAML 标量类型推断 + TOML 严格子集 + INI 注释
- **对话脚本**:
  1. YAML 三大坑：缩进敏感（必须用空格，禁 Tab）、标量类型自动推断（`yes` / `no` / `2024-01-01` / `0x1F` 自动转 bool/date/hex，要保留字符串加引号）、锚点 `&` / 别名 `*` 共享。手写简单解析器或用 `serde_yaml`，但 `serde_yaml` 已被 deprecated 推荐 `serde_yml`。
  2. 基于上面的坑，TOML 是更安全的选择：类型显式（字符串必加引号）、section 用 `[table]` / `[[array_of_tables]]`、日期必须是 RFC 3339 字符串。Rust 用 `toml` crate + `serde`，`Cargo.toml` / `pyproject.toml` 都是 TOML。给出嵌套表与数组的解析示例。
  3. INI 格式最简单：`key=value` + `[section]` + `;` 或 `#` 注释，没有类型（全部字符串）、没有嵌套、无引号转义规则。Rust 用 `configparser` 或手写按行解析。Windows 传统 .ini / Linux systemd unit 都用此格式。
  4. laew 的配置选型：当前用 SQLite 不用配置文件（CLAUDE.md 已注明）；如果加 `~/.config/laew/config.toml` 给斜杠命令自定义 / provider 默认值，TOML 是最优解（`serde::Deserialize` + 错误提示清晰）。给 laew 加一个 `--config <path>` 覆盖默认配置。

### BM10 自定义二进制协议：帧格式、版本与向后兼容
- **预期档位**: hard
- **考察维度**: 帧头设计 + 字节序 + 魔数 + 版本协商
- **对话脚本**:
  1. 设计一个自定义二进制协议帧：`[magic:4][version:2][type:2][length:4][flags:2][reserved:2][payload:length][crc32:4]`，共 20 字节头（不含 payload）。`magic` 是 ASCII（如 `LAEW` / `PROB`）+ version 字节序小端、`type` 是命令码、`flags` 用 bit 标记（压缩 / 加密 / 优先级）。
  2. 基于上面的帧结构，长度用 varint 还是固定 4 字节？varint 节省小帧空间但解析稍慢；固定 4 字节协议简单且支持 zero-copy（`&[u8]` 切片）。CRC32 用帧头 + payload 一起校验（`crc32fast::hash`），给出校验失败时丢弃 + 计数器 + 告警。
  3. 向后兼容策略：版本字段升级到 minor 版本（如 1.0 → 1.1）允许新增字段（追加在 payload 末尾）+ 新增 type 值；升级到 major 版本（1.x → 2.0）可不兼容。Tolerant Reader 模式：解析时跳过未知 type（返回 UnknownType 但不中断）+ 未知字段（已用 CBOR unknown 字段策略）。
  4. 实战：给 laew 的 MultiAgentOrchestrator 设计一个内部 IPC 协议（不用真实 IPC，逻辑层面）：Yolo → Main-Work → SubAgent 的 workflow 委派帧，含 `workflow_id` / `parent_session_id` / `priority` / `depends_on`；日志序列化到本地 socket 用这个协议比 JSON 紧凑 5 倍且类型安全。
