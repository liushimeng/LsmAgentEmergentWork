### CC01 同像性：代码即数据的语言设计哲学

- **预期档位**: medium
- **考察维度**: 同像性概念 + Lisp 家族 + 现代语言启示
- **对话脚本**:
  1. 同像性（Homoiconicity）指「程序的结构与语言自身的数据结构相同」，最经典的例子是 Lisp：S-表达式既是代码也是列表数据。解释为什么同像性让 Lisp 宏如此强大（操作列表 = 操作代码），为什么非同像性语言（如 Java / Python）需要复杂的 AST API 才能实现类似效果。
  2. 同像性语言谱系：(a) Lisp 家族（Common Lisp / Scheme / Clojure / Racket）—— 最纯粹的同像性；(b) Julia —— 表达式是 Expr 对象，可操作；(c) Elixir —— AST 是 Elixir 自身的数据结构；(d) Rust —— `macro_rules!` 操作 TokenStream，但非完全同像；(e) Prolog —— 程序是事实和规则的数据库，可自修改。请对比 Lisp 与 Rust 宏系统的能力边界。
  3. 同像性的工程价值：(a) 宏消除样板代码（DRY）；(b) 嵌入式 DSL（如 Clojure 的 core.async 把异步代码写成同步风格）；(c) 编译期计算（把运行时开销移到编译期）；(d) 语言扩展（用宏给语言加新语法）。请用 Rust 的 `macro_rules!` 或 Elixir 的宏举例说明其中两点。
  4. laew 的同像性启示：如果 laew 的提示词模板系统支持「提示词生成提示词」（类似 Lisp 宏），设计一个 `/macro` 命令：用户定义提示词宏（如 `/defmacro code-review "对 $file 做代码审查，关注 $aspects"`），之后调用 `/code-review src/main.rs 性能+安全` 自动展开。讨论这种「提示词即数据」设计的潜力与风险。

### CC02 宏系统：从文本替换到卫生宏

- **预期档位**: medium
- **考察维度**: 宏演进 + 卫生宏 + 多语言对比
- **对话脚本**:
  1. 宏的四代演进：(a) 文本替换宏（C 预处理器 `#define`，最原始但易出错）；(b) 语法宏（Scheme `syntax-rules`，模式匹配 + 卫生展开）；(c) 过程宏（Rust / Elixir，用函数操作 AST）；(d) 编译期执行（Zig `comptime` / D `static if`，直接在编译期运行代码）。请解释为什么 C 宏的 `#define SQUARE(x) x * x` 在 `SQUARE(1+2)` 时出错（展开为 `1+2*1+2 = 5` 而非 `9`）。
  2. 卫生宏（Hygienic Macro）解决的核心问题：宏展开时意外捕获外部变量。Scheme 的 `syntax-rules` 和 `syntax-case` 通过重命名绑定保证卫生性。请用一个例子说明不卫生宏的问题：定义 `swap!` 宏交换两个变量，但宏内引入的临时变量与外部变量同名导致错误。
  3. Rust 宏系统详解：(a) 声明宏 `macro_rules!`（模式匹配 + 片段分类符 `expr` / `ty` / `ident`）；(b) 过程宏（派生宏 / 属性宏 / 函数式宏）；(c) `proc_macro` 与 `proc_macro2` 的区别；(d) `syn` + `quote` 生态。请写一个简单的 `vec!` 宏实现，说明其如何把 `[1, 2, 3]` 展开为 `Vec::from([1, 2, 3])`。
  4. 宏的最佳实践与反模式：(a) 宏只用于函数无法表达的场景（如 DSL / 消除重复）；(b) 宏文档必须说明展开结果；(c) 避免「宏迷宫」（宏套宏套宏，调试困难）；(d) 优先用泛型 / trait 而非宏。请你为 laew 设计一个 `agent_tool!` 宏：自动为工具结构体实现 `Tool` trait 的 `name()` 和 `description()` 方法，减少样板代码。

### CC03 反射（Reflection）：程序在运行时认识自己

- **预期档位**: medium
- **考察维度**: 反射能力 + 类型自省 + 工程应用
- **对话脚本**:
  1. 反射（Reflection）是程序在运行时检查、修改自身结构和行为的能力。反射的两个维度：(a) 自省（Introspection）—— 查看类型 / 字段 / 方法 / 注解；(b) 互变（Intercession）—— 修改行为 / 调用方法 / 创建实例。请对比 Java 反射（`Class.forName` / `Method.invoke`）与 Python 反射（`getattr` / `hasattr` / `inspect`）的能力差异。
  2. 反射的经典应用场景：(a) 序列化 / 反序列化（Serde 通过反射遍历字段）；(b) 依赖注入框架（Spring 扫描 `@Autowired` 注解）；(c) ORM 映射（Django Model 通过元类把类定义转成 SQL 表）；(d) 测试框架（JUnit 扫描 `@Test` 方法）；(e) 插件系统（通过类名动态加载）。请用 Serde 举例说明反射如何把 JSON `{"name":"laew","version":1}` 反序列化为 Rust 结构体。
  3. 反射的代价与替代：(a) 运行时开销（类型检查在运行时）；(b) 类型安全丧失（编译器无法检查）；(c) 代码可读性下降（间接调用难追踪）。编译期替代方案：(a) Rust trait + 派生宏（编译期生成代码）；(b) Zig `@typeInfo`（编译期类型自省）；(c) TypeScript 条件类型（类型级编程）。请对比「运行时反射」vs「编译期代码生成」在序列化场景的优劣。
  4. laew 的反射能力设计：当用户问「laew 当前支持哪些工具？」时，laew 应该：(a) 通过 `ToolRegistry` 自省列出所有已注册工具；(b) 显示每个工具的 `name` / `description` / `input_schema`；(c) 标注哪些工具当前可用（如 Write 工具在只读模式下不可用）。讨论这种「Agent 自省」能力对用户体验的价值。

### CC04 Rust 过程宏：在编译期写代码的代码

- **预期档位**: hard
- **考察维度**: 过程宏三类型 + syn/quote + 派生宏实战
- **对话脚本**:
  1. Rust 过程宏（Procedural Macro）是在编译期把 TokenStream 转换为 TokenStream 的函数。三种类型：(a) 派生宏（`#[derive(MyTrait)]`，为结构体自动实现 trait）；(b) 属性宏（`#[my_attribute]`，包装任意 item）；(c) 函数式宏（`my_macro!(...)`，类似声明宏但更强大）。请解释为什么过程宏需要单独的 `proc-macro = true` crate（编译期执行需要独立二进制）。
  2. 派生宏实战：写一个 `#[derive(Describe)]` 宏，为任意结构体生成 `describe()` 方法，返回包含字段名和类型的字符串。关键步骤：(a) 用 `syn::parse::<DeriveInput>()` 解析输入；(b) 用 `quote!` 生成实现代码；(c) 用 `TokenStream::from` 返回。请写出完整的 `#[proc_macro_derive(Describe)]` 函数。
  3. 过程宏生态与工具：(a) `syn` —— 解析 TokenStream 为 AST；(b) `quote` —— 把 AST 转回 TokenStream；(c) `darling` —— 简化属性宏的参数解析；(d) `proc-macro2` —— 可在测试中使用的 TokenStream；(e) `cargo expand` —— 查看宏展开结果。请描述如何用 `cargo expand` 调试一个复杂的派生宏。
  4. 过程宏 vs 声明宏选择：(a) `macro_rules!` 适合简单模式匹配（如 `vec!` / `println!`）；(b) 过程宏适合需要完整 AST 操作的场景（如 Serde 的 `#[derive(Serialize)]`）；(c) 过程宏的编译时间更长（需要编译 + 执行）。请你为 laew 设计一个 `#[derive(AgentTool)]` 派生宏：自动从结构体定义生成 OpenAI / Anthropic 兼容的 `input_schema`，支持 `#[doc = "..."]` 作为字段描述。

### CC05 编译期计算：把运行时开销消灭在编译期

- **预期档位**: hard
- **考察维度**: 编译期求值 + const fn + comptime + 零成本抽象
- **对话脚本**:
  1. 编译期计算（Compile-time Computation）是把能在编译期完成的计算提前执行，运行时直接使用结果。四种实现路径：(a) C++ `constexpr` / `consteval`；(b) Rust `const fn`；(c) Zig `comptime`；(d) D `static if` / `mixin`。请解释为什么「编译期计算」是零成本抽象（Zero-cost Abstraction）的关键支撑（计算在编译期完成，运行时无开销）。
  2. Rust `const fn` 演进：(a) 早期只能做简单算术；(b) 逐步支持 `if` / `match` / `loop` / `trait` 方法；(c) 当前限制（不能分配内存、不能 trait 动态分发、不能 panic 到运行时）。请写一个 `const fn fibonacci(n: u64) -> u64` 在编译期计算斐波那契数，并用 `const FIB_20: u64 = fibonacci(20);` 在编译期绑定。
  3. Zig `comptime` 的独特设计：(a) `comptime` 关键字标记编译期参数；(b) 普通代码自动在编译期执行（无需特殊语法）；(c) `type` 是一等值（`comptime T: type`）；(d) `@comptimeEval` 强制编译期求值。请用 Zig 写一个编译期生成查找表（LUT）的例子：`comptime { var table: [256]u8 = undefined; ... }`。
  4. laew 的编译期启示：laew 的提示词模板系统可以借鉴编译期计算思想：(a) 模板在加载时（而非每次请求时）预编译为 AST；(b) 占位符类型检查在注册时完成（而非运行时）；(c) 静态提示词（无占位符）在启动时预渲染为最终字符串。讨论这种「提示词编译期优化」对 laew 性能的提升空间。

### CC06 注解与装饰器：声明式编程的元数据魔法

- **预期档位**: medium
- **考察维度**: 注解 + 装饰器 + AOP + 元数据驱动
- **对话脚本**:
  1. 注解（Annotation）与装饰器（Decorator）是「给代码附加元数据」的机制，让框架在运行时根据元数据改变行为。典型应用：(a) Java 注解（`@Override` / `@Autowired` / `@Transactional`）；(b) Python 装饰器（`@staticmethod` / `@property` / `@functools.lru_cache`）；(c) Rust 属性（`#[derive(...)]` / `#[test]` / `#[cfg(...)]`）；(d) TypeScript 装饰器（`@Component` / `@Injectable`）。请解释为什么注解让代码更「声明式」（说「是什么」而非「怎么做」）。
  2. Python 装饰器深入：(a) 本质是高阶函数（接收函数返回函数）；(b) `@functools.wraps` 保留元数据；(c) 带参数装饰器（三层嵌套）；(d) 类装饰器；(e) 常见装饰器库（`@dataclass` / `@click.command` / `@app.route`）。请写一个 `@timing` 装饰器：测量函数执行时间并打印，支持可选参数 `@timing(unit="ms")`。
  3. 面向切面编程（AOP）：(a) 把横切关注点（日志 / 事务 / 权限 / 缓存）从业务代码中分离；(b) Spring AOP 通过动态代理实现；(c) Python `aspectlib`；(d) 注解 + AOP = 声明式事务管理（`@Transactional` 自动开启 / 提交 / 回滚）。请用 Java Spring 的 `@Transactional` 举例说明 AOP 如何把事务管理从业务代码中剥离。
  4. laew 的注解启示：设计一个 laew 工具注解系统：(a) `#[tool(description = "...", permission = "readonly")]` 标注工具元数据；(b) `#[deprecated(since = "1.0", use_instead = "new_tool")]` 标记废弃工具；(c) `#[requires_config("api_key")]` 标注前置条件。讨论这种声明式工具定义相比当前硬编码注册的优势。

### CC07 代码生成（Code Generation）：让机器写重复代码

### CC08 运行时代码加载：热更新与插件系统

- **预期档位**: hard
- **考察维度**: 动态加载 + 热更新 + 插件架构
- **对话脚本**:
  1. 运行时代码加载（Runtime Code Loading）是在程序运行期间动态加载、执行新代码的能力。实现方式：(a) `dlopen` / `LoadLibrary` —— 动态库加载；(b) `eval` —— 字符串执行（JavaScript `eval` / Python `exec`）；(c) JIT 编译 —— 运行时编译执行（LuaJIT / V8）；(d) WASM 运行时 —— 沙箱化动态加载。请解释为什么插件系统需要运行时代码加载（核心程序编译时不知道插件存在）。
  2. Rust 动态加载：(a) `libloading` crate 调用 `dlopen`；(b) 插件定义在 `cdylib` crate 中；(c) 通过 C ABI 接口通信（`extern "C"`）；(d) 类型擦除（插件返回 `Box<dyn Plugin>`）。请写一个最小插件系统：主程序定义 `Plugin` trait，插件实现 trait，主程序用 `libloading` 加载 `.so` 文件。
  3. 热更新（Hot Reload）工程：(a) 游戏开发热重载（修改代码立即生效）；(b) Web 开发 HMR（Hot Module Replacement）；(c) Erlang 热升级（不停机更新）；(d) 实现关键：状态与代码分离（代码可替换，状态保持不变）。请讨论 laew 如何实现「工具热更新」：用户修改工具代码后，laew 重新加载而不重启会话。
  4. 运行时代码加载的安全考量：(a) 加载未签名代码的风险（恶意插件）；(b) 沙箱化（WASM / Landlock / Seccomp）；(c) 能力声明（插件声明需要的权限）；(d) 版本兼容性（ABI 稳定性）。请你为 laew 设计一个「安全插件系统」：插件运行在 WASM 沙箱中，通过 WASI 与宿主通信，声明式权限控制。

### CC09 模板元编程：C++ 与 D 的编译期编程

- **预期档位**: hard
- **考察维度**: C++ 模板 + D 模板 + 编译期多态
- **对话脚本**:
  1. C++ 模板元编程（Template Metamorphism Programming, TMP）是「用模板在编译期执行计算」的技术。演进：(a) 基础模板（类模板 / 函数模板）；(b) 模板特化（全特化 / 偏特化）；(c) SFINAE（替换失败不是错误）；(d) `constexpr if`（C++17 编译期分支）；(e) Concepts（C++20 模板约束）。请解释为什么 C++ TMP 被称为「图灵完备的编译期语言」（模板实例化是图灵机）。
  2. C++ TMP 经典案例：(a) 编译期阶乘（`Factorial<N>::value`）；(b) 编译期类型列表（`Typelist<T, Ts...>`）；(c) 编译期多态（CRTP —— 奇异递归模板模式）；(d) 表达式模板（Eigen 库延迟计算）。请写一个编译期计算斐波那契的 C++ 模板：`template<int N> struct Fib { static constexpr int value = Fib<N-1>::value + Fib<N-2>::value; };`。

  4. 模板元编程 vs Rust 泛型：(a) Rust 泛型 + trait 约束更清晰（无 SFINAE 复杂性）；(b) Rust `const fn` 替代部分 TMP 计算；(c) Rust 过程宏替代部分代码生成；(d) C++ TMP 更灵活但更难调试。讨论 laew 如果用 C++ 实现，哪些功能可以用 TMP 优化（如编译期工具注册、编译期提示词验证）。

### CC10 元对象协议（MOP）：对象系统的自我扩展

- **预期档位**: hard
- **考察维度**: MOP + CLOS + 反射架构 + 语言设计
- **对话脚本**:
  1. 元对象协议（Meta-Object Protocol, MOP）是「对象系统本身可被扩展和修改」的协议。最经典的是 CLOS（Common Lisp Object System）的 MOP：(a) 类是对象（类的类是元类）；(b) 方法组合（:before / :after / :around 辅助方法）；(c) 多分派（Generic Function 根据所有参数类型选择方法）；(d) 类创建 / 修改协议（`make-instance` / `add-dependent`）。请解释为什么 MOP 让 OOP 从「封闭」变「开放」（用户可以修改对象系统的行为）。
  2. CLOS 多分派 vs 单分派：(a) Java / C++ 单分派（只根据 `this` 选择方法）；(b) CLOS 多分派（根据所有参数类型选择最特化方法）；(c) 多分派的经典应用（图形碰撞检测：`collide(circle, rectangle)` vs `collide(circle, circle)`）；(d) 多分派的代价（更复杂的方法选择算法）。请用 CLOS 写一个多分派示例：`defmethod collide-after ((a asteroid) (b asteroid)) ...`。
  3. MOP 的现代应用：(a) Python `type` 元类（`__new__` / `__init__` / `__call__`）；(b) Ruby 元编程（`method_missing` / `define_method`）；(c) Smalltalk 元类系统；(d) Moose（Perl 现代 OO 系统）。请用 Python 元类实现一个「自动注册」模式：所有继承 `Plugin` 的类自动注册到全局注册表。
  4. laew 的 MOP 启示：如果 laew 的 Agent 系统支持 MOP：(a) 用户可以自定义 Agent 生命周期钩子（`before-run` / `after-run` / `on-error`）；(b) 用户可以扩展 Agent 的能力组合（类似 CLOS 方法组合）；(c) 用户可以修改 Agent 的选择策略（类似多分派）。讨论这种「开放 Agent 架构」对 laew 生态的价值与风险。
