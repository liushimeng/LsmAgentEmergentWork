### CK01 语义化版本（SemVer）：版本号的艺术

- **预期档位**: simple
- **考察维度**: SemVer 规范 + 版本约束 + 实践
- **对话脚本**:
  1. 语义化版本（Semantic Versioning, SemVer）是「用版本号传达破坏性」的规范。格式：`MAJOR.MINOR.PATCH`（如 `2.1.3`）。规则：(a) MAJOR（不兼容的 API 变更）；(b) MINOR（向后兼容的功能新增）；(c) PATCH（向后兼容的 bug 修复）；(d) 预发布（`1.0.0-alpha.1`）；(e) 构建元数据（`1.0.0+build.20240101`）。请解释为什么 SemVer 对依赖管理至关重要（依赖约束基于版本号语义）。
  2. 版本约束语法：(a) `=1.2.3`（精确版本）；(b) `^1.2.3`（兼容版本，允许 MINOR / PATCH 更新）；(c) `~1.2.3`（近似版本，只允许 PATCH 更新）；(d) `>=1.2.3`（范围）；(e) `1.2.3 - 2.3.4`（区间）。请解释为什么 `^1.2.3` 允许 `1.9.9` 但不允许 `2.0.0`（MAJOR 不变 = 兼容）。
  3. SemVer 的挑战：(a) 破坏性变更定义模糊（什么算「不兼容」？）；(b) 人为判断（开发者可能误判）；(c) 0.x.y 版本（预 1.0 阶段，SemVer 不适用）；(d) 依赖传递（A 依赖 B，B 升级影响 A）。请讨论为什么「SemVer 不是银弹」（需要配套自动化测试验证兼容性）。
  4. laew 的 SemVer 应用：laew 的版本号如何遵循 SemVer：(a) 主版本（不兼容 CLI 变更）；(b) 次版本（新功能）；(c) 补丁（bug 修复）；(d) 版本兼容性检查（启动时检查配置版本）。讨论 laew 的版本管理策略。

### CK02 依赖解析算法：SAT 与回溯

- **预期档位**: hard
- **考察维度**: 解析算法 + NP 完全 + Pubgrub
- **对话脚本**:
  1. 依赖解析（Dependency Resolution）是「选择满足所有约束的版本组合」的问题。核心挑战：(a) 约束冲突（A 要求 `B>=2`，C 要求 `B<2`）；(b) NP 完全问题（最坏情况指数时间）；(c) 回溯搜索（尝试版本 → 冲突 → 回溯 → 尝试其他版本）。请解释为什么「依赖解析」是 NP 完全的（可规约到 SAT 问题）。
  2. Pubgrub 算法（Dart / Flutter 使用）：(a) 决策（选择一个版本的包）；(b) 传播（推导其他包的约束）；(c) 冲突（发现不可满足的约束）；(d) 回溯（回退到上一个决策点）。请描述 Pubgrub 如何比「朴素回溯」更高效（冲突驱动学习 + 智能回溯）。
  3. 依赖解析的工程优化：(a) 缓存已解析结果（避免重复计算）；(b) 版本偏好（优先最新版本）；(c) 最小版本选择（MVS，选择满足约束的最低版本）；(d) 锁定（使用上次解析结果加速）。请讨论为什么「最小版本选择」比「最大版本选择」更稳定（减少意外升级）。
  4. laew 的依赖解析启示：laew 的工具依赖管理是否可以引入依赖解析：(a) 工具声明依赖的其他工具；(b) 自动解析工具加载顺序；(c) 冲突检测（两个工具需要不同版本的共享库）；(d) 版本锁定（确保可复现）。讨论依赖解析对 laew 工具系统的价值。

### CK03 锁文件（Lockfile）：可复现构建的基石

- **预期档位**: medium
- **考察维度**: 锁文件原理 + 可复现性 + 最佳实践
- **对话脚本**:
  1. 锁文件（Lockfile）是「记录所有依赖精确版本」的文件。代表：(a) `Cargo.lock`（Rust）；(b) `package-lock.json`（npm）；(c) `yarn.lock`（Yarn）；(d) `poetry.lock`（Python）；(e) `Gemfile.lock`（Ruby）。请解释为什么「锁文件」对可复现构建至关重要（相同锁文件 = 相同依赖 = 相同构建）。
  2. 锁文件内容：(a) 直接依赖 + 传递依赖；(b) 精确版本（`1.2.3` 而非 `^1.2.3`）；(c) 校验和（确保内容未被篡改）；(d) 来源（Registry URL / Git 仓库）。请描述 `Cargo.lock` 的结构：`[[name = "foo", version = "1.0.0", source = "registry"]]` + `dependencies` + `checksum`。
  3. 锁文件最佳实践：(a) 提交到版本控制（确保团队一致）；(b) 定期更新（`cargo update` / `npm update`）；(c) 审查锁文件变更（安全审计）；(d) CI 使用锁文件（`cargo build --locked` / `npm ci`）。请讨论为什么「CI 应使用 `--locked`」（确保 CI 与本地一致）。
  4. laew 的锁文件应用：laew 的工具系统是否可以引入锁文件：(a) 工具版本锁定（确保可复现执行）；(b) 提示词模板版本锁定；(c) Agent 配置版本锁定。讨论锁文件对 laew 可复现性的价值。

### CK06 依赖地狱：当依赖不再兼容

- **预期档位**: medium
- **考察维度**: 依赖冲突 + 解决方案 + 预防
- **对话脚本**:
  1. 依赖地狱（Dependency Hell）是「依赖冲突导致项目无法构建」的状态。类型：(a) 版本冲突（A 需要 `C>=2`，B 需要 `C<2`）；(b) 钻石依赖（A → B → D 和 A → C → D，B 和 C 需要不同版本的 D）；(c) 循环依赖（A 依赖 B，B 依赖 A）；(d) 传递依赖爆炸（一个包带来上百个传递依赖）。请解释为什么「钻石依赖」是依赖地狱的经典场景。
  2. 依赖地狱解决方案：(a) 语义化版本（减少冲突）；(b) 锁文件（固定版本）；(c) 依赖隔离（不同版本共存，如 Python virtualenv / Node node_modules）；(d) 依赖最小化（减少传递依赖）；(e) 依赖升级（升级到兼容版本）。请描述 Python 的「虚拟环境」如何隔离依赖（每个项目独立 site-packages）。
  3. 依赖地狱预防：(a) 定期更新依赖（避免积累）；(b) 自动化测试（升级后验证）；(c) 依赖审查（新依赖评估）；(d) 依赖最小化（不引入不必要的依赖）。请讨论为什么「依赖最小化」是预防依赖地狱的最佳策略（依赖越少，冲突越少）。
  4. laew 的依赖地狱预防：laew 如何避免依赖地狱：(a) 工具依赖最小化；(b) 工具版本锁定；(c) 工具隔离（每个工具独立环境）；(d) 工具兼容性测试。讨论 laew 的依赖管理策略。

### CK08 包安全：供应链攻击与防御

- **预期档位**: medium
- **考察维度**: 供应链安全 + 攻击方式 + 防御策略
- **对话脚本**:
  1. 供应链攻击（Supply Chain Attack）是通过「污染软件包」攻击下游用户的攻击方式。案例：(a) event-stream（2018，比特币钱包恶意代码）；(b) ua-parser-js（2021，挖矿恶意代码）；(c) colors / faker（2022，作者故意破坏）；(d) xz utils（2024，后门植入）。请解释为什么「供应链攻击」比「直接攻击」更高效（一个恶意包影响数千下游）。
  2. 攻击方式：(a) 账户劫持（盗取维护者账号发布恶意版本）；(b) 域名抢注（typosquatting，`lodash` vs `lodahs`）；(c) 依赖混淆（利用私有包名发布公共包）；(d) 社会工程（伪装贡献者提交恶意 PR）。请描述「依赖混淆」攻击的原理（构建系统优先下载公共 Registry 的同名包）。
  3. 防御策略：(a) 锁文件 + 校验和（确保包未被篡改）；(b) 漏洞扫描（Snyk / Trivy / npm audit）；(c) 签名验证（Sigstore / GPG）；(d) SBOM（软件物料清单）；(e) 最小权限（包运行在沙箱中）。请讨论「Sigstore」如何提供透明的软件签名（Keyless 签名 + 透明日志）。
  4. laew 的包安全：laew 如何防御供应链攻击：(a) 工具签名验证；(b) 工具沙箱执行；(c) 工具来源审计；(d) 工具更新审查。讨论 laew 的安全策略。

### CK09 可复现构建：相同输入 = 相同输出

- **预期档位**: hard
- **考察维度**: 可复现性 + 确定性 + 工程实践
- **对话脚本**:
  1. 可复现构建（Reproducible Build）是「相同源代码 + 相同构建环境 = 相同二进制输出」的能力。意义：(a) 安全审计（验证发布二进制与源码一致）；(b) 供应链安全（防止构建过程被污染）；(c) 可信计算（用户可独立验证）。请解释为什么「可复现构建」对安全至关重要（否则无法信任发布的二进制）。
  2. 可复现构建的挑战：(a) 时间戳（构建时间嵌入二进制）；(b) 随机性（随机数 / UUID）；(c) 路径（构建路径嵌入调试信息）；(d) 非确定性（并行构建顺序不固定）；(e) 依赖版本（依赖更新导致输出变化）。请描述如何消除「时间戳」对可复现性的影响（使用固定时间戳或相对时间戳）。
  3. 可复现构建实践：(a) Debian Reproducible Builds（Debian 项目推动）；(b) Nix（声明式包管理 + 可复现构建）；(c) Bazel（沙箱构建 + 确定性）；(d) Guix（GNU 可复现构建）。请解释为什么「Nix」能实现可复现构建（所有依赖哈希化 + 沙箱构建）。
  4. laew 的可复现构建：laew 如何支持可复现构建：(a) 构建环境容器化（Docker / Nix）；(b) 构建过程记录（构建日志 + 环境快照）；(c) 构建产物校验和；(d) 构建验证（独立重新构建验证）。讨论可复现构建对 laew 发布流程的价值。
