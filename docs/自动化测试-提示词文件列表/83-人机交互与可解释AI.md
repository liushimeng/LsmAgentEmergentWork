### CA51 心智模型与 AI 系统理解

- **预期档位**: medium
- **考察维度**: 心智模型概念 + 用户认知差异 + 设计应对
- **对话脚本**:
  1. 心智模型（Mental Model）是用户对系统工作方式的内在认知。请对比用户对「传统软件」与「AI 系统」的心智模型差异：传统软件（确定性输入 → 确定性输出，可推理）、AI 系统（概率性输出，常有「幻觉」，难以完全预测）。解释为什么 AI 系统的心智模型更复杂（黑盒 + 概率 + 上下文敏感）。
  2. 错误的用户心智模型会导致两类问题：(a) 过度信任（用户认为 AI 总对，结果接受错误建议）；(b) 过度不信任（用户认为 AI 总错，拒绝 AI 的正确建议）。请用真实案例说明：(a) 案例：律师用 ChatGPT 写法律意见书引用了虚假案例（2023 Mata v. Avianca 案）；(b) 案例：医疗 AI 给出的诊断医生不接受结果。
  3. 设计「心智模型对齐」机制：(a) 用 Onboarding 引导建立正确预期（明确告知「AI 可能犯错」）；(b) 用可视化呈现 AI 的思考过程（让用户看到推理步骤）；(c) 用反馈让用户调整心智模型（用户纠正错误后 AI 解释为什么会错）。讨论为什么「透明但不过度」是关键（太多细节反而让用户困惑）。
  4. laew 的用户心智模型调研：典型 laew 用户怎么理解它的工作方式？请画出三类潜在用户的心智模型：(a) 程序员（认为 laew 是「带 LLM 的 Bash」）；(b) 产品经理（认为 laew 是「对话式编程助手」）；(c) 普通用户（认为 laew 是「AI 助手，类似 Siri」）。针对每类心智模型设计对应的 Onboarding 文案 + TUI 提示。

### CA52 信任校准（Trust Calibration）：建立合适的信任水平

- **预期档位**: medium
- **考察维度**: 信任校准原理 + 工程实现 + 评估方法
- **对话脚本**:
  1. 信任校准（Trust Calibration）的目标是「让用户对 AI 系统的信任与系统真实能力匹配」：系统能力强时信任高、系统能力弱时信任低。请用「校准曲线」（Calibration Curve）说明：x 轴是 AI 自报置信度、y 轴是实际准确率，理想曲线是对角线（置信度 = 准确率），上方表示过度自信、下方表示过度不自信。
  2. 校准的三大工程实现路径：(a) 后处理校准（Temperature Scaling / Platt Scaling，调整输出 logits）；(b) 不确定性估计（Ensemble MC-Dropout / Evidential Deep Learning）；(c) 选择性回答（模型自评「不会就说不」）。请对比三者：后处理最简单但只调温度、不确定性估计最优雅但训练复杂、选择性回答最工程友好。
  3. LLM 的不确定性表达有独特挑战：LLM 没有传统意义上的概率输出（只有生成 token 的 logits）。请设计 LLM 置信度估计方案：(a) 输出 Top-K token 的概率分布（Top-1 占比 < 30% 视为低置信度）；(b) Self-Verification（让 LLM 自己评估「刚才回答的可信度」）；(c) Consistency Check（同问题问多次，答案一致视为高置信度）。讨论这三种方法的成本与准确率。
  4. laew 的信任校准实践：在 TUI 中显式标注 AI 输出的置信度。例如：Yolo 任务分类结果旁边显示「简单任务，置信度 92%」/「中等任务，置信度 65%」/「复杂任务，置信度 38%（建议人工确认）」。讨论这种设计是否会「过度打扰用户」（每条输出都标置信度），以及「分场景标注」的方案（只在置信度低时标注）。

### CA53 可解释 AI 技术全景：LIME / SHAP / Attention / CAV

- **预期档位**: hard
- **考察维度**: XAI 算法 + 适用场景 + 工程实现
- **对话脚本**:
  1. 可解释 AI（Explainable AI, XAI）分两类：内在可解释（Intrinsic，如线性回归 / 决策树 / 规则模型，模型本身可理解）；事后可解释（Post-hoc，如 LIME / SHAP / Attention，对已训练模型做解释）。请对比两类：内在可解释最强但模型能力受限、事后可解释灵活但解释不一定忠实于模型。
  2. LIME（Local Interpretable Model-agnostic Explanations，2016）：用「局部线性近似」解释单个预测：在样本周围采样 → 训练简单线性模型 → 用线性系数作为特征重要性。请设计 LIME 应用：图像分类模型预测「猫」→ LIME 解释「图像左上角 + 中间像素最影响预测」。讨论 LIME 的局限（局部采样不稳定 + 解释可被欺骗）。
  3. SHAP（SHapley Additive exPlanations，2017）：用博弈论 Shapley 值量化每个特征对单个预测的贡献，理论保证一致性 + 局部准确性。请设计 SHAP 应用：信用评分模型拒绝贷款 → SHAP 解释「收入贡献 +20 分 / 负债贡献 -30 分 / 年龄贡献 -10 分 / 总分 -20 = 拒绝」。讨论 SHAP 的工程开销（计算复杂度 O(2^N) 特征数大时不可行，需要 KernelSHAP / TreeSHAP 优化）。
  4. 注意力机制可视化：用 Transformer 注意力权重解释「模型看了哪些 token」。请设计一个 NLP 可解释应用：情感分类模型预测「正面」→ Attention 可视化显示模型重点关注「喜欢」「优秀」等词。讨论 Attention 可解释性的争议（Attention ≠ 因果关系，可能误导）。

### CA54 决策溯源（Decision Provenance）：从输入到输出的完整轨迹

- **预期档位**: medium
- **考察维度**: 决策溯源设计 + 工程实现 + 用户呈现
- **对话脚本**:
  1. 决策溯源（Decision Provenance）记录 AI 系统的决策过程：从输入数据 → 检索结果 → 推理步骤 → 工具调用 → 最终输出，每个环节可追溯。请设计一个决策溯源的数据结构：`{session_id, task_id, timestamp, step_type, input, reasoning, tool_calls, output, confidence}`。讨论为什么决策溯源对 debugging + 合规审计 + 用户信任都至关重要。
  2. RAG 系统的决策溯源特别重要（用户经常质疑「AI 哪里知道这个？」）。请设计 RAG 溯源：每次回答引用检索到的源文档 + 段落 + 相似度分数 → 在 UI 中展示「回答的每个论断都标注来源」。这与 Anthropic Citations API + Google Search Grounding 的设计一脉相承。讨论如何避免「过度引用」（每句都标来源反而打断阅读）。
  3. Agent 系统的决策溯源更复杂（涉及多轮思考 + 工具调用 + 子任务委派）。请设计 Agent 决策树可视化：父任务 → 子任务 1（读文件）+ 子任务 2（搜索）+ 子任务 3（编辑），每个子任务有自己的输入输出。参考 laew `-debug` 模式 + Debug Agent 的设计，每个 LLM 调用的输入输出 + Yolo 分类 + QC 结论 + 耗时 + token + 错误都被采集并持久化。
  4. laew 的决策溯源优化：在 TUI 中按 `Ctrl+T` 显示当前 Session 的决策树（用 ASCII 字符绘制层级结构），节点显示「Yolo 分类 → Plan 方案 → SubAgent 任务列表 → QC 结果」。讨论这种透明化的工程价值：用户能看清 Agent 在做什么 → 信任增加 + 错误早发现 + 学习 Agent 工作机制。

### CA55 算法审计（Algorithmic Audit）：公平性 / 偏差 / 责任

- **预期档位**: hard
- **考察维度**: 算法审计框架 + 偏差检测 + 责任追溯
- **对话脚本**:
  1. 算法审计（Algorithmic Audit）系统性评估 AI 系统的公平性 / 偏差 / 影响。审计三大维度：(a) 数据审计（训练数据是否有偏见）；(b) 模型审计（不同人群的预测准确率是否一致）；(c) 影响审计（AI 决策对社会的实际影响是否负面）。请设计一个招聘 AI 的审计框架：数据（简历 - 录用历史是否有性别 / 种族偏见）、模型（男女准确率是否一致 +5%）、影响（未录用的女性占比是否合理）。
  2. 偏差来源分析：(a) 样本偏差（训练数据代表性不足，如人脸识别对深肤色准确率低）；(b) 标签偏差（标注者偏见，如「亚裔美国人」标签的负面含义）；(c) 模型偏差（模型放大训练数据中的偏见）；(d) 部署偏差（应用场景引入的偏差）。设计检测每类偏差的工程方法（统计检验 / 反事实分析 / 公平性指标）。
  3. 公平性指标三定义：(a) Demographic Parity（人口均等，预测正例比例在各群体中相等）；(b) Equal Opportunity（机会均等，真正例率在各群体中相等）；(c) Predictive Parity（预测均等，正预测准确率在各群体中相等）。请证明三者不可能同时满足（Impossibility Theorem），讨论在 laew 这种工具类产品中公平性指标如何选型（用户群体相对单一，主要关注性别 / 语言 / 残障）。
  4. 责任追溯：当 AI 系统出错时谁负责？请用「责任链」概念分析：模型开发者（Anthropic / OpenAI）、应用开发者（laew）、最终用户（用户）。讨论当前法律框架（产品责任法 + 服务条款 + 监管法规）如何分配责任，以及 laew 在「AI 输出仅供参考」免责条款下的法律地位。

### CA56 以人为本 AI（Human-Centered AI）设计原则

- **预期档位**: medium
- **考察维度**: HCAI 七原则 + 工程落地
- **对话脚本**:
  1. 以人为本 AI（Human-Centered AI, HCAI）是 Google PAIR 团队提出的设计框架。请列出 HCAI 的核心原则：(a) 人类控制（人类始终有最终决策权）；(b) 透明可解释（用户能理解 AI 在做什么）；(c) 公平无偏（不歧视任何群体）；(d) 安全可靠（不出错或出错时有兜底）；(e) 隐私保护（不滥用用户数据）；(f) 包容可及（不同能力用户都能用）；(g) 价值对齐（AI 目标与人类价值一致）。
  2. 「人在回路」（Human-in-the-Loop, HITL）是把人类判断嵌入 AI 流程的工程模式。HITL 三层级：(a) AI 决策 + 人类审核（高风险场景）；(b) AI 提供选项 + 人类选择（中等风险）；(c) AI 自动决策 + 人类可推翻（低风险）。设计 laew 的 HITL 策略：文件删除（必须用户确认）/ BashTool 执行（高风险命令二次确认）/ Yolo 任务分类（自动决策但用户可改档）。
  3. 「人在回路之上」（Human-on-the-Loop, HOTL）让人类监督 AI 而非逐步审核：AI 自动运行 + 异常时通知人类。设计 laew 的 HOTL：默认 Yolo 自动分类 + SubAgent 自动执行 → 但每个工作流的开始/结束 / 异常事件在 TUI 状态栏高亮 + 用户可随时 `Ctrl+C` 中断 + 保留当前 Session 上下文等待用户决策。
  4. 「人在回路之外」（Human-out-of-the-Loop, HOOTL）让 AI 完全自主：适用于低风险、可逆的任务（如内部测试 / 数据整理）。设计 laew 的 HOOTL 模式：`laew --autonomous` 启用（需用户明确开启）→ 全自动执行 + 仅在严重错误时通知 + 默认安全策略（如禁止 rm -rf）。

### CA57 AI UX 模式：流式 / 不确定性 / 来源 / 拒绝 / 记忆

- **预期档位**: medium
- **考察维度**: AI UX 模式 + 工程实现 + 用户体验
- **对话脚本**:
  1. 流式输出（Streaming）是 AI UX 的核心模式：LLM 生成 token by token → 实时呈现给用户，降低「等待焦虑」。请设计 laew 的流式输出：在 TUI 主屏逐 token 显示（避免整段卡顿）→ 用户随时按 `Ctrl+C` 中断 → 已显示内容保留。讨论为什么流式输出比「整段一次性输出」体验好（用户感觉系统更快 + 早期错误可早停）。
  2. 不确定性传达（Uncertainty Communication）：让用户知道 AI 在哪部分不太确定。设计三种不确定性表达：(a) 数字置信度（"我 80% 确定"）；(b) 自然语言（"大致是""可能"）；(c) 视觉表达（黄色标记 + 闪烁）。讨论为什么「过度表达不确定性」会让用户不信任（每句都说"可能"反而显得不专业）。
  3. 来源引用（Source Citation）：AI 输出时标注每个事实的来源。请设计 RAG 应用的引用 UI：回答文本中关键论断后加上 `[1][2]` 角标 → 鼠标悬停或按 `g` 跳转到源文档段落 + 显示相似度分数。讨论为什么这是「信任建立」的核心机制（用户能验证 AI 不是凭空捏造）。
  4. AI 拒绝（AI Refusal）模式：AI 应该能识别「超出能力范围」的请求并明确拒绝，而不是编造答案。请设计 laew 的拒绝策略：(a) 明确能力边界（"我只能读写文件 + 跑 Bash，不能控制 GUI"）；(b) 提供替代方案（"如果想做 GUI 自动化，建议用 Selenium"）；(c) 表达同理心（"我理解你想做 X，很抱歉帮不上"）。对比过度拒绝（"我什么都不能做"）与不拒绝（"硬编一个错答案"）的体验差异。

### CA58 协作智能（Collaborative Intelligence）：人与 AI 的最优分工

- **预期档位**: medium
- **考察维度**: 人机分工 + 互补优势 + 协作模式
- **对话脚本**:
  1. 人与 AI 各有擅长：人擅长（常识 + 创造力 + 价值判断 + 模糊推理 + 跨领域迁移）、AI 擅长（速度 + 一致性 + 海量记忆 + 多任务并行 + 不疲劳）。请设计一个人机分工矩阵：客服场景（AI 处理 80% 常见问题，人类处理 20% 复杂投诉）；代码审查场景（AI 自动审查 100% PR，人类重点审查关键模块）。
  2. 三种协作模式：(a) AI 主导（AI 做决策，人监督）；(b) 人类主导（人做决策，AI 辅助）；(c) 协同决策（AI 提供选项 + 推理，人类结合判断做最终决策）。设计 laew 的默认模式：协同决策（Yolo 提议任务分类 → 用户可改；Plan 提议方案 → 用户可改；SubAgent 执行 → 用户随时中断）。
  3. 「AI 增强」（AI Augmentation）vs 「AI 替代」（AI Replacement）的哲学差异：增强让人类做得更好（医生 + AI 诊断 = 更准）、替代让人类失业（客服 + AI 客服 = 失业）。请讨论 laew 定位：作为程序员的「AI 结对编程伙伴」是增强还是替代？（增强：程序员决策 + AI 执行繁琐任务）。
  4. 协作智能的未来：AI 不只作为「工具」而是「队友」（Teammate）。这需要 AI 具备：(a) 长期记忆（记得上次对话说过什么）；(b) 主动建议（发现潜在问题主动提醒）；(c) 情感感知（识别用户沮丧并调整风格）；(d) 自我解释（解释自己为什么这么做）。laew 在这四方面的成熟度：长期记忆（部分，session_memory）/ 主动建议（弱）/ 情感感知（无）/ 自我解释（部分，Debug Agent 报告）。讨论如何逐步提升。

### CA59 AI 错误恢复：从失败到学习的工程模式

- **预期档位**: medium
- **考察维度**: 错误分类 + 恢复策略 + 学习机制
- **对话脚本**:
  1. AI 系统的错误分三类：(a) 输入错误（用户输入有歧义或不完整）；(b) 推理错误（AI 推理过程出错）；(c) 工具错误（工具调用失败或返回错误）。请为每类设计检测方法：输入错误（让 AI 复述理解 + 用户确认）、推理错误（链式推理可被审查）、工具错误（捕获异常 + 重试）。
  2. 错误恢复的「3R 原则」：(a) Retry（重试，简单粗暴有效）；(b) Refine（细化，把任务拆细再试）；(c) Rethink（反思，换思路重新规划）。设计 laew 的 3R 策略：Yolo 分类失败 → Retry（换 prompt）/ Refine（提供更多上下文）/ Rethink（升级到 Plan Agent）。
  3. 「优雅降级」（Graceful Degradation）：当 AI 系统部分能力不可用时仍提供有价值的服务。设计 laew 的降级策略：(a) 主 Provider 失败 → 自动切换备选 Provider；(b) 网络完全断 → 切换本地小模型（见 CA37 边缘 AI）；(c) Compact Agent 压缩失败 → 降级到硬截断（保留最近 N 条消息）；(d) 工具调用失败 → 返回错误信息 + 建议替代方案（如「Bash 工具不可用，试试 Python 脚本」）。
  4. 「从错误中学习」（Learning from Mistakes）：系统遇到错误后改进避免下次再犯。设计 laew 的学习机制：(a) 错误日志写入 `agent_memory` 表 + 错误分类；(b) 下次类似任务时由 Yolo 检索错误历史 + 在 prompt 中提示「之前类似任务失败原因是 X，避免重蹈」；(c) Quality-Check Agent 收集失败案例作为 Few-shot Examples 喂给后续 SubAgent。讨论这种「错误驱动学习」相比「人类反馈微调（RLAHF）」的优势（无需重新训练 + 实时生效）。

### CA60 laew AI UX 优化路线：从「功能可用」到「体验优秀」

- **预期档位**: hard
- **考察维度**: 工程化升级 + 用户体验优化
- **对话脚本**:
  1. 评估 laew 当前 AI UX 成熟度：(a) 流式输出（已实现，TUI 逐 token 显示）；(b) 不确定性传达（无）；(c) 来源引用（部分，Debug Report）；(d) AI 拒绝（部分，「能力范围」提示）；(e) 记忆（部分，session_memory + agent_memory）；(f) 主动建议（弱，仅 Quality-Check）；(g) 情感感知（无）；(h) 自我解释（强，Debug Agent）。请画出 AI UX 雷达图并标出每项的优先级（高 / 中 / 低）。
  2. 设计「P0 体验优化包」：(a) Yolo 任务分类结果显示置信度（如「简单任务 92%」「中等任务 68%（建议补充上下文）」）；(b) SubAgent 工具调用前显示「即将执行：Bash `rm -rf /tmp/foo`，是否确认？」(c) Compact Agent 触发时显示「即将压缩 X 条早期消息保留 Y 条，确认？」；(d) `/explain` 斜杠命令：解释上一步 AI 决策的推理过程（读取 Debug Trace）。
  3. 设计「P1 信任增强包」：(a) 每次 LLM 调用显示用量（`[本次用量: 1.2K input + 350 output, 累计 ¥0.05]`）；(b) 错误时显示详细诊断（不是「出错了」而是「BashTool 调用超时（30s），建议：检查命令是否阻塞 / 重试」）；(c) Quality-Check 结果透明化（不只显示 ✅ 通过，还要显示「检查项：代码风格 ✅ / 安全性 ⚠️（发现 hardcoded password）/ 性能 ✅」）；(d) 「撤销栈」：每步操作可 Ctrl+Z 回退（参考 BF03 2048 撤销栈）。
  4. 设计「P2 以人为本升级」：(a) 「人在回路」配置：`laew --autonomous` / `--confirm` / `--readonly` 三档模式；(b) 情感感知：检测用户沮丧（多次失败 + 「怎么还不行」字眼）→ 自动切换更简洁模式 + 主动询问是否需要休息；(c) 主动建议：检测到用户反复执行相似命令 → 提示「是否将 `git status && git diff` 设为 alias？」；(d) 多模态：未来支持图片输入（截图 + 提问「这段代码哪里有 bug」）。讨论 laew 在 AI UX 上的差异化定位：相比 ChatGPT 这种通用对话，laew 的优势是「专业场景（编程）+ 本地化（数据自主）+ 可控性（人在回路）」。

## 与 laew 工程的具体对接点

1. **CA52 → Yolo 任务分类置信度**：当前 Yolo 输出 `task_level` 但无 `confidence` 字段，建议在 `TaskClassification` 结构体加 `confidence: f32` 字段（参考 LLM 输出 token 概率）。
2. **CA54 → Debug Agent + Debug Report**：已实现的 `-debug` 模式是决策溯源的具体落地，未来可加 TUI 可视化（`Ctrl+T` 显示决策树）。
3. **CA56 → BashTool 安全确认**：当前 BashTool 无确认机制，建议高风险命令（`rm` / `chmod` / `dd`）自动二次确认（参考 BL 疑难 Bug 中的「rm -rf 误操作」反思）。
4. **CA59 → agent_memory 错误学习**：当前 agent_memory 存 Agent 输入/输出，但缺「错误分类」字段，建议加 `error_type` 与 `lesson_learned` 列。
5. **CA60 → 流式输出优化**：当前 TUI 已支持流式，但缺「中断 + 保留已显示内容」机制，建议加 `Ctrl+C` 安全中断（参考 BF 撤销栈思想）。
