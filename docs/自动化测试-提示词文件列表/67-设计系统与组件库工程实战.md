### BP01 Design Token：从设计变量到多端产物
- **预期档位**: medium
- **考察维度**: Token 三层模型 + 多端编译
- **对话脚本**:
  1. Design Token 的本质：把设计稿里的「颜色 / 字号 / 间距 / 圆角」从 Figma 静态属性抽取为可版本化、可分发的结构化变量。三层模型：Reference Token（原始值，`color-blue-500: #3B82F6`）→ System Token（语义别名，`color-action-primary: {color.blue.500}`）→ Component Token（组件特化，`button-bg-primary: {color.action.primary}`）。
  2. 主流规范与工具：Salesforce Theo（JSON）、Amazon Style Dictionary（多平台编译）、Figma Tokens 插件、Style Dictionary（Node.js 生态最成熟，支持 iOS/Android/Web/Flutter 多端输出）、Tokens Studio（多设计工具同步）。
  3. 多端产物示例：Web 输出 CSS Variables (`--color-action-primary: #3B82F6`)、iOS 输出 Swift 颜色扩展 (`Color.actionPrimary`)、Android 输出 `colors.xml` + Compose 主题、Web Compose / Tailwind 配置、`Sketch / Figma` 同步文件。SCSS 变量 vs CSS 自定义属性的差异（运行时可换主题）。
  4. laew 的 TUI 主题色目前硬编码在 `src/tui/theme.rs`，建议抽出 `SELECTED_FG` / `TAB_FOCUSED_FG` / `HIGHLIGHT_FG` 等为 Theme Token，便于后续做「亮色 / 暗色 / 高对比度」多主题切换，并支持用户自定义。

### BP02 组件库 API 设计：受控与非受控、插槽与组合
- **预期档位**: medium
- **考察维度**: 组件 API 哲学 + 复合组件
- **对话脚本**:
  1. 受控（Controlled）vs 非受控（Uncontrolled）：受控组件由父组件传 `value` + `onChange` 接管状态，非受控用 `defaultValue` + `ref` 自己管理；类比 React `<input value={x} onChange={fn}>` vs `<input defaultValue="x" ref={r}>`，对比 Vue 的 `v-model`。
  2. 复合组件（Compound Components）模式：`<Tabs>` 套 `<Tabs.List>` 套 `<Tab>` 套 `<Tabs.Panel>`，通过 React Context 共享状态（Radix UI / Headless UI 风格）；对比「扁平 props」反模式（`<Tabs tabs={[...]}` 把所有配置塞进单个对象）。
  3. 插槽（Slot）与组合：Vue 的 `<slot>` / Web Components 的 `<slot name="header">` / React 的 `children` / props 渲染（`renderItem` 函数）；什么时候用 props 什么时候用 slot？
  4. laew 的 TUI Tab 表单（`src/tui/screen/provider_form.rs`）目前是 5+1 Tab 写死结构，建议抽象为复合组件：`<TabForm tabs=[{label, content}] onSubmit onCancel>`，让新增 `provider add` 之外的 Tab 表单（如「自定义 Agent 提示词」）复用同一渲染引擎。

### BP03 主题与暗色模式：语义色与对比度
- **预期档位**: simple
- **考察维度**: 暗色模式 + WCAG 对比度 + 语义色
- **对话脚本**:
  1. 暗色模式不只是「反色」：要降低纯白（避免发光感）、提亮纯黑（避免与 OLED 屏幕对比过强）、调整饱和度（暗背景下高饱和度更刺眼）、统一阴影策略（暗模式下用「光晕」代替「阴影」）。参考 Material Design 3 的 tone mapping 算法。
  2. WCAG 对比度计算：`((L1 + 0.05) / (L2 + 0.05))`，L 是相对亮度；AA 级正文要求 4.5:1、大字 3:1；AAA 级正文 7:1、大字 4.5:1。推荐工具：Stark / Contrast Checker / Chrome DevTools 自带对比度提示。
  3. 语义色 vs 装饰色：`success / warning / error / info` 必须从 System Token 来，不要直接用 `green-500 / red-500`；图标、边框、文字色都要根据「语义角色」取色，色盲用户通过「图标 + 文字 + 颜色」三重编码识别。
  4. laew 的 TUI 渲染用 crossterm ANSI 16 色，主题能力受限；建议至少支持「亮色（默认 Cyan 选中态）/ 暗色（Yellow 选中态）/ 高对比度（Bright White on Black）」三档，用环境变量 `LAEW_THEME=light|dark|hc` 切换。

### BP04 图标系统：SVG Sprite、字体图标与按需打包
- **预期档位**: simple
- **考察维度**: 图标技术选型 + 按需加载
- **对话脚本**:
  1. 三种主流图标方案对比：SVG 单文件（可着色、可动画、最灵活，但 HTTP 请求多）、SVG Sprite（一张大图 + `<use href="#icon-id">`，HTTP 请求少但难缓存）、Icon Font（Font Awesome / Material Icons，CSS 控制大小但渲染模糊、不支持多色）。
  2. SVG 优化流程：`svgo` 压缩（去掉注释 / 合并属性 / 精度降到 2-3 位）、自动 viewBox 标准化、用 `<symbol id="icon-xxx" viewBox="0 0 24 24"><path d="..."/></symbol>` 包裹便于 Sprite 复用；图标命名规范 `category-name`（`nav-home`、`action-search`）。
  3. 按需打包策略：Tree-shaking（`import { IconHome } from '@iconify/react'` 配合 unplugin-icons 按需引入）、全量打包（`@ant-design/icons` 完整包几百 KB）、图标中心化（本地 `icons/` 目录 + 脚本生成组件库）。
  4. laew 的 TUI 受字符画限制，建议用 Unicode 符号（`▶ ◀ ▸ ► ● ○ ✗ ✓ ⏵ ⏸`）+ Box Drawing（`─ │ ┌ ┐ └ ┘ ├ ┤ ┬ ┴ ┼`）构建图标体系，避免 emoji 在不同终端的渲染差异。

### BP05 栅格与响应式：断点、容器查询与流式排版
- **预期档位**: simple
- **考察维度**: 栅格系统 + 容器查询
- **对话脚本**:
  1. 经典栅格系统：Bootstrap 的 12 列栅格（`col-md-6`）、Tailwind 的 4/6/8/12 列断点系统（`sm: 640px / md: 768px / lg: 1024px / xl: 1280px / 2xl: 1536px`）、Material Design 的响应式栅格（`compact / medium / expanded / large / extra-large`）。
  2. 媒体查询 vs 容器查询：`@media (min-width: 768px)` 响应视口宽度，`@container (min-width: 400px)` 响应父容器宽度；容器查询让组件真正可复用（同一卡片在侧栏窄容器用一列、主流宽容器用三列）。
  3. 流式排版：`clamp(MIN, PREF, MAX)` 实现字号随视口缩放（`font-size: clamp(1rem, 0.5rem + 2vw, 1.5rem)`）、`aspect-ratio: 16/9` 响应式图片框、CSS Subgrid（嵌套对齐）。
  4. laew 的 TUI 是固定终端尺寸（默认 100x30），不存在响应式问题；但 Debug 报告需要按终端宽度自适应折行（`textwrap` crate 按 `terminal_size` 返回的宽度断行），避免在 80 列终端上溢出。

### BP06 排版系统：字号阶梯、行高与中西文混排
- **预期档位**: simple
- **考察维度**: 字号阶梯 + CJK 排版
- **对话脚本**:
  1. 字号阶梯的来源：模块化比例（Major Third 1.250、Perfect Fourth 1.333、Golden Ratio 1.618），从中性 16px 推导 12/14/16/20/25/31/39；中文场景常用 12/14/16/18/20/24/30/36 这种整数阶梯便于设计还原。
  2. 行高（line-height）的经验值：英文正文 1.5-1.75、中文正文 1.6-2.0（中文笔画密，需要更多行高透气）；`line-height: 1.6` 相对单位比 `24px` 绝对单位更易维护。
  3. 中西文混排规范：中西文之间加半角空格（`Hello 世界` → `Hello 世界`）、数字与中文之间（`共 100 个`）、全角标点与英文标点的选择、引号嵌套（`"'嵌套'"` → `" '嵌套' "`）。
  4. laew 的 TUI 提示词渲染（Yolo 输出长中文文案 + 部分英文代码）时，建议自动在中英文之间补 1 个空格（用 `unicode-width` 计算宽度时按显示列而非字符数），让排版更易读。

### BP07 动效规范：时长、缓动曲线与降级
- **预期档位**: simple
- **考察维度**: 动效设计 + 可访问性降级
- **对话脚本**:
  1. 动效时长经验值：微交互（按钮反馈）100-150ms、过渡（菜单展开、模态弹出）200-400ms、页面切换（路由跳转）400-600ms；超过 1 秒用户就开始焦虑，超过 5 秒必须有进度提示。
  2. 缓动曲线（Easing）的语义：linear（机械）适合匀速运动；ease-in（慢进）适合出场（元素离开屏幕）；ease-out（慢出）适合入场（元素进入屏幕）；ease-in-out 适合往返运动；cubic-bezier 自定义（Material Design 的 `cubic-bezier(0.4, 0, 0.2, 1)`）。
  3. 可访问性降级：`@media (prefers-reduced-motion: reduce)` 用户开启系统级「减少动效」时，禁用所有非必要动画（保留功能性动画如进度条）；前端框架检测 `matchMedia('(prefers-reduced-motion: reduce)').matches`。
  4. laew 的 TUI 动画只有光标闪烁 + Esc 退场重绘，已天然避免动效过度；建议给「重绘帧率」加上限（每 16ms 一次 = 60fps），避免在远程连接的低带宽终端上刷屏过快。

### BP08 表单与数据录入规范：校验时机与错误呈现
- **预期档位**: medium
- **考察维度**: 表单 UX + 校验策略
- **对话脚本**:
  1. 校验时机三档：失焦校验（用户填完一项就校验，避免「提交时一堆错误」）、提交校验（最后一道关卡）、实时校验（用户输入时即时反馈，密码强度、用户名占用）；通常组合使用（失焦校验 + 提交兜底）。
  2. 错误呈现的位置：行内错误（字段下方红字 + 图标）、表单顶部汇总（适合多项错误）、Toast 提示（次要提醒）；不要用原生 alert 弹窗打断流程；错误文案要给出修复建议（不要只说「输入有误」，要说「密码至少 8 位，包含数字和字母」）。
  3. 数据录入的「智能默认」：自动填充历史值、记住用户选择、提供常见选项下拉（`+86 手机号` 选中区号）、自动格式化（输入身份证号自动 6-8-4 分段）；长表单分步骤（Wizard）降低单页认知负担。
  4. laew 的 `ProviderForm` 表单（`src/tui/screen/provider_form.rs`）目前是「Enter 进入编辑态 → Enter 退出编辑态 → 切换 Tab」流程，建议加失焦校验：end_point 必须以 `http://` 或 `https://` 开头、api_key 长度至少 16 位，避免提交后才发现格式错。

### BP09 数据可视化设计规范：图表选型与配色
- **预期档位**: medium
- **考察维度**: 图表选型 + 可视化语义
- **对话脚本**:
  1. 图表选型决策树：比较关系用柱状图 / 条形图、时间趋势用折线图 / 面积图、占比用饼图 / 环形图（项数 ≤ 7 时）、分布用直方图 / 箱线图、相关性用散点图 / 气泡图、流程用桑基图 / 漏斗图；地理用地图（choropleth / heatmap）。
  2. 配色原则：分类数据用 qualitative 色板（Categorical：ColorBrewer Set1/Set2、Tableau 10）、连续数据用 sequential（单色渐变，如 `viridis`、`plasma`）、有正负的用 diverging（双色渐变，中间白）；避免红绿组合（色盲不友好），改用蓝橙（ColorBrewer RdBu 反向）。
  3. 图表的可访问性：图例、坐标轴标签、悬浮 tooltip 必须文字化（不能只靠颜色区分系列）、提供数据表格备用视图、避免三维饼图（透视变形误导）、柱状图从 0 基线开始（截断 Y 轴会误导比例）。
  4. laew 的 Debug 报告（`DebugReport/debug_report_*.md`）想展示「各 Agent 的耗时 / Token 占比」时，建议用 Mermaid 图表（`pie` 饼图 + `bar` 柱状图）嵌入 Markdown，便于在 GitHub / VSCode 直接渲染，并辅以 Markdown 表格作为数据源。

### BP10 组件库文档与治理：变更、废弃与版本演进
- **预期档位**: medium
- **考察维度**: 文档站 + SemVer + 废弃流程
- **对话脚本**:
  1. 文档站的形态：Storybook（React/Vue 组件独立展示 + 控件面板）、Histoire（Vue 3）、Dumi（React + Umi）、MDX（Markdown + JSX 混写）、自定义文档站；核心要素：组件预览、Props 表格、代码示例（可一键复制）、设计稿链接（Figma embed）、变更日志（Changelog）。
  2. SemVer 语义化版本：主版本（破坏性变更）、次版本（向后兼容的新功能）、补丁版本（向后兼容的 bug 修复）；对组件库而言，删除 prop、改 prop 类型、修改默认行为都是主版本变更。
  3. 废弃（Deprecation）流程：标记 `@deprecated` JSDoc 注释 + IDE 删除线、文档中加废弃横幅、`console.warn` 运行时提示、给出迁移指南（migration guide）、预留至少 1 个次版本周期（3-6 个月）后再删除；维护「CHANGELOG.md」按 Keep a Changelog 规范分类（Added / Changed / Deprecated / Removed / Fixed / Security）。
  4. laew 的 8 个 Agent 角色（Yolo/Plan/Main-Work/SubAgent-Work/Quality-Check/SessionContext/Debug/Compact）如果某天要新增或合并，建议走类似流程：在 `docs/` 加 RFC 提案 → 标记旧角色为「deprecated」并保留至少 1 个版本 → 同步更新 `progress` 账本 → CHANGELOG 标注 Breaking Change。
