### CM01 大厅与房间服务器架构

- **预期档位**: medium
- **考察维度**: 连接管理 + 房间生命周期 + 广播扇出
- **对话脚本**:
  1. 用 Go 写一个「大厅 + 房间」两层的游戏服务器骨架：大厅维护在线玩家表 `map[PlayerID]*PlayerConn`（读写锁或分片锁），房间 `struct Room { ID, Players map[PlayerID]*Seat, State, Tick chan struct{} }`；玩家流程是 登录大厅 → 创建/加入房间 → 房间内收发消息。
  2. 房间生命周期状态机：等待中 → 倒计时 → 游戏中 → 结算 → 销毁；写房主迁移逻辑（房主退出后随机指定新房主并广播），再加一个定时回收空房与超时未开局房间的 goroutine。
  3. 房间广播的扇出实现：比较「每玩家一个发送队列 + 单独 writer goroutine」与「遍历连接同步写」两种方案在慢玩家（接收缓冲堆积）下的表现，给出背压策略（丢弃低优先级消息 / 踢出持续堵塞的连接）。
  4. laew 借鉴：laew 的 `MultiAgentOrchestrator` 同层 SubAgent 并行（tokio::spawn + Semaphore=3）与房间广播扇出同构，讨论「信号量限流」与「逐房间背压」在两种系统里各自的取舍。

### CM02 匹配系统：MMR 分桶与 ELO 更新

- **预期档位**: medium~hard
- **考察维度**: 匹配队列算法 + ELO 公式 + 分队均衡
- **对话脚本**:
  1. 设计匹配队列：玩家点击「开始匹配」后进入按 MMR 分桶的队列，写一个「时间窗扩大」的搜索循环——每 5 秒把可接受的分差 ±100 放宽一档，超过 60 秒给出「放宽提示」，避免高分玩家无限等待。
  2. 用 Python 实现 ELO 更新：预期胜率 `Ea = 1 / (1 + 10^((Rb - Ra) / 400))`，赛后 `Ra' = Ra + K * (Sa - Ea)`；讨论 K 因子分段（新手 K=40 快速收敛 / 高分段 K=10 防波动）。
  3. 分队均衡：8 名匹配成功的玩家分两队，目标是两队总 MMR 差最小且「5 连败玩家尽量不同队」；先写排序贪心（蛇形分票 1-2-2-2-1），再分析为什么动态规划或小规模枚举更优。
  4. laew 借鉴：把「匹配」思想用到 Yolo 任务分类——任务难度与执行档位（simple/medium/hard）就是一个双向匹配问题，设计一个「连续失败自动降档、连续成功尝试升档」的 ELO 式自适应策略。

### CM03 状态同步：快照、插值与延迟补偿

- **预期档位**: hard
- **考察维度**: 服务器 tick + delta 压缩 + 客户端插值 + 回溯判定
- **对话脚本**:
  1. 服务器以 15~30Hz 固定 tick 权威模拟整局游戏，每 tick 向客户端发快照；写 delta 压缩：快照只携带「相对上一确认帧变化的字段」+ 位标志（bitfield 标记哪些字段存在），用 Rust 定义 `Snapshot { seq, base_seq, changed_mask: u32, entities: Vec<DeltaEntity> }`。
  2. 客户端插值：本地缓冲两个快照（约 100ms），渲染时在两帧之间按 `t = (now - t0) / (t1 - t0)` 线性插值；再补「外推」逻辑——下一帧未到时按速度预测最多 250ms，写插值与外推的切换代码。
  3. 延迟补偿（Lag Compensation）：服务器保存每个实体最近 1 秒的历史位置环形缓冲，玩家开枪时带客户端时间戳，服务器回溯到该时刻做命中判定；解释这个设计为什么对高 ping 玩家公平、又如何被「回溯滥用」（故意高延迟 peek）利用。
  4. laew 借鉴：Compact Agent 的上下文压缩与快照 delta 同源——「只传变化量」的思想能否用于 `session_memory` 历史摘要的增量维护（上一任务摘要 + 本任务 delta，而不是每次全量重写）。

### CM04 帧同步 Lockstep 的服务端：指令中继与校验

- **预期档位**: hard
- **考察维度**: 指令中继 + 确定性哈希校验 + 丢指令重传
- **对话脚本**:
  1. 帧同步（Lockstep）架构下服务器**不跑游戏逻辑**，只做「指令中继」：客户端上传 `(logic_frame, player_id, op)`，服务器收集本帧全部指令广播给所有人；解释为什么这要求客户端模拟 100% 确定（同种子 + 同指令流 + 同浮点行为），与 AB06 的客户端帧同步互为表里。
  2. 防作弊校验：客户端在关键帧（每 30 帧）上报「状态哈希」（对全体单位位置/血量序列化后哈希），服务器比对各方哈希，分歧则标记作弊或环境异常；写这个状态哈希的序列化规则（字段顺序固定 / 浮点转定点再哈希）。
  3. 丢指令恢复：指令带自增 id 与 ack，服务器发现某客户端缺指令时下发补发窗口（环形缓冲保存最近 256 帧）；讨论「等最慢玩家」的 pace 调节对整体延迟的影响。
  4. laew 借鉴：把「状态哈希链」用于 Session transcript 完整性校验——每轮消息附带前一轮哈希形成链，检测会话上下文是否被篡改或丢失，与游戏防作弊哈希同构。

### CM05 断线重连与观战

- **预期档位**: medium~hard
- **考察维度**: 重连令牌 + 增量追赶 + 心跳超时 + 观战流
- **对话脚本**:
  1. 断线重连协议：进房时发放 `reconnect_token = HMAC(room_id, player_id, seat_id)`，掉线后凭 token 在 120 秒内重入原座位；重连后先发一份全量快照，再补发期间的增量指令流，写这个「全量 + 增量追赶」流程。
  2. 弱网判定：客户端 3 秒一次心跳 ping，服务器连续 3 次未收到判「掉线」，进入托管倒计时（AI 接管操作）而不是立刻清座位；讨论托管 AI 的最简单实现（原地防守 / 撤退）。
  3. 观战模式：比较「3 分钟延迟的直播流」（复制玩家视图延迟投递，可防偷屏）与「实时上帝视角」（仅裁判权限）两种实现，写观战者订阅房间的权限校验中间件。
  4. laew 借鉴：对照游戏重连讨论 laew 的「会话恢复」——TUI 进程崩溃后当前 Session 上下文全部在内存丢失，设计一个 transcript 落盘 + 重启后按 session_id 恢复的方案，指出与游戏重连的「全量快照」等价物是什么。

### CM06 服务器权威与反作弊

- **预期档位**: hard
- **考察维度**: 权威校验规则 + 行为统计检测 + 经济审计
- **对话脚本**:
  1. 服务器权威（Server Authority）原则：移动、伤害、资源全部在服务端验证——移动请求校验「速度上限 / 瞬移距离 / 碰撞体积」，伤害请求校验「射程 / 冷却 / 视线遮挡」；用 Rust 写一个移动合法性校验函数（基于上一次确认位置与最大速度推算可达域）。
  2. 行为统计反作弊：不做逐条规则，而是统计建模——APM 超人上限、爆头率突变（滑动窗口 z-score）、每分钟资源获取速率超出理论值即标记；写一个滑动窗口异常检测器并讨论阈值选择（误封代价 vs 漏检代价）。
  3. 经济系统反作弊：道具/货币只能由服务器生成，客户端仅表现；所有交易写 append-only 日志（流水号单调），写一个离线对账脚本扫描「凭空增加」「负库存」「自交易刷金」三类异常。
  4. laew 借鉴：BashTool 的命令执行就是「客户端发起、服务器裁决」的模型——讨论 laew 应该给 Bash 加哪些「权威校验」（路径白名单 / 危险命令拦截 / 输出长度限制），与游戏服务器权威的规则设计方法论一致。

### CM07 排行榜与赛季系统

- **预期档位**: medium
- **考察维度**: Redis ZSET + 分页查询 + 赛季归档 + 防刷门槛
- **对话脚本**:
  1. 用 Redis ZSET 实现排行榜：`ZADD rank:{season} score member`、`ZREVRANGE` 取 Top100、`ZREVRANK` 查我的名次；分数相同时「先达到者靠前」的技巧：score = 分数 × 10^10 + (MAX_TS - 达成时间戳)。
  2. 分页与邻居展示：Top100 分页接口 + 「我的名次 ± 3 名」的邻居段查询（`ZRANGE rank 637 643 BYSCORE` 思路），处理百万人榜单的大分页问题（深分页禁止 ZREVRANGE 大偏移，改用游标 score+member 定位）。
  3. 赛季系统：每赛季 8 周，到期「重置活跃榜 + 归档历史榜」（`RENAME rank:s7 rank:s7:archive`），奖励按名次段位发放且必须幂等（发奖流水表唯一键防重复）；写赛季切换的事务脚本。
  4. laew 借鉴：`session_memory` 历史摘要的「赛季」思想——超过注入窗口（最近 3 条）的摘要不要删，按月归档成冷数据，Yolo 遇到「上周做过什么」类问题时再按需召回。

### CM08 实时传输选型：TCP / WebSocket / KCP / QUIC

- **预期档位**: medium~hard
- **考察维度**: 传输层对比 + 不可靠通道设计 + 弱网实测
- **对话脚本**:
  1. 实时游戏传输对比：TCP 队头阻塞（一个包丢失阻塞全部）、WebSocket（基于 TCP 同样阻塞）、KCP（UDP 上的快速重传 + 可选前向纠错）、QUIC（UDP 上多流无队头阻塞）；给「回合制 / MOBA / FPS / 大逃杀」各选一个并说明理由。
  2. 双通道设计：用 Rust（quinn 或 kcp crate）实现一个房间网关——不可靠通道发「位置快照」（丢了就丢，下一帧覆盖），可靠通道发「聊天/技能释放/进出房」；写两个通道的消息分流路由代码。
  3. 弱网实测：用 `tc netem` 注入「10% 丢包 + 200ms 延迟 + 抖动」，对比三种方案下的指令到达延迟分布（p50/p99），解释 KCP 为什么在这种网络下反超 TCP（无阻塞快速重传 + 延迟优先模式）。
  4. laew 借鉴：laew 与 LLM 的通信是流式响应（SSE/chunked），讨论为什么「不可靠通道」对 LLM 语义完全不适用（一个 token 丢失整段语义损坏），以及流式渲染中「丢帧降级」的正确姿势（丢中间帧、保终止帧）。

### CM09 房间二进制协议设计

- **预期档位**: medium~hard
- **考察维度**: 帧格式 + 版本兼容 + 握手加密与防重放
- **对话脚本**:
  1. 手写二进制协议：帧头 `[len: u16][msg_id: u16][seq: u32][payload...]`，用 Rust 写 `read_frame(&mut stream)` 与 `write_frame()`，处理粘包/半包（BufReader + 循环 until len 齐全）与最大帧长防护（拒绝 len > 64KB 的帧防内存攻击）。
  2. 版本兼容演进：新增字段用「消息内 TLV（type-length-value）尾部追加」或「msg_id 升版本 + 旧版忽略未知尾段」；对比手写协议与 protobuf 的开发成本、包体大小、调试难度，说明什么规模之前手写更划算。
  3. 安全加固：握手阶段用 ECDH 协商会话密钥，之后所有帧用 AES-GCM 加密；seq 单调递增 + 接收方滑动窗口防重放（重放旧帧直接断连），写防重放窗口判定的位图实现。
  4. laew 借鉴：对照 laew 的 `llm/anthropic.rs` 与 `llm/openai.rs` wire 转换层——「协议差异封闭在客户端内部、上层用统一消息模型」的设计，如果房间协议也要同时支持 KCP 与 WebSocket 双底层，应该怎么抽象一个 `Transport` trait。

### CM10 协议机器人压测与容量估算

- **预期档位**: hard
- **考察维度**: 压测机器人 + pprof 瓶颈定位 + 单服容量模型
- **对话脚本**:
  1. 写协议压测机器人（Go 或 Rust）：模拟 N 个玩家完成 登录 → 进房 → 按真实行为模型（每秒 2~5 个随机操作 + 心跳）持续压测 10 分钟，统计 指令 RTT 分布 / 房间 tick 实际耗时 / 服务器 CPU 与内存曲线。
  2. 瓶颈定位：用 Go pprof（或 Rust tokio-console）抓火焰图，识别「单房间 tick 过长」「广播扇出占满 CPU」「GC 暂停导致 tick 超时」三类典型瓶颈，分别给出优化方向（tick 内逻辑切片 / 广播并行化 / 对象池减少分配）。
  3. 容量估算模型：单房间每 tick CPU 耗时 c 与 tick 频率 f 已知，单核可承载房间数 = 1 / (c × f)，再乘核数 × 预留 30% 余量得出整机房间数；讨论为什么「房间迁移」极难导致扩容只能靠预分配（新房间调度到新机器），与无状态服务的弹性伸缩的本质区别。
  4. laew 借鉴：mock LLM 的 e2e 压测与游戏机器人同构——给 laew 写一个「假 LLM 网关 + 并发会话机器人」，验证 MultiAgentOrchestrator 在 Semaphore=3 限流下的最大并发会话数与排队延迟，作为容量规划的依据。
