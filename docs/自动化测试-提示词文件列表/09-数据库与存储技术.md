# 自动化测试提示词 — 数据库与存储技术（I01–I10）

> 使用说明见同目录 `README.md`。每条提示词在同一 Session 内按轮次顺序喂入。

## 维度说明

本维度考察 Agent 在**数据库与存储工程**场景下的"动手闭环"能力：能不能现场造数据、写最小可跑 SQL/脚本、用命令验证产物。侧重索引/事务/迁移/备份/建模/性能等真实工程能力，所有产物落 `tmpPlan/agent-test/`，全部用 python3 内置 sqlite3 模块（不依赖 sqlite3 CLI）。

---

### I01 索引对查询的加速效果实测
- **预期档位**: simple
- **考察维度**: 索引设计 / 实验对比闭环
- **工具链**: Write → Bash → Bash → Bash
- **对话脚本**:
  1. 在 `tmpPlan/agent-test/i01.db` 用 python3 内置 sqlite3 模块建表 `orders(id, city, amount, created_at)`，用脚本循环插入 5 万行数据，其中 `city` 随机取自 10 个城市。
  2. 写一段 SQL：统计 `city='BJ'` 且 `created_at > '2024-01-01'` 的订单总金额，先不建索引跑一次，输出耗时与扫描行数（用 `EXPLAIN QUERY PLAN`）。
  3. 给 `(city, created_at)` 建复合索引后再跑同一条 SQL，输出新耗时与新 plan，对比提升倍数。
  4. 把实验脚本与对比结果写到 `tmpPlan/agent-test/i01_report.md`：解释复合索引列顺序的依据（高基数放前），断言第二次 `SEARCH ... USING INDEX` 不再含 `SCAN`。

### I02 索引场景辨析（含覆盖索引）
- **预期档位**: simple
- **考察维度**: 索引取舍 / 覆盖索引验证
- **工具链**: Write → Bash → Bash → Write
- **对话脚本**:
  1. 在 `tmpPlan/agent-test/i02.db` 建 `users(id, name, email, signup_at)`，插入 1 万行，跑 3 条查询并用 `EXPLAIN QUERY PLAN` 输出各自计划：全字段 SELECT、按 name 模糊查询、按 id 查 email。
  2. 对第 1 轮的"按 id 查 email"加索引 `idx_id(id)` 后再跑一次，断言计划变为 `USING INDEX idx_id` 且仍出现 `SEARCH ... USING COVERING INDEX`（若实现支持覆盖索引），否则比对检索代价是否下降。
  3. 故意建 4 个冗余索引（每列单独 + 复合），跑批量 INSERT 1 千行计时，对比删掉冗余索引后的耗时，验证"索引不是越多越好"。
  4. 总结写到 `tmpPlan/agent-test/i02_summary.md`：列出 3 个"不该建索引"的场景（小表/低基数/频繁写），并解释覆盖索引为何能避免回表。

### I03 SQLite WAL 模式下并发读写实测
- **预期档位**: medium
- **考察维度**: WAL 模式 / 并发安全验证
- **工具链**: Write → Bash → Bash → Bash
- **对话脚本**:
  1. 在 `tmpPlan/agent-test/i03.db` 建 `kv(key TEXT PRIMARY KEY, val TEXT)`，先写 `PRAGMA journal_mode=WAL`，用 `PRAGMA journal_mode` 输出确认切到 `wal`（不是 `delete`）。
  2. 用两个 python 进程并发：A 进程循环 1000 次 `UPDATE`，B 进程同时循环 1000 次只读 `SELECT`，最后断言两边都没抛 `database is locked` 异常（Bash 用 `wait` 收尾并打印 exit code）。
  3. 关掉 WAL 改回 `journal_mode=delete` 重复第 2 步的并发实验，断言会观察到 `database is locked` 抛错或性能下降。
  4. 把两次实验的耗时与错误计数写到 `tmpPlan/agent-test/i03_report.md`，解释 WAL 为什么读写不互斥（写日志+检查点合并），最后给 `agent_memory` 多 Session 并发写入一个最小防御方案（BEGIN IMMEDIATE + busy_timeout）。

### I05 迁移：单 provider 表 → 多 provider 表
- **预期档位**: hard
- **考察维度**: expand/contract 迁移闭环
- **工具链**: Write → Bash → Bash → Bash
- **对话脚本**:
  1. 在 `tmpPlan/agent-test/i05.db` 现场建一份"老格式"单表 `providers_v1(id, name, model, url, key)`，插入 3 行假数据，故意让其中 1 行 `key` 为空（用于后续断言）。
  2. Write 写迁移脚本 `tmpPlan/agent-test/i05_migrate.py`：用 expand 模式（新建 `providers_v2` 含 `protocol/api_key_enc/is_active/created_at/context_max_size`），把 v1 数据写回 v2 并打 `migrated_from=v1` 标记；先用 Bash 跑该脚本，断言 v2 行数=3 且空 key 行被记录到 stderr。
  3. 在脚本里加一段"故意写出错"的逻辑：尝试把 `model` 写到 `context_max_size INTEGER` 列，重跑脚本断言失败并回滚（脚本需 `try/except` 包在事务里），然后修复为正确类型再次跑通。

### I07 备份与完整性校验
- **预期档位**: medium
- **考察维度**: 备份策略 / 完整性校验
- **工具链**: Write → Bash → Bash → Write
- **对话脚本**:
  1. 在 `tmpPlan/agent-test/i07/` 准备一份 `source.db`（用 python3 写入 1000 行 `orders` 数据），写一个 `i07_backup.py`：调用 `sqlite3.Connection.backup()` 备份到 `backup.db`，并用 `VACUUM INTO 'backup_vac.db'` 再做一份。
  2. Bash 同时跑两种备份，Bash 用 `md5sum` 与 `wc -c` 比较两个备份与源库的体积/一致性；故意把 `backup.db` 截断 100 字节后跑 `PRAGMA integrity_check`，断言返回 `*** in database main ***` 错误信息。
  3. 用 `PRAGMA quick_check` 与 `PRAGMA integrity_check` 跑完好的 `backup_vac.db`，断言都返回 `ok`。
  4. 写 `tmpPlan/agent-test/i07_report.md`：列出三种备份方法的风险点（在线 `.backup` 安全、VACUUM INTO 安全、文件复制可能在 WAL 写入中途不一致），并给出"备份后自动跑 integrity_check"的 5 行 shell 片段。
