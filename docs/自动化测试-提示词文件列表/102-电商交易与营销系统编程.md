### CT01 购物车：加购、合并与凑单

- **预期档位**: medium
- **考察维度**: 匿名车登录合并 + 选中态 + 价格快照
- **对话脚本**:
  1. 数据模型：`cart(user_id, sku_id, qty, checked, added_at)` 唯一键 (user_id, sku_id)；加购重复 SKU 数量累加、上限 99、购物车总条数上限 100（防刷）；写加购 / 改量 / 删除的三个接口逻辑。
  2. 匿名车合并：未登录用 `device_id` 标识的匿名车，登录时与账户车合并——同 SKU 数量取「较大值」还是「相加」？写合并事务并讨论选择的理由（营销预算 vs 用户体验）。
  3. 价格快照问题：购物车展示「加购价」还是「当前价」？下单永远以「当前时刻价格」重新计算（防价格过期），加购价仅作「降价提醒」对比；写 `reprice(cart)` 批量查价函数并处理「SKU 已下架」的标记展示。
  4. laew 借鉴：匿名态到登录态的「身份归一」对照 laew 的 device_id / account_uuid / session_id 三层身份——讨论 Yolo 注入历史摘要时按哪层身份召回（同设备不同会话该共享多少记忆）。

### CT02 商品与 SKU：属性组合与规格建模

- **预期档位**: medium~hard
- **考察维度**: SPU-SKU 关系 / 规格生成 / 库存与价格挂 SKU
- **对话脚本**:
  1. SPU/SKU 建模：SPU「iPhone 17」是商品实体，SKU「黑色 256G」是可购买单元——规格属性（颜色 × 容量 × 版本）笛卡尔积生成候选 SKU，商家勾选实际售卖组合；用 SQLite 设计三张表（spu / sku / sku_spec）并写「提交规格生成 SKU」的事务。
  2. 不规则规格：不是所有属性组合都合法（256G 只有黑色）——前端动态联动（选了黑色才亮 256G），后端也要校验「提交的组合在 SKU 表存在」；写规格可用性查询（给定已选属性返回其它属性的可用值集合）。
  3. 库存与价格挂 SKU 不挂 SPU：每个 SKU 独立库存 / 价格 / 主图；处理「多规格统一改价」的批量操作与「部分 SKU 售罄但商品仍在售」的展示逻辑。
  4. laew 借鉴：SPU-SKU「同一实体的多维度变体」对照 laew 的 AgentProfile（8 个角色是「Agent」这个 SPU 的不同 SKU——工具集 / 系统提示词是规格维度），讨论未来加「自定义 Agent」时如何复用这套规格建模。

### CT03 库存扣减：预占与防超卖

- **预期档位**: hard
- **考察维度**: 数据库行锁 vs Redis 原子扣减 + 预占回滚
- **对话脚本**:
  1. 朴素版与超卖复现：`UPDATE sku SET stock = stock - 1 WHERE id = ?` 没有条件判断，并发下负库存；修复一 `WHERE stock >= qty` + 影响行数判断；用 SQLite/MySQL 并发脚本复现超卖再验证修复。
  2. 预占模型：下单不直接扣「可售库存」而是「预占」（15 分钟支付时限），`库存 = 总量 - 已售 - 预占`；超时未支付释放预占回滚；写预占 / 确认（支付成功转已售）/ 释放三态转换的表结构与事务。
  3. Redis 热点优化：爆款 SKU 数据库行锁竞争——Redis `DECRBY` + Lua 脚本原子判定（余量不足回滚），异步批量落库数据库做兜底对账；写这个 Lua 脚本并讨论「Redis 与 DB 不一致窗口」的修复路径。
  4. laew 借鉴：库存「预占 + 超时释放」对照 laew 的 Semaphore 并发上限（3）——讨论 SubAgent 配额是否也需要「预占语义」（任务开始占坑、卡死的任务超时自动释放坑位，防止一个挂起任务耗尽全部并发额度）。

### CT04 秒杀系统：削峰与热点账户

- **预期档位**: hard
- **考察维度**: 流量漏斗 + 队列串行化 + 库存分桶
- **对话脚本**:
  1. 流量漏斗设计：静态化活动页（CDN）→ 答题/验证码打散请求时间 → 前端按钮置灰防连点 → 网关限流（令牌桶，联动 AQ07）→ 库存检查 Redis 拦截 99% 流量 → MQ 排队异步下单；画漏斗并标注每层预期削峰比例。
  2. 队列串行化：进入 MQ 的请求按「SKU 维度」分区串行消费（同 SKU 一个消费者保序），消费端做库存扣减 + 订单落库；写分区键选择逻辑（sku_id hash）并讨论「用户重复排队」的幂等去重（user_id + activity_id 唯一）。
  3. 库存分桶：单 SKU 10 万件拆 100 个桶各 1000 件，用户 hash 到桶扣减，桶空后「借桶」重试其它桶；分析分桶对吞吐的提升与「部分桶剩余无法汇总卖完」的碎片问题及阈值合并策略。
  4. laew 借鉴：秒杀「快速失败 + 排队异步化」对照 laew 长任务体验——hard 任务全链路可能跑几分钟，讨论把 Yolo 编排改成「先秒回受理 + 后台执行 + TUI 进度轮询」的模式（现在的同步阻塞会发生什么）。

### CT05 优惠券：模板、领取与核销

- **预期档位**: medium~hard
- **考察维度**: 券模板约束 / 领取防超发 / 核销互斥规则
- **对话脚本**:
  1. 券模板：`coupon_template(id, 类型[满减/折扣/无门槛], 面额, 门槛, 总量, 每人限领, 适用范围, 生效期)`；领取表 `user_coupon(id, template_id, user_id, status[未用/已用/过期/锁定], received_at)` 唯一键 (template_id, user_id) 防超领；写领取接口（限量 DECR + 限领唯一键双保险）。
  2. 下单用券：锁定券（status → 锁定）→ 支付成功核销（→ 已用）→ 取消订单释放（→ 未用）；「最优券自动推荐」（多张可用时面额最大可完全使用的一张）的贪心选择算法；写这个三态流转与推荐逻辑。
  3. 互斥与叠加规则：品类券与全站券不可叠加、折扣券封顶 50 元、退款按「券是否退回」分策略（未核销退回 / 已核销不退）；把规则做成可配置的「叠加策略表」而不是硬编码 if 链。
  4. laew 借鉴：券的「锁定-核销-释放」三态对照 laew 工具执行的事务性——BashTool 执行中途失败的回滚语义（无事务，副作用已发生），讨论哪些工具需要「预演/锁定」阶段（Write 先写临时文件再 rename）实现准事务。

### CT06 订单状态机与超时关单

- **预期档位**: medium~hard
- **考察维度**: 状态机建模 + 守卫条件 + 延迟队列关单
- **对话脚本**:
  1. 订单状态机：待支付 → 已支付 → 履约中(发货/服务) → 已完成，分叉：取消 / 退款 / 部分退款；用 Rust enum + `transition(from, event) -> Result<To>` 建模，非法迁移（已完成→待支付）必须显式拒绝并记录；写状态迁移表（matrix）作为单一事实源。
  2. 守卫条件：迁移附带条件——「取消」仅当未发货且库存预占可释放、「已完成」仅当履约凭证齐全；守卫失败返回业务错误码而非通用失败；讨论守卫逻辑放状态机内还是业务层（推荐：结构性约束进状态机、业务规则做守卫注入）。
  3. 超时关单：待支付 15 分钟自动取消——实现方式对比：定时全表扫（简单但延迟大）、延迟消息队列（ RocketMQ delay / Redis ZSet 时间轮）、内存时间轮 + 落盘兜底；写 Redis ZSet 版（score = 到期时间，轮询器每秒取到期集合）并处理「关单与支付回调并发竞争」（谁先拿到状态机迁移权谁赢，后者收到明确失败）。
  4. laew 借鉴：状态迁移表对照 Yolo 的任务三档与失败回流——任务状态（分类中/执行中/质检中/完成/回流）也是状态机，讨论把回流规则显式建成「迁移表 + 守卫」而不是散落在编排代码里，可测试性差异。

### CT07 支付对接：回调、验签与状态一致性

- **预期档位**: hard
- **考察维度**: 异步回调协议 / 验签防伪 / 对账兜底
- **对话脚本**:
  1. 支付流程：创建订单 → 调支付渠道统一下单（拿支付链接/预支付 ID）→ 用户在渠道侧完成支付 → 渠道异步 POST 回调商户服务器；写「接收回调」端点的协议要求：必须幂等、必须快速返回成功 ACK（重业务异步化）、失败重试由渠道按衰减频率重发（1m/5m/10m…）。
  2. 验签与校验：按渠道规则验签（支付宝 RSA2 公钥验签 / 微信 APIv3 平台证书验签 HMAC/AES-GCM 解密）+ 业务校验（out_trade_no 存在、金额与订单一致、app_id 匹配）；写伪代码流程并解释「不验金额」的经典事故（回调伪造 0.01 元支付成功大额订单）。
  3. 主动查询兜底：回调可能丢失——支付后未收到回调时「主动查单」（轮询查单接口直到终态），以及每日对账文件比对（联动 CS03 三方对账）；写「回调查询双通道汇合」的状态更新函数（两通道都幂等，先到先得后到确认）。
  4. laew 借鉴：回调重试 + 主动查询的「双通道容错」对照 LLM API 的流式中断处理——SSE 断流后不能只等重连（被动），应主动「查询」当前生成状态或以最后完整块重试（主动），讨论两通道汇合的幂等去重在 laew 的等价物。

### CT08 商品搜索与筛选：facets 与相关性

- **预期档位**: medium~hard
- **考察维度**: 多条件筛选 / 分面聚合 / 搜索排序
- **对话脚本**:
  1. 需求拆解：搜索「手机」+ 筛选（品牌多选 / 价格区间 / 内存多选 / 有货）+ 排序（相关 / 销量 / 价格）+ 分页——核心是「结果列表」与「各筛选维度的可用值与计数（facets）」同时返回（选了小米后其它品牌的计数要反映剩余结果集）；写查询参数模型。
  2. SQLite/MySQL 实现：多条件动态 WHERE 拼接（防注入参数化）+ facets 用 `GROUP BY brand` 等多次聚合查询（对「应用筛选后（除本维度外）的结果集」）；讨论这种实现的数据量上限（万级）与翻页深分页问题（游标分页，联动 AQ04）。
  3. 搜索引擎实现：ES / Meilisearch 的倒排索引 + 聚合桶天然支持 facets；中文分词（ik / jieba）与拼音召回；销量 / 相关性的混合排序公式 `score = text_relevance * w1 + sales_rank * w2`；写出 DSL 查询并对比方案二的性能差距。
  4. laew 借鉴：facets「应用其它条件后本维度的分布」对照 laew 的 `/provider list` 展示——讨论 TUI 列表若支持筛选（按协议/模型名），正确的 facets 语义如何实现（先查全量分布再渲染，避免选了一个条件后其它选项计数失真）。

### CT09 营销风控：黄牛识别与防刷

- **预期档位**: medium
- **考察维度**: 设备指纹 / 频率控制 / 名单体系
- **对话脚本**:
  1. 风控信号采集：注册 / 登录 / 下单 / 领券各环节埋点采集信号——设备指纹（UA / 屏幕指纹 / canvas hash）、IP（代理池识别：同 IP 多设备）、行为（注册到下单间隔 < 3s 的机器节奏）、关系（同收货地址多账号）；设计一个打分卡模型（每信号一个分值加权求和）。
  2. 频率控制实现：滑动窗口计数（Redis ZSet 存时间戳，`ZREMRANGEBYSCORE` 清理后 `ZCARD` 计数比对阈值）——单个用户领券 ≤ 1 次/活动、下单 ≤ 10 次/分钟、同 IP ≤ 100 次/分钟；写通用 `rate_limit(key, limit, window)` 函数。
  3. 名单与处置：白名单（内部测试账号跳过）/ 灰名单（打分 60-80：静默降级——不发券但返回成功，浪费黄牛脚本时间）/ 黑名单（>80：直接拦截 + 人工复核申诉）；解释「静默降级」为什么优于显式拒绝（不给攻击者反馈信号）。
  4. laew 借鉴：打分卡的多信号加权对照 Yolo 的任务分类（多特征综合判定档位）——讨论「灰名单静默降级」的 Agent 版本：低置信度分类时不抛错给用户，而是静默走保守档（medium + 强 QC），体验更平滑。

### CT10 大促预案：降级、限流与开关

- **预期档位**: hard
- **考察维度**: 降级链设计 / 功能开关 / 预案演练
- **对话脚本**:
  1. 降级链路：大促流量下按优先级丢弃非核心功能——推荐个性化 → 热门榜单兜底、评价图片懒加载关、订单页营销组件隐藏、积分明细查异步化；每条链写成「触发条件（错误率/QPS/手动）→ 动作 → 恢复条件」三段式，画大促总体降级矩阵。
  2. 功能开关系统：开关（key / 灰度百分比 / 用户白名单 / 过期时间）存 DB + 本地缓存 30s 热更新，`if feature.enabled('hide-recommend')` 一行嵌入业务；写开关 SDK 的 `is_on(key, user_id)`（含 hash 百分比分流）并强调「开关必须有 TTL 防止借债不还」。
  3. 读多写少的读降级：核心读接口（商品详情）多级缓存（本地缓存 → Redis → DB），缓存过期时间加随机抖动防雪崩、空值缓存防穿透、热点 key 逻辑过期防击穿；写三级读取函数与三个「防」的实现要点。
  4. laew 借鉴：大促「预案演练」（ chaos 定期演练降级链确保真顶用时能开）对照 laew 的容错测试——讨论给 laew 做「故障注入测试」：mock LLM 超时 / 返回 429 / 返回烂 JSON，验证 Yolo 失败回流与 overflow 三级恢复真的能按预期工作，而不是只在文档里存在。
