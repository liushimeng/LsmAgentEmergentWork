### BJ01 进销存系统：库存事务与出入库单据
- **预期档位**: hard
- **考察维度**: 库存事务模型 + 乐观锁 + 单据一致性
- **对话脚本**:
  1. 进销存系统的核心实体：商品（SKU）、仓库、批次、库存余额、出入库单据（采购/销售/调拨/盘点）。讲清「库存余额」应该放在 SKU 维度还是「SKU + 仓库 + 批次」维度，零售与医药行业的差异。
  2. 基于上面的实体，写一个 SQLite Schema：`products`/`warehouses`/`stock_balances`（SKU + warehouse_id 唯一索引）/`stock_movements`（事务日志）。讲清「余额表 + 流水表」双表设计的工程价值。
  3. 库存并发问题：两个并发出库请求都看到余额 10、都想扣 5。讲清「悲观锁（SELECT ... FOR UPDATE）」、「乐观锁（version 字段 CAS）」、「条件更新（WHERE balance >= qty）」三种方案的实现与边界。
  4. laew 的 SQLite 是单文件本地数据库，没有高并发场景。基于 BJ01 的库存事务模型，如果给 laew 加一个「本地任务执行历史」的库存式记账表（TaskExecution + EventLog），给一份双表 schema 和并发安全保证。

### BJ02 工单系统：状态机、SLA 与升级策略
- **预期档位**: hard
- **考察维度**: 有限状态机 + SLA 计时器 + 升级编排
- **对话脚本**:
  1. 工单系统的核心状态机：`新建 → 已分派 → 处理中 → 待客户确认 → 已关闭/已退回`。讲清「合法转移表」与「非法转移报错」的设计，对比纯 if-else 实现和显式状态机的可维护性差异。
  2. 基于上面的状态机，用 Rust + `statig` crate（或手写 enum + match）实现一个工单状态机引擎：`transition(ticket, event) -> Result<Ticket, InvalidTransition>`，给出 trait 设计。
  3. SLA 与升级策略：响应 SLA（首响 < 30 分钟）、解决 SLA（普通 < 8 小时、紧急 < 2 小时），超时自动升级（升级到上级 / 改派 / 触发电话通知）。讲清定时器实现：内存版（tokio interval 定时扫描）vs 持久化版（数据库 last_polled_at）。
  4. laew 的 TaskExecution 也需要 SLA：用户提了一个 hard 任务，Plan Agent 必须在 60 秒内出方案否则降级到 Main-Work 直跑。基于 BJ02，给 laew 的任务编排器设计一套状态机 + SLA 升级机制。

### BJ03 OA 审批流：流程引擎与会签加签
- **预期档位**: hard
- **考察维度**: BPMN 简化 + 节点路由 + 动态参与人
- **对话脚本**:
  1. OA 审批流的核心概念：流程定义（template）、流程实例（instance）、节点（node）、转移条件（transition）、参与者（assignee）、动作（approve/reject/transfer）。讲清「顺序」「会签」「或签」「加签」四种多人审批语义差异。
  2. 基于这些概念，设计一个最小流程引擎：流程定义存为 JSON（nodes + edges + assignee 表达式），实例运行时维护「当前节点 + 待办列表 + 已办列表」，给出一个 5 行 JSON 示例和核心求值代码。
  3. 「动态参与人」的实现：assignee 不能写死，要支持「申请人所在部门负责人」「金额 > 1 万需要财务总监」。讲清「表达式求值（SpEL/Aviator）」与「外部服务查询（部门接口）」两种路径。
  4. laew 的多 Agent 编排里 Plan → Main-Work → SubAgent-Work 的「委派决策」本质上是一个动态参与人审批流。基于 BJ03，给 laew 设计一个迷你流程引擎：用 laew 自身的 Plan Agent 充当审批节点、SubAgent 充当执行节点，把任务编排变成可视化的审批流定义。

### BJ04 RBAC 权限模型：角色、数据权限与越权防护
- **预期档位**: medium
- **考察维度**: RBAC 模型 + 数据权限 + 越权检测
- **对话脚本**:
  1. RBAC 的三层模型：用户（User）/ 角色（Role）/ 权限（Permission），以及扩展 RBAC（引入资源与操作）。讲清「用户-角色-权限」与「用户-角色-角色继承」两种设计的差异。
  2. 基于三层模型，写一个 SQLite Schema：`users`/`roles`/`permissions`/`role_permissions`/`user_roles` 五张表，权限用 `resource:action` 字符串（如 `order:read`/`order:create`）。
  3. 「数据权限」与「功能权限」的区分：功能权限是「能不能看订单列表」、数据权限是「能看到哪些订单」（自己部门的 / 自己的 / 全部的）。讲清数据权限的 5 种常见实现：行级过滤、视图层过滤、强制 where 条件、PostgreSQL RLS、列级脱敏。
  4. laew 的 provider 表存着用户 API Key，谁能看到哪些 provider 记录？基于 BJ04，给 laew 加一个最小 RBAC：角色 `owner`/`dev`/`readonly`、provider 行的「数据权限」按 owner_id 隔离，防止一个用户用 `laew provider list` 看到别人的 API Key 末四位。

### BJ05 报表引擎：自定义查询、导出与大数据量分页
- **预期档位**: medium
- **考察维度**: 报表引擎 + 游标分页 + 异步导出
- **对话脚本**:
  1. 报表引擎的两大架构：「查询构建器（Query Builder）」让用户拖拽字段/筛选/排序生成 SQL、「数据集 + 模板」预先定义指标 + 维度。先讲清两者在工程复杂度和灵活性上的权衡。
  2. 基于查询构建器，写一个最小实现：前端传 JSON `{fields: [...], filters: [{field, op, value}], group_by: [...]}`，后端安全地拼成参数化 SQL（禁止拼接字符串！），给出关键代码片段。
  3. 大数据量分页三方案：offset/limit 性能差（深翻页慢）、游标分页（`WHERE id < last_id ORDER BY id DESC LIMIT 20` 稳定）、Search After（Elasticsearch 专用）。讲清三者在「跳页」与「实时新增数据」下的语义差异。
  4. laew 的 SessionContext 摘要表 `session_memory` 未来可能存上万条，怎么给 TUI `/export` 加「导出全部会话历史」？基于 BJ05，给一个游标分页（`WHERE id < last_id`）+ 后台异步导出到 Markdown 文件的方案。

### BJ06 多租户 SaaS：隔离级别与计费计量
- **预期档位**: hard
- **考察维度**: 多租户隔离 + 配额计量 + 计费模型
- **对话脚本**:
  1. 多租户 SaaS 的三种隔离模式：共享数据库 + tenant_id 列、共享数据库 + Schema 隔离、独立数据库。讲清三者在「安全隔离」「运维成本」「迁移难度」三角上的取舍。
  2. 基于共享数据库 + tenant_id 模式，写一个 Schema：`tenants`/`users`（含 tenant_id 外键）/ 所有业务表加 tenant_id 列。讲清「强制 tenant_id 过滤」的工程实现：MyBatis 拦截器、Spring AOP、JPA Hibernate Filter。
  3. 计费与配额：按席位（per seat）、按用量（per API call）、按存储（per GB-month）。讲清「用量计量（Metering）」的工程实现：每请求计数（Redis 原子 INCR）/ 周期聚合（每日凌晨 Rollup）/ 实时告警（阈值通知）。
  4. laew 的 SQLite 是单租户本地工具，但如果要演化为 SaaS（laew cloud），基于 BJ06 给一份多租户演进路径：先加 `tenant_id` 列 + 行级过滤、用 Usage 表记每个租户的 token 用量、按用量分级计费。

### BJ07 CRM 客户视图：主数据合并与去重
- **预期档位**: hard
- **考察维度**: 主数据管理 + 实体解析 + 合并策略
- **对话脚本**:
  1. CRM 客户视图的本质问题：一个客户在不同渠道被多次记录（销售 Excel 里、客服系统、市场表单），怎么识别「同一个人」？讲清「实体解析（Entity Resolution）」的三个层次：精确匹配、规则匹配、概率匹配（Fellegi-Sunter）。
  2. 基于规则匹配，写一个最小去重系统：字段匹配规则（手机号相同 / 邮箱相同 / 姓名 + 公司模糊匹配）、权重评分（手机号 50 分 + 邮箱 30 分 + 姓名 + 公司 20 分 = 100 分）、阈值 85 触发合并候选。
  3. 合并策略：「硬合并（Hard Merge）」与「软合并（Soft Merge / Survivor）」的差异：硬合并直接合并字段、软合并保留所有原始记录 + 一个 Master 记录，查询时聚合。讲清两者的回滚难度差异。
  4. laew 的 `agent_memory` 表里同一用户可能多次创建 Session，怎么识别「同一个开发者」？基于 BJ07，给 laew 设计一个轻量级客户去重：基于 device_id + 工作目录 + 默认 model 三个字段做软合并，提示用户「检测到您是上次会话的同一人，是否合并历史？」。

### BJ08 考勤与排班：日历、时区与工时规则
- **预期档位**: medium
- **考察维度**: 工时计算 + 时区处理 + 排班冲突
- **对话脚本**:
  1. 考勤系统的核心数据：打卡记录（in/out 时间戳）、班次定义（上午 9-12 / 下午 13-18）、请假记录、加班记录、调休记录。讲清「弹性工时」与「标准工时」在迟到判定逻辑上的差异。
  2. 时区陷阱：用 UTC 存时间戳是标配，但展示层必须按用户时区（IANA tz 数据库如 `Asia/Shanghai`）。讲清夏令时（DST）切换日的「缺失 60 分钟」和「重复 60 分钟」怎么处理。
  3. 排班冲突检测：同一人被排两个班、班次连续无休息时间、人均工时超 40 小时/周。讲清「约束满足问题（Constraint Satisfaction）」的工程实现：约束定义 + 求解器（OR-Tools / OptaPlanner）。
  4. laew 的 Session 上下文压缩触发（80% 阈值）和定时清理机制，本质上是一个「会话生命周期管理」。基于 BJ08 的工时规则，给 laew 设计一个「Session 使用量仪表盘」：按日聚合 token 用量、按周展示活跃天数、超阈值预警，类似工时系统的 dashboard。

### BJ09 低代码表单引擎：Schema 驱动渲染与校验
- **预期档位**: medium
- **考察维度**: Schema 驱动 + 动态渲染 + 联动规则
- **对话脚本**:
  1. 低代码表单引擎的核心：表单 Schema（字段定义 JSON）→ 运行时渲染（按字段类型生成对应控件）→ 数据收集 → 提交。讲清「JSON Schema」与「自研 DSL」两种 Schema 选型。
  2. 基于 JSON Schema，给一个 10 字段表单定义：文本/数字/日期/下拉/文件上传/子表单/数组/校验规则（required / min/max / regex），给出关键 JSON 片段和 React/Antd 渲染代码。
  3. 联动规则：「选择 A 选项时显示字段 B」「金额 > 1000 时禁用提交」。讲清「依赖收集 + 监听」的实现：MobX/Recoil 的 reactive 方案 vs 手写 Observer 模式。
  4. laew 的 `/provider add` TUI 表单（5+1 Tab：protocol/provider_name/model_name/end_point/api_key/确认）是典型 Schema 驱动表单。基于 BJ09，给 laew 重构表单引擎：把当前硬编码的 Tab 抽成 JSON Schema，由引擎渲染，支持未来新增字段零代码扩展。

### BJ10 对账与结算：账务模型与差异处理
- **预期档位**: hard
- **考察维度**: 双向核对 + 差异分类 + 差错处理
- **对话脚本**:
  1. 对账系统的本质：以一边为基准核对另一边（银行流水 vs 业务订单、支付渠道 vs 业务订单、供应商发货 vs 我们入库）。讲清「长款 / 短款 / 金额差异 / 时间差异」四类差异的业务含义。
  2. 基于上面的差异类型，写一个对账脚本：左侧是支付渠道 CSV（交易号 + 金额 + 时间）、右侧是业务系统 SQL 导出（订单号 + 金额 + 时间），按交易号 join 后分类四桶：双向匹配、单边有、金额差、时间差。
  3. 差错处理流程：对账差错不能直接改账，要走「差错单 → 调查 → 调账审批 → 落账」。讲清「差错单」状态机（待处理/调查中/已确认/已调账/已豁免）和审计追溯要求（每笔差错必须能查回原始证据）。
  4. laew 的 provider API key 调用计费（每个 provider 一条记录）和用户实际余额对账：基于 BJ10，给 laew 设计一个「调用对账」表：左表是 Provider 返回的真实 token 用量、右表是 laew 估算的 token 用量，定期跑对账，差异超过 10% 触发告警。
