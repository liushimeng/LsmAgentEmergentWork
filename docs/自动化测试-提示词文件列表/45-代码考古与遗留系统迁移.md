# 自动化测试提示词 — 代码考古与遗留系统迁移（AT01–AT10）

> 使用说明见同目录 `README.md`。每条提示词在同一 Session 内按轮次顺序喂入。

## 维度说明

本维度考察 Agent 在 **遗留代码工程化** 上的动手能力：能现场 git init 造一个"坏味道遗留仓库"、能跑死代码检测、能演练绞杀者迁移、能在重构后保持测试通过。
所有产物落到 `tmpPlan/agent-test/` 沙盒，不依赖企业级工具/外网。
与 README 其它维度互补：E 维度考察通用编码，AT 聚焦"考古 + 迁移"——坏味道识别、绞杀者切流、调用图分析、重命名测试。

---

### AT01 遗留代码心智模型：从代码反推架构
- **预期档位**: medium
- **考察维度**: 遗留代码理解 + 文档反推
- **工具链**: Write → Bash → Bash → Read
- **对话脚本**:
  1. 在 `tmpPlan/agent-test/at01/` 写 `gen_legacy.py`：脚本批量生成一个"遗留 Java 风格" Python 包 `legacy_app/`，含 8 个模块（user/order/payment/inventory/notification/report/audit/util），互相 import 形成依赖网。
  2. 跑 `python3 gen_legacy.py` 后用 `grep -rE '^(from|import)' legacy_app/ | wc -l` 数依赖行数，断言 ≥ 30；用 `python3 -c "import os; print(sum(len(f) for _,_,f in os.walk('legacy_app') for _ in f))"` 数总行数 ≥ 200。
  3. 写 `reverse_arch.py`：扫描所有 import，构图 `graph.dot`，输出节点 + 边到 `arch.txt`；用 `grep -c '^module:' arch.txt` 断言模块数=8。
  4. 在 `arch_notes.md` 写反推架构三视角：包结构反推模块边界 / 测试反推契约 / commit message 反推演进；每视角 1 段。

### AT03 绞杀者模式：双写切流
- **预期档位**: hard
- **考察维度**: Strangler Fig + 流量切换
- **工具链**: Write → Bash → Bash → Read
- **对话脚本**:
  1. 在 `tmpPlan/agent-test/at03/` 写 `legacy_search.py`（含 bug 的搜索：忽略 "TOkyo" 大小写不一致）与 `new_search.py`（修复版）；用 Write 双写 `search_dispatcher.py` 按 `?engine=legacy|new` 分流。
  2. 跑 `bash` 循环：依次用 `engine=legacy` 与 `engine=new` 查询 5 个关键词（"tokyo"、"TOKYO"、"paris"、"PARIS"、"missing"），断言 legacy 把 "TOKYO" 误判为 0 结果而 new 找到（grep 结果数差异）。
  3. 写 `cutover.py` 实现权重切流：读取 `weights.json` 的 `{"legacy":0.3, "new":0.7}` 用 `random.random()` 决定走哪条，跑 1000 次并统计实际分布到 `cutover_log.txt`（legacy≈300, new≈700 允许 ±50 误差）。
  4. 在 `strangler_notes.md` 写 4 阶段：双写 → 数据校验 → 切流 → 清理，每阶段关键指标（如双写期"双写一致率 ≥ 99.9%"），每行 1 阶段。

### AT04 数据库迁移：双写校验零停机
- **预期档位**: hard
- **考察维度**: 数据迁移 + 零停机
- **工具链**: Write → Bash → Bash → Read
- **对话脚本**:
  1. 在 `tmpPlan/agent-test/at04/` 写 `seed.py` 用 python 内置 sqlite3 创 `old.db` 含 1000 行 users(id, name, email)；写 `new.db` 同 schema。
  2. 写 `dual_write.py`：每次"业务写"同时插 old + new；写 `reconcile.py` 跑 `SELECT id, name, email FROM old.db.users EXCEPT SELECT id, name, email FROM new.db.users` 把差异写到 `diff.json`，断言空（"差 0 条"）。
  3. 写 `cutover_db.py` 把读流量从 old 切到 new（改 `app_config.json` 的 `db_path`），跑 100 次读断言 100% 来自 new（用 sqlite_sequence 或 rowid 范围）。
  4. 在 `migration_notes.md` 写 4 阶段关键指标：双写期一致率 / 校验期差异条数 / 切流期错误率 / 清理期回收磁盘字节数；表 4 行 3 列。

### AT05 框架升级：API 兼容与 shim
- **预期档位**: hard
- **考察维度**: 长期版本演进
- **工具链**: Write → Bash → Read → Bash
- **对话脚本**:
  1. 在 `tmpPlan/agent-test/at05/` 写 `v1_user.py`：`get_user(id) -> dict`，含 `legacy_field_1` 等 4 个字段；写 `v2_user.py` `get_user(id) -> dict`，含 2 个新字段 + 1 个字段重命名。
  2. 写 `shim.py` 实现 v1→v2 兼容：v1 调用时返回 v2 结果并把重命名字段映射回旧名（"new_name"→"legacy_field_3"）。
  3. 写 `test_shim.py` 跑 5 个用例：v1 调用拿到 legacy_field_3（值为 v2 的 new_name）、v2 调用拿到 new_name、字段数符合预期。
  4. 故意在 v2 里删 legacy_field_3，断言 shim 测试失败 → 看到失败信息后改回字段（演示"逐步迁移"），重跑全过。在 `upgrade_notes.md` 写"Codemod + shim" 4 步：写 shim → 跑双套测试 → 删 v1 调用点 → 删 shim。

### AT06 单体拆分：按包边界拆
- **预期档位**: hard
- **考察维度**: 微服务拆分决策
- **工具链**: Write → Bash → Bash → Read
- **对话脚本**:
  1. 在 `tmpPlan/agent-test/at06/` 写 `monolith.py` 单体含 4 域（user/order/inventory/notify），全部 import 在一起；用 `wc -l monolith.py` 断言 ≥ 100 行。
  2. 写 `splitter.py` 把 monolith.py 按 `^class (\w+):` 切到 `services/{name}.py`（用 ast 或 splitlines 简单实现），跑后 `ls services/` 断言 ≥ 4 个文件。
  3. 写 `consumer.py` 跨域调用 user + order 模拟跨服务 join，断言跑通；统计跨域 import 数 `grep -c 'from services' consumer.py` ≥ 2。
  4. 在 `split_decision.md` 写"何时不该拆"三判断：团队 < 5 人 / 业务单一 / 部署耦合度高；每条 1 行 + 反例场景。

### AT07 死代码消除：调用图统计
- **预期档位**: medium
- **考察维度**: 代码精简 + 依赖治理
- **工具链**: Write → Bash → Read → Bash
- **对话脚本**:
  1. 在 `tmpPlan/agent-test/at07/` 写 `module.py` 含 12 个函数（`f1..f12`），主入口只调用 `f1→f2→f3→f4→f5`，`f6..f12` 是死代码。
  2. 写 `callgraph.py` 用 ast 解析所有 `def` 与 `Call`，从 `if __name__ == "__main__"` 反向 BFS 可达集，输出 `reachable.json` 列出可达函数名集合 + 死函数列表。
  3. 跑脚本断言死函数数 ≥ 6（`f6..f12`），用 `python3 -c "import json; print(len(json.load(open('reachable.json'))['dead']))"` ≥ 6。
  4. 写 `cleanup.py` 删 dead 集合中所有 `def`，重写 module.py，用 `wc -l module.py` 断言行数下降 ≥ 30%，跑 `python3 module.py` 断言仍能跑通。

### AT09 性能与可维护性债：量化打分
- **预期档位**: medium
- **考察维度**: 技术债评估方法
- **工具链**: Write → Bash → Read → Bash
- **对话脚本**:
