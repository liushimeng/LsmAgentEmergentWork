### CI01 软件估算：为什么软件项目总是延期

- **预期档位**: medium
- **考察维度**: 估算挑战 + 延期原因 + 改进方法
- **对话脚本**:
  1. 软件项目延期是行业常态（Standish Group CHAOS 报告：约 70% 项目延期或超预算）。延期原因：(a) 乐观偏差（Optimism Bias，低估难度）；(b) 范围蔓延（Scope Creep，需求不断增加）；(c) 未知未知（Unknown Unknowns，未预见的问题）；(d) 学生综合征（Student Syndrome，拖到最后才开始）；(e) 帕金森定律（Parkinson's Law，工作膨胀填满时间）。请解释为什么「乐观偏差」是软件估算最大的敌人（人类天生低估复杂任务）。
  2. 估算心理学：(a) 锚定效应（Anchoring，第一个数字影响后续估算）；(b) 从众效应（Bandwagon，跟随他人估算）；(c) 规划谬误（Planning Fallacy，低估自己任务时间）；(d) 霍夫斯塔特定律（Hofstadter's Law，「实际时间总是比预期长，即使你考虑了霍夫斯塔特定律」）。请描述如何避免这些认知偏差（参考类 forecasting + 独立估算）。
  3. 估算改进方法：(a) 参考类估算（Reference Class Forecasting，用历史数据校准）；(b) 分解估算（把大任务拆成小任务分别估算）；(c) 独立估算（多人独立估算后对比）；(d) 持续校准（用实际时间修正未来估算）。请讨论为什么「参考类估算」比「直觉估算」更准确（用数据替代直觉）。
  4. laew 的估算能力：laew 如何帮助用户估算：(a) 基于历史数据估算（类似任务过去耗时）；(b) 分解估算（自动拆解任务并估算每步）；(c) 风险提示（识别高风险环节）；(d) 进度跟踪（实时对比估算 vs 实际）。讨论 laew 作为「估算助手」的价值。

### CI02 三点估算与 PERT：量化不确定性

- **预期档位**: medium
- **考察维度**: PERT + 概率估算 + 风险管理
- **对话脚本**:
  1. 三点估算（Three-point Estimation）是「用三个值描述任务时间」的估算方法：(a) 乐观时间（Optimistic，O，一切顺利）；(b) 最可能时间（Most Likely，M，正常情况）；(c) 悲观时间（Pessimistic，P，一切不顺利）。期望时间 E = (O + 4M + P) / 6，标准差 σ = (P - O) / 6。请解释为什么「最可能时间权重是 4」（基于 Beta 分布假设）。
  2. PERT（Program Evaluation and Review Technique）：(a) 任务网络图（Activity Network）；(b) 关键路径（Critical Path，最长路径决定项目最短时间）；(c) 浮动时间（Float / Slack，非关键任务可延迟的时间）；(d) 概率分析（项目在 X 天内完成的概率）。请描述如何计算关键路径（正向计算最早开始 + 反向计算最晚开始）。
  3. 三点估算实战：(a) 任务 A（O=2, M=4, P=8）→ E=4.33, σ=1；(b) 任务 B（O=3, M=5, P=10）→ E=5.5, σ=1.17；(c) 任务 A + 任务 B → E=9.83, σ=1.54；(d) 项目在 12 天内完成的概率（Z=(12-9.83)/1.54=1.41 → 约 92%）。请计算一个三点估算案例并解释结果。
  4. laew 的 PERT 支持：laew 如何支持三点估算：(a) 用户输入三点时间；(b) 自动计算期望时间和标准差；(c) 生成关键路径图；(d) 计算项目完成概率。讨论 PERT 对 laew 项目规划能力的价值。

### CI03 敏捷估算：故事点与规划扑克

- **预期档位**: medium
- **考察维度**: 敏捷估算 + 故事点 + 团队协作
- **对话脚本**:
  1. 敏捷估算（Agile Estimation）是「用相对大小而非绝对时间估算」的方法。核心概念：(a) 故事点（Story Point，相对复杂度单位）；(b) 速度（Velocity，每迭代完成的故事点）；(c) 规划扑克（Planning Poker，团队共识估算）；(d) 斐波那契数列（1/2/3/5/8/13/21，反映不确定性）。请解释为什么「故事点」比「人天」更准确（故事点包含复杂度 + 不确定性 + 工作量）。
  2. 规划扑克（Planning Poker）流程：(a) 产品负责人描述用户故事；(b) 团队讨论并提问；(c) 每人独立选择估算牌（斐波那契数）；(d) 同时亮牌；(e) 最高和最低讨论原因；(f) 重新估算直到共识。请描述为什么「同时亮牌」能避免锚定效应（独立判断后再讨论）。
  3. 速度（Velocity）与预测：(a) 速度 = 每迭代完成的故事点；(b) 用历史速度预测未来（如平均速度 30 点 / 迭代）；(c) 速度波动（新团队速度不稳定）；(d) 用速度计算交付时间（总故事点 / 速度 = 迭代数）。请讨论为什么「速度」是团队专属的（不同团队速度不可比）。
  4. laew 的敏捷估算支持：laew 如何支持敏捷团队：(a) 故事点估算助手（基于历史数据建议）；(b) 规划扑克工具（在线协作估算）；(c) 速度跟踪（自动统计每迭代完成量）；(d) 燃尽图生成（可视化进度）。讨论 laew 作为「敏捷助手」的价值。

### CI04 项目计划：从目标到可执行计划

- **预期档位**: medium
- **考察维度**: 计划方法 + WBS + 甘特图
- **对话脚本**:
  1. 项目计划（Project Planning）是「把目标分解为可执行任务」的过程。计划要素：(a) 范围（Scope，做什么 / 不做什么）；(b) 时间（Timeline，何时完成）；(c) 资源（Resources，谁来做 / 需要什么）；(d) 风险（Risks，可能出什么问题）；(e) 质量（Quality，做到什么程度）。请解释为什么「范围」是计划的基础（范围不清 → 计划无效）。
  2. WBS（Work Breakdown Structure）：(a) 把项目分解为可管理的工作包；(b) 分解原则（100% 规则：子工作总和 = 父工作）；(c) 分解维度（按功能 / 按阶段 / 按组件）；(d) 工作包大小（8/80 规则：8-80 小时）。请为一个「电商网站」项目创建 WBS：至少 3 层，每层 3-5 个工作包。
  3. 甘特图（Gantt Chart）：(a) 横轴时间 + 纵轴任务；(b) 任务条（开始 / 持续时间）；(c) 依赖关系（FS / SS / FF / SF）；(d) 里程碑（菱形标记关键节点）。请用甘特图描述一个 3 个月项目的关键里程碑：需求 → 设计 → 开发 → 测试 → 上线。
  4. laew 的项目计划支持：laew 如何帮助用户制定计划：(a) 自动生成 WBS（基于项目描述）；(b) 甘特图可视化；(c) 依赖关系管理；(d) 里程碑跟踪。讨论 laew 作为「计划助手」的价值。

### CI05 风险管理：识别、评估、应对

- **预期档位**: medium
- **考察维度**: 风险管理 + 应对策略 + 监控
- **对话脚本**:
  1. 风险管理（Risk Management）是「识别、评估、应对项目风险」的过程。流程：(a) 识别（Identification，列出可能风险）；(b) 评估（Assessment，概率 × 影响 = 风险值）；(c) 应对（Response，规避 / 转移 / 缓解 / 接受）；(d) 监控（Monitoring，持续跟踪）。请解释为什么「风险评估」用概率 × 影响（高概率 + 高影响 = 最高优先级）。
  2. 风险应对策略：(a) 规避（Avoid，消除风险来源）；(b) 转移（Transfer，把风险转给第三方，如保险）；(c) 缓解（Mitigate，降低概率或影响）；(d) 接受（Accept，承认风险并准备应急计划）。请为「核心开发人员离职」设计应对策略（缓解：知识共享 + 文档化；转移：外包部分工作）。
  3. 风险登记册（Risk Register）：(a) 风险 ID + 描述；(b) 概率 / 影响 / 风险值；(c) 应对策略 + 责任人；(d) 状态（活跃 / 已关闭）。请为一个项目创建风险登记册：至少 5 个风险，包含完整信息。
  4. laew 的风险管理支持：laew 如何帮助风险管理：(a) 风险识别（基于历史项目数据）；(b) 风险评估（自动打分）；(c) 风险监控（实时告警）；(d) 应急计划生成（风险发生时的应对方案）。讨论 laew 作为「风险助手」的价值。

### CI06 进度跟踪：从计划到执行

- **预期档位**: medium
- **考察维度**: 进度跟踪 + 燃尽图 + 纠偏
- **对话脚本**:
  1. 进度跟踪（Progress Tracking）是「监控项目实际进展 vs 计划」的过程。方法：(a) 每日站会（Daily Standup，昨天 / 今天 / 阻塞）；(b) 燃尽图（Burndown Chart，剩余工作量趋势）；(c) 燃起图（Burnup Chart，已完成工作量趋势）；(d) 看板（Kanban，任务状态可视化）。请解释为什么「燃尽图」能直观反映项目健康度（曲线在计划线上方 = 落后）。
  2. 燃尽图解读：(a) 理想燃尽线（直线从左上到右下）；(b) 实际燃尽线（波动）；(c) 曲线在计划线上方（进度落后）；(d) 曲线在计划线下方（进度超前）；(e) 曲线平坦（任务无进展）。请描述一个「进度落后」的燃尽图场景并分析原因。
  3. 纠偏措施：(a) 赶工（Crashing，增加资源缩短关键路径）；(b) 快速跟进（Fast-tracking，并行执行原串行任务）；(c) 缩减范围（Descoping，砍掉低优先级功能）；(d) 延期（Slippage，接受延期）。请讨论「赶工」vs「快速跟进」的风险（赶工增加成本 / 快速跟进增加风险）。
  4. laew 的进度跟踪支持：laew 如何帮助进度跟踪：(a) 自动燃尽图生成；(b) 进度异常告警（落后计划 X%）；(c) 纠偏建议（基于历史数据）；(d) 进度报告自动生成。讨论 laew 作为「进度助手」的价值。

### CI07 范围管理：控制项目的边界

- **预期档位**: medium
- **考察维度**: 范围定义 + 范围蔓延 + 变更控制
- **对话脚本**:
  1. 范围管理（Scope Management）是「定义和控制项目包含什么 / 不包含什么」的过程。核心概念：(a) 范围基准（Scope Baseline，批准的范围说明书 + WBS）；(b) 范围蔓延（Scope Creep，需求不断增加）；(c) 镀金（Gold Plating，添加用户不需要的功能）；(d) 变更控制（Change Control，正式评审范围变更）。请解释为什么「范围蔓延」是项目失败的主要原因之一（需求不断增加 → 资源耗尽）。
  2. 范围定义工具：(a) 项目范围说明书（Project Scope Statement）；(b) WBS 字典（WBS Dictionary，每个工作包的详细说明）；(c) 需求跟踪矩阵（Requirement Traceability Matrix）；(d) 验收标准（Acceptance Criteria）。请描述「需求跟踪矩阵」如何确保所有需求都被实现（需求 → 设计 → 实现 → 测试）。
  3. 变更控制流程：(a) 变更请求（Change Request）；(b) 影响分析（对时间 / 成本 / 质量的影响）；(c) 变更控制委员会（CCB，评审变更）；(d) 批准 / 拒绝；(e) 更新基准。请讨论为什么「变更控制」对项目成功至关重要（防止无序变更）。
  4. laew 的范围管理支持：laew 如何帮助范围管理：(a) 范围说明书生成（基于项目描述）；(b) 变更影响分析（自动评估变更对计划的影响）；(c) 范围跟踪（监控需求实现状态）；(d) 范围蔓延预警（需求增加时提醒）。讨论 laew 作为「范围助手」的价值。
