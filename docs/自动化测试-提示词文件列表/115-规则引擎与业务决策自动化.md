### DG01 为什么需要规则引擎：从 if-else 地狱说起

- **预期档位**: simple~medium
- **考察维度**: 规则引擎价值 / 选型 / 反模式
- **对话脚本**:
  1. 一个电商折扣逻辑：会员等级 × 品类 × 满减 × 节日活动，代码里 200 行嵌套 if-else，运营改一次规则要发版——讲清「规则频繁变、业务人员看得懂、执行可追溯」三个诉求如何导向规则引擎。
  2. 规则引擎的三种形态：表达式求值（简单——每条规则一个布尔表达式+动作）/ 决策表（二维表格——行是规则列是条件）/ Rete 网络（大规模规则高效匹配，Drools 内核）；选型看规则数量与复杂度。
  3. 反模式：规则引擎不是银弹——规则间隐式依赖导致「改 A 坏 B」、业务人员写的规则出 bug 比代码更难调试、规则 DSL 最终变成图灵完备的怪物；讨论「多少规则才值得上引擎」的阈值。
  4. 动手：把开头的折扣逻辑分别用 if-else 与「规则表 + 简单求值器」（每条规则 JSON：条件字段+动作）实现一遍，对比加一条新规则的成本。

### DG02 Rete 算法：大规模规则匹配的核心

- **预期档位**: medium~hard
- **考察维度**: Rete 网络 / 模式匹配 / 空间换时间
- **对话脚本**:
  1. 朴素匹配的问题：1 万条规则 × 每条 5 个条件，来一个事实全部重算一遍是 O(规则数×条件数)；Rete 的思想——把规则编译成条件节点网络，事实沿网络流动，共享公共条件只算一次。
  2. Rete 网络结构：alpha 网络（单条件过滤：年龄>18）+ beta 网络（多事实连接：同一个人的年龄和订单）；用 3 条规则手画 Rete 网络，标出共享的 alpha 节点。
  3. 基于上面的网络，讨论增量维护：事实更新/删除时只需沿网络传播变化（token 传递），而不是全量重算——这就是「空间换时间」；内存里的 beta 节点存中间匹配结果。
  4. 动手：用 Python 实现简化 alpha 网络——规则条件编译成节点链，10 条规则共享 3 个公共条件，用事实流验证公共条件只求值一次（计数器证明）。

### DG03 决策表与 DMN：业务人员的编程语言

- **预期档位**: medium
- **考察维度**: 决策表模型 / DMN 标准 / 命中策略
- **对话脚本**:
  1. 决策表是最亲民的规则形式：列 = 输入条件（年龄/职业/保额）+ 输出结论（费率/是否承保），行 = 一条规则；业务人员在 Excel 里就能写；设计一张 10 行的保险费率决策表。
  2. DMN（Decision Model and Notation）标准：决策表 + FEEL 表达式语言 + DRD 决策依赖图；七种命中策略（FIRST 首个命中 / UNIQUE 唯一命中 / COLLECT 收集全部 / PRIORITY 优先级）各适合什么场景。
  3. 基于上面的表，讨论完备性与一致性检查：条件组合有没有漏（16 种组合只写了 10 行）？有没有两行条件重叠但结论冲突？这两项检查是决策表工具的杀手级功能。
  4. 动手：用 Python 实现决策表引擎——读 CSV 决策表，输入 JSON 事实，按 FIRST 策略输出结论；再加一个完备性检查函数（找出条件空间未覆盖的组合）。

### DG04 规则 DSL 设计：让业务能写、让系统能跑

- **预期档位**: medium~hard
- **考察维度**: DSL 语法设计 / 解析 / 安全执行
- **对话脚本**:
  1. 规则 DSL 的设计约束：业务人员要看得懂（接近自然语言 `当 订单金额 > 100 且 用户是会员 则 打9折`）、系统要能解析执行、不能注入恶意代码；对比 Drools DRL / 自研中文规则语法 / JSON 结构化规则三种形态。
  2. 基于上面的对比，设计一个最小中文规则语法：`当 <条件组> 则 <动作>`，条件支持比较/包含/区间，动作支持设置字段/打标；写出 EBNF 文法。
  3. 解析与执行：用简单递归下降把 DSL 解析成 AST，再编译成谓词函数；沙箱执行——表达式里禁止函数调用白名单外的一切（防 `__import__` 类注入）；讨论错误提示要业务友好（「第2行：『大约』不是合法运算符」）。
  4. 动手：实现这个迷你规则 DSL 的解析器+求值器，支持 5 条规则顺序执行，测试一条语法错误规则的错误信息质量。

### DG05 实战：保险核保规则引擎

- **预期档位**: medium
- **考察维度**: 核保业务 / 规则分层 / 人工兜底
- **对话脚本**:
  1. 核保（underwriting）业务：健康险投保时根据年龄/BMI/既往病史/职业类别自动决定 标准承保/加费/除外责任/拒保/转人工；规则特点是强合规（每条款要能向监管解释）。
  2. 规则分层设计：第一层硬拒保（年龄>65 直接拒）→ 第二层评分（BMI 超区间 +N 分）→ 第三层综合（总分映射承保结论）→ 转人工兜底；为什么分层比扁平规则表好维护。
  3. 基于上面的分层，讨论可解释性：每个结论必须带出「命中了哪些规则」的证据链（`因 BMI 28.5 > 28 触发规则 R-203 加费 20%`）——这既是用户体验也是合规要求。
  4. 动手：用 DG03 的决策表引擎实现三层核保流程，输入 5 个测试案例（标准体/超重/高血压史/高危职业/临界转人工），输出结论+证据链。

### DG06 实战：实时风控决策引擎

- **预期档位**: medium~hard
- **考察维度**: 风控规则 / 实时特征 / 决策延迟
- **对话脚本**:
  1. 支付风控场景：一笔交易进来 200ms 内要决定 放行/拦截/人工审核；规则示例（同一卡 1 分钟 3 笔大额、异地+深夜+新设备组合）；特征分实时特征（需要流计算：近 1 分钟交易数）与静态特征（卡bin、商户类别）。
  2. 架构分层：特征平台（Flink 算实时特征存 Redis）→ 决策引擎（规则+模型评分卡）→ 处置通道（拦截/二次验证/放行）；为什么规则和模型要组合（规则管确定性黑产模式、模型管未知模式）。
  3. 基于上面的架构，讨论规则的对抗性演化：黑产会试探规则边界（小额试卡），规则要有「观察期」与自动化对抗指标（拦截率突降=规则被绕过）；规则热更新必须秒级生效。
  4. 动手：实现简化风控引擎——滑窗特征（内存里维护近 60 秒交易计数）+ 5 条规则（含组合条件）+ 三种处置输出；模拟正常用户与盗刷脚本各 20 笔验证拦截率。

### DG07 实战：积分与会员等级规则引擎

- **预期档位**: medium
- **考察维度**: 积分规则 / 状态机联动 / 幂等与对账
- **对话脚本**:
  1. 积分体系规则：消费得积分（品类系数不同）、签到得积分（连续签到加成）、积分过期（1 年滚动失效）、等级晋升（累计积分阈值）；这些规则的特点是多触发源（订单事件/签到事件/定时任务）。
  2. 规则与状态机联动：等级不是简单阈值——要处理升级（即时生效）、保级（年度评估）、降级（宽限期）；画出等级状态机，讨论「积分变动 → 规则重算 → 状态迁移」的事件流。
  3. 基于上面的设计，讨论幂等与对账：订单重复事件不能双倍积分（事件 ID 幂等）、每日对账任务重算积分余额与流水轧差；规则变更后存量用户怎么办（等级重算迁移方案）。
  4. 动手：实现积分引擎——事件驱动（order/checkin 事件）+ 规则表 + 幂等表 + 余额与流水双写；模拟 30 天事件流验证余额与流水始终对得上。

### DG08 规则冲突检测与优先级体系

- **预期档位**: medium~hard
- **考察维度**: 冲突类型 / 消解策略 / 静态分析
- **对话脚本**:
  1. 规则冲突三种类型：互斥冲突（同事实触发「打8折」和「打9折」）/ 冗余（A 规则是 B 规则的特例，B 永不命中）/ 循环（规则 A 的动作触发规则 B 的条件，B 又触发 A）；各给一个业务例子。
  2. 消解策略：显式优先级（规则带 priority 字段）/ 特异性优先（条件多的规则优先——Drools 的 specifity）/ 时间优先（新规则覆盖旧规则）；讨论「冲突时告警」vs「静默按策略执行」的产品取舍。
  3. 基于上面的分类，讨论静态检测：规则入库前自动分析——把条件转区间集合，区间相交且动作不同 → 报互斥冲突；一个条件的区间完全包含另一个 → 报冗余；这就是区间图分析问题。
  4. 动手：给 DG04 的 DSL 引擎加冲突检测器——条件统一转数值区间，检测两两规则的重叠关系，输出冲突报告（规则对+冲突类型+建议处理）。

### DG09 规则版本管理与灰度发布

- **预期档位**: medium
- **考察维度**: 规则治理 / 版本快照 / 灰度策略
- **对话脚本**:
  1. 规则即代码的治理：规则变更要有版本（每次发布一个快照，可回滚）、有审批（业务提交→风控复核→生效）、有审计（谁在什么时间改了哪条）；规则库存储模型（规则表 + 版本表 + 发布表）。
  2. 灰度发布策略：新规则先对 1% 流量生效（按用户 ID 哈希分流）→ 观察指标 → 全量；AB 对比（新旧规则并行执行但只用旧规则决策，对比差异）是更安全的影子模式。
  3. 基于上面的策略，讨论回滚与应急：误拦截正常用户时的「一键回滚到上一版本」；规则下线比上线更谨慎（可能有流程依赖该规则的输出）；决策日志留存（每笔决策记录用的哪个规则版本，用于事后争议仲裁）。
  4. 动手：给规则引擎加版本层——规则集按 version 存储，决策接口带 version 参数（默认 latest），实现「影子模式」：新旧版本同时执行、记录差异、只用旧版结果。

### DG10 手写迷你 Rete：事实 + 条件网络

- **预期档位**: hard
- **考察维度**: 编译到网络 / token 传播 / 端到端整合
- **对话脚本**:
  1. 项目目标：综合 DG01–DG09，用 Python 实现 300 行的迷你规则引擎——支持多条件规则、条件共享（Rete 思想）、事实增删改后的增量重算、冲突告警、决策证据链。先定规则与事实的数据模型。
  2. 实现 alpha 网络：把所有规则的原子条件编译成去重的条件节点（相同条件只建一个节点），事实进入时逐节点求值，通过的存到节点输出集；用计数器证明共享条件只求值一次。
  3. 实现简化 beta 层：同一规则的多条件输出做连接（join）生成完整匹配；事实更新时沿网络传播删除/新增 token；讨论与真 Rete 的差距（没有做 beta 记忆化）。
  4. 端到端验收：装载 DG05 核保的 10 条规则，跑 100 个随机投保人事实，输出每人结论+证据链；动态改一条规则，验证只有受影响的事实重算；统计共享条件带来的求值次数节省比例。
