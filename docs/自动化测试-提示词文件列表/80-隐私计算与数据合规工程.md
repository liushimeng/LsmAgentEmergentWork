### CA21 数据脱敏工程化：分级 / 假名化 / 匿名化 / 静态动态

- **预期档位**: medium
- **考察维度**: 脱敏分级 + 工程实现 + 不可逆性评估
- **对话脚本**:
  1. 数据敏感度可分为 4 级：L0 公开（产品说明书）、L1 内部（员工手册）、L2 机密（用户手机号）、L3 高敏（身份证号 / 银行卡 / 健康记录）。请画出 L0-L3 的脱敏策略矩阵：哪些字段必须脱敏、用什么算法、脱敏后是否可逆、L3 是否必须加密存储。
  2. 静态脱敏（Static Masking，在数据落库前脱敏）vs 动态脱敏（Dynamic Masking，查询时实时脱敏）：前者用于开发测试环境（一次性脱敏）、后者用于生产环境（运维查询不暴露明文）。请设计一个 laew 风格的脱敏中间件：所有 `provider` 表查询自动把 `api_key` 列脱敏为 `****<末4位>`，即使直接 SQL 查询也看不到明文。
  3. 假名化（Pseudonymization，用假 ID 替换真实 ID）vs 匿名化（Anonymization，去除所有可识别信息）：前者可还原（保留关联分析能力）、后者不可还原（彻底切断关联）。请解释为什么 GDPR 把假名化视为「仍属于个人数据」（合规要求更高），而匿名化则不属于（合规约束较少）。
  4. K-匿名（K-Anonymity）与 L-多样性（L-Diversity）：K-匿名保证每条记录的准标识符组合至少有 K 条相同；L-多样性在 K-匿名基础上保证敏感属性至少有 L 个不同值。请设计一个用户表脱敏方案，让「年龄=30, 性别=男, 邮编=100086」的组合至少有 5 条记录（K=5），并讨论 K-匿名如何被「组合攻击」破解（背景知识攻击 / 同质性攻击）。

### CA22 差分隐私：ε 预算 / 噪声机制 / 拉普拉斯与高斯

- **预期档位**: hard
- **考察维度**: 数学原理 + 隐私预算分配 + 工程实现
- **对话脚本**:
  1. 差分隐私（Differential Privacy, DP）由 Dwork 在 2006 年提出，核心思想是「加噪声让单条记录的加入或删除不影响查询结果分布」。请用公式 $Pr[M(D) \in S] \le e^\varepsilon \cdot Pr[M(D') \in S]$ 解释 ε-差分隐私的定义，并说明 ε 越小隐私越强（ε=0 为完美隐私，ε=∞ 无隐私）。
  2. 两种核心噪声机制：拉普拉斯机制（添加 Laplace(0, Δf/ε) 噪声到数值查询）适用于数值型输出（如「平均年龄」）；高斯机制（添加 N(0, σ²) 噪声）适用于向量查询（如梯度）。请对比两者在「隐私保证严格度」「实用性」「组合性」上的差异，并解释为什么 Google 的 RAPPOR 用随机响应（一种特殊的离散噪声机制）。
  3. 隐私预算（Privacy Budget）管理：多次查询会消耗预算，总预算 ε 必须控制在合理范围（如 ε=1 表示中等隐私）。请设计一个隐私预算分配方案：每日查询预算 ε_total=1，按查询重要性分配权重（如「用户总数」0.1、「平均消费」0.3、「敏感分群」0.6），超预算时拒绝查询并返回「隐私预算不足」。
  4. 差分隐私在 LLM 训练中的应用：DP-SGD（Differentially Private SGD）在梯度上加噪声 + 梯度裁剪，保证训练数据隐私。请解释 DP-SGD 的工程开销（比普通 SGD 慢 5-10 倍、模型质量下降 5-15%）以及为什么 Apple 用 DP 在设备端收集 emoji 使用频率。

### CA23 联邦学习：横向拆分 / 纵向拆分 / 迁移学习

- **预期档位**: hard
- **考察维度**: 联邦学习三种范式 + 工程挑战
- **对话脚本**:
  1. 联邦学习（Federated Learning, FL）让多个参与方在不共享原始数据的前提下联合训练模型。三种范式：横向 FL（参与方数据特征相同但样本不同，如不同地区医院都有「年龄 + 诊断 + 治疗」）、纵向 FL（参与方样本相同但特征不同，如同一批用户银行有「收入」、电商有「购物」）、联邦迁移学习（既不同样本也不同特征）。请用矩阵示意三种拆分方式。
  2. FedAvg（Fed Average Algorithm）是 2017 年 Google 提出的横向 FL 基础算法：每轮 Client 用本地数据训练 → 上传模型参数到 Server → Server 加权聚合 → 下发新模型。请设计 FedAvg 的关键参数：Client 数量（K=100）、本地 epoch 数（E=5）、参与率（C=0.1，每轮只选 10% Client），并解释这些参数如何影响收敛速度与通信开销。
  3. 纵向 FL 的核心挑战是「实体对齐」（Entity Alignment）：找到两个参与方共同的样本 ID（用 PSI 隐私集合求交协议）。请解释 PSI 的工程实现（同态加密 / 乱码电路 / 不经意传输）以及为什么纵向 FL 的工程复杂度远高于横向 FL。
  4. 联邦学习的安全威胁：模型反演攻击（从梯度反推原始数据）、成员推断攻击（判断某样本是否在训练集）。请设计一个安全聚合（Secure Aggregation）方案：Client 上传梯度前用 Mask 加密，Server 只能聚合密文无法看单个梯度，并讨论这种方案如何对抗「好奇但诚实的 Server」攻击模型。

### CA24 GDPR / PIPL / CCPA 合规框架对比

- **预期档位**: medium
- **考察维度**: 三大隐私法规对比 + 合规设计
- **对话脚本**:
  1. 欧盟 GDPR（2018 生效）、中国 PIPL（2021 生效）、加州 CCPA（2020 生效）是全球三大主要数据保护法规。请用对比表列出关键差异：管辖范围（GDPR 域外适用、CCPA 仅加州居民、PIPL 全球中国公民）、数据主体权利（知情权 / 删除权 / 可携带权 / 拒绝权）、违规处罚上限（GDPR 4% 全球营收 / PIPL 5% 营收或 5000 万 / CCPA $750/用户）。
  2. GDPR 的 7 大数据主体权利：知情权、访问权、更正权、删除权（被遗忘权）、限制处理权、可携带权、反对权。请为每条权利设计一个工程实现：「删除权」需要级联删除 + 备份清理 + 第三方通知；「可携带权」需要 JSON / CSV 导出接口；「反对权」需要用户偏好存储 + 营销系统接入。
  3. PIPL 的「数据出境」要求：向境外提供个人信息必须通过三条路径之一——安全评估（向监管机构申报）、标准合同（SCC）、个人信息保护认证。请为 laew 设计合规路径：用户把数据存到 laew 默认本地 SQLite（无需出境），但若用户主动用云端 Provider（Anthropic / OpenAI）则视为出境，需提示用户并签署同意。
  4. 合规差距分析（Gap Analysis）：对照 GDPR 评估 laew 当前实现。逐条检查：API Key 是否被用户视为敏感数据（GDPR 适用）/ 是否提供数据导出接口（访问权）/ 是否提供删除接口（删除权）/ 是否有同意管理（知情权）/ 是否有违规通知机制（72 小时上报）。给出 5 项关键差距清单。

### CA25 同意管理（Consent Management）：收集 / 撤回 / 可携带

- **预期档位**: medium
- **考察维度**: 同意生命周期 + 工程实现
- **对话脚本**:
  1. 同意管理是合规的核心。请设计一个同意（Consent）数据结构：`{consent_id, user_id, purpose, granted_at, expires_at, withdrawn_at, version, ip_address, source}`，并解释为什么必须记录 IP 地址 + 同意版本号（法律举证需要）。
  2. 同意的最小化原则：用户应该能精细控制「同意 A 目的但不同意 B 目的」。请设计一个分层同意 UI：基础功能（必同意，如服务交付所必需）、增值功能（可选，如个性化推荐）、第三方共享（可选，如广告归因），每个同意独立可撤回。
  3. 同意撤回的工程实现：用户撤回后必须立即生效。请设计一个「撤回即时生效」机制：用户在偏好中心点击「撤回营销同意」→ 后端写入 `consent_withdrawn_at` → 营销系统通过事件订阅收到通知 → 下次营销推送前检查同意状态 → 不发送。整个延迟要求 < 1 秒。
  4. 同意的可携带性（Portability）：用户能导出自己所有的同意记录供第三方核验。请设计一个同意导出格式（JSON / W3C VC 可验证凭证），并解释为什么「可携带」是 GDPR 的硬性要求（保护用户切换服务商的自由度）。

### CA26 数据驻留与跨境传输：SCC / BCR / 安全评估

- **预期档位**: hard
- **考察维度**: 跨境传输法律框架 + 工程实现
- **对话脚本**:
  1. 数据驻留（Data Residency）指数据必须存储在特定地理位置（欧盟数据必须留在欧盟、中国重要数据必须留在中国）。请对比三种主流方案：本地数据中心（成本高但合规简单）、区域云服务商（AWS 欧洲区 / 阿里云华东区）、混合架构（热数据本地 + 冷数据云端）的工程实现与合规优势。
  2. 跨境传输的三种合规路径：标准合同条款（SCC，欧盟委员会模板合同）、具有约束力的公司规则（BCR，跨国企业内部规则）、安全评估（中国 PIPL 要求的政府评估）。请为一家中国出海企业（用户在欧洲）设计跨境传输方案：选择哪条路径？需要什么文件？评估周期多长？违规风险多大？
  3. 数据本地化的「本地存储 + 跨境访问」模式：原始数据存储在本地，但允许授权用户从境外远程访问。请设计这个模式的访问控制：必须经过 VPN + MFA + 审计日志 + 时间限制 + 数据最小化（只读不下载），并解释为什么这种模式在 GDPR 下仍有合规风险（GDPR 要求「充分性保护」不止于访问控制）。
  4. laew 的本地存储策略与合规分析：所有 SQLite 库 + DebugReport + session_memory 都在用户本机硬盘，物理上完全本地化；如果用户使用云端 Provider 则数据出境，但属于「用户主动触发」且不经过 laew 服务器中转（laew 仅做客户端）。请评估这种架构在 GDPR / PIPL 下的合规立场：laew 是否属于「数据控制者」还是「数据处理者」？

### CA27 隐私增强技术 PETs 选型矩阵

- **预期档位**: medium
- **考察维度**: PETs 全景 + 场景化选型
- **对话脚本**:
  1. 隐私增强技术（Privacy Enhancing Technologies, PETs）涵盖六大类：数据脱敏（Masking）、假名化（ Pseudonymization）、差分隐私（Differential Privacy）、联邦学习（Federated Learning）、同态加密（Homomorphic Encryption）、安全多方计算（Secure Multi-Party Computation）、零知识证明（Zero-Knowledge Proof）、可信执行环境（TEE / SGX）。请用对比表说明每个技术的「隐私保证」「计算开销」「适用场景」「成熟度」。
  2. 场景化选型：医疗数据共享（医院 A + 医院 B 联合研究但不能共享患者数据）应选联邦学习；金融反欺诈（多家银行联合训练反欺诈模型）应选联邦学习 + 差分隐私；广告归因（证明用户在某平台看了广告但泄露具体行为）应选零知识证明；数据外包计算（让云厂商处理加密数据但不解密）应选同态加密。
  3. 同态加密（Homomorphic Encryption）的核心思想：在密文上直接做运算，解密后等于在明文上的运算结果。请对比三类：部分同态（PHE，加法或乘法）、有限同态（SHE，加乘都支持但有限次）、全同态（FHE，无限次运算）。并解释为什么 FHE 距离实用还差 5-10 倍性能。
  4. TEE（Trusted Execution Environment，如 Intel SGX / ARM TrustZone / AWS Nitro Enclaves）通过硬件隔离保护数据。请对比 TEE 与同态加密：TEE 性能高（接近明文计算）但依赖硬件厂商信任；同态加密无需信任硬件但性能差。设计一个金融场景的隐私计算架构：热数据用 TEE（实时交易）、冷数据分析用联邦学习（离线联合建模）。

### CA28 数据生命周期治理：采集 / 存储 / 使用 / 共享 / 销毁

- **预期档位**: medium
- **考察维度**: 数据全生命周期 + 各阶段合规要求
- **对话脚本**:
  1. 数据生命周期分为五个阶段：采集（Collection）、存储（Storage）、使用（Use）、共享（Sharing）、销毁（Destruction）。请为 laew 设计一个数据资产清单：每个阶段有哪些数据（如采集阶段有用户输入 + Provider API Key）、存储在哪里（本地 SQLite + 文件系统）、保留多久、有无加密、谁有访问权。
  2. 采集阶段的「最小化原则」与「目的限定原则」：只采集实现目的所需的最少数据；采集前必须明确目的且不能超目的使用。请设计 laew 的输入采集策略：用户输入的提示词是否被持久化（是的，存 session_memory）/ 是否被用于模型训练（默认否，可选同意）/ 是否被上传第三方（默认否，Provider 调用除外）。
  3. 存储阶段的金标准「加密静态数据」（Encryption at Rest）：全盘加密（FileVault / BitLocker）+ 数据库加密（SQLite SQLCipher）+ 备份加密。SQLite 默认明文存储 API Key 是不合规的；请设计升级路径：用 SQLCipher 加密 + Keychain 存储主密钥 + 启动时解锁（macOS Keychain / Linux Secret Service）。
  4. 销毁阶段：从主动删除到物理销毁。主动删除：用户「/clear」命令必须清空 SQLite session_memory + 重写文件（防止磁盘恢复取证）；备份销毁：所有备份（包括 rsync / Time Machine）必须同步删除；第三方销毁：通知云端 Provider 删除训练用数据（如 OpenAI 提供「删除所有训练数据」API）。

### CA29 Privacy by Design & by Default：七项原则

- **预期档位**: medium
- **考察维度**: 隐私设计七原则 + 工程落地
- **对话脚本**:
  1. Ann Cavoukian 提出的 Privacy by Design 七原则：主动而非被动（Proactive not Reactive）/ 默认隐私（Privacy as the Default）/ 嵌入设计（Privacy Embedded into Design）/ 全功能（Full Functionality）/ 端到端安全（End-to-End Security）/ 可见透明（Visibility and Transparency）/ 尊重用户（Respect for User Privacy）。请逐条解释每个原则在 laew 架构中的体现。
  2. 「默认隐私」原则：默认值就是最隐私的状态。请审计 laew 的默认配置：是否默认开启本地存储（是，符合隐私）/ 是否默认开启遥测（否，符合隐私）/ 是否默认共享用户数据给第三方（否，符合隐私）/ 是否默认记录详细日志（默认 INFO 级别，不记录 prompt 内容，符合隐私）。
  3. 「嵌入设计」原则：隐私不是事后补丁而是架构级考虑。请设计一个「隐私优先」的 laew 架构：所有 API Key 默认加密存储、所有调试日志默认脱敏、所有 LLM 请求默认不持久化 prompt 内容、所有备份默认加密。讨论这种架构与「开发者体验」的权衡（开发者想看 prompt 是否需要明确同意）。
  4. 「端到端安全」原则：从采集到销毁的全程保护。请设计一个端到端加密的 laew：用户输入 → 本地 SQLite 加密存储 → 发送到 Provider（TLS 1.3）→ Provider 处理（不在 laew 控制范围）→ 返回结果 → 本地加密存储 → 用户查看（内存中解密）。每一步的加密算法 + 密钥管理 + 完整性校验。

### CA30 laew 数据合规升级：从「明文 SQLite」到「隐私优先架构」

- **预期档位**: hard
- **考察维度**: 工程化升级 + 差距修复
- **对话脚本**:
  1. 审计 laew 当前合规现状：API Key 明文存 SQLite / session_memory 明文存对话历史 / DebugReport 明文写文件 / 多设备同步无加密。请评估每个差距的合规风险等级（高 / 中 / 低）与修复成本（小时 / 天 / 周）。
