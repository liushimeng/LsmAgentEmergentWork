## 二、登录前置的正确职责边界

新增 `agent/task_prerequisites.rs`,只识别“先登录/登录后/登录之后/登录成功后”等
明确顺序语义,普通“登录按钮/支持登录”不误触发。

- **Plan**:可打开首页确认登录态;发现未登录即停止搜索、遍历、评论/API探测,
  不调用 `request_human`。输出首个“人工登录 + 登录态验证”WorkFlow,其余网页单元
  全部依赖它。
- **Main-Work**:登录单元必须是首单元;后续单元显式 `depends_on`,不得并行抢登录。
- **SubAgent**:实际调用当前 Chrome 的 `control(request_human, reason="login"/"qr_login")`,
  人工完成后从页面昵称/退出入口等真实状态验证,再允许采集。

这条分工避免“规划阶段扫码 → 后续任何停测/重跑都让用户再扫码”的体验倒挂。

## 三、持久专用 Chrome profile

### 默认策略

| 模式 | 默认 user-data-dir | 退出行为 |
|------|--------------------|----------|
| headed | `~/.laew/chrome_profiles/work_<工作目录哈希>` | 正常关闭 Chrome,保留目录和登录态 |
| hidden / CI | 系统临时目录 `laew_chrome_<随机>` | 回收进程并删除目录 |
| `LAEW_CHROME_PROFILE=<路径>` | 用户显式目录 | 按持久 profile 处理 |
| `LAEW_CHROME_PROFILE_MODE=ephemeral` | 强制一次性 | 回收并删除 |
| `LAEW_CHROME_PROFILE_MODE=persistent` | 强制持久 | 正常关闭并保留 |

约束:

- 不读写用户日常 Chrome 默认 profile;Cookie 不落项目工作区。
- 按工作目录隔离,减少并行任务 SingletonLock 冲突与跨任务会话混用。
- `open` 回 `profile_persistent` 与 `login_reuse_hint`,让 Agent 明确知道能否复用登录。
- laew 退出仍回收 Chrome,不为了保登录在后台留浏览器进程。

### 为什么必须优雅关闭

`BrowserHolder::shutdown` 对持久 profile 先执行 chromiumoxide `Browser.close` 并等待
进程退出,超时才 `start_kill`;watchdog 新增 `--keep-profile`,强杀 laew 时仍回收 Chrome,
但不删持久目录。一次性 profile 的旧删除语义与 SIGKILL 契约不变。

**session cookie 还必须显式持久化**:实测 `restore_on_startup=1` 仍不能让本机 Chromium
保留无过期时间的会话 Cookie,且恢复旧 Tab 会制造重复页,因此最终不采用该设置。
正常关闭前通过 CDP `Storage.getCookies` 找到 `session=true` 的 Cookie,再用
`Storage.setCookies` 以 30 天有效期写回 Chrome 自身加密 Cookie DB;已有有效期的不碰,
不明文导出、不打印值。真实回归同时断言 localStorage 与 session cookie 跨重开存在。

**生产 watchdog 的 EOF 分支也曾无条件 `remove_profile`**:test harness 路径没覆盖真实
`laew __browser-watchdog --keep-profile`,导致前几轮目录仍在退出后消失。现 EOF 与
“目标已消失”两路都统一 `cleanup_profile(keep)`;新增真实二进制契约:回收目标进程但
保留 Cookies 文件。最终京东短探针复核:退出后目录存在,重开 laew 后
`#ttbar-login-2024` 与 `a.nickname` 均直接显示已登录昵称,无人工请求。

### 浏览器指定也必须进入规划层

后续复跑发现 Plan 偶发改用 Lsm 打开京东:`browser_mandate` 原先只在 SubFlow 注入。
现将判定移入共享任务约束,Plan 初次/再规划与 Main-Work 都接收“规划探查与网页操作
必须使用用户指定内核,登录态不共享”,避免 Plan 另开无登录态浏览器。

## 四、多 Tab / 多 Agent 控制模型

- 每个 `(Chrome, page_id)` 继续拥有独立 `web_control` 两态、蒙层与输入闸。
- 所有 `control` 在参数解析后先 `Page.bringToFront`;`request_human` 也先激活目标页,
  人工看到的是实际要登录/核验的 Tab。
- ChromeManager 持有跨 Tab `tokio::Mutex`:覆盖“激活→动作→输入闸恢复”完整窗口,
  防止两个 SubAgent 同时切 Tab 后把真实鼠标/键盘事件落到兄弟页面。
- 锁只串行化页面控制动作,不串行化 LLM 推理和只读 inspect;多 Agent 仍可各持
  page_id 分工。后台 Tab 不再被假定为可正常执行可信输入。
- `list` 的 managed pages 回 `active=true/false` 与 `visibility=visible/hidden`;
  control 成功回 `tab_activated=true`。

## 五、其它工具修复

- `click_text`:scope 根元素加入候选,修复同一 selector 用 click 能点、click_text
  却 `text_not_found`。
- `ERR_INVALID_RESPONSE`:保留原错误,不自动重试、不掩盖风控;附恢复建议——先确认
  登录/阻断,JSON/API 在站点页面上下文用 `eval_js(fetch(...,{credentials:'include'}))`,
  不反复顶层导航。
- `open` 同 URL 复用改为 URL 规范化比较,消除首页尾斜杠造成的重复 Tab。
