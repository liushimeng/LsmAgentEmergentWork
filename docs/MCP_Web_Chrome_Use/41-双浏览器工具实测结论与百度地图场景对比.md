# 41-双浏览器工具实测结论与百度地图场景对比(2026-10-23)

> 实测方式:`laew --info -f prompt_{chrome,lsm}.md`,同一任务(百度地图公交路线规划 + 截图 + 文档)
> 分别强制走 `MCP_Web_Chrome_Use` 与 `MCP_Web_LsmAgentBrowser_Use`。
> 总体设计见 `docs/双浏览器工具架构/01-设计与解决方案.md`;本篇记录**两工具的实测能力边界**。

## 一、结论速览

| 维度 | MCP_Web_Chrome_Use | MCP_Web_LsmAgentBrowser_Use |
|------|--------------------|------------------------------|
| 打开 map.baidu.com | ✅ 3.6s,真实 title/url(`百度地图`) | ✅ status=200,正文恒为「百度地图」4 字符 |
| 路线规划 UI | ✅ 可达(搜索框/路线按钮/POI 面板/「选为终点」按钮均可见) | ❌ app JS boot 失败,UI 不可达 |
| 到达终点 | 模型反复换 selector 无效(页面无渲染 UI),属内核渲染边界 | 同左 |
| 截图 | ✅ 现支持 `params.save_path` 落盘(见 §3) | ✅ save_path 落盘(原生支持) |
| 批量动作 | ❌ 基础动作集,无 explore/batch/sequence(P6 移植) | ✅ explore/batch/sequence 全套 |
| 任务耗时 | 修 F2 前 30+ 分钟未出文档(截图 base64 撑爆上下文) | 8 分钟产出诚实失败文档 |

**选用结论**:百度地图这类重 JS + canvas 的站点,**Chrome 侧可达、Lsm 侧不可达** —— 反-反爬内核的价值在「不被风控打标」,不在「跑得动所有站点」。两工具互补关系成立:常规站点走 Chrome,风控站点走 Lsm。

## 二、本轮暴露的四个问题(已修)

### F1 提示词批量范式未按工具分流(已修)
- 现象:Chrome 任务中 Main-Work 拆步模板与 **QC 死循环裁决建议**硬编码 `MCP_Web_LsmAgentBrowser_Use(action=explore/batch)`,
  QC 甚至建议把 Chrome 的 `c_00000000` page_id 传给 Lsm 工具 explore(确定性陷阱)。
- 修:SubAgent-Work 规范 1.5 / 16.1 批量范式显式标注「仅适用于 MCP_Web_LsmAgentBrowser_Use」;
  `plan_prompt.rs` 网页感知首选表述改为双工具中立;选用决策块补 Chrome 高效用法。
  (`src/agent/system_prompt/mod.rs`、`src/agent/system_prompt/plan_prompt.rs`)

### F2 截图 base64 内联撑爆上下文(已修,本轮最严重)
- 现象:单张 PNG base64 约 1.7MB 直进消息流,30+ 轮后 LLM 调用 >120s 响应头超时(网关重试 3 次);
  Reflection Agent 独立根因定位:「截图的大体积二进制回包滞留上下文后,推理失去前进锚点陷入纯文本自锁」。
- 修:`control(screenshot)` / `inspect(screenshot)` 支持 `params.save_path` —— 落盘 PNG,信封只回
  `{path, bytes, width, height}`,**不回 base64**;不传 save_path 时保持旧行为。
  顺带修正一处实现 bug:CDP `Page.captureScreenshot` 的 `data` 本身已是 base64 文本
  (`chromiumoxide::Binary` newtype),原实现二次编码导致落盘文件不是 PNG。
  (`src/agent/chrome_browser/page.rs`、`src/agent/tools/mcp_chrome_use/mod.rs`)

### F3 动作集缺口迫使模型绕行(已修)
- 现象:模型用 eval_js 手搓 focus+KeyboardEvent 输入地址;用 Bash+python 解码 base64 落盘截图。
- 修:`control_action` 增加 `input_text`(= `type` 的别名,对齐 Lsm 版命名,提升可发现性);
  `wait` 支持 `params.selector` + `timeout_ms` 就绪判定(轮询可见性,上限 30s)。

### F4 跨工具 page_id 无诊断(已修)
- 两工具页面注册表独立,误用时只返回干巴巴的 2000/2004。
- 修:Lsm 工具收到 `c_` 前缀 page_id、Chrome 工具收到 `p_` 前缀 page_id 时,报文直接点破
  「该 page_id 属于另一浏览器工具,注册表独立,page_id 不跨工具复用」并给出替代路径。
  (`src/agent/browser/mod.rs::EngineError::page_not_found`、
  `src/agent/tools/mcp_chrome_use/mod.rs::page_missing_message`)

### F5 laew 被强杀后 Chrome 成孤儿(已修)
- 现象:测试中被强杀的两轮留下 3 个孤儿 Chrome 进程(每个 100MB+ 内存持续占用);
  进程内 `close_all()` 只在正常收口/取消路径执行,`SIGKILL` / 任务管理器强杀无从回收。
- 修:移植历史 Chrome 时代的**进程外 watchdog**(见 `reference实现归档/src/agent/browser_watchdog.rs`):
  ① 新增 `src/agent/chrome_browser/watchdog.rs`(探活 / SIGTERM→SIGKILL 终止 / profile 清理);
  ② 新增隐藏子命令 `laew __browser-watchdog <browser_pid> <user_data_dir>`(stdin pipe EOF = 主进程已死);
  ③ Chrome 拉起成功后由主进程 spawn 该 watchdog(独立进程组,免被终端 Ctrl-C 波及)。
- 验证(2026-10-23):强杀 laew 前 Chrome 进程数 10 → SIGKILL 后 12s 内全部归零(修复前必然残留)。
- 集成测试可用 `LAEW_BROWSER_WATCHDOG_EXE` 指向 laew 二进制(测试 harness 本身不认识隐藏子命令)。
- 复核 + 回归固化(2026-10-27):真网关全链复核(laew → Chrome 子进程 → watchdog 同存,
  `kill -9 laew` 后 20s 内 Chrome 回收、watchdog 退出、profile 清理干净);同时发现
  `$TMPDIR` 残留 7 个历史 profile 与 6 个孤儿 Chrome 主进程(修复前的遗物,现场已清)。
  契约已固化为 `tests/chrome_watchdog_sigkill.rs`(真实二进制,unix 常规跑):
  管道在位 + 目标存活 → watchdog 不退出不误杀;stdin EOF(=SIGKILL 等价)→ SIGTERM
  回收目标 + profile 清理 + 退出码 0;目标已消失路径直接清理不悬挂。

## 四、Chrome 工具当前动作集(修后)

| action | 参数 | 说明 |
|--------|------|------|
| open | url | 返 `page_id`(c_ 前缀)+ 标题 + URL + `tool_hint` |
| list | — | 存活页 `(page_id, url)` |
| close | page_id / all | 关闭页;all 全关并回收 Chrome 子进程 |
| control(navigate) | url | 导航(受任务锚点 6001 约束) |
| control(click) | selector | JS click,返 `hit` |
| control(type / input_text) | selector + text | 原生 setter 赋值 + input/change 事件 |
| control(eval_js) | script | 页面上下文求值(一次可读多元素状态) |
| control(screenshot) | save_path? | 给 save_path 落盘只回元数据;不给回 base64 |
| control(scroll) | y / selector | 像素滚动或滚到元素 |
| control(wait) | ms 或 selector+timeout_ms | 固定等待或就绪判定 |
| control(back/forward/reload) | — | 历史导航 |
| inspect | url/title/text/html/screenshot | 页面观测(截图同样支持 save_path) |
