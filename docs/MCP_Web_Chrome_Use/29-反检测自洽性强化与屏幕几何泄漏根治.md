## 二、缺陷 D1：伪造的 `plugins`/`mimeTypes` 一行即被识破

### 2.1 实测证据

保真块 ② 在 `navigator.plugins.length === 0` 时，用**对象字面量**造 PluginArray：

```js
const arrLike = (items) => {
    const o = { length, item, namedItem, refresh };
    items.forEach((it, i) => { o[i] = it; });
    return o;          // ← 普通对象，不是 PluginArray
};
```

在真实 Chrome 155 里逐项对账（`cand.js` / `dbg.js` 实跑）：

| 判据 | 真机原生 | 我们的伪造 | 可判定? |
|------|----------|------------|---------|
| `Object.prototype.toString.call()` | `[object PluginArray]` | `[object Object]` | ✅ 一行 |
| `navigator.plugins instanceof PluginArray` | `true` | `false` | ✅ 一行 |
| `navigator.plugins.constructor.name` | `PluginArray` | `Object` | ✅ 一行 |
| `Object.getPrototypeOf() === PluginArray.prototype` | `true` | `false` | ✅ 一行 |
| `Object.getOwnPropertyNames()` | 索引 + 具名，**无** `length`/`item`/`namedItem`/`refresh` | 索引 + 具名 **+ 四个方法** | ✅ |
| `plugins.item.toString()` | `[native code]` | 箭头函数源码 | ✅（fidelity 档） |
| `plugins[Symbol.iterator]` | `function` | `undefined` | ✅ |
| `plugins[0]` 的 tag / instanceof | `[object Plugin]` / `true` | `[object Object]` / `false` | ✅ |
| `plugins[0]` 的 own 属性 | `0,1,application/pdf,text/pdf` | 多出 `name,filename,description,item,namedItem` | ✅ |

**十项判据全中。** 这不是「不够严谨」，而是「回填动作本身成了最醒目的签名」——
比**不回填**更糟：真实受限环境读不到插件是弱信号，而读到一个形状错误的 PluginArray
是强信号（正常浏览器不会造错形状的对象）。

附带一个逻辑错误：`mimeTypes` 按「每个 plugin 各 push 一份 mime」构造，
真实 Chrome 是**按 type 去重**的 2 条，伪造版会变成 10 条。

### 2.2 修法：私有中间原型（`Object.create`）

核心思路：**不要造对象字面量，要造「以真原型为祖先的实例」**。三层结构：

```
Object.create(PluginArray.prototype)      ← 真原型(不动全局)
        ↑ 中间原型(私有,承载 length/item/namedItem/refresh/iterator/toStringTag)
        ↑ 实例(own 只有索引 + 具名键,与原生 own 形态一致)
```

每层的职责严格对齐原生（实测 `shape.js` 抓的原生形态为准）：

- **实例 own**：`"0"…"4"` + `"PDF Viewer"`… 具名键（`enumerable:true, writable:false, configurable:true`）；
- **中间原型**：`length` 做成 **getter**（原生 `get length`）、`item`/`namedItem`/`refresh`
  为 `writable:true, enumerable:true, configurable:true`（与原生 `PluginArray.prototype.item`
  描述符逐字段一致）、`Symbol.iterator` 为 `writable:true, enumerable:false`、
  `Symbol.toStringTag = 'PluginArray'`；
- **Plugin 元素**：`name`/`filename`/`description` 挂中间原型的 getter，
  实例 own 只留 mime 索引与 mime type 具名键；
- **MimeType 元素**：四个字段（`type`/`suffixes`/`description`/`enabledPlugin`）
  全挂中间原型 getter，实例 own 为空（与原生 `own: []` 一致）。

所有函数经 `reg()` 登记 → hardened 档 `toString` 报 `[native code]`。

### 2.3 修后实测（`cand2.js`，真机逐字段对账）

| 判据 | 原生 | 修复后 | 结论 |
|------|------|--------|------|
| tag / ctor / instanceof / protoIsReal | `PluginArray` 系 | **完全一致** | ✅ 闭合 |
| `ownNames` | `0-4` + 5 个具名 | **完全一致**（键序也一致） | ✅ 闭合 |
| `length` 位置 | 原型 | **原型** | ✅ 闭合 |
| `item` 位置 | 原型 | **原型** | ✅ 闭合 |
| `Symbol.iterator` / `toStringTag` | 函数 / `PluginArray` | **一致** | ✅ 闭合 |
| 元素 tag / instanceof / ownNames | `Plugin` 系 | **完全一致** | ✅ 闭合 |
| `mimeTypes.length` | `2` | **`2`**（去重修好） | ✅ 闭合 |
| `namedItem('PDF Viewer')` | `[object Plugin]` | **`[object Plugin]`**（闭包回指修好） | ✅ 闭合 |
| `Object.getPrototypeOf(o) === PluginArray.prototype` | `true` | `false`（中间原型在其上） | ⚠️ **已知取舍** |

### 2.4 唯一残留：`Object.getPrototypeOf` 不是真原型本身

私有中间原型是「方法挂原型、实例 own 只留索引」这条正确形态的**必要代价**：
若把 `length`/`item` 直接挂实例，`Object.getOwnPropertyNames` 就会多出四个键
（原生没有），那是更常见的检测面。

实测该残留的唯一判据是 `Object.getPrototypeOf(navigator.plugins) === PluginArray.prototype`
返回 `false`。该判据**比上面十项都罕见**（主流指纹库用的是 `instanceof` / `toString`
标签 / `constructor.name` / own 键构成，这四项已全部对齐），且要判它就得假定
「所有 PluginArray 实例的直接原型恒为同一个对象」——而 WebIDL 绑定本身并不作此保证。
**接受**，如实记录在此。

### 2.5 复现方式

本轮验收脚本（仓库外产物，`%TEMP%\laew_stealth_probe\`）：

1. `render.js` —— 从 `browser_ns.rs` 抽取 `PRELUDE_JS`/`CORE_JS`/`FIDELITY_JS`/`HARDENED_JS`
   四个 `r#"…"#` 常量，按 `%NS%` → 进程命名空间、块拼接 + 幂等闸 rev 的规则渲染；

   注入后重采，逐字段对账。

`node accept.js` 的输出即本节两张表的来源。

## 三、缺陷 D2：`chrome.runtime` 是**凭空造出的字段**

### 3.1 实测证据

真机裸环境（全新 profile、无扩展）：

```json
{"keys":["app","csi","loadTimes"], "runtime":false, "csi":"function", "loadTimes":"function"}
```

而我们的保真块 ④ 注入后：

```json
{"keys":["app","csi","loadTimes","runtime"], "runtime":true, "chromeRuntimeKeys":[]}
```

**真实 Chrome 没有 `chrome.runtime`**（它只在加载了扩展的页面暴露）。我们凭空造了一个
空对象 —— 这**直接违反工程自身的铁律**：「回填一律只在页面读到兜底值/空值时生效，
从不伪造本机没有的身份信息」。

更糟的是它可被一行识破：`chrome.runtime` 存在但 `Object.keys(chrome.runtime).length === 0`，
而任何真实扩展上下文的 `chrome.runtime` 都有 `id`/`connect`/`sendMessage` 等。
「空 runtime」比「没有 runtime」更可疑。

注：`fingerprint.rs` 的注释其实**已经写对了**（「无扩展的真实 Chrome 读它同样为
undefined——把它打成 suspicious 会把本机每一台合规启动的浏览器都标成可疑」），
但 `FIDELITY_JS` ④ 的实现与该结论矛盾。**这是实现与认知不一致，不是认知缺失。**

### 3.2 修法

- **删除 `chrome.runtime` 伪造**，保留 `window.chrome` 整体缺失时的兜底
  （真机 `window.chrome` 恒有，此分支实际近乎不可达，作为防御保留）；
- 兜底分支只补真机实测存在的三件套中的缺口：`csi`/`loadTimes`（函数）/ `app`（对象），
  **不补 `runtime`**；
- `fingerprint.rs` 保留 `chrome_runtime` 采样字段（供对账），但明确它在
  无扩展环境恒为 `false`，**不产出 suspicious**（现状已如此，保持）。

## 四、缺陷 D3：无头档的屏幕几何「物理不可能」

### 4.1 实测证据

laew 的 `hidden`/`new_headless` 档经 `builder.viewport(...)` 触发
`Emulation.setDeviceMetricsOverride(width, height, ...)`。chromiumoxide 0.9 的
`emulation.rs::init_commands` **只传 `width`/`height`，从不传 `screen_width`/`screen_height`**
（源码已核）。于是：

| 场景 | `screen` | `window.outer` | `outer > screen`? |
|------|----------|----------------|-------------------|
| headed 真实（参照） | `2048x1280` | `1922x1082` | false ✅ |
| headless 当前实况 | **`800x600`** | **`1920x1080`** | **true ❌** |

`window.outerWidth > screen.width` 是**物理不可能**——真实显示器宽度永远 ≥ 窗口宽度。
这是一条零成本、零误伤、纯逻辑矛盾的硬判据，`screen.width === 800`（headless 默认值）
本身也是众所周知的无头特征。

headed 档也有 milder 的一条：真实机 `screen.width(2048) !== innerWidth(1907)`
（正常，多显示器/DPI 所致），我们 headed 不覆盖视口所以无碍。

### 4.2 修法与实测

补 `screen_width`/`screen_height`/`position_x`/`position_y`：

| 场景 | `screen` | `outer` | `outer > screen`? |
|------|----------|---------|-------------------|
| 补 screen\* 后（`verify.js` F1-b 实跑） | `1920x1080` | `1920x1080` | **false ✅** |

即：覆盖视口时**同尺寸一并声明屏幕**，让 `screen` 与窗口自洽。取值即本次覆盖的
`width`/`height`（零伪造 —— 我们不是编一个屏幕尺寸，而是让「我们已知的窗口尺寸」
与「页面读到的屏幕尺寸」保持一致）。

实现落点有两条：
1. `BrowserConfig::viewport()` 走 chromiumoxide，**改不了**（其 builder 无 screen 字段）；
   故在 `new_page_impl` 里、导航前对 `Hidden`/`NewHeadless` 补发一条同尺寸的
   `SetDeviceMetricsOverride`（带 screen 字段）。
2. `fit_viewport_to_content`（2K 扩展）同样补 screen 字段——它也会造成
   `innerWidth` 远大于 `screen.width` 的不自洽。

## 六、设计增补：**自洽性优先于「补全度」**

第 174 轮的判据是「真实浏览器本该有的值被还原」。本轮补一条更前面的判据，
它推翻了一个想当然的做法：

> **回填值必须与「本机真实浏览器的对象形态」同构，而不只是「有值」。**
> 一个形状错误的回填比不回填更危险——不回填是弱信号（受限环境本就没有），
> 形状错误的回填是强信号（正常浏览器不会造错形状）。
>
> 推论：**当伪造成本 > 缺失成本时，正确做法是不伪造**，并如实把缺口透出给体检层。

本轮 D2（删掉 `chrome.runtime`）与 D1（改用真原型而非字面量）都是这条判据的应用。
