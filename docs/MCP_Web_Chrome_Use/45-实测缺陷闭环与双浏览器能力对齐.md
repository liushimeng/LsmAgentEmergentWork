## 二、缺陷清单与根因

### D1 Lsm 工具的跨工具 page_id 诊断是**死代码**(文档 41 §F4 声称已修,实际未生效)

- **现象**:SubAgent iter=18 把 Chrome 的 `c_00000000` 传给
  `MCP_Web_LsmAgentBrowser_Use(action=control, control_action=wait)`,返回
  `{"code":2000,"data":{"page_id":"c_00000000"},"message":"page_id 无效或页面已关闭"}`
  —— 干巴巴,**没有**「该 page_id 属于另一浏览器工具」的指引,白费一轮。
- **根因**:`EngineError::page_not_found`(`src/agent/browser/mod.rs:306`)里写了跨工具分支,
  但 Lsm 工具兼容层**自己先做了存活校验**:
  `src/agent/tools/mcp_web_lsm_browser_use/control.rs:41` 与 `inspect.rs:34` 直接
  `envelope(2000, "page_id 无效或页面已关闭", ...)`,**根本走不到** `page_not_found`。
  → 文档 41 §F4 的修复只在 `browser::api` 内层路径可达,是最常见的兼容层路径的死代码。
- **影响**:双工具并存架构下,跨工具误传 page_id 是**高频**误用(本次 10 次工具调用命中 1 次),
  每次浪费一整轮 LLM 往返(本轮单次 LLM 往返均 ~12s)。

### D2 `control`/`inspect` 漏传 `page_id` → 1001 空转一轮

- **现象**:第二执行单元 iter=1 调 `MCP_Web_Chrome_Use(action=control, control_action=eval_js)`
  **漏传 page_id**,返回 1001,整轮作废。
- **根因**:两工具的 `page_id` **只接受顶层**(`str_arg(&args,"page_id")`),
  模型写在 `params` 里就丢;且「本轮只开了一个页面」这一**强上下文**未被利用,
  工具仍机械要求必填。
- **通用性**:单页任务里 page_id 是纯冗余参数,却成了整轮失败的来源。

### D3 Chrome 工具缺整页(full_page)截图,与 Lsm 工具不对齐

- **现象**:用户明确要「地图的**全景**截图」。Chrome 工具只支持视口截图,
  模型被迫连拍 3 张视口图充数 —— `map_route_bus.png` 与 `route_overview.png`
  **md5 完全相同**(`f0b996de…`),`route_result.png` 与之仅差 10 字节。
  「全景」诉求实际未满足,且白耗一个执行单元(wf-2)。
- **根因**:`MCP_Web_LsmAgentBrowser_Use` 的 screenshot 支持 `params.full_page=true`
  (`src/agent/browser/mod.rs:1480`),**Chrome 工具没有对应参数** —— 双工具能力不对齐。

### D4 Chrome 工具点击一律走 JS `el.click()`,无真实鼠标通道

- **现状**:`src/agent/chrome_browser/page.rs::click` 是 `eval_js` + `el.click()`,
  全仓库 `grep DispatchMouseEvent` **零命中**。
- **风险**:与已根治的 G1(键盘)是**同类问题** —— 重 JS 站点只认可信事件流
  (`isTrusted=true` 的 mousedown/mouseup 序列),JS `.click()` 可能「点了但没反应」。
  本轮侥幸成功(`el.click()` 命中了百度地图的事件委托),但这是**站点运气**,不是工具能力。
- **对照**:Lsm 工具已有 `hover` / `double_click` / `right_click`
  (`src/agent/browser/api.rs:471-479`),Chrome 侧全部缺失。

### D5 `wait` 就绪判定原语不对齐

- Lsm `control(wait)` 支持 `selector` + `state`(visible/hidden/attached/detached)
  + `text` + `js` + `network_idle`(`src/agent/browser/api.rs:1477`)。
- Chrome 侧只有「选择器可见」一种。模型想等「路线结果面板出现」只能固定 sleep
  (本轮用了 `ms:4000` / `ms:2500` / `ms:5000` 三次盲等),慢且不可靠。

### D6 新能力不可发现 = 等于没有

- Debug Agent 报告 P2 风险:模型**自造 selector**(`#search-button`、
  `input.route-start-input`)而非从 `inspect(elements)` 回显里取。
- 根因之一:工具 description 与提示词对「有哪些通道 / 哪些参数」描述过粗,
  模型看不到 `full_page` / `mode=real` / `state` 这些更稳的路径。

| 2 | 双工具 page_id 解析健壮化:① 顶层/`params` 双位置;② 缺失且**唯一存活页**自动选中(信封回 `page_id_auto`);③ 多页时 1001 并列存活页 | `tools/mcp_chrome_use/mod.rs`、`tools/mcp_web_lsm_browser_use/mod.rs` | 缺陷修复(D2) |

| 4 | Chrome 真实鼠标通道:`Input.dispatchMouseEvent`(mouseMoved→mousePressed→mouseReleased);新增 `click_real`/`hover`/`double_click`/`right_click`,`click`/`click_text` 支持 `params.mode=real` | `chrome_browser/mouse.rs`(新文件)+ 工具层 | 能力对齐(D4) |

| 6 | 工具 description 与 SubAgent 提示词补新通道说明(真实输入/真实点击/整页截图/就绪判定/page_id 可省) | `tools/mcp_chrome_use/mod.rs`、`system_prompt/mod.rs` | 可发现性(D6) |

### 设计约束

- **向后兼容**:所有新参数/新动作都是**增量**;`click` 默认仍走 JS 通道,
  `mode=real` 显式开启;`screenshot` 不传 `full_page` 行为不变;`wait` 不传新参数
  行为与旧版一致(仍是「先 settle 再等选择器可见」)。
- **跨工具对称**:同一能力在 Chrome / Lsm 两侧用**同名同义**的参数
  (`full_page` / `state` / `text` / `js` / `mode`),避免再造一套方言。
- **零新依赖**:全部用现成的 `chromiumoxide` CDP 类型,不引新 crate。
- **CDP 事件坐标语义**:`Input.dispatchMouseEvent` 的 x/y 是**主帧视口 CSS 像素**,
  故真实点击前必须 `scrollIntoView({behavior:'instant'})` 再量 `getBoundingClientRect()` 中心。
