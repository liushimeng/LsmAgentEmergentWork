## 1. 问题

### 1.1 频控横幅零识别(致命)
京东对高频搜索会话回横幅「**抱歉由于访问频繁导致无法搜索,请稍后再试!**」。阻断模式表
`BLOCKER_PATTERNS` 的 manual_verify 组只有「访问**过于**频繁」——与「访问频繁」互不为子串,
**零命中**。频控状态从未成为 `blocker_alert`/`page_health` 结构化信号,Agent 只能靠 OCR 截图
偶然看到,且 11:59 首见横幅后 12:02–12:10 仍继续导航硬闯(高频只会延长封锁)。

### 1.2 无导航节奏治理(致命)
全 run 对 jd.com 显式导航 ~117 次 search + ~40 次 list(同关键词重复:CPU×17、RTX 4060×13;
wf-2 的 QC 重试每次从头重扫)。工具层无 per-host 最小导航间隔、无「命中频控 → 冷却」。

### 1.3 登录墙关键词误报中断 sequence(高)
`list.jd.com` 频控降级壳的**页头渲染登出样式**(「你好,请登录」),登录态实际在(`#J_user` 无
`unlogin_layout`、用户名已显示)。关键词通道 kind=login 命中 → `step_has_blocker_alert` 中断
整批 sequence 剩余步骤(11:38–11:52 共 6 次),且告警误推 `next_action=request_human`。

### 1.4 结构探针滑块误报(中,本轮观察不改)
11:33 `detect_challenge` 把京东评论区某弹层判为 Slider,LLM 按载荷指引显式 HITL,用户答
「没有滑块,继续」。`slider_like` 几何启发式可独立成立是疑点;单样本不足以安全收紧打分,
记录在案待复现。

## 2. 方案

### 2.1 频控模式 `rate_limited`(`inspect.rs`)
- `BLOCKER_PATTERNS` **首位置**新增 `("rate_limited", ["访问频繁","频繁访问","操作频繁","请求频繁","请求过于频繁"], advice)`;
  与既有「访问过于频繁」「操作过于频繁」(manual_verify 风控墙)互不为子串,风控墙语义不变;
  表序即优先级——同页同时命中时频控优先回报。
- advice:「立即停止连续导航/搜索;工具层已自动冷却;先做本地整理/落盘或其它页面工作;冷却后低频重试」。
- **不进 HITL**:频控不是人工可解的挑战——
  - `probe_alert`(推送探针):rate_limited 专门分支,不走 auto-HITL / `human_assist`,
    回 `{blocker_alert, next_action:"cooldown", cooldown:{host,remaining_secs}}`,不进指纹去重;
  - `inspect(blockers)`:`suggested_action` 由 `request_human` 降为 `cooldown`,不挂
    human_assist 载荷,改挂 `data.cooldown` 剩余秒数。
- **命中即标记冷却**:推送探针与拉取式 inspect 双通道同源调
  `WebPace::global().mark_rate_limited(host)`(幂等取更晚截止)。

### 2.2 站点导航节奏治理(`src/agent/browser_pace.rs`,新模块)
进程级单例 `WebPace`(`OnceLock`,与 `TargetAnchor` 同构),两条防线:

| 防线 | 行为 | 配置(默认) |
| ---- | ---- | ---- |
| 最小导航间隔 | 同注册域两次**显式导航**间隔不足 → **透明等待补齐**(不打扰 LLM) | `LAEW_WEB_PACE_MIN_INTERVAL_MS`(2500) |
| 频控冷却 | 被标记后冷却期内同域导航返 **6004**(动作不执行);剩余 ≤ 自动等待上限时透明等待放行 | `LAEW_WEB_RATE_COOLDOWN_SECS`(240) / `LAEW_WEB_PACE_AUTO_WAIT_SECS`(45) |

- **6004 信封**:`{code:6004, message:"站点频控冷却中(jd.com):剩余 187s…", data:{host,
  remaining_secs, cooldown_secs, retry_after_secs, advice, force_hint}}`——6xxx 范围约束段
  (6001 锚点 / 6002 输入闸 / 6003 后台闸 / 6004 频控冷却),语义家族是「这件事本身不允许做」。
- **逃生口**:`open(params.force)` / `control(navigate, params.force)`;顶层 schema 已声明 `force`。
- **域归一 `host_of`**:`search/www/list.jd.com → jd.com`(最后两段);com.cn/co.uk 等双段
  后缀保留三段;IPv4/IPv6 字面量原样(剥端口);无 scheme 返回 None → fail-open。
- **接线点**:`run_open_inner` 顶部(open/new_window/connect 复用全路径)+ `control::run`
  navigate 分支(锚点守卫 6001 之后——目标纪律优先于节奏)。
- **只统计显式导航**:点击链接派生的导航不统计(合法外链跳转是正常任务形态,由锚点/QC 对账)。
- 杀开关 `LAEW_WEB_PACE=off/0/false/no` 整体关闭(严格向后兼容)。

### 2.3 登录墙误报降噪(`mod.rs` + `blocker_probe.rs`)
- `step_has_blocker_alert`:`kind=login` 的告警**不再中断 sequence**——登录墙是「状态疑似」
  而非「输入黑洞」,与验证码弹窗不同类;captcha/manual_verify/rate_limited 等仍立即中断
  (频控中断是止损,语义正确)。
- `probe_alert`:login 关键词命中不再附 `human_assist`、不触发 auto-HITL,`next_action` 降为
  `verify_login_state` + `login_check_hint`(先 inspect 复核真实登录态——频控降级壳页头是
  登出样式;确未登录再 `request_human(reason=login)`)。
- 语义权衡:真正未登录的页面少了 request_human 强推,但告警信号与复核路径仍完整,
  LLM 显式 request_human 通道不变(实测 wf-1 登录正是 LLM 自主发起)。

## 3. 单测
- `browser_pace.rs`:域名归一(多级折叠/双段后缀/IP 原样/非法 None)、频控冷却
  (超自动等待 Block、内 Wait、关闭自动等待一律 Block、过期放行)、最小间隔
  (补差等待/间隔足够放行)、信封码 6004。
- `mcp_web_use/tests.rs`:`detect_blockers_rate_limited_banner`(京东实测原句命中 +
  变体命中 + 评论「频繁掉线」噪声不误报 + 「访问过于频繁」仍归 manual_verify)、
  `step_has_blocker_alert_detection` 增补(login 不中断;manual_verify/rate_limited 中断)。
