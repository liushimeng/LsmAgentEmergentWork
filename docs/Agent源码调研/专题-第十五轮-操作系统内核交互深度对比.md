## 1. 内存管理

内存管理是操作系统内核交互的基础层面，涵盖内存映射、缓冲区管理、TLS 会话缓存、原子写入等机制。7 个工程在此维度差异显著。

### 1.1 七工程对比表

| 工程 | 内存映射/mmap | 缓冲区策略 | TLS 会话缓存 | 原子写入 | 核心特色 |
|------|-------------|-----------|-------------|---------|---------|
| **atomcode** | 未明确使用 | datalog 写入器 0o600/0o700 | reqwest 内置（15s 空闲超时） | 未明确 | 私有文件权限控制 |
| **claude-code** | 未明确使用 | 无特殊缓冲区设计 | undici Agent 内置 | 未明确 | 沙箱文件隔离 |
| **deepseek-harness** | **禁用** mmap（`mmap_size=0`） | Packed-Row 压缩 + Delta/Run 编码 | 未明确 | **SQLite WAL + synchronous=FULL** | Tail-Keep + Spill 文件溢出 |
| **openclaw** | 未明确使用 | SANDBOX_COMMAND_MAX_BUFFER_BYTES | 未明确 | **tmp + rename 原子操作** | 子进程 stdio 释放定时器 |
| **opencode** | 未明确使用 | Semaphore(1) 写互锁 | 未明确 | **tmp + rename + ensuring(remove)** | 7 种 Secret 正则检测 |
| **pi** | 无 mmap（使用 read/write） | 64KB 块读取，SPILL_HIGH_WATER_MARK=8MB | 未明确 | **tmp + rename 原子写入** | 严格 LF 行读取器 |
| **undici** | 未明确使用 | **FixedQueue 无锁环形缓冲区（SPSC）** | **WeakRef + FinalizationRegistry** | 不适用 | 2048 槽位链表混合体 |

### 1.2 核心发现

**deepseek-harness 的禁用 mmap 决策**：Session 持久化层显式禁用 memory-mapped I/O，注释说明"避免 mmap 在崩溃时丢失已写入但未 fsync 的数据"。这是对 SQLite 可靠性的极致追求——配合 `synchronous=FULL` 保证每次提交都 fsync，即使 OS 崩溃数据也不丢。同时采用 Packed-Row 压缩 + Delta/Run 编码（zigzag + varint），将 session 事件序列号列表压缩到极致，减少存储占用。

**undici 的 FixedQueue 无锁环形缓冲区**：这是从 Node.js `internal/fixed_queue.js` 提取的高性能队列。单个 `FixedCircularBuffer` 是 2048 槽位的环形缓冲区，多个 buffer 通过 `next` 指针链表连接。使用位掩码替代取模（`top = (top + 1) & kMask`），是单生产者单消费者（SPSC）无锁队列，用于请求排队。push 时若 head 满则创建新 buffer，shift 时若 tail 空则推进到下一个 buffer。

**undici 的 TLS Session 缓存（WeakRef + FinalizationRegistry）**：缓存的 session 不阻止 GC，当 session 被 GC 时，FinalizationRegistry 回调自动清理 Map 条目。这是 Node.js 14.6+ 的特性，避免 TLS session 缓存导致内存泄漏。

**pi 的 64KB 块读取 + 显式位置追踪**：`NodeTextLineReader` 使用 `file.read(buffer, offset, length, position)` 显式位置读取，支持中断后重试（不跳字节）。SPILL_HIGH_WATER_MARK=8MB 控制写缓冲区大小，超出部分 spill 到临时文件。

### 1.3 laew gap

- **L907 [P2]**：无 mmap 内存映射。laew 当前使用 read/write 进行文件 I/O，对大文件（如超大对话历史）缺乏高效的内存映射访问能力。
- **L908 [P2]**：无固定容量的环形缓冲区。laew 的 SubAgent 任务队列缺乏无锁 SPSC 队列优化，当前依赖 tokio 的 async channel。
- **L909 [P1]**：无 TLS Session 复用缓存。laew 每次 HTTP 请求都重新握手 TLS，缺乏 Session 复用机制，增加延迟和 CPU 开销。
- **L910 [P1]**：无原子文件写入机制。laew 的 providers 表写入、session_memory 表写入未使用 tmp+rename 模式，崩溃时可能产生半写文件。

## 2. 进程调度与 spawn

进程调度与 spawn 是 Agent CLI 执行 Bash 命令的核心能力。7 个工程在跨平台 spawn、进程跟踪、退出码处理等方面差异显著。

### 2.1 七工程对比表

| 工程 | 跨平台 spawn | 退出码处理 | 子进程跟踪 | 核心特色 |
|------|------------|-----------|-----------|---------|
| **atomcode** | 未明确 | 未明确 | 未明确 | 专注于 LLM 调用层 |
| **claude-code** | 双运行时 Bun/Node 适配 | **命令特定退出码语义解释器**（grep 1=无匹配） | ARGV0 dispatch 技巧 | Shell 快照注入 |
| **deepseek-harness** | node-pty + setsid | 信号终止映射 128+signum | OutputCollector Tail-Keep | 进程组 detached spawn |
| **openclaw** | @lydell/node-pty + Windows 批处理检测 | 未明确 | **stdio 释放定时器**（100ms 空闲/1s 截止） | 跨平台进程树终止 |
| **opencode** | cross-spawn（Windows）+ nodeSpawn（Unix） | AbortSignal 5s 超时 kill | **detached 子进程跟踪 Set** | PowerShell 参数解析 |
| **pi** | crossSpawn（Win）+ nodeSpawn（Unix） | **128+signalNumber 映射** | **trackedDetachedChildPids Set** | 背压控制（spill 文件） |
| **undici** | 不适用（HTTP 客户端） | 不适用 | 不适用 | 不直接 spawn 进程 |

### 2.2 核心发现

**claude-code 的命令退出码语义解释器**：`commandSemantics.ts` 定义了 grep/diff/test 等命令的退出码语义——grep 1=无匹配（非错误），diff 1=文件不同（非错误），test 1=条件假（非错误）。这避免了将信息性退出码误报为失败，是生产级 Agent CLI 的必要能力。

**claude-code 的 Shell 快照 ARGV0 dispatch**：`ShellSnapshot.ts` 通过 `argv[0]` 或 `ARGV0` 环境变量路由到内嵌工具（rg/bfs/ugrep）。Zsh 用 ARGV0 环境变量，Windows 用 ARGV0，Bash 用 `exec -a`。子 shell 检测（`$BASHPID != $$`）决定是否直接 `exec -a` 还是用 `(exec -a ...)` 子 shell 包裹。

**pi 的跨平台 spawn 策略**：Windows 使用 `crossSpawn`（处理 `.cmd` / `.bat` / shebang），Unix 使用原生 `nodeSpawn`（性能更优）。`trackedDetachedChildPids` Set 跟踪所有 detached 子进程，`killTrackedDetachedChildren` 在父进程退出时清理所有 detached 子进程，防止孤儿进程。

**openclaw 的子进程 stdio 释放定时器**：`releaseChildProcessOutputAfterExit` 解决 Execa 在子进程退出后仍等待 stdout/stderr 的问题。空闲定时器 `EXIT_STDIO_GRACE_MS=100ms` 无数据后触发释放，截止定时器 `EXIT_STDIO_MAX_DRAIN_MS=1_000ms` 强制释放。防止后台进程持有管道文件描述符导致父进程挂起。

### 2.3 laew gap

- **L911 [P1]**：无命令退出码语义解释器。laew 的 Bash 工具将所有非零退出码视为失败，grep 返回 1 会被误判为错误，导致 Agent 循环异常。
- **L912 [P1]**：无 Shell 快照/ARGV0 dispatch。laew 无法注入工具函数到用户 shell，也无法通过 argv[0] 路由到内嵌工具（如 rg/bfs）。
- **L913 [P1]**：无子进程 stdio 释放定时器。laew 的 Bash 工具在子进程退出后可能因未释放 stdout/stderr 管道而挂起，缺乏强制释放机制。
- **L914 [P1]**：无 detached 子进程跟踪。laew 无法在父进程退出时清理 detached 子进程，存在孤儿进程泄漏风险。

## 3. 文件系统操作

文件系统操作是 Agent CLI 读写配置、持久化状态、执行 Git 命令的基础能力。

### 3.1 七工程对比表

| 工程 | 原子写入 | Git 底层操作 | 文件锁 | 核心特色 |
|------|---------|------------|-------|---------|
| **atomcode** | 未明确 | 未明确 | 未明确 | datalog 0o600/0o700 私有权限 |
| **claude-code** | 未明确 | 未明确 | 未明确 | 沙箱文件隔离 |
| **deepseek-harness** | **WAL + synchronous=FULL** | 未明确 | SQLite 事务 | Packed-Row 压缩 |
| **openclaw** | **tmp + rename** | 未明确 | 未明确 | 沙箱文件系统桥接 |
| **opencode** | **tmp + rename + ensuring** | **cat-file --batch 批量读取** | **Semaphore(1) 按 gitdir** | 7 种 Secret 正则检测 |
| **pi** | **tmp + rename** | 未明确 | **proper-lockfile（30s stale）** | 严格 LF 行读取器 |
| **undici** | 不适用 | 不适用 | 不适用 | HTTP Cache 事务回滚 |

### 3.2 核心发现

**opencode 的 Git 底层对象数据库操作**：`snapshot/index.ts`（808 行）封装了完整的 Git 底层命令。`seed()` 通过 `objects/info/alternates` 共享源仓库的对象数据库，避免大仓库重新 hash。`diffFull()` 用 `git cat-file --batch` 一次进程调用读取多个 blob，避免逐文件 `git show` 的进程开销。`locks` Map 缓存 `Semaphore.makeUnsafe(1)`，按 `gitdir` 路径索引保证同一 gitdir 的操作串行。

**opencode 的文件锁并发控制**：`lock(key).withPermits(1)(fx)` 保证同一 gitdir 的 `track`/`patch`/`restore`/`revert`/`diff` 操作串行。`cleanup` 每小时执行一次 `git gc --prune=7.days`，清理过期对象。Semaphore 是 Effect 的异步互斥锁，比 fs 锁跨平台、比 flock 更可靠。

**pi 的 proper-lockfile 集成**：`acquireServerProfile` 使用 `proper-lockfile` 库实现分布式锁。`stale: 30_000` 锁持有者崩溃后 30 秒自动释放，`update: LOCK_STALE_MS / 3` 每 10 秒更新锁文件心跳，`retries` 固定 25ms 间隔重试最多 30 秒。`realpath: false` 不解析符号链接（安全）。

**opencode 的原子写入 + Secret 检测**：`append` 使用 `appendLock.withPermit` 保证并发安全。写入流程：`makeDirectory` → `writeFileString(tmp)` → `rename(tmp, target)` → `ensuring(remove(tmp))`。`secretFindings` 扫描 7 种正则模式（Bearer token / API key / AWS key / GitHub token / private key 等），环境变量名匹配 `API|AUTH|BEARER|CREDENTIAL|KEY|PASSWORD|SECRET|TOKEN`，值长度 ≥12 视为 secret。

### 3.3 laew gap

- **L915 [P1]**：无 Git 底层对象数据库操作。laew 的 Bash 工具执行 Git 命令时逐文件 `git show`，缺乏 `cat-file --batch` 批量读取能力，大仓库性能差。
- **L916 [P1]**：无文件锁并发控制。laew 的 SubAgent 并行执行时，对同一 gitdir 的操作缺乏 Semaphore 保护，可能导致 Git 对象库损坏。
- **L917 [P1]**：无 Secret 检测机制。laew 的录制/日志功能可能将 API Key 等敏感信息写入磁盘或版本控制，缺乏自动检测能力。
- **L918 [P2]**：无 proper-lockfile 分布式锁。laew 缺乏跨进程的文件锁机制，无法防止多实例同时写入同一数据库。

## 4. 信号处理

信号处理是 TUI 应用稳定性和优雅退出的关键，涵盖 SIGTERM/SIGINT/SIGHUP 处理器、子进程退出信号映射等。

### 4.1 七工程对比表

| 工程 | 信号处理器 | 子进程退出映射 | 优雅退出 | 核心特色 |
|------|----------|-------------|---------|---------|
| **atomcode** | **raw sigaction 处理器（async-signal-safe）** | 未明确 | 终端恢复字节序列 | 信号安全终端恢复 |
| **claude-code** | gracefulShutdown | 未明确 | WebSocket close + cleanup | 队友 shutdown 请求 |
| **deepseek-harness** | 未明确 | **128+signalNumber** | 未明确 | 信号终止映射 |
| **openclaw** | 未明确 | 未明确 | 进程树优雅终止（3s 优雅期） | signalPtySessionTree |
| **opencode** | 未明确 | 未明确 | AbortSignal 5s 超时 kill | Promise 信号封装 |
| **pi** | 未明确 | **128+signalNumber（osConstants.signals）** | killTrackedDetachedChildren | 子进程退出信号处理 |
| **undici** | 不适用 | 不适用 | 不适用 | HTTP 客户端不涉及信号 |

### 4.2 核心发现

**atomcode 的信号安全终端恢复**：`signal_restore.rs` 为 SIGTERM/SIGINT/SIGHUP 安装 raw `sigaction` 处理器，仅使用 async-signal-safe 调用（`write`/`tcsetattr`/`signal`/`raise`）：(1) 发送恢复字节序列（Kitty 键盘协议 pop、鼠标关闭、光标显示、自动换行、滚动区释放、bracketed-paste 关闭）；(2) 恢复捕获的 cooked `termios`；(3) 重新 raise 信号（保持正确退出状态）。注释强调"NOT a `tokio` signal task, which the very wedge that triggers the kill would starve"——使用 tokio signal 会在死锁时失效。

**atomcode 的 termios 原始模式**：OAuth 登录流程需要非阻塞单字节读取（轮询浏览器回调），通过 `termios` 关闭 ICANON（规范模式）和 ECHO，设置 VMIN=0/VTIME=0 实现非阻塞。RAII Drop 恢复原始终端属性。

**atomcode 的 poll() 非阻塞 I/O**：使用 `fcntl` 设置 `O_NONBLOCK` + `poll()` 实现 100ms 超时的 stdin 轮询，同时检查 `stop` 标志以支持取消。

**pi 的子进程退出信号处理**：`exitCode = code ?? (exitSignal ? 128 + (osConstants.signals[exitSignal] ?? 0) : 1)`。信号终止映射为 `128 + signalNumber`（Bash 惯例），`osConstants.signals[exitSignal]` 将信号名转为数字。

### 4.3 laew gap

- **L846 [P0]**：无信号安全恢复。laew 的 TUI 被信号杀死时内核直接拆除进程，不运行 Drop，导致终端留在 raw 模式。atomcode 的信号安全终端恢复是 TUI 类应用的最佳实践。
- **L847 [P0]**：无 termios 原始模式。laew 的 TUI 输入层缺乏非阻塞单字节读取能力，无法实现 OAuth 回调轮询等场景。
- **L848 [P1]**：无 poll 非阻塞 I/O。laew 的 stdin 输入缺乏基于 poll() 的超时轮询机制，无法同时响应取消信号。

## 5. io_uring / epoll

io_uring 和 epoll 是 Linux 内核提供的高性能异步 I/O 机制，在 Agent CLI 中主要用于高并发网络请求和文件 I/O。

### 5.1 七工程对比表

| 工程 | io_uring | epoll/kqueue | 异步 I/O 策略 | 核心特色 |
|------|---------|-------------|-------------|---------|
| **atomcode** | 未明确 | 未明确 | **poll() + fcntl O_NONBLOCK** | 手写 poll 轮询 |
| **claude-code** | 无 | 无（依赖 Bun libuv） | AsyncGenerator 心跳流 | 30s heartbeat chunk |
| **deepseek-harness** | 未明确 | 未明确 | SSE 帧严格解析 | EOF 检测 |
| **openclaw** | 无 | 无（依赖 Node.js libuv） | WebSocket 帧协议状态机 | Bun 兼容处理 |
| **opencode** | 未明确 | 未明确 | Effect 异步运行时 | FiberSet 并发管理 |
| **pi** | 无 | 无（依赖 libuv） | Lane 并发模型 | 串行 mutation + 并行 drive |
| **undici** | 不适用 | 不适用（依赖 libuv） | HTTP/2 流级别背压 | stream.pause/resume |

### 5.2 核心发现

**atomcode 的 poll() + fcntl O_NONBLOCK**：OAuth 登录流程使用 `fcntl` 设置 `O_NONBLOCK` + `poll()` 实现 100ms 超时的 stdin 轮询。这是 POSIX 标准的跨平台方案，比 epoll 更通用（适用于 macOS），比 io_uring 更简单。

**claude-code 的 AsyncGenerator 心跳流**：`withRetry.ts` 使用 AsyncGenerator 模式 `yield createSystemAPIErrorMessage(...)` 实时上报重试状态到 stdout。心跳 chunk 化：长 sleep 切 30s chunk（`HEARTBEAT_INTERVAL_MS`），防止 host 判定 session idle。

**undici 的 HTTP/2 流级别背压**：`onData` 函数中 `request.onResponseData(chunk) === false` 时调用 `stream.pause()`。HTTP/2 的 backpressure 是流级别的——`stream.pause()` 只影响当前流，不影响同胞流；而 HTTP/1.1 必须 destroy 整个 socket。这是 HTTP/2 多路复用的核心优势。

**通用结论**：7 个工程均未直接使用 io_uring。io_uring 是 Linux 5.1+ 的新特性，目前主要用于高性能存储和网络服务。Agent CLI 的 I/O 模式以少量并发连接为主，libuv 的 epoll/kqueue 抽象层已足够。

### 5.3 laew gap

- **L845 [P2]**：无 io_uring 显式使用。laew 依赖 Rust tokio 的异步 I/O（底层是 epoll），缺乏内核级事件通知优化。当前 Agent CLI 场景下 io_uring 收益有限。
- **L846 [P2]**：无 epoll/kqueue 直接调用。laew 通过 tokio 抽象层间接使用 epoll，缺乏对边缘触发模式的精细控制。

## 6. 沙箱（Landlock / Seccomp / bwrap）

沙箱是 Agent CLI 安全执行不可信代码的核心防线，涵盖 Landlock（Linux LSM）、Seccomp（系统调用过滤）、bwrap（用户命名空间）、Seatbelt（macOS 沙箱）、Windows ACL 等多层防护。

### 6.1 七工程对比表

| 工程 | Landlock | Seccomp | bwrap | Seatbelt | Windows ACL | 核心特色 |
|------|---------|---------|-------|---------|------------|---------|
| **atomcode** | 无 | 无 | 无 | 无 | 无 | BashWorkspaceGate 词法分析 |
| **claude-code** | **通过 sandbox-runtime** | **通过 sandbox-runtime** | 无 | 无 | 无 | FsRead/Write/Network 限制 |
| **deepseek-harness** | **自研 C11 launcher（296 行）** | 无 | **有** | **sandbox-exec** | **受限令牌** | 多平台沙箱链式选择 |
| **openclaw** | 无 | 无 | **Docker/Podman** | 无 | 无 | 容器级隔离 |
| **opencode** | 无 | 无 | 无 | 无 | 无 | 无沙箱 |
| **pi** | 无 | 无 | 无 | 无 | 无 | 依赖外部容器 |
| **undici** | 不适用 | 不适用 | 不适用 | 不适用 | 不适用 | HTTP 客户端不涉及沙箱 |

### 6.2 核心发现

**deepseek-harness 的自研 Landlock launcher**：`native/landlock-run/packages/entry/src/main.c`（296 行 C11 代码）实现了完整的 Landlock ABI 自协商：(1) 先调用 `landlock_create_ruleset` 带 `LANDLOCK_CREATE_RULESET_VERSION` 探测内核 ABI 版本；(2) 根据 ABI 版本动态计算 `handled_access_fs` 掩码（ABI 1 支持 13 种访问、ABI 2 加 `REFER`、ABI 3 加 `TRUNCATE`、ABI 5 加 `IOCTL_DEV`）；(3) 先 `PR_SET_NO_NEW_PRIVS` 再 `restrict_self`（无特权沙箱必须顺序）；(4) **Fail-Closed**：任何失败直接 `exit(125)` 不执行命令。

**deepseek-harness 的多平台沙箱链式选择**：按平台选择沙箱 runner 链——Linux 优先 bwrap（mount profile 最接近模式词汇），备选 Landlock；macOS 用 Seatbelt（sandbox-exec）；Windows 用受限令牌 + DACL。每个 runner 有功能探针（`probeBwrap`/`probeLandlock`/`probeSeatbelt`/`probeWindowsAcl`），探针实际执行命令验证内核是否接受 profile。Windows ACL 标记 `partial`（WRITE_RESTRICTED 需保留 Everyone、NTFS 硬链接可别名）。

**claude-code 的沙箱运行时适配**：`sandbox-adapter.ts` 封装 `@anthropic-ai/sandbox-runtime`，提供文件系统限制（`FsReadRestrictionConfig`/`FsWriteRestrictionConfig` + 路径模式解析）、网络限制（`NetworkRestrictionConfig`/`NetworkHostPattern`）、违规处理（`SandboxViolationStore` + `IgnoreViolationsConfig` + `SandboxAskCallback`）。Claude Code 特定路径约定：`//path` → 绝对路径；`/path` → 相对于 settings 文件目录；`~/path` → 家目录。

**openclaw 的 Docker/Podman 容器沙箱**：`container-engine.ts` 统一 Docker/Podman 执行接口。`SANDBOX_COMMAND_MAX_BUFFER_BYTES` 防止 stdout 爆炸，`cancelSignal: opts?.signal` 支持 AbortSignal 终止，`ENOENT` 区分引擎缺失 vs 命令失败。`fs-bridge.ts` 实现容器路径 ↔ 主机路径映射，挂载排序防止嵌套误匹配，路径守卫检查符号链接逃逸。

## 8. 进程组管理

进程组管理是确保子进程生命周期可控、防止孤儿进程逃逸的关键机制，涵盖 setsid、进程组 kill、SIGTERM→SIGKILL 升级等。

### 8.1 七工程对比表

| 工程 | setsid/detached | 进程组 kill | SIGTERM→SIGKILL 升级 | 核心特色 |
|------|----------------|------------|-------------------|---------|
| **atomcode** | 未明确 | 未明确 | 未明确 | 未明确 |
| **claude-code** | 未明确 | 未明确 | 未明确 | ARGV0 dispatch |
| **deepseek-harness** | **setsid() detached spawn** | **kill(-pgid) 整棵子树** | **graceMs=3s 后 SIGKILL** | OutputCollector Tail-Keep |
| **openclaw** | 未明确 | **isProcessGroupLeader 检测** | **DEFAULT_GRACE_MS=3000** | signalPtySessionTree |
| **opencode** | **detached: true（Unix）** | **handle.kill({ forceKillAfter: "3 seconds" })** | **5 秒后 SIGKILL** | AbortSignal 监听 |
| **pi** | 未明确 | **process.kill(-pid, SIGKILL)** | 未明确 | trackedDetachedChildPids |
| **undici** | 不适用 | 不适用 | 不适用 | HTTP 客户端不涉及进程组 |

### 8.2 核心发现

**deepseek-harness 的进程组 Detached Spawn**：POSIX 子进程 `setsid()` 成为新进程组首领，`kill(-pgid)` 可终止整棵子树。`OutputCollector` 实现 Tail-Keep 收集：保留最后 `maxBytes`（默认 64KB）在内存，错误/退出信息集中在尾部。溢出时打开 `O_EXCL|0o600` 随机名文件（防止符号链接种植）。`SIGTERM→SIGKILL` 升级：`graceMs`（默认 3s）后若树仍有存活成员，升级到 `SIGKILL`。

**openclaw 的进程树优雅终止**：`killProcessTree` 实现跨平台进程树终止。Windows 用 `taskkill /T` 包含子进程，先 SIGTERM（无 `/F`），超时后强制杀死。Unix 检测 `isProcessGroupLeader(pid)` 决定是否使用 `process.kill(-pid, SIGTERM)` 组杀。`DEFAULT_GRACE_MS=3000`，可配置 `MAX_GRACE_MS=60_000`。`process.kill(pid, 0)` 探测进程是否仍在。

**opencode 的 detached 子进程跟踪**：`detached: process.platform !== "win32"` 在 Unix 创建新进程组。`handle.kill({ forceKillAfter: "3 seconds" })` 先 SIGTERM，超时后 SIGKILL。`trackedDetachedChildPids` Set 跟踪所有 detached 子进程，`killTrackedDetachedChildren` 在父进程退出时清理。

**pi 的跨平台进程树 Kill**：Unix 使用 `process.kill(-pid, ...)` 发送信号给进程组（负 pid），Windows 使用 `taskkill /F /T` 强制终止进程树。`detached: true` + `windowsHide: true` 避免子进程继承控制台。

### 8.3 laew gap

- **L842 [P0]**：无进程树优雅终止。laew 当前 Bash 工具仅发送 SIGTERM，缺乏组杀和优雅期机制。openclaw 在第十五轮分析中明确标注此 gap 为 P0。

### 10.2 关键发现总结

1. **沙箱是 laew 最严峻的短板**：7 个工程中 4 个实现了沙箱（claude-code 通过 sandbox-runtime、deepseek-harness 自研 Landlock launcher、openclaw 容器沙箱），而 laew 完全空白。deepseek-harness 的自研 C11 Landlock launcher（296 行）是最高效的实现——不依赖 bwrap/用户命名空间，只需 Linux 5.1+ 内核。

2. **信号处理是 TUI 应用的生死线**：atomcode 的信号安全终端恢复（raw sigaction + async-signal-safe calls）是最佳实践。laew 当前 TUI 被信号杀死时会留下终端在 raw 模式，这是 P0 问题。

3. **进程组管理是长时间运行 Agent 的稳定性基线**：deepseek-harness 的 setsid + kill(-pgid) + SIGTERM→SIGKILL 升级是生产级方案。laew 缺乏进程组管理，子进程可能孤儿化。

4. **PTY 终端是交互式 CLI 应用的必要条件**：openclaw 和 opencode 都使用 `@lydell/node-pty`，opencode 额外支持 Windows ConPTY。laew 无法运行 vim/htop 等交互式命令。

5. **内存管理层面 undici 独树一帜**：FixedQueue 无锁环形缓冲区 + WeakRef TLS Session 缓存是高性能网络客户端的精髓。laew 可借鉴 FixedQueue 优化 SubAgent 任务队列。

6. **io_uring 在 Agent CLI 场景收益有限**：7 个工程均未直接使用 io_uring，libuv 的 epoll/kqueue 抽象层已足够。io_uring 更适合高性能存储服务（如数据库、对象存储）。
