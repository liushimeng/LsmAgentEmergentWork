## 0. 维度概览与工程定位

编译器前端在传统软件工程中将源代码转换为中间表示（IR），在 Agent CLI 中映射为三个核心场景：**命令安全分析**（Bash 词法/语法解析）、**代码理解**（AST 操纵/LSP 集成/代码图构建）、**协议消息解析**（Schema 验证/类型系统）。7 个工程在这一维度的实现深度差异显著：

| 工程 | 编译器前端深度 | 核心模块 | 典型行数 |
|------|--------------|---------|---------|
| claude-code | ★★★★★ | Bash Lexer + Parser + AST Walker | ~7.4k 行 |
| deepseek-harness | ★★★★★ | Typert TypeScript 编译器前端 | ~4.5k 行 |
| atomcode | ★★★★☆ | CodeIntel 七件套 + Tree-sitter | ~3k 行 |
| opencode | ★★★★☆ | Tree-sitter + LSP 客户端 | ~2k 行 |
| undici | ★★★☆☆ | llhttp WASM 解析器状态机 | ~10k 行(C) |
| pi | ★★☆☆☆ | TypeBox Schema + CBOR 编解码 | ~1k 行 |
| openclaw | ★☆☆☆☆ | TypeBox Schema 验证 | ~500 行 |

**laew 现状**：当前无词法分析器、无语法分析器、无 AST 操纵能力、无 LSP 集成、无 Schema 验证框架、无类型系统。Bash 工具直接执行命令，无任何结构分析能力——这是最大的安全缺口。

## 1. 词法分析（Lexer）

词法分析是将字符流转换为 token 流的过程，在 Agent CLI 中用于命令结构分析（区分 `echo hi` 和 `echo $(rm -rf /)`）。

### 1.1 7 工程对比表

| 维度 | atomcode | claude-code | deepseek-harness | openclaw | opencode | pi | undici |
|------|----------|-------------|------------------|----------|----------|-----|--------|
| **Lexer 实现** | 手写 Rust Bash Lexer | 纯 TypeScript Bash Lexer | 无（依赖 TS 编译器） | 无 | 无（用 Tree-sitter） | 无（用 CBOR） | llhttp C 状态机 |
| **Token 类型** | quote-aware 字符串/重定向/操作符 | 15 种（ANSI-C/DQUOTE/SQUOTE/DOLLAR_PAREN 等） | N/A | N/A | N/A | N/A | HTTP 方法/URL/版本/头部 |
| **UTF-8 处理** | 字节级索引 | 双索引（JS string index + UTF-8 byte offset） | N/A | N/A | N/A | 严格 UTF-8 校验 | SIMD 字符扫描 |
| **安全约束** | 无 | 50ms 超时 + 50000 节点上限 | N/A | N/A | N/A | maxDepth/maxContainerLength | lenient_flags |
| **设计哲学** | 精确 token 流供破坏性命令检测 | fail-closed（无法确定结构则拒绝） | N/A | N/A | N/A | 严格子集（拒绝非字符串 key） | 流式 + span 机制 |

### 1.2 核心发现

**claude-code 的纯 TypeScript Bash Lexer 是最完整的实现**（`src/utils/bash/bashParser.ts` 4436 行）：
- 追踪 JS 字符串索引（`i`）和 UTF-8 字节偏移（`b`）——ASCII 快速路径两者一致，非 ASCII 逐码点推进
- 15 种 Token 类型涵盖 bash 所有词法单元（ANSI-C quoting `$'...'`、命令替换 `$()` / `` ` ``、进程替换 `<()` / `>()`）
- 3449 输入 golden corpus 验证——与 tree-sitter-bash WASM parser 对比
- Heredoc 延迟处理：`heredocs: HeredocPending[]` 数组，newline 时扫描 body

**atomcode 的 Rust Bash Lexer**（`bash_workspace_gate.rs:209-250`）：
- 完整的 quote-aware 词法分析器，正确处理单引号/双引号嵌套、反斜杠转义
- 重定向操作符（`>`/`>>`/`2>`）独立成 token，fd 前缀吸收（`2>` → 单个 token）
- 注释强调"escaped `;`, `&`, or `|` remains ordinary word content rather than splitting the command"——防止注入绕过

**undici 的 llhttp 是 C 状态机典范**（`deps/llhttp/src/llhttp.c` 10102 行）：
- 完全手写 C 状态机（非 lex/yacc 生成），使用 SSE4.2/NEON/WASM SIMD 指令加速字符扫描
- span 机制处理跨 chunk 字段拼接——`_span_pos0` 记录字段起始位置，跨 TCP chunk 时回调拼接
- lenient_flags 允许选择性放宽 RFC 合规（`LENIENT_HEADERS`/`LENIENT_CHUNKED_LENGTH` 等 9 种）

## 2. 语法分析（Parser）

语法分析将 token 流转换为抽象语法树（AST），在 Agent CLI 中用于命令结构的安全判定。

### 2.1 7 工程对比表

| 维度 | atomcode | claude-code | deepseek-harness | openclaw | opencode | pi | undici |
|------|----------|-------------|------------------|----------|----------|-----|--------|
| **Parser 实现** | Tree-sitter-bash | 递归下降 Parser | TS 编译器 API | 无 | Tree-sitter-bash/PowerShell | 无 | llhttp 状态机 |
| **AST 节点** | tree-sitter 标准节点 | 自定义（command/pipeline/redirected_statement） | TS Node → TypeNodeModel | N/A | tree-sitter 标准节点 | N/A | HTTP 消息结构 |
| **错误恢复** | fail-closed（未知节点 → too-complex） | PARSE_ABORTED 哨兵 | TS 诊断 | N/A | N/A | 拒绝尾随数据 | 36 种错误码 |
| **资源上限** | 无 | 50ms/50000 节点 | N/A | N/A | N/A | maxContainerLength | maxFrameLength |
| **增量解析** | 是（thread_local 缓存） | 否 | 是（TS program） | 否 | 是（WASM 单例） | 是（FrameDecoder） | 是（流式） |

### 2.2 核心发现

**claude-code 的 AST 安全 Walker 是 fail-closed 设计的典范**（`src/utils/bash/ast.ts` 2679 行）：
- 显式 allowlist：`STRUCTURAL_TYPES`（program/list/pipeline/redirected_statement）+ `SEPARATOR_TYPES`（`&&`/`||`/`;`）+ 约 30 种已知节点类型
- 命令替换占位符：`$()` 提取为 `__CMDSUB_OUTPUT__`，内层命令独立做权限检查
- 变量追踪：`VAR_PLACEHOLDER` 替换已追踪的 `VAR=val` 赋值引用
- bare var 不安全检测：`BARE_VAR_UNSAFE_RE = /[ \t\n*?[]/` — 未引号的 `$VAR` 会分词+路径扩展
- 三态结果：`simple`（可提取 argv）/ `too-complex`（未知节点类型）/ `parse-unavailable`

**claude-code 的 PARSE_ABORTED 安全哨兵**（`src/utils/bash/parser.ts`）：
- Symbol 哨兵区分"未加载"（null）和"加载但失败"（abort）
- fail-closed 强制：abort 必须走 too-complex 路径，不得回退 legacy
- 对抗输入防护：`(( a[0][0]... ))` 2800 层下标触发 50ms 超时

**deepseek-harness 的 Typert 是唯一的完整 TypeScript 编译器前端**（`packages/typert/generator/src/analyzer.ts` 3142 行）：
- 把 TypeScript 的 18 种类型节点形式化为可序列化的 AST（`TypeNodeModel`）
- 每个节点有稳定 `TypeNodeId`，支持跨 face（host/client）引用
- 双 face 编译：Host 和 Client 是独立编译的 TypeScript 程序（各自有 tsconfig 聚合）
- 跨 face 的 import/re-export 被记录为 `CrossFaceLink`

**opencode 的 Tree-sitter 双语法解析器**（`packages/opencode/src/tool/shell.ts`）：
- 同时加载 `tree-sitter-bash` 和 `tree-sitter-powerShell` 两个 WASM 语法
- `commands(node)` 提取所有 `command` 类型的子孙节点
- `pathArgs(list, ps, cmd)` 区分 Unix/Windows 参数风格

### 3.2 核心发现

**atomcode 的代码图是最完整的 AST 操纵实现**（`crates/atomcode-capabilities/src/codeintel/graph.rs`）：
- 内存中的代码图，包含符号节点（Function/Method/Class/Trait/Enum 等 12 种）和边（Calls/Imports/Inherits/Implements/References 5 种）

## 9. 其他编译器前端相关发现

### 9.1 claude-code 的 Vim 状态机（Lexer/Parser 混合）

**代码位置**：`src/vim/transitions.ts` 491 行

- **11 状态**：idle / count / operator / operatorCount / operatorFind / operatorTextObj / find / g / operatorG / replace / indent
- **每状态一个 transition 函数**：可扫描的 state machine 真源
- **count 累积**：`fromCount` 逐位追加数字，`MAX_VIM_COUNT` 上限
- **操作符-动作分离**：operator 状态后接 motion/find/textObj 才触发执行
- **dot repeat (`.)` + find repeat (`;/,`)**：状态持久化 `lastFind`

**设计意图**：终端内嵌 vim 编辑器需要精确的按键序列解析——`d2w`（delete 2 words）和 `2dw`（同上）语义相同但解析路径不同。

**laew gap**：L843 [P2] laew 无 vim 状态机。终端编辑仅有基础行输入。

### 9.2 claude-code 的 sed BRE→ERE 转换器

**代码位置**：`src/tools/BashTool/sedEditParser.ts` 323 行

- **完整 sed 命令解析**：提取 `-i`/`-E`/`-e` 标志、表达式、文件路径
- **BRE→ERE 四步转换**：保护字面反斜杠 → 转义元字符→占位符 → 未转义元字符→转义 → 占位符→JS 等价
- **null-byte 占位符**：`\x00BACKSLASH\x00` 等永不在用户输入中出现，防注入
- **replacement 安全处理**：`&` → `$$&`（JS 中转义），`\&` → 随机 salt 占位符防注入

**设计意图**：`sed -i 's/pattern/replacement/g'` 是常见文件编辑操作，必须在浏览器端预览编辑效果而不实际执行。

**laew gap**：L844 [P2] laew 无 sed/parser 类 DSL 解析器。

### 9.3 atomcode 的 HTML 分词器

**代码位置**：`crates/atomcode-capabilities/src/tools/web_fetch.rs:632-770`

### 9.4 opencode 的流式 Tool Call 增量解析

**代码位置**：`packages/llm/src/protocols/utils/tool-stream.ts` 219 行

- `State<K>` 是 `Partial<Record<K, PendingTool>>`，K 是流局部 id
- `appendOrStart` 处理 OpenAI Chat 风格：id/name 首次出现在 delta 中
- `appendExisting` 处理 Anthropic/Bedrock 风格：必须先有 start 事件
- `finishAll` 处理 OpenAI Chat 的 `finish_reason` 终止：所有 pending tool 同时完成
- `finishWithInput` 处理 OpenAI Responses 风格：最终 input 覆盖累积值

**设计意图**：不同 provider 的 tool call 流语法差异大，统一抽象为 `start` → `append` → `finish` 三态机。`PendingTool.input` 累积原始 JSON 字符串，只在 `finish` 时 parse（避免中间态 JSON 不完整）。

**laew gap**：L844 [P1] laew 无流式 Tool Call 增量解析。

### 9.5 pi 的 JSON 修复（Repair）

## 11. 综合对比结论

### 11.1 工程深度排名

| 排名 | 工程 | 核心优势 | 典型行数 |
|------|------|---------|---------|
| 1 | claude-code | 工业级 Bash 编译器前端（Lexer + Parser + AST Walker） | ~7.4k 行 |
| 2 | deepseek-harness | 完整 TypeScript 编译器前端（Typert）+ Zod 发射 | ~4.5k 行 |
| 3 | atomcode | CodeIntel 七件套 + Tree-sitter 代码图 | ~3k 行 |
| 4 | opencode | Tree-sitter 双语法 + LSP 完整客户端 | ~2k 行 |
| 5 | undici | llhttp WASM 解析器状态机（C 语言典范） | ~10k 行(C) |
| 6 | pi | TypeBox Schema + CBOR 编解码 + 约束采样 | ~1k 行 |
| 7 | openclaw | TypeBox Schema 验证 + QuickJS 沙箱 | ~500 行 |

### 11.2 关键设计模式

1. **Fail-Closed 原则**：claude-code 的 AST Walker 是典范——任何未知节点类型 → `too-complex`（拒绝提取 argv）。atomcode 的 `is_read_only_bash()` 同样采用 fail-closed。
2. **双轨分析**：claude-code 手写 Lexer（快速路径）+ Tree-sitter（精确分析）双轨并行，兼顾性能与准确性。
3. **编译器无关模型**：deepseek-harness 的 Typert 把"编译器依赖"关在 analyzer 内部，下游只消费模型数据。
4. **确定性 ID**：atomcode 的 `make_id(file, name, start_line)` 基于确定性哈希，跨运行稳定。
5. **资源上限**：claude-code 的 50ms 超时 + 50000 节点上限防止病态/对抗输入。
6. **Schema 严格模式**：pi 和 openclaw 的 `additionalProperties: false` 防止协议漂移。
