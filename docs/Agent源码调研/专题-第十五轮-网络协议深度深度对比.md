| **多路复用流控** | — | — | — | — | — | — | **流级别背压**(stream.pause 不影响同胞流) |
| **GOAWAY 处理** | — | — | — | — | — | — | **双阶段分离**(先 detach 流、再统一关闭) |
| **MAX_CONCURRENT_STREAMS** | — | — | — | — | — | — | **noStreamsTimeout**防永远挂起 |
| **Ping 心跳** | — | — | — | — | — | — | **interval ping**防空闲断开 |

### 1.2 核心发现

**undici 的 HTTP/2 实现是所有对标工程中最完整的**，其 `client-h2.js`(1781 行)是单个最复杂的文件：

1. **GOAWAY 双阶段分离**（行 622-681）：收到 GOAWAY 帧后，先 detach 所有运行中流、再统一关闭，避免流关闭时同步触发 `frameError` 干扰兄弟流（注释明确记载根因 #3011）。这是生产级 HTTP/2 客户端的关键设计。

2. **流级别背压**（行 1323-1350）：`stream.pause()` 只暂停当前流，不影响同胞流；而 HTTP/1.1 必须 destroy 整个 socket。这是 HTTP/2 多路复用相比 HTTP/1.1 的核心优势。

3. **noStreamsTimeout**（行 446-456）：当对端广播 `MAX_CONCURRENT_STREAMS=0` 时启动定时器，防止请求永远挂起。

**其他工程均无显式 HTTP/2 实现**，依赖运行时/库内置：
- atomcode 通过 reqwest 隐式使用 HTTP/2，但无显式流控
- claude-code / deepseek-harness 通过 undici Agent 使用 HTTP/2，但应用层无感知
- pi 完全绕开 HTTP，使用自研 CBOR + 4-byte framing 二进制协议

### 1.3 laew gap

- **L836 [P1]**：laew 无 HTTP/2 多路复用实现，当前仅 HTTP/1.1 POST。缺流级别背压、GOAWAY 处理、并发流复用
- **L837 [P2]**：laew 无 GOAWAY 双阶段分离策略
- **L838 [P2]**：laew 无 noStreamsTimeout 防护

### 3.2 核心发现

**claude-code 的 WebSocket 实现**（`src/remote/SessionsWebSocket.ts`）是 Agent CLI 场景最完整的：
- 完整状态机（connecting/connected/closed）
- 永久关闭码语义：4003(unauthorized)立即停止重连；4001(session not found)允许 3 次重试（compaction 期间服务端短暂认为 session stale）
- 30s Ping/Pong 心跳，Bun 和 ws 双运行时适配
- JSON 消息宽松探测（仅检查 type 字段为字符串），避免硬编码 allowlist 导致新消息类型被静默丢弃

**openclaw 的 WebSocket 帧协议状态机**（`packages/gateway-client/src/protocol-client.ts:42-565`）：
- 三态转换：connectSent → socketOpened → helloReceived
- 双通道分发：`isGatewayEventFrame` / `isGatewayResponseFrame`
- 序列号追踪：`lastSeq` 检测帧间隙，触发 `onGap` 回调
- Challenge-Response 认证：服务端下发 nonce + ts，客户端绑定设备身份签名

**pi 的 CBOR 帧协议**（`packages/protocol/src/framing.ts`）：
- 4 字节大端无符号整数长度前缀 + CBOR 编码 payload
- 增量式解码器（FrameDecoder），可处理任意字节块边界
- 严格校验 maxFrameLength（16MB 默认上限），防止内存炸弹
- 三层管道：TypeBox 验证 → CBOR 编码 → 4-byte 帧封装

**undici 的 WebSocket 帧解析**（`lib/web/websocket/receiver.js`）：
- 状态机驱动：INFO → PAYLOADLENGTH_16/64 → READ_DATA 循环
- 控制帧（close/ping/pong）立即处理，数据帧累积到 fragments，FIN=1 时合并
- 压缩帧异步解压（permessage-deflate）
- SendQueue 双模式：快速路径直接 write + cork/uncork，慢速路径入队等待

**opencode 的 WebSocket 录制回放**（`packages/http-recorder/src/websocket.ts`）：
- 帧级 Record/Replay 系统，支持精确断言
- 三种模式：record/replay/passthrough
- binary 以 base64 编码存储，支持 JSON 消息规范化比较

### 4.2 核心发现

**atomcode 的 TLS 版本策略**（`crates/atomcode-config/src/tls.rs:1-172`）是所有工程中最精细的：
1. **环境变量覆盖**：`ATOMCODE_TLS_MAX=1.2` 进程启动即全局生效
2. **自动回退**：首次连接失败后 latch `MANAGED_TLS12` 标志，后续对托管端点(*.atomgit.com)自动使用 TLS 1.2
3. **作用域隔离**：自动状态仅适用于 `is_managed_https_url()` 匹配的托管端点，不影响第三方 API
4. **TLS 记录腐化检测**：通过错误链字符串匹配识别 `BadRecordMac`/`DecryptError`/`cannot decrypt peer's message`，这是 TLS 1.3 长连接状态失同步或中间盒篡改的特征

**claude-code 的 mTLS 全链路**（`src/utils/mtls.ts` + `src/utils/proxy.ts`）：
- 从 `CLAUDE_CODE_CLIENT_CERT/KEY/PASSPHRASE` 环境变量加载客户端证书
- undici Agent + connect TLS 配置
- 连接池毒化：检测到 ECONNRESET/EPIPE 后全局禁用 keep-alive（`keepAliveDisabled` 粘性标记），强制后续请求新建 TCP 连接

**openclaw 的 TLS 指纹 Pinning**（`packages/gateway-client/src/websocket-transport.ts:137-191`）：
- 在 WebSocket 握手阶段拦截 TLS 套接字
- 校验 `socket.getPeerCertificate()?.fingerprint256`
- 不匹配时 `request.destroy(new GatewayWebSocketTlsPinError(...))` 终止连接
- 在 `rejectUnauthorized: false` 模式下实现自定义信任锚

**undici 的 TLS Session 缓存**（`lib/core/connect.js:15-60`）：
- 使用 WeakRef + FinalizationRegistry
- 缓存的 session 不阻止 GC
- 当 session 被 GC 时，FinalizationRegistry 回调自动清理 Map 条目

### 5.2 核心发现

**atomcode 的连接池调优**（`crates/atomcode-capabilities/src/provider/retry.rs:45-54`）：
- 将 reqwest 默认的 90s 空闲超时压缩至 15s
- 原因：对真实网关负载均衡器的观察——LB 常在 30s 内关闭空闲连接，客户端复用这些半开连接会触发 hyper `IncompleteMessage` 错误
- 15s 既低于常见 LB 窗口，又足够覆盖工具循环中请求间的短间隙

**claude-code 的连接池毒化**（`src/utils/proxy.ts:27-31`）：
- 检测到 ECONNRESET/EPIPE 后全局禁用 keep-alive
- `keepAliveDisabled` 粘性标记，强制后续请求新建 TCP 连接
- 与 atomcode 的 SwappableClient 池毒化异曲同工——stale socket 必须隔离

**undici 的连接池拓扑**（4 种池，策略模式）：
1. **Pool**：FIFO + TTL 淘汰（pool.js:143 行）
2. **BalancedPool**：加权最大公约数（GCD）轮询（balanced-pool.js:214 行）——Nginx 风格平滑加权轮询（SWRR）变体
3. **RoundRobinPool**：纯轮询 + TTL 淘汰（round-robin-pool.js:159 行）
4. **Agent**：origin 路由 + 惰性清理（agent.js:177 行）

**关键设计细节**：
- BalancedPool 的权重动态调整：connect 成功 += errorPenalty(15)，connectionError 失败 -= errorPenalty(15)
- Agent 的惰性清理：disconnect 时不立即删除 dispatcher，等确认真正不用才清理（防 GOAWAY 后连接抖动）
- Pool 对 connectionError 立即移除（不关闭，因为可能已损坏），但对 disconnect 惰性清理

| **重连机制** | — | **10min 重连预算** | 无 | — | **2^n 退避上限 120s** | — | — |
| **永久码** | — | **401/403/404 不重试** | — | — | — | — | — |
| **三层超时** | **connect/open/idle** | — | — | — | — | — | — |
| **NDJSON 解码** | **Ollama NDJSON** | — | — | — | — | — | — |

### 6.2 核心发现

**atomcode 的三层超时体系**（`crates/atomcode-capabilities/src/provider/anthropic.rs:68-75`）：
1. `connect_timeout`(30s)：TCP/TLS 握手
2. `open_timeout`(90s)：等待响应 HEAD(首字节)
3. `idle_timeout`(120s)：字节流空闲(无数据到达)
- 注释强调"no overall request timeout is set here (deliberately: a streaming response must not be capped)"——流式响应故意不设整体超时，但字节级空闲看门狗检测"接受连接但永不响应"的网关

**claude-code 的 SSE 帧增量解析器**（`src/cli/transports/SSETransport.ts`）：
- 增量解析：处理 TCP 分包——未完整帧保留在 `remaining` 中等待下次 read
- SSE 完整实现：event/id/data 三字段 + comment 识别 + 头部空格剥离
- 背压感知：`LIVENESS_TIMEOUT_MS = 45_000`（server 15s 发 keepalive，45s 无数据判死）
- 10min 重连预算：`RECONNECT_GIVE_UP_MS = 600_000`
- 永久码：401/403/404 不重试

**deepseek-harness 的 SSE 严格解析**（`packages/llm/llm-deepseek/src/sse.ts:28-40`）：
- 使用 `eventsource-parser` 处理 SSE 帧边界（空行分隔、UTF-8 重组、CRLF/BOM、多 data: 拼接）
- 显式产出 `[DONE]` 作为终判信号
- **EOF 前未收到 `[DONE]` 抛 `STREAM_CLOSED`**——这是截断检测，而非把不完整尾部当有效载荷
- 设计意图：模型流式响应若在中途被网络截断，继续处理会产出不完整的 tool_call 或 reasoning

**opencode 的 SSE 长连接与重连**（`packages/opencode/src/control-plane/workspace.ts:184-438`）：
- `connectSSE` 发起 `text/event-stream` 请求
- `syncWorkspaceLoop` 无限循环：connectSSE → syncHistory → parseSSE → 失败后 `Effect.sleep(2^attempt)` 退避
- 退避上限 120 秒：`Math.min(120_000, 1_000 * 2 ** attempt)`
- 每次重连后执行 `syncHistory`，通过 `EventSequenceTable` 的 `seq` 做增量同步

**pi 的 SSE 解码器**（`packages/ai/src/api/anthropic-messages.ts:313-462`）：
- 严格遵循 SSE 规范（W3C EventSource）
- 处理 `\r\n` / `\n` / `\r` 三种换行符
- data 字段多行拼接（`\n` 分隔）
- AbortSignal 可中断流
- 流式 JSON 修复：`parseJsonWithRepair` 处理 LLM 输出的不完整/畸形 JSON

### 6.3 laew gap

- **L853 [P0]**：laew 无 SSE 帧增量解析器（仅整块 HTTP 响应）。缺 TCP 分包处理、帧边界识别

### 7.2 核心发现

**deepseek-harness 的 SSRF 防护链**（`packages/web/web-fetch-http/src/network.ts:74-109`）是所有工程中最完整的：

1. **DNS 钉扎**：通过 Undici `Agent.connect.lookup` 钩子注入自定义 DNS 解析器
2. **解析后验证**：`isPublicIpAddress()` 拒绝私播/链路本地/环回地址
3. **NAT64 探测**：对 IPv6 响应额外探测 NAT64 前缀（RFC 7050，通过 `ipv4only.arpa` 的 AAAA 记录发现 DNS64 前缀）
4. **连接时固定**：最终返回的地址集作为 Undici lookup 的固定答案集，连接不再做二次 DNS

**设计意图**：防止 **DNS 重绑定攻击**（DNS Rebinding）和 **NAT64 绕过**——即使首次解析返回公网地址，连接时 DNS 已变成私网地址的场景。

**其他工程均无显式 SSRF 防护**：
- atomcode / claude-code / openclaw / opencode / pi 均直接 `fetch(url)` 或依赖底层库的默认 DNS 解析
- 这意味着这些工程在 WebFetch 类工具场景下存在 SSRF 风险

### 8.2 核心发现

**claude-code 的指数退避+抖动重试**（`src/services/api/withRetry.ts:530-548`）：
- 10 次默认重试，BASE_DELAY_MS = 500，最大 32s，25% 随机抖动
- **529(overloaded) 分类**：前台源（repl_main_thread/compact/sdk 等）重试；后台源（summaries/titles/suggestions）立即放弃——避免容量级联放大
- **持久模式**（`CLAUDE_CODE_UNATTENDED_RETRY`）：429/529 无限重试，5min 最大退避，6h 重置上限，30s 心跳 chunk 防止 host 判定 idle
- **Fast Mode 降级**：429 时短 retry-after（<20s）等待并保持 cache；长 retry-after 进入 cooldown（30min 默认，10min 最小）
- **stale connection 检测**：ECONNRESET/EPIPE 触发 `disableKeepAlive()` + 客户端重建

**opencode 的 Retry Policy**（`packages/opencode/src/session/retry.ts:209 行`）：
- `RETRY_INITIAL_DELAY = 2000`，`RETRY_BACKOFF_FACTOR = 2`，`RETRY_JITTER_FACTOR = 0.25`
- 有 `retry-after-ms` header → 使用该值
- 有 `retry-after` header → 解析秒数或 HTTP 日期
- 否则 → `base + base * 0.25 * random`，base = `2000 * 2^(attempt-1)`
- `RETRY_MAX_DELAY_NO_HEADERS = 30_000`
- `retryable(error, provider)` 判断错误是否可重试：匹配 7 组正则（429/500/502/503/504/524/overloaded/timeout/network error）

**pi 的 Provider 请求重试**（`packages/ai/src/utils/provider-retry.ts:1-126`）：
- 尊重 `retry-after` / `retry-after-ms` 响应头
- 指数退避：`0.5s → 1s → 2s → 4s → 8s`（上限 8s）
- 25% 随机抖动（jitter）防止 thundering herd
- 可中断睡眠（`abortableSleep`）：`AbortSignal` 可取消等待
- `x-should-retry` header 显式控制

**deepseek-harness 的 HTTP 错误码映射**（`packages/llm/llm-deepseek/src/adapter.ts:332-344`）：
- 把 HTTP 状态码 + 错误体映射到稳定机器码（`AUTH`/`RATE_LIMIT`/`SERVER`/`QUOTA`/`CONTEXT_WINDOW_EXCEEDED`）
- 用正则识别上下文溢出（`context length exceeded`、`too large for context` 等 5 种句式）
- 区分"上下文溢出"和"普通 400 错误"——前者触发压缩，后者触发参数修正
