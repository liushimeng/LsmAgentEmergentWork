## 专题一：Context 上下文管理

### 横向对比总览

| 项目 | 压缩级数 | 压缩算法 | 触发条件 | Token 计数 | Prompt Cache | 工具结果处理 |
|------|---------|---------|---------|-----------|-------------|------------|
| **claudecode** | 4 级 | 时间清理 → cache_edit → LLM 摘要 → Session Memory | 时间间隔/工具数/token 阈值 | roughTokenCountEstimation | forked-agent 共享 | 替换为 `[Old tool result cleared]` |
| **atomcode** | 3 级(L0/L1/L2) | 硬裁剪 → 摘要 → 截断 | 各层独立阈值 | 内置计数 | 前缀缓存 | 按层级策略 |
| **openclaw** | 可插拔引擎 | ContextEngine 接口 | 统一配置 | 独立模块 | 可选 | 可定制 |
| **opencode** | 2 级 | prune + LLM compaction | token 阈值 | 效果 Schema 验证 | 效果集成 | 截断 + 丢弃 |
| **deepseek-harness** | 投影 | projection unit | 域配置 | 独立 | Cordis 集成 | 按 importance |
| **pi** | 2 级 | 压缩 + 分支摘要 | 轮次阈值 | 简单计数 | 无 | 简单截断 |
| **laew** | **0 级** | **无** | **无** | **无** | **无** | **无** |

### 各项目深入分析

#### claudecode — 四级压缩管线

**第一级：Time-Based Microcompact（时间触发型）**
- 触发：两次对话间隔 > `gapThresholdMinutes`
- 算法：替换为 `TIME_BASED_MC_CLEARED_MESSAGE` 常量
- 保留：最近 1 个工具结果
- 代码：`microCompact.ts:446 maybeTimeBasedMicrocompact()`

**第二级：Cached Microcompact（缓存编辑型）**
- 触发：工具结果数 > `config.triggerThreshold`
- 算法：生成 `cache_edits` 指令，API 服务端删除缓存条目
- 保留：`config.keepRecent` 个最近结果
- 代码：`microCompact.ts:305 cachedMicrocompactPath()`

**第三级：Auto-Compact（LLM 全文压缩）**
- 触发：token 使用量超过阈值
- 算法：调用 LLM 生成对话摘要
- 保留：system prompt + 摘要 + 附件
- 特殊：forked-agent 共享 prompt cache 减少重复计算
- 代码：`compact.ts:387 compactConversation()`

**第四级：Session Memory 压缩**
- 专门处理 Session Memory 的压缩
- 代码：`sessionMemoryCompact.ts`

**关键设计洞察**：
- `COMPACT_MAX_OUTPUT_TOKENS` 控制压缩后的最大输出
- 压缩前执行 `PreCompact` hooks
- 压缩后执行 `postCompactCleanup`
- 使用 `grouping.ts` 将消息按 API 轮次分组

#### atomcode — 三级 overflow ladder

**L0 层（内核级）**：
- 硬裁剪：超过 token 上限的消息直接丢弃旧内容
- 简单截断，无摘要

**L1 层（能力级）**：
- 工具结果超过阈值时替换为摘要
- 保留最近 N 个工具结果的完整内容

**L2 层（业务级）**：
- 完整的 LLM 摘要压缩
- 仅在 hard 任务时启用

#### opencode — prune + compaction

**prune 策略**：
- 保留最近 N 轮完整历史
- 保留所有 system 消息
- 工具结果超过阈值的长输出被截断

**compaction 策略**：
- 使用 LLM 将旧历史总结为摘要
- 摘要注入为 system 消息
- 压缩比目标：50-70%

**Token 预算管理**：
```
total_budget = model.context_window - reserved_for_output
available = total_budget - system_prompt_tokens - tool_definitions_tokens
history_budget = available * 0.8
```

### 设计模式提炼

1. **渐进式压缩**（4 级 → 3 级 → 2 级）：从轻量级到重量级，避免一次性大量压缩
2. **工具结果特殊处理**：工具输出是最占空间的部分，需要专门的压缩策略
3. **时间触发型**：利用对话间隔时间来判断是否需要压缩
4. **Prompt Cache 集成**：压缩不应破坏 prompt cache 前缀
5. **LLM 辅助摘要**：最终手段是用 LLM 生成摘要

### 对 laew 的综合建议

**当前状态**：完全无压缩，长任务必然溢出

**短期方案（P0，100-200 行 Rust）**：
- 在 `agent/mod.rs` 的主循环中加入简单 prune
- 保留最近 10 轮历史 + 所有 system 消息
- 工具结果超过 4096 token 的截断

**中期方案（P1，300-500 行）**：
- 实现 LLM compaction：旧历史 → 摘要
- 在 `agent/` 下新增 `compact.rs` 模块
- 压缩前注入 system 消息标记"以下是压缩摘要"

**长期方案（P2）**：
- 四级管线，参考 claudecode 设计
- Time-Based + Cached + Auto + Session Memory
- 需要与 laew 的 Session 机制深度集成

## 专题二：MCP（Model Context Protocol）架构

### 横向对比总览

| 项目 | 传输层 | 工具注册 | 资源处理 | Server 生命周期 | 认证 | 双向支持 |
|------|--------|---------|---------|---------------|------|---------|
| **claudecode** | 7 种(stdio/SSE/WS/...) | 自动注册到工具列表 | 资源订阅 | 启动/心跳/重连/关闭 | OAuth/API Key | 支持 |
| **atomcode** | stdio 为主 | Tool trait 适配 | 资源列表 | 进程管理 | trust 体系 | 部分 |
| **openclaw** | stdio + HTTP | Gateway 抽象 | 双向资源 | 完整 | OAuth | **双向** |
| **opencode** | 3 种(stdio/SSE/Streamable) | ToolRegistry 集成 | Catalog | 连接池 | OAuth | 部分 |
| **deepseek-harness** | stdio + HTTP | Cordis Service 集成 | projection | 重连策略 | 标准 | 部分 |
| **pi** | **无** | **无** | **无** | **无** | **无** | **无** |
| **laew** | **无** | **无** | **无** | **无** | **无** | **无** |

### 各项目深入分析

#### claudecode — 7 种传输层

最完整的 MCP 实现，支持：
1. **stdio**：子进程 stdin/stdout 管道
2. **SSE**：HTTP Server-Sent Events
3. **WebSocket**：全双工通信
4. **HTTP Streamable**：新标准流式 HTTP
5-7：其他变体

**工具注册流程**：
```
MCP Server 启动 → tools/list → 每个工具包装为内部 Tool → 注册到 Agent 工具列表 → Agent 可 tool_use
```

**关键代码**：`src/mcp/` 目录

#### atomcode — trust 体系

**信任等级**：
- `trusted`：自动批准所有工具调用
- `untrusted`：每次调用需用户确认
- `restricted`：仅允许只读工具

**设计亮点**：信任等级影响工具行为，而非简单地允许/拒绝

#### openclaw — 双向 MCP

**为什么需要双向**：
- MCP Server 可以主动推送资源更新给 Agent
- 支持 Agent 订阅资源变化

**实现**：
- Gateway 层同时实现客户端和服务端
- 服务端可推送 resource_updated 通知

#### opencode — Catalog 概念

**Catalog**：MCP Server 的注册中心，管理：
- 已注册的 MCP Server 列表
- 每个 Server 暴露的工具/资源/提示
- 连接状态与健康检查

**3 种传输**：
1. `stdio`：本地进程（最常用）
2. `SSE`：远程服务（旧标准）
3. `Streamable HTTP`：远程服务（新标准）

#### pi — 明确拒绝 MCP

作者 Mario Zechner 的哲学：
> "No MCP. Build CLI tools with READMEs"

**理由**：
- MCP 增加复杂度
- CLI 工具 + README（Skill）更简单直接
- MCP 服务器的维护成本高

**替代方案**：所有工具都是 CLI 命令，用 README 作为 Skill 描述

### 设计模式提炼

1. **传输层抽象**：统一接口隐藏 stdio/SSE/WS 差异
2. **工具注册桥接**：MCP 工具 → 内部 Tool trait 的适配器模式
3. **Trust 分级**：不是二元的允许/拒绝，而是多级信任
4. **Catalog 注册中心**：管理多个 MCP Server 的元数据
5. **双向通信**：Server 主动推送 vs 仅被动响应

### 对 laew 的综合建议

**当前状态**：无 MCP，最大生态短板

**Phase 1（P0，300-500 行 Rust）**：
- 在 `src/agent/tools/` 下新增 `mcp/` 模块
- 实现 stdio 传输的 MCP 客户端
- MCP 工具包装为 `Tool` trait 实现
- 注册到 `ToolRegistry`

**Phase 2（P1）**：
- 添加 SSE 传输支持
- 实现工具列表动态更新

**Phase 3（P2）**：
- 双向 MCP 支持
- 资源订阅与推送

### 各项目深入分析

#### claudecode — 16 种内置 Skill

**文件格式**：
```yaml
---
name: deploy
description: Deploy the application
tools: [bash, read]
---
# Deploy Steps
1. Run tests
2. Build
3. Deploy
```

**触发方式**：
- `/skill-name` 指令
- 注释中的 `@skill-name` 触发
- 自动检测（代码模式匹配）

#### pi — Skill 作为一等公民

**设计哲学**：Skill 就是"带 README 的 CLI 工具"

**核心接口**：
```typescript
interface Skill {
  name: string
  description: string
  tool: Tool  // 底层 CLI 工具

}
```

**为什么 Skill 优于 MCP**：
- 更简单：不需要 server 进程
- 更透明：用户可以直接看到和修改
- 更经济：不需要额外 token 开销

#### openclaw — workshop 自演化

**52 种内置 Skill** + **workshop** 概念：
- workshop 允许 Skill 从使用中学习和改进
- Skill 的版本管理
- 用户可以贡献新的 Skill

### 设计模式提炼

1. **Markdown + frontmatter**：最通用的格式，人机可读
2. **延迟加载**：不在启动时加载所有 Skill，按需加载
3. **双轨注册**：内置 + 用户自定义
4. **一等公民**：Skill 不是二等工具，而是核心功能

### 对 laew 的综合建议

**当前状态**：无 Skill 系统

**推荐方案**：
- 在 `src/agent/` 下新增 `skills/` 模块
- Skill 文件格式：Markdown + YAML frontmatter
- 存放位置：`.laew/skills/`（工作目录）
- 内置 Skill：`/docs/`、`/test/`、`/build/`、`/review/`
- 与 `AgentProfile` 集成：Skill 注入系统提示词

## 专题四：质检机制

### 横向对比总览

| 项目 | 形式 | 触发时机 | 检查项 | 自动修复 | 失败回流 | 额外 LLM |
|------|------|---------|--------|---------|---------|---------|
| **claudecode** | hooks + skills | 工具调用前后 / 每轮结束 | 权限 / 安全 / 格式 | 部分 | 注入提示 | 视 hook |
| **atomcode** | VerifyCadenceHook | 每 N 轮 | 编译 / 测试 / lint / 类型 | 无 | 注入警告 | 可能 |
| **openclaw** | exec auto-reviewer | 工具执行后 | 语法 / 编译 / 测试 / 安全 | 自动修复 | 注入错误 | 是 |
| **opencode** | doom_loop + permission | 每轮 / 工具调用前 | 死循环 / 权限 | 打断 | 强制中断 | 否 |
| **deepseek-harness** | guard plugin | 插件配置 | 可配置 | 可配置 | 插件决定 | 可配置 |
| **pi** | **无** | **无** | **无** | **无** | **无** | **无** |
| **laew** | 独立 QC Agent | 每执行单元后 | 全面检查 | 无 | 重新执行 | **是（1次）** |

### 各项目深入分析

#### atomcode — VerifyCadenceHook

**触发时机**：每 N 轮工具调用后自动触发

**检查项**：
1. 编译检查（`cargo check`）
2. 测试运行（`cargo test`）
3. Lint（`clippy`）
4. 类型检查

**失败回流**：将错误信息注入下一轮的上下文，让 Agent 自行修复

**设计亮点**：不是每次都检查，而是按节奏检查（Cadence）

#### opencode — doom_loop 死循环检测

**检测算法**：
1. 记录最近 K 轮的 (tool_name, input_hash)
2. 检测完全重复的调用模式
3. 连续 5+ 轮无文件变更
4. 同一工具 1 分钟内调用 10+ 次

**触发后处理**：
```
检测到 doom_loop → 注入 system warning → 提示换策略 → 继续则强制中断
```

#### openclaw — exec auto-reviewer

**工作流**：
```
工具执行完成 → auto-reviewer 检查结果 → 发现问题 → 尝试自动修复 → 修复失败则报告
```

**检查项**：
- 语法检查（TypeScript / ESLint）
- 编译检查（tsc）
- 测试运行（jest）
- 安全扫描

### 设计模式提炼

1. **节奏检查**：不是每次都检查，按频率检查
2. **轻量 vs 重量**：简单任务用轻量检查，复杂任务用重量检查
3. **自动修复优先**：能自动修复的就修复，修复不了再报告
4. **死循环检测**：独立于质检的保障机制

### 对 laew 的综合建议

**当前状态**：独立 QC Agent（最重方案），每单元都过 QC

**优化方案**：
- **simple 任务**：跳过 QC Agent（当前也是这样）
- **medium 任务**：轻量 QC（仅检查工具结果格式，无 LLM 调用）
- **hard 任务**：完整 QC（保留当前方案）
- **新增 doom_loop 检测**（30-50 行 Rust）：防死循环独立于 QC

## 专题五：任务拆解与分类

### 横向对比总览

| 项目 | 分类方式 | 分类级别 | 是否拆解 | 拆解粒度 | 失败处理 |
|------|---------|---------|---------|---------|---------|
| **claudecode** | 隐式（effort） | 无显式 | 模型自主 | 模型决定 | 模型重试 |
| **atomcode** | 显式（Goal 评估器） | 两档(Simple/Hard) | 调用方指定 | Step | 重试/降级 |
| **openclaw** | 无显式 | 无 | swarm 调度 | Agent | 调度器处理 |
| **opencode** | 隐式（Agent 类型） | 无显式 | 模型自主 | 任务级 | 状态机处理 |
| **deepseek-harness** | Goal 域模型 | maxGoalRounds | 子 Goal | Goal | 超限中断 |
| **pi** | 无 | 无 | 模型自主 | 模型决定 | 无 |
| **laew** | **显式三档(Yolo)** | **simple/medium/hard** | **Yolo 拆解** | **Step** | **回流** |

### 各项目深入分析

#### claudecode — 隐式分类

- 通过 `effort` 参数（low/medium/high）隐式分类
- 模型根据 effort 自行决定任务粒度
- 无显式的任务拆解机制
- 优点：简单、灵活
- 缺点：不可控、无法保证质量

#### atomcode — Goal 评估器

**两档分类**：
- **Simple**：直接委派给 SubAgent 执行
- **Hard**：先做任务拆解，再逐步执行

**Goal 评估器**：
- 输入：用户请求
- 输出：Goal 类型 + 预估难度
- 使用 LLM 进行评估

#### deepseek-harness — Goal 域模型

**最完整的目标管理系统**：
- Goal 有完整的生命周期（created → executing → completed/failed）
- `maxGoalRounds`：最大轮次限制
- 支持子 Goal（嵌套目标）
- 进度追踪与完成判定

### 设计模式提炼

1. **显式 vs 隐式**：显式分类可控但开销大，隐式分类灵活但不可控
2. **两档 vs 多档**：两档够用，多档增加复杂度
3. **Goal 域模型**：最完整的任务抽象，支持嵌套和生命周期
4. **模型自主**：越来越多的项目让模型自行管理任务

### 对 laew 的综合建议

**当前状态**：Yolo Agent 显式三档分类（simple/medium/hard）

**优化建议**：
- **保留三档**：这是 laew 的独特优势
- **简化 simple 路径**：simple 任务直接跳过 Plan/QC
- **引入 Goal 概念**：为 hard 任务的子任务建立生命周期
- **doom_loop 集成**：在任务拆解中加入死循环检测

## 专题六：SubAgent 与多 Agent 架构

### 横向对比总览

| 项目 | Agent 数量 | 编排模式 | 上下文传递 | 并发支持 | 通信方式 |
|------|-----------|---------|-----------|---------|---------|
| **claudecode** | 动态 | hooks + skills | 共享 context | 有限 | 消息传递 |
| **atomcode** | Team 多角色 | driver 编排 | L0/L1/L2 层级 | 有限 | 层级传递 |
| **openclaw** | 多 Agent + Swarm | scheduler | 消息 + 共享状态 | **支持** | 消息总线 |
| **opencode** | 3 种(coder/task/ask) | Session 状态机 | 独立上下文 | 有限 | 服务调用 |
| **deepseek-harness** | 动态注册 | Cordis 编排 | provider 传递 | **支持** | 事件系统 |
| **pi** | 扩展定义 | lane 并发 | **lane 隔离** | **原生支持** | lane 通信 |
| **laew** | **6 固定角色** | **MultiAgentOrchestrator** | **独立上下文** | **无** | **编排器传递** |

### 各项目深入分析

#### claudecode — 动态 Agent

- Agent 数量不固定，根据需求动态创建
- 通过 hooks 和 skills 扩展能力
- 上下文通过共享 session context 传递
- 无专门的多 Agent 编排器

#### atomcode — Team 多角色

**L0/L1/L2 层级协作**：
- L0（内核）：中立循环，不感知业务
- L1（能力）：工具集，供上层使用
- L2（业务）：编码 Agent，组合 L1 能力

**Team 概念**：多个 Agent 组成 Team，每个 Agent 有特定角色

#### openclaw — Swarm scheduler

**最完整的多 Agent 方案**：
- Swarm：多个 Agent 的集合
- Scheduler：调度器，决定哪个 Agent 执行当前任务
- 支持并发执行
- Agent 间通过消息总线通信

#### pi — lane 并发

**最独特的并发模型**：
- lane：独立的执行通道
- 每个 lane 有自己的上下文
- 支持真正的并行执行
- lane 间通过消息通信

### 设计模式提炼

1. **中央编排 vs 分布式**：中央编排可控，分布式灵活
2. **固定角色 vs 动态角色**：固定角色稳定，动态角色适应性强
3. **独立上下文 vs 共享上下文**：独立隔离好，共享通信快
4. **lane 并发**：真正的并行执行模型

### 对 laew 的综合建议

**当前状态**：6 角色固定多 Agent 编排

**优化建议**：
- **保留 6 角色**：这是 laew 的核心架构优势
- **简化 simple 路径**：simple 任务跳过 Plan/QC/SessionContext
- **引入 lane 概念**：为 hard 任务的并行子任务提供并发支持
- **上下文传递优化**：SubAgent 只接收必要的上下文，而非全部
