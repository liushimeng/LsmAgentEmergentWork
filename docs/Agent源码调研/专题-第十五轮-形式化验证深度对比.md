# 专题-第十五轮-形式化验证深度对比

> 本报告横向对比 7 个工程在「形式化验证」维度的实现，涵盖 TLA+规范、Coq/Lean证明、模型检测、属性测试、契约式编程、不变量检查、Schema验证、类型状态模式 8 个子维度。
>
> 输入来源：7 份第十五轮工程深度分析文件（atomcode / claude-code / deepseek-harness / openclaw / opencode / pi / undici）

---

## 0. 核心结论摘要

**7 个工程无一使用重型形式化验证工具（TLA+/Coq/Lean/模型检测）**。所有工程均以「轻量级形式化验证替代方案」保障正确性：

| 工程 | 最强项 | 最弱项 | 总体评级 |
|------|--------|--------|---------|
| **atomcode** | 可执行契约符合性框架（conformance） | 无 TLA+/Coq | ★★★★★ |
| **deepseek-harness** | Invariant 伴侣 + Schemastery + Replay | 无模型检测 | ★★★★☆ |
| **claude-code** | Fail-closed 安全验证 + 资源上限证明 | 无属性测试 | ★★★★☆ |
| **undici** | fast-check PBT + RFC 显式编码 | 无契约式编程框架 | ★★★☆☆ |
| **openclaw** | TypeBox 严格模式 + 状态机枚举 | 无属性测试 | ★★★☆☆ |
| **opencode** | Permission 引擎 + Doom Loop 检测 | 无 Schema 校验框架 | ★★★☆☆ |
| **pi** | TypeBox Schema + CBOR 安全约束 | 无 PBT/契约式编程 | ★★☆☆☆ |
| **laew** | 无 | 全部 | ★☆☆☆☆ |

**关键洞察**：atomcode 的 conformance 框架是 7 工程中最接近「可执行形式化验证」的实现——通过 `catch_unwind` + `with_timeout` 将 panic 契约和流良构性契约可执行化。claude-code 的 fail-closed 设计是安全关键路径上最严密的工程实践。deepseek-harness 在测试覆盖维度最全面（invariant + PBT + replay snapshot）。

### 5.2 核心发现

#### 5.2.1 atomcode：最完整的可执行契约框架

atomcode 在 `crates/atomcode-kernel/src/conformance/` 实现了 7 工程中最完整的契约式编程框架：

```rust
// ConformanceReport 结构
pub struct ConformanceReport {
    pub seam: &'static str,  // "Tool"/"ToolMiddleware"/"LifecycleHooks"/"LlmProvider"
    pub subject: String,
    pub checks: Vec<CheckOutcome>,
}

impl ConformanceReport {
    pub fn assert_conformant(&self) {
        if self.passed() { return; }
        panic!("{} conformance FAILED for `{}` ({} of {} checks failed):\n{}",
            self.seam, self.subject, self.failures().len(), self.checks.len(), ...);
    }
}
```

**5 层契约验证**：
1. **Provider 契约**：`model_name()` 非空且稳定、`context_window()` 稳定、`chat_stream()` 必须终止
2. **流良构性契约**：Done/Error 后无事件、Done 最多一次、中间错误不携带 http_status
3. **工具调用重建契约**：`ToolCallDelta.arguments` 拼接后必须重现完整 `ToolCall`
4. **必须不 panic 契约**：`catch_unwind` + `with_timeout(2s)` 可执行化
5. **契约符合性框架**：为 4 个扩展缝（LlmProvider/Tool/ToolMiddleware/LifecycleHooks）提供统一检查器

#### 5.2.2 claude-code：安全关键路径的 fail-closed 契约

```typescript
// PARSE_ABORTED 安全哨兵
export const PARSE_ABORTED = Symbol('parse-aborted')
// 资源上限
const PARSE_TIMEOUT_MS = 50
const MAX_NODES = 50_000
```

- **白名单穷举**：任何未知节点类型 → `too-complex`
- **三态穷尽**：`simple | too-complex | parse-unavailable`——无第四态
- **Symbol 哨兵**：区分"未加载"和"加载但失败"
- **fail-closed 强制**：abort 必须走 too-complex 路径，不得回退 legacy

#### 5.2.3 deepseek-harness：Schemastery Schema 契约

```typescript
const backoffSchema: z<BackoffConfig> = z.object({
  initialDelayMs: z.number().max(MAX_TIMER_DELAY_MS).default(DEFAULT_INITIAL_DELAY_MS),
  maxDelayMs: z.number().max(MAX_TIMER_DELAY_MS).default(DEFAULT_MAX_DELAY_MS),
  jitterRatio: z.number().min(0).max(1).default(DEFAULT_JITTER_RATIO),
})
```

- 用 `@deepseek-ai/schemastery`（Zod 替代品）定义配置 schema
- 自动填充默认值、类型校验、范围约束

#### 5.2.4 undici：运行时协议不变量（Design by Contract）

```javascript
// 控制帧不能分片
if ((payloadLength > 125 || fragmented) && isControlFrame(opcode)) {
```

## 12. 总结

### 12.1 7 工程的共同特征

1. **无重型形式化验证**：TLA+/Coq/Lean/模型检测在 7 工程中全部缺席
2. **轻量替代方案盛行**：可执行契约、运行时不变量、Schema 验证、属性测试
3. **安全关键路径优先**：claude-code 的 fail-closed、atomcode 的 panic 契约
4. **测试驱动正确性**：deepseek-harness 的 invariant + replay、undici 的 fast-check

### 12.2 对 laew 的启示

laew 在形式化验证维度几乎空白。建议优先采纳的 4 类轻量方案：

| 优先级 | 方案 | 来源 | 工作量 |
|--------|------|------|--------|
| **P0** | Secret 检测 + fail-closed 安全验证 | opencode + claude-code | 小 |
| **P1** | fast-check 属性测试 + 资源上限 | undici + claude-code | 中 |
| **P1** | 契约符合性框架 + 流良构性 | atomcode | 中 |
| **P2** | TLA+ 规范 + 模型检测 | 理论引入 | 大 |

### 12.3 关键洞察

> **形式化验证不等于 TLA+/Coq**。7 工程证明了在工业级 Agent CLI 中，「可执行契约 + 运行时不变量 + 属性测试 + Schema 验证」的组合已经能够覆盖绝大多数正确性需求。laew 应优先建立「可执行契约符合性框架」（参考 atomcode conformance/），这是投入产出比最高的改造路径。
