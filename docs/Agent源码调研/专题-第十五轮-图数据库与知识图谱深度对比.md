# 专题 — 第十五轮：图数据库与知识图谱深度对比

> **分析范围**: 7 个工程（atomcode / claude-code / deepseek-harness / openclaw / opencode / pi / undici）
> **分析维度**: Neo4j/RDF/SPARQL、知识图谱构建、向量检索(FAISS/Annoy)、图算法(BFS/最短路径)、LSP Call Hierarchy、代码图(CodeGraph)、实体关系建模、语义相似度
> **新增 gap 编号**: L986-L1010（25 个）
> **生成日期**: 2026-09-09

## 一、维度概述与 7 工程全景对比

图数据库与知识图谱是 Agent 实现**结构化知识管理**的核心基础设施——从代码的符号调用关系、实体的属性关联，到语义向量的近似检索，都属于这一维度。本轮分析发现：**7 个工程无一引入 Neo4j/ArangoDB/TigerGraph 等真正的图数据库**，但在「代码图」「类型图」「知识同步」「LSP 调用链」四个子方向存在显著的差异化实现。

### 7 工程图数据库能力总览

| 能力维度 | atomcode | claude-code | deepseek-harness | openclaw | opencode | pi | undici |
|---------|----------|-------------|------------------|----------|----------|-----|--------|
| **Neo4j/RDF/SPARQL** | 无 | 无 | 无 | 无 | 无 | 无 | 无 |
| **知识图谱构建** | 代码图(KG化) | teamMemorySync+extractMemories | 无(仅TypeGraph) | 无 | LSP符号索引(隐式) | 无 | 无 |
| **向量检索(FAISS/Annoy)** | 无 | Tool Search(API) | 无 | 无 | 无 | 无 | 无 |
| **图算法(BFS/最短路径)** | BFS+最短路径 | 无 | 无(TypeGraph仅遍历) | 无 | 无(仅LSP单步) | 树扫描 | 无 |
| **LSP Call Hierarchy** | 无(自研替代) | 无 | 无 | 无 | 完整实现 | 无 | 无 |
| **代码图(CodeGraph)** | 完整(12节点+5边) | 无 | TypeGraph(类型图) | 无 | 隐式(import图) | 无 | 无 |
| **实体关系建模** | Symbol+Edge | Memory+Session | RemoteBoundary+CrossFace | 无 | Definition-References | 无 | 无 |

**核心发现**: atomcode 拥有最完整的**内存代码图**实现（自研 CodeGraph + BFS + 最短路径）；claude-code 拥有唯一的**跨会话知识图谱同步**机制；opencode 拥有最完整的 **LSP Call Hierarchy** 集成；deepseek-harness 拥有**编译器无关的类型图**（TypeGraph）；openclaw、pi、undici 在此维度几乎空白。

**核心发现**:
- **claude-code** 在此维度领先：`teamMemorySync` 实现了**跨会话/跨团队的知识图谱同步**——团队成员的记忆可以广播给其他成员，这是 7 个工程中最接近"知识图谱网络"的实现。`sessionMemoryCompact.ts`（16,278 行）是最大的单一记忆压缩模块。
- **atomcode** 将代码图构建视为"知识图谱技术在代码分析中的典型应用"——tree-sitter Query 提取 `@callee` capture，归属到最近包围的 Function/Method symbol，支持 17 种源文件扩展名。
- **opencode** 通过 LSP 的 `workspaceSymbol` + `definition` + `references` 隐式构建了"定义-使用"链，这是代码知识图谱的核心边。

**laew gap**: L987 [P0] — 无知识图谱构建能力，当前记忆系统（`session_memory` 表）为线性历史，缺乏实体关系建模，无法做"谁调用了什么""这个函数依赖什么"等关系推理。

### 2.4 图算法（BFS / 最短路径 / PageRank / 社区发现）

| 工程 | 实现状态 | 算法 | 代码位置 |
|------|---------|------|---------|
| **atomcode** | 完整 | 双向 BFS 调用链追踪 + BFS 最短路径（MAX_HOPS=10） | `codeintel/graph.rs:153-200` |
| **claude-code** | 无 | 无图谱遍历算法 | — |
| **deepseek-harness** | 仅遍历 | `childTypeNodeIds()` 子节点遍历，无完整图算法 | `packages/typert/generator/src/model.ts` |
| **openclaw** | 无 | 无 | — |
| **opencode** | 无 | LSP 单步 `incomingCalls`/`outgoingCalls`，无图遍历 | `packages/opencode/src/lsp/lsp.ts` |
| **pi** | 树扫描 | `scanBranch` 从 tip 向根扫描，在 compaction 边界停止 | `packages/agent/src/harness/runtime/lane.ts` |
| **undici** | 无 | 无 | — |

**核心发现**:
- **atomcode** 是唯一实现完整图算法的工程：`trace_callers`/`trace_callees` 双向 BFS（`max_depth` 防循环），`shortest_path` BFS 最短路径（`MAX_HOPS=10` 防过度搜索），通过 `parent: HashMap` 重建完整路径。
- **deepseek-harness** 的 TypeGraph 仅提供 `childTypeNodeIds()` 子节点遍历能力，文档标注"支持图算法"但无具体实现。
- **opencode** 的 LSP Call Hierarchy 是**单步查询**（`incomingCalls` 返回直接调用者，`outgoingCalls` 返回直接被调用者），不做多跳遍历。
- **pi** 的 `scanBranch` 是树结构扫描（tip → root），在 `compaction` 边界停止，属于树遍历而非图算法。

**laew gap**: L989 [P1] — 无图算法（PageRank/社区发现/最短路径），无法做调用链分析、影响范围评估、依赖追踪。

| 工程 | 实现状态 | 机制 | 代码位置 |
|------|---------|------|---------|
| **atomcode** | 无(自研替代) | tree-sitter CodeGraph 替代 LSP Call Hierarchy | `codeintel/graph.rs` |
| **claude-code** | 无 | 无 LSP 集成 | — |
| **deepseek-harness** | 无 | 无 LSP 集成 | — |
| **openclaw** | 无 | 无 LSP 集成 | — |
| **opencode** | 完整 | `prepareCallHierarchy` + `incomingCalls` + `outgoingCalls` | `packages/opencode/src/lsp/client.ts:443-478` |
| **pi** | 无 | 无 LSP 集成 | — |
| **undici** | 无 | 无 LSP 集成 | — |

**核心发现**:
- **opencode** 是唯一完整实现 LSP Call Hierarchy 的工程：`prepareCallHierarchy` 获取当前位置的函数/方法定义，`incomingCalls` 返回调用者列表（影响范围评估），`outgoingCalls` 返回被调用者列表（依赖追踪）。`callHierarchyRequest` 复用 `prepareCallHierarchy` 结果避免重复请求。

### 2.6 代码图（CodeGraph）

| 工程 | 实现状态 | 节点类型 | 边类型 | 存储方式 |
|------|---------|---------|--------|---------|
| **atomcode** | 完整 | 12 种（Function/Method/Struct/Class/Trait/Interface/Enum/Constant/Variable/Module/Import/TypeAlias） | 5 种（Calls/Imports/Inherits/Implements/References） | 内存双向邻接表（`edges_out`+`edges_in`） |
| **claude-code** | 无 | — | — | — |
| **deepseek-harness** | TypeGraph | 类型表达式节点（keyword/literal/reference/union/intersection 等 18 种） | TypeNodeId 引用边 | 内存图（`declarations`+`nodes`） |
| **openclaw** | 无 | — | — | — |
| **opencode** | 隐式 | LSP Symbol（Function/Class/Method/Interface/Variable/Constant/Struct/Enum） | Definition-References 链 | LSP Server 维护，客户端缓存 |
| **pi** | 无 | — | — | — |
| **undici** | 无 | — | — | — |

**核心发现**:
- **atomcode** 的 CodeGraph 是最完整的代码图实现：`SymbolId = u64` 基于 `(file, name, start_line)` 确定性哈希（跨运行稳定），`#[serde(skip)]` 的 `by_name` 名称索引，`file_symbols` + `file_mtimes` 支持增量更新。注释中的"EDGE CONVENTION (load-bearing, from production)"警告表明这是从生产代码移植的负载约定。
- **deepseek-harness** 的 TypeGraph 是**编译器无关的类型图**——把 TypeScript 类型系统建模为可序列化图，支持跨 face 引用、Source Map、代码生成。这是与 atomcode 代码图互补的另一种图视角。
- **opencode** 的代码图完全依赖 LSP Server 维护（如 TypeScript 的 import 图），客户端通过 `didChange` 通知保持同步，属于"客户端-服务器"分离架构。

**laew gap**: L991 [P1] — 无代码图数据结构，无法做符号级代码分析、调用链追踪、影响范围评估。

### 2.7 实体关系建模

| 工程 | 实现状态 | 实体类型 | 关系类型 | 建模方式 |
|------|---------|---------|---------|---------|
| **atomcode** | 完整 | SymbolNode（12 种 SymbolKind） | Edge（5 种 EdgeKind） | 枚举 + 结构体 |
| **claude-code** | 间接 | Memory / Session / AgentSummary | 跨会话同步关系 | 服务层抽象 |
| **deepseek-harness** | 完整 | RemoteBoundaryModel / InvocationModel | CrossFaceLink / TypeNodeId 引用 | TypeScript interface |

| **pi** | 无 | — | — | — |
| **undici** | 无 | — | — | — |

**核心发现**:
- **atomcode** 的实体关系建模最为显式：`SymbolKind` 枚举定义 12 种实体类型，`EdgeKind` 枚举定义 5 种关系类型，`CodeGraph` 结构体是完整的实体-关系模型。
- **deepseek-harness** 的 `RemoteBoundaryModel` 和 `InvocationModel` 是面向 RPC 边界的实体关系建模——每个 Remote 方法建模为图节点，参数和返回值都是 `RemoteBoundaryModel`（含类型、codec、导入），`InvocationParameterModel` 区分 `json` 和 `lookup` 两种 wire 来源。`CrossFaceLink` 记录 host↔client 的 import/re-export 边。

**laew gap**: L992 [P1] — 无实体关系建模，当前 Agent-Memory 仅存储输入/输出/错误/产物摘要的扁平记录，缺乏符号-调用-依赖的结构化关系网络。

## 三、跨工程核心模式与架构差异

### 3.1 两种技术路线：自研 vs 标准协议

| 路线 | 代表工程 | 优势 | 劣势 |
|------|---------|------|------|
| **自研 CodeGraph** | atomcode | 零依赖、完全可控、深度定制 BFS/最短路径 | 仅覆盖代码领域、tree-sitter 解析开销 |
| **LSP 标准协议** | opencode | 标准化、多语言支持、Server 端维护依赖图 | 单步查询、无多跳遍历、依赖 LSP Server |
| **服务层抽象** | claude-code | 跨会话/跨团队知识同步 | 无显式图结构、依赖外部 API |

### 3.2 图结构的存储策略

| 策略 | 代表工程 | 实现 |
|------|---------|------|
| **内存双向邻接表** | atomcode | `edges_out` + `edges_in` HashMap，支持正反向遍历 |
| **LSP Server 维护** | opencode | Server 端维护 import 图，客户端通过 didChange 同步 |
| **编译器 IR** | deepseek-harness | TypeGraph 作为编译器中间表示，可序列化 |
| **线性链表** | openclaw | `ContextEngineRegistry` 管理压缩策略，非图结构 |
| **树结构** | pi | `scanBranch` tip→root 扫描，compaction 边界停止 |

### 3.3 知识图谱的"构建 vs 同步"二分

- **构建派**（atomcode / opencode）：从源代码/LSP 提取符号和关系，构建代码知识图谱
- **同步派**（claude-code）：不构建图谱，而是同步已有的记忆/知识（`teamMemorySync`）
- **缺失派**（openclaw / pi / undici）：既无构建也无同步，知识管理为线性历史

## 四、laew 现状与 gap 汇总

### 4.1 laew 当前状态

laew 在图数据库与知识图谱维度**完全空白**：
- **无图数据库**: 仅靠 SQLite 关系表（`providers`/`agent_memory`/`session_memory`），无 Neo4j/Memgraph 集成
- **无知识图谱**: `session_memory` 表存储线性历史摘要，无实体关系建模
- **无向量检索**: 无 FAISS/Annoy/HNSW 集成，无 embedding 索引
- **无图算法**: 无 BFS/最短路径/PageRank 等图遍历能力
- **无 LSP Call Hierarchy**: 无 LSP 客户端，无法做标准调用链分析
- **无代码图**: 无 CodeGraph 数据结构，Read/Grep/Glob 工具仅做文本级检索
- **无实体关系建模**: `agent_memory` 表仅存储扁平的输入/输出/错误/产物摘要
- **无语义相似度**: 无 embedding 计算，无 cosine similarity

## 七、关键结论
