## 2. Claude Code：Coordinator + Skill 多维度调度

### 2.1 分类方式

Claude Code 的任务分类是**多维度叠加**的，不存在单一的"任务级别"概念。分类发生在三个层面：

**层面一：Skill 声明级（用户/开发者配置）**

Skill YAML frontmatter 中声明了三个分类维度：

```yaml
---
effort: high | low | medium      # 推理力度
context: fork | inline           # 执行上下文（子 Agent vs 当前对话）
agent: agent-name                # 指定 Agent
model: opus | sonnet | haiku     # 模型选择
---
```

- `effort` 字段直接控制推理力度，三档映射到不同的 token 预算和思考深度
- `context: fork` 启动隔离子 Agent（`runForkedAgent`），`inline` 注入当前对话
- `agent` 字段可指定特定 Agent 角色执行该 Skill

**层面二：Agent Tool 调用级（模型运行时决策）**

模型在对话过程中可通过 `AgentTool` 主动发起子任务：

```
层次 1: Fork 子 Agent    — 轻量级，共享 prompt cache，用于 compact/skill
层次 2: AgentTool        — 模型通过 Agent 工具启动子 Agent（同步/异步）
层次 3: Task 系统        — 后台任务（异步执行 + 结果检索）
层次 4: Team/Swarm       — 多 Agent 团队协作
```

**层面三：Coordinator 编排级（高级模式）**

`coordinatorMode.ts`（19K）是 Claude Code 的高级编排层：
- 消息路由：将用户消息路由到合适的 Agent
- 任务分配：将大任务拆解为子任务分配给多个 Agent
- 结果聚合：收集各 Agent 的结果并汇总
- Agent 间通信：通过 `SendMessageTool` 实现

### 2.2 分类级别

| 维度 | 级别 | 含义 |
|------|------|------|
| effort | high | 全量推理，最大 token 预算 |
| effort | medium | 标准推理 |
| effort | low | 轻量推理，节省 token |
| context | fork | 隔离子 Agent，独立消息上下文，共享 prompt cache |
| context | inline | 注入当前对话，共享完整上下文 |
| Agent 层次 | Fork | 最轻量，用于 compact/skill 等内部任务 |
| Agent 层次 | AgentTool | 模型主动发起，同步/异步 |
| Agent 层次 | Task | 后台异步，结果可检索 |
| Agent 层次 | Team/Swarm | 多 Agent 并发协作 |

### 2.3 拆解粒度

- **Skill 级**：每个 Skill 是一个完整的、可独立执行的任务单元，由 Markdown 正文定义执行步骤
- **Task 级**：`TaskCreateTool` 创建后台任务，`TaskGetTool` 获取结果，粒度由模型决定
- **Team 级**：Swarm 支持多 Agent 并发执行，有独立的后端抽象（InProcess / Remote / LocalShell）

### 2.4 失败处理

- **Hook 拦截**：5 种 Hook 执行器（command / prompt / agent / http / callback）在 `PreToolUse` / `PostToolUse` 阶段拦截
- **Task 生命周期**：`Pending → Running → Completed | Failed | Cancelled`，支持手动停止
- **Swarm 后端**：每种后端有独立的失败处理逻辑
- **协调器**：结果聚合时可处理部分失败

## 3. AtomCode：L2 层按难度派发 + RiskLevel 风险分级

### 3.1 分类方式

AtomCode 采用**三层架构**（L0 Kernel / L1 Capabilities / L2 Coding），任务分类主要发生在 L2 业务层。

**子 Agent 派发的二维分类**：

```rust
// crates/atomcode-capabilities/src/tools/task.rs
const DEFAULT_MAX_CONCURRENT: usize = 3;
```

`TaskTool` 把子任务派发给隔离上下文的子 agent，分类沿两个维度展开：

| 维度 | 选项 | 含义 |
|------|------|------|
| 难度 | fast | 快速执行，轻量模型/少轮次 |
| 难度 | capable | 深度执行，强模型/多轮次 |
| 工具集 | explore | 只读（grep/glob/read），用于代码探索 |
| 工具集 | worker | 可编辑（bash/read/write/edit），用于代码修改 |

主 agent 根据任务性质**按难度选档位**（fast/capable），**按类型选工具集**（explore/worker）。

**工具风险分级（RiskLevel）**：

```rust
fn risk(&self, args: &str) -> RiskLevel { RiskLevel::Safe }
```

`risk()` 是 **arg-aware** 的：`BashTool` 根据命令内容判断 Safe/Risky，`ReadFileTool` 永远 Safe。这是细粒度的风险分类，不是任务难度分类。

**执行策略位图（ExecutionPolicy）**：

```rust
const NO_BUILD: u8 = 1 << 0;
const NO_TEST: u8 = 1 << 1;
const NO_SCRIPT: u8 = 1 << 2;
const NO_SHELL: u8 = 1 << 3;
const NO_VERIFY: u8 = 1 << 4;
```

从用户文本中解析约束（如"不要运行测试"），通过 `TurnExecutionPolicy` 在每轮更新并执行。这是一种**用户意图约束分类**。

### 3.2 分类级别

| 分类类型 | 级别 | 说明 |
|---------|------|------|
| 难度 | fast | 子 agent 快速模式 |
| 难度 | capable | 子 agent 深度模式 |
| 工具集 | explore | 只读探索 |
| 工具集 | worker | 可编辑执行 |
| 风险 | Safe | 自动批准 |
| 风险 | Risky | 需要审批 |
| 执行约束 | NO_BUILD/NO_TEST/... | 用户意图约束（位图） |

### 3.3 拆解粒度

- 子 agent 跑在**独立内核会话**里，结果用 `<task_result>` 包回
- 安全约束：`DenySensitivePaths`（硬拒绝敏感路径）+ `WorkerScopeGate`（confine 写入到声明的 scope，glob 匹配）+ `.git` 目录内部写入被拒绝
- 默认并发数 `DEFAULT_MAX_CONCURRENT = 3`

### 3.4 失败处理

- **VerifyCadenceHook**：编辑后验证纪律——如果 agent 做了代码修改但未验证，注入 nudge 提醒；达到阈值后强制要求验证
- **nuke → stop 熔断**：`repeat_rounds` 粗粒度重复熔断，`REPEAT_NUDGE_AT`（3）时警告，`MAX_REPEAT_ROUNDS`（6）时停止
- **PlanModeGate**：Plan 模式下硬阻断 Risky 工具调用
- **MCP trust 三级判定**：read_only → server_trusted → tool_auto_approved 的逐级降级

## 4. OpenClaw：Harness 选择 + Swarm 调度 + exec-auto-review 风险分类

### 4.1 分类方式

OpenClaw 的任务分类发生在三个独立层面，彼此正交：

**层面一：Harness 选择算法（系统自动）**

```typescript
// selection.ts
selectAgentHarness():
  1. 遍历所有已注册 harness
  2. 对每个调用 harness.supports(context) 判定兼容性
  3. compareHarnessSupport() 按 priority 降序排序
  4. 内置 "openclaw" harness 是兜底
```

`AgentHarness` 是 11 个 capability 的交叉类型，选择是基于 capability 匹配的，不是基于任务难度。

**层面二：exec auto-reviewer 风险分类（执行时）**

```typescript
type ExecAutoReviewDecision =
  | { decision: "allow-once"; rationale: string; risk: "low" }
  | { decision: "ask";       rationale: string; risk: ExecAutoReviewRisk };

type ExecAutoReviewRisk = "unknown" | "low" | "medium" | "high";
```

这是对**命令执行**的风险分类，不是任务分类。`allow-once` 必须伴随 `risk: "low"`，中高风险一律 `ask`。

**层面三：Swarm 调度（并发控制）**

```typescript
type SwarmGroupLane = {
  groupId: string;
  limit: number;              // 最大并发数
  active: Set<string>;
  queue: QueuedSwarmRun[];    // FIFO 等待队列
  pumpScheduled: boolean;
};
```

Swarm 调度器基于 lane 的 FIFO 容量控制，不涉及任务分类，但控制了任务的并发执行节奏。

### 4.2 分类级别

| 层面 | 分类 | 级别 |
|------|------|------|
| Harness 选择 | capability 匹配 | 11 种 capability 组合 |
| Run 终态 | 执行结果 | completed / aborted / blocked / error |
| exec risk | 命令风险 | unknown / low / medium / high |
| exec decision | 审阅决策 | allow-once / ask |
| Spawn 模式 | 启动模式 | run（一次性） / session（保持存活） |
| Context 模式 | 上下文模式 | isolated（不继承） / fork（fork 父上下文） |

### 4.3 拆解粒度

- **spawnSubagentDirect()** 有完整的 9 步流程：输入验证 → Session 准备 → Context Engine 准备 → Attachments 材料化 → Delivery Context 绑定 → Gateway 注册 → Swarm 容量预留 → Launch Request 构建 → Lifecycle Emitter
- **SubagentRunRecord** 有 90+ 字段的完整运行记录
- **代次管理**：`generation` 字段防止旧代次的 run 操作新代次的 session
- **终端完成锁**：`acquireTerminalCompletionLock` 保证同一 runId 只有一个 terminal completion 在处理

### 4.4 失败处理

- **Run 4 种终态**：`completed` / `aborted` / `blocked` / `error`，每种有独立的诊断映射
- **生命周期事件**：`subagent-complete` / `subagent-error` / `subagent-killed` 三种 ended reason
- **执行结果**：`ok` / `error` / `timeout` / `killed` 四种 outcome
- **Harness fallback**：`supports()` 返回 `{ supported: false, fallbackRuntime?: "openclaw" }` 可降级到内置 harness
- **exec auto-review 失败回流**：任何审阅异常都回退到 `ask`（人工审批），永远不静默放行
- **压缩安全超时**：180 秒超时防止压缩长时间阻塞
- **AbortSignal 传播链**：外部信号 → run 级 AbortController → tool 执行 AbortSignal

## 5. OpenCode：Agent 类型系统 + Permission Ruleset 驱动的隐式分类

### 5.1 分类方式

OpenCode **没有显式的任务分类机制**。它的分类是**隐式的**，通过 Agent 类型 + Permission Ruleset 实现：

**内置 Agent 类型**：

```typescript
const agents: Record<string, Info> = {
  build:     { mode: "primary",  permission: { question: "allow", plan_enter: "allow" } },
  plan:      { mode: "primary",  permission: { task: { general: "deny" }, edit: { "*": "deny", ".opencode/plans/*.md": "allow" } } },
  general:   { mode: "subagent", permission: { todowrite: "deny" } },
  explore:   { mode: "subagent", permission: { "*": "deny", grep: "allow", glob: "allow", ... } },
  compaction:{ mode: "primary",  hidden: true, permission: { "*": "deny" } },
  title:     { mode: "primary",  hidden: true, permission: { "*": "deny" } },
  summary:   { mode: "primary",  hidden: true, permission: { "*": "deny" } },
}
```

分类逻辑：
- **build**：默认主 Agent，拥有全部工具权限，可进入 plan 模式
- **plan**：Plan 模式 Agent，禁止编辑（除 `.opencode/plans/*.md`）、禁止派发子任务
- **explore**：子 Agent，只有只读工具（grep/glob/list/bash/read/webfetch/websearch）
- **general**：子 Agent，通用用途，禁止 todo 写入
- **compaction/title/summary**：隐藏 Agent，无工具权限，用于内部辅助任务

**Agent 选择机制**：

```typescript
// 没配置时，取第一个 primary + 非 hidden 的
return Object.values(agents).find(a => a.mode !== "subagent" && !a.hidden)
```

### 5.2 分类级别

| Agent | mode | 可见性 | 工具权限 | 定位 |
|-------|------|--------|---------|------|
| build | primary | 可见 | 全量 | 默认主 Agent |
| plan | primary | 可见 | 只读 + 计划文件编辑 | Plan 模式 |
| explore | subagent | 可见 | 只读探索 | 快速代码探索 |
| general | subagent | 可见 | 全量（无 todo） | 通用子任务 |
| compaction | primary | 隐藏 | 无 | 上下文压缩 |
| title | primary | 隐藏 | 无 | 标题生成 |
| summary | primary | 隐藏 | 无 | 摘要生成 |

### 5.3 拆解粒度

OpenCode 的任务拆解是**单层循环**的：

```typescript
// SessionPrompt.loop()
while (true) {
  const stream = llm.stream(...)
  const result = yield* processor.process(stream)
  switch (result) {
    case "compact": yield* compaction.process(...); continue
    case "stop":    return
    case "continue": return
  }
}
```

没有显式的任务拆解器。模型通过工具调用（如 TaskTool）自行决定是否委派子任务。子 Agent 的选择由 Agent 类型的 `mode` 和 `permission` 决定。

### 5.4 失败处理

- **doom_loop 检测**：连续 3 次相同工具+相同参数 → 触发 `doom_loop` 权限请求
  - 检测条件：连续性 + 同工具 + 同参数（JSON 严格相等）+ 非 pending
  - 处理方式：作为**权限请求**而非硬中断，用户可选择允许或拒绝
  - 用户拒绝 → `ctx.blocked = true` → `process()` 返回 `"stop"` → 循环终止
- **重试机制**：`SessionStatusType` 包含 `retry` 状态，`busy → retry`（如 rate limit）自动重试
- **权限拒绝**：`PermissionV1.DeniedError` 抛出后在 `failToolCall` 中标记为 error
- **溢出处理**：`compact` 结果触发 compaction 后继续循环

## 6. DeepSeek-Harness：Goal 域模型 + round driver 自动续轮

### 6.1 分类方式

DeepSeek-Harness 的任务分类完全围绕 **Goal 域模型** 展开，是所有 6 个项目中最接近"显式任务分类"的设计。

**GoalPhase 状态机**：

```typescript
type GoalPhase = 'active' | 'paused' | 'blocked' | 'complete'
```

状态转换图：
```
create → active → pause → paused
active → block  → blocked
active → complete → complete
paused/blocked/complete → resume → active（需有轮次预算）
```

**Goal 域模型**：

```typescript
interface GoalSnapshot extends GoalRef {
  readonly objective: string        // 目标描述
  readonly phase: GoalPhase         // 当前阶段
  readonly blockedReason?: GoalBlockReason  // 阻塞原因
  readonly maxGoalRounds: number    // 最大轮次数（默认 256）
}
```

**分类触发**：模型通过 `tool-goal` 工具（`get_goal` / `create_goal` / `update_goal`）自主管理 Goal 的生命周期。这不是系统侧的自动分类，而是模型侧的自主决策。

### 6.2 分类级别

| GoalPhase | 含义 | round driver 行为 |
|-----------|------|------------------|
| active | 目标活跃，继续执行 | 自动续轮 |
| paused | 目标暂停 | 不续轮 |
| blocked | 目标被阻塞 | 不续轮，注入 wrapup 上下文 |
| complete | 目标完成 | 不续轮，注入 wrapup 上下文 |

| 阻塞原因 | 含义 |
|---------|------|
| round-limit | 达到 maxGoalRounds 上限 |
| 其他 | 模型自行判断 |

### 6.3 拆解粒度

**round driver 自动续轮机制**：

```typescript
async function drive(state: DriverState): Promise<void> {
  if (!readyToDrive(state)) return

  // 持久化 checkpoint
  if (state.needsCheckpoint) {
    await ctx.sessions.flush(agent.session)
    if (!readyAfterCheckpoint(state)) return
  }

  const goal = currentGoal(state)
  if (goal === undefined || goal.phase !== 'active' || goal.activation !== 'armed') return

  // 轮次上限检测
  if (goal.roundsStarted >= goal.maxGoalRounds) {
    ctx.goals.block(agent, goalRef(goal), {
      code: 'round-limit',
      message: `Goal reached its configured limit of ${goal.maxGoalRounds} rounds.`,
    })
    return
  }

  // 发起下一轮
  const round = goal.roundsStarted + 1
  const content = renderGoalRoundPrompt(goal, round)
  const message = createUserMessage({ content, source: { kind: 'goal', ... } })
  agent.followup(message)
}
```

关键设计：
- **事件源**：每次 Goal 变更写入 `goal/change` session 事件，当前状态通过 fold 事件流重建
- **CAS 保证**：每次变更要求提供当前的 `{id, revision}` ref，不匹配则抛 `GOAL_STALE_REVISION`
- **防竞态**：`requestDrive` 使用 serialized loop 确保同一 agent 上只有一个驱动任务运行
- **双层轮次保障**：`GoalService.resume()` + `round driver.drive()` 都检查 `roundsStarted >= maxGoalRounds`

**wrapup 上下文注入**：

Goal complete/blocked 时，注入一个 plugin source 的 user 消息，告诉模型："目标已完成/阻塞，请总结工作"。

### 6.4 失败处理

- **round-limit 阻塞**：达到 maxGoalRounds（默认 256）时自动 block，注入阻塞原因
- **GOAL_STALE_REVISION**：CAS 不匹配时抛出，防止并发修改
- **GOAL_INVALID_TRANSITION**：resume 时检查轮次预算，不足则拒绝
- **状态转换验证**：`validateSnapshotTransition()` 严格验证每个事件的合法性，fail-loud
- **fold 事件流重建**：不仅重建状态，还验证每个事件的合法性

## 7. Pi：Lane 并发树 + Skill 注入 + drive 模式切换

### 7.1 分类方式

Pi 的任务分类是**最弱的**，没有显式的任务级别概念。它的分类体现在三个机制中：

**机制一：Skill 注入（知识分类）**

Skill 是文本注入，不是工具调用。用最少的抽象（Markdown）覆盖知识管理场景。Skill 不分类任务，但通过 `AgentLane.promptFromTemplate(name, args)` 可以注入特定的任务执行模板。

**机制二：drive 模式（执行模式分类）**

```typescript
drive?: "automatic" | "manual";
```

- `"automatic"`：Harness 自动运行 agent loop 直到完成
- `"manual"`：外部代码逐步驱动（`peekAction()` → `executeAction()`）

这是执行模式的二元分类，不是任务难度分类。

**机制三：Lane 并发（执行单元分类）**

Lane 是 session tree 上的命名分支指针，支持并发执行：

```typescript
interface AgentLane {
  steer(message): void;      // 注入调整消息
  followUp(message): void;   // 追加后续任务
  nextRun(message): void;    // 触发下一轮
  skill(name, args): void;   // 调用 Skill
}
```

Lane 之间的通信通过三种队列：`steer`（注入调整）、`followUp`（追加后续）、`nextRun`（下一轮）。

### 7.2 分类级别

| 机制 | 级别 | 说明 |
|------|------|------|
| drive | automatic | 自动执行到完成 |
| drive | manual | 逐步驱动，TUI 可插入 UI 更新 |
| Lane | main | 主 lane |
| Lane | 自定义 | 命名分支，session tree 分叉 |
| steeringMode | "latest" / "all" | steer 消息覆盖策略 |
| followUpMode | "latest" / "all" | followUp 消息覆盖策略 |

### 7.3 拆解粒度

- **Session Tree**：Session 不是线性历史，而是一棵树。`Session.view(lane)` 返回一个 `SessionTree` 视图，只暴露该 lane 的路径
- **Lane 创建**：`createLane(lane, at)` 在指定 entry 处分叉创建新 lane
- **Lane 导航**：`moveLane(lane, to)` 移动 lane 的 leaf 指针
- **并发限制**：`LaneBusy` 错误确保同一 lane 同时只有一个操作运行
- **事件溯源**：`reduceLaneState` 从持久化记录中重建 LaneState

### 7.4 失败处理

- **LaneBusy 错误**：同一 lane 同时只有一个操作运行，违反时抛出
- **suspended 状态**：崩溃后恢复时暂停，可通过 `resume()` 恢复并 fetch deferred 结果
- **branch summary**：当用户从 lane A 导航到 lane B 时，lane A 的工作被摘要保存
- **Deferred Handle**：异步工具结果（如 Claude extended thinking），支持长时间运行的推理任务

## 8. 设计模式提炼

### 模式 1：显式分类 vs 隐式分类

| 类型 | 项目 | 特点 |
|------|------|------|
| **显式分类** | DeepSeek-Harness（GoalPhase）、Claude Code（effort）、AtomCode（fast/capable） | 系统或用户明确定义任务级别，路由逻辑清晰 |
| **隐式分类** | OpenCode（Agent permission）、OpenClaw（Harness capability）、Pi（drive mode） | 通过权限/能力/模式间接实现分类，灵活但不易理解 |
| **混合分类** | Claude Code（Skill 声明 + 模型决策） | 静态声明 + 动态决策结合 |

**结论**：显式分类对用户更友好，隐式分类对开发者更灵活。laew 的 Yolo 三档分类属于显式分类，方向正确。

### 模式 2：分类触发点的三种位置

| 触发点 | 项目 | 优势 | 劣势 |
|--------|------|------|------|
| **用户侧**（配置/Skill 声明） | OpenCode、Claude Code Skill | 可预测、可控 | 灵活性低 |
| **模型侧**（LLM 自主决策） | DeepSeek-Harness、AtomCode | 灵活、适应性强 | 不可控、可能误判 |
| **系统侧**（算法自动选择） | OpenClaw Harness 选择 | 一致、可靠 | 不够智能 |

**结论**：最佳实践是**用户侧默认 + 模型侧微调**。laew 的 Yolo Agent 属于模型侧分类，建议增加用户侧覆盖机制。

### 模式 3：二维分类优于一维分类

| 维度数 | 项目 | 分类维度 |
|--------|------|---------|
| 一维 | DeepSeek-Harness、OpenCode | GoalPhase 或 Agent 类型 |
| 二维 | AtomCode | 难度 × 工具集 |
| 多维 | Claude Code | effort × context × agent × model |

**结论**：二维分类（难度 × 工具集/执行模式）在复杂度和表达力之间取得最佳平衡。laew 目前是一维（simple/medium/hard），建议增加第二维度。

### 模式 4：自动续轮 vs 人工续轮

| 模式 | 项目 | 机制 |
|------|------|------|
| **自动续轮** | DeepSeek-Harness（round driver）、Pi（nextRun） | 系统自动发起下一轮，用户无感 |
| **人工续轮** | OpenCode（用户输入）、OpenClaw（user message） | 需要用户显式输入 |
| **混合** | Claude Code（Task 后台自动 + 主循环人工） | 部分自动、部分人工 |

**结论**：自动续轮适合长时间任务（如代码重构），人工续轮适合交互式任务。laew 的 Main-Work Agent 拆 WorkFlow 后是线性自动执行，方向正确。

### 模式 5：熔断与防死循环

| 机制 | 项目 | 阈值 | 处理方式 |
|------|------|------|---------|
| maxGoalRounds | DeepSeek-Harness | 256 轮 | 自动 block |
| doom_loop | OpenCode | 3 次精确重复 | 权限请求 |
| MAX_REPEAT_ROUNDS | AtomCode | 6 次重复 | 强制停止 |
| NUDGE_AT | AtomCode | 3 次重复 | 警告提醒 |
| lane 并发限制 | Pi | 1 操作/lane | LaneBusy 错误 |
| Swarm 并发限制 | OpenClaw | 可配置 limit | FIFO 排队 |

**结论**：多层熔断（警告 → 限制 → 强制停止）是最佳实践。laew 目前的熔断机制较弱，应借鉴多层设计。

### 模式 6：失败回流的保守策略

| 项目 | 策略 |
|------|------|
| OpenClaw exec auto-review | 任何审阅异常 → `ask`（人工审批），永远不静默放行 |
| AtomCode RiskLevel | 工具自报风险，kernel 不强制，但 middleware 可拦截 |
| DeepSeek-Harness Goal | CAS 不匹配 → 抛出异常，fail-loud |
| OpenCode doom_loop | 精确重复 → 权限请求（用户选择） |
| Claude Code Hook | PreToolUse 拦截 → 可阻止执行 |

**结论**：保守策略（不确定就问用户）比激进策略（自动放行）更安全。laew 的 Yolo Agent 解析失败时降级为 simple，方向正确但应考虑是否需要通知用户。

## 9. 对 laew 的综合建议

### 9.1 当前状态评估

laew 的 Yolo Agent 已实现：
- 显式三档分类：`simple` / `medium` / `hard`
- 三步识别：目的 → 目标 → 意图
- JSON 结构化输出：`TaskClassification { task_level, goal, intent }`
- 失败降级：解析失败时降级为 simple
- 路由映射：simple → SubAgent、medium → MainWork、hard → Plan

这已经是**中等偏上**的设计水平，超过 OpenCode 和 Pi 的隐式分类，与 DeepSeek-Harness 的 GoalPhase 相当，但不及 Claude Code 的多维度分类和 AtomCode 的二维分类。

### 9.2 P0 建议：增加第二分类维度（难度 × 执行模式）

借鉴 AtomCode 的二维分类，建议 laew 增加"执行模式"维度：

```rust
pub enum ExecutionMode {
    Explore,    // 只读探索（类似 atomcode explore）
    Execute,    // 可编辑执行（类似 atomcode worker）
    Review,     // 代码审查（类似 atomcode review agent）
}
```

TaskClassification 扩展为：

```rust
pub struct TaskClassification {
    pub task_level: TaskLevel,        // simple/medium/hard
    pub execution_mode: ExecutionMode, // explore/execute/review
    pub goal: String,
    pub intent: String,
}
```

路由映射扩展为：
- simple + explore → SubAgent（只读工具集）
- simple + execute → SubAgent（全量工具集）
- medium + explore → MainWork（只读工作流）
- medium + execute → MainWork（全量工作流）
- hard + 任意 → Plan → MainWork → SubAgent

### 9.3 P0 建议：增加用户侧分类覆盖

借鉴 OpenCode 的 `default_agent` 配置和 Claude Code 的 Skill `agent` 字段，建议 laew 增加用户侧覆盖机制：

- CLI 参数：`--level simple|medium|hard` 强制指定任务级别
- TUI 命令：`/level medium` 切换当前会话的默认级别
- Skill 声明：在 CLAUDE.md 中声明 `<!-- laew-level: hard -->` 覆盖特定场景

### 9.4 P1 建议：借鉴 GoalPhase 状态机管理任务生命周期

借鉴 DeepSeek-Harness 的 Goal 域模型，建议 laew 为 hard 级别任务增加生命周期管理：

```rust
pub enum TaskPhase {
    Planning,    // Plan Agent 规划中
    Active,      // Main-Work 执行中
    Paused,      // 用户暂停
    Blocked,     // 阻塞（等待用户输入/外部依赖）
    Complete,    // 完成
    Failed,      // 失败
}
```

配合 round driver 的自动续轮机制，hard 级别任务可以：
1. Plan Agent 输出方案后自动进入 Active
2. Main-Work Agent 拆解 WorkFlow 后自动逐个执行
3. 每个 SubAgent 完成后自动检查是否需要继续
4. 达到轮次上限时自动 Block 并通知用户

### 9.5 P1 建议：增加多层熔断机制

借鉴各项目的熔断设计，建议 laew 增加：

| 层级 | 触发条件 | 处理方式 |
|------|---------|---------|
| 警告层 | SubAgent 连续 3 次相同工具+相同参数 | 注入 nudge 提醒（借鉴 atomcode NUDGE_AT） |
| 限制层 | 同一任务轮次达到 64 | 暂停并通知用户（借鉴 deepseek maxGoalRounds） |
| 强制层 | 同一任务轮次达到 128 | 强制 Block 并要求用户干预 |
| 兜底层 | Yolo 分类 JSON 解析失败 | 降级为 simple + 通知用户（当前已有，建议增加通知） |

### 9.6 P1 建议：SubAgent scope 约束

借鉴 AtomCode 的 `WorkerScopeGate` 和 `DenySensitivePaths`，建议 laew 的 SubAgent-Work 增加：

- **写入范围约束**：Main-Work Agent 拆解 WorkFlow 时声明每个 SubAgent 的写入范围（glob 模式）
- **敏感路径硬拒绝**：`.env` / `id_rsa` / `credentials` / `~/.ssh` 等路径永远不允许 SubAgent 访问
- **`.git` 目录保护**：防止 SubAgent 注入 hooks 或修改 git 配置

### 9.7 P2 建议：增加 Coordinator 编排层

借鉴 Claude Code 的 Coordinator 模式，建议 laew 在 hard 级别任务中增加编排层：

```
用户输入 → Yolo 分类 → hard → Plan Agent
                              → Coordinator Agent
                                 → 拆解为 N 个子任务
                                 → 并发分配给 N 个 SubAgent
                                 → 收集结果并聚合
                                 → Quality-Check
                                 → SessionContext
```

这需要：
- `SendMessageTool`：Agent 间消息传递
- `TaskManager`：后台任务管理（创建/查询/停止）
- 并发控制：类似 OpenClaw 的 `SwarmGroupLane` FIFO 容量控制

### 9.8 P2 借鉴：doom_loop 防死循环

借鉴 OpenCode 的 doom_loop 检测，建议 laew 在 SubAgent-Work 中增加：

```rust
const DOOM_LOOP_THRESHOLD: usize = 3;

fn detect_doom_loop(recent_calls: &[ToolCall]) -> bool {
    recent_calls.len() >= DOOM_LOOP_THRESHOLD
        && recent_calls.windows(DOOM_LOOP_THRESHOLD).all(|window| {
            window.iter().all(|c| c.tool == window[0].tool && c.args == window[0].args)
        })
}
```

触发后：
- simple 级别：自动终止 SubAgent，向 Yolo 报告失败
- medium 级别：暂停 WorkFlow，通知用户
- hard 级别：暂停整个任务，通知用户

### 9.9 汇总：建议优先级矩阵

| 优先级 | 建议 | 难度 | 收益 | 参考项目 |
|--------|------|------|------|---------|
| P0 | 增加第二分类维度（ExecutionMode） | 中 | 高 | AtomCode |
| P0 | 增加用户侧分类覆盖 | 低 | 中 | OpenCode、Claude Code |
| P1 | 借鉴 GoalPhase 状态机 | 中 | 高 | DeepSeek-Harness |
| P1 | 增加多层熔断机制 | 低 | 高 | 全部 6 个项目 |
| P1 | SubAgent scope 约束 | 中 | 高 | AtomCode |
| P2 | Coordinator 编排层 | 高 | 高 | Claude Code |
| P2 | doom_loop 防死循环 | 低 | 中 | OpenCode |
| P2 | 自动续轮 wrapup 注入 | 低 | 中 | DeepSeek-Harness |
