## 0. 维度概述与工程定位

分布式共识是分布式系统正确性的基石。在 Agent CLI 语境下,分布式共识的含义已从传统的"多副本状态机"扩展到:

1. **多 Agent 协调**: coordinator-worker 编排、SubAgent 注册/恢复/选举
2. **事件一致性**: SSE 长连接事件回放、seq 单调递增因果序、Event Sourcing
3. **状态同步**: CRDT 状态复制、Session 跨 Workspace 迁移、多端会话同步
4. **持久化共识**: SQLite WAL + fsync、JSONL append-only 日志
5. **负载均衡**: 平滑加权轮询、origin 隔离、连接池拓扑

本维度与「实时流处理」「会话持久化」「SubAgent 调度与并发」存在交叉,本报告聚焦**协议层与状态机层**的实现。

**替代路径**:
- **pi Chord**: 实现类 CRDT 的 Delta 状态同步,通过 `MutableReplicatedState` + `ReplicatedStateReplica` 实现 Publisher/Replica 模式,sequence 严格连续(`sequence !== this.#sequence + 1` 则清空并重新 hydrate)。这是最接近传统分布式共识的实现。

- **claude-code 序列号**: bridge transport 的 `getLastSequenceNum()` 实现高水位回放,避免 transport 切换时全量重放。

**laew 现状**: laew 无 Raft/Paxos 实现,也无任何替代方案。当前依赖 SQLite 单库,无多节点一致性保障。

### 2.2 核心发现

**唯一实现者**: pi 是唯一实现文件级分布式锁的工程,通过 `proper-lockfile` crate:
- `stale: 30_000`: 锁持有者崩溃后 30 秒自动释放
- `update: LOCK_STALE_MS / 3`: 每 10 秒更新锁文件心跳
- `retries: { retries: Math.ceil(LOCK_WAIT_MS / LOCK_RETRY_MS), ... }`: 固定 25ms 间隔重试

**设计意图**: pi 的实验性 Server + Session Worker 架构需要排他性——同一 `serverId` 只允许一个实例运行,新 server 注册时旧 server 通过 `server_replaced` 消息被替换。

**laew gap**: laew 无分布式锁,未来多 Agent 协作场景(如多个 laew 实例共享同一工作目录)需要此类机制。

## 5. CRDT 数据结构

### 5.1 7 工程对比表

| 工程 | CRDT 实现 | 机制 | 代码位置 |
|------|----------|------|---------|
| atomcode | ❌ 无 | — | — |
| claude-code | ❌ 无 | — | — |
| deepseek-harness | ❌ 无 | — | — |
| openclaw | ❌ 无 | — | — |
| opencode | ❌ 无 | — | — |
| pi | ✅ Delta CRDT | Flush-time change tracking + Path interning | `packages/chord/src/delta/index.ts:435-749` |
| undici | ❌ 无 | — | — |

### 5.2 核心发现

**唯一实现者**: pi 是唯一实现 CRDT 的工程,其 Delta CRDT 实现具有以下特征:

**核心机制**:
1. **MutableReplicatedState(Source of Truth)**:
   - `Tracker<T>` 通过 Proxy 追踪变更(flush-time change tracking)
   - `publish()` 递增 `sequence`,发射 ops + 新值
   - 订阅者收到 `hydrate`(首次)或 `update`(后续)投递

2. **ReplicatedStateReplica(远端副本)**:
   - 严格顺序:`sequence !== this.#sequence + 1` 则清空并抛错(触发重新 hydrate)
   - base batch:`["r", value]` 作为完整快照,可独立恢复
   - immutable updates:`applyImmutable` 不修改旧值,返回新值(结构共享)

3. **Flush-Time Change Tracking**:
   - **Proxy 追踪**:通过 Proxy 拦截所有读写操作,记录 dirty path
   - **baseline 同步**:`syncBaseline` 尝试通过引用共享(strings/scalars/array appends)避免 replay
   - **字符串优化**:`overlap()` 函数检测字符串重叠,生成 `["t", path, n] + ["a", path, tail]` 而非完整替换
   - **数组优化**:区分 `append` / `diff` / `replace` 三种变更模式

**设计意图**: Chord 的 Replicated State 支持增量更新与断线恢复,是 pi 的 Server + Session Worker + Coordinator 分布式架构的基石。

**laew gap**: laew 无 CRDT 实现。未来若实现多端会话同步(如 Web UI + CLI 共享同一 Session),CRDT 是解决冲突合并的理想选择。

## 6. 事件溯源(Event Sourcing)

### 6.1 7 工程对比表

| 工程 | 事件溯源 | 机制 | 代码位置 |
|------|---------|------|---------|
| atomcode | ❌ 无(仅有 broadcast 事件广播) | `tokio::sync::broadcast` 容量 1024 | `live_hub.rs:187-200` |
| claude-code | ❌ 无 | — | — |
| deepseek-harness | ❌ 无 | — | — |
| openclaw | ✅ 完整实现 | SQLite 流事件存储 + 序列号分配 | `acp-parent-stream-store.sqlite.ts:23-72` |
| opencode | ✅ 完整实现 | EventTable + EventSequenceTable + replay | `event-v2-bridge.ts` / `workspace.ts` |
| pi | ✅ JSONL 事务日志 | append-only 日志 + 多类型 write | `jsonl/io.ts:66-78` |
| undici | ❌ 无(仅有 Event Sourcing 简化版) | HTTP 请求/响应 cassette 持久化 | 测试框架 |

### 6.2 核心发现

**三实现者**: openclaw / opencode / pi 实现了事件溯源,但形态各异:

**openclaw 的流事件溯源**:
- `recordAcpParentStreamEvents` 记录所有子 Agent 流事件
- 序列号分配:`SELECT MAX(seq) WHERE session_id AND run_id` 获取当前最大序号
- 批量插入:`prepared.map((entry, index) => ({ seq: firstSeq + index, ... }))`
- 原子提交:`runOpenClawAgentWriteTransaction` 保证事件持久化
- JSON 序列化:`event_json` 字段存储原始事件,支持回放

**opencode 的 Event Sourcing + Replay**:
- `EventV2Bridge` 是事件总线,`publish(def, data)` 写入 `EventTable` + `EventSequenceTable`
- `replay(event, opts)` 反序列化事件,`publish: true` 触发本地订阅
- `ownerID` 标记事件来源,防止回环
- `seq` 是 aggregate 级单调递增,保证因果序
- 丢失检测:`if (done[id] < state[id])` 表示有缺失事件需补齐

**pi 的 JSONL 事务日志**:
- 每个 Session 是一个 **append-only JSONL 日志**
- 每行是一个事务(可包含多个 write)
- write 类型:`entry` / `usage` / `value(set/delete)` / `list(append/delete)`
- `serializeJsonlTransaction(writes)` / `parseJsonlTransaction(line)` 实现序列化/反序列化

**对比**:
| 维度 | openclaw | opencode | pi |
|------|---------|---------|-----|
| 存储 | SQLite | EventTable | JSONL 文件 |
| 序列号 | session_id + run_id 级别 | aggregate 级别 | 无(append-only) |
| 回放 | JSON 反序列化 | `events.replay()` | 逐行 parse |
| 原子性 | SQLite 事务 | SQLite 事务 | tmp + rename |

**laew gap**: laew 当前记忆系统为状态快照,无法回放历史。openclaw 的流事件溯源和 opencode 的 Event Sourcing 是值得借鉴的范式。

## 10. 核心发现与洞察

### 10.1 核心发现

**发现 1: 7 工程无一实现经典 Raft/Paxos/Gossip**

这是 Agent CLI 的工程定位决定的——它们是单 Agent 框架,不是分布式数据库。但 pi 的 Chord Replicated State 和 opencode 的 SSE 事件同步已经触及了分布式一致性的核心问题。

**发现 2: 事件溯源是最普遍的"类共识"机制**

openclaw / opencode / pi 都实现了事件溯源,但形态各异:
- openclaw: SQLite 流事件 + 序列号
- opencode: EventTable + Replay + 因果序
- pi: JSONL 事务日志

这反映了一个趋势:**Agent CLI 需要可追溯的历史记录**,事件溯源是实现这一目标的理想范式。

**发现 3: CRDT 是 pi 的独特优势**

pi 的 Delta CRDT(1268 行)是唯一一个实现 CRDT 的工程。其 Flush-time change tracking + Path interning 设计支持增量更新与断线恢复,是 pi 分布式架构的基石。

**发现 4: 分布式锁是 pi 的实验性需求**

pi 的 Server + Session Worker 架构需要排他性——同一 `serverId` 只允许一个实例运行。proper-lockfile 的 stale + update + retries 机制是文件级分布式锁的经典实现。

**发现 5: 负载均衡在 undici 中达到生产级**

undici 的 Nginx SWRR 平滑加权轮询虽然不是分布式共识,但展示了分布式系统中负载均衡的最佳实践——GCD 步长递减、故障权重惩罚、恢复权重回退。

### 14.2 关键设计模式

1. **事件溯源三态**: openclaw(SQLite 流事件) / opencode(EventTable + Replay) / pi(JSONL 事务日志)
2. **CRDT 增量同步**: pi 的 Delta CRDT + Flush-time change tracking + Path interning
3. **文件级分布式锁**: pi 的 proper-lockfile + stale + update + retries
4. **序列号驱动**: claude-code 高水位回放 / opencode seq 因果序 / openclaw 流事件序号
5. **负载均衡**: undici 的 Nginx SWRR + origin 隔离 + connectionError 立即移除
