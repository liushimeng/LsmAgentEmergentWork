## 一、维度概述

实时流处理是生产级 Agent CLI 的**核心基础设施层**——LLM 响应消费、SubAgent 事件分发、多端会话同步、TUI 实时渲染都依赖流式语义。本维度聚焦 8 个子维度，横向对比 7 个工程在流处理领域的实现深度。

**关键发现**：
- **无工程实现 Kafka/Flink 集成**——Agent CLI 场景以进程内流处理为主，分布式流处理留给外部基础设施
- **opencode 在事件溯源 + 全局事件总线 + 流管道三方面最完整**——EventV2Bridge + GlobalBus + StreamTransport 构成完整的事件驱动架构
- **atomcode 在流重建契约 + 滚动窗口限流上独树一帜**——契约符合性框架将流处理正确性显式化
- **openclaw 在事件溯源存储 + 父-子流中继上最成熟**——SQLite 持久化 + 序列号分配 + 原子提交
- **undici 在底层流控（HTTP/2 流级背压 + WebSocket 帧级处理）上最深**——双向背压传播 + SendQueue 双路径
- **pi 在流式 JSON 修复 + JSONL 事务日志上最严谨**——parseJsonWithRepair + append-only 事务日志

### 2.2 核心发现

**共性认知**：7 个工程均不直接集成 Kafka/Flink。Agent CLI 的典型部署形态是单进程/单节点，流处理需求通过**进程内队列**（broadcast channel / AsyncGenerator / Effect Stream / Lane）满足。分布式消息队列留给外部基础设施（如 opencode 的 SSE 长连接同步、pi 的实验性 Server 架构）。

**atomcode 的 broadcast 通道**：`tokio::sync::broadcast` 容量 1024，支持多订阅者，WebUI 的 `/live` SSE 端点允许多浏览器订阅同一会话。`cursor` 单调递增保证事件序，`generation` 检测 stale binding。

**opencode 的 Effect Stream**：`Stream<LLMEvent>` 是拉取模型，`Queue.offerAll` 桥接 AI SDK 的 ReadableStream。15 种统一事件类型封闭协议差异。

**pi 的 Lane 并发模型**：串行 mutation line + 并行 drive，`deliveryTail: Promise.resolve()` 保证更新串行投递，天然背压。

### 2.3 laew gap

- **L894 [P2]**：laew 无 Kafka/Pulsar 消息队列集成，当前 SubAgent 事件分发仅靠 `tokio::spawn` + Semaphore
- **L895 [P2]**：laew 无 Flink/Spark Streaming 式流处理引擎，缺乏有状态流计算能力

| 事件时间处理 | 无 | 无 | 无 | 无 | `seq` 单调递增 | 无 | 无 |

### 3.2 核心发现

**atomcode 的滚动窗口限流**（`rate_limit.rs:84-115`）：
- 基于 CodingPlan 配额窗口的智能限流决策
- 仅当窗口被服务器标记 `quota_exhausted` 时才暂停
- 选择最小 reopens 的窗口
- 瞬态 429（网关负载脱落）退化为 hint 的短 retry-after
- 注释警告："5h ROLLING window's countdown is large at almost all times regardless of remaining quota"

**deepseek-harness 的 write-behind 合并**（`writeBatchMaxDelayMs: 200`）：
- 高频流式事件（如 `assistant/chunk`）在 200ms 窗口内合并
- 合并后的事件打包成 packed row 写入 SQLite
- 减少物理写次数，让写比例于"新 durable batch"而非单个事件

**opencode 的 flush 节流**：
- 1 秒节流合并高频事件（如 `message.updated` 连续触发）
- `flush` 是幂等操作：即使重复发送，远端按 event ID 去重

**pi 的尾部窗口**（`bash.ts:82-86`）：
- `retain: "tail"` 实现尾部窗口（只保留最后 N 行/字节）
- `spill: true` 将头部溢出到磁盘文件

### 3.3 laew gap

- **L896 [P2]**：laew 无 tumbling/sliding session window，当前无窗口计算能力
- **L897 [P2]**：laew 无滚动窗口限流，当前仅简单 retry-after（第十二轮已修复基础退避，但无窗口感知）
- **L898 [P2]**：laew 无 write-behind 事件合并，高频事件逐次写入 SQLite

### 5.2 核心发现

**openclaw 的 CQRS 分离**（声明式）：
- 命令（请求）与查询（事件监听）分离
- 命令队列支持分组容量限制（`command-queue.capacity-groups.ts`）

### 6.2 核心发现

**undici 的双向背压传播**（`api-stream.js:183-193` + `api-pipeline.js:206-213`）：
- StreamHandler：可写端背压 → `controller.pause()` 暂停读取响应
- PipelineHandler：可读端背压 → `body.pause()` 暂停 body 读取
- HTTP/2 流级别背压：`stream.pause()` 只影响当前流，不影响同胞流

**opencode 的 Buffer 截断**（`shell.ts:428-558`）：
- `keep = limits.maxBytes * 2` 是 buffer 上限
- 超出 `keep` 时 `list.shift()` 丢弃最老 chunk
- `tail(raw, limits.maxLines, limits.maxBytes)` 从末尾截取，保留最新输出
- UTF-8 安全截断：`while (start < buf.length && (buf[start] & 0xc0) === 0x80) start++`

**pi 的 Shell 输出背压**（`nodejs.ts:529-558`）：
- `spillStream.write(chunk)` 返回 false 时设置 `spillBackpressured = true`
- `drain` 事件触发后恢复
- 防止内存无限增长（backpressure 从磁盘传播到进程）

**openclaw 的背压测试矩阵**（`code-mode.backpressure.test.ts:65-100`）：
- `limit=16, count=20`：正常溢出
- `limit=2, count=20`：严格限制
- `limit=1, count=20, race=true`：串行竞争
- `limit=16, count=144`：大量任务
- 验证 `active <= limit` 始终成立

**atomcode 的 UI 解耦**（`tuix/src/lib.rs:656`）：
- "we never want the upgrade task to block on UI backpressure"
- 升级任务与 UI 渲染解耦，通过异步通道和独立任务实现

**claude-code 的 AsyncGenerator 背压**：
- `yield createSystemAPIErrorMessage(...)` 实时上报重试状态
- `yield` 让调用方决定消费节奏

### 6.3 laew gap

- **L904 [P1]**：laew 无背压传播机制，当前仅限制并发数（`max_parallel_workflows`），缺乏速率反馈
- **L905 [P2]**：laew 无 Shell 输出背压，Bash 工具无流式输出限流（依赖第十二轮已修复的 timeout）

## 七、SSE 解码

### 7.1 七工程对比表

| 维度 | atomcode | claude-code | deepseek-harness | openclaw | opencode | pi | undici |
|------|----------|-------------|------------------|----------|----------|-----|--------|
| SSE 解析 | 三层超时体系 | `parseSSEFrames` 增量解析 | `eventsource-parser` + `[DONE]` 检测 | 无 | `parseSSE` 逐行解析 | `iterateSseMessages` 状态机 | 无 |
| 空闲看门狗 | `idle_timeout: 120s` | `LIVENESS_TIMEOUT_MS: 45_000` | 无 | 无 | 无 | 无 | 无 |
| 重连机制 | `MAX_STREAM_ATTEMPTS: 3` | `RECONNECT_GIVE_UP_MS: 600_000` | 无 | 无 | 指数退避 `2^attempt` | 无 | 无 |
| 截断检测 | 无 | 无 | `STREAM_CLOSED` 抛错 | 无 | 无 | 无 | 无 |
| 事件型 SSE | Anthropic 事件型 | event/id/data 三字段 | 严格模式 | 无 | `data:` / `id:` / `retry:` | W3C EventSource | 无 |

### 7.2 核心发现

**atomcode 的三层超时体系**（`anthropic.rs:68-75`）：
- `connect_timeout`（30s）：TCP/TLS 握手
- `open_timeout`（90s）：等待响应 HEAD（首字节 TTFB）
- `idle_timeout`（120s）：字节流空闲（无数据到达）
- 注释强调："no overall request timeout is set here (deliberately: a streaming response must not capped)"
- 字节级空闲看门狗检测"接受连接但永不响应"的网关

**claude-code 的 SSE 帧增量解析器**（`SSETransport.ts:57-100`）：
- 增量解析：处理 TCP 分包——未完整帧保留在 `remaining` 中等待下次 `read`
- SSE 完整实现：event/id/data 三字段 + comment 识别 + 头部空格剥离
- 背压感知：`LIVENESS_TIMEOUT_MS = 45_000`（server 15s 发 keepalive，45s 无数据判死）
- 10min 重连预算：`RECONNECT_GIVE_UP_MS = 600_000`
- 永久码：401/403/404 不重试

**deepseek-harness 的 SSE 严格解析**（`sse.ts:28-40`）：
- 使用 `eventsource-parser` 处理 SSE 帧边界（空行分隔、UTF-8 重组、CRLF/BOM、多 `data:` 拼接）
- EOF 前未收到 `[DONE]` 抛 `STREAM_CLOSED`——这是截断检测，而非把不完整尾部当有效载荷
- 严格模式把"未终止的 SSE"当作错误，避免静默数据损坏

**opencode 的 SSE 长连接**：
- `connectSSE` 发起 `text/event-stream` 请求，返回 `Stream<Uint8Array>`
- `parseSSE` 逐行解析 `data:` / `id:` / `retry:` 字段，空行触发事件发射
- `syncWorkspaceLoop` 无限循环：`connectSSE` → `syncHistory` → `parseSSE` → 失败后 `Effect.sleep(2^attempt)` 退避
- Workspace 跨机器同步依赖 SSE 长连接，断连后必须自动重连

**pi 的 SSE 状态机**（`anthropic-messages.ts:313-462`）：
- 严格遵循 SSE 规范（W3C EventSource）
- 处理 `\r\n` / `\n` / `\r` 三种换行符
- `data` 字段多行拼接（`\n` 分隔）
- `AbortSignal` 可中断流

### 7.3 laew gap

- **L907 [P1]**：laew 无 SSE 帧增量解析器（仅整块 HTTP 响应），TCP 分包场景可能丢帧
- **L908 [P1]**：laew 无字节级空闲超时，当前依赖 reqwest 默认 90s 空闲超时
- **L909 [P1]**：laew 无 SSE 截断检测，未终止的 SSE 可能被静默处理
- **L910 [P2]**：laew 无 SSE 长连接重连机制，断连后无法自动恢复

### 8.2 核心发现

**opencode 的 GlobalBus**（`bus/global.ts:23`）：
- `GlobalBus` 是 `EventEmitter` 单例，`emit("event", event)` 触发所有订阅
- `GlobalEvent` 结构：`{ directory?, project?, workspace?, payload }`
- 自动注入 ID：`if (!("id" in event.payload)) event.payload.id = event.payload.syncEvent?.id ?? Identifier.create("evt", "ascending")`
- 跨模块通信解耦：workspace sync / session update / permission ask 都通过 GlobalBus
- `directory` / `project` / `workspace` 三元组实现事件路由（只发给相关订阅者）
- `Identifier.create("evt", "ascending")` 保证事件 ID 单调递增

**opencode 的 Stream Transport**（`stream.transport.ts:1463`）：
- `createLayer` 创建长生命周期 `SessionTransport` service
- `events = sdk.global.event({ signal })` 订阅全局事件流
- `applyEvent(event)` 处理 10+ 种事件类型：`message.updated` / `message.part.delta` / `session.status` / `permission.asked` / `question.asked` 等
- `reduceSessionData` 将事件归约为 `SessionData` 状态，输出 `StreamCommit[]` 和 `FooterPatch`
- `buffered` 数组缓存 booting 阶段事件，`drainBuffered` 在 bootstrap 完成后处理
- `tick` 计数器防止 stale idle event 错误完成新 turn

**atomcode 的 LiveViewHub**（`live_hub.rs:187-200`）：
- `tokio::sync::broadcast` 通道容量 1024，支持多订阅者
- `LiveObservation` 包含 `binding_id/generation/cursor/event`
- `cursor` 单调递增保证事件序
- `generation` 检测 stale binding（运行时已重启但订阅者仍持有旧 binding）
- WebUI 的 `/live` SSE 端点允许多个浏览器订阅同一会话的实时事件流

**deepseek-harness 的 Cordis 事件系统**：
- `llm/stream` 是 waterfall 类型事件（Cordis 框架）
- 监听器可以调用 `next()` 到达下游，或自行 yield chunks 短路
- 支持 retry、replay、routing 拦截
- 让插件在不修改 adapter 的情况下拦截/修改/短路模型流式调用

### 8.3 laew gap

- **L911 [P1]**：laew 无全局事件总线，当前模块间通信靠直接函数调用，缺乏解耦
- **L912 [P1]**：laew 无事件路由机制，无法按 directory/project/workspace 过滤事件
- **L913 [P2]**：laew 无事件排序保证，当前无 `cursor` / `seq` 单调递增机制

### 10.2 核心发现

**undici 的 WebSocket 帧解析状态机**（`receiver.js:25-305`）：
- `INFO` → `PAYLOADLENGTH_16/64` → `READ_DATA` → `INFO` 循环
- 控制帧（close/ping/pong）立即处理
- 数据帧累积到 fragments，FIN=1 时合并
- 压缩帧异步解压（回调模式）

**undici 的 SendQueue**（`sender.js`）：
- 快速路径：socket 空闲时直接 write + cork/uncork 批量发送
- 慢速路径：socket 忙时入队（FixedQueue），等待 `#run` 消费
- Blob 需要异步 `arrayBuffer()` 转换，使用 promise 链
- 这是背压控制的典型实现

**undici 的 permessage-deflate**（`permessage-deflate.js`）：
- 每个 chunk 写入 InflateRaw
- FIN=1 时追加 `0x00 0x00 0xFF 0xFF` 尾标（RFC 7692）
- `flush` 后拼接所有 buffer
- 超过 maxPayloadSize 时立即终止

**claude-code 的 SessionsWebSocket**（404 行）：
- 双运行时适配：Bun 用 `globalThis.WebSocket` + 事件监听；Node 用 `ws` 包 + `.on()` 回调
- JSON 消息解析：宽松的 `isSessionsMessage` 探测（仅检查 `type` 字段为字符串）
- 指数退避重连 + ping/pong 心跳

**openclaw 的 WebSocket 帧协议**（`protocol-client.ts` 565 行）：
- 帧类型识别：`isGatewayEventFrame` / `isGatewayResponseFrame` 双通道分发
- TLS 指纹 pinning：`secureConnect` 事件中校验 `socket.getPeerCertificate()?.fingerprint256`
- Challenge-Response 认证：服务端在 `connect.challenge` 事件中下发 `nonce` + `ts`

## 十一、流重连与容错机制（补充维度）

### 11.1 七工程对比表

| 维度 | atomcode | claude-code | deepseek-harness | openclaw | opencode | pi | undici |
|------|----------|-------------|------------------|----------|----------|-----|--------|

| 元数据缓冲 | `pending_metadata` | 无 | 无 | 无 | 无 | 无 | 无 |

### 11.2 核心发现

**atomcode 的流重连机制**（`ollama.rs:171-200`）：
- 流读取失败时最多 3 次透明重连
- 关键约束：仅在未发射 replay-sensitive 输出前可重放整个请求
- 元数据可重复，内容和工具数据不可
- 注释解释："a gateway resetting connections under load can drop more than one attempt before a healthy backend answers"
- `pending_metadata` 缓冲元数据直到首个 replay-sensitive 事件确认当前尝试有效

**claude-code 的重连预算**：
- `RECONNECT_GIVE_UP_MS = 600_000`（10 分钟重连预算）
- 永久码 401/403/404 不重试

**opencode 的无限重连**：
- `syncWorkspaceLoop` 无限循环：`connectSSE` → `syncHistory` → `parseSSE` → 失败后 `Effect.sleep(2^attempt)` 退避
- Workspace 跨机器同步依赖 SSE 长连接，断连后必须自动重连

### 11.3 laew gap

- **L920 [P1]**：laew 无流重连机制，当前流读取失败直接报错
- **L921 [P2]**：laew 无 replay-sensitive 区分，重放语义不明确

4. **Event Sourcing + Replay**（opencode）：`EventV2Bridge` + `EventSequenceTable`，`seq` 单调递增保证因果序
5. **GlobalBus 路由**（opencode）：`directory/project/workspace` 三元组实现事件路由，`Identifier.create("evt", "ascending")` 保证 ID 单调递增
6. **Stream Transport 管道**（opencode）：1463 行事件流管道，`reduceSessionData` 归约事件为状态

8. **双向背压传播**（undici）：`api-stream.js` + `api-pipeline.js` 实现可写端/可读端双向背压
9. **SendQueue 双路径**（undici）：快速路径直接 write + cork/uncork，慢速路径入 FixedQueue
