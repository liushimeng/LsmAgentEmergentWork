## 1. 横向对比总览表

### 1.1 核心机制对比

| 维度 | Claude Code | AtomCode | OpenClaw | OpenCode | DeepSeek-Harness | Pi |
|------|-------------|----------|----------|----------|-----------------|-----|
| **循环入口** | `src/query.ts` query() | `crates/atomcode-kernel/src/agent.rs` run_turn() | `src/gateway/agent-turn/` turn 路由 | `packages/opencode/src/session/prompt.ts` SessionPrompt.loop() | `packages/goal/goal-round-driver` round driver | `packages/agent/src/agent-loop.ts` runLoop() |
| **循环结构** | while + 递归 compact | 单层 loop + 多层计数器 | Harness turn 状态机 | while(true) + Effect generator | while(true) serialized loop | 双层 while（外层 followUp + 内层 tool calls） |
| **驱动方式** | 查询驱动（query source） | 轮次驱动（round++） | Turn 路由驱动 | 消息驱动（LoopInput） | Goal 状态机驱动 | 消息队列驱动（steer/followUp/nextRun） |
| **终止条件** | 无 tool_use / compact 触发 / 用户 stop | round_cap / MAX_REPEAT_ROUNDS(6) / 空响应 | terminal: completed/aborted/timed_out/error | ctx.blocked / process()返回"stop" | maxGoalRounds(256) / goal complete | 无 pendingMessages / terminate 标记 |
| **工具结果回填** | tool_result 消息追加 | 融合器合并 + cap_tool_result 截断 | callTool → result 事件 | processor → tool_result part | round driver 注入下一轮 prompt | emit ToolResultEvent |
| **续轮机制** | Auto-Compact 后续轮 | TRUNCATION_RESUME_NUDGE（最多 4 次） | turn attempt 重试 | 无显式续轮（单次 loop 内） | round driver 自动续轮（核心特性） | followUp 队列驱动外层循环 |
| **流式耦合** | 流式事件驱动 compact | 流式 + 截断检测 | WebSocket/SSE 双工 | Effect Stream 全栈 | Cordis 事件流 | AssistantMessageEventStream |
| **防死循环** | 时间/工具数/token 阈值触发 compact | ToolLoopPolicy(3 警告→4 停止) + MAX_REPEAT_ROUNDS(6) | 超时 + 外部 abort | doom_loop 检测（3 次重复） | maxGoalRounds 硬上限 | LaneBusy + 队列容量限制 |

### 1.2 循环复杂度光谱

```
简单（单轮主导）                                    复杂（多轮自适应）
←─────────────────────────────────────────────────────────────────────────→
OpenCode(单loop)  Pi(双层)  AtomCode(单层+熔断)  Claude Code(compact递归)  OpenClaw(turn状态机)  DeepSeek(round driver)
```

laew 的 `run_session` 循环位于光谱的**简单端**（单层 while + 工具执行），与 OpenCode 接近。

### 1.3 终止策略光谱

```
隐式（模型自主）                                    显式（规则硬限）
←─────────────────────────────────────────────────────────────────────────→
Claude Code(无tool_use)  OpenCode(blocked)  Pi(terminate)  AtomCode(MAX_REPEAT)  OpenClaw(terminal)  DeepSeek(maxGoalRounds)
```

laew 当前仅有「无 tool_use 则退出」的隐式终止，缺乏显式硬限。

## 2. AtomCode：L0 中立循环 + 多层熔断

### 2.1 设计哲学

AtomCode 的 L0 Kernel 核心设计原则：**Agent 循环永远不触及协议细节，差异封闭在 `LlmProvider` trait 内部**。循环只关心「发消息→收响应→处理工具→决定是否继续」，不感知 Anthropic/OpenAI 差异。

这与 laew 的 `src/agent/mod.rs` 设计高度一致——laew 的 Agent 循环同样不接触协议细节，协议差异封闭在 `llm/anthropic.rs` 与 `llm/openai.rs` 两个客户端内部。

### 2.2 Agent 主循环状态机

入口在 `RunningAgent::run_turn()`（`crates/atomcode-kernel/src/agent.rs:1850`），是一个复杂的 `loop`，内含多层计数器/融合器：

**轮次循环结构**：
```
loop {
  round += 1
  // 1. 检查 round_cap（可选的交互式 checkpoint）
  // 2. 构造请求（融合历史 + 系统提示 + 工具定义）
  // 3. 调用 LLM provider（含 provider_retry）
  // 4. 解析响应（text + tool_use）
  // 5. 执行工具调用
  // 6. 融合工具结果到上下文
  // 7. 检查续接/截断/溢出/空响应
  // 8. 决定是否继续循环
}
```

**关键计数器**：
- `round: u32` — 当前轮次（1-based）
- `repeat_rounds: u32` — 粗粒度重复熔断
  - `REPEAT_NUDGE_AT = 3`：第 3 次重复时注入警告 nudge
  - `MAX_REPEAT_ROUNDS = 6`：第 6 次重复时强制停止
- `provider_retry: u32` — provider 级重试，最多 3 次，退避 3/6/9s
- `truncation_resume: u32` — 截断续接计数，最多 4 次

### 2.3 多层熔断机制

AtomCode 的防死循环采用**多层独立计数器**，每层有独立上限和策略：

| 策略名 | 触发条件 | 警告阈值 | 停止阈值 |
|--------|---------|---------|---------|
| **ToolLoopPolicy** | 同一工具调用重复 | 3 次（nudge） | 4 次（stop） |
| **MAX_REPEAT_ROUNDS** | 同一 round signature 重复 | 3 次（nudge） | 6 次（stop） |
| **provider_retry** | ProviderError::retryable | — | 3 次 |
| **truncation_resume** | finish_reason=length | — | 4 次 |

**nudge 机制**：达到警告阈值时，不直接停止，而是向上下文注入一条「你似乎在重复，请换策略」的提示，给模型自我纠正的机会。只有达到停止阈值才强制中断。

### 2.4 截断续接

当 `finish_reason=length`（输出被截断）时，AtomCode 注入 `TRUNCATION_RESUME_NUDGE` 提示，让模型从断点继续。最多 4 次续接，避免无限截断循环。

**对 laew 的借鉴**：laew 当前无截断续接机制，长输出被截断后直接丢失。

### 2.5 工具结果处理

`cap_tool_result()` 对工具输出做 HEAD+TAIL 截断（保留首尾各半），中段插入省略标记。默认上限 `DEFAULT_MAX_TOOL_RESULT_BYTES = 64 KiB`。

**对 laew 的借鉴**：laew 的 Bash 工具输出无截断，长输出会直接撑爆上下文。

## 3. Claude Code：Query 引擎 + 四级压缩管线

### 3.1 设计哲学

Claude Code 的循环以**查询（query）**为核心驱动单位，每次用户输入触发一次 `query()` 调用。循环内部通过**四级压缩管线**动态管理上下文，使得循环可以持续很多轮而不溢出。

### 3.2 Query 主循环

入口在 `src/query.ts` 的 `query()` 函数。核心流程：

```
query(source, messages, model, options) {
  while (true) {
    // 1. 检查是否需要压缩（四级管线）
    if (shouldAutoCompact(messages, model, source)) {
      messages = await compactConversation(messages)
    }
    // 2. 构造请求
    const request = buildRequest(messages, model, options)
    // 3. 调用 API（流式）
    const stream = await client.stream(request)
    // 4. 处理流式事件
    for await (const event of stream) {
      switch (event.type) {
        case 'content_block_delta': ...
        case 'tool_use': ...
        case 'message_delta': ...
      }
    }
    // 5. 执行工具调用
    if (hasToolCalls) {
      const results = await executeToolCalls(toolCalls)
      messages.push(...results)
      continue  // 继续循环
    }
    // 6. 无工具调用 → 退出循环
    break
  }
}
```

### 3.3 四级压缩管线

Claude Code 的循环之所以能持续很多轮，核心是四级压缩：

| 级别 | 触发条件 | 算法 | 保留 |
|------|---------|------|------|
| **Time-Based Microcompact** | 间隔 > gapThresholdMinutes | 替换为常量消息 | 最近 1 个工具结果 |
| **Cached Microcompact** | 工具结果数 > triggerThreshold | cache_edits 指令删缓存 | keepRecent 个最近结果 |
| **Auto-Compact** | token 使用量超阈值 | LLM 生成摘要 | system prompt + 摘要 + 附件 |
| **Session Memory Compact** | Session Memory 过大 | 专用压缩 | 关键记忆 |

**关键设计洞察**：
- 压缩前执行 `PreCompact` hooks
- 压缩后执行 `postCompactCleanup`
- 使用 `grouping.ts` 将消息按 API 轮次分组
- `COMPACT_MAX_OUTPUT_TOKENS` 控制压缩后最大输出

### 3.4 终止条件

- **无 tool_use**：模型未请求工具调用，循环自然结束
- **Auto-Compact 触发**：压缩后继续循环（不终止）
- **用户 stop**：外部中断
- **Hook 拦截**：PreToolUse/PostToolUse hooks 可阻断

### 3.5 流式与循环的耦合

Claude Code 的循环与流式深度耦合：
- 流式事件驱动工具调用检测
- `message_delta` 中的 `finish_reason` 决定后续行为
- 异步 Hook 协议支持后台执行不阻塞主循环

## 4. DeepSeek-Harness：Goal 域 + round driver 自动续轮

### 4.1 设计哲学

DeepSeek-Harness 拥有 6 个项目中最完整的**目标管理系统**。循环不是简单的「执行到无工具」，而是围绕 Goal 的生命周期驱动——Goal 有完整的状态机，round driver 自动续轮直到目标完成或达到轮次上限。

### 4.2 Goal 状态机

```
created → active → paused/blocked/complete
              ↑         ↓
              └── resume ┘
```

- `maxGoalRounds`：最大轮次限制（默认 256）
- `roundsStarted`：已启动轮次计数
- 支持子 Goal（嵌套目标）
- 进度追踪与完成判定

### 4.3 round driver —— 自动续轮机制

round driver 是 DeepSeek 最独特的循环机制，是一个 Cordis 插件，监听 `agent/status` 变为 `idle` 时检查是否需要自动发起下一轮：

```typescript
// packages/goal/goal-round-driver/src/index.ts:138-205
async function drive(goal: Goal, agent: Agent) {
  // 1. 检查 Goal 状态
  if (goal.phase !== 'active') return

  // 2. 轮次上限检测 —— 核心！
  if (goal.roundsStarted >= goal.maxGoalRounds) {
    await blockGoal(goal, {
      code: 'round-limit',
      message: `Goal reached its configured limit of ${goal.maxGoalRounds} rounds.`,
    })
    return
  }

  // 3. 启动下一轮
  const round = goal.roundsStarted + 1
  const content = renderGoalRoundPrompt(goal, round)
  await agent.sendMessage(content)
}
```

### 4.4 防竞态设计

`requestDrive` 使用 serialized loop 确保同一 agent 上只有一个驱动任务运行：

```typescript
// serialized loop —— 防竞态核心
while (state.requested && !state.stopping) {
  await waitForStateChange()
}
state.requested = true
try {
  await drive(goal, agent)
} finally {
  state.requested = false
}
```

### 4.5 maxGoalRounds 双重检测

1. **GoalService.resume()**：恢复时检查 `roundsStarted >= maxGoalRounds`，抛 `GOAL_INVALID_TRANSITION`
2. **round driver.drive()**：每轮开始前检查，达到限制则自动 block

**对 laew 的借鉴**：laew 的 Main-Work Agent 拆 WorkFlow 列表后，缺乏自动续轮机制——子任务完成后不会自动推进到下一个，需要编排器显式调度。

## 5. OpenClaw：Harness Turn 路由 + Gateway 传输

### 5.1 设计哲学

OpenClaw 的循环以 **Turn** 为核心单位，通过 Harness 抽象层路由到不同的 Agent 实现。循环由 Gateway 层统一管理传输（WebSocket/SSE），Harness 层管理 turn 生命周期。

### 5.2 Turn 状态机

```
pending → running → settled(terminal)
                         ├── completed
                         ├── aborted
                         ├── timed_out
                         └── error
```

**终止判定**（`context-engine-turn-attempt.ts`）：
```typescript
if (terminal.timedOut) return "timed_out"
if (terminal.externalAbort || terminal.aborted) return "aborted"
if (terminal.promptErrorSource !== null) return "error"
return "completed"
```

### 5.3 Gateway 传输层

OpenClaw 支持多种传输协议，循环与传输层解耦：
- **WebSocket**：全双工，通过 `resolveGatewayWebSocketTransport()` 处理 TLS 指纹归一化、proxy 路由、loopback 检测
- **SSE**：Server-Sent Events，单向推送
- **Cloudflare Access 代理**：`cloudflare-access.ts`

### 5.4 工具执行

工具调用通过 `callTool(request.params, extra.signal)` 执行，支持：
- 超时控制（signal）
- 未知工具回退：`{ content: [{ type: "text", text: "Unknown tool" }], isError: true }`
- 风险分级（4 级 risk）

### 5.5 与 laew 的对比

OpenClaw 的 turn 状态机比 laew 的简单 while 循环更结构化。laew 当前只有「执行中→完成」两种状态，缺乏 timeout/error 的细粒度终态。

## 6. OpenCode：SessionPrompt.loop() + doom_loop 检测

### 6.1 设计哲学

OpenCode 的循环以 **SessionPrompt.loop()** 为核心，采用 Effect 框架的 generator 风格实现。循环内嵌 doom_loop 防死循环检测，是 6 个项目中最具代表性的「单 loop + 安全阀」设计。

### 6.2 SessionPrompt.loop() 主循环

入口在 `packages/opencode/src/session/prompt.ts`：

```typescript
const loop = Effect.fn("SessionPrompt.loop")(function* (input: LoopInput) {
  while (true) {
    // 1. 构建 PromptInput
    const promptInput = yield* SessionPrompt.prompt(input)

    // 2. 调用 LLM（流式）
    const stream = yield* LLM.stream(promptInput)

    // 3. 处理流事件
    const result = yield* SessionProcessor.process(stream, input)

    // 4. 判断是否继续
    if (result === "stop") break   // doom_loop 触发 / 无工具调用
    if (result === "continue") continue
  }
})
```

**完整链路**：
```
用户输入 → SessionPrompt.prompt() 构建 PromptInput
         → SessionPrompt.loop() 进入循环
           → LLM.stream() 发起流式请求
             → SessionProcessor.process() 处理流事件
               → 工具调用 → 执行 → 结果回填 → continue
               → 无工具调用 → "stop" → 退出
```

### 6.3 doom_loop 防死循环机制

doom_loop 是 OpenCode 最独特的安全机制，检测算法：

```typescript
// packages/opencode/src/session/processor.ts
const DOOM_LOOP_THRESHOLD = 3

function detectDoomLoop(parts: Part[]): boolean {
  const recentParts = parts.slice(-DOOM_LOOP_THRESHOLD)

  // 判断是否满足 doom_loop 条件
  if (recentParts.length !== DOOM_LOOP_THRESHOLD) return false

  // 条件 1：连续 3 次完全相同的工具调用
  const allSameTool = recentParts.every(
    p => p.type === "tool" && p.tool === recentParts[0].tool
  )
  // 条件 2：连续 3 次工具输入 hash 相同
  const allSameInput = recentParts.every(
    p => p.type === "tool" && hashInput(p.input) === hashInput(recentParts[0].input)
  )

  return allSameTool && allSameInput
}
```

**触发后处理**：
```
检测到 doom_loop → 注入 permission: "doom_loop" 请求
  → 用户允许 → 继续
  → 用户拒绝 → RejectedError → ctx.blocked = true → process()返回"stop" → 循环终止
```

### 6.4 与主循环的集成

doom_loop 检测嵌入在 `processor.ts` 的 `handleEvent` 中，是 LLM 流式事件处理的一部分：
- 不中断 LLM 流
- 在 tool-call 事件时同步检查
- 触发后走标准权限流程

### 6.5 流式与循环的耦合

OpenCode 使用 Effect Stream 全栈：
- LLM 响应是 Stream<Event>
- processor 消费 Stream 并产出 Part
- 循环通过 generator 的 yield 控制流

**对 laew 的借鉴**：doom_loop 检测是 laew 最急需的安全机制（30-50 行 Rust 即可实现）。

## 7. Pi：双层循环 + Lane 并发

### 7.1 设计哲学

Pi 的循环采用**双层循环**结构，是 6 个项目中最复杂的循环设计之一。外层处理 followUp 消息（agent 停止后追加的新任务），内层处理 tool calls + steering 消息。

### 7.2 runLoop 双层循环

入口在 `packages/agent/src/agent-loop.ts:156`：

```typescript
async function runLoop(
  initialContext,
  newMessages,
  initialConfig,
  signal,
  emit,
  streamFunction
) {
  // 外层循环：处理 followUp 消息（agent 停止后追加的新任务）
  while (true) {
    // 内层循环：处理 tool calls + steering 消息
    while (hasMoreToolCalls || pendingMessages.length > 0) {
      // 1. 获取下一个工具调用
      // 2. 执行工具
      // 3. emit ToolResultEvent
      // 4. 检查 steer 消息（用户中途干预）
      // 5. 决定是否继续
    }

    // 内层结束 → 检查是否有 followUp
    if (followUpMessages.length > 0) {
      newMessages = followUpMessages
      continue  // 外层继续
    }
    break  // 无 followUp → 完全结束
  }
}
```

### 7.3 终止条件

- **terminate 标记**：工具可设置 `terminate?: boolean` 终止整个工具批次
- **无 pendingMessages**：内层循环结束
- **无 followUp**：外层循环结束
- **signal.abort**：外部中断

### 7.4 工具结果处理

- 工具结果通过 `emit ToolResultEvent` 回传
- 工具结果截断到 `TOOL_RESULT_MAX_CHARS = 2000` 字符
- 截断原因：bash 输出可能有数万行，全部传给摘要 LLM 会浪费 token

### 7.5 Lane 并发

Pi 的循环与 Lane 并发模型深度集成：
- 每个 Lane 是独立的执行通道
- Lane 间通过消息通信
- `while (lanes.get(lane.groupId) === lane && lane.active.size < lane.limit)` 控制并发容量

### 7.6 流式协议

Pi 使用 `AssistantMessageEventStream` 统一流式协议：
- 事件粒度更细（text_start/delta/end 分离）
- 对 TUI 实时渲染更友好
- `supportsFinishReason` 标志位标识流式 finish_reason 支持

**对 laew 的借鉴**：
1. 双层循环结构适合 laew 的「主对话 + 子任务」场景
2. 工具结果截断（2000 字符）值得借鉴
3. steer 消息机制适合 TUI 的用户中途干预

## 8. 设计模式提炼

### 8.1 模式一：协议无关循环（AtomCode / laew）

**描述**：Agent 循环永远不触及协议细节，差异封闭在 Provider trait 内部。

**体现**：
- AtomCode：`LlmProvider` trait 封闭 Anthropic/OpenAI 差异
- laew：`LlmClient` trait + `llm/anthropic.rs` / `llm/openai.rs`

**优势**：循环逻辑简洁，新增协议只需实现 trait，不改循环。

### 8.2 模式二：多层独立熔断（AtomCode）

**描述**：防死循环不用单一计数器，而是多层独立计数器，每层有独立上限和策略。

**体现**：ToolLoopPolicy / MAX_REPEAT_ROUNDS / provider_retry / truncation_resume

**优势**：不同故障模式用不同策略处理，避免「一刀切」。

### 8.3 模式三：压缩驱动的长循环（Claude Code）

**描述**：循环不追求「最少轮次」，而是通过压缩管线让循环可以持续很多轮。

**体现**：四级压缩管线（Time-Based → Cached → Auto → Session Memory）

**优势**：长任务不会溢出，用户体验更连贯。

### 8.4 模式四：目标驱动自动续轮（DeepSeek-Harness）

**描述**：循环由 Goal 状态机驱动，round driver 自动续轮直到目标完成。

**体现**：`goal-round-driver` 监听 idle → 检查轮次 → 自动发送下一轮 prompt

**优势**：多步骤任务无需用户反复触发，Agent 自主推进。

### 8.5 模式五：安全阀嵌入式检测（OpenCode）

**描述**：在循环的关键节点嵌入轻量检测，触发后走标准权限流程。

**体现**：doom_loop 检测嵌入 `processor.ts` 的 `handleEvent`

**优势**：不中断主流程，检测与权限系统解耦。

### 8.6 模式六：双层循环分离关注点（Pi）

**描述**：外层处理「任务级」消息，内层处理「工具级」调用。

**体现**：外层 followUp 循环 + 内层 tool calls 循环

**优势**：用户中途追加任务不影响当前工具执行。

### 8.7 模式七：Turn 状态机终态（OpenClaw）

**描述**：循环的每个 Turn 有明确的终态集合，便于监控和调试。

**体现**：completed / aborted / timed_out / error

**优势**：运维可观测，问题可定位。

### 8.8 模式八：流式事件驱动（通用）

**描述**：循环与流式深度耦合，事件驱动工具调用检测与结果处理。

**体现**：所有 6 个项目均采用流式事件驱动

**优势**：实时性好，可中途干预。

    Completed,
    Aborted,
    TimedOut,
    Error(AgentError),
    RoundLimitExceeded,
    DoomLoopDetected,

/// 循环配置
pub struct LoopConfig {
    pub max_rounds: u32,
    pub max_provider_retry: u32,
    pub max_truncation_resume: u32,
    pub max_repeat_rounds: u32,
    pub repeat_nudge_at: u32,
    pub doom_loop_threshold: usize,
    pub max_tool_result_bytes: usize,
}

impl Default for LoopConfig {
    fn default() -> Self {
        Self {
            max_rounds: 64,
            max_provider_retry: 3,
            max_truncation_resume: 4,
            max_repeat_rounds: 6,
            repeat_nudge_at: 3,
            doom_loop_threshold: 3,
            max_tool_result_bytes: 64 * 1024,
        }

/// doom_loop 检测
pub fn detect_doom_loop(history: &[ToolCallRecord], threshold: usize) -> bool {
    if history.len() < threshold {
        return false;
    }
    let recent = &history[history.len() - threshold..];
    let first = &recent[0];
    recent.iter().all(|call| call.name == first.name && call.input_hash == first.input_hash)

    if result.len() <= max_bytes {
        return result.to_string();

    let half = max_bytes / 2;
    format!(
        "{}...[truncated {} bytes]...{}",
        &result[..half],
        result.len() - max_bytes,
        &result[result.len() - half..]
    )
}

### C.2 集成到 run_session

```rust
use crate::agent::loop::{LoopConfig, LoopCounters, ToolCallRecord, detect_doom_loop, cap_tool_result, TurnResult};

pub async fn run_session(session: &mut Session) -> Result<TurnResult, AgentError> {
    let config = LoopConfig::default();
    let mut counters = LoopCounters::default();
    let mut tool_history: Vec<ToolCallRecord> = Vec::new();

    loop {
        // 轮次上限检测
        counters.round += 1;
        if counters.round > config.max_rounds {
            return Ok(TurnResult::RoundLimitExceeded);
        }

        // 构造请求 + 调用 LLM
        let response = match call_llm_with_retry(session, &config).await {
            Ok(r) => r,
            Err(e) if e.retryable() && counters.provider_retry < config.max_provider_retry => {
                counters.provider_retry += 1;
                sleep(backoff(counters.provider_retry)).await;
                continue;
            }
            Err(e) => return Err(e),
        };

        // 处理工具调用
        if let Some(tool_calls) = response.tool_calls {
            // doom_loop 检测
            for call in &tool_calls {
                tool_history.push(ToolCallRecord {
                    name: call.name.clone(),
                    input_hash: hash_input(&call.input),
                });
            }
            if detect_doom_loop(&tool_history, config.doom_loop_threshold) {
                return Ok(TurnResult::DoomLoopDetected);
            }

            // 执行工具 + 截断结果
            for call in tool_calls {
                let result = execute_tool(call).await?;
                let capped = cap_tool_result(&result, config.max_tool_result_bytes);
                session.context.push(Message::tool(capped));
            }
            continue;
        }

        // 无工具调用 → 完成
        return Ok(TurnResult::Completed);
    }
}
```
