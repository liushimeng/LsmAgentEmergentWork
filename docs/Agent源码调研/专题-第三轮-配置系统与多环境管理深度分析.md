## 1. 引言与 laew 现状

### 1.1 分析背景

配置系统是 Agent 工程的「静默骨架」——它决定多模型接入如何管理、多环境如何切换、敏感凭证如何保护、旧版本如何平滑升级。本轮从 6 个代表性项目中提炼配置系统的设计谱系，为 laew 的「DB-as-config」独特路线提供评估与演进依据。

### 1.2 laew 现状快照

laew 采用**零配置文件、全量 SQLite**路线。核心代码位于 `src/config/mod.rs`（375 行）：

```rust
// src/config/mod.rs:144-154
CREATE TABLE IF NOT EXISTS providers (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    protocol      TEXT NOT NULL CHECK(protocol IN ('anthropic','openai')),
    provider_name TEXT NOT NULL,
    model_name    TEXT NOT NULL,
    end_point     TEXT NOT NULL,
    api_key       TEXT NOT NULL,
    is_active     INTEGER NOT NULL DEFAULT 0,
    created_at    TEXT NOT NULL DEFAULT (datetime('now','localtime')),
    UNIQUE(protocol, provider_name, model_name, end_point)
);
```

**关键特征**：
- 五元组 `(protocol, provider_name, model_name, end_point, api_key)` 存于 `providers` 表，`is_active` 唯一（`set_active` 事务清零其他行，`src/config/mod.rs:263-277`）
- 路径探测：`Paths::detect()` 以 `current_exe()` 父目录为根，`current_dir()` 为工作目录（`src/config/mod.rs:87-96`）
- TUI 内 `/provider add` 5+1 Tab 表单管理，API Key 浏览态脱敏 `****<末4位>`（仅编辑态明文）
- 数据库文件 `LsmAgentEmergentWork.db` 在根目录自动创建，`Db::clone()` 按路径重开保留 Mutex 语义（`src/config/mod.rs:116-125`）

**独特约束**：laew 没有全局/项目/本地分层，没有 JSON/TOML 文件，没有 Schema 校验，没有热加载。所有配置状态 = SQLite 中的行。

  const errors: JsoncParseError[] = []
  const data = parseJsoncImpl(text, errors, { allowTrailingComma: true })
  if (errors.length) {
    const issues = errors.map((e) => {
      const beforeOffset = text.substring(0, e.offset).split("\n")
      const line = beforeOffset.length
      const column = beforeOffset[beforeOffset.length - 1].length + 1
      const problemLine = lines[line - 1]
      const error = `${printParseErrorCode(e.error)} at line ${line}, column ${column}`
      if (!problemLine) return error
      return `${error}\n   Line ${line}: ${problemLine}\n${"".padStart(column + 9)}^`
    }).join("\n")
    throw new JsonError({ path: filepath, message: ... })
  }
  return data
}

// packages/coding-agent/src/core/settings-manager.ts:152-174
function deepMergeObjects(base: Record<string, unknown>, overrides: Record<string, unknown>): Record<string, unknown> {
  const result = { ...base }
  for (const key of Object.keys(overrides)) {
    const overrideValue = overrides[key]
    if (overrideValue === undefined) continue
    const baseValue = base[key]
    result[key] =
      isMergeableObject(baseValue) && isMergeableObject(overrideValue)
        ? deepMergeObjects(baseValue, overrideValue)
        : overrideValue  // 数组/标量直接替换
  }
  return result
}
function deepMergeSettings(base: Settings, overrides: Settings): Settings {
  return deepMergeObjects(base, overrides) as Settings
}
```

**特征**：纯深合并，数组不拼接（与 opencode/claudecode 的数组拼接策略不同）。

// vendor/loader/src/config/entry.ts:142-246
async update(options: Partial<EntryOptions>, create = false, force = false) {
  const previousOptions = this.options
  const candidate = create ? options : { ...previousOptions }
  if (!create) {
    for (const [key, value] of Object.entries(options)) {
      if (isNullable(value)) delete candidate[key]
      else candidate[key] = value
    }
  }
  const diff = Object.keys({ ...candidate, ...legacy })
    .filter(key => !deepEqual(candidate[key], legacy[key]))
  if (!diff.length && !force) return  // 无变化则跳过

  const replace = diff.some(key => key === 'name' || key === 'inject' || key === 'group')
  if (!replace) {
    this.options = candidate
    await this._patchContext(diff)  // 热更新配置
  } else {
    // 需要重启：先 dispose 旧 fiber，再 start 新插件
    await this._dispose(previous)
    await this._start(plugin)
  }
  commit()
}
```

**关键设计**：区分「配置热更新」（`_patchContext`）与「模块重启」（dispose+start），前者用于 `config` 变化，后者用于 `name`/`inject`/`group` 变化。

  if (isJsExpr(value)) return evaluate(ctx, value.__jsExpr)
  else if (Array.isArray(value)) return value.map(item => interpolate(ctx, item))
  else return valueMap(value, item => interpolate(ctx, item))
}
```

fn atomic_replace(path: &Path, bytes: &[u8]): Result<()> {
  let parent = path.parent().unwrap_or_else(|| Path::new("."))
  let mut temp = tempfile::NamedTempFile::new_in(parent)?
  temp.write_all(bytes)?
  temp.as_file().sync_all()?  // fsync
  temp.persist(path)?  // 原子 rename
  #[cfg(unix)]
  File::open(parent)?.sync_all()?  // 同步目录项
  Ok(())
}

## 4. 可复用设计模式

### 模式 1：分层配置发现链（Layered Discovery Chain）

**描述**：配置按「全局 → 项目 → 本地 → 环境变量 → CLI 参数 → 策略」多层发现，高优先级覆盖低优先级。

**最佳实践**：claudecode 的 5 源体系（`constants.ts:7-24`）+ opencode 的 8 层加载（`config.ts:328-611`）。

**关键决策点**：
- 数组是「拼接去重」还是「替换」？（opencode/claudecode 选择拼接，pi 选择替换）
- 未知键是「忽略」还是「保留」？（claudecode `.passthrough()` 保留，便于升级）
- 错误是「全量拒绝」还是「容忍隔离」？（atomcode 隔离无效 section）

**laew 适用性**：laew 当前无分层，但项目级 AGENTS.md 已有注入机制，可复用此链。

---

### 模式 2：容忍解析与隔离区（Tolerant Parsing + Quarantine）

**描述**：配置加载时不因局部错误而整体失败，无效部分被隔离并原样保留。

**最佳实践**：
- atomcode `quarantined_providers`（`config/mod.rs:366-373`）：无效 provider 原样保留为 raw TOML，回写时不丢弃
- claudecode `filterInvalidPermissionRules`（`settings.ts:215-217`）：单条无效权限规则不导致整个文件被拒

**laew 适用性**：SQLite 行级天然隔离，但 TUI 表单校验可借鉴「字段级错误不阻塞整体提交」。

---

### 模式 3：ApplyPolicy 生效策略分级（Staged Application Policy）

**描述**：不同配置项的变更需要不同的生效时机，显式声明而非隐式假设。

**最佳实践**：atomcode 5 级 ApplyPolicy（`settings.rs:25-31`）：

```
ImmediateUi → NextTurn → AgentReassemble → CapabilityReprepare → NextStartup
```

**laew 适用性**：laew 的 `set_active` 是即时生效（切换 provider 重建 Agent），但未来若引入更多配置项，可复用此分级。

---

### 模式 4：运行时 Secret 内存隔离（Runtime Secret Retention）

**描述**：运行时生成的 secret 仅保留在内存，永不写回配置文件。

**最佳实践**：openclaw `retainGeneratedOwnerDisplaySecret`（`io.owner-display-secret.ts:7-30`）。

**laew 适用性**：laew 的 API Key 存 SQLite，浏览态脱敏。可借鉴「生成凭证不落盘」原则，用于未来 OAuth token 场景。

---

### 模式 5：配置即代码 + 热补丁（Config as Code + Hot Patching）

**描述**：配置系统本身是一个插件加载器，支持配置热更新与模块重启的区分。

**最佳实践**：deepseek-harness `Entry.update`（`entry.ts:142-246`）：
- `config` 变化 → `_patchContext` 热更新
- `name`/`inject`/`group` 变化 → dispose + start 重启
- 失败自动回滚到旧插件

**laew 适用性**：laew 的 provider 切换本质是「热补丁」，但当前是重建整个 Agent。可借鉴「区分配置热更新与模块重启」。

---

### 模式 6：Schema 向后兼容约束（Backward-Compat Schema Governance）

**描述**：通过测试+文档明确 Schema 变更规则，防止破坏性变更。

**最佳实践**：
- claudecode `types.ts:212-241`：明确列出 ✅ 允许/❌ 禁止的变更类型
- atomcode `settings.rs:537-570`：编译期测试保证目录不暴露凭证

**laew 适用性**：laew 的 SQLite schema 变更（如新增 provider 字段）可借鉴此治理模式。

---

### 模式 7：原子写入 + CAS 修订（Atomic Write + CAS Revision）

**描述**：配置写入使用临时文件+原子 rename，并通过修订版本号实现乐观并发控制。

**最佳实践**：atomcode `atomic_replace`（`store.rs:336-358`）+ `ConfigRevision`（`store.rs:19-26`）。

**laew 适用性**：SQLite 事务天然原子，但多进程场景（如 TUI + daemon）可借鉴 CAS 修订。

---

### 模式 8：项目信任隔离（Project Trust Isolation）

**描述**：项目级配置可能被恶意篡改，需显式信任开关或安全隔离。

**最佳实践**：
- pi `projectTrusted`（`settings-manager.ts:493-520`）：不受信任时清空项目配置
- claudecode 排除 projectSettings 于敏感权限（`settings.ts:877-928`）

**laew 适用性**：laew 的 AGENTS.md 注入机制已有项目上下文，可借鉴「项目配置不可覆盖全局安全策略」。

---

### 模式 9：Drop-in 配置片段（Drop-in Configuration Fragments）

**描述**：配置目录支持按字母序加载多个片段文件，各团队/工具独立管理。

**最佳实践**：openclaw `managed-settings.d/*.json`（`io.read-helpers.ts`）—— 类似 systemd/sudoers 约定。

**laew 适用性**：未来若支持多 provider 配置包，可复用此模式。

---

### 模式 10：配置文档化与编辑器集成（Config Documentation + IDE Integration）

**描述**：配置 Schema 发布为 JSON Schema，编辑器自动补全与校验。

**最佳实践**：claudecode `schemaOutput.ts` → `https://json.schemastore.org/claude-code-settings.json`。

**laew 适用性**：若 laew 引入配置文件，应同步发布 JSON Schema。

## 5. laew 借鉴路线：DB-as-config 评估与混合方案

### 5.1 DB-as-config 路线的优势

laew 的「全量 SQLite」路线在 6 个项目中独树一帜，具有以下**不可替代的优势**：

| 优势 | 说明 | 对比 |
|------|------|------|
| **原子性** | SQLite 事务保证读写原子 | 文件配置需额外实现（atomcode tempfile+rename） |
| **并发安全** | Mutex + 事务隔离 | 文件配置需额外锁（pi proper-lockfile） |
| **结构化查询** | SQL 查询 provider 状态 | 文件配置需全量解析 |
| **零文件污染** | 无散落配置文件 | 其他项目需管理多层文件 |
| **迁移简单** | ALTER TABLE 加列 | 其他项目需写迁移函数 |
| **单文件备份** | 拷贝 .db 即可 | 其他项目需同步多层级文件 |

### 5.2 DB-as-config 路线的劣势

| 劣势 | 说明 | 影响 |
|------|------|------|
| **无可视化** | 用户无法直接编辑文本 | 需 TUI 表单（已实现 /provider add） |
| **无项目级覆盖** | 全局 provider 无法按项目切换 | 多项目场景不便 |
| **无版本控制** | .db 文件不可 diff | 配置变更无法 git 追踪 |
| **无编辑器集成** | 无 JSON Schema 自动补全 | 需 TUI 表单补全 |
| **共享困难** | 无法通过 git 分享配置 | 团队配置同步困难 |

### 5.3 是否需要引入分层配置？

**结论：需要，但应保持 DB 为核心，文件为「覆盖层」**。

理由：
1. **项目级 AGENTS.md 已有注入机制**（`src/agent/project_context.rs`），说明 laew 已认可「项目级上下文」概念
2. **多 provider 切换是刚需**：不同项目可能需要不同 provider，纯 DB 无法表达「此项目用 X，彼项目用 Y」
3. **团队协作场景**：DB 难以分享，文件配置可 git 追踪

### 5.4 混合方案设计

```
┌─────────────────────────────────────────────────┐
│              配置优先级（高→低）                  │
├─────────────────────────────────────────────────┤
│ ⑤ CLI 参数（--provider, --model）                │
│ ④ 环境变量（LAEW_PROVIDER, LAEW_MODEL）          │
│ ③ 项目配置（.laew.json，git 可选）               │
│ ② 全局配置（~/.laew/config.json）               │
│ ① SQLite DB（LsmAgentEmergentWork.db，核心）    │
└─────────────────────────────────────────────────┘
```

// 自下而上查找 .laew.json
fn discover_project_config(work_dir: &Path) -> Option<PathBuf> {
    let mut current = work_dir;
    loop {
        let candidate = current.join(".laew.json");
        if candidate.exists() { return Some(candidate); }
        match current.parent() {
            Some(parent) if parent != current => current = parent,
            _ => return None,
        }
    }
}
```

- 项目配置**不可**覆盖 `api_key`（凭证仅 DB 管理）

fn migrate(db: &Db) -> Result<()> {
    let current: u32 = db.get_meta("schema_version")?.parse().unwrap_or(1);
    if current < 2 {
        // v1 → v2: 新增 project_overrides 表
        db.execute_batch(include_str!("migrations/v2.sql"))?;
        db.set_meta("schema_version", "2")?;
    }
    Ok(())
}

## 6. 结论

### 6.1 核心发现

1. **配置发现链复杂度差异巨大**：opencode 8 层 > claudecode 5 层 > openclaw 4 层 > pi 2 层 > atomcode 1 层 > laew 0 层（纯 DB）。laew 的极简路线在单用户场景下高效，但多项目/团队协作场景受限。

2. **数组合并策略是分水岭**：opencode/claudecode 选择「拼接去重」，pi 选择「直接替换」。laew 未来引入文件配置时需明确此决策。

3. **Schema 校验是标配**：5/6 项目使用强类型 Schema（Effect Schema / Zod / Serde），仅 pi 依赖 JSON 动态解析。laew 的 SQLite CHECK 约束是弱等价，建议引入 Serde 结构体。

4. **项目信任隔离是安全基线**：pi 的 `projectTrusted` 与 claudecode 的「projectSettings 排除」是防御恶意项目配置的关键设计。laew 的 AGENTS.md 注入机制需同步考虑此风险。

5. **ApplyPolicy 生效策略被忽视**：仅 atomcode 显式声明 5 级生效策略。laew 的 `set_active` 是即时生效，但未来配置项增多时需分级管理。

6. **原子写入是文件配置必备**：atomcode 的 tempfile+fsync+rename 是黄金标准。laew 的 SQLite 事务天然满足，但引入文件配置时需复刻此模式。

7. **运行时 secret 隔离是最佳实践**：openclaw 的「生成凭证不落盘」原则值得 laew 在 OAuth 场景复用。

### 6.2 laew 独特路线的终极评估

**DB-as-config 路线在以下场景优于文件配置**：
- 单用户、多 provider 频繁切换
- 需要原子性保证与并发安全
- 配置项动态扩展（ALTER TABLE 优于 Schema 迁移）
- 无需版本控制或团队分享

**DB-as-config 路线在以下场景劣势明显**：
- 多项目需要不同 provider/配置
- 团队需要共享配置或 git 追踪
- 用户习惯直接编辑文本配置
- 需要编辑器自动补全

**最终建议**：采用「DB 为核心 + 文件为覆盖层」的混合方案，保持 SSOT 在 SQLite，项目/全局配置作为「偏好声明」写入 DB。此方案兼顾 laew 现有架构优势与多环境管理需求。
