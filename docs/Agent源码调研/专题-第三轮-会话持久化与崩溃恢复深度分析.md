## 1. 引言与 laew 现状

会话持久化是 Agent CLI 的「记忆底座」——进程被 kill、机器断电、用户次日回来,对话能否续上,取决于持久化与崩溃恢复设计。本轮从 7 个维度横向对比 6 个外部仓库:

| 维度 | 核心问题 |
|------|----------|
| 存储格式选型 | JSONL / SQLite / 文件树?消息级 schema 如何存 tool_call/thinking? |
| 写入时机与原子性 | 每条落盘 vs 批写?fsync?temp+rename? |
| 崩溃恢复 | kill 后如何恢复?撕裂尾部检测?损坏丢弃?版本兼容? |
| 会话管理操作 | resume/continue/fork/改名/搜索/时间旅行 |
| 多端同步 | 本地 vs 云?并发写冲突? |
| 大消息处理 | 超大 tool_result?图片/二进制? |
| 目录布局 | 实际落盘路径?命名规则?索引文件? |

### laew 当前状态(必读,建议的靶向基线)

`src/session.rs` 的 `Session` 结构体是**纯内存态**:

```rust
// src/session.rs:122-128
pub struct Session {
    pub id: String;
    pub device_id: String,
    pub created_at: String,
    pub context: Vec<ChatMessage>,   // 对话历史,进程退出即失
}
```

- **无 resume**:进程重启后无法恢复任何会话。
- **无崩溃恢复**:`context` 在内存 `Vec` 中,无任何落盘。
- **仅有的持久化**:`src/config/mod.rs` 的 SQLite 库(`LsmAgentEmergentWork.db`)只存 `providers` / `session_memory`(每任务摘要)/ `agent_memory`(Agent 记忆)三张表,**不存对话上下文**。
- **Session ID 生成**(src/session.rs:62-94):`{YYYYMMDD-HHmmss}-{指纹前8位}-{Unix毫秒}-{6位随机hex}`,信息量丰富但无持久化配合。

> **结论**:laew 在持久化维度是「零」——本轮借鉴路线将给出从 P0 到 P2 的渐进方案。

### 2.1 pi — 双后端 + 树状会话 + Writer Lease

> TypeScript,`packages/agent/src/harness/session/`(JSONL 后端)+ `packages/session-backends/sqlite-node/`(SQLite 后端)。pi 是本轮最复杂的持久化实现,双后端共享同一套 `SessionStorage` trait。

#### 存储格式选型

**JSONL 后端**(v4 格式):每会话一 `.jsonl` 文件,首行是 header,后续每行是一个 **mutation**(非原始消息)。

```typescript

    metadata?: Record<string, JsonValue>;

```

**Mutation 模型**(state.ts:17-22)——pi 不直接存消息,而是存「变更事件」:


**Entry 类型**(types.ts:67-74):`MessageEntry | ModelChangeEntry | ThinkingLevelEntry | ActiveToolsEntry | CompactionEntry | BranchSummaryEntry | CustomEntry`。tool_call/tool_result 打包在 message 中,thinking 通过 `thinking_level_change` entry 记录级别切换。

**目录布局**(repo.ts:27-29):`--<cwd编码>--/<ISO时间>_<uuidv7>.jsonl`,例如 `--Users-foo-proj--/2025-09-05T10-30-00Z_019123a0-....jsonl`。

#### 写入时机与原子性

**每条 mutation 立即 append**(storage.ts:267-272),**写入串行化**(storage.ts:258-265 `this.tail` Promise 链)。

**撕裂尾部修复 + 原子发布**(storage.ts:33-46, 80-107)——pi 最精妙的设计:

```typescript
// storage.ts:33-46 — 原子发布:先写 .tmp,再 rename
async function publishFileAtomically(fs, destinationPath, populate): Promise<void> {
    const tempPath = `${destinationPath}.tmp`;
    try {
        await populate(tempPath);
        fileResult(await fs.renameFile(tempPath, destinationPath), ...);
    } catch (error) {
        await fs.remove(tempPath, { force: true });  // 失败清理
        throw error;
    }
}

// storage.ts:84-93 — load 时检测撕裂尾部(仅最后一行 syntax 错误才视为撕裂)
const isTornTail = index === physicalLines.length - 1 && mutationResult.error.kind === "syntax";
if (isTornTail) {
    const validPrefix = `${physicalLines.slice(0, index).join("\n")}\n`;
    await publishFileAtomically(fs, path, async (tempPath) => {
        fileResult(await fs.writeFile(tempPath, validPrefix), ...);  // 截断撕裂行

```

> **关键洞察**:仅在「最后一行」且错误类型是 `syntax` 时才视为撕裂尾部;中间行的 schema 错误直接抛 `invalidFile`——区分「崩溃导致的不完整写」与「真正的 schema 不兼容」。

#### 崩溃恢复

- **撕裂尾部**:load 时自动检测并原子截断。
- **非尾部损坏**:`throw invalidFile(path, index + 1, mutationResult.error)`(storage.ts:93)——整 session 不可用。
- **版本兼容**:codec.ts:73 `if (value.version !== 4) throw ...`——硬拒绝,无升级路径(v3→v4 通过 `legacyParentSessionPath` 保留兼容)。

#### 会话管理操作

**树状 fork**(repo.ts:142-156):header 中 `parentSessionId` + `fork()` 复制源 entries。**Lane 分支机制**(state.ts:50-75):多 lane,每 lane 一个 `leafId` 指针。**resume**:`listJsonlSessionMetadata()`(repo.ts:65-87)读首行 header 按 `modifiedAt` 降序。**改名**:`setName()` 产生 `fact` mutation(storage.ts:227-233)。

#### SQLite 后端(`session-backends/sqlite-node`)

```typescript

        if (seen.has(currentMsg.uuid)) { break }  // 环检测
```

#### 写入时机与原子性——WriteBehind 200ms

**SessionWriteBehind**(write-behind.ts:22-159)——本轮最精巧的写入控制器:

```typescript
export class SessionWriteBehind {
    private pending: SessionEvent[] = []
    private timer: ReturnType<typeof setTimeout> | undefined
    private active: Promise<void> | undefined
    private barrier: Promise<void> | undefined
    private deadlineExpired = false
    private automaticPaused = false

    enqueue(event: SessionEvent): void {
        const wasEmpty = this.pending.length === 0
        this.pending.push(structuredClone(event))   // 独立副本
        if (this.barrier !== undefined) return
        if (this.automaticPaused) { this.armTimer() }
        else if (wasEmpty) { this.armTimer() }       // 首个事件启动 200ms 窗口
    }

    flush(): Promise<void> {                         // 排空到静止点
        if (this.barrier !== undefined) return this.barrier  // 并发调用者共享同一 barrier
        const barrier = Promise.withResolvers<void>()
        this.barrier = barrier.promise
        void this.drainBarrier(barrier.resolve, barrier.reject)
        return barrier.promise
    }

    private startWrite(background: boolean): Promise<void> {
        const batch = this.pending.splice(0)
        const operation = Promise.resolve().then(() => this.options.write(batch))
        const active = operation
            .catch((error) => {
                this.pending = batch.concat(this.pending)  // 失败:拼回前面,保序
                this.automaticPaused = true                // 暂停自动重试
                throw error
            })
        this.active = active; return active
    }
}
```

#### 崩溃恢复——SessionLogScanner + interruptedTurnClosers

**增量扫描 + torn-tail 检测**(format.ts:305-411):

```typescript
export class SessionLogScanner {
    private readonly events: SessionEvent[] = []
    private committedBytes: number
    private issue: Error | undefined

    finish(): SessionLogScan {                             // 忽略无换行的末记录作为 torn tail
        this.finished = true
        return { meta: this.meta, events: this.events, committedBytes: this.committedBytes }
    }

    private consumeEventLine(line, endByte): void {
        let decoded: SessionEvent[]
        try { decoded = decodeStorageRecord(expandProvenanceFromStorage(JSON.parse(line.toString('utf8')))) }
        catch { this.issue ??= new Error(`corrupt: unparsable event at line ${this.eventLine}`); return }
        if (this.issue !== undefined) {
            if (decoded.some(e => e.type === 'turn/end')) throw this.issue  // 有结尾才确定损坏
            return
        }
        for (const event of decoded) {
            if (event.seq !== this.events.length) {             // seq 不连续 → 损坏
                this.issue = new Error(`seq gap at line ${this.eventLine}`)
                if (decoded.some(c => c.type === 'turn/end')) throw this.issue
                return
            }
            this.events.push(event)
        }
        this.committedBytes = endByte                           // 更新连续前缀
    }
}
```

> Rust,~150k 行。`crates/atomcode-capabilities/src/session/`,feature-gated。**本轮唯一的 Rust 实现,与 laew 同语言,借鉴价值最高**。

**TranscriptHook**(transcript.rs:140-215):

```rust
fn flush(&self, convo: &Conversation) {
    let buffer = { self.lock().take() };
    let Some(b) = buffer else { return };
    if b.assistant.is_empty() && b.tools.is_empty() { return }   // 空 turn 丢弃
    // 按 tool_call_id 从 live conversation 配对 tool result
    let mut results: HashMap<&str, (&str, bool)> = HashMap::new();
    for m in &convo.messages {
        if m.role == Role::Tool { if let Some(id) = &m.tool_call_id {
            results.insert(id.as_str(), (m.text.as_str(), m.is_error)); }
        }
    }
    let record = TurnRecord { ... };
    if let Err(error) = self.append(&record) {
        eprintln!("[TranscriptHook] session transcript was not saved; ...");  // 写失败不 fail turn
    }
}
```

#### 原子写——temp + rename + dir sync

**atomic_write**(manager.rs:4085-4139)——Rust 版最严谨的原子写:

```rust
fn atomic_write_tracked(path: &Path, bytes: &[u8]) -> Result<(), AtomicWriteFailure> {
    fs::create_dir_all(parent)?;
    reject_existing_non_regular(path)?;                    // 拒绝符号链接/特殊文件
    let tmp = path.with_file_name(format!(".{file_name}.{}.{}.tmp", process::id(), sequence));
    let mut file = options.create_new(true).write(true).open(&tmp)?;
    ensure_private_file_permissions(&tmp, &file)?;         // 0o600
    file.write_all(bytes)?; file.sync_all()?;              // 先落盘
    fs::rename(&tmp, path)?;                                // 再原子替换
    #[cfg(unix)] File::open(parent).and_then(|d| d.sync_all())?;  // 目录项也 sync
    // 失败时 remove tmp;AtomicWriteFailure.mutated 标记 rename 是否已完成
}
```

> 注释(:4082):「A crash mid-write never leaves a half-written (corrupt) session file. The tmp's extension (`…tmp`) is ignored by `list`'s `*.meta` filter, so a leftover tmp from a crash never appears as a session.」

**多文件原子提交**(manager.rs:1500-1568, 2508-2579):snapshot/meta/presentation 三文件各自提交,失败时对已 rename(`mutated=true`)的项回滚。**JSONL 追加**(manager.rs:2859-2895):`lock_exclusive` + 大小上限(`MAX_JSONL_LINE_BYTES=16MB`、`MAX_JSONL_BYTES=512MB`),对 PermissionDenied/WouldBlock 做重试。

#### 崩溃恢复——inflight 快照

**save_inflight_snapshot**(manager.rs:1142-1160):用户 prompt 接受后立即写独立检查点(不加 meta lock)。

**load_native_session_for_resume**(manager.rs:1243-1283)——崩溃恢复核心:

```rust
pub fn load_native_session_for_resume(&self, lease) -> SessionResult<(LoadedSession, Option<Message>)> {
    let mut loaded = self.load_native_session(lease.id())?;
    let inflight = match self.load_inflight_snapshot(lease.id()) { ... };
    let canonical_len = loaded.snapshot.messages.len();
    let recoverable = inflight.snapshot.messages.len() == canonical_len.saturating_add(1)
        && inflight.snapshot.messages[..canonical_len] == loaded.snapshot.messages
        && inflight.snapshot.messages.last().is_some_and(|m|
            m.role == Role::User && !m.synthetic && m.internal_origin.is_none() && m.tool_calls.is_empty());
    if recoverable {
        if inflight.replay_safe { Ok((loaded, inflight.snapshot.messages.last().cloned())) }  // 返回待重放的用户消息
        else { loaded.snapshot = inflight.snapshot; Ok((loaded, None)) }
    } else { self.clear_inflight_snapshot(...); Ok((loaded, None)) }   // 陈旧/不安全 checkpoint 丢弃
}
```

> **恢复语义**:仅当 inflight = canonical 前缀 + 一条最终 user 消息时才接受;拒绝不完整的 assistant/tool 轮。

**逐行校验**(manager.rs:4005-4052):`for_each_jsonl_line()` 按 `\n` 切行,单条损坏可隔离。**meta/snapshot 读取**:`read_meta` 拒绝 `v > META_VERSION` 的未来 schema,校验 `meta.id == id`;`read_regular_file_bounded` 拒绝符号链接/特殊文件 + 大小上限。

#### 会话管理操作

**acquire_lease**(manager.rs:1302-1322):OS 级 advisory 排他锁(`fs2::FileExt::try_lock_exclusive`),争用立即返回 `SessionInUse`,永不等待。`SessionLease` RAII——进程终止时 OS 自动释放锁。**fork**(manager.rs:3653-3654):`parent_id` 字段记录父 session。**rewind(时间旅行)**:`<id>.rewind.json` 账本 + `<id>.rewind.txn.json` 事务日志。**list**(manager.rs:2776-2802):扫 `*.meta`,跳过未来 schema/损坏,按 `updated_at` 降序。

#### 大消息处理

- **MAX_JSONL_LINE_BYTES = 16MB**——单 turn 记录上限。
- **images**:`Vec<ImageContent>` 内联 base64(小图)或引用(大图)。
- **reasoning_blocks**:有符号 thinking 块独立存储,不污染 text。

### 2.6 openclaw — 分布式网关 + 双模态存储

> TypeScript,201 万行。Gateway 中心化 + 多 Agent 本地存储,架构最复杂。

**双模态**:

1. **Gateway SQLite**:session 元数据、参与者、状态——`sessions-row.ts` 定义 `SessionRowSchema`,含 `key, sessionId, kind(direct/group/global), status(queued/running/done/failed/killed/timeout), parentSessionKey, childSessions, forkedFromParent, spawnDepth, subagentRole, worktree, permissionMode, model, tokens, cost, ...` 60+ 字段。

## 4. 可复用设计模式

从 6 个仓库提炼 8 个可复用设计模式,每个给出「模式名 + 描述 + 最佳来源 + laew 适用性」。

### 模式 P1:Append-Only Mutation Log(追加型变更日志)

**描述**:不存当前状态,存「变更事件」序列。每条消息/操作/命名都作为不可变事件追加,当前状态 = 从头 fold 所有事件。

**最佳来源**:pi(mutation 模型)、deepseek-harness(SessionEvent 流)、opencode(Event Sourcing)。

**laew 适用性**:⭐⭐⭐ 高。laew 已有 `ChatMessage` 统一消息模型,可改为「每条消息即一个事件」追加到 JSONL,当前 context = 重放所有事件。与现有 `Session.context` 兼容(内存 fold 结果)。

### 模式 P2:Torn-Tail Atomic Publish(撕裂尾部原子发布)

**描述**:写入时先写 `.tmp` 兄弟文件 + fsync,再 `rename` 覆盖目标。读取时检测不完整的末行,若是 syntax 错误则原子截断(重写有效前缀到 .tmp 再 rename)。

**最佳来源**:pi(storage.ts:33-46, 80-107)——最简洁;atomcode(manager.rs:4085-4139)——最严谨(含 dir sync)。

**laew 适用性**:⭐⭐⭐ 高。Rust 实现可参考 atomcode 的 `atomic_write`,直接移植到 laew 的 `src/config/`。

### 模式 P3:WriteBehind Bounded Batch(有界批量延迟写)

**描述**:事件入队后启动固定窗口(100-200ms)定时器,窗口到期后一次性写入累积批次。`flush()` 创建 barrier,并发调用者共享同一 barrier。失败时 batch 拼回 pending 前面保序。

**最佳来源**:deepseek-harness(write-behind.ts:22-159)——最工业级;claudecode(100ms 节流)——最简洁。

**laew 适用性**:⭐⭐ 中。laew 是交互式 CLI,每条消息间隔通常 > 200ms,批量收益不大。但「失败保序 + barrier」模式值得借鉴。

### 模式 P4:Inflight Checkpoint(进行中检查点)

**描述**:在用户 prompt 接受后、模型开始处理前,写一个独立的检查点文件(不加主锁)。崩溃恢复时,仅当检查点 = 主快照前缀 + 一条最终 user 消息时才接受,拒绝不完整的 assistant/tool 轮。

**最佳来源**:atomcode(manager.rs:1136-1283)——唯一完整实现。

**laew 适用性**:⭐⭐⭐ 高。laew 多 Agent 架构中,SubAgent-Work 执行耗时任务时可能被杀,inflight 检查点可恢复「已接受但未执行」的用户消息。

### 模式 P5:OS Advisory Lease(OS 级建议锁)

**描述**:通过 `fs2::FileExt::try_lock_exclusive()`(Rust)或 `fcntl LOCK_EX`(POSIX)获取排他锁。进程终止时 OS 自动释放。争用立即返回 `SessionInUse`,永不等待。

**最佳来源**:atomcode(manager.rs:1302-1322)——RAII SessionLease。

**laew 适用性**:⭐⭐⭐ 高。laew 可能多实例运行(如多个 TUI 实例),lease 防止同一 session 并发写。

### 模式 P6:Parent-Chain Tree(父链树状会话)

**描述**:每条消息记录 `parentUuid`(父消息 uuid)。叶节点 = 无子节点的消息。resume 时从最新叶节点沿 parent 反向走到 root,重建链。支持 fork(从任意消息点分叉)。

**最佳来源**:claudecode(sessionStorage.ts:2069-2094 buildConversationChain)——DAG→线性恢复。

**laew 适用性**:⭐⭐⭐ 高。laew 多 Agent 架构天然需要 fork(SubAgent 从 Main-Work 的某个检查点分叉),parent-chain 是最自然的模型。

### 模式 P7:Externalized Large Result(大结果外置)

**描述**:超过阈值的 tool_result 写入独立文件,消息里只留预览(2KB) + 文件路径。阈值可按 tool 通过 feature flag 覆盖。

**最佳来源**:claudecode(toolResultStorage.ts:137-184);opencode(tool-output-store.ts:13-176,2k 行/50KB 阈值)。

**laew 适用性**:⭐⭐ 中。laew 的 Bash 工具可能产生超大输出,外置避免 context 膨胀。

### 模式 P8:Legacy Event Migration(旧事件迁移)

**描述**:读取时把旧版本事件形状升级到当前形状(而非写入时拒绝)。一组 `migrateLegacy*` 函数处理每种旧形状,升级后的事件进入正常流程。

**最佳来源**:deepseek-harness(coordinator.ts:347-538)——最系统(4 种旧形状)。

**laew 适用性**:⭐⭐ 中。laew 当前无历史包袱,但一旦落地持久化,未来 schema 变更时此模式必不可少。

### 模式 P9:Content-Addressed Archive(内容寻址归档)

**描述**:归档时计算 `sha256`,存储 zstd 压缩 blob。清理时按高水位删除最旧归档 + SQLite 空闲页回收。

**最佳来源**:openclaw(session_transcript_archives 表 + session-history-archive-pruning.ts)。

**laew 适用性**:⭐ 低。laew 单用户 CLI,归档清理需求不强,但 sha256 校验可防静默损坏。

### 模式 P10:Per-ID Serialization(per-id 串行化)

**描述**:同一 session 的所有操作(读/写/flush)串成 Promise 链,不同 session 的操作可并发。避免锁,天然保证写顺序。

**最佳来源**:deepseek-harness(coordinator.ts:1091-1114 serialize());pi(storage.ts:258-265 this.tail 链)。

**laew 适用性**:⭐⭐⭐ 高。laew 多 Agent 架构中,同一 session 的多个 Agent 可能并发写(如 SubAgent-Work 与 Quality-Check),per-id 串行化保证一致性。

## 5. laew 借鉴路线

基于 laew 现状(纯内存)和上述模式,给出 P0/P1/P2 渐进路线图。

### P0:最小可用持久化(1-2 周)

**目标**:进程重启后可 resume 最近会话。

| 任务 | 借鉴模式 | 实现要点 |
|------|---------|----------|
| 对话上下文落盘 | P1 Append-Only Log | 每条 ChatMessage 作为一行 JSONL 追加到 `<root>/sessions/<sessionId>.jsonl` |
| 原子写入 | P2 Torn-Tail Publish | 参考 atomcode `atomic_write`,temp + fsync + rename |
| 撕裂尾部修复 | P2 | load 时检测不完整末行,syntax 错误则截断 |
| resume 最近会话 | P6 | 启动时扫 `sessions/*.jsonl`,按 mtime 取最近,fold 所有消息重建 context |
| Session ID → 文件映射 | - | 利用现有 `generate_session_id`,文件名即 `<sessionId>.jsonl` |

**关键文件**:新增 `src/session/persist.rs`(持久化层),修改 `src/session.rs` 的 `Session::new()` 支持从文件加载。

**存储格式建议**(兼容现有 ChatMessage):

```jsonl
{"kind":"header","version":1,"id":"20250905-...","createdAt":1725500000000,"cwd":"/home/foo/proj"}
{"kind":"message","id":"msg-001","prevId":null,"msg":{"role":"user","content":"..."}}
{"kind":"message","id":"msg-002","prevId":"msg-001","msg":{"role":"assistant","content":"...","toolCalls":[...]}}
```

### P1:崩溃恢复 + 并发安全(2-4 周)

**目标**:进程被杀后可恢复到崩溃前状态,多实例安全。

| 任务 | 借鉴模式 | 实现要点 |
|------|---------|----------|
| inflight 检查点 | P4 | 用户 prompt 接受后写 `<sessionId>.inflight`,SubAgent-Work 完成后清除 |
| resume 恢复 | P4 | 启动时检查 inflight,若 = 前缀 + 一条 user 消息则恢复 |
| OS 排他锁 | P5 | 参考 atomcode `acquire_lease`,`<sessionId>.lease` 文件 + `fs2::FileExt` |
| per-id 串行化 | P10 | 同一 session 的写入通过 Promise 链/Mutex 串行 |
| 大结果外置 | P7 | Bash 输出超 16KB 写 `<sessionId>/tool-results/<callId>.txt` |

**关键文件**:扩展 `src/session/persist.rs` 增加 `save_inflight` / `load_inflight` / `acquire_lease`。

### P2:高级特性(4-8 周)

**目标**:fork/branch、时间旅行、版本兼容。

| 任务 | 借鉴模式 | 实现要点 |
|------|---------|----------|
| 树状 fork | P6 | ChatMessage 增加 `parentId: Option<String>`,支持从任意消息分叉 |
| 时间旅行 | opencode revert | 增加 `revert` 状态,支持回退到某条消息重试 |
| 版本迁移 | P8 | `header.version` + `migrateLegacy*` 函数预留 |
| 会话列表/搜索 | - | 扫 `sessions/*.jsonl` 首行 header,按 mtime 排序 |
| 清理策略 | - | 默认 30 天 `cleanupPeriodDays`,参考 claudecode |

**关键文件**:新增 `src/session/fork.rs`、`src/session/revert.rs`。

```
P0 (必须)                P1 (重要)                P2 (增强)
─────────────────────────────────────────────────────────────
JSONL 落盘               inflight 检查点          树状 fork
原子写入                 OS 排他锁                时间旅行
撕裂修复                 per-id 串行化            版本迁移
resume 最近会话          大结果外置                会话搜索/清理
```

## 6. 结语

本轮深挖 6 个外部 Agent 仓库的会话持久化实现,覆盖存储格式、写入原子性、崩溃恢复、会话操作、多端同步、大消息处理、目录布局 7 个维度。核心发现:

1. **JSONL 是主流**(5/6 仓库使用),因其 append-only 天然适合对话流,按行读取避免全量加载。
2. **原子性实现分化**:atomcode/openclaw 用最严谨的 temp+fsync+rename+dir sync;claudecode/opencode 依赖单进程/写锁,不做原子 rename。
3. **崩溃恢复是分水岭**:atomcode(inflight 检查点)和 deepseek-harness(撕裂修复 + 合成 closers)最完善;claudecode/opencode 无崩溃恢复。
4. **树状会话是共识**:5/6 仓库支持 parent 链或 parentUuid,fork 是标配。
5. **laew 是「零持久化」**:当前纯内存,P0 方案(最小可用持久化)可直接借鉴 atomcode 的 Rust 实现,工作量约 1-2 轮迭代。

> **核心建议**:laew 应优先落地 P0 + P4(inflight 检查点),因为多 Agent 架构中 SubAgent-Work 执行耗时任务被杀是常见场景,恢复「已接受但未执行的用户消息」价值最高。
