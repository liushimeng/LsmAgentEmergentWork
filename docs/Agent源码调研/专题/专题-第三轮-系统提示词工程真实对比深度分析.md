## 2. 各仓逐个深挖

### 2.1 claudecode — 分段拼装 + 动态边界

**物理组织**:分段函数拼装 + `SYSTEM_PROMPT_DYNAMIC_BOUNDARY` 显式分界。
核心入口 `getSystemPrompt()` (`src/constants/prompts.ts:444`) 返回 `string[]`,分静态段(cacheable)和动态段(用户/会话相关)。

**真实 prompt 文本 — 身份段** (`src/constants/prompts.ts:175-184`):
```
You are an interactive agent that helps users with software engineering tasks.
Use the instructions below and the tools available to you to assist the user.

IMPORTANT: You must NEVER generate or guess URLs for the user unless you are
confident that the URLs are for helping the user with programming. You may use
URLs provided by the user in their messages or local files.
```

**安全约束 — 危险操作清单** (`src/constants/prompts.ts:256-266`):
```
# Executing actions with care

Carefully consider the reversibility and blast radius of actions. Generally you
can freely take local, reversible actions like editing files or running tests.
But for actions that are hard to reverse, affect shared systems beyond your
local environment, or could otherwise be risky or destructive, check with the
user before proceeding. ...

Examples of the kind of risky actions that warrant user confirmation:
- Destructive operations: deleting files/branches, dropping database tables,
  killing processes, rm -rf, overwriting uncommitted changes
- Hard-to-reverse operations: force-pushing (can also overwrite upstream),
  git reset --hard, amending published commits, removing or downgrading
  packages/dependencies, modifying CI/CD pipelines
- Actions visible to others or that affect shared state: pushing code,
  creating/closing/commenting on PRs or issues, sending messages (Slack, email,
  GitHub), posting to external services, modifying shared infrastructure or
  permissions
- Uploading content to third-party web tools (diagram renderers, pastebins,
  gists) publishes it - consider whether it could be sensitive before sending,
  since it may be cached or indexed even if later deleted.
```

**工具使用教学** (`src/constants/prompts.ts:269-314`):
```
# Using your tools

Do NOT use the Bash tool to run commands when a relevant dedicated tool is
provided. Using dedicated tools allows the user to better understand and review
your work. This is CRITICAL to assisting the user:
- To read files use Read instead of cat, head, tail, or sed
- To edit files use Edit instead of sed or awk
- To create files use Write instead of cat with heredoc or echo redirection
- To search for files use Glob instead of find or ls
- To search the content of files, use Grep instead of grep or rg
- Reserve using the Bash tool exclusively for system commands and terminal
  operations that require shell execution. ...

You can call multiple tools in a single response. If you intend to call multiple
tools and there are no dependencies between them, make all independent tool calls
in parallel. Maximize use of parallel tool calls where possible to increase
efficiency. However, if some tool calls depend on previous calls to inform
dependent values, do NOT call these tools in parallel and instead call them
sequentially.
```

**输出效率 — 外部用户版** (`src/constants/prompts.ts:416-428`):
```
# Output efficiency

IMPORTANT: Go straight to the point. Try the simplest approach first without
going in circles. Do not overdo it. Be extra concise.

Keep your text output brief and direct. Lead with the answer or action, not the
reasoning. Skip filler words, preamble, and unnecessary transitions. Do not
restate what the user said — just do it. ...

Focus text output on:
- Decisions that need the user's input
- High-level status updates at natural milestones
- Errors or blockers that change the plan

If you can say it in one sentence, don't use three. Prefer short, direct
sentences over long explanations. This does not apply to code or tool calls.
```

**动态环境注入** (`src/constants/prompts.ts:640-710`):
```
Here is useful information about the environment you are running in:
<env>
Working directory: ${getCwd()}
Is directory a git repo: ${isGit ? 'Yes' : 'No'}
${additionalDirsInfo}Platform: ${env.platform}
${getShellInfoLine()}
OS Version: ${unameSR}
</env>
${modelDescription}${knowledgeCutoffMessage}
```

**动态边界标记** (`src/constants/prompts.ts:114-115`):
```
export const SYSTEM_PROMPT_DYNAMIC_BOUNDARY =
  '__SYSTEM_PROMPT_DYNAMIC_BOUNDARY__'
```
注释(`src/constants/prompts.ts:106-113`)明确说:边界前内容可 `scope: 'global'` 缓存,边界后是用户/会话特定内容不应缓存。

**Hooks 段** (`src/constants/prompts.ts:127-129`):
```
Users may configure 'hooks', shell commands that execute in response to events
like tool calls, in settings. Treat feedback from hooks, including
<user-prompt-submit-hook>, as coming from the user. If you is blocked by a
hook, determine if you can adjust your actions based on the blocked message.
If not, ask the user to check hooks configuration.
```

**关键设计点**:
- 工具 description 是 prompt 的一部分,每个工具有独立 `prompt.ts`(如 `src/tools/BashTool/prompt.ts`)
- 有 `isUndercover()` 模式,对外隐藏模型 ID / 前沿模型名(`src/constants/prompts.ts:621-628`)
- 有 `getSimpleSystemSection()` 简单模式(`src/constants/prompts.ts:186-197`)
- 有 proactive / coordinator / REPL 等多种模式分支

You are in plan mode. Stay in plan mode until exit_plan_mode succeeds or the
user switches the session mode. Imperative language to implement changes means
plan the implementation, not execute it. A user's conversational agreement —
including an answer confirming something you asked — approves nothing and does
not end plan mode; fold the confirmed decision into the plan and submit it

implementation after an approved plan, while the plan itself belongs in
exit_plan_mode.

## 4. 8 大提示词工程模式提炼

### 模式 1:动态边界 + Cache 分段

**描述**:将 system prompt 分为静态段(可跨用户/会话缓存)和动态段(用户/会话特定),用显式边界标记。
**代表**:claudecode `SYSTEM_PROMPT_DYNAMIC_BOUNDARY`(`src/constants/prompts.ts:114`)
**原理**:Anthropic prompt cache 按 Blake2b 前缀哈希匹配,边界前内容可 `scope: 'global'`,边界后内容每次不同。

### 模式 2:模型家族人格定制

**描述**:为不同模型家族提供完全不同的 prompt 文本(不仅是尾缀差异)。
**代表**:opencode 14 个 .txt(`packages/opencode/src/session/prompt/`)、atomcode 弱模型纪律块(`persona.rs:346-425`)
**原理**:不同模型训练分布不同,anthropic 适合 "best coding agent" 强势人格,GPT 适合 "pragmatic engineer" 协作人格,弱模型需要 MANDATORY 硬规则。

### 模式 3:工具偏好硬规则 + Litmus 测试

**描述**:不仅说 "prefer dedicated tools",还给出具体判断标准(Litmus)和反例。
**代表**:atomcode `TOOL DISCIPLINE (MANDATORY)`(`persona.rs:346-356`) + claudecode `getUsingYourToolsSection()`(`src/constants/prompts.ts:269-314`)
**原理**:模型在模糊情况下会退化为 Bash,Litmus 测试("a pipeline that returns a COUNT → bash; anything that just reads bytes → file tool")消除歧义。

### 模式 4:失败行为显式建模

**描述**:不仅说 "handle errors",还列出具体的失败模式(隐藏错误、放弃过早、假完成)和对应规则。
**代表**:atomcode `EXECUTION DISCIPLINE (MANDATORY)`(`persona.rs:382-425`) + claudecode `getSimpleDoingTasksSection()`(`src/constants/prompts.ts:199-253`)
**原理**:模型在失败时容易产生模式化行为(重复相同命令、删除测试、声称成功),显式命名这些反模式并给出规则更有效。

### 模式 5:优先级声明(PRECEDENCE)

**描述**:显式声明 system prompt 默认规则 vs 用户/项目指令的优先级。
**代表**:atomcode `## PRECEDENCE:`(`persona.rs:210-217`)
**原理**:当 AGENTS.md/CLAUDE.md 中的指令与 system prompt 冲突时,模型需要知道哪个优先。atomcode 明确说 "用户指令优先,但安全/身份/模型不可覆盖"。

### 模式 6:冻结日期锚

**描述**:在 system prompt 中注入当前日期,但每会话只注入一次(而非每轮),保持 cache 稳定。
**代表**:atomcode `date_anchor_line()`(`persona.rs:430-432`) + opencode `Today's date`(`system.ts:81`)
**原理**:模型没有内置当前日期,web_search 默认使用训练年份。日期锚是 cache-stable 的(一天内不变),跨日刷新时通过 `reconcile_coding_persona` 重建。

### 模式 7:组合式 Section 注册

**描述**:将 prompt 拆分为独立 section,按 `order` 排序,支持 scoped 覆盖。
**代表**:deepseek-harness `SystemPrompt.section()`(`packages/core/system-prompt/src/index.ts:432-441`) + openclaw `buildOverridablePromptSection()`(`src/agents/system-prompt.ts:1288-1306`)
**原理**:不同部署/preset 可以替换某个 section(如 persona)而不影响其他 section,scoped 覆盖避免冲突。

### 模式 8:内容安全硬编码

**描述**:在 prompt 中直接写入内容安全规则(涉政/涉黄/涉暴),而非依赖服务端 moderation。
**代表**:atomcode `CONTENT SAFETY`(`persona.rs:121-158`)
**原理**:外部 provider 可能没有服务端 moderation,prompt 级是最后一道防线。明确区分 "do-not-generate" vs "may-handle"(分类/检测/清洗任务不过度拒绝)。

### 模式 9:输出效率量化锚

**描述**:给出具体的字数/行数限制,而非模糊的 "be concise"。
**代表**:claudecode `numeric_length_anchors`(`src/constants/prompts.ts:530-537`) "keep text between tool calls to ≤25 words" + opencode "fewer than 4 lines"
**原理**:定性 "be concise" 效果不稳定,定量锚(25 words / 4 lines)可测量且可 A/B。

### 模式 10:工具调用风格分场景

**描述**:区分 "何时静默调用" vs "何时叙述调用"。
**代表**:openclaw `## Tool Call Style`(`src/agents/system-prompt.ts:1295-1306`) "Routine low-risk: call silently. Narrate only complex, sensitive/destructive, or requested steps."
**原理**:所有调用都叙述会浪费 token,所有调用都静默会让用户困惑。按风险分场景。

### 模式 11:项目上下文 XML 包装

**描述**:用 XML 标签包装注入的项目上下文,明确标记 "非用户输入"。
**代表**:claudecode `<system-reminder>`、opencode `<env>` / `<available_references>`、pi `<project_context>` / `<project_instructions>`
**原理**:模型需要区分 "用户输入" 和 "系统注入",XML 标签是最明确的边界。

### 模式 12:协议尾缀差异化

**描述**:同一 prompt 对不同协议(Anthropic/OpenAI)追加不同尾缀。
**代表**:laew `set_protocol_tail()`(`src/agent/system_prompt/mod.rs:64-67`) + claudecode proactive 模式分支
**原理**:不同协议的工具调用语法不同(Anthropic `tool_use` vs OpenAI `function calling`),尾缀提醒模型使用正确语法。

## 6. 核心发现(5 条)

1. **opencode 为 14 个模型家族提供完全不同的 prompt 文本**(自信/协作/自主/客观等人格),证明"一 prompt 通吃"不是最优解 — `packages/opencode/src/session/prompt/` 14 个 .txt 文件。

2. **atomcode 按模型家族注入不同纪律块**(GLM/DeepSeek/Qwen 获得 `TOOL DISCIPLINE (MANDATORY)` + `EXECUTION DISCIPLINE (MANDATORY)` 硬规则,Claude/GPT 保持简洁),是"模型适配"最精细的实现 — `crates/atomcode-coding/src/persona.rs:325-425`。

3. **claudecode 用 `SYSTEM_PROMPT_DYNAMIC_BOUNDARY` 显式分界**(边界前 `scope: 'global'` 缓存,边界后用户/会话特定),是 prompt cache 工程化最完整的案例 — `src/constants/prompts.ts:114-115`。

4. **atomcode 的失败行为建模最具体**(命名 9 种反模式:FIX-DON'T-HIDE / EDIT-WITH-EDIT-TOOL / VERIFY-BEFORE-FINISHING / FINISH-THE-JOB / DON'T-QUIT-EARLY / PAST-FAILURE-ISN'T-A-VERDICT / DON'T-FAKE-FINISH / SIGNPOST-BEFORE-ACTING),是"如何让模型不犯错"的最佳参考 — `crates/atomcode-coding/src/persona.rs:382-425`。

5. **laew 当前 prompt 缺乏动态环境注入、失败行为建模、安全约束、并行调用显式指引**,与外部项目差距明显;但已具备多角色隔离和项目上下文注入两个强项,补齐 P0(环境注入 + 工具教学 + 并行指引)即可显著提升 — `src/agent/system_prompt/mod.rs:109-122`。
