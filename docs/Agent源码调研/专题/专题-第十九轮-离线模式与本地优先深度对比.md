### 1.2 openclaw：Gateway 三态探测（最完整实现）

openclaw 的离线检测走 Gateway 层统一处理：

**三态状态机**：
- `Online`：Gateway 可达，所有功能正常
- `Degraded`：Gateway 可达但性能下降（高延迟/部分失败），触发 Failover
- `Offline`：Gateway 不可达，进入离线模式

**16 种 FailoverReason**（`packages/gateway-protocol/src/`）：
- 超时类：`TIMEOUT_CONNECT`、`TIMEOUT_READ`、`TIMEOUT_TOTAL`
- 网络类：`NETWORK_ERROR`、`DNS_FAILURE`、`TLS_ERROR`
- 服务端类：`SERVER_ERROR`、`RATE_LIMITED`、`QUOTA_EXCEEDED`
- 客户端类：`CLIENT_ERROR`、`INVALID_REQUEST`
- 其他：`UNKNOWN`、`CIRCUIT_OPEN`、...

**时间驱动冷却**：
- Failover 后进入冷却期（可配），冷却期内不再尝试同一 provider
- 冷却期结束后 HalfOpen 探测（对齐 laew 的 H13 熔断器设计）

### 1.3 claudecode：无专用离线检测

claudecode 的「离线」概念分散在多处，无统一状态机：
- `src/services/api/promptCacheBreakDetection.ts`：Prompt Cache Break 检测（服务端缓存失效，非网络离线）
- `src/services/compact/microCompact.ts`：上下文压缩（与离线无关）
- `src/utils/ultraplan/ccrSession.ts`：会话级，无网络状态

**关键缺失**：claudecode 无法区分「网络断了」和「模型慢」，用户只能看到通用的等待动画。

### 1.4 pi：Lane 三态（最接近离线的逻辑模型）

pi 的 Lane 三态（`running` / `paused` / `drained`）虽为并发模型，但语义最接近离线状态机：
- `running`：正常执行（Online）
- `paused`：暂停，可恢复（Degraded）
- `drained`：排空，不再接受新任务（Offline-like）

**WriterLease fence**：离线恢复时的写入保护，防止 stale 写入。

### 1.5 关键设计差异

| 维度 | 无检测 | 二态 | 三态 |
|------|-------|------|------|
| 代表 | claudecode / atomcode | opencode / pi | openclaw |
| 降级精度 | 无法区分断网 vs 慢速 | 可区分断/连 | 可区分断/慢/正常 |
| 用户体验 | 通用等待动画 | 重连提示 | 精确状态表达 |

**laew gap L1821-L1830**：
- L1821 P0：无离线检测（网络断了只能等 SSE 超时）
- L1822 P0：无三态状态机
- L1823 P1：无探测频率与退避
- L1824 P1：无离线事件广播（TUI 横幅不反映网络状态）

### 2.2 openclaw：JSONL 事务日志（最完整实现）

openclaw 的请求排队走**事件溯源（Event Sourcing）**路线：

**核心机制**：
- 离线期间的请求/事件写入 JSONL 事务日志（追加写，崩溃安全）
- 每条记录带**时间戳 + 序列号 + 幂等键**
- 恢复连接后按 FIFO 顺序重放
- **不变式校验**：重放时校验前置条件（如「账户余额≥0」），不满足则跳过+告警

**JSONL 格式优势**：
- 追加写 = 崩溃安全（不会出现写一半的文件）
- 人类可读 = 可手动修复
- 行级原子 = 单行损坏不影响其他行

### 2.3 claudecode：后台任务队列

claudecode 的请求排队能力分散在后台任务体系：
- `cronScheduler.ts`（565 行）：定时任务调度（D15 覆盖）
- `cronTasks.ts`（458 行）：任务执行
- `cronTasksLock.ts`（195 行）：锁防重入
- `backgroundHousekeeping.ts`（94 行）：后台清理

**与离线的关系**：后台任务在离线时仍执行（本地 cron），但**不处理用户请求排队**。

### 2.4 undici：RetryHandler 队列

undici 的请求排队在 HTTP 层：
- `RetryHandler`：失败请求自动重试队列
- `RetryController`：背压控制（重试速率）
- 内存态，非持久化——进程退出队列丢失

### 2.5 关键设计差异

| 维度 | 内存队列 | JSONL 持久化 | SQLite 持久化 |
|------|---------|-------------|-------------|
| 崩溃安全 | ❌ | ✅ | ✅(WAL) |
| 可审计 | ❌ | ✅(可读) | ⚠️ |
| 实现复杂度 | 低 | 中 | 中 |
| 代表 | undici | openclaw | pi |

**laew gap L1831-L1840**：
- L1831 P0：无请求排队（离线请求直接丢失）
- L1832 P0：无持久化队列（进程退出队列丢失）
- L1833 P1：无上限与背压

### 3.2 deepseek-harness：prefix-stability 内容寻址（最精巧设计）

deepseek-harness 的本地优先走**内容寻址（Content-Addressable）**路线：

**核心机制**：
- 所有内容（代码/文档/配置）按 **sha256 修订号**寻址
- 本地存储完整历史（每个修订一个 blob）
- 离线时可访问任意历史版本
- 同步时按修订号 diff，只传增量

**prefix-stability**：
- 前缀稳定性保证——相同前缀的内容在缓存中稳定存在
- 离线期间缓存命中率高（前缀不变→内容不变）

**Write-Behind 一致性**：
- 写入先落本地（低延迟）
- 后台异步同步到远端
- 离线时写入正常，恢复后自动同步

### 3.3 pi：Session Backends 双后端

pi 的本地优先走**双后端**路线：
- `packages/session-backends/`：本地 SQLite + 远端 Session 双写
- 本地为 source of truth，远端为备份
- 离线时只写本地，恢复后合并

**WriterLease fence**：
- 写入需要获取 Lease（租约）
- 离线时 Lease 本地持有，恢复时与远端对账
- 防止「离线期间远端被其他设备修改」的冲突

### 3.4 claudecode：7 种应用缓存（云端依赖）

claudecode 的缓存体系（第十四轮已覆盖）以**云端为主**：
- Prompt Cache Break 检测
- 微压缩（microCompact）
- 插件 zip 缓存（`zipCacheAdapters.ts`）
- 市场（marketplace）元数据缓存

**离线限制**：缓存为加速在线访问，离线时无法创建新缓存条目。

### 3.5 关键设计差异

| 维度 | 云端为主 | 本地优先(内容寻址) | 本地优先(双后端) |
|------|---------|------------------|----------------|
| 代表 | claudecode | deepseek-harness/atomcode | opencode/pi |
| 离线能力 | 弱（只读缓存） | 强（完整历史） | 强（本地读写） |
| 存储开销 | 低 | 高（完整历史） | 中 |
| 同步复杂度 | 低 | 高（修订号 diff） | 中（Lease 对账） |

**laew gap L1841-L1850**：
- L1841 P0：无本地优先存储（API Key/配置存明文 SQLite，无修订历史）
- L1842 P1：无内容寻址
- L1843 P1：无 TTL/stale-while-revalidate
- L1844 P1：无离线只读能力

### 4.2 openclaw：10 万行审计 + Gateway（最重量级）

openclaw 的分布式本地优先是整个知识库中最重的基础设施：

**审计日志（10 万行）**：
- 所有操作（读/写/工具调用/决策）写入审计日志
- HMAC 假名化（用户标识不可逆加密）
- 支持合规审计（GDPR/SOC2）

**Gateway 多节点同步**：
- 多节点各自维护本地审计日志
- Gateway 统一编排同步
- 时间驱动冷却 + 16 种 FailoverReason

### 4.3 pi：Session Backends + Lease（最精巧）

pi 的分布式走**租约（Lease）**路线：
- 每个 Session 有唯一 Lease
- 写入需持有 Lease（排他）
- 多节点通过 Lease 协调——持 Lease 者为 SoT
- Lease 过期（节点失联）时，其他节点可接管

**CBOR 帧协议**：
- 节点间通信走 CBOR（二进制 JSON）
- 4-byte length prefix + strict subset（深度/长度/周期限制）
- 与 WriterLease fence 配合防止 stale 写入

- 限制：推理质量下降（小模型），但**功能不中断**

**降级矩阵示例**：
| 功能 | 在线 | 离线 |
|------|------|------|
| 代码生成 | Claude（高质量） | 本地 GGUF（中低质量） |
| 文件搜索 | Grep/Glob | 本地 Grep/Glob（不变） |
| Web 搜索 | ✅ | ❌ |
| 工具调用 | ✅ | ✅（本地执行） |

### 5.3 openclaw：16 种 Failover + 时间驱动冷却

openclaw 的降级最细粒度：
- 每种 FailoverReason 对应不同的降级策略
- 时间驱动冷却：Failover 后等待 T 再重试
- Gateway banner 实时显示状态

### 5.4 关键设计差异

| 维度 | 无降级 | 粗粒度 | 细粒度 | 离线 LLM |
|------|-------|-------|-------|---------|
| 代表 | claudecode/atomcode | opencode/pi | openclaw | deepseek-harness |
| 用户体验 | 卡顿/失败 | 重连提示 | 精确状态 | 功能不中断 |
| 实现成本 | 低 | 中 | 高 | 极高 |

**laew gap L1856-L1865**：
- L1856 P0：无降级矩阵（离线即失败）
- L1857 P1：无用户状态表达（TUI 横幅不反映网络）
- L1858 P2：无离线 LLM 回退
- L1859 P2：无功能级粒度降级

## 6. D13-6 同步与冲突合并

离线期间的写操作在恢复后如何与远端合并。

### 6.1 7 工程横向对比

| 工程 | 合并策略 | 版本向量 | 冲突检测 | 自动合并 | 代码量 |
|------|---------|---------|---------|---------|--------|
| **claudecode** | ❌ | — | — | — | 0 |
| **opencode** | ⚠️ Durable Object | ⚠️ | ⚠️ | ⚠️ | ~数百行 |
| **openclaw** | ✅ | ✅ | ✅ | ✅ | ~数百行 |
| **deepseek-harness** | ✅ Write-Behind | ✅ | ✅ | ⚠️ | ~数百行 |
| **atomcode** | ⚠️ OAuth 状态机 | ⚠️ | ⚠️ | ⚠️ | ~数百行 |
| **pi** | ✅ Lease | ✅ | ✅ | ✅ | ~数百行 |
| **undici** | N/A | — | — | — | — |
| **laew** | ❌ | — | — | — | 0 |

### 6.2 三种合并策略

**Last-Write-Wins（LWW）**：
- 最简单的策略——时间戳最新的写入获胜
- 丢失并发写入
- 代表：atomcode OAuth 状态机

**版本向量（Version Vector）**：
- 每个写入带向量时钟
- 可检测并发冲突（向量不可比较）
- 代表：openclaw Gateway

**CRDT（Conflict-free Replicated Data Type）**：
- 数据结构保证合并无冲突
- 代表：pi Delta CRDT（1268 行，第九轮已覆盖）

### 6.3 openclaw：Gateway 合并（最完整）

openclaw 的合并走**服务端权威**路线：
- Gateway 为唯一真理来源
- 节点离线期间写入暂存本地
- 恢复后上报 Gateway，Gateway 按版本向量裁决
- 冲突时按「最后写入优先 + 业务规则」合并

### 6.4 deepseek-harness：Write-Behind 一致性

deepseek-harness 的合并走**异步同步**路线：
- 写入先落本地（Write-Behind）
- 后台线程异步同步到远端
- 远端冲突时按修订号 diff
- 自动合并（相同文件不同区域）或标记冲突

**laew gap L1866-L1870**：
- L1866 P1：无同步合并（离线写入丢失）
- L1867 P2：无版本向量
- L1868 P2：无冲突检测
- L1869 P2：无自动合并

## 7. D13-7 连接恢复与重连

网络恢复后的行为——如何优雅地回到在线状态。

### 7.1 7 工程横向对比

| 工程 | 重连策略 | backoff 曲线 | 会话续接 | stale 清理 | 代码量 |
|------|---------|-------------|---------|-----------|--------|
| **claudecode** | ✅ 指数退避 | ✅ | ❌ | — | ~数百行 |
| **opencode** | ✅ WS 重连 | ✅ | ✅ | ✅ | ~数百行 |
| **openclaw** | ✅ 时间驱动冷却 | ✅ | ✅ | ✅ | ~数百行 |
| **deepseek-harness** | ✅ 自动重连 | ✅ | ✅ | ⚠️ | ~数百行 |
| **atomcode** | ⚠️ | ⚠️ | — | — | 少量 |
| **pi** | ✅ WriterLease | ✅ | ✅ | ✅ | ~数百行 |
| **undici** | ✅ RetryHandler | ✅ | — | — | ~数百行 |
| **laew** | ⚠️ 仅重试+熔断 | ✅ | ❌ | ❌ | ~数百行 |

### 7.2 opencode：WebSocket 重连（最清晰实现）

opencode 的 WS 重连机制：
- 断连后自动重连（1s→2s→4s→8s→最大 30s 指数退避）
- 重连成功后续接会话（不丢失上下文）
- stale 连接清理（超时未响应的连接主动关闭）
- 与 Durable Object 配合：重连后从 DO 恢复状态

### 7.3 claudecode：指数退避 + 熔断器（与 laew 最相关）

claudecode 的重连机制与 laew 的 `llm/resilient.rs` 高度相似：
- 指数退避（1s→2s→4s→8s）
- 熔断器三态（Closed/Open/HalfOpen）
- HalfOpen 单探测

**与 laew 的差异**：claudecode 的熔断器还会触发 `useOfflineStatus` 类 hook 更新 UI 状态，laew 的 H13 熔断器只控制请求，**无 UI 状态反馈**。

### 7.4 laew 当前重连能力

laew 现有的连接恢复：
- `llm/resilient.rs`：重试 + 熔断三态
- `llm/sse.rs`：idle 90s 超时
- **缺失**：
  - 无会话续接（SSE 断了上下文不恢复，需重连后重新开始）
  - 无 stale 连接清理
  - 无 UI 重连状态反馈

**laew gap L1871-L1880**：
- L1871 P1：无会话续接（SSE 断了需重开会话）
- L1872 P1：无 UI 重连状态反馈（TUI 横幅不变）
- L1873 P1：无 stale 连接清理
- L1874 P2：无重连后的请求重放
- L1875 P2：无重连成功事件通知

## 11. 设计哲学总结

### 11.1 离线能力层次

| 层次 | 能力 | 代表工程 |
|------|------|---------|
| L0 无 | 离线即失败 | laew |
| L1 检测 | 能感知网络状态 | openclaw |
| L2 降级 | 离线部分可用 | deepseek-harness |
| L3 本地优先 | 离线完整读写 | opencode/pi |
| L4 多节点 | 多设备同步 | openclaw/pi |

### 11.2 laew 的差异化定位建议

laew 作为 Rust CLI，应走 **「终端优先 + 本地优先」** 路线：
- SQLite 已为本地存储基础，扩展为本地优先 SoT
- JSONL 事务日志（崩溃安全 + 可读）替代复杂 CRDT
- 三态状态机 + TUI 横幅状态（`/offline` 斜杠命令）
- 可选 `ollama-rs` 离线 LLM 回退（低优先级，存储/网络层优先）
- 不追求多设备同步（CLI 单设备定位）

### 11.3 与既有 laew 能力的关系

| 既有能力 | 本轮增强 |
|---------|---------|
| `llm/resilient.rs` 重试+熔断 | 加 UI 状态反馈 + 会话续接 |
| `llm/sse.rs` idle 90s 超时 | 加断连探测 + 续接 |
| `agent/overflow.rs` 溢出恢复 | 加离线溢出处理 |
| 明文 SQLite | 加本地优先缓存分层 |
