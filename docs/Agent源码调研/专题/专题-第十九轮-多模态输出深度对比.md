### 2.2 opencode：shiki-wasm 双栈方案（最具代表性）

opencode 的语法高亮是整个知识库中最完整的「Web + TUI 双栈」范例：

**marked-parser.tsx**（68 行核心）：
```ts
import katex from "katex"
import { Marked, type MarkedExtension, type Tokens } from "marked"
import markedShiki from "marked-shiki"

export function createMarkdownParser(highlight: (code: string, language: string) => string | Promise<string>) {
  return new Marked(
    { renderer: { link({ href, title, text }) { /* OSC 8 超链接 */ } } },
    katexExtension,
    markedShiki({ highlight }),
  )
}
```

**关键设计**：
- `marked-shiki` 把 shiki 集成到 marked 的 `code` 渲染钩子
- `highlight` 回调由调用方注入：Web 端用 `shiki-wasm`，TUI 端用 ANSI 高亮
- `bundledLanguages`（来自 shiki）做语言名→shiki 语言 id 的映射
- 语言探测失败时回退到 `"text"`（无高亮，不崩溃）

**KaTeX 数学公式**（inline + block）：
```ts
const inlineMathRegex = /^\\\(((?:\\.|[^\\\n])*?)\\\)/
const blockMathRegex = /^\$\$\n([\s\S]+?)\n\$\$(?:\n|$)/const katexExtension: MarkedExtension = { extensions: [ /* inlineMath + blockMath */ ] }
```
- 行内公式：`\( ... \)`
- 块级公式：`$$ ... $$`
- TUI 端 KaTeX 无法渲染，回退到纯文本标记 `∑...`

### 2.4 atomcode：主动放弃 syntect

atomcode 做了一个**反直觉的工程决策**：
- 主动放弃 syntect（Rust 语法高亮库，性能最优）
- 主动放弃 truecolor（24-bit 色）
- 原因：**跨平台一致性优先**——syntect 在不同终端的配色差异大，truecolor 在老终端显示异常
- 改用固定 16 色 ANSI 方案，确保 Windows/macOS/Linux 三端一致
- `atomcode-tuix/src/render/retained.rs`：retained cell-based 渲染器，无语法着色

### 2.5 pi：自研 18 语言 ANSI 高亮

pi 采用最小可行方案：
- 自研正则高亮器，支持 18 种语言
- 输出固定 ANSI 转义序列（`\x1b[32m` 风格）
- 无 wasm、无 tree-sitter、无 TextMate
- 与 pi 的「轻量派」哲学一致

## 5. D10-5 终端图片协议

图片是终端渲染的「圣杯」——在不离开终端的前提下展示截图、图表、UI 设计。

### 5.1 终端图片协议三大家族

| 协议 | 原理 | 兼容性 | 代表工程 |
|------|------|--------|---------|
| **Sixel** | 光栅图形（6 色/像素） | 最广（xterm/foot/WezTerm） | claudecode |
| **Kitty** | PNG 内联（APC 序列） | Kitty/Alacritty/WezTerm | claudecode/opencode |
| **iTerm2** | Base64 内联（OSC 1337） | iTerm2 专属 | claudecode |

### 5.2 claudecode：三协议完整支持（最深度实现）

claudecode 的图片协议支持是整个知识库中最完整的：

**渲染管线**：
```
图片文件 → 探测终端能力 → 选择协议 → 内联嵌入
                ↓
        ┌───────┼───────┐
       sixel  kitty   iTerm2
```

**关键机制**：
- **终端能力探测**：查询 `TERM_PROGRAM` + `COLORTERM` + terminfo
- **自动降级**：Kitty → Sixel → iTerm2 → 文本占位符 `[图片]`
- **图片缓存 LRU**：避免重复渲染同一图片
- **Rust ColorFile 引擎**：高性能图片→ANSI 转换（第七轮已部分覆盖）
- **JS fallback**：Rust 不可用时回退到 JS 实现（LRU 500 条）

**原子code 的关联**：
- `atomcode/crates/atomcode-kernel/tests/multimodal.rs`：多模态（图片）处理测试
- `atomcode-kernel/src/message.rs`：消息中的图片块
- `atomcode-capabilities/src/tools/mod.rs`：图片工具能力

### 5.3 openclaw：HTML 公开分享替代终端图片

openclaw 的哲学不同：
- **不直接在终端渲染图片**（避免终端兼容性地狱）
- 而是**生成 HTML 公开分享链接**——用户点击链接在浏览器查看
- `packages/markdown-core/` 负责 HTML 生成
- 优势：完美图片渲染 + 可分享；劣势：需离开终端

### 5.4 关键设计差异

| 维度 | 终端图片协议优先 | HTML 分享优先 | 放弃 |
|------|---------------|-------------|------|
| 代表 | claudecode | openclaw | atomcode/pi |
| 离线性 | ✅ | ❌ 需浏览器 | — |
| 保真度 | 中（终端限制） | 高 | — |
| 复杂度 | 高（3 协议+降级） | 中 | 低 |

**laew gap L1681-L1690**：
- L1681 P1：无终端图片渲染（截图工具结果只能存文件路径）
- L1682 P2：无 Kitty/Sixel/iTerm2 协议适配
- L1683 P2：无图片缓存 LRU

## 6. D10-6 数学公式渲染

数学/科学计算场景的 Agent 输出需要 LaTeX 公式渲染。

### 6.1 7 工程横向对比

| 工程 | 公式引擎 | 行内公式 | 块级公式 | TUI 降级 | 代码量 |
|------|---------|---------|---------|---------|--------|
| **opencode** | **KaTeX** | ✅ `\(...\)` | ✅ `$$...$$` | ⚠️ 文本标记 | ~40 行 |
| **openclaw** | mdast 数学插件 | ✅ | ✅ | ⚠️ | 在 markdown-core 内 |
| **deepseek-harness** | ⚠️ 可选 | ⚠️ | ⚠️ | ⚠️ | 少量 |
| **claudecode** | ❌ | ❌ | ❌ | — | 0 |
| **atomcode** | ❌ | ❌ | ❌ | — | 0 |
| **pi** | ❌ | ❌ | ❌ | — | 0 |
| **undici** | N/A | — | — | — | — |
| **laew** | ❌ | ❌ | ❌ | — | 0 |

### 6.2 opencode：KaTeX 行内+块级双模式（最清晰实现）

opencode 的数学公式集成在 `marked-parser.tsx` 中（见第 2 节代码）：

**双正则匹配**：
```ts
const inlineMathRegex = /^\\\(((?:\\.|[^\\\n])*?)\\\)/
const blockMathRegex = /^\$\$\n([\s\S]+?)\n\$\$(?:\n|$)/
```

**渲染链路**：
```
Markdown 源 → marked 解析 → 数学扩展识别 → KaTeX.renderToString()
  → Web 端：HTML <span class="katex">
  → TUI 端：回退到纯文本标记 [公式: \sum_{i=1}^n x_i]
```

**关键设计**：
- 数学公式作为 `MarkedExtension` 注入，不侵入 marked 核心
- TUI 端无法渲染 SVG，用方括号标记 ` [公式: ...] ` 提示用户
- Web 端完美渲染，利用 KaTeX 的 `throwOnError: false` 容错

### 6.3 openclaw：mdast 数学插件

openclaw 的数学公式走 mdast 插件体系：
- `packages/markdown-core/` 中的数学插件
- mdast AST 中 `math` / `inlineMath` 节点类型
- 双输出：HTML（KaTeX 渲染）+ 终端（文本标记）

### 6.4 为什么多数工程不做数学公式

工程决策分析：
- **使用频率低**：Agent 对话中数学公式占比 < 1%
- **依赖重量**：KaTeX ~ 300KB，marked-shiki + katex 双依赖
- **终端限制**：TUI 无法渲染 SVG，HTML 端才完整
- **收益成本比**：多数工程选择「不渲染，保留原始 LaTeX」

**laew gap L1691-L1695**：
- L1691 P2：无 KaTeX 渲染（数学对话只能输出原始 LaTeX）
- L1692 P2：无行内/块级公式区分

**帧率节流**：

**虚拟列表**：
- `src/components/VirtualMessageList.tsx`：只渲染可视区内的消息

**流式消费**：
- SSE 流与 Ink 渲染解耦
- `src/components/Spinner.tsx`：流式等待动画
- `src/components/MessageRow.tsx`：逐 token 增量显示

**大文件截断**（第七轮 Bash PTY 专题已覆盖）：
- 30K 字符 / 150K 字符两档截断
- 截断后标记 `... [N lines truncated] ...`

### 7.3 atomcode/opencode：retained cell-based 增量重绘

atomcode 的 `atomcode-tuix/src/render/retained.rs` 和 opencode 的 retained 渲染：
- **只重绘变化的 cell**，而非全屏清除
- 减少终端闪烁 + 降低 CPU
- opencode 的 TUI 通过 `tui/src/` 组件实现

### 7.4 undici：流式背压（HTTP 底座贡献）

undici 虽非 Agent，但其流式机制支撑所有工程的 SSE 消费：
- `FixedQueue`：有界发送队列

- 流级背压（HTTP/2 flow control）
- 与 claudecode/opencode 的 Agent SSE 消费层对接

### 7.5 关键设计差异

| 维度 | 全量重绘 | 增量重绘 | retained cell |
|------|---------|---------|---------------|
| 闪烁 | 严重 | 无 | 无 |
| CPU | 高 | 低 | 最低 |

| 代表 | laew | claudecode(虚拟列表) | atomcode/opencode |

## 11. 设计哲学总结

### 11.1 终端优先 vs Web 优先

| 派别 | 工程 | 核心取舍 |
|------|------|---------|
| **终端优先** | claudecode / atomcode / pi | 完整终端图片协议 + ANSI 降级；代价是跨平台兼容性地狱 |
| **Web 优先** | opencode / openclaw / deepseek | HTML/Canvas 完美渲染 + 公开分享；代价是需离开终端 |
| **混合** | opencode（shiki-wasm 双栈） | Web 端 wasm 高亮 + TUI 端 ANSI 高亮，共享 marked 解析 |

### 11.2 高亮引擎选型

| 引擎 | 准确度 | 性能 | 语言数 | 离线 |
|------|-------|------|-------|------|
| 正则 | 低 | 最快 | 10-20 | ✅ |
| tree-sitter | 高 | 中 | 40+ | ✅ |
| shiki (服务端 TextMate) | 最高 | 中 | 100+ | ❌ |
| shiki-wasm | 最高 | 快 | 100+ | ✅ |

### 11.3 laew 的差异化定位建议

laew 作为 Rust CLI，应走 **「终端优先 + 离线优先」** 路线：
- `syntect`（内嵌语法集，无需 wasm/网络）替代 shiki-wasm
- `viuer` + `sixel` 终端图片（claudecode 路线的 Rust 等价）
- `pulldown-cmark` + `unicode-width` Markdown（GFM，CJK 友好）
- 不追求 HTML 分享（与 CLI 定位不符）
