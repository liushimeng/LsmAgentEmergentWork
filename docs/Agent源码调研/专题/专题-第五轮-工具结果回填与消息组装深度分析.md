## 2. tool_result 回填的运行时细节

### 2.1 Anthropic 与 OpenAI 协议差异

**Anthropic(协议)**:
```json
{
  "role": "user",
  "content": [
    { "type": "tool_result", "tool_use_id": "toolu_xxx", "content": "...", "is_error": false }
  ]
}
```
- 多个 tool_result 可放在同一个 user message 的 content array 里
- 严格配对:`tool_use_id` 必须出现在前序 assistant 的 `tool_use` block

**OpenAI**:
```json
{
  "role": "tool",
  "tool_call_id": "call_xxx",
  "content": "..."
}
```
- 每个 tool_result 必须是独立 message(role="tool")
- 同样严格配对,但结构不同

### 2.2 各仓库的实现路径

#### atomcode:Rust 协议中立 + 转 wire

`ToolResult` 结构(协议中立):
```rust
pub struct ToolResult {
    pub call_id: String,
    pub content: String,
    pub is_error: bool,
    // ...
}
```
- `llm/anthropic.rs` 把它转为 `ContentBlock::ToolResult { tool_use_id, content, is_error }`
- `llm/openai.rs` 转为 `Message { role:"tool", tool_call_id, content }`

#### claudecode:协议中立 messages + wire 转换

```ts
// src/Tool.ts 通用返回
interface ToolResult {
  content: string | ContentBlock[]
  isError?: boolean
}
// src/utils/api.ts 转换
// anthropic 模式:role="user", content=[{ type:"tool_result", tool_use_id, content, is_error }]
// openai 模式:role="tool", tool_call_id, content
```

#### deepseek-harness:events 流 + source 标记

工具结果作为 session event 追加:
```ts
session.append('tool_result', {
  callId: '...',
  output: '...',
  source: { kind: 'plugin', plugin: 'tool' }  // 类似 checkpoint 标记
})
```
- 与 compaction 一致用 `kind:'plugin'` 标记,可统一识别哪些是"自动产物"。

#### opencode:MessageV2 part 模型

```ts
type Part =
  | { type: "text"; text: string }
  | { type: "tool"; toolCallId, toolName, state: "pending"|"running"|"completed"|"error", output?: string }
  // ...
```
- 每个 assistant message 包含 parts 数组,tool result 是 part.state 的一部分
- transform 层(`transform.ts:358-381`)按 provider 分发 cache

#### pi:显式类型 + 截断元信息

```ts
type AssistantMessage = {
  role: "assistant"
  content: AssistantContent  // 可能是 text 或 toolCall 数组
  // ...
}
type ToolResultMessage = {
  role: "toolResult"
  toolCallId: string
  output: { content: Content[], isTruncated: boolean, truncation: TruncationResult }
}
```
- `isTruncated` 显式标记,模型可决定是否要求更多输出

### 2.3 并发多工具调用的顺序保证

**关键问题**:LLM 一次返回多个 `tool_use` 时,工具执行的顺序 vs 回填的顺序。

| 仓库 | 顺序保证 |
|---|---|
| atomcode | `FuturesOrdered` 保持 emission 顺序(详见第五轮 19.5 节) |
| claudecode | 并发执行,但 ToolResult 按 tool_use 出现顺序回填 |
| deepseek | `agent/pre-step` 钩子串行化,但 internal step 可并行 |
| opencode | processor 串行处理,stream 内顺序 |
| pi | 同 opencode,串行 streamSimple 派发 |

## 3. 工具结果截断与降级

### 3.1 三类截断位置

1. **工具内部截断**:工具自己决定多少内容写到 stdout(如 bash 的 head/tail 截断)
2. **回填前截断**:在 messages 数组里限制每条 tool_result 大小
3. **组装前总预算**:所有 tool_result 加起来不超过单 message 上限

### 3.2 各仓库的具体数值

#### atomcode
```rust
const MAX_SUMMARY_BYTES: usize = 64 * 1024;          // 摘要 64 KiB
const MAX_SUMMARY_TOKENS: u32 = 16_000;
const SUMMARY_TOOL_OUTPUT_MAX_CHARS: usize = 2_000;  // 摘要输入头
const SUMMARY_TOOL_OUTPUT_TAIL_CHARS:  usize = 500;   // 摘要输入尾
```
- 注意这是**压缩时**用的,不是普通回填时。
- 普通 tool_result 截断在工具内部自行处理(详见第五轮 19.5 节)。

#### claudecode
```ts
// src/constants/toolLimits.ts
DEFAULT_MAX_RESULT_SIZE_CHARS = 50_000  // 单工具默认
MAX_TOOL_RESULT_TOKENS = 100_000        // ~400KB
MAX_TOOL_RESULTS_PER_MESSAGE_CHARS = 200_000  // 单 user message 聚合

// 工具覆盖
Bash: maxResultSizeChars = 30_000       // 覆盖默认
FileRead: maxResultSizeChars = Infinity  // 显式不限
```

**每 message 聚合上限执行点**(`query.ts:379`):
```ts
await applyToolResultBudget(messagesForQuery, ...)
// 注释:大块按 tool_use_id 替换为文件路径 preview
```

#### opencode
```ts
// tool/truncate.ts
MAX_LINES = 2000
MAX_BYTES = 50 * 1024

// tool/read.ts
MAX_LINE_LENGTH = 2000   // 行级
```

#### pi
```ts
// coding-agent/src/core/tools/truncate.ts
DEFAULT_MAX_LINES = 2000
DEFAULT_MAX_BYTES = 50 * 1024
```

#### openclaw
```ts
// tool-call-repair/src/stream-normalizer.ts
MAX_PAYLOAD_BYTES = 256_000
MAX_PENDING_EVENTS = 256
MAX_PROTECTED_CONTEXT_CHARS = 1_000_000
MAX_TOOL_NAME_CHARS = 120
```

#### deepseek
- 无固定截断上限,按 retainTokens 动态计算
- `selectCompactableRange` 保留 tail 至达到 `retainTokens`

### 3.3 截断格式

**claudecode Bash**(`src/tools/BashTool/utils.ts:156-162`):
```ts
const truncatedPart = content.slice(0, maxOutputLength)
const truncated = `${truncatedPart}\n\n... [${remainingLines} lines truncated] ...`
```

**opencode 行级**(`tool/read.ts:14-17`):
```ts
const MAX_LINE_SUFFIX = `... (line truncated to ${MAX_LINE_LENGTH} chars)`
```

**pi 截断元信息**(`bash.ts:384`):
```ts
truncation: snapshot.truncation.truncated ? snapshot.truncation : undefined,
// TruncationResult { truncated: bool, totalLines/Bytes, lastLine/Byte }
```

## 4. 每轮请求前的消息组装管线

### 4.1 5 个阶段(所有仓库通用)

1. **System prompt 分段拼接**
2. **历史消息清理(prune/erase old tool result)**
3. **缓存断点注入(cache_control / cache_point)**
4. **图片/附件进消息(base64 / url)**
5. **最终 wire 转换(anthropic / openai 各自格式)**

### 4.2 System prompt 分段

#### claudecode
```ts
// src/QueryEngine.ts:321-325
const systemPrompt = asSystemPrompt([
  ...(customPrompt !== undefined ? [customPrompt] : defaultSystemPrompt),
  ...(memoryMechanicsPrompt ? [memoryMechanicsPrompt] : []),
  ...(appendSystemPrompt ? [appendSystemPrompt] : []),
])

// src/query.ts:449-451
const fullSystemPrompt = asSystemPrompt(
  appendSystemContext(systemPrompt, systemContext)
)
```
- 4 段:customPrompt / memoryMechanics / appendSystemPrompt / systemContext(CLAUDE.md)
- 顺序关键:memoryMechanics 在中间,避免被工具的 appendSystemPrompt 覆盖

#### atomcode
- Base + Skill + Hook + Environment(详见第四轮文档)
- 顺序:base → skill 展开 → hook 注入 → 环境(目录/git/env)
- `order` 字段控制具体位置

#### opencode
```ts
// transform.ts:358-381 applyCaching
// system 前 2 条 + 非 system 末 2 条打 ephemeral
```

#### deepseek
- 静态 + 动态 + plugin context
- `order` 字段(类似 atomcode)控制拼接位置

### 4.3 CLAUDE.md / AGENTS.md / README.md 加载

**claudecode 三作用域**(`src/utils/claudemd.ts`):

- 排除规则:`claudemd.ts:540` `claudeMdExcludes`

**laew 现状**(`CLAUDE.md` 描述):以工作目录为基准五级链发现 CLAUDE.md→AGENTS.md→README.md→自动生成→空。

### 4.4 cache_control 注入

#### opencode 6 provider 分发

## 5. 孤儿与异常消息修复

### 5.1 5 种异常场景

1. **孤儿 tool_use**:assistant 发起但 tool_result 没回来(中断/崩溃)
2. **孤儿 tool_result**:tool_result 没有配对的 tool_use(损坏)
3. **半截 assistant 消息**:流中断导致 assistant 消息只完成一半
4. **跨协议校验失败**:wire 转换后发现消息不合规
5. **plain-text 工具调用**:LLM 没走 schema 直接输出工具调用文本(乱码)

### 5.2 修复策略对比

| 场景 | atomcode | claudecode | deepseek | openclaw | opencode | pi |
|---|---|---|---|---|---|---|
| 1 孤儿 tool_use | `backfill_missing_tool_results("(cancelled)")` | yield `UserInterruptionMessage` | compaction/end 事务 | turn-handoff 合成 user 消息 | processor `return "stop"` | emit `turn_end` + `agent_end` |
| 2 孤儿 tool_result | `repair_pairing(convo.messages)` | 启动时校验 | session event 校验 | — | MessageV2 校验 | session startup 校验 |
| 3 半截 assistant | 流中断不保存 | 流中断不保存 | finish.kind==='aborted' 报错 | stream-normalizer 兜底 | takeUntil 优雅终止 | stopReason='aborted' 短路 |
| 4 wire 校验失败 | error.rs 映射 | API 400 重试 | `agent/request-error` 钩子 | repair 五阶段 | retry policy | retry with backoff |
| 5 plain-text | n/a | n/a | n/a | **tool-call-repair 五阶段** | n/a | n/a |

### 5.3 openclaw 的 tool-call-repair(独家)

LLM 输出 plain-text 工具调用时(没走 schema),五阶段管线(详见第五轮 16.2 节):

1. **Grammar**:标记定义(`END_TOOL_REQUEST`、`HARMONY_CHANNEL_MARKER`、`<|call|>` 等)
2. **Payload**:块解析(`harmony` / `named-bracket` / `tool-bracket`)
3. **Protection Fast-Path**:识别 fenced code、缩进块、`>`、`-/*/+`、`1.` 等保护范围
4. **Stream Normalizer**:流事件归一化,在保护范围外扫描
5. **Promote**:已识别块升级为 `{type:"toolCall", id, name, arguments, partialArgs}` 完整生命周期

**关键常量**:`MAX_PAYLOAD_BYTES=256_000`、`MAX_PENDING_EVENTS=256`、`MAX_PROTECTION_CONTEXT_CHARS=1_000_000`。

**laew 现状**:tool_result 错误直接返回,无修复路径。

### 5.4 deepseek 的工具对配对保护

`region.ts:317-338` 的 `toolPairingBalancedBefore` / `toolPairingBalancedAfter`:

```ts
// region 边界必须落在 toolPairingBalanced=true 的位置
// 否则 keepFromIdx-- 继续后退直到配对平衡
while (keepFromIdx > 0) {
  if (toolPairingBalancedBefore(session, surfaceNodes[keepFromIdx]!)) break
  keepFromIdx -= 1
}
```
- **设计要点**:压缩不能切断 tool-call/result 对——否则下次请求 400

### 5.5 claudecode 的 system message 校验

`QueryEngine.ts:762-807` 显式校验 `stop_reason`:

```ts
if (message.message.stop_reason != null) lastStopReason = message.message.stop_reason
if (message.event.delta.stop_reason != null) lastStopReason = message.event.delta.stop_reason
```
- 注释(`query.ts:554`):「`stop_reason === 'tool_use'` is unreliable — it's not always set correctly.」
- 因此 stopReason 跟踪**显式**维护,而不依赖 wire 字段

## 6. 共性模式总结

### 6.1 截断三档:工具内 / 单结果 / 单 message 聚合

- **工具内**:Bash/FileRead 等决定自己多少内容
- **单结果**:截断后插入提示符(`[N lines truncated]`)
- **单 message 聚合**:claudecode 200k char 上限(`query.ts:379` applyToolResultBudget)

laew **只**有工具内截断(隐式,无显式上限)。

### 6.2 50KB / 2000 行是行业默认

claudecode / opencode / pi 都是 `MAX_BYTES=50*1024` + `MAX_LINES=2000`。
- 50KB ≈ 12.5k tokens(以 BYTES_PER_TOKEN=4 算)
- 2000 行 ≈ 普通日志一个完整 unit

laew 无此上限,大输出会直接塞进 context。

### 6.3 协议中立 ToolResult → 转 wire

所有仓库都遵循同一模式:
1. 工具返回协议中立结构(`{call_id, content, is_error}`)
2. wire 转换层(anthropic / openai 各自)把它变为协议特定 message
3. 错误也作为正常 message 回填(`is_error=true`),不抛异常中断 loop

laew `src/llm/anthropic.rs` 和 `src/llm/openai.rs` 已采用此模式,但 `src/agent/mod.rs:146` 直接 push `ChatMessage::tool_result` 缺少截断。

### 6.4 截断元信息回传模型

pi 把 `TruncationResult { truncated, totalLines, lastLine }` 回传模型,模型可决定是否要求更多。
claudecode Bash 简单追加 `[N lines truncated]`。
opencode 行级追加 `... (line truncated to 2000 chars)`。

**回传元信息的好处**:模型可主动用 Read 工具分页,而不是猜测。

### 6.5 Cache 断点按 provider 分发

opencode 6 provider,claudecode anthropic/openai 两套,deepseek 通过 transport 注入。
- 字段名因 provider 而异(anthropic `cache_control`, bedrock `cachePoint`, copilot `copilot_cache_control`)
- 位置:system 前 2 + 非 system 末 2(常用模式)

laew **无任何 cache 注入**——可在 `src/llm/anthropic.rs` 加 system 末尾 `cache_control:{type:'ephemeral'}` 起步。

### 6.6 Prune 阈值保护最近 turn

opencode `PRUNE_PROTECT=40K` + 跳近 2 turn;claudecode `HISTORY_SNIP` snipTokensFreed 回馈阈值判断。

laew 无此机制,完全靠模型 context window。
