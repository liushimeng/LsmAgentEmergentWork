## 1. 横向对比总览表

### 1.1 核心机制对比

| 维度 | Claude Code | AtomCode | OpenClaw | OpenCode | DeepSeek-Harness | Pi |
|------|-------------|----------|----------|----------|-----------------|-----|
| **分类维度** | 多维度：`effort`(high/low/medium) + `context`(fork/inline) + `agent` 指定 | 二维：难度(fast/capable) + 工具集(explore/worker) | 单维：Harness 选择(priority 降序) + exec risk(4 级) | 单维：Agent 模式(primary/subagent/all) | 单维：GoalPhase(4 状态) | 单维：drive 模式(automatic/manual) |
| **分类触发点** | 用户侧：Skill YAML 声明；模型侧：AgentTool 调用 | 模型侧：TaskTool 参数决定 | 系统侧：`selectAgentHarness()` 自动选择 | 用户侧：配置文件 `agent` 字段或 `/agent` 切换 | 模型侧：`tool-goal` 工具 create/update | 用户/系统侧：Harness 构造时 `drive` 参数 |
| **分类粒度** | 3 级 effort + 2 种 context + 按 Skill 配置的 agent/model | 2 档难度(fast/capable) + 2 类工具集(explore/worker) | 11-capability Harness + 4 级 risk | 7 种内置 Agent 角色 | 4 种 GoalPhase + 可配置 maxGoalRounds | 2 种 drive 模式 + 3 种 QueueMode |
| **任务拆解方式** | Coordinator 拆子任务 → 分配给 Team/Swarm；Skill fork 模式委派子 Agent | 主 agent 通过 TaskTool 发起子 agent，scope 约束写入范围 | `spawnSubagentDirect()` 9 步 spawn 流程 + Swarm FIFO 容量控制 | SessionPrompt.loop() 自驱动；子 Agent 通过工具调度 | round driver 自动续轮 + tool-goal 模型自助管理 | Lane 并发分支 + steer/followUp/nextRun 三队列 |
| **失败处理** | Hook PreToolUse/PostToolUse 拦截；Task 系统 Pending/Running/Failed/Cancelled | VerifyCadenceHook 编辑后验证；nuke → stop 熔断 | Run 4 种终态(completed/aborted/blocked/error)；失败回退到内置 harness | doom_loop 3 次精确重复 → 权限请求；retry 状态自动重试 | GoalPhase blocked 状态 + round-limit 自动阻塞 | LaneBusy 错误；suspended → resume 恢复 |
| **与 laew 最相似点** | Skill 多维度调度 ≈ laew Yolo 三档 | 子 Agent 难度分档 ≈ laew simple/hard | Harness 可插拔 ≈ laew 多 Agent 角色 | Agent 权限隔离 ≈ laew AgentRole | Goal 自动续轮 ≈ laew Main-Work 流程 | Lane 并发 ≈ laew SubAgent 并发执行 |

### 1.2 分类策略光谱

```
隐式分类（间接/被动）                                    显式分类（直接/主动）
←─────────────────────────────────────────────────────────────────────────→
Pi(drive)  OpenCode(permission)  OpenClaw(harness)  AtomCode(fast/capable)  DeepSeek(GoalPhase)  Claude Code(effort)
```

laew 的 Yolo 三档分类位于光谱的**显式端**，与 DeepSeek-Harness 和 Claude Code 同属一类。

```
粗粒度（单层）                                           细粒度（多层嵌套）
←─────────────────────────────────────────────────────────────────────────→
OpenCode(单循环)  Pi(lane分叉)  AtomCode(子agent派发)  DeepSeek(round driver)  OpenClaw(9步spawn)  Claude Code(4层)
```

## 2. Claude Code：Coordinator + Skill 多维度调度

### 2.1 分类方式

Claude Code 的任务分类是**多维度叠加**的，不存在单一的"任务级别"概念。分类发生在三个层面：

**层面一：Skill 声明级（用户/开发者配置）**

Skill YAML frontmatter 中声明了三个分类维度：

```yaml
---
effort: high | low | medium      # 推理力度
context: fork | inline           # 执行上下文（子 Agent vs 当前对话）
agent: agent-name                # 指定 Agent
model: opus | sonnet | haiku     # 模型选择
paths: ["src/**", "tests/**"]    # 条件激活路径
---
```

- `effort` 字段直接控制推理力度，三档映射到不同的 token 预算和思考深度
- `context: fork` 启动隔离子 Agent（`runForkedAgent`），`inline` 注入当前对话
- `agent` 字段可指定特定 Agent 角色执行该 Skill
- `paths` 字段实现条件激活：只有当用户操作的文件匹配路径模式时才激活该 Skill

**层面二：Agent Tool 调用级（模型运行时决策）**

模型在对话过程中可通过 `AgentTool` 主动发起子任务。Claude Code 的 SubAgent 体系分四层：

```
层次 1: Fork 子 Agent    — 轻量级，共享 prompt cache，用于 compact/skill
层次 2: AgentTool        — 模型通过 Agent 工具启动子 Agent（同步/异步）
层次 3: Task 系统        — 后台任务（异步执行 + 结果检索）
层次 4: Team/Swarm       — 多 Agent 团队协作
```

各层次的上下文传递方式不同：

| 模式 | 上下文隔离 | Prompt Cache | 用途 |
|------|-----------|-------------|------|
| Fork 子 Agent | 隔离消息，共享 cache-safe 参数 | 共享 | compact、skill fork |
| AgentTool（同步） | 完全隔离 | 独立 | 模型启动的子任务 |
| AgentTool（异步） | 完全隔离 | 独立 | 后台任务 |
| InProcessTeammate | 共享进程 | 独立 | 进程内队友 |

**层面三：Coordinator 编排级（高级模式）**

`coordinatorMode.ts`（19K）是 Claude Code 的高级编排层：
- 消息路由：将用户消息路由到合适的 Agent
- 任务分配：将大任务拆解为子任务分配给多个 Agent
- 结果聚合：收集各 Agent 的结果并汇总
- Agent 间通信：通过 `SendMessageTool` 实现

### 2.2 分类级别详解

| 维度 | 级别 | 含义 | 实现机制 |
|------|------|------|---------|
| effort | high | 全量推理，最大 token 预算 | 传递给模型的 thinking 配置 |
| effort | medium | 标准推理 | 默认配置 |
| effort | low | 轻量推理，节省 token | 降低 max_tokens |
| context | fork | 隔离子 Agent，独立消息上下文 | `runForkedAgent()` 创建独立会话 |
| context | inline | 注入当前对话 | `processPromptSlashCommand()` 注入消息 |
| Agent 层次 | Fork | 最轻量 | `forkedAgent.ts`，共享 cache-safe 参数 |
| Agent 层次 | AgentTool | 模型主动发起 | `AgentTool/runAgent.ts` |
| Agent 层次 | Task | 后台异步 | `TaskCreateTool` → `LocalAgentTask` |
| Agent 层次 | Team/Swarm | 多 Agent 并发 | `utils/swarm/` 多后端支持 |

### 2.3 Skill 条件激活机制

```typescript
// loadSkillsDir.ts:997
export function activateConditionalSkillsForPaths(filePaths, cwd) {
  for (const [name, skill] of conditionalSkills) {
    const skillIgnore = ignore().add(skill.paths);
    for (const filePath of filePaths) {
      if (skillIgnore.ignores(relativePath)) {
        dynamicSkills.set(name, skill);
        conditionalSkills.delete(name);
      }
    }
  }
}
```

这是一种**文件路径驱动的动态分类**：用户的文件操作自动触发相关 Skill 的激活，无需用户显式选择。

### 2.4 拆解粒度

- **Skill 级**：每个 Skill 是一个完整的、可独立执行的任务单元，由 Markdown 正文定义执行步骤
- **Task 级**：`TaskCreateTool` 创建后台任务，`TaskGetTool` 获取结果，粒度由模型决定
- **Team 级**：Swarm 支持多 Agent 并发执行，有独立的后端抽象（InProcess / Remote / LocalShell）

Task 系统的完整状态机：

```
TaskCreateTool → Pending → Running → Completed
                                → Failed
                                → Cancelled（手动停止）
```

### 2.5 失败处理

- **Hook 拦截**：5 种 Hook 执行器（command / prompt / agent / http / callback）在 `PreToolUse` / `PostToolUse` 阶段拦截
- **Task 生命周期**：`Pending → Running → Completed | Failed | Cancelled`，支持手动停止
- **Swarm 后端**：每种后端有独立的失败处理逻辑
- **协调器**：结果聚合时可处理部分失败
- **压缩后恢复**：文件、plan、skill 等关键状态必须在压缩后重新注入

### 2.6 对 laew 的借鉴点

1. **Skill 的 `effort` 字段**：laew 可以在 Yolo 分类后为不同级别设置不同的推理力度
2. **`context: fork` vs `inline`**：laew 的 SubAgent 目前是 fork 模式，可考虑增加 inline 模式用于轻量任务
3. **条件激活 Skill**：laew 可以根据用户操作的文件类型自动注入相关上下文
4. **四层 SubAgent 体系**：laew 目前只有 SubAgent-Work 一层，可参考分层设计

## 3. AtomCode：L2 层按难度派发 + RiskLevel 风险分级

### 3.1 分类方式

AtomCode 采用**三层架构**（L0 Kernel / L1 Capabilities / L2 Coding），任务分类主要发生在 L2 业务层。这是 Rust 生态中最接近 laew 的设计。

**子 Agent 派发的二维分类**：

```rust
// crates/atomcode-capabilities/src/tools/task.rs
const DEFAULT_MAX_CONCURRENT: usize = 3;
```

`TaskTool` 把子任务派发给隔离上下文的子 agent，分类沿两个维度展开：

| 维度 | 选项 | 含义 | 工具集 |
|------|------|------|--------|
| 难度 | fast | 快速执行，轻量模型/少轮次 | 可配置 |
| 难度 | capable | 深度执行，强模型/多轮次 | 可配置 |
| 工具集 | explore | 只读探索 | grep / glob / read |
| 工具集 | worker | 可编辑执行 | bash / read / write / edit |

主 agent 根据任务性质**按难度选档位**（fast/capable），**按类型选工具集**（explore/worker）。这是一个 2×2 的分类矩阵。

**工具风险分级（RiskLevel）**：

```rust
// crates/atomcode-kernel/src/tool.rs
pub enum RiskLevel {
    Safe,
    Risky,
}

// 每个工具实现 arg-aware 的风险判断
fn risk(&self, args: &str) -> RiskLevel { RiskLevel::Safe }
```

`risk()` 是 **arg-aware** 的：
- `BashTool`：根据命令内容判断——`check_destructive_command()` 检测特权提升、递归强删、`find -delete`、`dd`、fork bomb 等
- `ReadFileTool`：永远 Safe
- `EditFileTool`：永远 Risky（因为修改文件）
- `WriteFileTool`：永远 Risky

**执行策略位图（ExecutionPolicy）**：

```rust
// crates/atomcode-coding/src/execution_policy.rs
const NO_BUILD: u8 = 1 << 0;
const NO_TEST: u8 = 1 << 1;
const NO_SCRIPT: u8 = 1 << 2;
const NO_SHELL: u8 = 1 << 3;
const NO_VERIFY: u8 = 1 << 4;

pub(crate) struct ExecutionPolicy(u8);
```

从用户文本中解析约束（如"不要运行测试"），通过 `TurnExecutionPolicy`（同时实现 `LifecycleHooks` 和 `ToolMiddleware`）在每轮更新并执行。`skips_verification()` 为 true 时 `VerifyCadenceHook` 跳过验证。

这是一种**用户意图约束分类**，将自然语言转化为机器可执行的约束。

### 3.2 参数化系统提示词

AtomCode 的系统提示词是**参数化的**，根据任务特征动态组装：

```rust
// crates/atomcode-coding/src/persona.rs
pub fn coding_persona_with_capabilities(...) -> String {
    let mut p = format!("You are AtomCode...");
    // 按条件注入
    if model_needs_firm_tool_steering(model) { p.push_str(FIRM_TOOL_DISCIPLINE); }
    if model_needs_firm_execution(model) { p.push_str(FIRM_EXECUTION_DISCIPLINE); }
    if todo_enabled { p.push_str(TODO_USAGE); }
    if subagents_enabled { p.push_str(SUBAGENT_DELEGATION); p.push_str(TEAM_DELEGATION); }
    if review_enabled { p.push_str(CODE_REVIEW_USAGE); }
    p
}
```

弱模型（GLM/DeepSeek/Qwen/LongCat）额外注入 `FIRM_TOOL_DISCIPLINE`（强制用专用工具而非 shell），DeepSeek/Qwen 额外注入 `FIRM_EXECUTION_DISCIPLINE`（不删代码清错误、不未经验证就提交等）。

### 3.3 Plan 模式 / Apply 模式

```rust
// crates/atomcode-coding/src/plan_mode.rs
pub struct PlanModeGate {
    active: Arc<AtomicBool>,
    mcp_grants: Arc<dyn PermissionStore>,
}
```

**Plan 模式策略**：
- 内置 Risky 工具（bash/edit/write）→ **硬阻断**
- MCP 工具 `readOnlyHint: true` → **允许**（只读外部查询）
- 其他 MCP 工具 → **提示**用户决定
- `PlanModeReminderHook` 通过 `pre_request` 注入提醒："Do NOT create, edit, or delete files"

切换机制：`Arc<AtomicBool>` 共享给 `PlanModeGate`（ToolMiddleware）和 `PlanModeReminderHook`（LifecycleHooks），driver 调用 `CodingRuntime::set_mode()` 即时切换，无需 respawn。

### 3.4 分类级别汇总

| 分类类型 | 级别 | 说明 | 实现位置 |
|---------|------|------|---------|
| 难度 | fast | 子 agent 快速模式 | TaskTool 参数 |
| 难度 | capable | 子 agent 深度模式 | TaskTool 参数 |
| 工具集 | explore | 只读探索 | TaskTool 参数 |
| 工具集 | worker | 可编辑执行 | TaskTool 参数 |
| 风险 | Safe | 自动批准 | Tool::risk() |
| 风险 | Risky | 需要审批 | Tool::risk() |
| 执行约束 | NO_BUILD/NO_TEST/... | 用户意图约束（位图） | ExecutionPolicy |
| 模式 | Plan | 只读分析 | PlanModeGate |
| 模式 | Apply | 可编辑执行 | PlanModeGate |

### 3.5 拆解粒度

- 子 agent 跑在**独立内核会话**里，结果用 `<task_result>` 包回
- 安全约束：
  - `DenySensitivePaths`：子 agent 运行在 `AutoRespond::AllowAll` 模式，对敏感路径是硬拒绝而非提示
  - `WorkerScopeGate`：confine 子 agent 的写工具到声明的 scope（glob 匹配）
  - `.git` 目录内部写入被拒绝（防止子 agent 注入 hooks）
- 默认并发数 `DEFAULT_MAX_CONCURRENT = 3`

### 3.6 失败处理

**VerifyCadenceHook（编辑后验证纪律）**：

```rust
// crates/atomcode-coding/src/discipline/verify.rs
const NUDGE: &str = "You made code edits but have not verified them. \
  Run a fast check (typecheck, lint, or build) to confirm nothing is broken.";
```

如果 agent 做了代码修改但未验证，注入 nudge 提醒。这是**质量门控**，不是熔断。

**重复熔断**：

| 参数 | 值 | 行为 |
|------|-----|------|
| REPEAT_NUDGE_AT | 3 | 警告提醒 |
| MAX_REPEAT_ROUNDS | 6 | 强制停止 |

**MCP trust 三级判定**：
- `read_only`：只读工具，自动 Safe
- `server_trusted`：config 里 `trust: true` 的 server，所有工具自动 Safe
- `tool_auto_approved`：用户手动批准的工具

## 4. OpenClaw：Harness 选择 + Swarm 调度 + exec-auto-review 风险分类

### 4.1 分类方式

OpenClaw 的任务分类发生在三个独立层面，彼此正交：

**层面一：Harness 选择算法（系统自动）**

```typescript
// selection.ts - selectAgentHarness() 核心逻辑
// 1. 遍历所有已注册 harness（listRegisteredAgentHarnesses()）
// 2. 对每个调用 harness.supports(context) 判定兼容性
// 3. compareHarnessSupport() 按 priority 降序排序
// 4. 内置 "openclaw" harness 是兜底（builtin-openclaw.ts 创建）
// 5. "openclaw" id 是保留名，注册时直接抛错
```

`AgentHarness` 是 11 个 capability 的交叉类型：

```typescript
export type AgentHarness = AgentHarnessRunCapability &
  AgentHarnessSideQuestionCapability &
  AgentHarnessClassificationCapability &
  AgentHarnessCompactionCapability &
  AgentHarnessRuntimeArtifactCapability &
  AgentHarnessAuthBindingCapability &
  AgentHarnessProviderUsageCapability &
  AgentHarnessModelCatalogCapability &
  AgentHarnessMcpCatalogCapability &
  AgentHarnessSessionForkCapability &
  AgentHarnessSessionLifecycleCapability;
```

选择是基于 capability 匹配的，不是基于任务难度。每个 harness 声明自己支持哪些 capability，系统自动选择最匹配的。

`supports()` 返回类型：

```typescript
export type AgentHarnessSupport =
  | { supported: true; priority?: number; reason?: string }
  | { supported: false; reason?: string; fallbackRuntime?: "openclaw" };
```

**层面二：exec auto-reviewer 风险分类（执行时）**

```typescript
type ExecAutoReviewDecision =
  | { decision: "allow-once"; rationale: string; risk: "low" }
  | { decision: "ask";       rationale: string; risk: ExecAutoReviewRisk };

type ExecAutoReviewRisk = "unknown" | "low" | "medium" | "high";
```

这是对**命令执行**的风险分类，不是任务分类。关键约束：`allow-once` **必须**伴随 `risk: "low"`——中高风险一律 `ask`。

审阅器的完整流程：

```
第一步：输入验证（尺寸检查 > 16KB → ask；注入攻击检测 → ask）
第二步：模型调用（30 秒超时，360 max_tokens，temperature=0）
第三步：响应解析（JSON 提取 → 重复 key 检测 → Zod 校验 → __proto__ 注入检测）
第四步：安全兜底（risk ≠ low 的 allow 一律降级为 ask）
```

**层面三：Swarm 调度（并发控制）**

```typescript
type SwarmGroupLane = {
  groupId: string;            // 调度组标识
  limit: number;              // 最大并发数
  active: Set<string>;        // 当前活跃 run IDs
  queue: QueuedSwarmRun[];    // FIFO 等待队列
  pumpScheduled: boolean;     // 防止并发 pump
};
```

调度流程：
1. **占位**：`reserveSwarmRun()` → 创建 FIFO 队列项
2. **绑定启动**：`activateSwarmRun()` → 绑定 `start()` 和 `onStartFailure()` 回调
3. **容量检查**：`pumpLane()` → 用 `queueMicrotask()` 微任务调度
4. **释放**：`releaseSwarmRun()` → 从 `active` 移除，触发 `pumpLane()`
5. **失败重试**：启动失败时，若非持久化失败，将项放回队头，1 秒后 `retryReady = true`

### 4.2 SubAgent Spawn 生命周期

`spawnSubagentDirect()` 有完整的 9 步流程：

```
1. 输入验证：task 非空、label 清理、mount path 安全检查
2. Session 准备：createInitialSubagentSession()
3. Context Engine 准备：prepareContextEngineSubagentSpawn()
4. Attachments 材料化：materializeSubagentAttachments()
5. Delivery Context 绑定：mergeDeliveryContext()
6. Gateway 注册：callNativeSubagentGateway()
7. Swarm 容量预留：activateSwarmRun()
8. Launch Request 构建：buildSubagentLaunchRequest()
```

### 4.3 Run 终态与生命周期事件


### 4.4 失败处理

- **Run 4 种终态**：`completed` / `aborted` / `blocked` / `error`，每种有独立的诊断映射
- **Harness fallback**：`supports()` 返回 `{ supported: false, fallbackRuntime?: "openclaw" }` 可降级到内置 harness
- **exec auto-review 失败回流**：任何审阅异常都回退到 `ask`（人工审批），永远不静默放行
- **压缩安全超时**：180 秒超时防止压缩长时间阻塞
- **AbortSignal 传播链**：外部信号 → run 级 AbortController → tool 执行 AbortSignal

```typescript
// 评估逻辑：后匹配优先（findLast）
export function evaluate(permission: string, pattern: string, ...rulesets: Ruleset[]): Rule {
  return rulesets.flat().findLast(
    (rule) => Wildcard.match(permission, rule.permission) && Wildcard.match(pattern, rule.pattern)
  ) ?? { action: "ask", permission, pattern: "*" }
}
```

规则是 **后匹配优先**（`findLast`），后面的规则覆盖前面的。这允许 `defaults` 设置基础规则，Agent 特定规则覆盖特定项。

## 6. DeepSeek-Harness：Goal 域模型 + round driver 自动续轮

### 6.1 分类方式

DeepSeek-Harness 的任务分类完全围绕 **Goal 域模型** 展开，是所有 6 个项目中最接近"显式任务分类"的设计。

**GoalPhase 状态机**：

```typescript
type GoalPhase = 'active' | 'paused' | 'blocked' | 'complete'
```

状态转换图：
```
create → active → pause → paused
active → block  → blocked
active → complete → complete
paused/blocked/complete → resume → active（需有轮次预算）
```

**Goal 域模型**：

```typescript
interface GoalSnapshot extends GoalRef {
  readonly objective: string        // 目标描述
  readonly phase: GoalPhase         // 当前阶段
  readonly blockedReason?: GoalBlockReason  // 阻塞原因
  readonly maxGoalRounds: number    // 最大轮次数（默认 256）
}
```

**分类触发**：模型通过 `tool-goal` 工具（`get_goal` / `create_goal` / `update_goal`）自主管理 Goal 的生命周期。

**authority 模型**：

```typescript
// tool-goal/src/authority.ts
// requireDirectHuman(): 只允许直接人类请求调用（不允许子代理）
// completionAuthority(): 允许 goal-round 内的自动续轮调用
```

- `create_goal`、`edit`、`pause`、`resume` 都要求 `requireDirectHuman()`（人类发起）
- `complete` 和 `blocked` 在 goal-round 内自动续轮时也允许（`completionAuthority`）

### 6.2 round driver 自动续轮机制

```typescript
// packages/goal/goal-round-driver/src/index.ts:138-205
async function drive(state: DriverState): Promise<void> {
  if (!readyToDrive(state)) return

  // 持久化 checkpoint
  if (state.needsCheckpoint) {
    await ctx.sessions.flush(agent.session)
    if (!readyAfterCheckpoint(state)) return
  }

  const goal = currentGoal(state)
  if (goal === undefined || goal.phase !== 'active' || goal.activation !== 'armed') return

  // 轮次上限检测
  if (goal.roundsStarted >= goal.maxGoalRounds) {
    ctx.goals.block(agent, goalRef(goal), {
      code: 'round-limit',
      message: `Goal reached its configured limit of ${goal.maxGoalRounds} rounds.`,
    })
    return
  }

  // 发起下一轮
  const round = goal.roundsStarted + 1
  const content = renderGoalRoundPrompt(goal, round)
  const message = createUserMessage({ content, source: { kind: 'goal', ... } })
  agent.followup(message)
}
```

**防竞态设计**：`requestDrive` 使用 serialized loop 确保同一 agent 上只有一个驱动任务运行：

```typescript
// index.ts:208-241
function requestDrive(state: DriverState): void {
  state.requested = true
  if (state.run !== undefined) return  // 已有驱动任务
  let run = ctx.agents.withoutInitiator(async () => {
    while (state.requested && !state.stopping) {
      state.requested = false
      await drive(state)
    }
  })
  state.run = run
}
```

### 6.3 事件源设计

Goal 是一个**事件源**（event-sourced）模型：每次变更都写入 `goal/change` session 事件，当前状态通过 fold 事件流重建。

```typescript
// packages/goal/goal/src/index.ts:183-197
export class GoalService extends TypertRemoteService {
  static Config: z<Config> = z.object({
    defaultMaxGoalRounds: z.number().default(256),
  })
}
```

CAS（Compare-And-Set）保证：每次变更都要求提供当前的 `{id, revision}` ref，不匹配则抛 `GOAL_STALE_REVISION`。

fold 不仅重建状态，还**验证**每个事件的合法性（状态转换规则），fail-loud。

### 6.4 wrapup 上下文注入

Goal complete/blocked 时，注入一个 plugin source 的 user 消息：

```typescript

// 告诉模型："目标已完成/阻塞，请总结工作"
```

这是一个巧妙的 UX 设计：自动触发总结，避免用户手动要求。

### 6.5 分类级别汇总

| GoalPhase | 含义 | round driver 行为 | 触发方式 |
|-----------|------|------------------|---------|
| active | 目标活跃，继续执行 | 自动续轮 | create_goal / resume |
| paused | 目标暂停 | 不续轮 | pause_goal |
| blocked | 目标被阻塞 | 不续轮，注入 wrapup | block_goal / round-limit |
| complete | 目标完成 | 不续轮，注入 wrapup | complete_goal |

### 6.6 失败处理

- **round-limit 阻塞**：达到 maxGoalRounds（默认 256）时自动 block
- **GOAL_STALE_REVISION**：CAS 不匹配时抛出，防止并发修改
- **GOAL_INVALID_TRANSITION**：resume 时检查轮次预算，不足则拒绝
- **状态转换验证**：`validateSnapshotTransition()` 严格验证每个事件的合法性，fail-loud
- **双层轮次保障**：`GoalService.resume()` + `round driver.drive()` 都检查 `roundsStarted >= maxGoalRounds`

## 7. Pi：Lane 并发树 + Skill 注入 + drive 模式切换

### 7.1 分类方式

Pi 的任务分类是**最弱的**，没有显式的任务级别概念。它的分类体现在三个机制中：

**机制一：Skill 注入（知识分类）**

Skill 是文本注入，不是工具调用。用最少的抽象（Markdown）覆盖知识管理场景：

```typescript
// AgentLane 接口
interface AgentLane {
  steer(message): void;      // 注入调整消息
  followUp(message): void;   // 追加后续任务
  nextRun(message): void;    // 触发下一轮
  skill(name, args): void;   // 调用 Skill
}
```

**机制二：drive 模式（执行模式分类）**

```typescript
drive?: "automatic" | "manual";
```

- `"automatic"`：Harness 自动运行 agent loop 直到完成
- `"manual"`：外部代码逐步驱动（`peekAction()` → `executeAction()`），TUI 可在每个 action 之间插入 UI 更新、用户确认等操作

**机制三：Lane 并发（执行单元分类）**

Lane 是 session tree 上的命名分支指针：

```typescript
interface LaneInfo {
  lane: string;
  leafId: string;
  createdAt: number;
}
```

Lane 之间的通信通过三种队列：
- `steer`：注入调整消息（修改当前行为）
- `followUp`：追加后续任务（当前完成后再做）
- `nextRun`：触发下一轮（类似 deepseek round driver）

### 7.2 Session Tree 结构

Session 不是线性历史，而是一棵**树**：

```typescript

  return {
    getLeafId: () => this.getLeafIdForLane(lane),
    findEntriesOnBranch: (query) => this.queryBranchEntries(lane, query),

}
```

`createLane(lane, at)` 在指定 entry 处分叉创建新 lane，`moveLane(lane, to)` 移动 lane 的 leaf 指针。

### 7.3 Lane 状态还原器（Reducer）

pi 的 lane 状态通过**事件溯源**（event sourcing）从持久化记录中重建：

```typescript

  lane: string;
```

### 7.4 分类级别汇总

| 机制 | 级别 | 说明 |
|------|------|------|
| drive | automatic | 自动执行到完成 |
| drive | manual | 逐步驱动，TUI 可插入 UI 更新 |
| Lane | main | 主 lane |
| Lane | 自定义 | 命名分支，session tree 分叉 |

### 7.5 失败处理

- **LaneBusy 错误**：同一 lane 同时只有一个操作运行，违反时抛出
- **suspended 状态**：崩溃后恢复时暂停，可通过 `resume()` 恢复并 fetch deferred 结果
- **branch summary**：当用户从 lane A 导航到 lane B 时，lane A 的工作被摘要保存（公共祖先算法）
- **Deferred Handle**：异步工具结果（如 Claude extended thinking），支持长时间运行的推理任务

## 8. 设计模式提炼

### 模式 1：显式分类 vs 隐式分类

| 类型 | 项目 | 特点 | 适用场景 |
|------|------|------|---------|
| **显式分类** | DeepSeek-Harness（GoalPhase）、Claude Code（effort）、AtomCode（fast/capable） | 系统或用户明确定义任务级别，路由逻辑清晰 | CLI 工具、需要用户可控的场景 |
| **隐式分类** | OpenCode（Agent permission）、OpenClaw（Harness capability）、Pi（drive mode） | 通过权限/能力/模式间接实现分类，灵活但不易理解 | 平台型产品、需要高度可扩展性 |
| **混合分类** | Claude Code（Skill 声明 + 模型决策） | 静态声明 + 动态决策结合 | 复杂产品、多角色协作 |

**结论**：显式分类对用户更友好，隐式分类对开发者更灵活。laew 的 Yolo 三档分类属于显式分类，方向正确。

### 模式 2：分类触发点的三种位置

| 触发点 | 项目 | 优势 | 劣势 |
|--------|------|------|------|
| **用户侧**（配置/Skill 声明） | OpenCode、Claude Code Skill | 可预测、可控 | 灵活性低 |
| **模型侧**（LLM 自主决策） | DeepSeek-Harness、AtomCode | 灵活、适应性强 | 不可控、可能误判 |
| **系统侧**（算法自动选择） | OpenClaw Harness 选择 | 一致、可靠 | 不够智能 |

**结论**：最佳实践是**用户侧默认 + 模型侧微调**。laew 的 Yolo Agent 属于模型侧分类，建议增加用户侧覆盖机制。

### 模式 3：二维分类优于一维分类

| 维度数 | 项目 | 分类维度 |
|--------|------|---------|
| 一维 | DeepSeek-Harness、OpenCode | GoalPhase 或 Agent 类型 |
| 二维 | AtomCode | 难度 × 工具集 |
| 多维 | Claude Code | effort × context × agent × model |

**结论**：二维分类（难度 × 工具集/执行模式）在复杂度和表达力之间取得最佳平衡。laew 目前是一维（simple/medium/hard），建议增加第二维度。

### 模式 4：自动续轮 vs 人工续轮

| 模式 | 项目 | 机制 | 适用场景 |
|------|------|------|---------|
| **自动续轮** | DeepSeek-Harness（round driver）、Pi（nextRun） | 系统自动发起下一轮 | 长时间任务、代码重构 |
| **人工续轮** | OpenCode（用户输入）、OpenClaw（user message） | 需要用户显式输入 | 交互式任务、需要确认 |
| **混合** | Claude Code（Task 后台自动 + 主循环人工） | 部分自动、部分人工 | 复杂场景 |

**结论**：laew 的 Main-Work Agent 拆 WorkFlow 后是线性自动执行，方向正确。建议为 hard 级别增加 pause/resume 能力。

### 模式 5：熔断与防死循环

| 机制 | 项目 | 阈值 | 处理方式 |
|------|------|------|---------|
| maxGoalRounds | DeepSeek-Harness | 256 轮 | 自动 block |
| doom_loop | OpenCode | 3 次精确重复 | 权限请求 |
| MAX_REPEAT_ROUNDS | AtomCode | 6 次重复 | 强制停止 |
| NUDGE_AT | AtomCode | 3 次重复 | 警告提醒 |
| lane 并发限制 | Pi | 1 操作/lane | LaneBusy 错误 |
| Swarm 并发限制 | OpenClaw | 可配置 limit | FIFO 排队 |

**结论**：多层熔断（警告 → 限制 → 强制停止）是最佳实践。

### 模式 6：失败回流的保守策略

| 项目 | 策略 | 设计哲学 |
|------|------|---------|
| OpenClaw exec auto-review | 任何审阅异常 → `ask`（人工审批） | 永远不静默放行 |
| AtomCode RiskLevel | 工具自报风险，kernel 不强制，但 middleware 可拦截 | advisory + composable gate |
| DeepSeek-Harness Goal | CAS 不匹配 → 抛出异常 | fail-loud |
| OpenCode doom_loop | 精确重复 → 权限请求（用户选择） | 给用户选择权 |
| Claude Code Hook | PreToolUse 拦截 → 可阻止执行 | 可编程拦截 |

**结论**：保守策略（不确定就问用户）比激进策略（自动放行）更安全。

### 模式 7：参数化系统提示词

| 项目 | 机制 | 效果 |
|------|------|------|
| AtomCode | 根据 model/todo/subagent 开关条件注入不同段落 | 弱模型获得更强的工具纪律 |
| Claude Code | Skill 的 `allowed-tools` 控制工具权限 | 精细化工具暴露 |
| OpenCode | Agent 的 `prompt` 字段指定系统提示词 | 按角色定制提示词 |

**结论**：laew 的 Yolo/Plan/Work Agent 可以借鉴参数化提示词，根据任务级别动态组装。

```rust
fn detect_doom_loop(recent_calls: &[ToolCall]) -> bool {

        return false;
```

## 附录 E：反模式警示

### E.1 过度分类反模式

**问题**：分类维度过多导致路由逻辑爆炸。

**案例**：如果 laew 同时引入 task_level(3) × execution_mode(3) × model_tier(3) × priority(3)，路由表将有 81 种组合，维护成本极高。

**建议**：保持在 2-3 个维度，每个维度 2-4 个级别。laew 的 task_level(3) × execution_mode(3) = 9 种组合是合理上限。

### E.2 隐式分类不可观测反模式

**问题**：分类逻辑隐藏在权限系统中，用户无法理解和预测。

**案例**：OpenCode 的 Agent 选择完全由配置文件决定，用户如果不读文档，不知道为什么某些工具不可用。

**建议**：laew 的 Yolo Agent 在分类后应向用户展示分类结果（当前已在 TUI 横幅中展示），这是正确做法。

### E.3 单点分类失败反模式

**问题**：分类器是单点故障，一旦失败整个系统瘫痪。

**案例**：如果 laew 的 Yolo Agent 的 LLM 调用超时或返回格式错误，没有降级机制。

**当前状态**：laew 已实现降级为 simple，这是正确的。但建议增加通知用户"分类失败，已降级为简单模式"。

### E.4 无熔断的自动续轮反模式

**问题**：自动续轮没有上限，可能无限循环。

**案例**：如果 Main-Work Agent 的 WorkFlow 拆解逻辑有 bug，可能生成无限长的流程列表。

**建议**：借鉴 DeepSeek-Harness 的 maxGoalRounds（256），laew 应为每个任务级别设置最大轮次上限。

### E.5 分类结果不持久化反模式

**问题**：分类结果只在内存中，崩溃后丢失。

**案例**：如果 laew 在 hard 级别任务执行到一半时崩溃，重启后无法恢复之前的分类结果和执行进度。

**建议**：借鉴 DeepSeek-Harness 的事件源设计，将分类结果和执行进度写入 SQLite（laew 已有 `session_memory` 表，可扩展）。

laew 的 hard 级别处理链路（Plan → MainWork → SubAgent → QC → SessionContext）已经是最完整的。主要差距在于：
