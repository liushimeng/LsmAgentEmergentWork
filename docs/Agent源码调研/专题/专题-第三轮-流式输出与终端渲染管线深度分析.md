## 0. 前言:为什么需要这一轮

laew 当前的 LLM 调用走的是 **阻塞式 complete**:`src/llm/anthropic.rs` 的 `complete()` 通过 `resp.chunk()` 循环喂给 `SseStream` + `ParseSink`,直到 `Stop` 事件才聚合成一个 `Completion` 返回。`src/llm/sse.rs:282-301`:

```rust
let mut sse = SseStream::new();
let mut sink = ParseSink::new();
let mut resp = resp;
loop {
    match resp.chunk().await {
        Ok(Some(bytes)) => {
            let evs = sse.push(&bytes)?;
            for ev in evs { ... sink.feed(...)?; }   // 只聚合,不输出
        }
        ...
    }
}
let completion = sink.finish()?;   // 全文就绪后才返回
```

这意味着:**模型已经开始生成了,但用户要等到最后一个 token 才看到整段文字一次性弹出**。同时 `src/tui/engine.rs:212-241` 的 `present()` 是全量清屏重绘(MoveTo(0,0) + Clear(All)),没有任何增量渲染和 markdown 能力。

本轮聚焦的就是这条链路——从 SSE 字节流到终端像素的完整管线——在 6 个成熟 Agent 里是怎么做的,以及 laew 该如何借鉴。

## 1. 流式传输协议解析

### 1.1 atomcode(Rust):协议无关的 StreamEvent 枚举

atomcode 把"协议线 → 内核"的边界收拢为一个极度完整的枚举 `StreamEvent`(`crates/atomcode-kernel/src/stream.rs:93-156`),覆盖所有已知的流式语义:

```rust
pub enum StreamEvent {
    TextDelta(String),
    Reasoning(String),                         // thinking/reasoning 通道
    ReasoningSignature { opaque: String, provider: String },  // signed thinking 块收尾
    ToolCall(ToolCall),                        // 完整工具调用(执行用)
    ToolCallDelta { index: u32, id: Option<String>, name: Option<String>, arguments: String },  // 流式片段(仅展示)
    Usage(TokenUsage),                         // 可能多次,merge_max 折叠
    ResponseId(String),
    ResponseModel(String),
    Error(ProviderError),
    Malformed,                                 // 解析失败信号(非输出)
    Done { truncated: bool },
}
```

关键设计点:

1. **thinking 双轨**:`Reasoning(String)` 文本作为普通 delta 转发(实时通道 + 写入 `Message.reasoning`),`ReasoningSignature` 是"块收尾"事件,把截至目前的文本 + opaque token 封存为一个 `ReasoningBlock`(stream.rs:98-113)。这样既支持实时回显,又保留了 Anthropic signed thinking / OpenAI encrypted_content 的 round-trip 能力。

2. **ToolCall vs ToolCallDelta 分离**:`ToolCallDelta` 是"观察性"的,仅供 UI 实时展示"模型正在填参数";真正执行的是最后完整的 `ToolCall`。注释明确说"An adapter that cannot stream tool calls simply never emits this — the complete-ToolCall path is entirely unchanged"(stream.rs:114-121)——降级优雅。

3. **Usage 折叠策略 `merge_max`**(stream.rs:25-29):因为 Anthropic 把 input tokens 放在 `message_start`、累计 output tokens 放在每个 `message_delta`,字段被拆到多个事件里,且 output 是累加值。`merge_max` 按字段取 MAX,既不会重复计数累加值,也不会丢只在早期事件里出现的 `prompt` 字段。注释把 OpenAI 单次累计 vs Anthropic 分字段累加的差异讲透了(stream.rs:12-24)。

4. **ProviderError::is_context_overflow`**(stream.rs:59-86):集中了 9 种 context overflow 的 message 签名 + 结构化 code,避免上层字符串匹配。

实际 SSE 字节流解析在 atomcode 里由上层 provider adapter 完成(本仓库 `crates/atomcode-coding/` 是 stub,L2 wire 解析在 daemon/远程服务里),但 `StreamEvent` 作为 L1→L0 的协议无关界面非常干净。

### 1.2 pi(TypeScript):手写 SSE 解码 + partial-json 容错

pi 在 `packages/ai/src/api/anthropic-messages.ts:404-458` 实现了一个手行的 SSE 解码器 `iterateSseMessages`,用 `TextDecoder({ stream: true })` 处理跨 chunk 的 UTF-8 序列:

```ts
async function* iterateSseMessages(body: ReadableStream<Uint8Array>, signal?: AbortSignal):
    AsyncGenerator<ServerSentEvent> {
    const reader = body.getReader();
    const decoder = new TextDecoder();
    const state: SseDecoderState = { event: null, data: [], raw: [] };
    let buffer = "";
    while (true) {
        if (signal?.aborted) throw new Error("Request was aborted");  // 中断检查
        const { value, done } = await reader.read();
        buffer += decoder.decode(value, { stream: true });           // 增量 UTF-8 解码
        let consumed = consumeLine(buffer);
        while (consumed) {
            buffer = consumed.rest;
            const event = decodeSseLine(consumed.line, state);
            if (event) yield event;
            consumed = consumeLine(buffer);
        }
    }
    // 流尾 flush
    buffer += decoder.decode();
    ...
    const trailingEvent = flushSseEvent(state);
}
```

partial-JSON 工具参数处理(anthropic-messages.ts:678-690):每个 `input_json_delta` 追加到 `block.partialJson`,随即调用 `parseStreamingJson(block.partialJson)` 尝试解析。`parseStreamingJson` 基于 `partial-json` 库(`packages/ai/src/utils/json-parse.ts:1`),能在 JSON 不完整时解析出已有字段。`thinking_delta` 和 `signature_delta` 也有独立处理(666-698)。

pi 的 `AssistantMessageEventStream`(`packages/ai/src/utils/event-stream.ts:4-67`)是一个带终态的异步迭代器:`push()` 入队/唤醒等待者,`done` 时结算 `finalResultPromise`,消费者既能 `for await` 逐个收 delta,也能 `await stream.result()` 拿最终结果——双通道设计。

### 1.3 opencode(TypeScript,Effect):ToolStream 状态机

opencode 把"跨 chunk 的工具参数拼接"抽象成一个泛型状态机 `ToolStream`(`packages/llm/src/protocols/utils/tool-stream.ts`):

```ts
export interface PendingTool extends ToolAccumulator {
    readonly providerExecuted?: boolean
    readonly providerMetadata?: ProviderMetadata
}
export type State<K extends StreamKey> = Partial<Record<K, PendingTool>>
```

核心操作 `appendOrStart`(tool-stream.ts:117-179):如果一个 `tool_call` delta 携带着 `id/name`,就新建一个 `PendingTool`;如果只携 `text`,就往已有的 `tools[key]` 上拼接。这统一了 OpenAI Chat(index 作 key,id/name 只在首个 delta)和 Anthropic(content_block index,key 稳定)两种风格。

delta 事件类型:`LLMEvent.toolInputStart / toolInputDelta / toolCall`(schema 层),UI 层订阅后增量渲染。`parseToolInput` 在 `toolCall` 终态才做完整 JSON 校验,中间态只存 raw string——和 atomcode 的"观察性 delta"思路一致。

### 1.4 claudecode(TypeScript):content_block_delta 状态机 + 主动规避 O(n²)

claudecode 的 SSE 解析在 `src/services/api/claude.ts:2053-2162`,针对 Anthropic 的 `content_block_delta` 事件做了一个精细的 switch:

```ts
case 'content_block_delta': {
    const contentBlock = contentBlocks[part.index]
    switch (delta.type) {
        case 'input_json_delta':
            contentBlock.input += delta.partial_json;   // 直接拼接,不反复 parse
            break;
        case 'text_delta':
            contentBlock.text += delta.text;
            break;
        case 'thinking_delta':
            contentBlock.thinking += delta.thinking;
            break;
        case 'signature_delta':
            contentBlock.signature = delta.signature;
            break;
    }
}
```

**关键性能决策**(claude.ts:1818-1820):claudecode 刻意绕开了 SDK 自带的 `BetaMessageStream`,原因是它每个 `input_json_delta` 都调 `partialParse()`,导致长工具参数 → **O(n²)** 的 JSON 解析。claudecode 选择"自己拼接字符串,终态一次性 parse",注释写得非常直白:"we handle tool input accumulation ourselves"。

thinking 流和 text 流在 `contentBlocks[]` 里按 index 隔离,互不干扰。`content_block_stop` 事件做块级收尾(2171-2182)。

### 1.5 openclaw(TypeScript):EventStream + agent-loop 聚合

openclaw 的 `EventStream<T,R>`(`packages/llm-core/src/utils/event-stream.ts:4-67`)和 pi 异曲同工:双通道(`for await` + `result()`),额外多了 `rejectFinalResult`(流异常终态)。`queueHead` 指针 + 滑动队列避免 `shift()` 的 O(n)。

`packages/agent-core/src/agent-loop.ts:94-119` 的 `appendTextDeltaToAssistantMessage` 是最简单的"按 contentIndex 累加":

```ts
function appendTextDeltaToAssistantMessage(message, contentIndex, delta) {
    const content = [...message.content];
    const currentContent = content[contentIndex];
    content[contentIndex] = currentContent?.type === "text"
        ? { ...currentContent, text: currentContent.text + delta }
        : { type: "text", text: delta };
    return { ...message, content };
}
```

`resolveAssistantMessageUpdate`(agent-loop.ts:108-119) 还处理了 `event.partial` 直接覆盖的快捷路径——上游如果愿意可以直接传完整 partial 消息,跳过逐 delta 累加。

### 1.6 deepseek-harness(TypeScript):parseSse + translate 双阶段

deepseek-harness 把 SSE 解析分成清晰的两层:

**第一层 `parseSse`**(packages/llm/llm-deepseek/src/sse.ts:28-40):字节流 → data 字符串流。用 `TextDecoderStream` + `eventsource-parser` 的 `EventSourceParserStream` 处理 chunk 重装配/UTF-8/CRLF/BOM/注释过滤。以 `[DONE]` 作为流终止信号,提前抛 `LlmError('STREAM_CLOSED')`(sse.ts:39)。

**第二层 `translate`**(packages/llm/llm-deepseek/src/translate.ts:95-194):data 字符串流 → `StreamChunk`。核心是 `OpenBlock` 状态机:为 text/reasoning/tool-call 各维护一个 `OpenBlock`,`block.text += fragment` 逐片累加,遇到 `[DONE]` 才 yield `block-end`(translate.ts:110-126)。特别处理 `reasoning_content` 优先(139-149)——"Reasoning first: thinking mode interleaves it before text. The empty-string first chunk must not open a block"。

`tool_blocks` 用 `Map<number, OpenBlock>` 按 index 隔离多个并行工具调用(translate.ts:99,161-179),每个工具独立 yield `tool-call-delta`。

## 2. 增量渲染管线

### 2.1 atomcode:retained-mode cell-diff 引擎(工业级)

atomcode 的 `crates/atomcode-tuix/src/render/` 是本轮分析中最复杂、最工业化的渲染系统,26012 行的 `retained.rs` 实现了完整的保留模式终端渲染器。

**架构**(retained.rs:13-18):
```
event_loop ── UiLine ─▶ RetainedRenderer ── 更新 widget 状态
                                           ── paint_frame 绘制到 Screen
                                           ── render_diff → bytes
                                           ── out.write_all(bytes)
```

**双帧 cell-diff 引擎**(`crates/atomcode-tuix/src/render/screen.rs:233-315`,`crates/atomcode-tuix/src/render/cell.rs:394-514`):

`diff_cell_frames(prev, next)` 逐 cell 比对生成 `Patch{row,col,cell}` 列表(cell.rs:394-415)。`serialize_patches` 是关键优化(cell.rs:426-514):

```ts
// 游标 run-pack:ASCII 字符直接续写,遇到非-ASCII 强制发 CUP 重置游标
if (patch.cell.ch as u32) < 0x80 {
    expected_cursor = Some((r, c + patch.cell.width as u16));  // ASCII:预测游标+1
} else {
    expected_cursor = NULL;  // 非 ASCII:放弃预测,下个 patch 必须发 CUP
}
```

注释把"为什么"讲得极清楚(cell.cs:463-501):因为 `unicode-width` 对 East Asian Ambiguous 字符(× ✓ → •)的宽度和终端实际渲染宽度可能差 1 列,run-pack 游标预测错位会逐格累积,导致"CodingPlan" → "CodedingPlan" 式错乱。**ASCII 走 run-pack(零额外开销),非 ASCII 强制 CUP(每字符多 6 字节但安全)**——对 CJK Heavy 帧多几百字节,对 ASCII-heavy 帧零成本。

**DECSET 2026 同步输出**(screen.rs:275-299):每帧开头发 `\x1b[?2026h`(BSU),结尾配对 ESU,让 Windows Terminal/iTerm2/kitty/wezterm/alacritty 等支持同步输出的终端整帧一次性上屏,消除中间态闪烁。帧内先 `\x1b[?25l` 隐藏光标走完 patch walk,结束时再显式 CUP 回到输入框。

**JediTerm 特化路径 `serialize_frames_tight`**(cell.rs:543-582):因为 JediTerm 的 GRID 和 cell 模型一致(CJK=2 cell),可以整行 `CUP(row,1)+EL` 后连续输出,不用逐 cell CUP。注释详列了 3 个 JediTerm 症状和取舍。

**CJK 宽度探测 `width.rs:40-70`**:默认 **不** 用 `width_cjk`(因为现代终端 macOS Terminal/iTerm2/alacritty/kitty/wezterm/Windows Terminal 都把 ambiguous 字符按 1 列渲染,强制 width_cjk 反而错位),仅 `ATOMCODE_CJK_WIDTH=1` 显式开启。emoji 特殊处理:legacy symbol block(☀ ☎ ✂)被 `unicode-width` 报 1 但 GUI 终端按 2 列渲染,主动放宽到 2(width.rs:61-70)。

**分块写入**(retained.rs:10018-10030):Mac Terminal.app 在单 write 携带 ~1KB+ 混合 CSI+SGR+UTF-8 时会丢字节,所以拆成 512 字节 chunk 分次 write+flush。

### 2.2 pi:marked 增量 lex + 未闭合 fence 修剪

pi 的 markdown 渲染基于 `marked` v18,在 `packages/tui/src/components/markdown.ts` 里。

**未闭合代码块处理**(markdown.ts:160-168):
```ts
// Trim streamed partial closing fences so code blocks do not shrink/flicker
// when the final fence character arrives. See https://github.com/earendil-works/pi/issues/5825.
const marker = /^(`{3,}|~{3,})/.exec(token.raw)?.[1];
const lastLine = token.raw.split("\n").pop();
if (!marker || !lastLine || lastLine.length >= marker.length || lastLine !== marker[0]?.repeat(lastLine.length)) {
    return;
}
token.text = token.text.slice(0, -lastLine.length).replace(/\n$/, "");
```

流式过程中模型逐步输出 `` ``` `` 的关闭围栏,如果每次重渲染都把这个"半截围栏"当普通文本显示,代码块会反复伸缩闪烁。pi 的做法:检测到末尾行是"不完整的关闭围栏前缀"就把它从 token.text 里剥掉,等完整围栏到了才关闭。

**LaTeX 流式感知**(markdown.ts:26-118):`LatexToken` 带 `pending?: boolean` 字段,`looksLikePendingDollarMath` 用启发式(`\\[A-Za-z]+|[_^=+*/...]`)判断一个未闭合的 `$...$` 是"公式还是普通美元符号",pending 态走特殊渲染。

**CJK 宽度**:依赖 `get-east-asian-width` 1.6.0(pi/tui/package.json),比 `unicode-width` 更贴合终端实测。

### 2.3 opencode:markdown-stream 投影(增量解析的数学证明)

opencode 的 `packages/session-ui/src/components/markdown-stream.ts` 是本轮分析中**增量 markdown 渲染最优雅的实现**。

核心洞察:流式 markdown 只需要**最后一个 block 是"不稳定"的**,之前的 block 都已闭合,可以缓存。`stream(text, live)`(markdown-stream.ts:53-86):

```ts
export function stream(text: string, live: boolean): Block[] {
    if (!live) return completedProjection(text).blocks;
    const tokens = marked.lexer(text);
    const tail = tokens.findLastIndex((token) => token.type !== "space");
    const last = tokens[tail];
    // tail 之前的所有 block → mode: "full" / "code+complete:true"
    for (let index = 0; index < tail; index++) {
        if (token.type === "code") result.push({ ..., mode: "code", complete: true });
        else result.push({ ..., mode: "full" });
    }
    // 最后一个 block:如果是未闭合 code → mode: "code" 不带 complete
    if (last.type !== "code") return [...result, { ..., mode: "live" }];
    if (!open(code.raw)) return [...result, { ..., mode: "code", complete: true }];
    return [...result, { ..., src: openCode(code.raw), mode: "code" }];  // 未闭合
}
```

`open(raw)`(markdown-stream.ts:32-41)检测"最后一个换行之后是否构成完整关闭围栏"——`marked.lexer` 会把未闭合围栏的内容也吃进 `code` token,`open()` 通过正则 `^[\\t ]{0,3}${char}{${size},}[\\t ]*$` 判断末行是否已是完整围栏,不是就标记为"仍在流入的代码块"。

`project(previous, text, live)`(markdown-stream.ts:88-122)是增量投影:如果新 text 以 old text 为前缀,且最后一个 block 是未闭合 code,就**只追加 suffix 到该 block**,而不是重新 lex 全文——O(增量长度)而非 O(全文)。`closesFence(tail.raw, suffix)`(markdown-stream.ts:43-47)判断新到的 suffix 是否闭合了围栏。

Block 类型:`{ raw, src, mode: "full"|"live"|"code", language?, complete? }`——UI 层据此决定哪些块可以缓存、哪些要重渲、哪些显示为"仍在流入"。

### 2.4 claudecode:StreamingMarkdown 稳定边界 + token 缓存

claudecode 的 `src/components/Markdown.tsx:186-235` 实现了同样的"稳定前缀"算法,但用 React ref 承载:

```tsx
export function StreamingMarkdown({ children }): React.ReactNode {
    const stripped = stripPromptXMLTags(children);
    const stablePrefixRef = useRef('');
    if (!stripped.startsWith(stablePrefixRef.current)) stablePrefixRef.current = '';
    const boundary = stablePrefixRef.current.length;
    const tokens = marked.lexer(stripped.substring(boundary));  // 只 lex 不稳定后缀
    let lastContentIdx = tokens.length - 1;
    while (lastContentIdx >= 0 && tokens[lastContentIdx]!.type === 'space') lastContentIdx--;
    let advance = 0;
    for (let i = 0; i < lastContentIdx; i++) advance += tokens[i]!.raw.length;
    if (advance > 0) stablePrefixRef.current = stripped.substring(0, boundary + advance);
    const stablePrefix = stablePrefixRef.current;
    const unstableSuffix = stripped.substring(stablePrefix.length);
    return <Box flexDirection="column" gap={1}>
        {stablePrefix && <Markdown>{stablePrefix}</Markdown>}   // 缓存,不重渲
        {unstableSuffix && <Markdown>{unstableSuffix}</Markdown>} // 每 delta 重渲
    </Box>;
}
```

注释点明关键(Markdown.tsx:177-184):"marked.lexer() correctly handles unclosed code fences as a single token, so block boundaries are always safe. The stable boundary only advances (monotonic), so ref mutation during render is idempotent and safe under StrictMode double-rendering."

**性能优化——token 缓存**(Markdown.tsx:78-110):`cachedLexer` 用 `Map<string,Token[]>` + `hashContent` 做 LRU(TOKEN_CACHE_MAX=500),因为 `marked.lexer` 在虚拟滚动重挂载时是热点(~3ms/消息)。`hasMarkdownSyntax` 用单正则 `/[`*`>\\-_\~]|\\n|^\\d+\\. |\\n\\d+\\. /` 做快速路径:纯文本直接返回单 paragraph token,跳过完整 lex。

### 2.5 openclaw:Markdown IR + 渲染器钩子

openclaw 的 markdown 不走字符串拼接,而是先转成 `MarkdownIR`(中间表示),再由 `render.ts` 的 `RenderOptions` 输出为目标格式:

```ts
export type RenderOptions = {
    styleMarkers: RenderStyleMap;       // bold/italic/code → 开闭标记
    annotationMarkers?: RenderAnnotationMap;
    escapeText: (text: string) => string;

```

`MarkdownStyleSpan` / `MarkdownAnnotationSpan` / `MarkdownLinkSpan` 是 IR 节点,`ir-spans.ts` 提供 `mergeStyleSpans / mergeAnnotationSpans`。这套 IR 让同一份 markdown 可以渲染到终端(ANSI 转义)、HTML、Discord 等不同目标。

`render-aware-chunking.ts:58-60` 的 `renderMarkdownIRChunksWithinLimit` 把 IR 按"渲染后尺寸"分块,用于消息长度受限的传输场景。

### 2.6 deepseek-harness:无独立 markdown 渲染层

deepseek-harness 的 `packages/terminal/tool-terminal/src/render.ts` 只做"终端工具结果"的渲染(截断/UTF-8 安全/列表),没有 markdown 渲染层——它的前端(apps/web)是极简的,流式文本直接走 DOM。这是"库而非应用"定位决定的。

## 3. 帧率与节流

### 3.1 atomcode:5ms 帧聚合 + 脏标记

atomcode 的 `RetainedRenderer` 用 `dirty: bool` 标记 + 5ms 心跳实现帧聚合(retained.rs:1233-1241):

```rust
/// True when widget state has changed since the last frame emit.
/// `render()` flips this to true instead of painting immediately;
/// `flush_deferred()` (called every 5ms by the event loop tick) checks
/// this and does the paint+emit at most once per tick.
/// An IME burst of 40 keystrokes in 1ms thus produces ONE frame instead of 40.
```

`flush_deferred`(retained.rs:9960-10019)是聚合点:多个 `render()` 调用在 5ms 窗口内只触发一次 `paint_frame + render_diff + write_all`。

**worker 线程**(worker.rs:437-553):渲染在独立线程跑,主线程通过 `mpsc::Sender<RenderCmd>` 发 `Line / Flush / FlushDeferred / Resize`。`Resize` 做了 **75ms 防抖**(worker.rs:444):连续 resize 只取最后一个,避免 conhost 在 resize 中间态写大段 ANSI reflow。`flush_pending: Arc<AtomicBool>` 实现"已排队则跳过"的聚合(worker.rs:478-492)。

### 3.2 pi:16ms requestAnimationFrame 节流

pi 的 `TuiBase.MIN_RENDER_INTERVAL_MS = 16`(tui.ts:343),对应 ~60fps。

`requestRender`(tui.ts:772-781):`renderRequested` 标志去重,`process.nextTick(scheduleRender)`。`scheduleRender`(tui.ts:806-824)计算 `delay = max(0, 16 - elapsed)`,`setTimeout` 到下一个 16ms 窗口。`requestImmediateRender`(tui.ts:783-798)处理"用户输入必须抢占节流帧"的场景——按键时立即渲染,不等 16ms。

### 3.3 claudecode:FRAME_INTERVAL_MS=16 + 脏区 damage

claudecode 的 `src/ink/constants.ts:1-2`:
```ts
// Shared frame interval for render throttling and animations (~60fps)
export const FRAME_INTERVAL_MS = 16
```

`LogUpdate`(`src/ink/log-update.ts`)是 ink 渲染器的核心:`renderFullFrame` 全量绘制,`diffEach` 做脏区检测。`Screen` 用 `Int32Array` 存 cell(screen.ts:363-389),`diffEach(prev, next, cb)`(screen.ts:1156-1206)通过 `next.damage` 矩形 + `prev.damage` 矩形做**脏区并集**,只扫描变化区域:

```ts
if (next.damage) {
    region = next.damage;
    if (prev.damage) region = unionRect(region, prev.damage);
}
```

`findNextDiff`(screen.ts:1213+)用纯整数比较找首个差异 cell,利于 JIT 内联。

### 3.4 opencode:requestAnimationFrame 批处理

opencode 的 `packages/session-ui/src/components/basic-tool.tsx:57-82` 用 `requestAnimationFrame` 批处理挂载:

```ts
deferredFrame = deferredMounts.length > 0 ? requestAnimationFrame(flushDeferredMounts) : undefined
```

`createEffect` + Solid 的细粒度响应式系统自动追踪依赖,只在相关信号变化时重渲局部。OpenTUI 底层做终端 diff。

### 3.5 openclaw / deepseek-harness

openclaw 的渲染节流在 `packages/terminal-core` 之上,由宿主应用决定;`EventStream` 的 `push` 是同步入队,消费端自定节奏。deepseek-harness 作为库不强制帧率。

## 4. TUI 框架技术选型对比

| 项目 | 框架 | 组件模型 | 虚拟 DOM / diff | 渲染原语 |
|------|------|---------|----------------|---------|
| atomcode | **自研 crossterm** | `UiLine` 枚举 + `RetainedRenderer` widget 状态机 | 双帧 cell-diff(`diff_cell_frames`)+ 脏标记 | `Cell{ch,style,width}` + ANSI patch stream |
| pi | **自研 differential** | `Component { render(width): string[] }` + 树 | 行级 diff(`lastFrame` 对比) | 字符串行 + `get-east-asian-width` |
| opencode | **OpenTUI + Solid** | Solid 组件 + `createEffect/Signal` | Solid 细粒度 + OpenTUI 终端 diff | `@opentui/solid` render |
| claudecode | **自研 ink fork** | React 函数组件 + hooks | `Int32Array` cell + damage 脏区 | `LogUpdate` + `Screen` |
| openclaw | **自研 terminal-core** | 渲染器钩子(Markdown IR → marker) | 无(流式推送) | ANSI 转义 + `string-width` + grapheme |
| deepseek-harness | **无(库定位)** | — | — | 纯文本截断/UTF-8 安全 |

**选型洞察**:

- **React/ink**(claudecode)适合复杂交互 UI(弹窗/列表/输入框),但需要手写 `StreamingMarkdown` 稳定边界 + token 缓存来抵消 React 重渲成本。
- **Solid/OpenTUI**(opencode)细粒度响应式天然适合"每 delta 更新",无需 `useMemo` 手动缓存。
- **自研 crossterm**(atomcode)工程量最大但上限最高——DECSET 2026 同步输出、JediTerm 特化、ASCII run-pack 优化都需要在渲染原语层动手。
- **自研 differential**(pi)最轻量,16ms 节流 + 行级 diff 足够应对中等复杂度。

### 5.1 atomcode

`StreamEvent::Error(ProviderError)` 是中止信号(stream.rs:143-144),`Done { truncated: bool }` 标记是否被 max_output_tokens 截断(stream.rs:152-155)。UI 层收到 `Error` 后冻结当前 body_lines,保留已生成内容(retained.rs:1299-1305 `live_spinner_active` 标志位控制 spinner 冻结)。

### 5.3 claudecode

```ts
// We need to handle a streaming abort before anything else.
if (toolUseContext.abortController.signal.aborted) {
    if (toolUseContext.abortController.signal.reason !== 'interrupt') {
        return { reason: 'aborted_streaming' }

}
```

`abortController.signal.reason` 区分 `interrupt`(用户主动 Ctrl-C)和其他原因,决定是否回滚。`streamingFallbackOccured`(query.ts:657-714)处理"流式失败 → 回退到非流式重试"的复杂场景:丢弃失败的 streamingToolExecutor,新建 executor,注释警告"These partial messages (especially thinking blocks) have invalid signatures"。

### 5.4 openclaw

Any running background processes may still be active...`。

### 5.5 deepseek-harness

`parseSse` 在 EOF 未收到 `[DONE]` 时抛 `LlmError('STREAM_CLOSED')`(sse.ts:39),由上层决定重试或报错。

## 8. 可复用设计模式

### 模式 P1:协议无关的 StreamEvent 枚举 + merge_max 折叠

**问题**:不同 provider 的 usage/thinking/tool_call 流式语义差异大,硬编码 parse 会散。
**解法**:定义 `enum StreamEvent { TextDelta, Reasoning, ToolCallDelta{index,id,name,arguments}, Usage, Done, Error, Malphas }`,provider adapter 是唯一知道协议细节的地方。`Usage` 多次出现时用 field-wise MAX 折叠。
**出处**:atomcode `crates/atomcode-kernel/src/stream.rs:93-156`。
**laew 适用**:laew 已有 `DeltaEvent`(sse.rs:176-199),但缺 `Reasoning` 和 `ToolCallDelta`(观察性)。应补齐 thinking 通道和"仅展示用"的 tool delta。

### 模式 P2:partial-JSON 累加 + 终态一次性 parse

**问题**:工具参数跨多个 chunk,每个 chunk 都 parse → O(n²)。
**解法**:中间态只拼接 raw string(`block.text += fragment`),终态才 `JSON.parse`。
**出处**:claudecode `src/services/api/claude.ts:1818-1820`(主动规避 BetaMessageStream 的 partialParse);deepseek-harness `translate.ts:161-179`。
**laew 适用**:laew 的 `ParseSink` 已经是这个模式(sse.rs:264-268 `json_buf.push_str`),保持。

### 模式 P3:稳定边界增量 markdown 解析

**问题**:流式 markdown 每来一个 delta 就重 lex 全文 → O(n²)。
**解法**:`marked.lexer` 把未闭合围栏当作单 token。最后一个 block 之前的所有 block 都已闭合,缓存为"稳定前缀",只 lex 不稳定后缀。
**出处**:claudecode `StreamingMarkdown`(Markdown.tsx:186-235);opencode `project()`(markdown-stream.ts:88-122);pi 的 fence 修剪(markdown.ts:160-168)。
**laew 适用**:laew 当前无 markdown 渲染,引入时**必须**用此模式,否则 CJK 长文本流式重渲会卡。

### 模式 P4:ASCII run-pack + 非 ASCII 强制 CUP

**问题**:cell-diff 后逐 cell 发 CUP 浪费带宽,但 run-pack 游标预测在宽度歧义字符处会错位累积。
**解法**:ASCII(U+0000..U+007F)走 run-pack(零开销),非 ASCII 强制发 CUP 重置游标(~6 字节/字符,安全)。
**出处**:atomcode `crates/atomcode-tuix/src/render/cell.rs:463-501`。
**laew 适用**:laew 若做增量渲染,此模式是性能关键。

### 模式 P5:DECSET 2026 同步输出

**问题**:帧内 patch walk 时光标乱跑 + 中间态闪烁。
**解法**:帧头 `\x1b[?2026h`(BSU),帧尾配对 ESU,支持同步输出的终端整帧上屏。
**出处**:atomcode `crates/atomcode-tuix/src/render/screen.rs:275-299`。
**laew 适用**:laew 全量重绘不需要,但切到增量渲染后直接加两行即可。

### 模式 P6:脏标记 + Nms 帧聚合

**问题**:IME 单毫秒内 40 次按键 / 流式每秒数百 delta,每变化一帧会炸。
**解法**:`render()` 只置 `dirty=true`,独立 tick(5ms/16ms)检查 dirty 后 paint+emit,窗口内多变化合并为 1 帧。
**出处**:atomcode retained.rs:1233-1241 + worker.rs:478-492;pi tui.ts:343 + 806-824;claudecode constants.ts:1-2。
**laew 适用**:laew 流式化后必须加,否则每个 TextDelta 都触发全量重绘。

### 模式 P7:中断分级(reason 字段)

**问题**:用户 Ctrl-C 中断 vs 工具主动 yield vs 网络错误,处理策略不同。
**解法**:`AbortSignal.reason` 携带结构化原因(`interrupt` / `turnHandoff`),上层据此决定是否回滚/保留已生成内容。
**出处**:claudecode query.ts:1015-1051;openclaw turn-interruption.ts:42-52。
**laew 适用**:laew 当前无中断语义,流式化后需加。

### 模式 P8:thinking/text 按 index 隔离

**问题**:thinking 流和 text 流交织,同一 index 的 delta 要累加到正确 block。
**解法**:`contentBlocks[part.index]` 按 index 寻址,`type` 字段校验(`text_delta` 必须落到 `type==='text'` 的 block,否则抛错)。
**出处**:claudecode `src/services/api/claude.ts:2053-2162`。
**laew 适用**:laew 接入 thinking 模型(如 Claude 3.7 extended thinking / DeepSeek R1)时直接复用。

### 模式 P9:EventStream 双通道(for await + result())

**问题**:消费者既要实时看 delta,又要等最终结果。
**解法**:`push()` 入队/唤醒,`done` 结算 `finalResultPromise`,双通道互不干扰。
**出处**:pi `packages/ai/src/utils/event-stream.ts:4-67`;openclaw `packages/llm-core/src/utils/event-stream.ts:30-62`。
**laew 适用**:laew 的 `ParseSink` 是纯阻塞聚合,改为双通道后 UI 可实时订阅。

### 模式 P10:resize 防抖

**问题**:拖拽窗口时每秒数十次 resize,每次都 reflow 会卡死。
**解法**:`RESIZE_REFLOW_DEBOUNCE = 75ms`,连续 resize 只取最后一个,安静 75ms 后才 reflow。
**出处**:atomcode `crates/atomcode-tuix/src/render/worker.rs:444,506-540`。
**laew 适用**:laew 当前无 resize 处理,加增量渲染时一并加。

## 10. 总结:6 个核心发现

1. **laew 的 SSE 解析层已就绪,缺的是"ParseSink→TUI"的实时通道**——`src/llm/sse.rs` 的 `ParseSink` 是纯阻塞聚合,加一个 `on_delta` 回调 + TUI 侧 `mpsc::Receiver` 订阅即可解锁流式输出,无需重写解析。

2. **增量 markdown 渲染的"稳定边界"模式是流式体验的基石**——opencode `packages/session-ui/src/components/markdown-stream.ts:88-122` 的 `project()` 证明:利用 `marked.lexer` 把未闭合围栏当单 token 的特性,只 lex 不稳定后缀,可达 O(增量长度)而非 O(全文)。

3. **atomcode 的 cell-diff 引擎是终端渲染的"工业级参考答案"**——`crates/atomcode-tuix/src/render/cell.rs:426-514` 的 ASCII run-pack + 非 ASCII 强制 CUP、`screen.rs:275-299` 的 DECSET 2026 同步输出,解决了"游标乱跑"和"中间态闪烁"两个经典难题。

4. **claudecode 主动规避 O(n²) partial JSON 的决策值得借鉴**——`src/services/api/claude.ts:1818-1820` 明确绕开 SDK 的 `partialParse()`,选择"中间态只拼接、终态一次性 parse",长工具参数场景性能差距显著。

5. **帧率节流是流式体验的隐形门槛**——atomcode 用 5ms 脏标记聚合(retained.rs:1233-1241)、pi 用 16ms requestAnimationFrame(tui.ts:343)、claudecode 用 16ms + damage 脏区(constants.ts:1-2 + screen.ts:1156-1206),三者在"每变化一帧会炸"问题上殊途同归。

6. **中断语义需要结构化,不能只是"停掉"**——openclaw `packages/agent-core/src/turn-interruption.ts:42-52` 用 `signal.reason.turnHandoff` 区分用户中断 vs 工具主动让出,claudecode query.ts:1015-1051 用 `reason !== 'interrupt'` 决定是否回滚,这种分级在中断后"保留已生成内容"场景至关重要。

## 11. 反模式警示:踩过的坑

本轮分析中各仓库记载的"血泪教训",值得 laew 在实现时直接规避。

### 反模式 AP1:逐 delta 全量 markdown 重渲

**症状**:每来一个 text_delta 就对全文调用 `marked.lexer()` + 渲染,长文本时 UI 卡顿甚至卡死。
**真实案例**:claudecode Markdown.tsx:177-184 的注释明确指出不优化的代价——`marked.lexer` 在虚拟滚动重挂载时是热点(~3ms/消息),所以才加了 `TOKEN_CACHE_MAX=500` 的哈希 LRU 缓存 + `hasMarkdownSyntax` 快速路径。
**正确做法**:稳定边界算法(模式 P3),只 lex 不稳定后缀。

### 反模式 AP2:非 ASCII 游标预测 run-pack

**症状**:CJK 文本或含 × ✓ → • 等符号的文本,终端出现字符错位,如 "CodingPlan" → "CodedingPlan"。
**真实案例**:atomcode cell.rs:463-501 详细记录了两类失败:(1) East Asian Ambiguous 字符 `unicode-width` 报 1 列但终端渲染 2 列;(2) wide emoji 报 2 列但某些 Windows 字体渲染 1 列。游标预测错位逐格累积,字符被挤进彼此位置。
**正确做法**:ASCII 走 run-pack,非 ASCII 强制 CUP(模式 P4)。

### 反模式 AP3:逐 chunk partial JSON parse

**症状**:工具参数较长时(如大段代码 generation),parse 耗时随已接收长度线性增长,整体 O(n²),流式输出越来越卡。
**真实案例**:claudecode claude.ts:1818-1820 的注释是直接证据:"Use raw stream instead of BetaMessageStream to avoid O(n²) partial JSON parsing. BetaMessageStream calls partialParse() on every input_json_delta"。
**正确做法**:中间态只拼接 raw string,终态一次性 parse(模式 P2)。

### 反模式 AP4:单 write 大缓冲区

**症状**:Mac Terminal.app 在单 write 携带 ~1KB+ 混合 CSI+SGR+UTF-8 时丢字节,表现为底部横线"变短"或乱码。
**真实案例**:atomcode retained.rs:10018-10030 记录了"bot_rule shortens"bug,解法是拆成 512 字节 chunk 分次 write+flush。
**正确做法**:分块写入,512 字节/chunk。

### 反模式 AP5:resize 即时 reflow

**症状**:拖拽窗口时每秒数十次 resize,每次触发完整 ANSI reflow,conhost 在 resize 中间态写大段数据导致闪烁/卡死。
**真实案例**:atomcode worker.rs:444 用 75ms 防抖 + worker.rs:506-540 的"安静窗口"逻辑规避。
**正确做法**:resize 防抖 75ms,只取最终尺寸。

### 反模式 AP6:强制 width_cjk

**症状**:markdown 表格边框在 Windows 上被拉伸为 2 倍宽,Pondering spinner 左右抖动。
**真实案例**:atomcode width.rs:10-39 详述了从"按 locale 探测"到"按 Windows ACP 探测"再到"纯 opt-in"的三次迭代,最终发现现代终端(macOS Terminal/iTerm2/alacritty/kitty/wezterm/Windows Terminal/conhost ConPTY)都把 ambiguous 字符按 1 列渲染,强制 width_cjk 反而错位。
**正确做法**:默认 `UnicodeWidthChar::width`,仅 `ATOMCODE_CJK_WIDTH=1` 显式开启。

## 12. laew 现状深度走读:阻塞链的全链路分析

在给出借鉴路线前,有必要把 laew 当前的"阻塞链"完整走读,明确每一步的改造点。

### 12.1 入口:`agent/mod.rs` 的 `run_session`

`src/agent/mod.rs` 的 agent 循环是 `Session` 驱动的 `complete → tool_calls → 执行 → tool_result 回填` 流程。LLM 调用发生在 `complete` 阶段,调用链为:

```
run_session → LlmClient::complete(messages) → Completion { text, tool_calls, ... }
```

`complete` 是 `async fn`,内部调用 `anthropic.rs` 或 `openai.rs` 的 `complete()`。整个调用**阻塞等待** `Completion` 返回,期间 TUI 无任何更新。

### 12.2 Anthropic 阻塞循环

`src/llm/anthropic.rs:234-301` 的 `AnthropicClient::complete`:

```rust
async fn complete(&self, messages, tools) -> Result<Completion> {
    let params = AnthropicRequest { stream: true, ... };  // 开了 stream 头
    let resp = self.client.post(&self.end_point).json(&params)
        .headers(headers).send().await?;
    let mut sse = SseStream::new();
    let mut sink = ParseSink::new();
    let mut resp = resp;
    loop {
        match resp.chunk().await {
            Ok(Some(bytes)) => {
                let evs = sse.push(&bytes)?;
                for ev in evs {
                    let mut p = AnthropicParser;
                    p.feed(&ev, &mut sink)?;  // 只聚合
                }
            }
            Ok(None) => break,
            Err(e) => return Err(...),
        }
    }
    if let Some(ev) = sse.finish()? { ... }
    sink.finish()  // ← 全文就绪后才返回
}
```

关键观察:**`stream: true` 已经设了,HTTP 层已经在流式接收,`SseStream` 也在按事件解析,但 `ParseSink` 只累积不输出**。数据流已经到了"事件"层,只是没有"事件→UI"的桥。

### 12.3 ParseSink 的纯函数式设计

`src/llm/sse.rs:202-319` 的 `ParseSink`:

```rust
pub struct ParseSink {
    text: String,
    in_flight: VecDeque<InFlightToolCall>,
    tool_calls: Vec<ToolCallReq>,
    usage: Usage,
    stop_reason: Option<String>,
    finished: bool,
    errored: Option<String>,
}
```

这是一个纯状态机,**没有任何回调/通道/通知机制**。`feed()` 只修改自身状态,finish() 返回最终 `Completion`。

### 12.4 TUI 侧:`engine.rs` 的全量重绘

`src/tui/engine.rs:212-241` 的 `present()`:

```rust
pub fn present(frame: &Frame) -> io::Result<()> {
    let mut stdout = io::stdout().lock();
    execute!(stdout, MoveTo(0, 0), Clear(ClearType::All))?;  // 全量清屏
    for (y, row) in frame.cells.iter().enumerate() {
        execute!(stdout, MoveTo(0, y as u16))?;
        for cell in row { ... paint_cell ... }
    }
    execute!(stdout, ResetColor)?;
    stdout.flush()?;
}
```

全量清屏 + 逐 cell 重绘,没有 diff、没有区域标记、没有同步输出。对 <30 行的子屏(ProviderForm/ProviderList)够用,但对流式长文本是性能灾难。

### 12.5 改造点总结

| 层次 | 现状 | 改造 | 借鉴来源 |
|------|------|------|---------|
| `ParseSink` | 纯聚合无通知 | 加 `on_delta: Option<Box<dyn Fn(&DeltaEvent)>>` | pi EventStream.push |
| `DeltaEvent` | 无 Reasoning | 加 `Reasoning(String)` | atomcode StreamEvent |
| agent 循环 | `complete()` 阻塞 | 拆为 `stream()` 返回 `mpsc::Receiver<DeltaEvent>` | opencode ToolStream |
| TUI 主循环 | 无事件源 | 加 `select!{ recv(delta_rx) → render }` | pi requestRender |
| `present()` | 全量清屏 | 加脏标记 + diff 渲染 | atomcode cell-diff |
| 中断 | 无 | `AbortSignal` 传入 complete | claudecode query.ts |

## 14. 多流并发渲染的深入观察

laew 是多 Agent 架构(Yolo/Plan/Main-Work/SubAgent-Work/Quality-Check/SessionContext 共 6 角色),多流并发是刚需。本轮补充观察各仓如何处理"多个输出源同时更新终端"。

### 14.1 atomcode 的 parallel batch 模型

`crates/atomcode-tuix/src/render/retained.rs:1369-1439` 的 `parallel tool batch`:

```rust
/// header + N child rows for a parallel tool batch. Subsequent ...
batch_id: String,
```

每个并行工具有独立 `batch_id`,`commit_inflight_tool` 在单个工具完成时就地更新该工具的 child rows,不影响其他正在运行的工具。`skip_body_scroll_count`(retained.rs:1254-1260)记录"在途工具占据的多行",每个工具完成时回补,避免 body 区域出现空白缝隙。

对 laew 的启示:SubAgent-Work 和 Main-Work 并行时,每个 Agent 输出占据独立的 y 区域行范围,各自的 spinner 在自己的 header 行内更新,互不覆盖。

### 14.2 claudecode 的 Agent 状态隔离

`src/components/CoordinatorAgentStatus.tsx` 为每个 Agent 渲染独立的状态行,`AgentProgressLine.tsx` 显示单 Agent 的流式进度。ink 的帧缓冲是单一 `Screen`,多 Agent 通过"不同 y 区域 + 各自 damage 矩形"隔离——`diffEach` 的脏区并集自然处理多区域并发更新(screen.ts:1169-1178)。

### 14.3 laew 的多流设计建议

laew 的 6 角色不是同时输出的——Yolo 分类 → Plan(仅 hard) → Main-Work(仅 medium/hard) → SubAgent → QC → SessionContext,是**流水线**而非**并行墙**。所以 laew 的多流并发场景主要是:

1. **SubAgent 并行**:多个 SubAgent-Work 同时执行 → 参考 atomcode parallel batch,每个 SubAgent 一个 y 区域 + spinner。
2. **正文 + 状态栏同时更新**:正文流式追加时,底部状态栏显示 token 数/耗时 → 参考 atomcode 的 footer 固定区域 + body 滚动区域分离(retained.rs:208-226 `scroll_up` 只滚 body 区,footer 不动)。

## 15. 总结

本轮分析聚焦"流式传输 + 终端渲染"这一独立维度,覆盖 6 个外部仓库 + laew 自身基线。

**核心结论**:laew 的 SSE 解析基础设施(`SseStream` + `ParseSink` + `DeltaEvent`)已经完备,实现流式输出的**主要工作不在解析层,而在"ParseSink→TUI"的实时通道**——具体是加一个 on_delta 回调、一个 mpsc 通道、一个 16ms 脏标记节流。这三步(P0)即可让 laew 从"等全文弹出"跨越到"类 Claude Code 的流式体验"。

**最高性价比投入**:P0(流式骨架,2 周) + P1(增量 markdown,2 周)。合计 4 周,每天代码量约 100-200 行 Rust,无架构风险。

**最深工业级参考**:atomcode 的 `crates/atomcode-tuix/src/render/` 整套 cell-diff + DECSET 2026 + ASCII run-pack + 分块写入 + resize 防抖,是终端渲染的"完全体",laew 在 P3 增量 diff 阶段可直接对标。

**最巧妙算法**:opencode `packages/session-ui/src/components/markdown-stream.ts:88-122` 的 `project()` 增量投影——利用 `marked.lexer` 把未闭合围栏当单 token 的副作用,实现 O(增量长度)的流式 markdown 解析,是"借力打力"的典范。
