## 1. D21-1 伪标记识别（Harmony 流标记）

模型（尤其是开源模型）常在工具调用外包裹伪标记，流式输出时这些标记与用户文本混流。

### 1.1 伪标记类型谱系

| 标记类型 | 示例 | 含义 | 出现模型 |
|---------|------|------|---------|
| **Harmony channel** | `<\|channel\|>final<\|message\|>{...}<\|call\|>` | OpenAI Harmony 格式 | GPT-OSS 系列 |
| **END_TOOL_REQUEST** | `[END_TOOL_REQUEST]` | 旧版序列化结束标记 | 部分微调模型 |
| **XML-ish function tag** | `<function_calls>...</function_calls>` | 类 XML 工具调用 | Hermes / Gemma |
| **纯文本工具名** | `Tool: Bash\nCommand: ...` | 无 JSON 的纯文本 | 小模型/微调 |

### 1.2 openclaw grammar.ts（最完整伪标记库）

`openclaw/packages/tool-call-repair/src/grammar.ts`（321 行）：

**核心常量**：
```ts
export const END_TOOL_REQUEST = "[END_TOOL_REQUEST]"
export const HARMONY_CHANNEL_MARKER = "<|channel|>"
export const HARMONY_MESSAGE_MARKER = "<|message|>"
export const HARMONY_CALL_MARKER = "<|call|>"
```

**字符分类函数**：
```ts
export function isPlainTextToolNameChar(char: string | undefined): boolean {
  return Boolean(char && /[A-Za-z0-9_-]/.test(char))
}
export function isXmlishNameChar(char: string | undefined): boolean {
  return Boolean(char && /[A-Za-z0-9_.:-]/.test(char))
}
```

**扫描函数族**：
- `indexOfAsciiMarkerIgnoreCase`：在流中定位伪标记（忽略大小写）
- `isAsciiMarkerPrefixIgnoreCase`：判断当前位置是否以某标记开头
- `startsWithAsciiMarkerIgnoreCase`：从行首匹配
- `skipLineIndentation` / `skipWhitespace`：跳过缩进/空白
- `consumeLineBreak`：消费换行
- `utf8ByteLengthWithinLimit`：UTF-8 字节长度校验（防护超大 payload）

## 2. D21-2 保护区间（Protected Range）

**核心问题**：模型可能在**用户可见的代码块/行内代码**里写出「看起来像工具调用」的文本。如果修复器把这些文本当成工具调用删掉，用户就丢失了可见内容。

### 2.1 openclaw contracts.ts（保护区间类型系统）

`openclaw/packages/tool-call-repair/src/contracts.ts`（关键类型）：

```ts
/** Source range that must remain literal user-visible text. */
export type PlainTextToolCallProtectedRange = { end: number; start: number }

export type PlainTextToolCallProtectedRangeResolver = (
  text: text,
) => readonly PlainTextToolCallProtectedRange[]

export function isOffsetInProtectedRanges(
  offset: number,
  ranges: readonly PlainTextToolCallProtectedRange[],
): boolean {
  return ranges.some((range) => offset >= range.start && offset < range.end)
}

export type PlainTextToolCallParseOptions = {
  allowedToolNames?: Iterable<string>   // 工具名白名单
  maxPayloadBytes?: number              // 单条最大 payload
}
```

**保护区间来源**：
- 围栏代码块（fenced code block ` ``` `）
- 行内代码（inline code `` ` `）
- 缩进代码块（indented code）
- 其他用户可见文本区域

### 2.2 保护语义

**conservative 原则**：
- 只要候选工具调用**部分落在保护区间内**，就**不修复**
- 宁可漏修（工具调用没被识别），不可误删（用户文本被改）
- 这是**安全优先**的设计——与 laew 的 fail-closed 哲学一致

### 2.3 laew 现状

laew 的 `json_repair.rs` **无保护区间概念**：
- 它修复的是**已确定为工具调用参数**的 JSON 文本
- 不做「这段文本是用户可见代码还是工具调用」的区分
- 在纯 JSON 修复场景下这是合理的（输入已隔离），但**流式场景需要保护区间**

**laew gap L2301-L2310**：
- L2301 P1：无保护区间（代码块内伪工具调用可能被误处理）
- L2302 P1：无工具名白名单（任意「工具名」形状都被尝试修复）
- L2303 P2：无 maxPayloadBytes 限制（超大 payload 可致 OOM）
- L2304 P2：无 conservative 语义（误删用户文本风险）

## 3. D21-3 流式防护（Stream Normalizer）

**核心问题**：流式输出是**增量 delta**，工具调用可能跨多个 delta 到达。修复器必须在**不等待完整响应**的情况下实时工作。

### 3.1 openclaw stream-normalizer.ts（1961 行，最核心实现）

`openclaw/packages/tool-call-repair/src/stream-normalizer.ts`（1961 行）：

**核心职责**：
- 接收增量文本 delta
- 维护**累积状态**（已处理文本 + 当前解析位置）
- 实时识别伪标记 + 工具调用候选
- 调用 protection-fast-path 判断是否在保护区内
- 输出：修复后的工具调用 + 剥离伪标记的用户文本

**关键依赖**：
```ts
import { isOffsetInProtectedRanges, ... } from "./contracts.js"
import { consumeLineBreak, END_TOOL_REQUEST, HARMONY_CALL_MARKER, ... } from "./grammar.js"
import { scanPlainTextToolCall } from "./payload.js"
import { advanceProtectionScanState, resolveProtectionFastPath, ... } from "./protection-fast-path.js"
```

### 3.2 增量扫描状态机

stream-normalizer 维护的状态：
- `accumulatedText`：已累积的完整文本
- `scanPosition`：当前扫描位置
- `protectionState`：当前 Markdown 块状态（来自 protection-fast-path）
- `pendingToolCalls`：已识别待确认的工具调用

**扫描循环**：
```
新 delta 到达
  → 追加到 accumulatedText
  → 从 scanPosition 继续扫描：
      ├─ 识别伪标记（Harmony / END_TOOL / XML-ish）
      ├─ 识别工具调用候选（JSON 形状 / 纯文本形状）
      ├─ 调用 protection-fast-path 判断是否在保护区内
      │    ├─ 在保护区内 → 跳过（conservative）
      │    └─ 不在保护区内 → 尝试修复
      └─ 输出修复结果 + 更新 scanPosition
```

### 3.3 与 laew partial_json.rs 的对比

| 维度 | laew partial_json.rs | openclaw stream-normalizer |
|------|--------------------|--------------------------|
| 输入 | 完整/截断的单个 JSON | 增量 token 流 |
| 输出 | 修复后的 JSON 或 None | 修复后的工具调用 + 用户文本 |
| 保护区间 | ❌ | ✅ ProtectedRange |
| 伪标记 | ❌ | ✅ Harmony/END_TOOL/XML-ish |
| 状态机 | 单遍 char 扫描 | 增量累积 + 块状态 |
| 失败语义 | None（丢弃） | conservative（保留原文） |

**laew gap L2311-L2320**：
- L2311 P1：无流式工具调用修复（partial_json 只处理完整/截断 JSON）
- L2312 P1：无增量扫描状态机
- L2313 P2：无伪标记剥离
- L2314 P2：无用户文本/工具调用分流输出

## 4. D21-4 增量 Markdown fast-path

**核心问题**：判断「候选工具调用是否在代码块内」最准确的方式是完整 Markdown 解析，但**每收到一个 delta 就全文解析是 O(n²)**。

### 4.1 openclaw protection-fast-path.ts（252 行，精巧设计）

`openclaw/packages/tool-call-repair/src/protection-fast-path.ts`：

**设计哲学**（文件头部注释）：
> *Conservative fast path. It answers only when it can prove the verdict from fence state alone, and reports `undefined` for every shape it does not model. Callers must fall back to the authoritative full parse whenever the answer is `undefined`, so protection semantics stay identical to a full parse.*

**核心状态 ProtectionScanState**：
```ts
export type ProtectionScanState = {
  fenceChar: "`" | "~" | undefined  // 当前围栏字符
  fenceLength: number                 // 围栏长度（``` vs `）
  paragraphAmbiguous: boolean         // 当前段落含不可建模结构
  // ...（更多状态字段）
}
```

**增量推进**：
```ts
export function advanceProtectionScanState(
  state: ProtectionScanState,
  delta: string,
): ProtectionScanState
```

**三种返回**：
- `true`：确定在代码块外（可安全修复）
- `false`：确定在代码块内（必须跳过）
- `undefined`：无法确定（回退到完整 Markdown 解析）

### 4.2 状态机建模范围

**能建模的**：
- 围栏代码块（fenced code block）：` ``` ` ~~~ `
- 围栏开/关状态追踪

**不能建模的**（返回 undefined）：
- 行内代码（inline code span）
- 缩进代码块（indented code）
- 块引用（block quote）
- 列表（list）

**关键设计**：`paragraphAmbiguous` 标志——当当前段落含不可建模结构时置位，**遇到空行才清除**（因为这些结构不跨空行）。

### 4.3 与 laew 的对比

laew 无 Markdown 解析能力（`tui/` 是纯文本 cell-based），因此：
- 无代码块概念
- 无保护区间需求（工具调用 JSON 已隔离于 SSE 流）
- 但**未来若支持 Markdown 渲染（D10-3）**，保护区间将变得必要

**laew gap L2321-L2325**：
- L2321 P2：无增量 Markdown 状态机
- L2322 P2：无 conservative fast-path
- L2323 P2：无 full-parse fallback

## 10. 设计哲学总结

### 10.1 工具调用修复的演进

| 层级 | 能力 | 代表 |
|------|------|------|
| L1 语法修复 | 修 JSON 语法错误 | laew / atomcode |
| L2 截断恢复 | 恢复不完整 JSON | laew partial_json.rs |
| L3 Schema 校验 | 校验参数类型 | laew tool_schema_validator.rs |
| L4 伪标记识别 | 识别模型伪标记 | openclaw |
| L5 流式防护 | 增量实时修复 | openclaw |
| L6 保护区间 | 不误删用户文本 | openclaw |

laew 当前在 L1-L3，openclaw 达到 L4-L6。

### 10.2 laew 的差异化定位建议

laew 作为 Rust CLI，应走 **「协议纯净 + 流式防护」** 路线：
- 优先支持主流模型（Anthropic/OpenAI）的干净 JSON（L1-L3 已覆盖）
- 增量增加 Harmony/伪标记支持（L4）——服务开源模型用户
- 流式防护（L5）与 `llm/sse.rs` 深度集成
- 保护区间（L6）与 D10-3 Markdown 渲染同步建设
- 不追求纯文本修复（小模型非 CLI 主流场景）

### 10.3 与既有 laew 能力的关系

| 既有能力 | 本轮增强 |
|---------|---------|
| `json_repair.rs` 5 种语法修复 | 加伪标记识别 + 流式入口 |
| `partial_json.rs` 截断恢复 | 加增量扫描 + 保护区间 |
| `tool_schema_validator.rs` schema 校验 | 加 maxPayloadBytes 限制 |
| `llm/sse.rs` SSE 流 | 加 stream-normalizer 中间层 |
