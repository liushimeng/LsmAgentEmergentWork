> **本专题不是什么**：不重复 `专题-工具调用深度分析.md` 已经覆盖的工具 Schema 概述；不重复 `atomcode.md` 第 9 章 CodeIntel 七件套的整体介绍（那个文档已在 3400-3700 行区间把 CodeIntel 主线讲清楚），本文**只补充 CodeIntel 主线未深入的「索引存储格式、增量失效、内存缓存、Fallback 链」**。
> **目标读者**：正在为 `laew` 设计 Grep / Glob / 符号检索 / 语义检索工具的工程师。

  if (userWantsSystemRipgrep) {

  }
  // 2. bundled 模式（Bun-internal rg）

**ripgrep 来源**（三层 fallback）：
- `system` —— 系统 PATH 的 `rg`（用户显式 `USE_BUILTIN_RIPGREP=false` 才走，**避免 PATH hijacking**：`src/utils/ripgrep.ts:38-44` 注释明确警告只用 `'rg'` 不传完整路径）

    .hidden(true)
    .git_ignore(true)
    .git_global(true)
    .git_exclude(true)

pub struct CodeIndex {
    cache: Mutex<Option<(u64, Arc<CodeGraph>)>>,

impl CodeIndex {
    pub fn get(&self, root: &Path) -> Arc<CodeGraph> {
        let root = super::canonical(root);
        let files = collect_files(&root);
        let fp = fingerprint(&files);
        if let Some((cfp, g)) = self.cache.lock().unwrap().as_ref() {
            if *cfp == fp { return g.clone(); }   // 命中缓存
        }
        let g = Arc::new(build_from_files(&root, files));
        *self.cache.lock().unwrap() = Some((fp, g.clone()));

    }
}

**指纹策略**（`index.rs:144-148` + `191-199`）：
```rust
struct Walked {
    path: PathBuf,
    mtime_ns: u128,    // 纳秒级（不是秒），防同秒编辑不重建
    len: u64,           // 防同 mtime 但内容变化
}

fn fingerprint(files: &[Walked]) -> u64 {
    let mut h = DefaultHasher::new();
    for w in files {
        w.path.hash(&mut h);
        w.mtime_ns.hash(&mut h);
        w.len.hash(&mut h);
    }
    h.finish()
}
```

## ④ 10~15 个设计模式 / 反模式

### 模式 P1：ripgrep 三层 fallback（system / bundled / vendor）
**来源**：claudecode `src/utils/ripgrep.ts:31-65`
**精华**：覆盖「用户显式指定系统 rg」/「Bun 静态编译内部 rg」/「npm vendor 预编译 rg」三种场景；memoize 避免重复探测。
**反例**：单纯 spawn `rg` 不带 PATH hijacking 防护（注释 `:38-44` 警告）。

### 模式 P2：包内 ripgrep + pkg sidecar 双源
**来源**：deepseek-harness `search-core.ts:171-181`
**精华**：pkg single-file runtime 必须在 executable 旁放 `-rg` sidecar（pkg 虚拟文件系统不能 spawn），否则用 `@vscode/ripgrep` npm 包。
**适用**：需要在 Node.js 单文件分发场景用 ripgrep。

### 模式 P3：GitHub Release 自举 + Effect.cached
**来源**：opencode `packages/core/src/ripgrep/binary.ts:92-122`
**精华**：下载 + 解压 + chmod 0o755 一次性完成；`Effect.cached` 让重复 `ripgrep.filepath()` 拿纯缓存值。**下载完立刻删压缩包**节省磁盘。
**适用**：不希望 vendor ripgrep 但又需要保证 ripgrep 一定可用的工具链。

### 模式 P4：streaming `Sink` 回调 + heap_limit
**来源**：atomcode `crates/atomcode-capabilities/src/tools/grep.rs:144-211`
**精华**：用 ripgrep 内核 crate 的 `Searcher` + `Sink` 而非 `regex::Regex::find_iter`，前者流式扫描 + `heap_limit(10MB)` 内存上限防 OOM。
**反例**：`laew` 当前 `grep.rs:323-324` 用 `reader.lines().filter_map(|l| l.ok()).collect()` —— **整文件读**到 `Vec<String>`，3MB 单文件就能 OOM。

### 模式 P5：smart-case + literal fallback
**来源**：atomcode `grep.rs:101-114`
**精华**：先按"是否含大写字母"决定 case-insensitive；regex 编译失败自动转义为字面量再试。
**适用**：模型常输出非法 regex（如未转义括号），必须给恢复路径。

### 模式 P6：mtime 纳秒 + len 指纹
**来源**：atomcode `codeintel/index.rs:144-148` + `:191-199`
**精华**：用 `mtime_ns` 而非 `mtime`（秒级），并加 `len` 双重防护。**测试 `index.rs:397-411` 验证同秒编辑能重建**。
**反模式**：用 `mtime` 秒级做失效 → 同秒写多次会导致缓存陈旧。

### 模式 P7：把 Read 工具的 deny rules 反向注入 Grep/Glob ignore
**来源**：claudecode `src/tools/GrepTool/GrepTool.ts:412-427` + `src/utils/permissions/filesystem.ts:837`
**精华**：统一权限模型，Read 不能读的文件 → Grep 也不能搜内容，避免"绕过 Read 直接 Grep 偷文件"。
**反模式**：opencode 是显式 ask（`ctx.ask({ permission: 'grep' })`），每次都问用户；体验差。

### 模式 P8：截断引导话术三件套
**来源**：claudecode / pi / opencode / deepseek-harness 都有
**精华**：截断时给出**具体下一步动作**（加 limit / 加 path / 换 glob），不是干巴巴 "truncated"。
**反例**：`laew` `grep.rs:208-211` 只说 `...[截断,还有 N 个文件未显示]`，没告诉模型"再 grep 加 path 或更具体的 pattern"。

### 模式 P9：treesitter 符号索引 + LSP 双通道 fallback
**来源**：atomcode `codeintel/index.rs:303-324` + `lsp_tool.rs:51-58`
**精华**：grep（regex 找）→ lsp unavailable（语义）→ read_symbol/find_references（符号定义）三层 fallback；不强制某层存在，模型自主选择。
**反模式**：硬绑定单一策略（只 grep 或只 lsp），任一失败就死。

### 模式 P10：search error vocabulary 稳定化
**来源**：deepseek-harness `search-core.ts:78-96`
**精华**：4 个稳定 error code（`SEARCH_INVALID_PATTERN` / `SEARCH_FAILED` / `SEARCH_RAW_OUTPUT_OVERFLOW` / `SEARCH_ABORTED`），调用方按 code 分支而非解析消息。
**适用**：工具链可观测性 / 重试策略 / UI 降级。

### 模式 P11：memory_search 多维度融合
**来源**：openclaw `extensions/memory-core/src/memory/hybrid.ts:88-335`
**精华**：6 个评分维度（vector + BM25 + path + importance + project + specificity tier），加权融合后再做 MMR + temporal decay 重排。
**反模式**：仅 BM25 或仅 cosine，召回/精度单维优化。

### 模式 P12：FTS5 UPDATE OF narrow trigger
**来源**：hermes-agent `hermes_state_common.py:737-746`
**精华**：FTS5 trigger 用 `AFTER UPDATE OF content, tool_name, tool_calls, role` 而非 broad `AFTER UPDATE`，**只在内容列变化时触发**，避免 status/compacted 写入触发 FTS I/O。
**适用**：任何「内容表 + FTS 虚表」双表维护。

### 模式 P13：LanceDB metadata 谓词在向量 ranking 之前
**来源**：openclaw `extensions/memory-lancedb/lancedb-store.ts:185-190`
**精华**：`table.vectorSearch(vector).where(memoryAgentPredicate(agentId)).limit(limit)` —— metadata 谓词先过滤，再做向量 ANN；保证跨 agent 行根本进不了候选集。

### 模式 P14：ensureTool 链 + Termux/Android 特殊处理
**来源**：pi `packages/coding-agent/src/utils/tools-manager.ts:335-374`
**精华**：
1. 自己的 bin 优先
2. 系统 PATH 兜底（fd 还试 `fdfind` 别名）
3. `PI_OFFLINE=1` 跳过下载
4. Android/Termux 提示 `pkg install ripgrep`（glibc 二进制跑不了）

### 反模式 A1：reader.lines().collect() 整文件读
**来源**：`laew` 当前 `src/agent/tools/grep.rs:323-324`
**问题**：3MB 单文件就能让进程内存吃紧，minified bundle 文件直接 OOM。
**修复**：用 `grep-searcher` 内核 crate 或 `BufRead::read_line` 流式 + heap cap。

### 反模式 A2：硬编码 SKIP_DIRS 数组代替 .gitignore
**来源**：`laew` 当前 `src/agent/tools/grep.rs:26`
```rust
const SKIP_DIRS: &[&str] = &[".git", "target", "node_modules", ".cache", "dist", "build"];
```
**问题**：不读项目 `.gitignore`，意味着 `Cargo.lock`、`build/`（非 `dist`）、`coverage/`、`__pycache__/` 仍会被扫到。
**修复**：用 `ignore::WalkBuilder`（atomcode 已示范），自动读 `.gitignore` / `.ignore` / `.git/info/exclude`。

### 反模式 A3：截断引导不告诉模型下一步
**来源**：`laew` 当前 grep.rs
**问题**：`...[截断,还有 N 个文件未显示]` 是被动报告，没给"再加 path / 加 head_limit / 换 glob"等动作。
**修复**：参考 pi 的 `${effectiveLimit} matches limit reached. Use limit=${effectiveLimit * 2} for more, or refine pattern`。

### 反模式 A4：walkdir 无并行度
**来源**：`laew` 当前 `grep.rs:260-301`
**问题**：10w 文件串行遍历，单核跑满。
**修复**：`ignore::WalkBuilder::new(...).threads(num_cpus::get())`（rayon 并行）；或 fork/join per directory。

### 模式 P15：FTS5 + Trigram 双索引并存
**来源**：hermes-agent `hermes_state_common.py:697-794`
**精华**：同时维护标准 FTS5（按 word 切）+ Trigram FTS5（CJK + 部分匹配支持），查询时按需选择；trigger 用 `AFTER UPDATE OF <col>` narrow 模式避免 status/compacted 写入触发 FTS I/O。
**适用**：需要在 SQL 数据库内做全文检索 + 多语言支持的会话历史 / 日志检索场景。

### 模式 P16：presentationMeta 拆分（render vs meta）
**来源**：deepseek-harness `search-core.ts:60-65` 注释
**精华**：`render` 是给模型看的 markdown 文本，`presentationMeta` 是给 UI 的结构化数据（sources / snippet / publishedAt / answer）。`meta` 持久化到 session log 每次请求重发，必须单独 cap（`SEARCH_META_MAX_BYTES = 65_536`）；`meta` malformed 时 `searchMetaFromResult` defensive narrowing 返 undefined，UI 退化到 generic card 而非 throw。
**适用**：任何 tool 输出有「给模型 + 给 UI」双消费者的场景。

### 反模式 A5：deny rules 不反向注入 grep ignore
**来源**：`laew` 当前没有权限系统，但若未来引入 Read 权限，**必须**参考 claudecode 模式 P7 反向注入。
**问题**：Read 不能读的文件用户能 grep 偷取 → 权限模型被绕过。

### 反模式 A6：用静态 `Vec<String>` 收集整文件
**来源**：`laew` 当前 `grep.rs:323-324` `reader.lines().filter_map(|l| l.ok()).collect()`
**问题**：
- 3MB 单文件 → Vec 占用 ~3MB
- minified bundle 单行 5MB → Vec 单元素就 5MB
- 100 个文件就 OOM
**修复**：参考 atomcode `grep.rs:144-211` 用 `Searcher` + `Sink` 回调流式 + `heap_limit`；或者最简方案：`BufReader::read_line` 循环 + 在循环里即匹配即输出，零中间 Vec。

```rust
use grep::regex::RegexMatcherBuilder;
use grep::searcher::{SearcherBuilder, BinaryDetection, Sink};
use ignore::WalkBuilder;

const DEFAULT_LIMIT: usize = 100;
const MAX_RESULTS_CAP: usize = 10_000;
const MAX_LINE_BUF_BYTES: usize = 10 * 1024 * 1024;

fn search(root: &Path, matcher: &RegexMatcher, max: usize, context: usize) -> (Vec<String>, usize) {
    let mut out = Vec::new();
    let mut match_count = 0usize;
    let walk = WalkBuilder::new(root)
        .hidden(false)                          // 默认不读隐藏（与 claudecode Grep 反）
        .git_ignore(true).git_global(true).git_exclude(true)
        .filter_entry(|e| {
            if e.file_type().map(|t| t.is_dir()).unwrap_or(false) {
                if let Some(name) = e.file_name().to_str() {
                    return !is_skip_dir(name);  // .git / target / node_modules / dist / build / __pycache__
                }
            }
            true
        })
        .build();
    let mut searcher = SearcherBuilder::new()
        .line_number(true)
        .before_context(context).after_context(context)
        .binary_detection(BinaryDetection::quit(b'\x00'))
        .heap_limit(Some(MAX_LINE_BUF_BYTES))
        .build();
    for entry in walk.flatten() {
        if match_count >= max { break; }
        let _ = searcher.search_path(matcher, entry.path(), sink);
    }
    (out, match_count)
}
```

## ⑧ 附录 A：openclaw hybrid 融合评分细节深挖

为了让 laew 在 P2-1 设计混合检索时有完整参考，下面展开 openclaw `hybrid.ts:88-335` 的完整评分逻辑（按出现顺序）：

### 步骤 1：双源合并（`hybrid.ts:127-194`）

```typescript
const byId = new Map<string, MergedEntry>()

// Vector 来源
for (const r of params.vector) {
  byId.set(r.id, {
    vectorScore: r.vectorScore,
    textScore: 0,
    exactPathSpecificity: r.exactPathSpecificity ?? 0,
    hasVector: true,
    hasKeyword: false,
    ...
  })
}

// Keyword 来源（同 id 合并）
for (const r of params.keyword) {
  const existing = byId.get(r.id)
  if (existing) {
    existing.textScore = r.textScore
    existing.hasKeyword = true
    existing.exactPathSpecificity = Math.max(existing.exactPathSpecificity, r.exactPathSpecificity ?? 0)
  } else {
    byId.set(r.id, { vectorScore: 0, textScore: r.textScore, ... })
  }
}
```

### 步骤 2：计算 keyword 分数（`hybrid.ts:200-205`）

```typescript
const keywordScore =
  entry.textScore > 0
    ? entry.rankingScore                                       // body BM25
    : entry.exactPathSpecificity > 0
      ? 0                                                     // exact path tier 不需要 keyword
      : entry.pathScore                                       // 部分路径命中
```

### 步骤 3：加权 content score（`hybrid.ts:211-213`）

```typescript
const dropMediaTextSignal =
  entry.hasVector && !entry.hasKeyword &&
  params.vectorWeight > 0 && params.isNonTextMediaPath?.(entry.path) === true

const contentScore = dropMediaTextSignal
  ? entry.vectorScore                                          // 媒体文件只信向量
  : params.vectorWeight * entry.vectorScore +
    params.textWeight * keywordScore                             // 加权融合
```

### 步骤 4：Temporal decay（`hybrid.ts:253-258`）

调用 `applyTemporalDecayToHybridResults` 把 `merged` 按 mtime 衰减：
- DEFAULT_TEMPORAL_DECAY_CONFIG 启用 → score 乘 `exp(-Δt / τ)`
- 关闭 → 保留原 score

### 步骤 5：Importance + project ranking（`hybrid.ts:259-273`）

```typescript
const rankable = applyProjectRanking(
  applyImportanceMultiplier(decayed),                          // 重要性乘子
  params.activeProjectKeys,
).map((entry) => {
  const exactPathTieScore = entry.score
  return Object.assign(entry, {
    exactPathTieScore,
    // exact tier 强制 score = projectScoreMultiplier（path 特异性 > 一切）
    score: entry.exactPathSpecificity > 0
      ? projectScoreMultiplier(entry.projectKey, params.activeProjectKeys)
      : entry.score,
  })
})
```

### 步骤 6：3 档 specificity tier 排序 + MMR（`hybrid.ts:300-323`）

```typescript
const compareExactTieScores = (a, b) =>
  b.exactPathTieScore - a.exactPathTieScore ||                 // 1. decayed 加权 score
  b.lexicalRank - a.lexicalRank ||                            // 2. BM25 rank (raw)
  a.path.localeCompare(b.path) ||                             // 3. path 字典序
  a.startLine - b.startLine ||
  a.endLine - b.endLine

const exact = ([3, 2, 1] as const).flatMap((specificity) => {
  const tier = rankable
    .filter((entry) => entry.exactPathSpecificity === specificity)
    .toSorted(compareExactTieScores)                          // tier 内排序
  if (temporalDecayConfig.enabled) return rerankExactGroup(tier)
  const contentBacked = tier.filter((e) => e.hasWeightedContentRelevance || e.lexicalRank > 0)
  const pathOnly = tier.filter((e) => !e.hasWeightedContentRelevance && e.lexicalRank === 0)
  return rerankExactGroup(contentBacked).concat(rerankExactGroup(pathOnly))
})

const ranked = [
  ...exact,
  ...(mmrConfig.enabled ? applyMMRToHybridResults(nonExact, mmrConfig) : nonExact),
]
```

**关键设计点**：

## ⑫ 附录 E：本专题对 laew 的 6 条 actionable 总结

1. **`grep.rs` 必须用 `grep-searcher` 内核 crate + `ignore::WalkBuilder`**：当前 `BufRead::lines().collect()` 整文件读在大仓库会 OOM。优先 P0。
2. **`grep.rs` SKIP_DIRS 硬编码数组改为 `ignore::WalkBuilder` 自动读 `.gitignore`**：覆盖 `Cargo.lock`、`__pycache__/`、`coverage/` 等漏网场景。优先 P0。
3. **截断引导话术改为「refine pattern / use limit=N / use head_limit=N」**：当前 `...[截断,还有 N 个文件未显示]` 是被动报告，模型不知道怎么继续。优先 P0。
4. **CLAUDE.md 第 31 行更新为「内置 Bash / Read / Write / Edit / Glob / Grep 共 6 个工具」**：与实际代码状态对齐。可在任意合并窗口做。
5. **符号提取走 tree-sitter 而非 LSP**：LSP 需要常驻 server 进程负担太重；tree-sitter 内嵌在进程内，按需 parse + 指纹缓存。中期 P1。
6. **语义检索默认关闭 + 用户显式开 + sqlite-vec 本地存储**：与本地 SQLite 持久化兼容；embedding 走 `candle-transformers` 或 OpenAI API 均可。远期 P2。
