## 2. 背景：企业为何需要多租户与团队记忆

LLM Agent CLI 的工业落地已经从「个人开发者的 `-p` 玩具」走向「企业级研发团队的协作工具」。这一阶段
绕不开四件事：

1. **租户隔离 (Tenant Isolation)**：一家公司可能有 N 个团队（前端、后端、测试、SRE），团队之间不能
   看到对方的私有 L1 记忆与项目说明。
2. **团队记忆 (Team Memory)**：团队成员共享的"团队约定 / 代码风格 / 上线流程 / 值班人"——典型的
   L2/L3 沉淀。
3. **组织级共享 (Org-level Sharing)**：跨团队复用的资产（中间件权限说明、Common Skill 库、Wiki）。
4. **审计与合规 (Audit & Compliance)**：GDPR/SOC2 要求按 user/team 粒度的数据保留、删除请求、访问日志。

企业级 Agent CLI 必须同时回答以下问题：

- "这条 L1 记忆属于哪个 user / agent / team / session？"
- "我能不能看到别人 L1 里的某条记录？"
- "团队成员能不能引用其它成员的 L2 场景？"
- "L1 写入时，相同语义的旧记录要不要合并？"
- "用户 A 离职了，他的 L0/L1 数据要 30 天内删除——脚本能不能批量完成？"
- "团队共享的 Skill 升级到 v2，team member 看到的是不是 v2？"

7 个工程的回答深度差异巨大，下面逐项剖析。

**ACL 判定七步**（`permission-checker.ts:43-138`，**最强的一段**）：

```typescript
export function checkPermission(ctx: PermCheckContext): PermCheckResult {
  // 1. 资源不存在/归档 → DENY asset_not_available
  // 2. Owner 全允许
  if (asset.owner_user_id === user.user_id) return ALLOW owner
  // 3. 非 team 成员（status !== 'active'）→ DENY not_team_member
  // 4. visibility 限制
  switch (asset.visibility) {
    case "private":     // 严格私密：仅 owner；admin 也看不到
      return DENY visibility_restricted
    case "restricted":  // 仅显式 ACL 放行
      if (membership.role !== "admin") { /* 走 ACL 匹配 */ }
      break
    case "task":        // 任务内可读，admin 之外不可写
      if (action !== "read" && role !== "admin") return DENY
      break
    case "team":
    case "agent":       // 走角色默认权限
      break
  }
  // 5. 角色默认权限（admin = [read,write,assign,share]; member = [read]）
  // 6. 显式 ACL（user / team_role / agent 三种 subject）
  // 7. 拒绝
}
```

`roleDefaultCovers()` 工具判断"是否需要查 ACL 表"——admin 写操作 / member 读操作都是高频
**命中即放行**，跳过 ACL 查询；这条是性能优化关键。

`canBindAsset()` 与 `checkPermission` **互补**：前者管"资源能否挂到 agent 上"（如 private 资产
不能挂到别人的 agent；restricted 资产不能直接挂）。

**RRF 混合检索**（`store/search-utils.ts:18-46`）：

```typescript
export const RRF_K = 60;
export function rrfMerge<T>(lists: T[][], getId: (item: T) => string, k = RRF_K) {
  // 每个 item 的 RRF 分数 = sum over all lists of 1/(k + rank + 1)
  // 多次出现在不同列表的 item 分数相加（Reciprocal Rank Fusion）
  // 返回按 rrfScore 降序的合并结果
  for (const list of lists) {
    for (let rank = 0; rank < list.length; rank++) {
      const score = 1 / (k + rank + 1);
      const existing = map.get(id);
      existing ? existing.rrfScore += score : map.set(id, { item, rrfScore: score });
    }
  }
  return [...map.values()].sort((a, b) => b.rrfScore - a.rrfScore);
}
```

export const create = fn(z.object({ name: z.string().min(1) }), async ({ name }) => {
  const account = Actor.assert("account");
  const workspaceID = Identifier.create("workspace");
  const userID = Identifier.create("user");
  await Database.transaction(async (tx) => {
    // 1. account 必须 active（未删除）
    const active = await tx.select({ id: AccountTable.id }).from(AccountTable)
      .where(and(eq(AccountTable.id, account.properties.accountID), isNull(AccountTable.timeDeleted)))
      .then(rows => rows[0]);
    if (!active) throw new Error("Account is not active");
    // 2. 创建 workspace
    await tx.insert(WorkspaceTable).values({ id: workspaceID, name });
    // 3. 创建第一个 user（admin 角色）
    await tx.insert(UserTable).values({ workspaceID, id: userID, accountID, name: "", role: "admin" });
    // 4. 创建 billing（余额 0）
    await tx.insert(BillingTable).values({ workspaceID, id: Identifier.create("billing"), balance: 0 });
  });
  // 5. 用 system actor 创建 default API key
  await Actor.provide("system", { workspaceID }, () => Key.create({ userID, name: "Default API Key" }));
  return workspaceID;
});

### 5.4 RRF 公式

```text
score(item) = Σ over all lists L:
                1 / (k + rank_in_L(item) + 1)
where k = 60 (RRF_K constant from original paper)

多次出现在不同列表的 item 分数相加（Reciprocal Rank Fusion）
返回按 rrfScore 降序的合并结果
```

典型使用（`auto-recall.ts`, `memory-search.ts`, `conversation-search.ts`）：

```typescript
const merged = rrfMerge(
  [ftsResults, vecResults],
  (item) => item.record_id,
);
```

消除 3 处重复代码（`auto-recall` + `memory-search` + `conversation-search`）。

## 6. 共性模式

1. **"多维 ID 元组"是租户隔离的基础**。TencentDB `(teamId, userId, agentId, sessionId, taskId)` 5 元，
   opencode `(workspaceID, userID, accountID, role)` 4 元，jiuwenswarm `(session_id, member_name, role)`
   3 元；pi 仅 `(user)` 1 元。**维度越多，隔离越细；维度越少，部署越简单**。
2. **"显式 ACL" vs "scope 白名单" vs "默认角色权限"** 是 3 条不同路线。TencentDB 把 ACL 做成独立
   `AclEntity` 表（`subject_type × permission × effect × asset_id`），按需懒加载；opencode 把
   `admin/member` 写死成 enum；atomcode 用 `scope: Vec<String>` 物理路径白名单。
3. **"乐观锁"是并发写的最后一道防线**。TencentDB `assertVersionFresh` + `SKILL_VERSION_STALE=40901`；
   openclaw `version: 1` schema 字段；opencode Share `timeDeleted` 软删。
4. **"消息总线 vs 文件共享 vs 强一致数据库"** 是 3 种跨 agent 通信：claudecode mailbox 文件
   + lockfile；jiuwenswarm shared `outputs/` 文件名区分；TencentDB SQLite row-level。
5. **"租户 = 物理路径"** 是一种朴素但有效的方式（openclaw `workspaceKey = realpathSync`、
   deepseek-harness `WorkspaceRecord.path = fs.realpath`、jiuwenswarm `team_home`）。前提是
   文件系统支持硬链接/symlink 规范化，避免别名跨租户。
6. **"无 server 多租户"=本地 schema 升级**。claudecode、openclaw、pi、atomcode 都没有 server 层
   多租户，他们的多租户/团队/组织概念是**本地文件级别的协作**。
7. **"RRF"是事实标准混合检索融合公式**（TencentDB 唯一使用，k=60）；其它 6 工程都没有混合检索。
8. **"9 注入点"是协议无关注入的工业范式**。openclaw 的 context-engine 10 阶段（bootstrap/maintain/
   ingest/ingestBatch/afterTurn/commitTurn/assemble/compact/prepareSubagentSpawn/onSubagentEnded）
   是 lifecycle 视角；TencentDB 的 9 点是 content-position 视角；两者互补。
9. **"Actor / Context AsyncLocalStorage"** 是 opencode 提供的多租户上下文传递的 Rust/TS 范式
   （`Context.create<Info>()` + `provide()` + `use()`）。laew 后续扩 team 时可直接抄。
10. **"CrDT / LWW / 人工仲裁"** 是 3 种冲突解决路线。TencentDB L1 走 LLM 仲裁（store/update/
    merge/skip）；opencode Share 走 LWW（map set）；jiuwenswarm 走人工 review（review_runtime +
    `review_trigger=True`）。**没有工程用 CRDT**——Agent CLI 场景下，CRDT 的复杂度没收益。

> 当前零租户/团队/组织概念（仅 device_id + session_id）**，借鉴本专题 P0 路线图是性价比最高
> 的工业升级路径。
