### 1.2 laew 当前状态(必读,建议的靶向基线)

laew 当前持久化处于**「基础设施阶段」**:

```rust
// src/config/mod.rs:108-138
pub struct Db {
    conn: Mutex<Connection>,        // 单连接 + std::sync::Mutex 串行化
    db_path: PathBuf,
}

pub fn open(paths: &Paths) -> Result<Self> {
    let conn = Connection::open(&paths.db_path)?;
    Self::init_schema(&conn)?;       // 3 张表 + 2 个索引,IF NOT EXISTS,无迁移
    Ok(Self { conn: Mutex::new(conn), db_path: paths.db_path.clone() })
}
```

**已实现**:
- 序列化:`serde` + `serde_json`(QualityReport / AgentRole / ChatMessage / WorkFlowPlan)
- 存储:`rusqlite` + 3 张表(providers / session_memory / agent_memory)+ 2 个索引
- 并发:`std::sync::Mutex` 串行化所有 DB 操作
- 一致性:`UNIQUE(session_id, seq)` 约束 + `CHECK` 枚举约束
- 进程内计数:`AtomicU64` Session ID 计数器

**未实现**(本轮重点分析的对象):
- ❌ 多文件事务 / WAL / 跨表 ACID
- ❌ Schema 版本号 + 迁移 runner
- ❌ 序列化层抽象(MessagePack/二进制可选)
- ❌ 状态机持久化(Goal/Task/Plan 的 enum 转换目前只在内存中)
- ❌ 快照与检查点(无 rewind/journal/inflight snapshot)
- ❌ 事件溯源 + 投影
- ❌ 缓存与持久化一致性层
- ❌ 进程间锁(目前仅进程内 Mutex)
- ❌ 损坏检测 / 撕裂修复
- ❌ 崩溃恢复(SQLite 默认无 WAL,无 backup)

> **结论**:laew 是「能跑」的持久化底座,缺少「能恢复」「能演进」「能扩展」「能观测」四件套。本轮 8 个外部仓库恰好各自覆盖了不同缺口。

## 2. atomcode — Rust 单一 JSON 线格式 + 5 版本常量 + WAL 风格重做日志

> **仓库路径**:`/usr/local/LsmGitOpenSource/atomcode`
> **核心架构**:Rust workspace 14 crates,7055 行 SessionManager,5966 行 Agent kernel
> **序列化基线**:**100% JSON,零二进制 codec**(无 bincode/prost/CBOR/MessagePack/postcard/rkyv)
> **恢复路径**:**RewindTransactionJournal = 真正的 WAL**,写在 worktree 修改之前
> **完整分析**:`/tmp/atomcode_persistence_analysis.md`(约 600 行)

### 2.1 序列化框架(3/5)

#### 2.1.1 Crate 清单(单一线格式策略)

| Crate | 用途 |
|-------|------|
| `serde` | 所有 14 crates 的基础 |
| `serde_json` | **唯一**的持久化线格式 |
| `toml` + `toml_edit` | 配置文件(后者支持格式保留编辑) |
| `chrono` (serde feature) | 时间戳 |
| `sha2` | 内容指纹(`signals_hash` / `source_sha256`) |
| `fs2` | 操作系统级 advisory file lock |
| `libc` | `O_NOFOLLOW` 等 syscall |

**关键决策**:**故意放弃二进制 codec**,理由:
- ✅ 人类可调试(`cat .snapshot | jq` 即可)
- ✅ 单一工具链,无需测试 5 种 codec 的边角
- ❌ 体积代价:snapshot 上限 64 MiB,meta 上限 4 MiB(`MAX_*_BYTES`)

#### 2.1.2 Wire 格式(完全 JSON)

### 2.2 状态机持久化(4/5)

#### 2.2.1 多状态机并存

| 状态机 | 文件 | 状态枚举 | 持久化路径 |
|--------|------|---------|-----------|
| **Goal** | `coding/src/controllers.rs` | `GoalPhase { Pending, Running, Completed, Failed }` | **未持久化**(纯内存,进程退出即失) |
| **Runtime** | `coding/src/runtime.rs` | `RuntimePhase { Idle, Busy, Compacting, ... }` | **未持久化**(纯内存) |
| **Message role** | `message.rs:74-78` | `Role { System, User, Assistant, Tool }` | 通过 `Message` enum tag 序列化到 snapshot |
| **Session status** | `manager.rs:4000+` | 内置 `StorageError` 家族,无显式 status 字段 | n/a |

#### 2.2.2 状态转换与持久化的解耦

```rust
// 目标状态机(coding 层)未持久化:
pub enum GoalPhase { Pending, Running, Completed, Failed }
// → 仅由 GoalController 在内存中推进,从不写盘

// 消息角色状态机(kernel 层)持久化:
pub enum Role { System, User, Assistant, Tool }
// → 序列化为字符串字面量,反向时从字符串恢复
```

**观察**:atomcode **故意**不持久化「任务层」状态机(Goal/Runtime),只持久化「数据层」(Message/Metadata/Snapshot)。理由:Goal/Task 状态变化太快,持久化代价 > 收益,崩溃后从「对话历史 + checkpointer」重放更准确。

### 2.3 快照与检查点(4/5)

#### 2.3.1 双层快照:SessionSnapshot + InflightSnapshot

```rust
// crates/atomcode-capabilities/src/session/manager.rs:567-620
pub struct InflightSnapshot {
    pub version: u32,   // INFLIGHT_SNAPSHOT_VERSION
    pub session_id: SessionId,
    pub target_snapshot: Arc<SessionSnapshot>,   // 写前的稳定快照
    pub started_at: SystemTime,
    pub owner: String,
}
```

**核心**:**InflightSnapshot = 崩溃恢复哨兵**。任何写操作开始前先落盘,完成后立即删除(详见 §2.10)。

#### 2.3.2 WorkspaceCheckpoint(per-session git dir)

每个 session 分配独立的 `.git` 目录,用真实 Git 对象保存 worktree 状态(非 JSON)。**这是唯一一个二进制层**,但被外部化(依赖 Git 工具)。

### 2.4 事件溯源(1/5,故意不做)

**没有 event sourcing**。最近的等价物是 `RewindTransactionJournal`(详见 §2.10),但它是「WAL」(write-ahead log)而不是「event log」—— 记录的是「为了撤销工作树需要做什么」,不是「发生了什么」。

**设计权衡**:Agent 的事件流(用户消息 + 助手消息 + tool 调用)直接落在 `SessionSnapshot` 里,反序列化即回放;不需要单独的事件存储。

### 2.5 事务与一致性(5/5,**最强维度**)

#### 2.5.1 进程内互斥:`fs2` advisory lock + 进程内 Mutex

```rust
// crates/atomcode-capabilities/src/session/manager.rs:2508
pub fn commit_native_runtime_mutation(
    &self, session_id: SessionId, mutation: RuntimeMutation
) -> Result<RuntimeMutationOutcome, StorageError>
{
    // 1. 序列化 out of lock(避免死锁)
    let mutation_serialized = serialize_bounded(&mutation)?;
    // 2. 获取跨进程 advisory lock(10s 截止)
    let lock = self.open_lease(session_id, Duration::from_secs(10))?;
    // 3. 读所有 3 个 artifact + 原始 before bytes
    let before = self.read_full_state_unlocked(session_id)?;
    // 4. 调用方变更(用 mutation_serialized)
    let after = apply_mutation(&before, mutation_serialized)?;
    // 5. diff-only 写入
    let outcome = self.diff_write_unlocked(session_id, before, after)?;
    // 6. 多文件 replace with rollback
    self.commit_diff_with_rollback(outcome)?;
    Ok(outcome)
}
```

#### 2.5.2 `AtomicWriteFailure` — 失败分类的艺术

```rust
// crates/atomcode-capabilities/src/session/manager.rs:4075
pub struct AtomicWriteFailure {
    pub error: io::Error,
    pub mutated: bool,   // 关键标志!
}
```

- `mutated=false`:**rename 之前**失败 → 目标文件未触动,可重试,无需回滚
- `mutated=true`:**rename 之后**失败 → 必须回滚到快照

**多文件回滚顺序**:catalog-visible meta 最后回滚(因为它是 catalog 的索引,先回滚它会让其他 meta 引用到「不存在的」会话)。

#### 2.5.3 `commit_native_import_if_unchanged`(CAS 原语)

```rust
// crates/atomcode-capabilities/src/session/manager.rs:2081

    // 读 source_sha256 → 与 expected_sha256 比较 → CAS
```

**这是 laew 缺失的 CAS 原语**:laew 目前只能 `INSERT` / `UPDATE`,无法「如果文件没变就提交」。

### 2.6 存储引擎(2/5)

#### 2.6.1 物理布局

```
$ROOT/.atomcode/
├── <session-id>/
│   ├── <id>.meta            // SessionMeta(v=1)
│   ├── <id>.snapshot        // SessionSnapshot(v=1)
│   ├── <id>.inflight        // InflightSnapshot(v=1, 崩溃哨兵)
│   ├── <id>.rewind-ledger   // RewindLedger(v=1..=2)
│   ├── <id>.journal         // RewindTransactionJournal(v=1)
│   └── worktree/            // 独立 .git 目录
└── catalog.json             // 全局索引
```

#### 2.6.2 存储抽象

**几乎没有抽象层** —— 直接读写文件。这在 Rust 14-crate workspace 中是劣势(无法换后端),但是优势是性能可预测 + 调试容易。

### 2.7 缓存与持久化一致性(3/5)

#### 2.7.1 `cache_epoch: u64` 在 Conversation 上

### 2.8 数据版本管理(4/5)

#### 2.8.1 版本常量 vs 迁移 runner

atomcode 用 **5 个独立版本常量** + `#[serde(default)]` 标注 + 「reject-future-only」策略,**没有传统的 migration runner**。

```rust
// reader 端:
if meta.version > META_VERSION {
    return Err(StorageError::FutureSchema { found: meta.version, supported: META_VERSION });
}
// 不需要「schema 4 → 5 迁移代码」,因为 #[serde(default)] 已经搞定
```

**优势**:零停机升级、零迁移代码、零迁移测试。
**劣势**:无法做「数据 shape 大改」(如 rename 字段)。

### 2.9 并发持久化(4/5)

#### 2.9.1 三层锁

```
┌────────────────────────────────────────┐
│ Layer 3: 进程内 Mutex<SessionManager>  │  内存缓存
├────────────────────────────────────────┤
│ Layer 2: fs2 advisory file lock        │  跨进程互斥(同 session)
├────────────────────────────────────────┤
│ Layer 1: O_EXCL create(.inflight)      │  崩溃检测
└────────────────────────────────────────┘
```

#### 2.9.2 `proper-lockfile` 替代品:fs2 advisory lock

Rust 没有 npm 的 `proper-lockfile`,但 `fs2` crate 提供等价功能。

### 2.10 恢复与容错(5/5,**最强维度**)

#### 2.10.1 启动时的恢复流程

```
1. 读 catalog.json → 拿到所有 session 路径
2. 对每个 session:
   a. 读 <id>.meta → 拿到快照指针
   b. 读 <id>.snapshot → 主数据
   c. 读 <id>.inflight? → 若存在 → 崩溃未完成!
      → 读取 <id>.journal → 逐条 reverse 操作
      → 删除 .inflight
   d. 读 <id>.rewind-ledger → 验证 checkpoint 一致性
3. 对每个 session 的 worktree/.git:
   git fsck + git reflog
```

#### 2.10.2 WAL:RewindTransactionJournal

```rust
// crates/atomcode-capabilities/src/session/rewind.rs:151-220
pub struct RewindTransactionJournal {
    pub version: u32,  // TRANSACTION_VERSION = 1
    pub entries: Vec<JournalEntry>,
    pub session_id: SessionId,
    pub started_at: SystemTime,
}

pub enum JournalEntry {
    CreateFile { path: PathBuf, content: Vec<u8> },
    ModifyFile { path: PathBuf, before_hash: Sha256, after_hash: Sha256 },
    DeleteFile { path: PathBuf, content_before: Vec<u8> },
```

```rust
    let tmp = path.with_extension(format!("tmp.{}.{}", pid, now()));
    {
        let mut f = File::create(&tmp)?;
        f.write_all(data)?;
        f.sync_all()?;  // fsync data
```

## 11. 结语

### 10.1 关键洞察

1. **持久化复杂度 vs Agent 复杂度强相关**:Agent 越复杂(多 Agent + SubAgent Registry + Durable Object),持久化越完整(deepseek-harness 4.9/5);Agent 越轻量(claudecode 单进程 LLM CLI),持久化越弱(2.5/5)。

2. **「事件溯源」是 max 维度的天花板**:deepseek-harness 是唯一完整实现 event sourcing 的项目,直接拉高总分到 4.9。其他项目(JSONL 文件 + 双总线)严格来说是「消息日志 + 推模式」,**不是事件源**。

3. **「fail-closed vs fail-open」是持久化哲学分水岭**:
   - **fail-closed**(deepseek-harness):torn-tail → 抛错,不静默截断
   - **fail-open**(atomcode):部分丢失 → 继续运行,记录到 telemetry
   - laew 当前是「fail-silent」(没检测)

4. **「Schema 演进」两条路线**:
   - **版本常量 + `#[serde(default)]`**(atomcode):零迁移代码,接受 v <= MY_VERSION
   - **migrationVersion + 内联函数**(claudecode):每版本一个函数,显式演化
   - **双管齐下**(deepseek-harness):5 个独立命名空间 + migrate-on-continue

5. **「存储引擎」有「直接 IO vs 抽象」权衡**:
   - atomcode 直接文件 IO(2/5)→ 性能可预测但难换后端
   - deepseek-harness `Storage<K, V>` 抽象(5/5)→ 双后端(JSFS+SQLite)
   - laew 直接用 rusqlite(2/5)→ 同 atomcode,但单线程没利用 WAL

### 10.2 laew 改造优先级

- **立即**(本周):PRAGMA WAL + fs2 advisory lock + atomic_write + schema_version 字段
