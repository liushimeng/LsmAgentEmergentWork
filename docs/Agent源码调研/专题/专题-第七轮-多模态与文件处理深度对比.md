# 专题-第七轮-多模态与文件处理深度对比

> 横向深度对比 claudecode / opencode / openclaw / pi / atomcode / deepseek-harness 的多模态与文件处理全链路
> 输入模态矩阵 · 图片 resize/编码/传输 · PDF 抽取/分页 · Notebook · 大文件兜底 · 产物下载 · 成本/缓存 · 安全
> 同步给出 laew 现状诊断 + P0/P1/P2 路线图（含 Rust `infer`/`image`/`base64` crate 改造方案 + ContentBlock 枚举设计）

---

## ① 结论速览

1. **图片处理已收敛为四步流水线**：magic number 探测 → resize（按 client / provider / per-side / total-pixel budget 四类策略）→ base64 编码 → content block 组装。各项目只有侧重点不同，没有本质架构差异。
2. **客户端默认上限普遍是 2000×2000px / 5MB base64**，但 deepseek-harness 走的是 `total-pixel budget 2048×2048 + long-edge 8192 + 4MiB encoded bytes` 的"总像素预算 + 长边 cap"双因子模型，与 Anthropic/OpenAI 的"边长 cap"模型有结构性差异。
3. **图片 token 计算没有人做**——所有项目都依赖上游 SSE chunk 的 usage 字段做精确计费；客户端只做 size-budget 兜底，不估算 token。
4. **PDF 处理是分化的最大点**：claudecode 出 pdftoppm（poppler）+ 走 base64 document block 双路径（3MB 阈值），其他五家要么只走 model-native PDF block（opencode/openclaw/anthropic provider），要么纯文本 fallback（pi/atomcode）。**没有任何项目做 PDF→image 后的 token 估算**。
5. **只有 claudecode 支持 Notebook（.ipynb）**：6 阶段处理（cells map → source 拼合 → outputs 10000 字符阈值截断 → 图片 base64 → cell 输出 XML 化 → tool_result 回填），其他五家完全缺失。
6. **大文件兜底策略分裂为两派**：claudecode `maxSizeBytes=256KB 预检 → maxTokens=25000 后置 token 校验 + offset/limit 流式分块`；pi/claudecode/atomcode 走"先给前 N 行 + 提示继续读"；openclaw 走 chat-mode 提示压缩。
7. **重复图片去重**：deepseek-harness 在 attachment 层做了"同图片只存一次 + request variant 派生缓存 + singleflight"；其他项目完全没做，每次 read 都重新编码 base64。
8. **安全**：claudecode/pi/atomcode 做 magic number 探测 + 扩展名兜底；pi 还做了 EXIF orientation 应用；deepseek-harness 走 8-bit sRGB 强校验；**没有任何项目实现"图片内容里的 prompt injection"主动检测**——都依赖上游模型自身防御。
9. **laew 现状**：Read 工具仅支持纯文本（`MAX_LIMIT=4000` + 单行 4000 字符截断 + utf-8 全量读），完全无图片 / PDF / Notebook / 编码探测 / mime 分流；ContentBlock 枚举只有 Text / ToolUse / ToolResult 三变体，扩展多模态需先扩枚举。
10. **P0 路线**：(a) ContentBlock 扩 `Image { media_type, base64_data }` + `Document { media_type, base64_data }` 两变体；(b) Read 工具按扩展名与 magic number 探测分流文本 / 图片 / PDF；(c) 引入 `infer` + `image` + `base64` crate；(d) 复用 claudecode 2000×2000 + 5MB base64 默认值。

## ② 逐项目剖析

### 2.1 claudecode — 全功能多模态基线

claudecode 是六家项目中**唯一支持 Notebook + PDF 抽取 + 截图粘贴 + 图片自动 resize + token-based compression** 的完整实现。其设计围绕 Anthropic API 硬限制（5MB base64 + 100 页 PDF）展开。

**核心常量（`src/constants/apiLimits.ts`）：**

```typescript
// 第 22-43 行
export const API_IMAGE_MAX_BASE64_SIZE = 5 * 1024 * 1024  // 5 MB
export const IMAGE_TARGET_RAW_SIZE = (API_IMAGE_MAX_BASE64_SIZE * 3) / 4  // 3.75 MB
export const IMAGE_MAX_WIDTH = 2000
export const IMAGE_MAX_HEIGHT = 2000

// 第 54-83 行
export const PDF_TARGET_RAW_SIZE = 20 * 1024 * 1024  // 20 MB
export const API_PDF_MAX_PAGES = 100
export const PDF_EXTRACT_SIZE_THRESHOLD = 3 * 1024 * 1024  // 3 MB
export const PDF_MAX_EXTRACT_SIZE = 100 * 1024 * 1024  // 100 MB
export const PDF_MAX_PAGES_PER_READ = 20
export const API_MAX_MEDIA_PER_REQUEST = 100  // 单请求最多 100 个图片/PDF
```

**图片 resize 流水线（`src/utils/imageResizer.ts`）：**

四阶段渐进式压缩，每阶段失败再降级：

| 阶段 | 策略 | 限制 |
|------|------|------|
| 1 | sharp().resize(2000,2000).png({compressionLevel:9, palette:true}) | 保真保透明 |
| 2 | sharp().resize().jpeg({quality: 80}) 循环 [80, 60, 40, 20] | 渐进降质 |
| 3 | 1000px 长边 + jpeg q=20 | 兜底缩到 1000 |
| 4 | magic byte 兜底（PNG/JPEG/GIF/WebP） | 不 resize 走原始 |

源码 256-274 行注释明确说"每次压缩必须新建 sharp 实例（`sharp(imageBuffer)`），复用会因 native 内存模型 bug 返回相同 size"。这是 vips/libvips 与 napi-rs 边界的真实坑。

**magic byte 探测（769-812 行）**：

```typescript
export function detectImageFormatFromBuffer(buffer: Buffer): ImageMediaType {
  if (buffer.length < 4) return 'image/png'  // 兜底
  // PNG: 89 50 4E 47
  if (buffer[0] === 0x89 && buffer[1] === 0x50 && buffer[2] === 0x4E && buffer[3] === 0x47) return 'image/png'
  // JPEG: FF D8 FF
  if (buffer[0] === 0xff && buffer[1] === 0xd8 && buffer[2] === 0xff) return 'image/jpeg'
  // GIF: GIF87a/GIF89a
  if (buffer[0] === 0x47 && buffer[1] === 0x49 && buffer[2] === 0x46) return 'image/gif'
  // WebP: RIFF....WEBP
  if (buffer[0] === 0x52 && buffer[1] === 0x49 && buffer[2] === 0x46 && buffer[3] === 0x46 && ...) return 'image/webp'
  return 'image/png'
}
```

**PDF 处理双路径（`src/utils/pdf.ts`）：**

- **路径 A**：PDF ≤ 3MB → 走 Anthropic native document block（`type:'document', source:{type:'base64', media_type:'application/pdf', data}`），单 base64 字段注入 user message
- **路径 B**：PDF > 3MB → `pdftoppm -jpeg -r 100`（poppler-utils）逐页转 JPEG 到 `${getToolResultsDir()}/pdf-${uuid}/page-NN.jpg`，每个 JPEG 独立过 resize 流水线后作为 image block 上传
- 页数限制 100（API 硬限），单 read 调用最多 20 页（PDF_MAX_PAGES_PER_READ）
- 大小校验：PDF 抽图路径 ≤ 100MB；走 base64 路径 ≤ 20MB（`PDF_TARGET_RAW_SIZE`）

**Notebook 处理（`src/utils/notebook.ts`）：**

**Read 工具双层 cap（`src/tools/FileReadTool/limits.ts`）：**

| cap | 默认 | 检查时机 | 触发动作 |
|-----|------|----------|----------|

`readFileInRange.ts` 实现的是双码路径：< 10MB 走 `readFile()` + 内存 split；≥ 10MB 走 `createReadStream()` + 流式 line counter（不缓存 selected range 外的行，避免 100GB 单文件 OOM）。

**截图粘贴（`src/utils/screenshotClipboard.ts`）**：macOS 走 `screencapture -selection clipboard -t image/png -i`；Linux 走 `xclip --clipboard --input --type image/png`。

**Base64→byte size 反算（`imageResizer.ts:399`）：** `base64Size = ceil((originalSize * 4) / 3)`。**注意**：这是基于 base64 字符串字节数，不是解码后字节数；常用于 PNG 文件头 24 字节内读取 IHDR 宽高（`imageResizer.ts:404-411`）做"不过 sharp 也校验 pixel 维度"的快速失败路径。

### 2.2 opencode — Effect/Schema 全栈 DI 模式

opencode 的图片处理与 claudecode 形态最接近，但走 Effect + Layer + Service 三层 DI（`packages/opencode/src/image/image.ts`）。

**核心常量（`image.ts:10-14`）：**

```typescript
const MAX_BASE64_BYTES = 5 * 1024 * 1024
const MAX_WIDTH = 2000
const MAX_HEIGHT = 2000
const AUTO_RESIZE = true
const JPEG_QUALITIES = [80, 85, 70, 55, 40]
```

**resize 策略（`image.ts:75-164`）**：

```typescript
// 第 112-125 行：渐进式 0.75 缩放序列（最大 32 步），直到 1×1
const scale = Math.min(1, info.maxWidth / originalWidth, info.maxHeight / originalHeight)
for (const size of Array.from({length: 32}).reduce<...>(...)) {
  const resized = photon.resize(decoded, size.width, size.height, photon.SamplingFilter.Lanczos3)
  // 同时尝试 PNG（无损）+ 5 档 JPEG（80/85/70/55/40），找第一个 ≤ maxBytes 的
  const candidate = [{data: PNG, mime:'image/png'}, ...JPEG_QUALITIES.map(...)]
    .map(...).find((item) => item.bytes <= info.maxBase64Bytes)
  if (candidate) return ...
}
```

**关键设计**：
1. 用 `photon-node`（Rust→WASM）而非 sharp，**冷启动更小但无 sharp 的 libvips 系统库依赖**；`loadPhoton` 用 `Effect.cached` 保证一次加载。
2. PNG 无损 + JPEG 有损同时生成，**直接挑字节数小的**——claudecode 是分阶段先 PNG 再 JPEG，opencode 是同时比较。
3. 错误用 Schema.TaggedErrorClass 分四类（`ResizerUnavailableError` / `InvalidDataUrlError` / `DecodeError` / `SizeError`），**完全排除类**，符合 Effect 的 fail-fast 哲学。

**媒体嗅探（`util/media.ts:15-26`）**：

```typescript
export function sniffAttachmentMime(bytes: Uint8Array, fallback: string) {
  if (startsWith(bytes, [0x89,0x50,0x4E,0x47,0x0D,0x0A,0x1A,0x0A])) return "image/png"
  if (startsWith(bytes, [0xFF,0xD8,0xFF])) return "image/jpeg"
  if (startsWith(bytes, [0x47,0x49,0x46,0x38])) return "image/gif"
  if (startsWith(bytes, [0x42,0x4D])) return "image/bmp"
  if (startsWith(bytes, [0x25,0x50,0x44,0x46,0x2D])) return "application/pdf"
  if (startsWith(bytes, [0x52,0x49,0x46,0x46]) && startsWith(bytes.subarray(8), [0x57,0x45,0x42,0x50])) return "image/webp"
  return fallback
}
```

**Cap 协商（`provider.ts:709-718, 1293-1302`）**：每个 model 注册 capabilities 时携带 `input.image` / `input.pdf` 布尔，由 `model.modalities?.input?.includes("image")` 派生。`transform.ts:409-444` 实现 `unsupportedParts`：模型不支持该 modality 时**用 ERROR 文本占位**而非静默丢弃。

**tool-result 媒介提取（`message-v2.ts:131-193`）**：当 `@ai-sdk/openai` 等不支持 tool result 内嵌媒介的 provider 时，把 tool output.attachments 提取成 user message 的 media parts——**这是协议层面的 workaround**，claudecode 没有这个问题（Anthropic SDK 原生支持 tool result 嵌入 image）。

**PDF 处理**：opencode 没有 PDF 抽取（pdftotext / pdftoppm）工具，**完全依赖 provider 模型声明的 `input.pdf` 能力**。GitHub Copilot 等模型不声明 PDF → 一律拒绝。

### 2.4 pi — Photon Worker + compact 资源分类

pi 的 read 工具形态最简朴（`packages/coding-agent/src/core/tools/read.ts`），但有两点独特设计：

**1. Worker 隔离 + Bun fallback（`utils/image-resize.ts:85-110`）：**

```typescript
export async function resizeImage(inputBytes, mimeType, options?) {
  const isTypeScriptRuntime = import.meta.url.endsWith('.ts')
  const workerUrl = new URL(isTypeScriptRuntime ? './image-resize-worker.ts' : './image-resize-worker.js', import.meta.url)
  // Bun 二进制用 string path 走 embedded worker
  if (typeof process.versions.bun === 'string') {
    try { return await resizeImageInWorker('./src/utils/image-resize-worker.ts', ...); } catch {}
  }
  try { return await resizeImageInWorker(workerUrl, ...); }
  catch { return resizeImageInProcess(inputBytes, mimeType, options); }  // 兜底
}
```

设计目的：**防止 WASM 解码阻塞 TUI 事件循环**；兜底链路保证 Bun 编译产物路径失效时仍可用。

**2. resize 算法（`image-resize-core.ts:122-154`）：**

```typescript
const qualitySteps = Array.from(new Set([opts.jpegQuality, 85, 70, 55, 40]));
let currentWidth = targetWidth;
let currentHeight = targetHeight;
while (true) {
  const candidates = tryEncodings(currentWidth, currentHeight, qualitySteps);  // 同时生成 PNG + JPEG 5 档
  for (const candidate of candidates) {
    if (candidate.encodedSize < opts.maxBytes) return ...
  }
  // 维度按 0.75 缩放（log₄(5)≈1.16 步搞定 5MB → <4.5MB），直到 1×1
  if (currentWidth === 1 && currentHeight === 1) break;
  const nextWidth = Math.max(1, Math.floor(currentWidth * 0.75));
  const nextHeight = Math.max(1, Math.floor(currentHeight * 0.75));
  currentWidth = nextWidth; currentHeight = nextHeight;
}
return null;  // 兜底：1×1 都放不下 → 整体放弃（不让无效图片进入上下文）
```

**默认 4.5MB base64（`image-resize-core.ts:22`）**：比 claudecode 5MB 更保守，留 0.5MB headroom 防止 Anthropic 服务端边界判定差异。

**3. EXIF Orientation 应用（`utils/exif-orientation.ts`）**：手机拍的照片旋转 metadata 必须在 client 端读出来应用，否则模型看到的图是横着的。**opencode 没做这一步**，是真实坑（用户上传 HEIC 转 JPEG 后没旋转）。

**4. magic byte 探测（`utils/mime.ts:6-23`）：**

```typescript
export function detectSupportedImageMimeType(buffer: Uint8Array): string | null {
  if (startsWith(buffer, [0xff, 0xd8, 0xff])) return buffer[3] === 0xf7 ? null : 'image/jpeg';
  // 注：SOF0xa0（baseline）vs SOF0xa1（extended）等；buffer[3]===0xf7 排除 SOF
  if (startsWith(buffer, PNG_SIGNATURE)) return isPng(buffer) && !isAnimatedPng(buffer) ? 'image/png' : null;
  // 显式排除 APNG（扫描 acTL chunk）
  if (startsWithAscii(buffer, 0, 'GIF')) return 'image/gif';
  if (startsWithAscii(buffer, 0, 'RIFF') && startsWithAscii(buffer, 8, 'WEBP')) return 'image/webp';
  if (startsWithAscii(buffer, 0, 'BM') && isBmp(buffer)) return 'image/bmp';
  return null;  // 不支持的格式 → 文本读
}
```

这是六家中**唯一主动拒绝 BMP/animated PNG** 的——BMP 因为 model 不接受（claudecode 也拒绝）；APNG 同样如此。

**5. compact 资源分类（`read.ts:123-144`）：**

### 2.5 atomcode — Kernel-native VL 预处理 + 简化版图片路径

atomcode 的设计哲学与上面四家 TS/JS 项目**根本不同**——它把"图片处理"拆成**两段**：

**1. 客户端路径（`crates/atomcode-capabilities/src/tools/read.rs`）：**

```rust

    let ext = path.extension()?.to_str()?.to_ascii_lowercase();

        "jpg" | "jpeg" => "image/jpeg",
        "png" => "image/png",
        "gif" => "image/gif",
        "webp" => "image/webp",
        _ => return None,
```

**关键观察**：
- **不做 resize**，只做 4MB 上限硬卡 + 扩展名识别 + base64。

- 注释（read.rs:165-167）说明"每张图 ~1600 tokens"——这是 Anthropic 文档披露的近似值，不是实测。

```rust
         报错截图或终端输出，请逐字转录文本。",
    );
    let messages = vec![Message::user_with_images(prompt, images.to_vec())];
    // ... 流式累积，30s idle-timeout 而非 wall-clock（防止健康慢网关被误杀）
}
```

**设计精髓**：当主模型是 text-only（如 Sonnet 但用户开 vision 模式走别的 provider）时，把图片先发给一个**VL 专用模型**（如 Qwen-VL）做 OCR → 把 OCR 文本折进 user message、丢弃图片。**这是预算受限的聪明解**——让所有模型都能用 vision 图片，但需要额外的 VL 成本。

**3. 文本兜底（`read.rs:526-565`）：PDF/docx 等二进制不直接读取，提示用 `pdftotext` / `pandoc` / `unzip`：**

```rust

     ..."
),
```

**4. 编码兜底（`tools/encoding.rs`）：UTF-8 失败时降级到 GB18030**——专为中国 Windows 编辑器写 GBK 编码的 .txt/.csv 场景；这是其他五家都没做的（claudecode/opencode 都假定 UTF-8 + latin1）。

### 2.6 deepseek-harness — 长链路 attachment 持久化

deepseek-harness 的 attachment 系统是六家中**唯一把图片作为一等公民持久化**的。

**核心常量（`packages/attachment/attachment-local/src/index.ts:28-52`）：**

```typescript
export const DEFAULT_MAX_IMAGE_BYTES = 20 * 1024 * 1024         // 接受源 ≤ 20MiB
export const DEFAULT_MAX_IMAGES_PER_MESSAGE = 20                // 单消息 ≤ 20 张
export const DEFAULT_MAX_IMAGE_PIXELS = 64_000_000              // 64M pixels（像素总数）
export const DEFAULT_MAX_IMAGE_DIMENSION = 8192                  // 长边 ≤ 8192
export const DEFAULT_NORMALIZED_IMAGE_MAX_PIXELS = 2048 * 2048  // 标准化后 ≤ 4M pixels
export const DEFAULT_NORMALIZED_IMAGE_MAX_DIMENSION = 8192
export const DEFAULT_NORMALIZED_IMAGE_MAX_BYTES = 4 * 1024 * 1024  // 4MiB encoded
export const MAX_IMAGE_COMPRESSION_CONCURRENCY = 8               // FIFO 并发
```

**两阶段处理（`normalization.ts`）：**

1. **Stage 1: 持久化归一化**（provider-independent）—— 接受任意合法源，强制 8-bit sRGB/sRGBA、剥 EXIF metadata、按 total-pixel budget 缩放、存到 `${DSH_HOME}/attachments/v1`。
2. **Stage 2: 请求变换**（provider-specific）—— 按 route 的 pixel budget 再缩放，再走 alpha-routed encoding（alpha 走 WebP，opaque 走 JPEG，质量阶梯 85/75/60）。

**Pass-through 快路径（`normalization.ts:35-48`）：**

```typescript
export function canPassThroughNormalization(detected, bytes, policy): boolean {
  return detected.mediaType !== 'image/gif'
    && !detected.animated
    && !detected.carriesMetadata
    && detected.depth === 'uchar'
    && detected.space === 'srgb'
    && bytes <= policy.maxBytes
    && detected.width * detected.height <= policy.maxPixels
    && Math.max(detected.width, detected.height) <= policy.maxDimension
}
```

**幂等 + 跨重启**：归一化后图片字节相同则 SHA-256 deduplication——同图多次 attach 不重复存储。

**单飞（singleflight）**：`request-image.ts` 描述"并发调用方共享一次变换与缓存写入"，避免冷启高峰 race。

**base64 规范化（`attachment/src/admission.ts:9-15`）：**

```typescript
function decodeBase64(data: string): Uint8Array {
  const decoded = Buffer.from(data, 'base64');
  // 关键：round-trip 校验 — 编码回去必须等于原串，否则视为非 canonical 拒收
  if (data.length === 0 || decoded.toString('base64') !== data) {
    throw new AttachmentError('Image upload is not canonical base64.', 'INVALID_IMAGE_BASE64');
  }
  return new Uint8Array(decoded);
}
```

这是六家中**唯一校验 base64 canonical 形式**的——杜绝 padding 错位或换行污染。

## ⑥ 设计模式与反模式（13 项）

### 模式 1：Magic byte 探测优先于扩展名（6/6）
所有项目都做 magic byte 探测。claudecode 注释（`apiLimits.ts:73-86`）强调"扩展名错的 PDF 一旦进入 message history 会让整个 session 不可恢复"——这是六家共识。

### 模式 2：resize 失败兜底而非直接报错
claudecode（`imageResizer.ts:383-432`）和 pi（`image-resize-core.ts:157-158`）都在 sharp/photon 失败时返回空而非抛错，提示用户手动处理。**反例**：opencode 一旦 Photon 不可用就 `ResizerUnavailableError`，对用户不友好。

### 模式 3：base64 size 反算 + size+dim 双卡
claudecode（`imageResizer.ts:399`）`base64Size = ceil((rawSize * 4) / 3)`；pi（`image-resize-core.ts:65`）`Math.ceil(inputBytes.byteLength / 3) * 4`（等价但表达不同）。**反例**：atomcode/cardinal 用 raw size 但 model 限制是 base64，会有 4MB raw → 5.3MB base64 的硬卡失败。

### 模式 4：Worker 隔离 resize
pi（`image-resize.ts`）用 `worker_threads` 隔离 Photon 解码——避免阻塞 TUI 16ms 帧率。claudecode 不做（依赖 Bun 同步调用），是真实坑。

### 模式 5：Total-pixel budget + long-edge cap 双因子
deepseek-harness（`normalization.ts:81-90`）：先按 `total_pixels` 缩放，再按 `max(d.w, d.h)` 二次缩放，保证极端宽高比（横幅 / 垂直截图）不丢失短边分辨率。这是真正的工程最优解——claudecode 2000×2000 单边卡对 10000×100 横幅会硬伤。

### 模式 6：Pass-through 字节等同
deepseek-harness（`normalization.ts:35-48`）和 claudecode（`imageResizer.ts:212-227`）都在文件已是 8-bit sRGB 且尺寸合规时**原样返回**，避免无谓重编码（PNG 重编码会引入 palette 损失）。

### 模式 7：alpha 路由 + 多格式候选
deepseek-harness（README:79）"alpha 走 WebP、opaque 走 JPEG"——按 alpha 选编码器减少文件大小。claudecode / pi 同时生成 PNG + JPEG 5 档，挑字节最小的（更通用但更慢）。

### 模式 8：持久化去重（仅 deepseek-harness）
SHA-256 dedup + request variant 缓存 + singleflight——其他项目每次 read 都重新编码 base64，浪费 CPU。

### 模式 9：行号格式化（claudecode `cat -n` 风格）
claudecode 文件读出带 `     1\t...` 行号；laew 已抄（read.rs:99）。**但 claudecode 用 width 自适应**，laew 也是（`let width = (total.max(1)).to_string().len()`）——共同模式。

### 模式 10：大文件 256KB + 25K tokens 双 cap
claudecode（`limits.ts:18-92`）预检 size + 后校 token；这是考虑 memory pressure + API cost 的最优组合。**反例**：pi 只卡 50KB+2000 行，对超大单文件（如 100GB 日志）会 OOM（实际由 createReadStream 救了）。

### 模式 11：base64 canonical 校验（仅 deepseek-harness）
`admission.ts:11-13` round-trip 校验——杜绝 padding / 换行污染。**反例**：其他项目直接 `Buffer.from(b64, 'base64')`，容忍任意脏 base64。

### 模式 12：VL 模型预处理（仅 atomcode）
当主模型不支持 vision 时，先用 VL 专用模型 OCR 转文字——保证 text-only 模型也能用 vision。代价：额外 30s 延迟 + VL 模型成本。**反模式警示**：claudecode 没做这一步，依赖上游模型声明。

### 模式 13：流式 read + 选区外不缓存（claudecode `readFileInRange.ts:281-303`）
100GB 单文件读 line 1 不会 OOM——选区外的行只 count 不 cache。

### 反模式 1：BMP 进入 vision wire（atomcode 主动排除）
claudecode `imageResizer.ts:769-812` 也排除 BMP。注释（read.rs:175-177）解释 BMP 不被 OpenAI / Anthropic wire 接受。

### 反模式 2：依赖扩展名（pi `mime.ts:6` 注释明示）
"magic byte 探测优先"是六家共识；任何依赖扩展名的 magic byte 跳过都是埋雷。

### 反模式 3：tool_result 内嵌 image 不检查 SDK 支持（claudecode 隐式接受）
opencode（`message-v2.ts:147-159`）显式判断 `supportsMediaInToolResult`，按 `@ai-sdk/{provider}` 区分。claudecode 信任 Anthropic SDK，但 OpenAI 路径会失败。

### 反模式 4：无 prompt injection 检测
六家都依赖上游模型防御，没有 client 侧的图片→文本 OCR → injection pattern match。**这是 2026 年的真实威胁**（"图里塞了 `Ignore previous instructions...`"）。

### 反模式 5：resize 失败后默默使用原图
claudecode（`imageResizer.ts:414-421`）`base64Size <= API_IMAGE_MAX_BASE64_SIZE && !overDim` 时返回原图——但**没记入 telemetry** 用户看不到 resize 失败原因。opencode 用结构化 Schema.TaggedErrorClass 强制暴露。

```rust
use infer::Infer;
use base64::Engine;
use image::{ImageReader, imageops::FilterType, ImageFormat};

const MAX_IMAGE_BASE64_BYTES: usize = 5 * 1024 * 1024;     // 5MB
const MAX_IMAGE_RAW_BYTES: usize = (MAX_IMAGE_BASE64_BYTES * 3) / 4;  // 3.75MB
const MAX_IMAGE_DIMENSION: u32 = 2000;

fn classify(path: &Path) -> Class {
    let mut buf = vec![0u8; 4100];
    let mut f = fs::File::open(path)?;
    let n = f.read(&mut buf)?;
    let kind = Infer::new().get(&buf[..n]);
    match kind {
        Some(k) if k.mime_type().starts_with("image/") => Class::Image(k.mime_type()),
        Some(k) if k.mime_type() == "application/pdf" => Class::Pdf,
        _ => Class::Text,
    }
}

async fn read_image(path: &Path) -> Result<ContentBlock> {
    let bytes = fs::read(path)?;
    if bytes.len() > MAX_IMAGE_RAW_BYTES {
        return Err(...);
    }
    // 用 image crate 解码 + resize
    let img = ImageReader::new(Cursor::new(&bytes))
        .with_guessed_format()?.decode()?;
    let resized = if img.width() > MAX_IMAGE_DIMENSION || img.height() > MAX_IMAGE_DIMENSION {
        img.resize(MAX_IMAGE_DIMENSION, MAX_IMAGE_DIMENSION, FilterType::Lanczos3)
    } else { img };
    let mut out = Vec::new();
    resized.write_to(&mut out, ImageFormat::Png)?;
    let data = base64::engine::general_purpose::STANDARD.encode(&out);
    Ok(ContentBlock::Image {
        media_type: "image/png".into(),
        data,
        source_path: Some(path.display().to_string()),
    })
}
```

```rust
            "source":{"type":"base64","media_type":media_type,"data":data}
        }),
        ContentBlock::ToolUse { id, name, input } => json!({"type":"tool_use","id":id,"name":name,"input":input}),
        ContentBlock::ToolResult { tool_use_id, content, is_error } => json!({
            "type":"tool_result","tool_use_id":tool_use_id,
            "content": content.iter().map(block_to_anthropic).collect::<Vec<_>>(),
            "is_error":is_error,
        }),
    }
}
```

**7.2.5 修改 OpenAI wire（`src/llm/openai.rs`）：**

```rust
fn block_to_openai(b: &ContentBlock) -> Value {
    match b {
        ContentBlock::Image { media_type, data, .. } => json!({
            "type":"image_url",
            "image_url":{"url":format!("data:{};base64,{}", media_type, data)}
        }),
        ContentBlock::Document { media_type, data, .. } => json!({
            "type":"file",
            "file":{"file_data":format!("data:{};base64,{}", media_type, data),
                     "filename":"document.pdf"}
        }),
        // ToolResult.content 必须是 string（OpenAI 限制）
        ContentBlock::ToolResult { tool_use_id, content, is_error } => {
            // 把 image 块序列化成 markdown 占位，避免 image 在 tool result 里
            let text: String = content.iter().map(|c| match c {
                ContentBlock::Text { text } => text.clone(),
                ContentBlock::Image { source_path, .. } =>
                    format!("[image: {}]", source_path.as_deref().unwrap_or("?")),
                _ => String::new(),
            }).collect();
            json!({"role":"tool","tool_call_id":tool_use_id,"content":text})
        }
        _ => ...
    }
}
```

### 7.3 P1 — 第二阶段（2-4 周）

1. **PDF 抽图分流**：调用 `pdftoppm`（用户装 poppler-utils）或 `pdf-extract` crate 抽文本；>3MB PDF → 逐页转 PNG → 走 image 块；≤3MB → base64 document 块。
2. **Notebook（.ipynb）基础支持**：解析 `cells[]` JSON；code cell 保留 source + outputs（image outputs 走 image 块，text outputs 截断 10000 字符）；markdown cell 保留 source。
3. **EXIF orientation**：用 `kamadak-exif` crate 读 orientation tag，旋转后再 resize。
4. **行截断优化**：从字符截断改为字节截断（`fs::read_to_string` 后用 `bytes::Bytes` 流式扫描）。

### 7.4 P2 — 第三阶段（4-8 周）

1. **持久化附件层**：参考 deepseek-harness，把图片 SHA-256 dedup 存到 `${LsmAgentEmergentWork.db}` 的 `attachments` 表，跨 Session 复用。
2. **VL 预处理路径**：配置次级 VL provider（如 Qwen-VL），text-only 主模型自动 OCR 图片降级。
3. **Prompt injection 检测**：对图片 OCR 文本做 pattern 匹配（"Ignore previous instructions"、"reveal system prompt" 等），命中则警告 + 截断。
4. **多模态 token 估算**：本地近似公式 `tokens ≈ (width × height) / 750`（Anthropic 公开公式近似），用于预算预警。
5. **tool_result 嵌入 image**：claudecode 模式，Anthropic wire 直接放 image block 进 tool_result（OpenAI 走 markdown 占位）。

### 7.5 反模式警示（必读）

1. **不要做 base64 canonical round-trip 校验**（deepseek-harness 独有，对客户端 read 路径过度严格）——客户端读的是用户文件，宽容点。
2. **不要引入 sharp 系统依赖**——laew 是 Rust，避免 libvips/libpng 系统库依赖；用纯 Rust `image` crate。
3. **不要尝试 OCR-on-read**（VL 模型）——过度工程，laew 的 SubAgent 调度更适合后台异步。
4. **不要支持 audio/video**——OpenAI audio wire (`input_audio`) 复杂度过高，2026-09 阶段放弃。
5. **不要把 image/document 序列化进历史**——大附件持久化应该是独立 attachment 表（参考 P2.1）。
