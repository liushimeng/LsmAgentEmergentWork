## 4. 推理优化

### 4.1 七工程对比表

| 工程 | 推理优化 | 实现方式 | 代码位置 |
|------|---------|---------|---------|
| **atomcode** | 透明流重连 | Ollama NDJSON 流失败时最多 3 次重开 | `ollama.rs:171-200` |
| **claude-code** | Token 精确计数 + 上下文精算 | thinking blocks 检测 + 13K buffer 断路器 | `tokenEstimation.ts` / `autoCompact.ts` |
| **deepseek-harness** | KV Cache 对齐 Compaction | 压缩指令作为最后一条 user 消息,复用 warm prefix cache | `compaction-basic/src/summarizer.ts` |
| **openclaw** | TTS 运行时回退 | 主 Provider 失败时降级到本地 sherpa-onnx-tts | `src/tts/` |
| **opencode** | Context Overflow 检测 + Tail-Preserve 压缩 | 可用上下文精算 + 保留尾部预算算法 | `overflow.ts` / `compaction.ts` |
| **pi** | 约束采样 + 重试退避 | JSON Schema Strict + Grammar + 指数退避 | `constrained-sampling.ts` / `provider-retry.ts` |
| **undici** | 无 | HTTP 客户端,不涉及推理优化 | N/A |

### 4.2 核心发现

**推理优化的两种范式**:

1. **客户端侧优化**(claude-code/opencode/pi): 不改变推理执行,而是优化推理资源利用
   - **Token 精确计数**: claude-code 通过 API 原生 countTokens 获取精确 token 数,避免字符/4 估算误差
   - **上下文窗口精算**: claude-code 的 `getEffectiveContextWindowSize()` 预留摘要输出 token(p99.99=17,387),opencode 的 `usable()` 预留 `min(20000, maxOutputTokens)`
   - **Tail-Preserve 压缩**: opencode 的 `preserveRecentBudget = min(15000, max(2000, floor(usable * 0.25)))` 保留最近 N 轮完整对话

2. **Provider 侧感知优化**(deepseek-harness): 利用 Provider 的内部特性
   - **KV Cache 对齐**: deepseek-harness 的 compaction 指令作为最后一条 user 消息,使辅助调用成为"最后路由请求的真前缀",复用 provider 的 warm prefix cache,避免重新计算

**atomcode 的透明流重连**: 虽然不是传统推理优化,但 atomcode 的 Ollama NDJSON 流重连机制(最多 3 次重开)提高了本地推理的可靠性,属于推理可用性的优化。

**openclaw 的 TTS 回退**: openclaw 在 TTS 场景实现了 Provider 回退机制,主 Provider 失败时降级到本地 sherpa-onnx-tts,这是唯一的本地推理 fallback 实现。

### 4.3 laew gap

- **L884 [P2]**: laew 无推理优化(Continuous Batching / PagedAttention / Speculative Decoding)
- **L855 [P0]**(claude-code 标注): laew 无 token 精确计数(仅字符/4 估算)

## 5. KV Cache

### 5.1 七工程对比表

| 工程 | KV Cache | 实现方式 | 代码位置 |
|------|---------|---------|---------|
| **atomcode** | 无 | 不涉及 KV Cache 管理 | N/A |
| **claude-code** | 间接利用 | Prompt Caching 通过 cache_control 断点 | 第十三轮已覆盖 |
| **deepseek-harness** | **KV Cache 对齐 Compaction** | 压缩指令作为最后一条 user 消息,复用 warm prefix cache | `compaction-basic/src/summarizer.ts:28-66` |
| **openclaw** | 间接利用 | 依赖 Provider 内部 Prompt Caching | N/A |
| **opencode** | 间接利用 | 依赖 Provider 内部 Prompt Caching | N/A |
| **pi** | 无 | 依赖 Provider 内部实现 | N/A |
| **undici** | 无 | HTTP 客户端,不涉及推理 | N/A |

### 5.2 核心发现

**deepseek-harness 的独特实现**: 在 KV Cache 维度,deepseek-harness 是唯一有明确"KV Cache 感知"设计的工程:

```typescript
// compaction-basic/src/summarizer.ts:28-66
/**
 * The summarization directive, delivered as the FINAL user message after the
 * replayed conversation rather than as a distinct summarizer system prompt.
 * Keeping the conversation's own system prompt, tools, and message prefix in
 * front of it makes the auxiliary call a genuine prefix of the last routed
 * request, so the provider's KV cache is reused instead of invalidated.
 */
```

**设计要点**:
- 压缩指令作为**最后一条 user 消息**追加,而非独立的 system prompt
- 重放原始对话的 system prompt、tools、消息前缀
- 辅助调用成为"最后路由请求的真前缀",复用 provider 的 warm prefix cache
- **核心收益**: compaction 是昂贵的 LLM 调用(需要总结整个对话),通过前缀共享命中 KV cache,避免重新计算

**其他工程的 Prompt Caching**: claude-code/openclaw/opencode 都依赖 Provider 内部的 Prompt Caching(通过 `cache_control` 断点),但这是 Provider 客户端 SDK 的行为,各工程没有显式的 KV Cache 管理逻辑。

**第十三轮 KV Cache 专题**: 已详细分析 KV cache 内存精算 + PagedAttention + Continuous Batching + Speculative Decoding + RadixAttention + Flash Attention,但这些都是推理引擎(vLLM/TGI)的内部实现,Agent CLI 工程仅作为客户端间接利用。

- **L885 [P2]**: laew 无 KV Cache 管理
- **L851 [P1]**(deepseek-harness 标注): laew 无 KV Cache 感知的 compaction
- **L852 [P2]**(openclaw 标注): laew 无 KV Cache 优化,每次请求发送完整上下文
- **L857 [P1]**(pi 标注): laew 无 KV Cache 管理(依赖 Provider 内部实现)

### 6.2 核心发现

**atomcode 的 Ollama 完整集成**(唯一生产级本地推理):

```rust
// ollama.rs:1-125
pub struct OllamaConfig {
    pub api_key: String,  // OPTIONAL — Ollama itself needs none
    pub base_url: String, // e.g. http://localhost:11434
    pub model: String,
    pub max_tokens: Option<u32>, // → options.num_predict
    pub think: bool, // Enable thinking (think: true)
    pub idle_timeout: Duration,
    pub connect_timeout: Duration,
    pub retry: RetryPolicy,
    pub skip_tls_verify: bool,
}
```

**核心机制**:
- **NDJSON 流解码**: 每行一个完整 JSON 对象(无 `data:` 前缀,无 `[DONE]` 哨兵)
- **思考模式**: `think: true` 启用推理模型(如 deepseek-r1)
- **工具调用 id 合成**: Ollama 不返回 id,Decoder 内部合成稳定 id 以便 kernel 配对 call/result
- **透明流重连**: 最多 3 次重开(1 初始 + 2 重开),仅在未发射 replay-sensitive 输出前可重放

**设计意图**: "Ollama tool calls carry NO id — the decoder SYNTHESIZES a stable id so the kernel can pair the call with its result; the id stays internal (never sent back, since a tool result is matched by ORDER on the wire)"

**openclaw 的 TTS 本地回退**: openclaw 在 TTS 场景支持 `sherpa-onnx-tts` 本地推理,但这是特定于语音合成的轻量级推理,不是通用 LLM 推理。

**其他工程的纯云端依赖**: claude-code/deepseek-harness/opencode/pi 完全依赖云端 API,无任何本地推理能力。

### 8.2 核心发现

**pi 的唯一约束采样实现**:

```typescript
// constrained-sampling.ts:1-128
const UNSUPPORTED_STRICT_SCHEMA_KEYS = [
    "$ref", "$defs", "definitions", "allOf", "oneOf",
    "patternProperties", "dependentSchemas", "dependencies",
    "unevaluatedProperties", "propertyNames", "contains",
    "prefixItems", "not", "if", "then", "else",
] as const;

export function makeStrictJsonSchema(schema: Tool["parameters"]): Record<string, unknown> {
    const cloned: unknown = structuredClone(schema);
    makeJsonSchemaNodeStrict(cloned);
    if (cloned.type !== "object") throw new UnsupportedStrictJsonSchemaError("root schema must have type object");
    return cloned;
}
```

**JSON Schema Strict 模式**:
- 将任意 JSON Schema 转换为 **Strict 子集**(OpenAI structured output 兼容)
- 拒绝 `$ref` / `allOf` / `oneOf` 等复杂关键字
- 自动补全 `required` 和 `additionalProperties: false`
- 非 required 字段自动添加 `anyOf: [T, { type: "null" }]`

**Grammar 约束采样**:
```typescript
export interface GrammarConstrainedSampling {
    format: "lark" | "regex";
    definition: string;
    inputProperty: string;
}
```

- 支持 Lark 语法和正则约束
- 流式 `input` 属性拼接(`appendGrammarToolInputJsonDelta`)
- 单调性校验(`nextInput.startsWith(buffer.input)`)

**其他工程的"无"**: 其他 6 个工程均未实现约束采样,完全依赖 Provider 内置的 structured output 能力(如 OpenAI 的 `response_format: json_schema`)。

### 10.2 关键发现

1. **本地推理全零格局**: 除了 atomcode(Ollama)和 openclaw(TTS 回退),所有工程完全依赖云端 API。这是 Agent CLI 架构的共识——推理交给专业服务,Agent 负责编排。

2. **推理优化三范式**:
   - **客户端侧精算**(claude-code/opencode): Token 精确计数 + 上下文窗口精算 + Tail-Preserve 压缩
   - **Provider 侧感知**(deepseek-harness): KV Cache 对齐的 compaction
   - **可用性优化**(atomcode): 透明流重连 + 工具调用 id 合成

3. **多 Provider 路由成熟度**: pi(15+ Provider) > opencode(15+) > atomcode(3) > claude-code(2)。pi 和 opencode 的统一 Route 抽象是行业最佳实践。

4. **约束采样唯一实现**: pi 是唯一实现 JSON Schema Strict + Grammar 约束采样的工程,这是 structured output 的客户端侧保障。

5. **KV Cache 感知稀缺**: deepseek-harness 的 KV Cache 对齐 compaction 是唯一显式利用 Provider 内部缓存机制的设计,其他工程仅间接依赖 Prompt Caching。
