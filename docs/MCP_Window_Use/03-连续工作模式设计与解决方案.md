# MCP_Window_Use 连续工作模式(run_sequence)设计与解决方案

> 2026-09-19 第 91 轮。本文档是「MCP_Window_Use 连续工作模式」的完整设计与
> 解决方案:在 macOS / Windows 上,用户会同时使用键盘鼠标、切换窗口,
> Agent 需要先**摸索排查窗口结构**,统一 plan 之后**一次调用连续执行一套动作**,
> 给出**完整执行记录**,并对异常(步骤失败 / 焦点被抢 / UI 未就绪)做结构化处理。
>
> 前置阅读:`01-设计与解决方案.md`(第 84~88 轮,工具总体架构)、
> `02-鼠标键盘操控与优先级链方案.md`(第 90 轮,原子能力与 input_batch)。

## 1. 背景与问题

### 1.1 用户场景

桌面自动化的真实运行环境是**人机共用一台机器**:

1. 用户会随时用键盘鼠标操作、切换窗口 —— Agent 执行动作序列的中途,
   前台焦点随时可能被用户抢走(第 88 轮实测痛点:消息打进别的软件);
2. 一次完整任务(如「打开微信 → 找到某会话 → 翻阅记录 → 汇总发回」)
   需要**先摸索**(list/find/inspect/ocr 了解窗口架构与控件结构),
   **统一规划**后**连续执行多个步骤**,而不是每步都返场 LLM 重新决策;
3. 执行过程要**留下记录**(哪步成功、哪步失败、失败原因、焦点事件),
   遇到异常要**按策略处理**(重试 / 跳过 / 止损中止),而不是一失败就裸奔或全停。

### 1.2 现状缺口(代码评审结论)

对 `src/agent/tools/mcp_window_use/` 全部 12 个 action 的分析:

| # | 级别 | 问题 | 位置 |
|---|------|------|------|
| C1 | P0 | **input_batch 无验证能力**:10 个 op 全是「动作」,没有「断言/等待 UI 就绪」;UI 异步加载(列表刷新、对话框弹出)只能靠盲 `wait{ms}` 赌时长,赌错即后续步骤全部打空 | `input_batch.rs` op 集 |
| C2 | P0 | **input_batch 无重试策略**:默认 fail-fast 或 `continue_on_error` 二选一;瞬时失败(控件还没渲染出来、动画未结束)没有「等一下重试」的中间档 | `input_batch.rs::execute_steps` |
| C3 | P0 | **批量执行期间无焦点守护**:只在批次开头 `ensure_frontmost` 一次;用户在批次中途切窗,后续物理输入全部打进别人的窗口(第 88 轮 chat_loop 已有止损,input_batch 没有) | `input_batch.rs::run_input_batch` |
| C4 | P1 | **input_batch 无执行记录落盘**:chat_send/chat_loop 有 `chat_log_path` 落盘 `[SEND]/[RECV]/[FAIL]`,input_batch 只有一次性 JSON 返回,长批失败后无法追溯现场 | `input_batch.rs` |
| C5 | P1 | **input_batch 时长/步数预算偏紧**:steps ≤ 40、整批 ≤ 60s,面向「短复合动作」;连续工作模式需要更长预算(探索后一次性执行几十个步骤、含等待 UI 就绪) | `input_batch.rs` 常量 |
| C6 | P1 | **chat_loop 是特化循环**:只覆盖「定时发消息」一个场景,通用「计划好的动作序列连续执行」没有入口 | `chat.rs` |

### 1.3 与既有 action 的定位划分

| action | 定位 | 预算 | 验证/重试/焦点守护 |
|--------|------|------|--------------------|
| `control` | 单步原子操作 | 单步 | 无 |
| `input_batch` | **短复合动作**(点输入框→ctrl+a→输文本→回车),零返场 | ≤40 步 / ≤60s | 开头一次前台守卫,fail-fast |
| `chat_loop` | 特化:定时多轮发消息 + 回复检测 | ≤1000 轮 / 间隔 ≤300s | 连续 3 次前台守卫失败止损 |
| **`run_sequence`(本轮新增)** | **连续工作模式**:探索后统一计划的一套动作(含验证/等待),一次调用连续执行完毕 | ≤100 步 / 默认 ≤180s(可调 ≤600s) | 逐步焦点守护 + 三级错误策略 + 逐步落盘记录 |

## 2. 连续工作模式方法论(先摸索 → 统一 plan → 连续执行)

工具描述与系统提示词引导 LLM 按以下范式工作:

```
① 摸索排查(只读,了解窗口架构与结构):
   capability_probe(能力矩阵) → open/list/find(定位 window_id)
   → inspect(控件树) / ocr(自绘 UI 视觉路线)
② 统一 plan(LLM 在自身上下文里把后续动作排成 steps 数组,
   异步 UI 处插 wait_for_text / wait_front,关键结果处插 assert_text / get_text)
③ 连续执行(一次调用):
   MCP_Window_Use(action=run_sequence, window_id=W, steps=[...],
                  on_error="retry", log_path=...)
④ 复查与续作:按返回的 steps 记录 + log_path 对账;
   失败片段 re-inspect 后用新的 run_sequence 补做
```

## 3. 协议与参数定义(action=run_sequence)

### 3.1 顶层参数

| 参数 | 类型 | 必填 | 默认 | 说明 |
|------|------|------|------|------|
| `action` | string | * | — | `"run_sequence"` |
| `window_id` | string | * | — | 目标窗口(open/list/find 获取) |
| `steps` | array | * | — | 步骤数组,≤ 100(超出拆多次调用) |
| `on_error` | string | | `"abort"` | 错误策略:`abort`(失败即停,剩余标记 skipped)/ `continue`(继续后续步骤)/ `retry`(先逐步重试,仍败则停) |
| `retry_times` | int | | 1 | `on_error=retry` 时每步最多重试次数,≤ 3;步骤级可用同名键覆盖 |
| `retry_delay_ms` | int | | 500 | 重试前等待毫秒,≤ 5000;步骤级可覆盖 |
| `focus_guard` | bool | | true | 逐步焦点守护:每个**物理输入步骤**(mouse_*/key_press/type_text/click)执行前确认窗口仍在前台 |
| `focus_wait_ms` | int | | 5000 | 焦点丢失后重新激活+轮询等待的预算,≤ 30000 |
| `max_total_ms` | int | | 180000 | 整批时长硬顶,≤ 600000;超时剩余步骤标记 skipped |
| `log_path` | string | | `<工作目录>/laew_sequence_<unix_ts>.log` | 执行记录落盘路径(逐步 [STEP]/[RETRY]/[FOCUS_LOST]/[FAIL]/[SUMMARY]) |

### 3.2 步骤 op 集(input_batch 10 个 + 连续模式 3 个新 op)

沿用 input_batch 全部 op(参数语义完全一致,复用同一执行函数):

- 鼠标:`mouse_move` / `mouse_click` / `mouse_drag` / `mouse_scroll`
- 键盘:`key_press` / `type_text`
- 控件树(自动 T1 无障碍 → T2 消息 → T3 物理优先级链):`click` / `set_text` / `get_text`
- `wait{ms}`(连续模式下上限放宽到 30000,内部分片睡眠并响应时长硬顶)

连续工作模式新增:

| op | 参数 | 语义 |
|----|------|------|
| `assert_text` | `path*`, `contains*` | 读控件文本,不含 `contains` 即步骤失败(触发 on_error 策略);关键节点自检 |
| `wait_for_text` | `path*`, `contains*`, `timeout_ms`(≤30000,默认 10000), `poll_ms`(默认 500) | 轮询控件文本直到出现目标内容或超时;**异步 UI 就绪等待**,替代盲 wait |
| `wait_front` | `timeout_ms`(≤30000,默认=focus_wait_ms) | 显式等待/重新拿前台(用户切窗后的恢复点;长时间动作前的保险) |

每个步骤通用键:`delay_ms`(≤2000,步前等待)、`optional`(bool,失败容忍:
记 `ok:false, optional:true` 但不触发 on_error 策略、不进 failed_steps)、
`retry_times` / `retry_delay_ms`(步骤级覆盖)。

### 3.3 返回体(结构化执行记录)

```json
{
  "ok": false,
  "action": "run_sequence",
  "window_id": "1234:0",
  "frontmost_acquired": true,
  "steps_total": 12,
  "steps_ok": 9,
  "steps": [ {"i":0,"op":"click","ok":true,"route":"uia","detail":"...","attempts":1} ],
  "results": {"余额": "128.00"},
  "failed_steps": [7],
  "retried_steps": 2,
  "focus_lost_count": 1,
  "focus_aborted": false,
  "elapsed_ms": 18340,
  "log_path": "D:\\work\\laew_sequence_1758240000.log",
  "next_action": "第 7 步 wait_for_text 超时;UI 可能未按预期就绪,先 action=inspect 或 action=ocr 重新定位,再把失败片段拆成新的 run_sequence 补做"
}
```

落盘记录格式(与 chat_log 同源,`{unix_ts} [标签] 内容`):

```

1758240003 [FOCUS_LOST] window_id=1234:0 步骤 4 执行前焦点不在目标窗口,重新激活
1758240004 [FOCUS_REGAINED] elapsed=820ms attempts=6
1758240005 [RETRY] i=7 op=wait_for_text attempt=2/3
1758240009 [FAIL] i=7 op=wait_for_text detail=超时未等到...
1758240009 [SUMMARY] total=12 ok=9 failed=1 retried=2 focus_lost=1 elapsed=18.3s
```

### 3.4 异常处理矩阵

| 异常 | 处理 |
|------|------|
| 步骤瞬时失败(控件未渲染/动画中) | `on_error=retry` + `retry_delay_ms` 等待重试 ≤3 次 |
| 步骤确定性失败 | `abort`:剩余步骤标记 `skipped` 并附原因;`continue`:记 failed_steps 继续 |
| 非关键步骤失败 | 步骤级 `optional:true` 容忍 |
| UI 异步未就绪 | `wait_for_text` 轮询等待;超时按步骤失败走策略 |
| **用户切窗抢焦点** | focus_guard:物理步骤前探测,丢失则 bring_to_front + 轮询 ≤ focus_wait_ms;**连续 3 次重夺失败 → 整批止损中止**(`focus_aborted=true`,提示用户保持窗口前台;与第 88 轮 chat_loop 止损同源) |
| 批次开头就拿不到前台 | 结构化报错,**一步都不执行**(不盲打,与 input_batch 一致) |
| 整批超时 | max_total_ms 硬顶,剩余 skipped |

## 4. 实现设计

### 4.1 代码结构(零新 crate,复用既有底座)

```
src/agent/tools/mcp_window_use/
  sequence.rs     本轮新增:run_input_sequence 入口 + 同步执行循环
  input_batch.rs  execute_step / step_str / step_i64 提升为 pub(super) 复用
  chat.rs         ensure_frontmost 同步变体思路复用;append_chat_log /
                  format_chat_log_line 直接复用(pub(super) 已有)
  mod.rs          schema 注册(action 枚举 + 新顶层参数 + steps op 枚举扩展)
                  + 描述文案(连续工作模式范式)+ dispatch 分支
src/tui/format_brief.rs  run_sequence 摘要(steps=x/y focus_lost=n retries=n)
```

### 4.2 执行循环(sequence.rs 核心)

```
run_input_sequence(args):
  校验 window_id / steps(1..=100) / on_error ∈ {abort,continue,retry}
  run_blocking(同步闭包):
    ① 同步前台守卫(轮询 is_frontmost ≤1500ms,平台不支持探测则放行
       —— 与 ensure_frontmost 同语义,run_blocking 内用 thread::sleep)
    ② for each step:
       - max_total_ms 硬顶检查 → 剩余 skipped
       - delay_ms 步前等待
       - focus_guard 且为物理输入 op → is_frontmost 检查;
         丢失 → bring_to_front + 轮询 ≤focus_wait_ms,落盘 FOCUS_LOST/REGAINED;
         重夺失败 consecutive_focus_fail+=1,≥3 → 止损中止
       - 执行(新 op 本模块处理,其余委托 input_batch::execute_step)
       - 失败且非 optional → 按 on_error:retry 则重试(retry_times/
         retry_delay_ms,步骤级覆盖优先);仍败 abort/continue
       - 每步落盘 [STEP]/[RETRY]/[FAIL]
    ③ [SUMMARY] 落盘 + 结构化 JSON 返回
```

### 4.3 护栏(与既有 action 同量级,不新增攻击面)

- steps ≤ 100;max_total_ms ≤ 600s;wait ≤ 30s;wait_for_text timeout ≤ 30s;
  retry_times ≤ 3;focus_wait_ms ≤ 30s —— 全部硬校验,超限结构化报错;
- 物理输入最终落到既有 `ControlAction`,权限/优先级链与 control 完全一致;
- 焦点守护默认开,可 `focus_guard=false` 关闭(无人值守场景);
- 止损语义与 chat_loop 一致:连续 3 次焦点重夺失败立即中止,防止误输入
  到其他软件。

## 6. 风险与取舍

- **focus_guard 与用户输入的竞态**:用户正在打字时 Agent 抢回前台会打断用户;
  取舍为「物理步骤前才检查 + 重夺预算 ≤30s + 连续 3 次失败止损」,宁可中止
  也不与用户拉锯;无人值守场景可 focus_guard=false。
- **wait_for_text 只覆盖控件树路线**:自绘 UI 无控件文本可读,需 OCR 路线
  的 `wait_for_ocr_text`(依赖屏录权限);本轮不引入,文档备案为后续候选。
- **同步阻塞**:执行循环在 `run_blocking`(spawn_blocking)内,UIA COM /
  AX IPC 不阻塞 tokio runtime,与 input_batch 同模式。
