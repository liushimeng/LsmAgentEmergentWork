## 1. 背景与问题

### 1.1 现状缺口(代码评审结论)

对 `src/agent/window/`(驱动层)与 `src/agent/tools/mcp_window_use/`(工具层)
的全面分析,发现四类问题:

| # | 级别 | 问题 | 位置 |
|---|------|------|------|
| G1 | P0 | **缺鼠标原子能力**:无 `move_point`(悬停)、`drag_point`(拖拽)、`middle_click_point`(中键);点击类动作不支持修饰键(ctrl+click 多选 / shift+click 区选 / alt+drag 复制)——「同时操作鼠标、键盘」没有原语 | `ControlAction` 枚举 |
| G2 | P0 | **缺复合步骤动作**:`type_text_submit` 只覆盖「点+输+回车」一个特例;任意「鼠标序列 + 键盘序列 + 控件树操作」组合(如 点输入框 → ctrl+a → 输新文本 → 点确定)需多次工具调用,每两次调用之间都有焦点竞态窗口(第 80 轮动机)且烧 SubAgent 16 次迭代上限 | 工具层 action 集 |
| G3 | P0 | **Windows 驱动优先级链违背「无障碍/消息优先,物理兜底」**:`click` 是 UIA Invoke → **物理点击** → BM_CLICK(物理抢在消息前);`set_text` 是 ValuePattern → **物理键入** → WM_SETTEXT;`send_keys` 直接物理 SendInput 不试消息;`scroll` 不试 UIA ScrollPattern 直接物理滚轮 | `windows.rs::act` |
| G4 | P1 | **route 可观测性缺失**:control 返回文案不带结构化路线标注,QC/Debug 无法对账「这一步到底走了 UIA 还是物理输入」 | 三平台驱动返回文案 |

### 1.2 macOS / Linux 现状

- **macOS legacy 驱动**:`click` 已按控件真实 AX action 能力选择
  (AXPress/AXPick/AXConfirm/Open),`set_text` 走 AXValue,`get_text` 走
  AXValue/AXTitle —— **无障碍 API 已是第一优先级,符合要求**;
  macOS 无 Windows 消息等价层,CGEvent 物理输入即兜底层,链路成立;
  但同样缺 G1 的鼠标原子能力(无拖拽/中键/修饰键点击)。
- **fallback(Linux)驱动**:仅 Focus/Scroll/TypeText 尽力而为(xdotool),
  缺新原子能力的 xdotool 实现。
- **macos-axui feature 路径**:坐标动作返回「legacy 驱动已支持」结构化引导,
  新变体沿用同一模式。

## 2. 设计总览

### 2.1 操作优先级链(四层,全平台统一语义)

```
┌─ T1 系统无障碍 API(首选,语义级、不抢焦点、不依赖窗口位置)
│    Windows: UIA Pattern —— Invoke / Toggle / ExpandCollapse / SelectionItem /
│             Value / Scroll / ScrollItem
│    macOS:   AX Action —— AXPress / AXPick / AXConfirm / AXOpen /
│             AXValue Set / AXScrollToVisible
├─ T2 系统消息层(次选,句柄级、同步/异步投递,不移动光标)
│    Windows: BM_CLICK / WM_SETTEXT / WM_GETTEXT / WM_MOUSEWHEEL /
│             PostMessage WM_KEYDOWN+WM_CHAR+WM_KEYUP(仅原生 HWND 控件)
│    macOS:   ——(无等价层,直接进 T3)
├─ T3 物理鼠标键盘(兜底,SendInput / CGEvent / xdotool)
│    自绘 UI(微信 4.x / Electron canvas / 游戏)唯一可靠路径;
│    一切坐标类动作(click_point / drag_point / move_point ...)天然落在本层
└─ T4 外部命令降级(macOS osascript System Events / cliclick,既有机制不变)
```

**判定规则**:
- 元素暴露 T1 能力(Pattern / AX action)→ 直接走 T1,成功即返回;
- 元素有**原生 HWND**(`IUIAutomationElement::CurrentNativeWindowHandle != 0`)
  → T2 消息可用(BM_CLICK 限 Button 系类名,WM_SETTEXT/WM_GETTEXT 限标准控件);
- 其余(自绘 UI 无 HWND、坐标动作、拖拽)→ T3 物理输入;
- 每步返回文案带 `route=` 标注(`route=uia` / `route=win32_msg` / `route=physical`),
  QC/Debug 可对账(第 88 轮 TUI [tool] 摘要同源)。

**零回归保证**:第 67 轮「自绘 UI 优先真实输入」的行为不变 —— 自绘 UI 元素
既无 Pattern 也无原生 HWND,自动落穿到 T3 物理输入,与旧行为一致;
标准 Win32 控件从「物理抢跑」回归到「消息优先」,符合本轮要求。

### 2.2 新增鼠标键盘原子能力(G1)

`ControlAction` 变更(`src/agent/window/mod.rs`):

| 变更 | 变体 | 参数 | 语义 |
|------|------|------|------|
| 新增 | `MovePoint` | `x, y` | 移动光标(悬停:菜单展开 / tooltip) |
| 新增 | `MiddleClickPoint` | `x, y` | 中键点击(浏览器新标签打开等) |
| 新增 | `DragPoint` | `x, y, x2, y2, modifiers?` | 从 (x,y) 按住拖到 (x2,y2),可按住修饰键(ctrl+拖=复制) |
| 扩展 | `ClickPoint` / `DoubleClickPoint` / `RightClickPoint` | `+ modifiers?` | 修饰键 + 点击(ctrl/shift/alt+点击,多选/区选) |

- `modifiers` 为字符串规格(`"ctrl"` / `"ctrl+shift"`),与 `send_keys` 组合键语法同源;
- 工具层 `control_action` 新枚举值:`move_point` / `middle_click_point` / `drag_point`;
  工具新参数 `modifiers` / `x2` / `y2`;
- `parse_ext` 签名扩展为 `(name, text, x, y, x2, y2, modifiers)`。

**平台实现**:

| 平台 | move | middle click | drag | 修饰键 |
|------|------|-------------|------|--------|
| Windows | `SetCursorPos` | SendInput MIDDLEDOWN/UP | SendInput 按住左键 + 10 步插值移动 + 抬起 | `parse_key_spec` 前缀段 → VK 按下 → 动作 → 逆序释放 |
| macOS | `CGEventCreateMouseEvent(mouseMoved)` | otherMouseDown/Up(button=2) | CGEvent leftDown(带 flags)→ 插值 moved → leftUp | `CGEventSetFlags`(OR 多修饰键 mask) |
| Linux | `xdotool mousemove` | `xdotool click 2` | `xdotool mousedown 1 → mousemove --sync → mouseup 1` | `xdotool keydown/keyup` |

### 2.3 新增复合 action `input_batch`(G2)

```
MCP_Window_Use(action=input_batch, window_id*, steps*, continue_on_error?)
steps: [
  {"op":"mouse_move",    "x":100, "y":200},
  {"op":"mouse_click",   "x":100, "y":200, "button":"left|right|middle", "clicks":1|2, "modifiers":"ctrl"},
  {"op":"mouse_drag",    "x":10, "y":10, "x2":300, "y2":300, "modifiers":"ctrl"},
  {"op":"mouse_scroll",  "x":400, "y":600, "direction":"up|down", "lines":3},
  {"op":"key_press",     "keys":"ctrl+a"},                  // 单键/组合键
  {"op":"type_text",     "text":"你好"},                     // Unicode 物理键入
  {"op":"click",         "path":"/0/2"},                     // 控件树路线(T1→T2→T3)
  {"op":"set_text",      "path":"/1/0", "text":"内容"},       // 同上
  {"op":"get_text",      "path":"/1/0", "key":"搜索结果"},    // 读取值进 results
  {"op":"wait",          "ms":300},
  ...每步可选 "delay_ms"(该步执行前等待,≤2000)
]
```

- **一次前台守卫**(`ensure_frontmost` 复用第 88 轮实现),批量执行,
  步骤间零 LLM 返场、零焦点竞态窗口 —— 这就是「同时操作鼠标、键盘」的统一入口;
- 返回 `{ok, steps_total, steps_ok, results{key→get_text 值}, steps[{i,op,route,ok,detail}], next_action}`;
- 护栏:steps ≤ 40;`wait.ms` ≤ 5000;`delay_ms` ≤ 2000;总时长硬顶 60s;
- 失败策略:默认 fail_fast(失败即停,已执行步骤照常返回);
  `continue_on_error=true` 时继续执行后续步骤(汇总 failed 明细);
- 控件树步骤(click/set_text/get_text)走 `driver.act` —— 自动享受 T1→T2→T3 链。

### 2.4 Windows 驱动 act() 优先级链重构(G3 + G4)

| 动作 | 重构后链路(旧链路的问题) |
|------|---------------------------|
| `click` | T1 Invoke → **T1 Toggle → T1 ExpandCollapse → T1 SelectionItem.Select**(新增:复选框/下拉/列表项的语义化点击,旧链路全落物理)→ T2 BM_CLICK(原生 Button/CheckBox/Radio 系 HWND;旧链路排在物理后)→ T3 物理点击中心 |
| `set_text` | T1 ValuePattern.SetValue → T2 WM_SETTEXT(原生 HWND;旧链路排在物理后)→ T3 focus+SendInput 逐字键入 |
| `get_text` | T1 Value → T1 Name → T2 WM_GETTEXT(原生 HWND,新增) |
| `send_keys` | T2 PostMessage WM_KEYDOWN+WM_CHAR+WM_KEYUP(仅原生 HWND 控件;新增)→ T3 SetFocus+force_foreground+SendInput。**Electron/自绘根窗口(无子 HWND)保持物理路线,零回归** |
| `scroll` | T1 ScrollPattern(新增)→ T2 WM_MOUSEWHEEL(原生 HWND)→ T3 物理滚轮(旧链路物理优先,消息兜底) |
| `scroll_to_visible` | T1 ScrollItemPattern → T3 物理滚轮降级(不变) |
| 点动作 | T3(force_foreground + SendInput;`MovePoint` 无需前台化) |

消息键注入(`PostMessage keys`)细节:
- 主键 `WM_KEYDOWN`(wScan=`MapVirtualKeyW(vk, MAPVK_VK_TO_VSC)`)→
  可打印字符补 `WM_CHAR`(VK→字符,ctrl 组合键不补)→ `WM_KEYUP`;
- 修饰键逐个 `WM_KEYDOWN` → 主键序列 → 逆序 `WM_KEYUP`;
- `PostMessageW` 异步投递(不阻塞、不要求目标响应),每事件间 sleep 10ms。

### 2.5 uia_actions 能力标注扩展

`uia_actions(el)` 在 Invoke/Value 之外,补 Toggle / ExpandCollapse /
SelectionItem 探测(inspect 树的 `actions` 字段更完整,LLM 选择依据更准)。

### 2.6 macOS 驱动补齐(G1)

- 新增 `cg_click_at_ex(x, y, button: Left|Right|Middle, clicks, flags)`、
  `cg_drag(from, to, flags)`、`parse_modifier_flags("ctrl+shift") -> u64`;
  旧 `cg_click_at` 保留为 wrapper;
- act() 增补 `MovePoint` / `MiddleClickPoint` / `DragPoint` / 修饰键点击分支;
- click/set_text/get_text 链路不变(AX 已是 T1 优先,CGEvent 即 T3,无 T2)。

## 4. 典型用法(LLM 视角)

```
1) ctrl+点击多选两行(微信文件多选 / 邮件批量操作):
   MCP_Window_Use(action=control, window_id=W, path="/", control_action="click_point",
                  x=300, y=500, modifiers="ctrl")
   MCP_Window_Use(action=control, window_id=W, path="/", control_action="click_point",
                  x=300, y=540, modifiers="ctrl")

2) 拖拽文件到文件夹 / 滑块拖到最右:
   MCP_Window_Use(action=control, window_id=W, path="/", control_action="drag_point",
                  x=120, y=400, x2=700, y2=400)

3) 一次调用完成「聚焦输入框 → 全选 → 替换文本 → 回车」(零返场):
   MCP_Window_Use(action=input_batch, window_id=W, steps=[
     {"op":"mouse_click","x":520,"y":760},            // T3 点输入框
     {"op":"key_press","keys":"ctrl+a"},               // 键盘
     {"op":"type_text","text":"新内容"},                // 键盘
     {"op":"key_press","keys":"enter"}                 // 键盘
   ])

4) 控件树语义操作(标准 UI,全程不抢鼠标):
   MCP_Window_Use(action=control, window_id=W, path="/0/3", control_action="click")
   → route=uia(InvokePattern)优先;无 Pattern 且原生按钮 → route=win32_msg(BM_CLICK);
     自绘 UI → route=physical(SendInput 兜底)

5) 读取输出信息(无障碍优先):
   MCP_Window_Use(action=input_batch, window_id=W, steps=[
     {"op":"click","path":"/2/1"},
     {"op":"get_text","path":"/3/0","key":"结果文本"}
   ]) → results["结果文本"] 直接带回,无需第二次调用
```

## 6. 风险与取舍

- **`macos_legacy.rs` 已超 1800 行红线**(本轮前 1837 行):本轮为编译完整性
  必须追加 match 分支(+~90 行);按拆分规范应在下一轮把 CGEvent 输入底座
  (`cg_*` 家族)拆到独立子模块 `macos_legacy/input.rs`,本轮先在文档备案。
- **PostMessage 键注入的固有局限**:消息级按键对部分应用(游戏 / 自绘 /
  部分防自动化软件)无效且无法感知失败 —— 因此仅对**原生 HWND 控件**启用,
  其余一律物理路线;`route=` 标注暴露实际走向,QC 可对账。
- **拖拽无 T1/T2 路线**:UIA DragPattern 极少有应用实现,Win32 无通用内容
  拖拽消息 —— 拖拽跨平台恒走 T3 物理输入,符合「兜底」定位(自绘场景本就
  只有物理路线可靠)。
- **input_batch 权限面**:复合步骤最终落到既有 ControlAction,权限/护栏与
  单步 control 完全一致(steps 上限 40 / 总时长 60s / 前台守卫复用第 88 轮),
  不新增攻击面。
