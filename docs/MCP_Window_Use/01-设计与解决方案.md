# MCP_Window_Use 设计与解决方案

> 2026-09-18 主文档。本文档是「删除 `LsmAgentEmergentWork-WindowUse` Agent(第 9 角色),
> 将其窗口操控能力降级为 Agent Tools 中的单一 MCP 风格工具 `MCP_Window_Use`」的完整设计。
>
> 平台技术参考(实现依据,先于本文档存在):
> - `docs/MCP_Window_Use/MCP_Window_Use_MacOS_技术文档.md`(macOS AX / CGEvent / TCC 权限)
> - `docs/MCP_Window_Use/MCP_Window_Use_Window_技术文档.md`(Windows UIA / SendInput / OCR)

---

## 1. 背景与目标

### 1.1 现状(改造前)

窗口操控能力以**独立 Agent 角色**存在(第 9 角色 `LsmAgentEmergentWork-WindowUse`):

- `WindowUseRunner`(`src/agent/window_use.rs`,893 行):镜像 SubAgentRunner 的专项执行器,
  带首迭代强制 WindowOpen、Runner 出口兜底、目标应用自动启动、窗口会话状态跨轮持久化等
  大量Runner 层补丁逻辑;
- 7 个独立工具(WindowOpen / WindowList / WindowFind / WindowInspect / WindowAction /
  WindowOCR / WindowScreenshot)+ WindowUse 专用 Bash 白名单模式
  (`LAEW_WINDOW_USE_MODE` 进程级环境变量 + trust_level);
- `AgentRole::WindowUse` 角色渗透全链路:Yolo 关键词推断、Main-Work 委派纠正、
  `run_wf_unit` 三路 Runner 路由、QC 专项诊断、TUI 标识、窗口状态表 `window_state`;
- 第 54~83 轮的实测复盘表明:专项 Agent 形态的维护成本极高(forced tool / nudge /
  stale 状态校验 / 委派错配双重防御),而核心价值只在「窗口操控工具能力」本身。

### 1.2 目标(改造后)

1. **彻底删除 WindowUse Agent**:Runner、profile、角色枚举、委派路由、系统提示词、
   Bash 白名单模式、窗口状态持久化、相关文档(`docs/WindowUse桌面窗口操控Agent/`、
   `docs/WindowUse多轮对话与Agent间通信增强设计/`)。
2. **能力降级为工具**:新增单一工具 `MCP_Window_Use`,把原 7 个工具的参数与使用方法
   收敛为**一个 MCP 风格服务接口**(`action` 枚举分发),由持有该工具的 Agent
   (SubAgent-Work)在自身多轮对话循环中直接调用。
3. **平台门控**:仅在 macOS / Windows 运行时定义该工具(注册表 + 系统提示词同步门控),
   Linux 等其他平台不出现工具定义。
4. **零行为回退**:驱动层(`src/agent/window/`,Windows UIA / macOS AX / 视觉 OCR /
   SendInput)原样保留为服务实现;桌面窗口任务改走
   「Yolo 分类(最低 medium)→ Main-Work 拆解(delegate_to=subagent)
   → SubAgent-Work 持 MCP_Window_Use 多轮工具调用 → QC → SessionContext」标准链路。

### 1.3 为什么叫「MCP 服务」

`MCP_Window_Use` 按 **MCP(Model Context Protocol)服务的调用语义**设计:

| MCP 概念 | 本设计落地 |
| ---- | ---- |
| 单一服务入口 | 一个工具 `MCP_Window_Use`,而非 7 个并列工具 |
| `tools/call` 方法分发 | `action` 枚举参数(open/list/find/inspect/control/ocr/screenshot) |
| 结构化 JSON 入参/出参 | 统一 JSON Schema;返回均为结构化 JSON 文本(含 `next_action` 引导) |
| 服务与宿主解耦 | 服务实现封闭在 `agent::window` 驱动层 + `tools/mcp_window_use/` 处理器,Agent 循环只见到一个 ToolDef |
| 多轮对话调用 | Agent 在自身 agentic loop 中反复调用该工具完成「定位→检视→操作→复查」 |

当前进程内实现(in-proc service),不引入独立 MCP server 进程与 JSON-RPC 传输;
接口形态与 MCP 对齐,未来如需拆分为真实 MCP server(stdio/SSE),仅需把
`McpWindowUseTool::execute` 的分发改为 RPC 调用,Agent 侧零改动。

## 2. 总体架构

```
用户输入
  → Yolo 分类(窗口操控类任务最低 medium,suggested_delegate 不再产出 windowuse)
  → Main-Work 拆解 WorkFlow(delegate_to 二选一:subagent / webuse;
    桌面 GUI 强信号 → subagent)
  → run_wf_unit 路由 SubAgentRunner(执行层唯一通用执行器;webuse 仍走 WebUseRunner)
  → SubAgent-Work Agent 循环
      └─ 工具集(macOS/Windows):Bash / Read / Write / Edit / Glob / Grep / MCP_Window_Use
      └─ MCP_Window_Use(action=...) ──► tools/mcp_window_use/ 处理器
                                          └─► agent::window 驱动层
                                              (Windows UIA+SendInput+Media.Ocr /
                                               macOS AX+CGEvent+CGWindow /
                                               其他平台 fallback,不注册工具)
  → Quality-Check → SessionContext 收口
```

**关键取舍**:

- **不再有专项 Runner**:首迭代强制工具、nudge、Runner 出口兜底、窗口状态跨轮持久化、
  目标应用自动启动等 Runner 层机制随 Agent 一并删除。`MCP_Window_Use(action=open)`
  自身即包含「启动/激活 + 等待窗口出现 + 权限状态 + next_action 引导」,
  工具返回的 `next_action` / `permission_hint` 字段承担了原 Runner 的引导职责。
- **Bash 白名单模式删除**:`LAEW_WINDOW_USE_MODE` 环境变量、两级白名单、trust_level
  全部移除。SubAgent 的 Bash 本就全量可用(黑名单约束不变),降级路径
  (osascript / cliclick / screencapture)天然可用,不再需要模式切换。
- **AgentRole 枚举收缩**:`WindowUse` 变体删除;存量 DB 中 `role='windowuse'` 的
  agent_memory / session_memory 行由 `From<&str>` 兜底映射为 `SubAgent`(只读兼容,
  不做表迁移)。

## 3. 工具定义 `MCP_Window_Use`

### 3.1 基本信息

- **name**: `MCP_Window_Use`
- **定位**: 通过软件窗口读取与操作桌面软件(枚举窗口、遍历控件树、点击/输入/滚动、
  OCR 视觉识别、截图),是桌面 GUI 自动化的统一入口。
- **注册**: `builtin_registry()` / `builtin_registry_with_work_dir()`
  (SubAgent-Work 全套工具)中,仅 `cfg!(target_os = "macos") || cfg!(target_os = "windows")`
  为真时注册;其余平台不注册、不出现在 tools 列表与系统提示词中。

### 3.2 参数 Schema(单工具 + action 分发)

| 参数 | 类型 | 适用 action | 说明 |
| ---- | ---- | ---- | ---- |
| `action` | enum(必填) | 全部 | `open` / `list` / `find` / `inspect` / `control` / `ocr` / `screenshot` |
| `query` | string | open*, find* | 应用/窗口查询词(中英文别名自动扩展,如 WeChat↔微信↔Weixin) |
| `app_name` | string | open | 启动用应用名/路径(缺省=query) |
| `bundle_id` | string | open | macOS Bundle ID(走 `open -b`) |
| `wait_seconds` | int 0-30 | open | 启动后等待窗口出现秒数(默认 10) |
| `filter` | string | list, inspect | 窗口标题/进程名子串过滤;控件名/角色子串过滤 |
| `match_mode` | enum | find | `exact` / `contains`(默认)/ `fuzzy` |
| `window_id` | string | inspect*, control*, ocr*, screenshot | open/list/find 返回的不透明窗口 id |
| `path` | string | control* | 控件路径(如 `/0/2/1`;`/` = 窗口本身,坐标动作照传) |
| `max_depth` | int 1-12 | inspect | 控件树遍历深度(默认 3) |
| `control_action` | enum | control* | click/invoke/focus/set_text/get_text/send_keys/scroll/scroll_to_visible/click_point/double_click_point/right_click_point/scroll_point/type_text/type_text_submit |
| `text` | string | control | set_text/send_keys/type_text* 文本;scroll 传方向行数(`down:3`) |
| `x`,`y` | int | control | 坐标动作必填(屏幕绝对坐标,取 ocr 返回的 screen_cx/screen_cy) |
| `region` | object | ocr, screenshot | `{x,y,width,height}` 窗口相对区域(物理像素) |
| `lang` | string | ocr | BCP-47 语言标签(默认系统语言) |
| `output_path` | string | screenshot | PNG 落盘路径(默认临时目录) |

(`*` = 该 action 的必填参数。)

### 3.3 action 语义(与原 7 工具一一对应)

| action | 原工具 | 语义 |
| ---- | ---- | ---- |
| `open` | WindowOpen | 启动/激活桌面应用并等待窗口出现;已运行则恢复前置(已前台跳过激活);返回 window_id + 权限状态 + next_action |
| `list` | WindowList | 枚举可见顶层窗口(macOS 走 CoreGraphics 无需授权);返回 id/title/进程/PID/bounds/cg_window_id |
| `find` | WindowFind | 按标题/进程名子串 + 模糊打分找单一最佳窗口,直接返回 window_id |
| `inspect` | WindowInspect | 枚举控件树(Windows UIA / macOS AX),双重截断(≤500 节点 / ≤32KB);空树自动追加路线引导 |
| `control` | WindowAction | 双路线操作:控件树路线(path 定位) + 视觉坐标路线(click_point / type_text_submit 等) |
| `ocr` | WindowOCR | 窗口 OCR,返回词块文本 + 窗口相对坐标 + 屏幕绝对坐标(视觉路线入口) |
| `screenshot` | WindowScreenshot | 截图落盘 PNG(Windows GDI / macOS CGWindow 原生优先、screencapture 降级) |

### 3.4 模块布局(遵循单文件 ≤1800 行拆分规范)

```
src/agent/tools/mcp_window_use/
  mod.rs       McpWindowUseTool(name/description/parameters/execute 分发)
               + 共享辅助(get_str/require_str/tool_err/run_blocking/树剪枝/
               查询别名扩展/driver_preflight/macOS AX 授权引导)
               + mcp_window_use_available() 平台门控
  query.rs     action=list / find(模糊打分:Damerau-Levenshtein + Unicode 归一化)
  open.rs      action=open(Windows 启动解析链:ShellExecuteW/开始菜单/安装路径探测;
               macOS open -a/-b;已在运行恢复前置)
  inspect.rs   action=inspect / control(控件树双重截断 + 空树路线引导 + ControlAction)
  vision.rs    action=ocr / screenshot(词块坐标换算 / CGWindow 原生截图降级链)
  tests.rs     单元测试(schema/dispatch/别名/打分/剪枝/平台门控)
```

服务实现层 `src/agent/window/`(驱动层)**原样保留**:WindowDriver trait、
Windows UIA 后端、macOS AX 后端、OCR/截图/输入底座、权限检测
(`check_platform_permissions` / `build_permission_failure_message`)、
`auto_launch_target`。仅把错误/引导文案中的旧工具名
(`WindowInspect` 等)改写为 `MCP_Window_Use(action=...)` 形态。

## 4. 系统提示词兼容(仅 macOS/Windows 注入)

### 4.1 SubAgent-Work(工具持有者)

`SystemPrompt::sub_agent_work()` 在 `mcp_window_use_available()` 为真时,
向 base 追加 `MCP_WINDOW_USE_PROMPT_SECTION`(桌面窗口操控使用说明),内容自
原 WindowUse 系统提示词精炼(约 90 行 → 约 40 行):

- 标准作业顺序:`open`(未启动)→ `find`/`list` → `inspect` 或 `ocr` → `control` → 复查;
- 双路线决策树(控件树为空 ⇢ 视觉路线 ocr + click_point/type_text_submit);
- 权限矩阵(macOS:辅助功能缺失 → 仅 list/find/open 可用;辅助功能✅+屏幕录制❌ →
  inspect/control 主路线可用,禁 ocr/screenshot/screencapture);
- 中文 UI 同义词表、Unicode 上标归一化、`type_text_submit` 原子发送范式;
- 安全红线(支付/删除/发送类按钮无把握不点击;禁止 Read PNG;3 轮无进展止损);
- Bash 降级路径(osascript/cliclick/pbcopy,SubAgent Bash 全量可用,无白名单)。

### 4.2 Yolo(分类层)

- 「读取/操作桌面软件窗口」任务**最低 medium** 的分类约束保留,措辞改为
  「由 Main-Work 拆解后交 SubAgent-Work 通过 MCP_Window_Use 工具执行」;
- `suggested_delegate` 推断:删除窗口操控关键词表与 `"windowuse"` 产出
  (web 命中 → `"webuse"` 不变;桌面 GUI 词不再产生建议,由 Main-Work 关键词推断接管)。

### 4.3 Main-Work(流程层)

- `delegate_to` 从三选一收缩为**二选一**:`subagent`(通用执行,含桌面窗口操控)
  / `webuse`(网页浏览器操控);
- 提示词明确:「读取/操作桌面软件窗口」类流程填 `subagent`,执行层 SubAgent-Work
  在 macOS/Windows 上持有 MCP_Window_Use 工具,验收标准允许 UI 状态描述;
- 委派推断(`main_work/delegate.rs`):桌面 GUI 强信号(微信/钉钉/控件树/UIA 等)
  → 强制 `SubAgent`(原 → WindowUse);web 命中 → WebUse 不变;
  宽松反序列化 `"windowuse"` 兼容映射为 `SubAgent`;
- 同应用连续 UI 操作链自动合并(`coalesce_same_app_window_workflows`)保留,
  判定条件由 `delegate_to==WindowUse` 改为 `delegate_to==SubAgent` + 桌面 GUI 强信号。

### 4.4 Quality-Check(质检层)

- 删除 WindowUse 专项诊断/重试指引分支;桌面窗口单元即 SubAgent 单元,
  走通用 trace 证据门;
- Main-Work 判定提示中 delegate_to 枚举同步收缩为 subagent/webuse。

## 8. 第 85 轮增量(2026-09-18,微信桌面自动化能力全面强化)

> 本章为第 85 轮增量设计。背景:本次 `laew --debug` 在「微信桌面自动聊天」任务下
> 3 次重试 928s 全部走降级,根因 = `open -a 微信` 在 macOS 上**不识别中文 DisplayName**,
> 直接报 `Unable to find application named '微信'`,exit 1;微信从未被工具成功启动,
> 后续 inspect/control 被 AX 权限全数拒绝,QC 卡在文本字段缺失。
>
> 完整方案:`tmpPlan/2026-09-18_01-MCP_Window_Use微信桌面自动化能力全面强化方案.md`。

### 8.1 macOS 启动解析链强化(解决 open -a 中文名失败的根因)

**根因**: macOS `open -a` 只匹配 CFBundleName,不匹配中文 DisplayName。微信的
`CFBundleName=WeChat` / `CFBundleDisplayName=微信` / `CFBundleIdentifier=com.tencent.xinWeChat`,
三者只有 `open -b com.tencent.xinWeChat` 才能可靠启动。本机实测:
- `open -a "微信"` → `Unable to find application named '微信'`,exit 1
- `open -b com.tencent.xinWeChat` → exit 0

**修复**(`src/agent/tools/mcp_window_use/open.rs`):
1. 新增 `KNOWN_BUNDLE_IDS` 常量(30+ 桌面应用),LLM 仍可只传 `query="微信"`,工具自动
   查表用 bundle id 启动;
2. 新增 `mdfind` 兜底:表里没命中 + open -a 失败时,Spotlight 查 .app 路径直接 `open <path>`;
3. 优先级链:**显式 bundle_id → 已知映射表 → open -a 别名遍历 → mdfind 兜底 → gtk-launch(Linux)**;
4. 错误文案统一为「建议传 bundle_id + system_profiler 查真实 bundle id + 手动启动再 activate」。

### 8.2 视觉路线全场景化(chat_send / chat_loop 复合 action)

新增两个复合 action,把当前需要 4~5 步工具调用 + 焦点竞态的事变成 1 步:

**`chat_send(window_id*, text*, click_point?, input_field_path?, submit_key?, verify?)`**:
- 一次调用完成「点击输入框 + Unicode 键入 + Enter + OCR 验证发送」;
- 自动按 `WindowCapability` 选路线(控件树 / 视觉坐标 / 焦点已对 / 降级提示);
- 微信/钉钉/飞书 发送消息首选。

### 9.2 osascript_fallback 路线(chat_send 第 5 路线)

**`src/agent/tools/mcp_window_use/chat.rs::run_chat_send`**

```rust
let route = if input_field_path.is_some() && cap.inspect_control {
    "ax"
} else if click_point.is_some() && cap.coordinate_input {
    "visual"
} else if cap.coordinate_input {
    "visual_no_input"
} else if cfg!(target_os = "macos")
    && crate::agent::window::check_platform_permissions().accessibility
{
    "osascript_fallback"  // 第 86 轮新增
} else {
    "degraded_no_op"
};
```

**实现**(走 BashTool 调 osascript,不走 driver):

```
1. osascript -e 'tell application "<App>" to activate'
   (window_id 推断 app_name:WeChat/DingTalk/Lark/QQ)
2. sleep 200ms(微信 runloop 拿焦点)
3. osascript -e 'tell application "System Events" to keystroke "<text>" as Unicode text'
   (中文/emoji 走 "as Unicode text" 不丢失)
4. sleep 120ms
5. osascript -e 'tell application "System Events" to key code 36' (Return)
```

**整链路不调用 window driver,完全不走截图/OCR**,所以 `screen_recording=false` 时仍可工作。

### 9.3 chat_log 强制写盘(chat_send / chat_loop)

**`src/agent/tools/mcp_window_use/chat.rs::resolve_chat_log_path`**

新增 `chat_log_path` 参数(可选),缺省 = `<工作目录>/llaew_chat_<unix_ts>.log`。

每次 send:
- 成功 → `{ts} [SEND] window_id={wid} text="..." route=... capability=... verified=...`
- 失败 → `{ts} [FAIL] window_id={wid} text="..." route=... stage=... error=...`

每次 reply 检测:
- 检测到 → `{ts} [RECV] window_id={wid} sample="..."`

chat_loop 结束:
- `{ts} [SUMMARY] rounds=N sent=K replies=M rate=R% elapsed=Ss`

IOException 不阻断主流程,仅 `tracing::warn`。

## 15. 第 100 轮 —— 双工作模式与 UI 快照治理(2026-09-21)

### 15.1 动机

人机共用一台机器是 laew 本地自动化的高频场景:SubAgent 一边执行桌面 GUI 操作,
用户一边用键盘鼠标切换窗口、回复消息。当前模式每个「发现阶段」要走 4~5 次 LLM
往返(capability_probe → find/open → inspect → ocr),每次往返 LLM 都要重拼参数、
写回 SubAgent 上下文、驱动层再次启动 —— Agent 操作太慢,与人工切窗相互干扰,
严重影响用户体验。

本轮目标 = **「先探索后批量执行」** 框架正式化:一次 `action=explore` 拿全 +
快照落盘,接一次 `action=run_sequence` 连续执行,中间不再拆。

### 15.2 双工作模式定义

#### 15.2.1 单步执行模式(Single-Step Mode)

LLM 一次工具调用只执行一个 action:capability_probe / find / inspect / ocr /
control / screenshot 等。适合:

- 未知页面首次探索;
- 高风险或不可逆操作(支付/发送/确认按钮);
- 调试与问题定位。

典型序列(共 4~5 次往返):

```
capability_probe → find/open → inspect → ocr → control → inspect 复查
```

#### 15.2.2 连续执行模式(Continuous Mode,**默认首选**)

由 `action=explore`(探索侧)与 `action=run_sequence`(执行侧)组合,2 次调用
完成整条窗口操控链:

```
explore (1 次) + run_sequence (1 次)
```

适合:

- 人机共用机器、任务链 ≥ 3 步;
- 用户会随时切窗;
- 自绘 UI(微信 4.x、QQ、Electron 等)需要 OCR 视觉路线;
- 长时多轮任务或保活。

方法论四步:
1. **探索**:`action=explore` 一次拿全(capability + 窗口 + 控件树 + 快照落盘 +
   actionable 摘要);
2. **规划**:LLM 在上下文里根据 `actionable[*].path` / `screen_cx` / `screen_cy`
   拼装 `run_sequence` 的 steps,异步 UI 处插 `wait_for_text`,关键节点插
   `assert_text`;
3. **执行**:`action=run_sequence` 一次连续执行(逐步焦点守护 + 三级错误策略
   + 落盘记录);
4. **复查**:按 `返回` 里的 steps 记录 + log_path 落盘对账;失败片段 re-explore 后
   新 run_sequence 补做。

#### 15.2.3 混合用法

| 场景 | 调用序列 |
|------|---------|
| 标准连续模式 | `explore` → `run_sequence` |
| 失败片段重做 | `explore` → `run_sequence` → `explore` → `run_sequence` |
| 长链多次连续 | `explore` → `run_sequence` × N (窗口稳定时连续多次 run_sequence) |
| 单点只读 | `inspect` / `ocr` 单步即可 |
| 发送类(不进 run_sequence) | `chat_send` / `chat_loop` |
| 调试与轨迹验证 | `input_batch`(≤10 步短复合,fail-fast) |

### 15.3 explore 复合 action 设计

#### 15.3.1 入参

| 参数 | 类型 | 必填 | 默认 | 说明 |
|------|------|------|------|------|
| `query` | string | 与 window_id 二选一 | — | 窗口查询词(自动 find,无则按白名单 open 启动) |
| `window_id` | string | 与 query 二选一 | — | 已知 window_id 直接探索(跳 find) |
| `max_depth` | int | 否 | 6 | 控件树遍历深度,连续模式放宽到 12 |
| `filter` | string | 否 | — | 控件名/角色子串过滤 |
| `include_ocr` | bool | 否 | true | 控件树为空/自绘 UI 时自动追加窗口 OCR |
| `snapshot_path` | string | 否 | `<工作目录>/laew_ui_snapshot_<unix_ts>.json` | 落盘路径;不传则自动生成 |
| `snapshot_label` | string | 否 | — | 快照短标签(写入文件头与 digest) |
| `wait_seconds` | int | 否 | 10 | query 模式下,等待窗口出现秒数 |
| `app_name` / `bundle_id` | string | 否 | — | 配合 query 时,目标应用启动参数 |

#### 15.3.2 执行步骤

```
1. capability 探测(走 cache,零 RTT 开销)
2. 解析 window_id:query 模式走 find → 找不到则按白名单 open 启动
3. inspect(window_id, max_depth, filter) → 全量控件树(无截断,落盘时)
4. has_actionable_controls 判定:
   ├─ 有可操作控件 → 仅走控件树路线
   └─ 空 + capability.ocr_screenshot_cgwindow → 自动追加 ocr_with_info 兜底
5. 构造 actionable 摘要(屏幕绝对坐标 = WindowInfo.bounds.origin + 控件 bounds 中心;
   若控件 name 与 OCR 词块匹配则取 OCR 中心更精确)
6. 构造 snapshot_id(随机 6 位)+ 写盘 snapshot_path(含 tree_full + ocr_blocks +
   window_info + capability)
7. 缓存到进程内 HashMap<snapshot_id, ControlNode>(供 @explore_ref 引用)
8. 返回 compact digest(目标 ≤ 80KB,超过建议加大 filter 或减小 max_depth)
```

### 15.4 snapshot 引用约定(被动引用)

`run_sequence` 的 step.path 不需新增 schema 字段。约定:

- `path: "/0/2/1"` 与 `path: "@explore_ref/snap_a1b2c3/0/2/1"` 都合法;
- 解析器:若 path 以 `@explore_ref/<id>/` 开头,剥前缀得到字面 path;若当前会话
  缓存命中 `id`,后续步骤可优化为跳过驱动 inspect(本期未实装优化,仅解析);
- miss 时按字面 path 走驱动(零回归);
- 若 `id` 在缓存中不存在,工具文案 next_action 引导先 action=explore。

### 15.5 Doom Loop 检测(工具层内置)

借鉴 opencode `DOOM_LOOP_THRESHOLD = 3`(L1516),用 ~50 行代码阻断
click→fail→click→fail 死循环:

### 16.2 新 action:read_text

```
read_text(window_id*, strategy?=auto|ax|clipboard, focus_point?,
          expect_contains?, timeout_ms?=0, max_chars?=8000)
```

- `strategy=auto`:AX 树有 web 内容(tree_has_web_content)→ ax;否则 clipboard;
- `clipboard`(macOS/Windows):ensure_frontmost → 点击 focus_point(默认窗口 (50%w,40%h)
  消息区,避开底部输入框)→ cmd+a → cmd+c → 300ms → pbpaste/Get-Clipboard → Escape 清选;
- 轮询:首轮完整流程,后续轮仅 cmd+c(选中态保持),1s 间隔直到命中 expect_contains 或超时;
- 截断策略:**保留尾部**(对话内容向底部追加,最新回复在末尾),`truncated=true` + 省略标注;
- 副作用明示:`clipboard_overwritten=true`(不自动恢复,图片类剪贴板无法可靠还原)。

### 16.3 观测性增强

- explore 快照/摘要新增 `ax_warmup_ms`(建树等待)、`ax_manual_accessibility_ack`
  (-1 未探测 / 0 应用回读 false / 1 true;false 提示该 Electron 构建可能忽略手动无障碍开关)、
  `tree_summary.web_content`;
- 窗口列表 AX 标题富化:无屏录时 kCGWindowName 恒为空(豆包实测列表全是 "title=(进程)"),
  AX 已授权时用 `ax_window_title_quiet(pid, idx)` 补全(不设 ManualAccessibility,
  2s TTL 缓存,≤40 窗口);
- TUI `[tool]` 摘要:explore 增 `web=0|1` / `warmup=Nms`;read_text 增
  `strategy=... chars=N contains=✓/✗`。

### 16.4 豆包任务的标准执行链(修复后)

```
explore(query=豆包)                     → open -b com.bot.pc.doubao / open .app 路径,
                                           10s 内匹配窗口(pid 制 window_id)
  └ self_drawn=true(红绿灯豁免后正确判定)→ next_action 强制引导:
chat_send(window_id, text=查询)          → pid 前置 + (0.50,0.90) 输入区点击 +
                                           System Events keystroke + Enter([SEND] 落盘)

```
