# LLM 交互死循环指纹检测与质检裁决 —— 设计与解决方案

> 状态：已实现
> 模块：`src/agent/dead_loop/`（检测）+ `src/agent/quality.rs`（裁决）
> 职责方：检测由进程内 `DeadLoopGuard` 完成；**根因归类与换路径裁决由
> `LsmAgentEmergentWork-Quality-Check` Agent 负责**（新增 `check_dead_loop` 通道）。

---

## 1. 背景与既有机制的盲区

`src/agent/loop_guard.rs`（第 120 轮 ReAct 循环守卫）解决的是**工具级**无进展：
判定键 = `工具名 + 参数稳定 JSON + 结果摘要`，连续 3~4 次即止损。

它有三条结构性盲区，本方案逐一覆盖：

| 盲区 | 现象 | 为什么 LoopGuard 抓不到 |
| ---- | ---- | ---------------------- |
| **A. 换序打转** | 模型每轮调用**不同**工具（`Read(a)`→`Read(b)`→`Read(a)`→`Read(b)`…），工具集在轮转 | `last_key` 只比**相邻**两轮，换动作即重置链，`max_repeats` 恒为 1 |
| **B. 换工具打转** | `Grep(pattern=X)` → `Bash(grep X .)` → `Read(a.rs)` → 回到 `Grep(X)`，表面动作各异实则同一目标 | 同上，链被反复打断 |
| **C. 上下文自锁** | 模型反复**改写同一份输出**（重述同一段计划、重新提交同一份 JSON），工具调用极少甚至没有 | 没有工具调用就没有 `observe`，`doom_loop_repeats` 恒为 0 |

三条盲区共同的根因是：**判定键建立在「动作」上，而死循环的本质发生在
「模型看到的输入状态 ↔ 模型产出的输出」这一层**。因此需要一个 LLM 交互级
的指纹守卫。

同时，止损之后「为什么循环、该怎么换路径」目前是 `abort_fallback_text` 里
一句固定的机械文案（"请上游据此换路径重试"），换路径建议实际由 LLM QC 自由
发挥，缺乏结构化的根因归类与强制约束。

## 2. 总体方案

```
                        ┌──────────────────────────────────────┐
  每轮 LLM 调用前  ───▶  │  DeadLoopGuard::begin_turn()         │
   投影上下文 → 集合摘要   │   · 抽出「模型已见信息集合」        │
                        │   · 折叠成 in_hash (FNV-1a 64)        │
                        └──────────────────────────────────────┘
                        ┌──────────────────────────────────────┐
  每轮 LLM 响应后  ───▶  │  DeadLoopGuard::end_turn()           │
                        │   · text+thinking+tool_calls → out_hash│
                        │   · tool 名+参数 → action_hash         │
                        │   · 写入哈希索引表 + 轮次序列         │
                        │   · 相邻两轮输出逐字节重复 → 硬自锁   │
                        │   · 尾部周期扫描 → 小循环 / 大循环    │
                        │   · 低新颖度窗口 → 大循环             │
                        │   · 裁决 Nudge / Grace / Abort         │
                        └──────────────────────────────────────┘
                                          │ Abort
                                          ▼
                        ┌──────────────────────────────────────┐
                        │ ExecutionTrace.dead_loop = 诊断        │
                        │  failure_signals += dead_loop:*        │
                        └──────────────────────────────────────┘
                                          ▼
                        ┌──────────────────────────────────────┐
   Quality-Check Agent  │ ① prompt 死循环硬门（LLM 侧）          │
   （裁决方）           │ ② gate_report_on_trace 机械门（进程侧）│
                        │ ③ check_dead_loop 根因裁决通道（新）  │
                        └──────────────────────────────────────┘
```

## 3. 数据结构（内存方案）

### 3.1 轮次指纹 `LlmTurnFingerprint`

```rust
pub struct LlmTurnFingerprint {
    pub iter: usize,       // 第几轮（从 0 起）
    pub in_hash: u64,      // 输入状态指纹
    pub out_hash: u64,     // 输出全文指纹（text+thinking+tool_calls）
    pub action_hash: u64,  // 输出动作指纹（工具名+参数，忽略措辞）
    pub in_bytes: usize,   // 上下文字符数（诊断用）
    pub out_bytes: usize,
    pub in_preview: String,  // ≤160 字符，人类可读
    pub out_preview: String, // ≤160 字符，人类可读
    pub tools: Vec<String>,  // 本轮调用的工具名（诊断用）
}
```

### 3.2 哈希索引表 `FingerprintIndex`

哈希数据表按 `hash → 出现轮次` 建两本账（输入 / 输出），供 O(1) 重复计数与
证据回溯：

```rust
pub struct FingerprintIndex {
    in_seen:  HashMap<u64, Vec<usize>>,  // in_hash  → 轮次下标
    out_seen: HashMap<u64, Vec<usize>>,  // out_hash → 轮次下标
    digests:  BTreeSet<String>,          // 「模型已见信息集合」摘要（有序去重）
}
```

**内存边界**（无外部依赖、进程内分配、单元结束即释放）：

| 结构 | 上限 | 说明 |
| ---- | ---- | ---- |
| `steps: Vec<LlmTurnFingerprint>` | `MAX_STEPS = 64` | 超出 FIFO 丢弃最早（迭代上限 32，64 有两倍余量） |
| `digests: BTreeSet<String>` | `MAX_DIGESTS = 512` | 每条摘要 16 hex 字符，最坏 ~24 KB/单元 |
| `in_seen / out_seen` | ≤ 64 项/本 | 每项一个 `Vec<usize>`，O(轮数) |
| 合计 | ≈ 30 KB/单元 | 并行单元数 ≤ 3，总量 < 100 KB |

生命周期 = 一次 `run_session_body`（与 `LoopGuard` / `ExecutionTrace` 同域），
**不跨单元、不落库、不落盘**。

### 3.3 哈希函数

自实现 **FNV-1a 64**，不用 `DefaultHasher`：`DefaultHasher` 官方明确不保证跨
Rust 版本稳定，指纹要能写进 trace 供事后对账，必须是确定性算法。

```rust
const FNV_OFFSET: u64 = 0xcbf29ce484222325;
const FNV_PRIME:  u64 = 0x100000001b3;
```

## 4. 输入指纹：`in_hash` 的投影设计（本方案的关键）

### 4.1 为什么不能直接 hash 整个上下文

会话上下文每轮都在增长（assistant 消息 + tool_result + 控制消息），
整段 hash **永远不同**，重复检测彻底失效。这是朴素方案的第一个坑。

### 4.2 为什么不能用「尾部 N 条消息」

尾部窗口在死循环里**每轮都在平移**：第 k 轮看到 `[…, A, R, A, R]`，第 k+1 轮
看到 `[…, A, R, A, R, A]`，窗口内容整体错位，`in_hash` 同样恒不相同。
这是朴素方案的第二个坑（也解释了为什么 LoopGuard 的相邻比较够用、
而跨轮比较不够）。

### 4.3 采用的投影：**「模型已见信息集合」**

```
digests = { fnv(归一化后的每条消息) }        // 有序去重集合
in_hash = FNV( agent_tag ‖ forced_tool ‖ sorted(digests) )
```

语义：**`in_hash` 只在「模型看到了此前没见过的新信息」时才变化**。

- 健康轮次：assistant 消息 + tool 结果几乎必然是新内容 → 集合增长 → `in_hash` 变。
- 死循环：模型重复产出同一段文字 / 同一组 tool_use，工具返回同一份结果 →
  集合零增长 → **`in_hash` 冻结**。

集合**排序后**折叠，因此对消息顺序平移与重复插入免疫（正是 4.2 的病根）。

### 4.4 三条归一化规则

1. **空白归一**：连续空白折叠为单空格，首尾去空白。防止格式抖动打断指纹。
2. **长度取样**：每条消息内容取前 `IN_MSG_CHARS = 320` 字符参与哈希，
   尾部差异（时间戳、耗时）不参与判定。尾部差异不参与判定。
3. **控制消息豁免**：文本以 `<<<LAEW:` 开头的消息（项目上下文注入、会话历史、
   附件块、以及本守卫自己注入的 nudge/grace）**不计入集合**。
   否则守卫每推一条提醒就刷新一次状态哈希，**把死循环伪装成有进展**——
   自反馈污染，是这类守卫最容易踩的坑。

## 5. 检测算法

### 5.1 输出侧三层指纹

| 指纹 | 覆盖内容 | 用途 |
| ---- | -------- | ---- |
| `out_hash` | `text` + `thinking` + `tool_calls(名+参数稳定 JSON)` | 完全相同 → 硬自锁 |
| `action_hash` | 仅 `tool_calls` 的 `(名, 参数)` 排序折叠 | 措辞在变、动作没变 |
| `in_hash` | §4.3 的信息集合 | 上下文有没有新信息 |

### 5.2 硬自锁的最短路径：相邻两轮输出逐字节重复

键周期扫描（§5.3）要求 **(输入状态, 输出) 二元组**整体重复。但「上下文还在
长、模型却一字不差地又交回同一份响应」本身就已经是铁证 —— 上下文给了它**更多**
信息，它却交回同一个答案。键扫描要等到信息集合冻结（多轮之后）才响，
这里提前一轮抓到：连续两轮 `out_hash` 相等即判 `period = 1` 的 `ShortCycle`。

间隔约束：**只认相邻两轮**（gap = 1）。相隔 2 轮以上的重复不归本判据 ——
那属于「回到某个先前状态」，应交给键序列周期扫描按真实周期定级，不在这里
草率按 `period=1` 定性。

### 5.3 小循环 / 大循环：尾部周期扫描

把轮次序列映射为键序列 `k_i = (in_hash, out_hash)`，自末尾反扫求**尾部最长的
p-周期后缀**：

```
for p in 1..=n/2:
    streak = 从末尾往回连续满足 k[i] == k[i-p] 的步数
    suffix_len = p + streak
    reps = suffix_len / p
    首个 reps ≥ 门槛(p) 的 p 即最小周期
```

| 周期 | 分类 | 语义 |
| ---- | ---- | ---- |
| `p = 1` | `ShortCycle` | 硬自锁：输入状态与输出逐字节相同 |
| `2 ≤ p ≤ 4` | `ShortCycle` | 小循环：2~4 轮一圈的打转（最常见的「A→B→A→B」） |
| `p ≥ 5` | `LongCycle` | 大循环：5 轮以上一圈的长周期打转 |

**重复次数门槛**（`reps_threshold`）：

| 周期 | 门槛 | 理由 |
| ---- | ---- | ---- |
| `p = 1` | 2 圈 | 上下文在增长而输出逐字节相同，本身就是铁证 |
| `2 ≤ p ≤ 4` | 3 圈 | 2 圈可能只是正常的二次确认 |
| `p ≥ 5` | 2 圈 | 长周期跑满三圈必然先超预算，届时止损已无意义 |

**为什么不能用「整串最小周期」**（KMP `n - π[n-1]` 那一套）：整串最小周期要求
**从头到尾**都满足 `k[i] == k[i-p]`，一旦序列前面有一段瞬态就恒判不出周期 ——
而首轮状态天然与后续不同（信息集合从 1 条长到 3 条），典型硬自锁序列
`[(H0,o), (H1,o), (H1,o), (H1,o), …]` 的整串最小周期恒为「无循环」，
**恰恰是最该抓的形态抓不到**。改为尾部反扫只要求稳态部分构成循环，
瞬态前缀不再遮蔽循环。

代价 O(n²/2)（n ≤ 64 时约两千次比较），可忽略。

### 5.4 大循环第二形态：低新颖度窗口

键周期扫描要求输出**逐字节相同**才能构成周期。现实中的大循环常是「模型换着
措辞重复同一件事」，此时 `out_hash` 恒不相同，周期扫描无能为力。

补充判定——**低新颖度窗口**（`LowNovelty`）：

```
window  = 最近 LONG_WINDOW(默认 12) 轮
distinct_in = window 内不同 in_hash 的个数
frozen   = window 内 in_hash 与上一轮相同的轮数

命中 ⟺ window ≥ LONG_WINDOW
    ∧ distinct_in ≤ max(2, window / 3)
    ∧ frozen      ≥ LOW_NOVELTY_MIN_REPEATS(默认 6)
```

**为什么这个判据是安全的**（关键论证）：由 §4.3 的构造，`in_hash` 相同
⟺ 本轮上下文零新增消息摘要。健康轮次每轮必然新增 assistant 消息与工具结果，
`distinct_in` 恒等于 `window`；只有真正打转时 `in_hash` 才会冻结。
`LONG_WINDOW=12` 下要求 `distinct_in ≤ 4`，即 12 轮里至少 8 轮上下文毫无
新增——**误伤面极小**。

对比之下，若改用「`action_hash` 重复率高」做判据会**误杀编译修复场景**
（`Bash cargo check` 连跑 6 次修 6 个编译错，每次输出都不同，是健康工作）。
本方案因此**明确不用** action 重复率做长窗口判据，action_hash 仅用于
诊断取证。

### 5.5 裁决阶梯

沿用 `LoopGuard` 的三档结构，保证两套守卫行为一致、可预测：

| 裁决 | 触发 | 注入方式 | 语义 |
| ---- | ---- | -------- | ---- |
| `Progress` | 未命中 | — | 有进展 |
| `Nudge(text)` | 小循环首次命中 | 下一轮经 `meta.runtime_tail` 注入 | 软提醒，**不终止**（不污染上下文前缀，保 prompt cache） |
| `Grace(text)` | 小循环第二次命中；**大循环首次命中即命中** | **本轮结束后作为 user 消息推入上下文** | 强提醒，保证送达 LLM（对齐第 25 轮 F9 教训） |
| `Abort(diag)` | 宽限轮已用后再次命中 | — | 终止本单元，诊断写入 trace |

**检测顺序即证据强度**：相邻两轮输出逐字节重复（§5.2，最短铁证）> 键序列
周期扫描（§5.3，最精确的周期）> 长窗口低新颖度（§5.4，最宽容，覆盖换措辞
不换信息的形态）。

**大循环跳过 Nudge 直达 Grace**：能在 12 轮窗口上命中的单元，预算本就所剩
无几，此时「礼貌提醒一轮」只是白白烧掉最后一轮。

同一条循环链（`kind + period` 为签名）只 Nudge 一次；`Grace` 会话级一次
（对齐 `LoopGuard::abort_grace_used`）；换签名后重新计。

### 5.6 止损后的收尾语义

与 `LoopGuard` 完全一致，不发明第二套：

- **已有工具产出** → 优雅收尾，交 QC（真实成果不能被硬失败吞掉）；
- **全程零产出** → `Err(...)`，走既有 Yolo 失败回流。

### 5.7 与工具级守卫的优先级：工具级优先

两套守卫可以同轮命中，此时**以工具级 `doom_abort` 为准**：

- 工具级结论证据更硬（同动作 + 同结果，逐项可复算），LLM 级只给出形态与周期；
- 本守卫的定位是**兜底** —— 只在工具级相邻比较结构上抓不到的形态上生效。

配套的一条工程约束：命中 LLM 级止损时**不跳过本轮工具调用**。跳过会让
`LoopGuard` 拿不到本轮 Observation，从而丢掉那条更硬的证据、把诊断退化成只有
形态与周期。代价是多跑一轮（模型已经发出这些调用了），而**终止决策仍在同一轮
做出**，不多烧一轮预算 —— 换回精确的根因归因，这笔交换是划算的。

## 6. 诊断结构 `DeadLoopDiagnosis`

```rust
pub struct DeadLoopDiagnosis {
    pub kind: LoopKind,             // ShortCycle | LongCycle | LowNovelty
    pub period: Option<usize>,      // 最小周期（LowNovelty 为 None）
    pub reps: usize,                // 重复次数
    pub turns: usize,               // 参与判定的总轮数
    pub distinct_inputs: usize,     // 窗口内不同 in_hash 数
    pub distinct_outputs: usize,    // 全会话不同 out_hash 数
    pub cycle_turns: Vec<usize>,    // 构成循环的轮次下标
    pub sample_in: String,          // 输入预览
    pub sample_out: String,         // 输出预览
    pub tools: Vec<String>,         // 循环中反复出现的工具
}
```

写入 `ExecutionTrace.dead_loop`（`#[serde(default)]`，旧 trace 反序列化为
`None`），并进 `failure_signals`：

- `dead_loop:short_cycle(p=2,reps=3)` / `dead_loop:long_cycle(p=7,reps=2)`
- `dead_loop:low_novelty(distinct_in=3/14)`

`render_prompt()` 追加一行 `- dead_loop: ...` + 循环内工具摘要，QC 一眼可见。

## 7. Quality-Check 侧的裁决（本方案的第二半）

用户需求明确要求「检测与问题解决交给 `LsmAgentEmergentWork-Quality-Check`
Agent 实现」。落地为**三道互补的关卡**：

### 7.1 关卡① · 机械门（进程侧，不可被 LLM 覆盖）

`quality.rs::gate_report_on_trace` 现有职责就是「用不可伪造的执行轨迹约束
LLM 的 pass 结论」。新增一条同级硬门：

```
trace.dead_loop.is_some()  ∧  report.verdict == Pass
    ⟹ 降级为 Fail(retryable = true)，evidence 写入完整诊断
```

与 `early_terminate` / `high_error_rate` 同级。理由与该函数既有设计一致：
**LLM QC 是语义判断，但不能覆盖进程级事实**。

### 7.2 关卡② · 提示词硬门（LLM 侧）

`build_unit_qc_prompt` 在 `trace.dead_loop` 存在时注入「死循环硬门」段：

- 命中死循环诊断的单元**一律判 Fail**，无论终答文本写得多漂亮；
- 必须按固定枚举归类根因（供下游程序化消费）：
  `same_action`（同一动作原地打转）/ `same_target`（目标不可达）/
  `context_stuck`（上下文自锁）/ `budget_starved`（预算被无效动作烧光）；
- `suggestion` 必须写出**具体的换路径动作**（换工具 / 换参数 / 换目标 /
  直接收口），禁止只写「请重试」。

### 7.3 关卡③ · 根因裁决通道 `QualityRunner::check_dead_loop`

新增轻量入口，只在 `trace.dead_loop.is_some()` 时调用（每次多一次 LLM 调用，
但只在已被止损的单元上发生，相对已烧掉的预算可忽略）：

- 输入：诊断结构 + 单元职责 + 期望输出 + 实际输出 + 轨迹摘要；
- 输出：`LoopResolution { root_cause, retry_path, retryable, rationale }`；
- 在 `run_wf_unit` 里与常规 QC 结论**合并**：`retryable` 取或，`suggestion`
  前置拼接 `retry_path`，作为下一轮**局部重试**的 hint 注入。

于是「止损之后怎么走」这条关键决策从固定机械文案变成 **QC 结构化裁决**，
闭环回到编排器的局部重试 → 预算耗尽 → 档位级重试 → Yolo 回流。

### 7.4 根因枚举

| 枚举 | 含义 | 典型换路径 |
| ---- | ---- | ---------- |
| `same_action` | 同一动作原地打转 | 换工具 / 换参数 / 换路径 |
| `same_target` | 目标不可达（页面/接口/权限） | 换目标层级（列表页→详情页）、换数据来源 |
| `context_stuck` | 上下文自锁，模型在复述 | 压缩上下文后重新给指令、直接收口 |
| `budget_starved` | 预算被无效动作烧光但方向正确 | 砍步骤、只做最关键一件事 |

## 8. 开关

| 环境变量 | 取值 | 行为 |
| -------- | ---- | ---- |
| `LAEW_DEAD_LOOP` | `off`/`0`/`false`/`no` | 关闭死循环检测裁决 + QC 根因裁决通道（默认开启）。**统计仍保留**（可观测性不丢） |
| `LAEW_DEAD_LOOP_LONG_WINDOW` | 正整数（默认 `12`） | 大循环低新颖度窗口长度 |

关闭时行为与「未引入本模块」逐字节一致（检测照跑、只不裁决、不注入提醒），
保证出问题时可一键回退。

## 9. 与既有机制的分工（不重复造轮子）

| 机制 | 判定层 | 键 | 覆盖 |
| ---- | ------ | -- | ---- |
| `REPEATED_FAILURE_THRESHOLD` | 工具 | 工具+参数 | 连续**失败**同动作 |
| `NO_TEXT_CONVERGE_THRESHOLD` | 轮次 | — | 只 tool_use 无文本 |
| `NO_TOOL_USE_THRESHOLD` | 轮次 | — | 空跑 |
| `loop_guard::LoopGuard` | 工具 | 工具+参数+结果 | **相邻**同动作同结果 |
| **`dead_loop::DeadLoopGuard`（本方案）** | **LLM 交互** | **信息集合 + 输出全量** | **跨轮次任意周期循环、换序打转、换工具打转、上下文自锁、低新颖度** |

三者**串联不互斥**：LoopGuard 先在工具层拦最常见的「同动作同结果」，
DeadLoopGuard 在更上层兜住 LoopGuard 结构上抓不到的形态。止损路径、
宽限轮语义、trace 字段命名风格全部对齐 LoopGuard，降低认知负担。

## 10. 测试矩阵

**单测**（`src/agent/dead_loop/tests.rs`，`cargo test --lib`）：

1. 健康多轮序列零误报（每轮新信息 → `in_hash` 每轮变 → 恒 `Progress`）；
2. `p=1` 硬自锁在第 2 次命中 Nudge；
3. `p=2` 小循环 `A→B→A→B` 命中且 period 判为 2；
4. `p=3 / p=4` 边界；`p=5` 归入 LongCycle；
5. 低新颖度窗口命中 / 差一轮不命中的边界；
6. **编译修复场景不误伤**（`Bash cargo check` 连跑 6 次、输出各不相同 →
   `in_hash` 每轮变 → 恒 `Progress`）——这是本方案最关键的反误伤回归；
7. 控制消息豁免：注入 `<<<LAEW:` 提醒后 `in_hash` 不变（不自反馈污染）；
8. 空白归一化：`"a\n b"` 与 `"a  b"` 指纹相同；
9. FNV-1a 确定性：同输入两次哈希一致、已知向量正确；
10. 大循环跳过 Nudge 直达 Grace；Grace 后再命中 → Abort；
11. 关闭开关后恒 `Progress` 但统计不丢；
12. 索引表与 `steps` 上限截断行为，绝对轮次号不被裁剪影响；
13. 相邻两轮输出逐字节重复（§5.2）提前一轮命中，且只认 gap=1；
14. **React 循环级用例**（`src/agent/react_tests.rs`）：构造 `A→B→A→B` 换序打转
    的 mock LLM，断言 `LoopGuard` 恒不命中的形态被本守卫在跑满预算前止损，
    且 `trace.dead_loop.period == 2`、`failure_signals` 含 `dead_loop:`。
