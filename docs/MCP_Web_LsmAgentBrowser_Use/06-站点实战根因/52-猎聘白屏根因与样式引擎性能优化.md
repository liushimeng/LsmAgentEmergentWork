## 二、根因 1:猎聘 `/zhaopin/` 白屏 = 站点自身的全视口加载遮罩

对 dump 的 1.69 MB HTML 做离线重排,显示列表 111 项,最后一项:

```
#106 bg(Solid([255,255,255],255)) x=0 y=0 w=1920 h=1080 op=1.00 z=9999 layer=1 clip=None
```

对应站点内联样式表原文:

```css
.searchjobs-spin-loading-box{background:#fff;bottom:0;height:100vh;left:0;
  position:absolute;right:0;top:0;width:100%;z-index:9999}
```

DOM 位置:`#lp-search-job-box > div.ant-spin-nested-loading.searchjobs-spin-loading-box`
(站点 JS 动态创建,带 `data-lsm-id`)。该元素**无定位祖先** → 包含块 = 初始包含块,
`inset:0 + 100vh/100%` 铺满视口,`z-index:9999` 盖住包括登录弹层在内的一切。

**遮罩为什么不消失**:职位列表接口在内核里持续返回业务错误体
`{"flag":0,"code":"-1400","msg":"出错了(400)!"}`(未登录/风控),站点自身的
loading→error 收尾逻辑走不到,遮罩常驻。控制台 35 条事件里 20+ 条是同一个 400 的
`Unhandled promise rejection`,另有 `脚本管线达到墙钟预算(240000ms)` 与 3 次
`JS 执行超时(线程预算耗尽,含宽限)`。

> 与 `40-…md`「E4b z=9999 白遮罩 = 站点自身的 loading 层」同结论。
> **不是内核渲染故障**,内核按 CSS 忠实绘制了这层遮罩。

## 四、根因 3(真正的内核 bug):样式引擎 O(节点数 × 规则数)

`StyleEngine::computed`(`src/agent/browser/style/mod.rs`)对**每个元素**遍历
**全部 CSS 规则**,逐选择器调 `selector::matches` → `match_compound`(每次
`el.attributes.borrow()` 借 RefCell + `class.split_whitespace()` 重新分配)。

实测:

| 场景 | 优化前 |
| --- | --- |
| 离线重排猎聘 `/zhaopin/`(1.69 MB HTML / 225 盒 / 603 节点) | **56 s** |
| 真站探针 `page_health`(快照再算一遍样式) | **> 5 min 未结束** |
| 猎聘首页(2.09 MB HTML)截图 | **> 11 min 未结束** |

猎聘页内联样式表 1.2 万条规则 × 上千节点 = 数千万次选择器匹配。**这是「卡住 /
显示失败 / 任务不及预期」的直接放大器** —— 即使站点没有风控,内核也会在布局与快照
阶段耗光脚本预算与工具超时。

## 五、修复

### 5.1 主体预过滤(性能,通用)

`selector::matches` 的第一件事就是 `match_compound(node, subject)`,而 `match_compound`
的前三项检查恰是 tag / id / class。抽成预计算特征 `selector::SubjectHint`:

- `Rule` 构造时保存 `subjects: Vec<SubjectHint>`(与 `selectors` 平行);
- `computed` 每节点只取一次 `id` / `class`(一次 RefCell 借、一次切分),
  `rule.subjects.iter().any(|h| !h.rejects(tag, id, classes))` 全组否决即跳过整条规则。

**语义约束(关键)**:只能用于否定 —— `rejects=true` 时 `match_compound` 必然失败
(tag 不符 / id 不符 / class 不全含),故整条规则可安全跳过;`false` 时仍走完整
`matches`(属性、伪类、组合符尚未检查)。**不会引入假否决**,由单测
`主体预过滤不误否任何会命中的规则` 逐节点 × 逐规则对照 `full_match ⇒ hint_pass` 锁死。

效果:猎聘 `/zhaopin/` 离线重排 **55.98 s → 12.30 s(4.5×)**,显示列表**逐字节一致**。

### 5.2 `page_health` 增加 `loading_overlay` 诊断(可观测,通用)

现状:`blank_page=false` + 「页面已渲染出部分内容」——**误导**:页面其实被盖得严严实实,
Agent 会以为渲染故障而反复截图重试。

新增 `detect_loading_overlay(display, vp_w, vp_h)`:识别「不透明背景 + 铺满视口
(≥95%)+ **z 严格高于全部内容项**」的项。最后一条是关键的反假阳性约束 ——
根画布背景恒为「铺满视口 + 不透明 + `z=i64::MIN`」,整页 hero 背景与文字同层,
二者都不该被判成遮罩(实测猎聘页内容最高 z=1000,遮罩 z=9999,判定成立)。
`page_health` 输出:

```json
"loading_overlay": {
  "present": true, "z": 9999, "is_topmost": true, "covers_viewport": true,
  "note": "页面被站点自身的加载/风控遮罩整幅覆盖,下方内容不可见;这是站点状态而非内核渲染故障"
}
```

`diagnosis` / `hint` 同步改口,引导 Agent 去看 `inspect(console)` 与
`inspect(network)`(定位站点接口错误),而不是对着白屏反复截图。

### 5.3 不做什么(如实声明)

- **不做任何绕 WAF / 伪造登录态的尝试**:猎聘 400 与 BOSS 安全验证都是站点风控层
  (与 `40-…md` 第四节、`43-…md` 一致)。内核侧职责是**如实渲染 + 如实上报**。
- `hm.baidu.com` 本机不可达属网络环境,不在代码修复范围。

## 七、边界(未解决,如实声明)

- 主体预过滤只能否掉「主体 tag/id/class 不符」的规则;**纯属性/伪类主体**
  (如 `span[data-k="1"]`)无法被否决,这类样式表下的加速比会明显降低;
- 猎聘遮罩的**根因**(站点接口 400)未解,属站点风控层;本轮只让内核**如实上报**;
- `api.geetest.com` 带超长 `w=` 时的偶发取回失败未定位到具体原因(不带 `w=` 稳定 200)。
