# WorkFlow Agent（第 10 角色）设计与解决方案

## 1. 背景与目标

### 1.1 问题陈述

当前 laew 已具备 9 角色多 Agent 架构（Yolo / Plan / Main-Work / SubAgent-Work / Quality-Check / SessionContext / Debug / Compact / WindowUse），但面对**超大型复杂任务**（如「重构整个项目的错误处理架构」「为 50 个模块各写 10 个单测」）和**海量高并发任务**（如「批量分析 1000 个文件的代码质量」）时，存在以下缺口：

| 缺口 | 描述 |
|------|------|
| **无 Goal 状态机** | 当前任务是一次性编排，缺乏事务性生命周期追踪（Pursuing/Blocked/Satisfied 等状态转换） |
| **无 Agent Squad** | SubAgent 执行单元是单兵作战，无法组建「小队」协作完成复杂子工程 |
| **无自适应循环** | 失败回流仅回到 Yolo，无法在执行层内部做自适应修复循环 |
| **无批量任务通道** | 高并发场景（1000 个文件分析）无专用调度通道，串行执行效率极低 |
| **无 WorkFlow Agent** | 缺少一个专门负责「工作流全生命周期管理」的独立角色 |

### 1.2 设计目标

新增 **WorkFlow Agent**（`LsmAgentEmergentWork-WorkFlow`）作为第 10 角色，实现：

1. **自动感知**：识别任务规模与复杂度，决定是否需要 WorkFlow 编排
2. **自动加载**：加载历史 WorkFlow 模板、Goal 状态、Agent-Memory 经验
3. **自动规划**：生成 Goal 树（Phase → WorkFlow → Task 三层分解）
4. **自动执行**：指挥多个 Agent Squad 并行/串行执行，自适应重试
5. **自动质量评价**：每个 Phase/Squad/Task 完成后自动 QC
6. **循环处理**：未达目标时自动分析原因、修复、重执行，直到完成

## 3. Goal 状态机设计

### 3.1 Goal 状态定义

借鉴 atomcode（5 态）与 deepseek-harness（4 态 + CAS 事件溯源）：

```rust
pub enum GoalState {
    Pending,      // 等待执行
    Pursuing,     // 执行中
    Blocked,      // 被阻塞（依赖未满足 / 资源不可用）
    Paused,       // 暂停（等待用户输入 / 时间耗尽）
    Satisfied,    // 目标达成
    Failed,       // 终态失败（超过重试上限）
}
```

### 3.2 Goal 结构

```rust
pub struct Goal {
    pub id: String,                    // 全局唯一 Goal ID
    pub parent_id: Option<String>,     // 父 Goal（支持嵌套）
    pub title: String,                 // Goal 标题
    pub description: String,           // 详细描述
    pub state: GoalState,              // 当前状态
    pub priority: u8,                  // 优先级 1-10
    pub dependencies: Vec<String>,     // 依赖的 Goal ID 列表
    pub acceptance_criteria: Vec<String>, // 验收标准
    pub subgoals: Vec<Goal>,           // 子 Goal
    pub retry_count: usize,            // 已重试次数
    pub max_retries: usize,            // 最大重试次数
    pub created_at: String,
    pub updated_at: String,
    pub completed_at: Option<String>,
}
```

### 3.3 状态转换图

```
                    ┌──────────┐
                    │ Pending  │
                    └────┬─────┘
                         │ start()
                         ▼
                    ┌──────────┐
            ┌──────│ Pursuing │──────┐
            │      └──────────┘      │
            │ done()    │    block()  │
            ▼           │    pause()   │
     ┌──────────┐       ▼             ▼
     │Satisfied │   ┌────────┐  ┌────────┐
     └──────────┘   │ Blocked│  │ Paused │
                    └───┬────┘  └───┬────┘
                        │ unblock() │ resume()
                        └─────┬─────┘
                              │
                              ▼
                         Pursuing (resume)

            fail (over retry limit)
                    ┌──────────┐
                    │  Failed  │
                    └──────────┘
```

### 3.4 CAS 状态转换

每个状态转换都是 Compare-And-Swap 原子操作，防止并发 Squad 写入冲突：

```rust
impl Goal {
    pub fn transition(&mut self, from: GoalState, to: GoalState) -> Result<()> {
        if self.state == from {
            self.state = to;
            self.updated_at = now();
            Ok(())
        } else {
            Err(AgentError::StateTransition {
                goal_id: self.id.clone(),
                from: self.state.clone(),
                attempted_to: to.clone(),
            })
        }
    }
}
```

## 4. Agent Squad 调度设计

### 4.1 Squad 概念

Squad（小队）= 一组 SubAgent-Work 实例的集合，共同完成一个 Phase 内的并行任务。

```rust
pub struct Squad {
    pub id: String,
    pub phase_id: String,
    pub members: Vec<SquadMember>,
    pub strategy: SquadStrategy,
    pub max_concurrent: usize,       // 并发上限（默认 5）
    pub timeout_secs: u64,           // 整体超时
}

pub struct SquadMember {
    pub member_id: String,
    pub role: SquadRole,             // Leader / Worker / Verifier
    pub task: String,
    pub expected_output: String,
    pub status: MemberStatus,
    pub result: Option<String>,
}

pub enum SquadStrategy {
    AllMustPass,       // 全部通过才算完成
    Quorum(usize),     // 多数通过即可
    LeaderDecides,     // Leader 汇总判定
}
```

### 4.2 调度算法

借鉴 atomcode Semaphore(3) + openclaw Swarm 调度：

```rust
pub struct SquadDispatcher {
    semaphore: Arc<Semaphore>,        // 并发控制
    max_squads: usize,                // 最大并行 Squad 数
    max_members_per_squad: usize,     // 每 Squad 最大成员数
}

impl SquadDispatcher {
    pub async fn dispatch(&self, squad: &Squad) -> Result<SquadResult> {
        let _permit = self.semaphore.acquire().await?;
        let mut handles = vec![];
        for member in &squad.members {
            let handle = tokio::spawn(async move {
                self.execute_member(member).await
            });
            handles.push(handle);
        }
        let results = join_all(handles).await;
        self.aggregate_results(squad, results).await
    }
}
```

### 4.3 高并发通道

针对海量任务（1000+ 文件分析），提供专用 Batch 通道：

```rust
pub struct BatchChannel {
    chunk_size: usize,           // 每批处理量
    max_parallel_batches: usize, // 最大并行批次数
    retry_queue: Vec<String>,    // 失败重试队列
}

impl BatchChannel {
    pub async fn process<T: BatchTask>(&self, tasks: Vec<T>) -> BatchResult {
        let chunks: Vec<_> = tasks.chunks(self.chunk_size).collect();
        let mut results = BatchResult::default();
        for batch in chunks.chunks(self.max_parallel_batches) {
            let batch_results = join_all(
                batch.iter().map(|chunk| self.process_chunk(chunk))
            ).await;
            results.merge(batch_results);
        }
        // 处理失败重试
        if !self.retry_queue.is_empty() {
            results.merge(self.retry_failed().await?);
        }
        results
    }
}
```

## 5. Phase 执行器设计

### 5.1 Phase 定义

Phase = Goal 的一个执行阶段，包含多个 WorkFlow 单元。Phase 之间严格串行，Phase 内部可并行。

```rust
pub struct Phase {
    pub id: String,
    pub name: String,
    pub description: String,
    pub workflows: Vec<WorkFlowSpec>,
    pub quality_gate: QualityGate,
    pub on_failure: PhaseFailurePolicy,
}

pub enum PhaseFailurePolicy {
    Retry(usize),          // 重试 N 次
    SkipAndContinue,       // 跳过继续
    FailGoal,              // 终止整个 Goal
    AskUser,               // 询问用户
}
```

### 5.2 执行流程

```
Phase Start
    │
    ▼
Quality Gate (前置检查)
    │
    ├── Pass ──▶ Execute WorkFlows (并行/串行)
    │                    │
    │                    ▼
    │              Quality Gate (后置检查)
    │                    │
    │              ┌─────┴─────┐
    │              │           │
    │           Pass         Fail
    │              │           │
    │              ▼           ▼
    │         Phase Done   Adaptive Loop
    │                          │
    │                    ┌─────┴─────┐
    │                    │           │
    │              Fixed         Not Fixed
    │                    │           │
    │                    ▼           ▼
    │              Re-execute    Escalate
    │
    └── Fail ──▶ Phase Failure Policy
```

## 6. 自适应循环引擎

### 6.1 循环策略

借鉴 atomcode MAX_UNPRODUCTIVE=5 熔断 + claudecode doom_loop 3 次检测：

```rust
pub struct AdaptiveLoop {
    max_attempts: usize,              // 单 Goal 最大尝试次数
    max_unproductive: usize,          // 连续无进展熔断阈值
    backoff_strategy: BackoffStrategy,
    repair_strategies: Vec<RepairStrategy>,
}

pub enum RepairStrategy {
    SimplifyScope,        // 缩小任务范围
    ChangeApproach,       // 换一种实现方式
    AddContext,           // 补充更多上下文
    SplitTask,            // 拆分为更小的子任务
    EscalateToPlan,       // 升级到 Plan Agent 重新规划
    AskUser,              // 请求用户介入
}
```

### 6.2 自适应循环流程

```
执行 Goal
    │
    ▼
Quality Gate ─── Pass ──▶ Goal Satisfied ✓
    │
   Fail
    │
    ▼
分析失败原因
    │
    ├── 工具调用失败 ──▶ 重试（指数退避）
    ├── 输出不满足 ──▶ 补充上下文重试
    ├── 依赖未满足 ──▶ 先执行依赖
    ├── 范围过大 ──▶ 拆分任务
    ├── 方案错误 ──▶ 升级到 Plan 重新规划
    └── 无法自动修复 ──▶ 询问用户 / 标记 Failed
    │
    ▼
修复后重执行 ──▶ 回到 Quality Gate
    │
    ▼
超过 max_attempts ──▶ 熔断，标记 Failed
```

## 11. 关键设计决策

| 决策 | 选择 | 理由 |
|------|------|------|
| 状态机实现 | 内存 + SQLite 持久化 | 兼顾性能与可恢复性 |
| Squad 并发上限 | Semaphore(5) | 平衡并发与资源消耗 |
| 自适应循环上限 | 单 Goal 5 次 | 防止无限循环 |
| 模板存储 | SQLite + 内置 | 简单可靠，无需文件系统 |
| 失败策略 | 分层（Task→Squad→Phase→Goal） | 精细化控制 |
| QC 复用 | 复用 QualityRunner | 不重复造轮子 |
