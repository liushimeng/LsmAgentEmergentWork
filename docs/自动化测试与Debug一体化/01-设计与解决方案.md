# 自动化测试与 Debug 一体化 — 设计与解决方案

> 版本：2026-09-12　|　状态：已定稿并落地
> 产物：根目录 `AutoTestAndDebug.sh`（入口脚本）+ `AutoTestAndDebug.md`（执行提示词）
> 取代：`AutoTestAndSaveReport.sh/.md` 与 `AutoDebugTestReport.sh/.md`（旧两段式，已删除）

---

## 1. 背景与目标

### 1.1 旧架构（两段式，2026-09-08 ~ 2026-09-11）

| 脚本 | 角色 | Agent 候选 | 核心流程 | 产物 |
| ---- | ---- | ---- | ---- | ---- |
| `AutoTestAndSaveReport.sh/.md` | 只测不改 | codex/claude/hermes/opencode | 三层基线（build/test/e2e）+ 知识库抽测 + git 变更定向 | `testReport/自动化测试报告_*.md`（问题报告） |
| `AutoDebugTestReport.sh/.md` | 消费修复 | codex/claude/opencode | 读最早一份问题报告 → 定位修复 → 验证 → 中文 commit → 报告三分支归档 | 代码修复提交 + 报告归档 |

旧架构痛点：

1. **流程割裂**：测试与修复分属两个脚本、两次 Agent 会话，报告文件作为中间载体容易积压
   （`testReport/` 下待处理报告需逐份消费，`_无问题` 后缀文件长期残留）。
2. **两套提示词、两套守门**：维护成本高，Agent 候选池不一致（hermes 只在测试侧）。
3. **测试面偏「工程基线」**：以 cargo/e2e 为主，对 laew 真正的 **Agent 能力**
   （Yolo 分类、SubAgent 调度、工具执行、文件修改、任务完成质量）实测不足。
4. **知识库抽测条数少**（每轮仅 2 组），1840 条提示词的覆盖推进过慢；旧提示词引用的
   知识库路径（`01-问题知识库-第01-50问.md`）在知识库重构后已失效。
5. **git 流程不完整**：测试侧只 commit 不 push，调试侧同样不 push，长期依赖人工同步；
   无「拉取最新代码后再测」的步骤，可能测的是过期代码。

### 1.2 新架构目标（一体化闭环）

一次 Agent 会话内完成「**同步 → 感知 → 实测 → 方案 → 修复 → 收尾**」闭环：

1. **git 自动拉取**最新 main 分支（冲突自动处理），感知**近 10 天**新功能与优化项；
2. 从 `docs/自动化测试-提示词文件列表/`（184 主题 × 10 条 = 1840 条）按**本机操作系统**
   随机选出 **10~100 条**、**优先 bash/编程相关**的提示词；已测条目（✅ 已测试）不重复处理；
3. 在 `TestWorkSpace/` 工作目录下用 `laew -debug` / `laew -f` **实测 laew 的 Agent 能力**
   （工具执行 / Agent 调度 / SubAgent 编排 / 文件修改 / 任务完成质量），**不是测大模型能力**；
4. 测试发现的问题**不再生成 testReport/ 问题报告**，改为汇总成
   「测试与代码优化报告 + 解决方案」落盘 `tmpPlan/*.md`（文件名自定义）；
5. **按方案实现代码功能**并完成 cargo test / rebuild / e2e 回归验证；
6. git **中文提交并推送**（冲突自动解决；并行任务隔离，只处理自己修改的文件）；
   清理测试中间产物，保持工程整洁。

## 2. 现状关键事实（设计输入）

| 事实 | 数据 / 位置 | 对设计的影响 |
| ---- | ---- | ---- |
| 知识库规模 | `docs/自动化测试-提示词文件列表/` 184 主题文件 + README，共 1840 条 | 选条必须随机 + 优先级加权，单轮 10~100 条 |

| 日志体系 | `logs/auto_run_index.log` 索引 + 单次运行日志；保留 30 天 | 沿用，事件名换 `AutoTestAndDebug` |

**职责分工原则**（继承自旧脚本验证过的模式）：

- **shell 层做「确定性工程」**：进程管理、随机选 Agent、日志、防重入、守门；
  不做 git 写操作（避免与 Agent 会话内的 git 序列竞争）。
- **Agent 层做「智能决策」**：测试执行、问题判断、方案编写、代码修复、
  git 冲突解决、并行任务文件隔离判断。

## 4. `AutoTestAndDebug.sh` 设计

### 4.1 与旧脚本的差异对照

| 能力 | AutoTestAndSaveReport | AutoDebugTestReport | **AutoTestAndDebug（新）** |
| ---- | ---- | ---- | ---- |
| Agent 候选 | codex/claude/hermes/opencode | codex/claude/opencode | **claude/codex/opencode**（用户指定三选一随机） |
| 提示词守门 | 无 | 「绝对禁止修改 CLAUDE.md/AGENTS.md」锚点 | **保留同锚点** `grep -qF '绝对禁止修改 \`CLAUDE.md\`、\`AGENTS.md\`'` |
| 启动预检 | 提示词文件存在 | + 待处理报告存在（无则静默退出） | 提示词文件 + 工程基本结构（`Cargo.toml`/`src/`） |
| git 启动前拉取 | 无 | 无 | **后台段 best-effort `git pull --ff-only`**（超时 60s，失败仅记日志不阻塞） |
| Agent 退出后 git | 脚本侧 add/commit 测试报告 | Agent 侧 commit（不 push） | **Agent 侧中文 commit + push 双远端 + 冲突自解**（提示词 §6） |
| flock 防重入 | 无 | `logs/auto_debug.lock` | `logs/auto_testdebug.lock` |
| 冒烟模式 | AGENT_SMOKE=1 前台 | AGENT_SMOKE=1 前台 | 保留 |
| 日志 | `auto_test_<agent>_<ts>.log` | `auto_debug_<agent>_<ts>.log` | `auto_testdebug_<agent>_<ts>.log`（索引/清理逻辑沿用） |

### 4.2 关键实现点

1. **随机选 Agent**：`AGENT_CANDIDATES=(claude codex opencode)`；`AGENT_CLI` 环境变量
   可强制指定（定向调试）；三者都不可用则 `exit 3`。
2. **各 Agent 非交互调用**（沿用本机实测结论）：
   - codex：`codex exec --dangerously-bypass-approvals-and-sandbox - < prompt.md`（stdin 直读）
   - claude：`claude --dangerously-skip-permissions -p "<prompt>"`
   - opencode：`opencode run --auto -m <provider/model> "<prompt>"`（模型参数从
     `~/.config/opencode/config.json` 推导，无 provider 前缀时补全）
3. **守门条款**：提示词缺失「绝对禁止修改 `CLAUDE.md`、`AGENTS.md`」锚点即 `exit 2`，
   防止提示词被误改后 Agent 失控改规则文件。
4. **后台脱离**：`nohup setsid bash -c "<script>" &; disown`，调用者不阻塞；
   后台段顺序执行：flock → git pull（best-effort）→ Agent 会话 → 索引收尾。
5. **运行索引**：`logs/auto_run_index.log` 追加
   `script=AutoTestAndDebug agent=<名> event=<start|launched|agent_done|done|…>` 单行，
   便于事后 grep 审计。
6. **日志清理**：`*_testdebug_*.log` 超过 `LOG_RETAIN_DAYS`（默认 30 天）自动删除；
   兼容清理旧脚本遗留的 `*_test_*.log` / `*_debug_*.log`。

## 5. `AutoTestAndDebug.md` 提示词设计（八阶段）

| 阶段 | 时间盒 | 核心动作 | 硬性要求 |
| ---- | ---- | ---- | ---- |
| §0 环境准备与 git 拉取 | ≤3min | `git pull --ff-only origin main`；`uname -s` 探测 OS；读 CLAUDE.md 常用命令 | 冲突自动处理（只动自己文件）；工程说明只读 |
| §1 近 10 天变更感知 | ≤3min | `git log --since="10 days ago"` 梳理新功能/优化项 | 产出「定向测试关注清单」进最终方案文档；无代码变更则注明 |
| §2 知识库随机选条 | ≤5min | 按本机 OS 过滤主题 → 优先 bash/编程相关 → 随机选 10 条起步（余量足可扩至 100 条） | `✅ 已测试` 条目跳过；`🔄 待重测` 优先 |
| §3 laew Agent 能力实测 | ≤25min | `TestWorkSpace/` 下 `timeout 180-300 ../laew -debug -f <条目文件>` 逐条执行 | 断言四要素：Yolo 档位命中 / 工具链执行 / SubAgent 编排 / 产物落盘达标；观察卡死/崩溃/死循环/TUI 显示异常；provider 不可用降级 mock 或记 SKIP（不得标 ✅） |
| §4 问题汇总与方案落盘 | ≤5min | 写 `tmpPlan/YYYY-MM-DD_NN-<主题>测试与优化方案.md` | **不再生成 testReport/ 问题报告**；方案含问题清单（P0-P2/复现/根因）+ 解决方案 + 验证方式；无问题也落盘轻量测试记录 |
| §5 按方案实现代码功能 | ≤15min | 修码 → `cargo test` → `./rebuild_restart_app.sh` → `run_e2e.sh` 回归 | 动手前确认问题仍存在；遵循 CLAUDE.md 工程约束；e2e 资源独占检查（18899 端口、他人 mock 不 kill）；知识库 `✅` 回填在全部验证通过后 |
| §6 git 中文提交推送与清理 | ≤4min | 清理 TestWorkSpace/ 中间产物 → 显式路径 add → 中文 commit → push 双远端 | **只处理自己修改的文件**（并行任务隔离）；冲突 `pull --rebase` 自解；禁止 force push；push 失败留本地并记录 |
| §7 终止条件 | — | 总时长 60min 硬上限；工具连续 5 次失败不可恢复即落盘终止 | 任何情况下 tmpPlan 方案文档必须落盘 |

### 5.1 「测 Agent 能力，不测模型能力」的判定口径

每条知识库提示词执行后按四要素判定（写入方案文档的测试矩阵）：

1. **Yolo 档位**：实际分类 vs 条目「预期档位」（simple/medium/hard），不符记 P2；
2. **工具链**：条目「工具链」字段声明的 Write/Bash/Read 序列是否真实执行、参数正确；
3. **SubAgent 编排**：档位对应编排是否成立（simple→SubAgent 直通；
   medium→Main-Work→SubAgent；hard→Plan→Main→SubAgent 并行 + QC 全链路）；
4. **产物达标**：条目对话脚本中的 grep/test 断言是否逐条命中（工具产物在
   `TestWorkSpace/` 下落盘后由执行 Agent 复核）。

模型回答的内容质量**不是**缺陷依据；工具不执行、编排缺失、产物不达标、卡死崩溃才是。

### 5.2 TUI 观察项（发现显示问题一并优化）

自动化环境默认用 `-f` 单轮模式（无 TTY）；当需要验证 TUI 展示时用 tmux control-mode
真 PTY（`docs/TUI自动化测试/` 的既有方法：`tmux new-session -d -s <名> -x 100 -y 30`
+ `send-keys` + `capture-pane -p`）。观察清单：

- Agent 操作展示（阶段进度 / 工具调用提示）是否正常滚动、乱码、错位；
- **SSE 流式渲染**是否逐块出现（而非一次性倾泻或丢块）；
- 结果显示（任务结果双版本）、报告（DebugReport 四章节）、**用户的选择显示**
  （Picker/按钮选中态）、用户提示词回显是否达预期；
- CJK 截断 / 选中态视觉规范（`src/tui/theme.rs` 常量）是否被破坏。

### 5.3 知识库「测试状态」防重复机制

- 选条时：`grep -L '✅ 已测试'` 与逐条过滤 `🔄 待重测 / 无标记` 才是候选；
- 回填时：**仅当本轮四要素全过且（若改码）回归全绿**，把条目状态行改为：
  `- **测试状态**: ✅ 已测试（YYYY-MM-DD <一句话结果>；详见 tmpPlan/<方案文件名>）`
- 条目的主题/预期档位/对话脚本一律不得改动 —— 这是知识库唯一允许的修改，
  与「CLAUDE.md/AGENTS.md 只读」同为硬约束。

## 6. git 自动化与并行任务隔离策略

1. **拉取**：每轮会话开头 `git pull --ff-only origin main`；本地有自己未提交改动时
   先 `git stash push -- <自己的文件>` 再拉再 `stash pop`；别人的未提交改动不碰
   （ff-only 会因分叉失败时，才允许 `pull --rebase` 且仅解自己文件的冲突）。
2. **提交**：`git add` 一律**显式路径**（自己本轮改的 `src/**`、`docs/自动化测试-提示词文件列表/**`
   标记行、`tmpPlan` 之外的新文档等）；提交信息中文，格式
   `测试与优化: <摘要>（知识库抽测 X 条，修复 Y 项）`。
3. **推送**：`git push origin main`（远端配置 push=gitee+gitcode 双远端）；
   冲突时 `git pull --rebase origin main` 后重推；仍失败则保留本地提交并在方案文档记录，**禁止 force push**。
4. **并行隔离**（工程常态：多 Agent 会话并行）：提交前 `git status --porcelain` 逐行
   核对，凡不是本轮修改产生的路径一律不 add；发现别人文件出现在自己暂存中
   （异常情况）立即 `git restore --staged <别人的文件>`。
