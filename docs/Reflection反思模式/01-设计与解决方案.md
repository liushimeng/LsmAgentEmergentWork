# Reflection（反思）模式 — 设计与解决方案

## 1. 背景与问题

现有执行—验证—修订闭环已经能回答「**产物对不对**」：

```
SubAgent 执行 → Quality-Check → (Fail & retryable) → retry_hint → 局部重试
```

但它回答不了「**推理路径为何走偏**」。三处实测缺口：

1. **重试 hint 是缺陷清单不是教训**：`unit_retry_hint = QC issues + suggestion`
   只告诉执行层「哪里不达标」，不说「上一轮哪一步开始走错、下次应如何调整策略」。
   实测出现连续 3 轮完全重复同一失败的工具调用序列（tesseract/psm 链），
   靠 `extract_failed_methods` 关键词黑名单事后补救——这是症状级修补，
   不是路径级复盘。
2. **跨尝试无累积记忆**：第 1 次尝试踩过的坑，第 2、3 次尝试各自重新踩。
   同层姊妹单元也完全隔离，A 单元学到的「这个站点先要 dismiss 弹层」
   对 B 单元零可见性。
3. **QC 是外部裁判不是自我审视**：QC 只看产物与期望输出的差距，
   不看「执行轨迹内部的逻辑矛盾 / 事实误读 / 策略错配」。产出
   「碰巧符合期望输出但推理链路错误」的结果时，QC 可能放行。

目标：在执行链路中嵌入 **Reflection（反思）模式**——模拟人类
「执行 — 复盘 — 迭代」的认知逻辑，独立反思模块校验输出的
**逻辑自洽性、事实准确性、目标匹配度**，定位偏差后生成修正指令，
反向调整推理路径与工具调用策略，驱动多轮迭代优化（Reflexion 架构范式）。

## 2. 设计原则

| 原则 | 含义 |
| ---- | ---- |
| **反思是顾问不是闸门** | 解析失败/超时 fail-open 为「无教训」，绝不阻断主流程；与 QC 的 fail-closed 语义相反（QC 是质量门，Reflection 是策略顾问） |
| **判断权在模型** | 反思结论由 Reflection Agent 生成；机械通道只做「结构化信号 → 通用教训」的零幻觉映射，不做价值判断 |
| **效率优先（硬约束）** | 条件触发 + 预算上限 + 轻量机械档 + 杀开关；正常成功路径零额外 LLM 调用 |
| **通用性** | 不绑定具体工具/协议/站点；lessons 描述策略而非 API；接入点在执行单元层，可扩展到 Plan/Main-Work/收口 |
| **教训去重合并** | 多轮反思的 lessons 做规范化去重后追加，不线性叠加撑爆 context |
| **提示词纪律** | 无「第 N 轮」沿革标注、无政策性约束；运行正确性约束保留 |

## 3. 总体方案

```
SubAgent 执行 ──► Quality-Check
                     │
                     │ Fail & retryable & 预算未满
                     ▼
             [Reflection 复盘]  ←条件触发,不是每步
               ┌──────────────────────────────┐
               │ 三维度校验                    │
               │  ① 逻辑自洽 logic            │
               │  ② 事实准确 factual          │
               │  ③ 目标匹配 goal             │
               └──────────────────────────────┘
                     │
                     ▼
             ReflectionReport
               { lessons[], corrections[], strategy_shift, root_cause }
                     │
                     │  merge + 去重
                     ▼
             unit_retry_hint = QC issues/suggestion
                             + 【反思教训】lessons
                             + 【策略调整】strategy_shift
                     │
                     ▼
             局部重试(推理路径已按教训调整)
```

### 3.1 与既有机制的关系

| 机制 | 角色 | 与 Reflection 的分工 |
| ---- | ---- | ---- |
| **Quality-Check** | 外部裁判 | 判「产物 vs 期望输出」；Reflection 不重复判定 verdict，只复盘**过程** |
| **Replan（再规划）** | 规划缺口回灌 | 治「方案没覆盖现场」；Reflection 治「现场内策略走偏」。互补不重叠 |
| **LoopGuard** | 无进展止损 | 检测 doom_loop 后**中止**；Reflection 在中止前**纠正** |
| **SameCauseBreaker** | 同因熔断 | 归一化失败原因止损；Reflection 产出差异化教训降低同因复发率 |
| **retry_hint overlay** | 重试提示 | Reflection 的 lessons **注入该通道**，不新建提示注入路径 |
| **Debug Agent** | 事后评估 | 任务级、离线、写报告；Reflection 是过程级、在线、驱动下一轮 |
| **decision_audit** | 决策留痕 | Reflection 触发与否、产出了什么教训，记入 AuditTrail 可回溯 |

### 3.2 三维度校验定义

1. **逻辑自洽（logic）**：推理链有无矛盾、跳步、循环论证；结论是否被中间证据支撑；
   有无「做了 A 却报告 B」的自相矛盾。
2. **事实准确（factual）**：工具返回值是否被误读/选择性忽略；有无无依据编造
   （未执行的操作、未观测到的页面状态、伪造的完成证据）；证据与结论是否对得上。
3. **目标匹配（goal）**：执行路径是否服务本单元验收标准与用户原始意图；
   有无目标漂移的苗头（改派、降级、绕开核心动作）；产出是否落在正确的目标对象上。

每个维度输出 `score`（0=无问题 / 1=有瑕疵 / 2=严重偏差）与 `findings`（具体发现）。

### 3.3 ReflectionReport 输出结构

```json
{
  "root_cause": "一句话根因(下一轮必须正视)",
  "dimensions": {
    "logic":   { "score": 0, "findings": ["..."] },
    "factual": { "score": 0, "findings": ["..."] },
    "goal":    { "score": 0, "findings": ["..."] }
  },
  "lessons": [
    "遇到<情形>时应<做法>(下一轮起生效的通用经验)"
  ],
  "corrections": [
    "立即修正:把<错误动作>改为<正确动作>"
  ],
  "strategy_shift": "工具调用策略调整(如:先只读探查确认结构再执行写操作)",
  "sound": true
}
```

- `sound`：本次执行路径是否大体健全（true=局部修补即可；false=策略需要转向）。
- `lessons`：**跨 attempt 累积**的通用经验（Reflexion 的 episodic memory）。
- `corrections`：只对下一轮生效的具体修正指令。
- `strategy_shift`：工具/步骤层面的策略调整建议，注入重试描述的策略段。

## 4. 触发与效率（硬约束）

反思是**条件触发**的顾问，不是每步必过的开销。默认档位下的触发矩阵：

| 时机 | 触发? | 档位 | 额外 LLM 调用 |
| ---- | ---- | ---- | ---- |
| QC **Pass** 且无失败信号 | 否 | — | **0** |
| QC **Pass** 但 trace 有失败信号/工具错误率高 | 机械轻量 | light | **0** |
| QC **Fail** 且 `retryable=true` 且局部重试预算未满 | **是** | deep | 1 次（≈QC 同量级） |
| QC **Fail** 且即将升级档位级失败 | 机械轻量 | light | **0** |
| 执行早停（doom_loop / RepeatedToolFailure）后进 QC | 随上两行 | — | — |

**效率保障五件套**：

1. **条件门**：只在「即将带着错误再跑一遍」时深度反思——此时反思期望收益最高；
   成功路径零开销。
2. **预算上限**：每单元深度反思次数 ≤ `LAEW_REFLECTION_BUDGET`（默认 2，
   与 `unit_retry_budget` 对齐）；超限后退化为纯机械教训，不再调 LLM。
3. **轻量机械档**：`LAEW_REFLECTION_MODE=light` 时全程零 LLM——
   从 `ExecutionTrace` 结构化信号机械映射通用教训（工具错误率、早停原因、
   failure_signals、连续失败键、truncation、doom_loop），零幻觉零延迟。
4. **截断纪律**：喂给 Reflection 的 trace/output 沿用 QC 的 clip 策略
   （头尾保留窗口）；lessons 渲染进 retry_hint 时总长上限 1200 字符，
   超出按优先级截断。
5. **杀开关**：`LAEW_REFLECTION=off` 全关（连机械通道也不跑），
   行为与改造前完全一致。

**默认档**：`LAEW_REFLECTION` 未设置 = 开启 deep 档（条件门内才调 LLM）。
理由：条件门已经把调用次数压到「重试前一次」，与一次局部重试本身相比，
反思的边际成本远低于盲重试；`light` 档留给超低延迟/离线/测试场景。

## 5. 通用性设计

### 5.1 与具体工具解耦

- lessons / corrections 的措辞规范要求写**策略**（「先只读探查再写操作」）
  而非具体 API（「先调 inspect(info=dom) 再调 click」）——
  同一教训对 MCP_Web_Use / MCP_Window_Use / Bash 均适用。
- 机械通道只读 `ExecutionTrace` 的**工具无关字段**（错误计数、早停原因、
  failure_signals），不解析具体工具参数。
- prompt 中给 Reflection Agent 的材料是「目标 / 职责 / 期望 / 实际输出 /
  执行轨迹 / QC 结论」，不含工具 schema。

### 5.2 与具体角色解耦

- `ReflectionRunner` 对外只认 `goal / unit_scope / expected / actual / trace /
  qc_issues / qc_suggestion` 六元组——任何执行层（SubAgent-Work 今天，
  未来可能的专项执行器）都能接入。
- 未来扩展点（本版不实现，预留接口语义）：
  - Plan 复盘：hard 档 QC-Plan 失败后反思「规划假设哪里错」；
  - Main-Work 拆解复盘：依赖图/验收标准缺陷；
  - 任务收口复盘：把整任务 lessons 沉淀进 `session_memory`。

### 5.3 配置面（环境变量）

| 变量 | 取值 | 行为 |
| ---- | ---- | ---- |
| `LAEW_REFLECTION` | `off`/`0`/`false`/`no` | 全关（deep + light 均不跑），行为与改造前一致 |
| | 未设置 / 其它 | 默认开启（deep 条件档） |
| `LAEW_REFLECTION_MODE` | `deep`（默认） | 条件触发 LLM 反思 + 机械教训合并 |
| | `light` | 全程零 LLM，只跑机械教训 |
| `LAEW_REFLECTION_BUDGET` | 正整数（默认 2） | 每单元深度反思次数上限；0/非法回退默认 |

## 6. 实现设计

### 6.1 模块：`src/agent/reflection.rs`

```
reflection.rs
├── ReflectionReport        // 结构化反思结论(Serialize/Deserialize)
├── DimensionScore          // 单维度得分 + findings
├── ReflectionRunner        // LLM 深度反思(与 QualityRunner 同构:Agent + prompt + 解析)
│     └── reflect(...) -> Result<(ReflectionReport, Usage)>
├── mechanical_lessons()    // 零 LLM:ExecutionTrace → Vec<String> 通用教训
├── merge_lessons()         // 规范化去重合并(跨 attempt 累积)
├── render_reflection_block() // lessons/corrections/strategy_shift → retry_hint 文本段
├── parse_reflection_report() // JSON 提取 + json_repair;失败 Ok(None) 即 fail-open
└── reflection_enabled()/reflection_mode()/reflection_budget()  // env 决策
```

**`ReflectionRunner`**（对齐 `QualityRunner` 形态）：

- 持有 `Agent`（profile = `AgentProfile::reflection_profile()`，无工具、
  `SpawnPolicy::Disabled`、无 emit tool）；
- `reflect()` 组装 prompt（目标/职责/期望/实际/QC 结论/trace）→
  `run_session` 单轮 → `parse_reflection_report`；
- 解析失败 / LLM 失败：`Ok(None)`（fail-open，上层用纯机械教训继续）；
- 用量经返回值带回，由 `run_wf_unit` 累进单元 usage。

**`mechanical_lessons()` 信号映射**（全部零幻觉）：

| 结构化信号 | 生成教训 |
| ---- | ---- |
| `tool_calls_err / tool_calls > 0.5` | 「工具调用错误率过高：下一轮先用只读探查确认参数与环境，再执行写操作」 |
| `early_terminated` + reason | 「上一轮触发早终止（{reason}）：避免同型重复，改用差异化步骤或收敛收口」 |
| `failure_signals` 非空 | 「上一轮出现失败信号 {signals}：下一轮先针对性处置该信号再继续」 |
| `max_consecutive_failures ≥ 2` | 「同一失败连续出现：禁止重复同一失败方法，换工具/换参数/拆细步骤」 |
| `doom_loop_repeats ≥ 2` | 「出现无进展打转：先换观察角度获取新信息，再决定动作」 |
| `truncated_tool_calls > 0` | 「工具参数被输出上限截断：拆小参数/分步执行，避免巨型单次调用」 |
| `truncation_resumes > 0` | 「LLM 输出曾被截断续接：控制单次输出体量，关键结论前置」 |

### 6.2 系统提示词：`SystemPrompt::reflection()`

- 新增 `REFLECTION_IDENTITY`（一句话身份）+ `REFLECTION_BASE_PROMPT`
  （职责 / 三维度定义 / 输出 JSON schema / 教训措辞规范 / 效率纪律）。
- 形态对齐 Debug/Compact：`without_tools` + `set_identity`，无协议尾巴。
- 提示词硬性要求：只输出一个合法 JSON 对象；`lessons` 写策略不写具体 API；
  不复述 QC 已判明的缺陷清单（那是 retry_hint 的事），只产出**增量洞察**。

### 6.3 角色接线

| 文件 | 改动 |
| ---- | ---- |
| `context.rs` | `AgentRole::Reflection`（`as_str="reflection"`，`From<&str>` 兼容） |
| `agent_message.rs` | `role_display` 补 `"Reflection"` |
| `config/agent_memory.rs` / `session_memory.rs` | 存量角色串映射补 `"reflection"` |
| `profile.rs` | `REFLECTION_AGENT_NAME` + `reflection_profile()` |
| `tools/mod.rs` | `reflection_registry()`（空表，对齐 debug_registry） |
| `system_prompt/mod.rs` | `SystemPrompt::reflection()` + 提示词守卫测试纳入第 10 角色 |
| `agent/mod.rs` | `pub mod reflection;` |

### 6.4 编排器接入：`run_wf_unit`

调用点唯一（`run_wf_unit` 是串行/并行/简单档三条路径的共同执行核）：

```rust
// 单元内跨 attempt 的教训账本(局部重试环外声明)
let mut lessons_acc: Vec<String> = mechanical_lessons(&outcome.trace); // 基线,零 LLM
let mut deep_reflections = 0usize;

// QC Fail & retryable & 预算未满 →(首次)深度反思一次
if qc.retryable && attempt < retry_budget
   && reflection_enabled()
   && reflection_mode() == Deep
   && deep_reflections < reflection_budget()
{
    match reflection.reflect(...).await {
        Ok((report, usage)) => {
            deep_reflections += 1;
            acc_usage = add_usage(acc_usage, usage);
            lessons_acc = merge_lessons(lessons_acc, &report);
        }
        Err(_) => { /* fail-open:保留机械教训继续 */ }
    }
}

unit_retry_hint = format!(
    "{}\nqc suggestion: {}\n{}",
    qc.issues.join("; "),
    qc.suggestion,
    render_reflection_block(&lessons_acc),
);
```

- **机械基线永远合并**（零 LLM）：即使 deep 关闭/超预算/失败，教训段仍在。
- **升级档位级失败时**也带 `render_reflection_block`（写入 `QualityFailure.reason`
  或 suggestion），让 Yolo 回流/档位重试同样看到教训。
- **进度可见**：`emit_progress` 打一行「🔍 Reflection：根因=… / 教训 N 条」。

### 6.5 决策审计

`decision_audit::record_reflection(...)`：记录触发与否、维度得分、教训条数、
root_cause（脱敏截断），与 5 个既有决策点同构，fail-open 不影响主流程。

## 8. 明确不做

1. **不改变 QC 的 fail-closed 语义**——Reflection 永远 fail-open，二者不可混淆。
2. **不做每步/每工具调用级反思**——成本不可控，ReAct 循环内的自我纠正已由
   runtime hints 与 LoopGuard 承担。
3. **不跨任务全局共享 lessons**——避免无关任务的经验污染；同任务内跨 attempt 累积。
4. **不做自动改写系统提示词**——「反向调整提示词」由 lessons 注入描述段实现，
   不动态改写角色提示词（会摧毁 Anthropic prefix cache）。
5. **不引入新 crate**——JSON 解析复用 `json_repair`，提示词复用 `SystemPrompt`。

## 9. 风险与取舍

| 风险 | 处置 |
| ---- | ---- |
| 反思调用增加延迟 | 条件门把调用压到「重试前一次」；light 档零 LLM；budget 封顶 |
| 反思结论质量不稳 | 教训措辞规范 + 不复述 QC + 机械基线兜底（LLM 失败仍有教训） |
| lessons 撑爆 context | merge 去重 + 渲染上限 1200 字符 + 每条教训长度限制 |
| 与 QC 结论矛盾 | Reflection 不改 verdict；若 lessons 与 QC issues 冲突，两者并列由执行层自行取舍 |
| 并行单元相互干扰 | lessons 账本是单元局部变量，不做全局共享（见 §8.3） |
