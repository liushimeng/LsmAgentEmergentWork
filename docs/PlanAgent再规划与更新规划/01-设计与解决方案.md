# Plan Agent 再规划 / 更新规划 — 设计与解决方案

## 1. 背景与问题

`LsmAgentEmergentWork-Plan`（hard 档规划层）在规划前会用 MCP_Web_LsmAgentBrowser_Use 等观察类工具
探索目标站点，但实际场景中存在三类系统性缺口：

1. **探索不全面**：复杂登录流程、数据填报、表单提交等流程需要真实凭证与多步交互，
   Plan 只有观察类工具（写操作默认留给执行层），遇到登录墙 / 滑块 / 扫码验证时
   只能停在墙外，方案只能基于"墙外可见的信息"编写。
2. **方案与现场脱节**：执行层（SubAgent-Work）按方案执行时，才发现页面结构、
   登录流程、表单字段与规划假设不符（规划时没探索到），单元 QC 判 Fail。
3. **盲重试浪费预算**：失败后编排器只有两条路——同档位带 retry_hint 重跑
   （方案本身没更新，重跑大概率撞同一堵墙），或回流 Yolo 重新分类。
   规划层从未拿到"执行现场的真实反馈"，无法修订方案。

目标：给 Plan 增加**再规划（re-plan）/ 更新规划（update-plan）**能力——
执行层遇阻 → 编排器把失败现场回灌 Plan → Plan 修订方案 → 执行层按新方案继续。

## 2. 设计原则

- **判断权在模型**：是否再规划、再规划成什么样，全部由 Plan / Main-Work 模型决定；
  编排器只做**机械路由**（失败信号识别 + 重规划通道调度），不做价值判断。
- **机械信号只做路由提示**：「这是登录墙类缺口」的识别是关键词/信号级的机械检测
  （与 `SameCauseBreaker` 归一化、target_drift 信号同性质），误触发的代价是
  "多问 Plan 一次"，漏触发的代价是"在死路上烧满重试预算"，取舍明确偏向前者。
- **断点续跑优先**：再规划复用第 146 轮的 completed_digest 机制——已完成且 QC 通过
  的单元禁止重复规划/重跑，Plan 只修订受阻部分。
- **零配置生效 + 杀开关**：默认开启（每任务再规划预算 2 次），`LAEW_REPLAN=off` 关闭。
- **提示词不写轮次沿革**：新增约束按「默认如此 + 例外需理由」的软约束口径书写。

## 3. 总体方案

```
执行层单元失败(QC Fail, retryable)
        │
        ▼
[机械识别] 规划缺口信号?(replan::detect_replan_signal)
  登录墙 / 表单流程 / 访问受阻 / 流程未知 / 人工验证
        │ 命中且预算未满
        ▼
[编排器] try_replan
  ├─ hard 档 → PlanRunner::replan_update(原方案 + 失败现场 + 已完成清单)
  │            → 新 Plan 文档落盘 plans/{session}-{seq}.md
  └─ medium 档 → MainWorkRunner::plan_workflows_with_delegate(replan_context)
                 → 新 WorkFlowPlan(确定性校验不过则回落常规重试)
        │
        ▼
[状态] ReplanPending { plan_path | plan, summary } ← handle_inner 跨轮暂存
        │
        ▼
下一轮重试
  ├─ run_hard:有 ReplanPending.plan_path → 直接解析新文档,跳过 Plan 重新生成
  │            (同步跳过 QC-Plan——再规划是带反馈的定向修订,非盲生成;
  │             QC-Main 与单元 QC 照常把守)
  └─ run_medium:有 ReplanPending.plan → 注入复用分支,跳过 Main-Work 重拆
        │
        ▼
execute_workflows 只执行新方案中的(剩余)单元
  新单元 description 已注入档位级 retry_hint(= 失败现场 + 再规划摘要)
```

### 3.1 规划缺口信号识别（机械通道）

新模块 `src/agent/replan.rs`：

```rust
pub enum ReplanTrigger { LoginWall, FormFlow, AccessBlocked, UnknownFlow, HumanVerify }
pub struct ReplanSignal { pub trigger: ReplanTrigger, pub evidence: String }
pub fn detect_replan_signal(reason: &str, suggestion: &str, failure_signals: &[String])
    -> Option<ReplanSignal>
```

扫描源（按优先级）：
1. `failure.reason` + `failure.suggestion`（QC issues / suggestion 文本）；
2. `trace.failure_signals`（执行层机械信号，如 blocker 类）；
3. 关键词表（中英双语）：
   - `LoginWall`：登录、登陆、扫码、验证码、滑块、短信验证、账号密码、captcha、
     slider、login required、扫码登录
   - `FormFlow`：表单、填报、提交申请、上传材料、报名、申请表、form
   - `AccessBlocked`：403、拒绝访问、权限不足、未授权、风控、访问受限、WAF
   - `UnknownFlow`：页面结构与预期不符、未探索到、找不到入口、无此元素、
     流程未知、与规划假设不符
   - `HumanVerify`：request_human、human_assist、manual_verify、需要人工、
     人工核验

命中即返回信号 + 命中证据摘录（截 120 字符），供日志与再规划 prompt 使用。

### 3.2 Plan 再规划（hard 档）

`PlanRunner::replan_update(...)`（`src/agent/plan.rs` 新增方法）：

- 输入：goal/purpose/intent/decomposition + **原方案 Markdown（截断头 3000 字符）**
  + **再规划触发上下文**（触发类别 + 失败单元 id + QC issues/suggestion +
  trace 失败信号）+ completed_digest + 用户原始 prompt。
- Prompt 语义：这是**再规划/更新规划**，不是从头规划——
  ① 保留原方案中已验证有效的部分；
  ② 只修订受阻/未覆盖的 WorkFlow，补齐缺口处置策略
  （登录前置步骤、表单分步填写、request_human 人工介入点、换路径/换入口）；
  ③ 已完成单元禁止重复规划；
  ④ 输出仍是完整五段 Markdown 模板（可选「## 六、未决阻碍与再规划触发点」）。
- 产物落盘 `plans/{session_id}-{seq}.md`（新 seq，旧方案保留可回溯）。

### 3.3 Main-Work 更新规划（medium 档）

`plan_workflows_with_delegate` / `plan_workflows_inner` 新增
`replan_context: Option<&str>` 参数：

- 存在时在 prompt 追加【再规划/更新计划】块：失败单元 + QC 结论 + 触发类别，
  要求更新编排（补前置登录步骤 / 表单分步 / 人工介入点），只拆剩余目标。
- 产物走与正常拆解相同的确定性校验（auto_repair + validate_plan_blocking），
  不过即回落常规重试路径（不消耗再规划预算之外的资源）。

### 3.4 编排器闭环（`src/agent/orchestrator/`）

- `types.rs` 新增 `ReplanPending { plan_path, plan, summary }`（pub(super)）；
  `OrchestratorConfig` 新增 `replan_budget: usize`（默认 2，0 = 关闭）。
- 新子模块 `orchestrator/replan.rs`：`try_replan(...)` —— 构建再规划上下文、
  按档位分派到 Plan / Main-Work、产物确定性校验、组装 ReplanPending。
- `pipeline.rs::handle_inner`：
  - 失败路径在「常规重试 / Yolo 回流」之前插入再规划判定：
    `failure.retryable && !cancelled && 预算未满 && 信号命中 && LAEW_REPLAN 未关`
    → `try_replan`；成功则 `retry_hint = 失败现场 + 再规划摘要`、`same_cause.reset()`、
    `continue`（下一轮 run_hard/run_medium 消费 ReplanPending）；失败静默回落。
  - `last_plan_path: Option<PathBuf>` 跨轮暂存（run_hard 成功生成 Plan 后记录），
    再规划时读取原文注入 Plan。
- `run_hard` 增 `replan_pending: &mut Option<ReplanPending>` 参数：
  有 `plan_path` → 读文档构造 PlanOutput，跳过 Plan 生成与 QC-Plan；
  无 → 原有 generate 路径。
- `run_medium` 增同参数：有 `plan` → 替换进 `plan_cache` 走既有复用分支
  （执行 + 失败反馈注入语义与计划复用完全一致）。
- 进度行：`「检测到规划缺口(登录墙/表单/…),触发 Plan 再规划…」`、
  `「再规划完成:{path},按更新方案继续执行剩余单元」`。

### 3.5 初次规划提速（Plan 感知能力增强，`plan_prompt.rs`）

- **批量感知规范**：网页类任务首选 `MCP_Web_LsmAgentBrowser_Use(action=explore)` 一次拿全
  （elements/dom/页面元信息/阻断态多维度一次收集）；同一响应里连续的只读观察
  工具调用会并行执行——把能并行的观察合并到同一响应，减少 round-trip。
- **探索轮数软预算**：观察类行动一般控制在个位数轮次；信息足够支撑方案即收口，
  不要为探索而探索。软约束（非禁令），与既有「信息足够时立即收口」呼应。
- **顽固阻碍收口**：遇到登录墙 / 验证码 / 滑块 / 扫码 / 需真实账号数据的填报流程，
  默认**不要**在墙外反复尝试不同入口——记录为「未决阻碍」写入风险段，按已知信息
  完成方案并给出「再规划触发点」（如"wf-2 执行遇登录墙时触发再规划，补充登录
  前置步骤"）。执行层遇阻后编排器会自动把现场反馈带回 Plan 做再规划。
- 输出模板新增可选段「## 六、未决阻碍与再规划触发点」（无未决阻碍可省略）。

### 3.6 Work Agent 继续任务（需求 4）

再规划完成后，新方案的单元经 `execute_workflows → build_subflow_input` 构造，
档位级 retry_hint（含失败现场 + 再规划摘要）自动注入每个单元的 description——
执行层在新一轮天然看到「上一轮为什么失败、方案已如何更新」，按更新后的步骤继续。
该机制为既有能力（第 146/149 轮），本方案零改动复用。

## 5. 失败与边界语义

- 再规划本身失败（LLM 错 / 解析校验不过）→ 静默回落常规重试，**不额外消耗**
  档位重试预算之外的语义（再规划预算已消耗，不再连续再规划同一现场）。
- `failure.retryable=false`（如 target_drift 目标一致性硬门）→ 不再规划，
  走既有 Yolo 回流（重规划救不了错位目标）。
- 用户取消 → 短路退出，不再规划。
- 再规划预算独立计数（默认 2），与 `max_retry_per_level` / `unit_retry_budget`
  正交；耗尽后走既有路径。
- ReplanPending 只存活一个重试轮：消费后清空，避免过期方案被复用。
- medium 档再规划产物必须通过确定性校验才进入执行，杜绝带结构缺陷的计划
  被执行层跑飞。
