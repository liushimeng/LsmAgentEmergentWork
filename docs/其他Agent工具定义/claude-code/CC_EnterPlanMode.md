## 何时使用此工具

对于实施任务，除非任务很简单，否则优先使用 EnterPlanMode。当适用以下任何条件时，请使用它：

1.  **新功能实施**：添加有意义的新功能
    -   示例：“添加注销按钮”——它应该放在哪里？点击时会发生什么？
    -   示例：“添加表单验证”——规则是什么？错误消息是什么？

2.  **多种有效方法**：可以通过几种不同的方式解决任务
    -   示例：“为 API 添加缓存”——可以使用 Redis、内存、基于文件等。
    -   示例：“提高性能”——有许多可能的优化策略

3.  **代码修改**：影响现有行为或结构的更改
    -   示例：“更新登录流程”——具体应该更改什么？
    -   示例：“重构此组件”——目标架构是什么？

4.  **架构决策**：任务需要在模式或技术之间进行选择
    -   示例：“添加实时更新”——WebSockets 与 SSE 与轮询
    -   示例：“实现状态管理”——Redux 与 Context 与自定义解决方案

5.  **多文件更改**：任务可能会触及 2-3 个以上的文件
    -   示例：“重构身份验证系统”
    -   示例：“添加带有测试的新 API 端点”

6.  **需求不明确**：在理解完整范围之前需要进行探索
    -   示例：“让应用程序更快”——需要分析并确定瓶颈
    -   示例：“修复结帐中的错误”——需要调查根本原因

7.  **用户偏好很重要**：实施可以合理地以多种方式进行
    -   如果您将使用 AskUserQuestion 来澄清方法，请改用 EnterPlanMode
    -   计划模式允许您先探索，然后在上下文中呈现选项

## 何时**不**使用此工具

仅对简单任务跳过 EnterPlanMode：
-   单行或几行修复（错别字、明显错误、小调整）
-   添加具有明确要求的单个函数
-   用户已给出非常具体、详细说明的任务
-   纯研究/探索任务（改用带有 explore agent 的 Agent 工具）

## 计划模式中会发生什么

在计划模式下，您将：
1.  使用 `find`/Glob、`grep`/Grep 和 Read 彻底探索代码库
2.  理解现有模式和架构
3.  设计实施方法
4.  向用户展示您的计划以供批准
5.  如果需要澄清方法，请使用 AskUserQuestion
6.  准备好实施时使用 ExitPlanMode 退出计划模式

## 示例

###  好 - 使用 EnterPlanMode：
用户：“向应用程序添加用户身份验证”

用户：“优化数据库查询”
-   多种方法可能，需要先分析，影响重大

用户：“实现深色模式”
-   关于主题系统的架构决策，影响许多组件

用户：“向用户个人资料添加删除按钮”
-   看似简单，但涉及：放置位置、确认对话框、API 调用、错误处理、状态更新

用户：“更新 API 中的错误处理”
-   影响多个文件，用户应批准该方法

###  不好 - 不要使用 EnterPlanMode：
用户：“修复 README 中的错别字”
-   直截了当，不需要计划

用户：“添加 console.log 以调试此函数”
-   简单，明显的实施

用户：“哪些文件处理路由？”
-   研究任务，不是实施计划
