# Yolo Agent 设计与解决方案

> 关联需求:双 Agent 架构 / Yolo 入口层 / 任务分类与拆解 / Work 执行层。
> 关联模块:`src/agent/yolo.rs`、`src/agent/profile.rs`、`src/agent/system_prompt/`、`src/tui/mod.rs`、`src/main.rs`。

## 1. 背景与目标

### 1.1 现状

当前 `laew` 采用单 Agent 架构(`LsmAgentEmergentWork`),用户输入直接进入工具调用循环。存在以下问题:

1. **简单问题也走完整工具循环**:用户问个 "你好" 或一个常识问题,系统也会带着全套工具定义发起 LLM 请求,浪费 token。
2. **复杂任务缺乏前置规划**:中等/高难度任务直接丢给 Agent 自己摸索,可能走弯路、迭代次数多、效果不稳定。
3. **没有任务分级**:所有任务一视同仁,无法针对不同难度采取不同策略。

### 1.2 目标

| 目标 | 说明 |
|------|------|
| 双 Agent 架构 | 引入 Yolo(入口层)+ Work(执行层)双层 Agent |
| 任务四级分类 | trivial / simple / medium / hard,不同级别不同处理策略 |
| 前置任务拆解 | medium/hard 任务由 Yolo 先做结构化拆解,再交给 Work 执行 |
| 简单任务快速响应 | trivial 任务 Yolo 直接回答,省去工具循环开销 |
| 架构可扩展 | 为未来更多 Agent 类型(如 Reviewer、Planner)预留扩展口 |

## 2. 总体架构

### 2.1 双 Agent 协作流程

```
用户输入
   │
   ▼
┌─────────────────────────────────────┐
│   Yolo Agent(LsmAgentEmergentWork-Yolo) │
│   入口层 · 首交互                       │
│   - 目标识别                            │
│   - 意图识别                            │
│   - 任务难度分类(四级)                   │
│   - medium/hard:输出结构化拆解计划       │
│   工具:仅 Read(理解上下文用)             │
│   max_iterations: 4                     │
└───────────────┬─────────────────────────┘
                │
     ┌──────────┴─────────────┐
     ▼                        ▼
 trivial(极其简单)        simple/medium/hard
 直接文本回答                │
                            ▼
              ┌──────────────────────────────────┐
              │  Work Agent(LsmAgentEmergentWork-Work) │
              │  执行层 · 实干                       │
              │  - 全套 Bash/Read/Write 工具         │
              │  - 完整工具调用循环(最多 16 轮)        │
              │  输入:结构化计划 + 原始需求            │
              └──────────────────────────────────┘
```

## 3. Yolo Agent 设计

### 3.1 身份与定位

- **名称**:`LsmAgentEmergentWork-Yolo`
- **角色**:用户对话的第一层入口 Agent,任务分析与分类专家
- **风格**:简洁、果断、结构化
- **边界**:只做分析和分类,不做实际执行;只读取不改写

### 3.2 工具集

Yolo 仅持有 **Read** 工具:

| 工具 | 用途 |
|------|------|
| Read | 读取文件内容,帮助理解上下文以更准确地分类(如 "帮我看看这个文件有什么问题") |

**不持有** Bash / Write 等会修改系统状态的工具——那些交给 Work Agent。

### 3.3 max_iterations

Yolo 的 `max_iterations` 设为 **4**:
- 正常情况下 1-2 轮就能完成分类(可能 1 轮 Read + 1 轮输出)
- 避免 Yolo 陷入不必要的工具调用循环
- 控制 token 开销

## 4. 任务分类机制

### 4.1 四级难度定义

| 级别 | 名称 | 判定标准 | Yolo 行为 |
|------|------|---------|-----------|
| **trivial** | 极其简单 | 纯知识问答 / 闲聊 / 简单计算 / 概念解释,无需任何工具 | 直接回答 |
| **simple** | 简单 | 单步操作(读一个文件 / 执行一条命令 / 写一个文件),1 个工具调用完成 | 直接委派 Work |
| **medium** | 中等难度 | 2-5 步操作,涉及多个文件,需要先了解再动手 | 输出拆解计划 → 委派 Work |
| **hard** | 高等难度 | 多模块综合改动 / 架构级变更 / 深度理解 + 反复调试,5 步以上 | 输出详细分阶段计划 + 验收标准 → 委派 Work |

### 4.2 结构化输出格式

Yolo 的最终回复中必须包含一个 ```json 代码块:

```json
{
  "task_level": "medium",
  "goal_summary": "一句话概括用户的核心目标",
  "intent": "code_refactor",
  "decomposition_plan": [
    "步骤 1: ...",
    "步骤 2: ..."
  ],
  "direct_answer": null
}
```

字段说明:

| 字段 | 类型 | 说明 |
|------|------|------|
| `task_level` | string | 难度等级:`trivial` / `simple` / `medium` / `hard` |
| `goal_summary` | string | 一句话复述用户目标,用于传递给 Work Agent |
| `intent` | string | 粗粒度意图分类(英文标识),如 `code_refactor` / `info_query` / `file_operation` / `chat` / `config` / `debug` |
| `decomposition_plan` | string[] | 分解步骤数组;trivial 为空,simple 可空或单步,medium/hard 必须详细 |
| `direct_answer` | string \| null | 仅 trivial 时有值,为最终回答文本;其他级别为 null |

### 4.3 解析容错机制

`parse_classification()` 函数采用三级容错:

1. **优先匹配 ```json 代码块**:最规范的输出格式,直接提取
2. **降级匹配独立 JSON 对象**:如果没找到代码块,扫描文本中的第一个 `{ ... }` 结构
3. **最终降级为 simple**:如果 JSON 解析完全失败,默认分类为 `simple`,直接委派给 Work Agent,保证不阻塞用户

## 5. 任务拆解策略

### 5.1 Simple 级别

- 分解计划可空或只有 1 步
- Work Agent 直接拿到原始需求 + 简单计划
- 与原单 Agent 行为接近,主要是多了一层目标确认

### 5.2 Medium 级别

- 列出 2-5 个清晰步骤
- 每步是一个具体可执行的动作(读文件 / 改代码 / 运行命令等)
- 步骤之间有逻辑先后关系

示例:
```
decomposition_plan: [
  "阅读 src/agent/mod.rs 完整理解 run_session 的逻辑",
  "将工具调用执行部分抽取为 execute_tool_calls 函数",
  "将 LLM 调用与 usage 累计部分抽取为 call_llm 函数",
  "重构 run_session 主体,调用新子函数",
  "运行 cargo build 验证编译通过"
]
```

### 5.3 Hard 级别

- 分阶段计划(如:调研 → 设计 → 实现 → 验证)
- 每阶段有明确产出物
- 包含注意事项和验收标准
- 步骤数 5+

示例:
```
decomposition_plan: [
  "阶段一(调研):阅读 docs/ 下相关设计文档,理解架构约束",
  "阶段二(设计):制定模块拆分方案,确定新增/修改的文件列表",
  "阶段三(实现):按依赖顺序实现各模块,每完成一个模块运行 cargo check",
  "阶段四(集成):串联各模块,修改 TUI 和 main.rs 入口",
  "阶段五(验证):运行单元测试 + e2e 测试,确保全部通过",
  "验收标准:cargo test 全过 / run_e2e.sh 全过 / 手动验证 TUI 交互正常"
]
```

## 6. 委派执行机制

### 6.1 上下文传递

Yolo → Work 的上下文通过 **主 Session** 传递:

```
主 Session 上下文变化:
  [用户消息]                       ← 用户输入
  [Yolo 分析文本]                  ← Yolo 的自然语言分析 + JSON
  [任务计划消息(用户角色)]          ← build_work_prompt() 构造
  [Work 的工具调用 / 结果 / ...]    ← Work Agent 执行循环
  [Work 最终回答]                  ← 最终结果
```

这样做的好处:
- **对话历史连贯**:用户看到完整的分析 → 计划 → 执行过程
- **Work 有完整上下文**:Work 既能看到 Yolo 的分析,也能看到结构化计划
- **Session 简单**:只有一个主 Session,不需要管理多个 Session 的同步

### 6.2 Work 任务提示构造

`build_work_prompt()` 将分类结果格式化为 Work Agent 的任务提示:

```
【任务计划】
目标: {goal_summary}
难度: {display_name} ({task_level})
意图: {intent}

分解步骤:
  1. {步骤 1}
  2. {步骤 2}
  ...

请按照以上计划执行任务。使用可用工具完成目标,完成后用简洁中文回复最终结果。
```

### 6.3 Token 用量汇总

Yolo 和 Work 的 token 用量分别统计,最终汇总:

```rust
total_usage.input_tokens = yolo_usage.input + work_usage.input
total_usage.output_tokens = yolo_usage.output + work_usage.output
total_usage.cache_read_input_tokens = yolo_usage.cache_read + work_usage.cache_read
```

用户看到的是**总用量**,透明且一致。

## 7. TUI 集成方案

### 7.1 输出格式

```
>> 帮我重构一下 agent/mod.rs 的 run_session 函数

  [yolo 分析中...]

  [assistant]
  这是一个中等难度任务,涉及函数拆分与可读性优化。已制定以下计划:
  ...(Yolo 的自然语言分析 + JSON 代码块)...

  【任务计划】
  目标: ...
  难度: 中等难度 (medium)
  ...

  (Work Agent 的执行过程 / 工具调用 / 最终回答)
  ...

  本次用量: input=...  output=...
```

Yolo 阶段显示 `[yolo 分析中...]` 提示,让用户知道正在处理。

### 7.2 TuiSession 变更

```rust
// 变更前
pub struct TuiSession {
    pub agent: Agent,
    ...
}

// 变更后
pub struct TuiSession {
    pub yolo: YoloRunner,
    ...
}
```

`YoloRunner` 内部同时持有 yolo_agent 和 work_agent,外部只看到一个统一入口。

### 7.3 Provider 切换

切换 provider 时,同时重建 Yolo 和 Work Agent(共享同一个 LLM 客户端):

```rust
fn switch_provider(&mut self, id: i64) -> Result<()> {
    // ... set_active ...
    self.yolo = build_yolo_with_record(&record, &user_agent)?;
    Ok(())
}
```

## 8. 单轮模式(-p / -f)集成

`run_one_shot()` 同样走 Yolo 流程:

1. 构造 `YoloRunner::with_work_max_iterations(llm, max_iterations)`
2. 通过 `with_work_env_tail()` 为 Work Agent 注入环境上下文
3. 调用 `yolo_runner.handle(&mut session)`
4. 打印最终答案 + 总用量

stdout 只输出最终答案,Yolo 的中间过程对单轮模式透明。

## 9. 与单 Agent 模式的对比

| 维度 | 单 Agent | 双 Agent(Yolo + Work) |
|------|----------|----------------------|
| 简单问题响应 | 走完整工具循环,慢 | Yolo 直接回答,快 |
| 复杂任务质量 | Agent 自行摸索,不稳定 | Yolo 先规划再执行,质量更高 |
| Token 用量 | 单次请求含全套工具定义 | 两次请求,Yolo 工具少但多一轮 |
| 架构扩展性 | 差,所有能力混在一起 | 好,可按需新增更多 Agent 类型 |
| 调试难度 | 简单 | 需要理解两层协作 |

**总体**:对于简单任务有速度优势,对于复杂任务有质量优势,代价是多一次 LLM 调用。

## 10. 风险与缓解

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| Yolo 输出 JSON 不合法 | 分类失败,无法继续 | 三级容错机制(代码块 → 独立 JSON → 降级 simple) |
| Yolo 分类不准 | 该快的不快,该规划的没规划 | 系统提示词中给出明确的分级标准和示例 |
| Token 用量增加 | 每次对话多一次 Yolo 调用 | Yolo 工具少(max 1 个)、迭代少(4 轮),增量可控 |
| 对话上下文变长 | Work 拿到的上下文更多 | 合理控制 Yolo 输出长度,计划部分简洁 |
| 误分类为 trivial 导致回答不准 | 用户问题需要工具但被直接回答了 | trivial 标准从严,宁多走 Work 不漏掉 |
