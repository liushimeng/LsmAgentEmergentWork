> 关联测试:`cargo test`、`testReport/run_e2e.sh`。
>
> **本文是 Yolo 设计的唯一一份现行文档**。此前分散在 `02-系统提示词设计.md`(第一版存档,自标「仅作历史参照」)与 `03-Yolo工具集扩展与ReAct信息收集设计.md`(改造方案)中的内容已全部并入本文,两份旧文档已删除。文中只描述**当前实现**,不再保留逐轮变更沿革 —— 沿革归 git 历史。

## 1. 定位

Yolo 是**用户对话的第一层入口 Agent**,负责「目的 → 目标 → 意图」三步分析与任务难度三档分类,并对 medium / hard 任务给出结构化拆解计划。真正的执行交给下游 Main-Work / SubAgent-Work。

- **名称**:`LsmAgentEmergentWork-Yolo`
- **风格**:简洁、果断、结构化
- **默认分工**:入口层收集信息与判断,执行层动手。这是一条**默认约定而非硬边界** —— 提示词明确告诉模型「若判断某任务就该当场动手,直接做即可」,不在入口层设写作/执行的禁令。

## 2. 系统提示词设计原则

本工程的系统提示词按**两类约束**切分,这是 Yolo 提示词(以及其余 8 个角色)的统一编写依据:

| 类别 | 定义 | 处置 |
| --- | --- | --- |
| **政策性约束** | 约束「该不该接这个任务」——按任务性质(攻击 / 越权 / 违法 / 违反服务条款 / 危害他人)决定拒绝 | **不写进提示词,程序也不拦截**。判断权完全交给模型 |
| **运行正确性约束** | 约束「怎么把任务做对」——目标保真、证据不伪造、路径保真、能力边界、澄清门 | 保留,但写成「默认如此 + 例外需理由」而非「禁止 / 红线」 |

### 2.1 为什么政策性约束一律不写

- **重复劳动**:模型自身已具备判断力,提示词再写一套「什么该拒什么不该拒」的清单,既占 token 又与模型自身判断打架。
- **误伤**:关键词式条款会连带压制合法任务(如「安全」类词在正常工程语境里高频出现)。
- **不该由编排器代劳**:程序层做价值判断会把「模型的判断」变成「框架的判断」,且一旦判断有误,用户拿到的是框架的拒绝而非模型的拒绝。

因此:**「这个任务该不该接」完全由 Yolo 模型自行决定**。若判断不适合接,把结论与替代方向写进 `direct_answer`,编排器原样返回给用户;若判断可以接,照常分级委派。系统对此**不做任何检测、拦截或改写**。

> 历史沿革:此前存在 `refuses_task` 布尔字段 + 编排器「拒绝终态门」+ `detect_refusal` 机械短语检测(27 个中文拒绝 marker)构成的三层程序级拒绝链路。该链路已整体移除,相关字段、Schema 属性、提示词指令段、编排器三处闸门与终态收口函数均不再存在。

### 2.2 移除程序级拒绝门后,空转如何止动

移除拒绝门不影响对「反复重试同一件失败的事」的止损 —— 那由**同因熔断器**(`orchestrator/types.rs::SameCauseBreaker`)承担:

- 失败原因归一化(trim → 首行 → 截 120 字符)后比对,连续 2 次相同即 `force_fail`;
- 模型自行拒绝任务时,其 Plan 输出同样解析不出 WorkFlow,归一化后三轮逐字相同 → 第 2 次熔断收口;
- Yolo 失败回流重分类后计数复位(失败语境已变)。

熔断阈值 2 轮(首次失败 + 一次修正机会),把浪费上界从 `max_retry_per_level` 收紧到 2 轮。

## 3. 工具面

| 工具 | 用途 |
| --- | --- |
| Read | 读取文件内容,帮助理解上下文以更准确地分类 |
| Glob / Grep | 路径模式与内容检索,在分类前定位「相关代码」「刚才那个文件」 |
| Bash | 以只读侦察为主(`ls`/`cat`/`grep`/`git log`/`git status` 等);写盘命令一般留给执行层 |
| MCP_Web_Use | 以 `open`/`list`/`inspect`/`screenshot` 观察类 action 为主 |
| SubAgent | 并行只读侦察(`SpawnPolicy::ReadOnlyChildren`) |
| `submit_task_classification` | 结构化输出通道,唯一出口 |

**不持有** Write / Edit / TodoWrite / MCP_Window_Use。

工具面之外的纵深防御仍在:`permissions::check_bash_command` 危险命令黑名单(`rm -rf`/`sudo`/`curl|bash`/`~/.ssh` 等)、`SpawnPolicy::ReadOnlyChildren` 子 Agent 工具上限。

## 4. ReAct 信息收集

### 4.1 max_iterations 与延迟强制

`max_iterations = 8`,通过 `AgentProfile.defer_emit_force` 开启**延迟强制**:

- **探索轮**(非最后一轮)不注入 `forced_tool`(`tool_choice: auto`)—— 模型可自由 ReAct;
- **最后一轮**强制注入 `submit_task_classification`,保证结构化出口;
- **倒数第二轮**追加「收口预告」runtime hint,给模型主动交卷的机会。

> 早期版本每轮都强制指名 emit 工具,与多轮探索在协议层互斥 —— 模型没有机会先 `Bash` 再 `Read` 再提交,`Read` 工具形同虚设。延迟强制修正了这一点。

`explore_budget` 显式设为 **0**:该 hint 文案面向浏览器操控(「进入执行期后禁止再开 inspect/screenshot」),对 Yolo 的信息收集语义是误导。

### 4.2 信息收集纪律

分类质量取决于信息充分度。提示词要求模型区分两类信息:

- **可侦察的事实**(代码在哪、现状如何、文件内容、依赖版本、难度依据)→ 用工具查,不要问用户;
- **用户自己的选择 / 侦察不出来的信息**(「这个网站」指哪个站、「那个文件」是哪个)→ 侦察工具帮不上忙,这类情况填 `target_status="unresolved"` + `clarification_question`,由编排器回问用户。

反面实测:用户提示词多行粘贴被终端截断后只剩「打开网站搜索,这个网站最新时间的 3 个文章」,Yolo 正确识别出指代不明,却去 `Read` 运行日志、`Glob **/*`、`ls` 工作目录想找出用户指哪个网站 —— 当然找不出来,于是分类 medium 委派下去,执行层先后猜了两个站点,在**完全无关的站点**上跑了 6 分钟并被判「成功」。

### 4.3 刚性分级

提示词里的约束按强度分三档,只保留必要的硬表述:

| 强度 | 例子 |
| --- | --- |
| **硬**(必须) | JSON 字段类型、工具 schema、目标标识逐字保真、证据不伪造 |
| **中**(默认如此,例外需理由) | 批量优先、ReAct 三段推进、迭代预算 |
| **软**(建议 / 一般 / 通常) | 收集轮次上限、拆解数量对齐 |

早期版本几乎全部写成「禁止 / 必须 / 严禁 / 红线」,导致模型在边界情况下不敢变通。

## 5. 任务分类机制

### 5.1 三档难度定义

| 级别 | 判定标准 | Yolo 行为 |
| --- | --- | --- |
| **simple** | 单一明确操作(读一个文件、执行一条命令、写一个文件);纯知识问答、闲聊、简单计算;单步工具调用即可完成 | 无需工具时填 `direct_answer` 由编排器直答短路;否则直接委派 |
| **medium** | 2~5 个工具调用步骤;涉及多个文件或多个子任务,需先了解现状再动手 | 输出 `decomposition_plan` → Main-Work 拆解 → SubAgent-Work 执行 |
| **hard** | 多文件/多模块综合改动;需深度理解代码结构;需反复调试验证,可能 5 步以上 | 输出详细多步骤分解计划(含注意事项与验收标准) |

**最低档位规则**:涉及「读取/操作桌面软件窗口」或「网页/浏览器操作」的任务**最低按 medium 分类**(这两类由 SubAgent-Work 的 `MCP_Window_Use` / `MCP_Web_Use` 工具执行,入口层不持这两个工具)。

三档边界不确定时的取向:整体偏向「高估难度」,避免低估导致执行环节反复补救。

### 5.2 结构化输出格式

最终分类结果必须通过 `submit_task_classification` 工具提交(工具参数即结构化输出,不在正文裸写 JSON):

```json
{
  "task_level": "simple | medium | hard",
  "purpose": "一句话概括用户目的",
  "goal_summary": "一句话概括核心目标",
  "intent": "code_refactor | info_query | file_operation | chat | config | debug | ...",
  "decomposition_plan": ["步骤 1", "步骤 2"],
  "direct_answer": null,
  "target_status": "explicit | resolved | unresolved",
  "clarification_question": null
}
```

| 字段 | 说明 |
| --- | --- |
| `task_level` | 三档难度之一 |
| `purpose` / `goal_summary` / `intent` | 三步分析的三个产物,每次都要认真填写 |
| `goal_summary` | 必须保留原始任务的**核心动词与对象**(发送/保存/读取/截图/启动/点击/键入…),不得压缩成同义词 |
| `decomposition_plan` | 字符串数组;medium / hard 必须有详细步骤 |
| `direct_answer` | simple 且无需工具时填答案;需委派时必须是 JSON `null`(不是字符串 `"null"`) |
| `target_status` / `clarification_question` | 目标可解析性判定,见 §6 |

工具调用不可用时,降级为在正文输出 ```json 代码块,结构同上。

### 5.3 解析容错

`parse_classification()` 三级容错:

1. 优先匹配 ```json 代码块;
2. 降级匹配独立 JSON 对象(扫描第一个 `{ ... }` 结构);
3. 最终降级为 `simple` + `yolo_degraded=true`,直接委派下游,保证不阻塞用户。

## 6. 目标可解析性与澄清门

`target_status` 三态(配套 `safety/target_anchor.rs` 的跨层防线):

| 取值 | 含义 | 编排器行为 |
| --- | --- | --- |
| `explicit` | 原文显式给出目标标识(URL / 域名 / 文件路径 / 应用名) | 正常委派;这些标识已被机械抽取为**任务锚点**,执行层偏离会被工具层阻断(`code=6001`) |
| `resolved` | 原文用指代,但先行词能从会话上下文/历史摘要解析出来 | 正常委派 |
| `unresolved` | 指代无先行词,全上下文找不到任何目标标识 | 把 `clarification_question` 原样回给用户,**不委派执行** |

`target_status="unresolved"` 时 `clarification_question` 必填:中文、直接可答、列明具体缺哪一项。

**不可解析的目标不委派**:不要把「向用户澄清」写进 `decomposition_plan` 当成一个执行步骤 —— WorkFlow 单元在 DAG 里无法暂停等待用户输入,这类步骤会退化成 `Bash echo "已询问用户"` 假装提问,然后下游单元在没有目标的情况下乱跑(系统对此有确定性阻断校验,会秒级打回)。

**目标标识逐字保真**:原文里的 URL / 域名 / 文件路径 / 应用名应逐字写进 `goal_summary` 与 `decomposition_plan`,而不是抽象成「目标网站」「该文件」。下游拿到的是 Yolo 的摘要,抽象掉就等于让执行层去猜。

## 7. 与编排器的衔接

```
用户输入
   │
   ├─ 项目上下文注入(CLAUDE.md / AGENTS.md / README.md 五级链,`<<<LAEW:PROJECT_CONTEXT>>>`)
   ├─ 会话历史摘要注入(最近 N 条,`<<<LAEW:SESSION_HISTORY>>>`)
   │
   ▼
Yolo(三步分析 → ReAct 信息收集 → 三档分类)
   │
   ├─ target_status=unresolved ──→ 回问用户(不进 WorkFlow)
   ├─ simple + direct_answer  ──→ 直答短路
   ├─ simple / medium ──────────→ 委派执行层
   └─ hard ──────────────────────→ Plan Agent 规划 → Main-Work 拆解 → SubAgent-Work 执行
   │
   ▼
Quality-Check(每个执行单元完成后必经)
   │
   ▼
SessionContext 收口摘要
```

失败时按 `retryable` 分层重试:单元级局部重试(默认预算 2)→ 档位级重试(`max_retry_per_level=3`)→ Yolo 回流重分类;连续 2 次同因即熔断(见 §2.2)。实现见 `src/agent/orchestrator/`。
