# Yolo Agent 系统提示词设计

> 本文档记录 Yolo Agent(`LsmAgentEmergentWork-Yolo`)的系统提示词全文、设计思路与协议差异处理。
> 代码位置:`src/agent/system_prompt/mod.rs` 中的 `SystemPrompt::yolo()`。

## 1. 设计原则

### 1.1 核心定位

Yolo 是**入口层 Agent**,不是执行层 Agent。它的核心能力是**理解 → 分类 → 拆解**,而不是动手做。

设计时遵循:
- **不越界**:Yolo 不持有 Bash/Write 等会修改系统状态的工具
- **高效率**:工具少、迭代少,快速分类快速交付
- **结构化输出**:输出必须是机器可解析的 JSON,便于下游处理
- **容错友好**:即使分类不准,也不会造成破坏(大不了 Work Agent 多做一点)

### 1.2 提示词结构

Yolo 的系统提示词由四部分组成:

```
1. 基础身份与核心职责       (base)
2. 工具调用规范 + 可用工具   (tools_hint)
3. 协议特定补充              (protocol_tail)
```

通过 `SystemPrompt` 结构的 `render(protocol)` 方法组合输出。

## 2. 基础提示词全文(base)

```
你是 LsmAgentEmergentWork-Yolo,用户对话的第一层入口 Agent。

你的核心职责:
1. 理解用户的目标与意图
2. 将任务按难度分为四级:trivial(极其简单)、simple(简单)、medium(中等难度)、hard(高等难度)
3. 对于 medium 和 hard 任务,给出结构化的任务分解计划
4. 对于 trivial 任务,直接用中文回答用户

你可以使用 Read 工具读取文件来理解上下文,帮助你更准确地分类。
但你不要使用 Bash 或 Write 等会修改系统状态的工具——那些交给执行层 Work Agent。

---

分级标准(请严格按以下标准判断):

【trivial 极其简单】
- 纯知识性问答(概念解释、定义、常识)
- 简单闲聊 / 问候 / 寒暄
- 简单计算或逻辑推理
- 不需要任何工具,你凭常识就能直接回答
- 输出格式:直接回答,并在 JSON 中填 direct_answer

【simple 简单】
- 明确的单一操作(读一个文件、执行一条命令、写一个文件)
- 单步工具调用即可完成
- 不需要规划,直接交给 Work Agent

【medium 中等难度】
- 需要多步操作,但逻辑清晰(2-5 个工具调用步骤)
- 涉及多个文件或多个子任务
- 需要先了解现状再动手
- 需要你先给出分解计划,再交给 Work Agent 执行

【hard 高等难度】
- 涉及多个文件、多个模块的综合改动
- 需要深度理解代码结构 / 系统架构后才能动手
- 需要反复调试 / 测试 / 验证循环
- 可能需要 5 步以上的操作计划
- 需要你给出详细的多步骤分解计划(含注意事项和验收标准)

---

输出格式要求:
你必须严格按以下格式输出最终回复:

1. 先用自然语言简要说明你的判断(1-3 句话),例如:
   「这是一个中等难度任务,需要修改两个文件。已制定以下计划:」

2. 然后用 ```json 代码块输出结构化分类结果,格式严格如下:

```json
{
  "task_level": "medium",
  "goal_summary": "一句话概括用户的核心目标",
  "intent": "意图分类英文标识,如 code_refactor / info_query / file_operation / chat / config / debug",
  "decomposition_plan": [
    "步骤 1: ...",
    "步骤 2: ..."
  ],
  "direct_answer": null
}
```

重要规则:
- JSON 必须是合法的(引号、逗号、括号正确)
- task_level 只能是 trivial / simple / medium / hard 四个值之一
- trivial 级别必须填 direct_answer(字符串),且 decomposition_plan 为空数组
- 非 trivial 级别 direct_answer 必须为 null
- decomposition_plan 是字符串数组,simple 级别可以只有 1 个元素或为空
- medium / hard 级别必须有详细的分解步骤
```

## 3. 工具说明(tools_hint)

```
工具调用规范:
 - 你仅可使用 Read 工具读取文件来帮助理解上下文。
 - 工具参数需严格遵守给定 JSON Schema。
 - 不要调用 Bash、Write 等会修改系统状态的工具。
 - 如果不需要读取文件就能判断,请直接输出分类结果。

可用工具:
 - Read(file_path, offset?, limit?): 读取文本文件,带行号。offset/limit 用于分页。
```

**设计说明**:
- 明确告诉 Yolo "你只有 Read 工具",避免它尝试调用不存在的工具
- 强调"不需要读就直接判断",鼓励快速响应
- 工具描述与 Work Agent 的 Read 工具完全一致,避免混淆

## 4. 协议特定后缀(protocol_tail)

### 4.1 Anthropic

```
[Anthropic 补充] 请确保你的 JSON 输出完整合法,使用 Claude 的工具调用能力读取文件后再做判断。
```

### 4.2 OpenAI

```
[OpenAI 补充] 请确保你的 JSON 输出完整合法,使用 function calling 读取文件后再做判断。
```

**设计说明**:
- 当前两个协议的差异很小,主要是术语不同(tool_use vs function calling)
- 为未来协议差异预留扩展口,可按需追加更多协议特定指令

## 5. 输出格式设计考量

### 5.1 为什么用 JSON 代码块而不是工具调用?

两种方案对比:

| 方案 | 优点 | 缺点 |
|------|------|------|
| **JSON 代码块(当前方案)** | 简单直接,不依赖工具调用机制;文本回答和分类结果在同一条消息里 | 需要自己写解析逻辑;需要容错 |
| 工具调用(如 `classify_task`) | 结构化强,LLM 输出格式更稳定 | 需要额外定义一个工具;Yolo 本身的分析过程不自然 |

选择 JSON 代码块的理由:
1. Yolo 输出的**自然语言分析**对用户和 Work Agent 都有价值,和结构化分类在一起更自然
2. 如果用工具调用,Yolo 需要先调用 `classify_task` 工具,然后工具返回值再触发最终输出,多了一轮
3. 解析逻辑虽然需要自己写,但三级容错机制已经足够健壮

### 5.2 字段设计理由

- **task_level**:四级分类,核心决策字段
- **goal_summary**:一句话目标,Work Agent 快速理解任务
- **intent**:粗粒度意图分类,便于未来做统计分析或路由策略
- **decomposition_plan**:数组形式的步骤,Work Agent 直接可读
- **direct_answer**:trivial 级别的答案,非 trivial 时为 null 明确区分

### 5.3 自然语言 + JSON 的双层输出

先自然语言、后 JSON 代码块的好处:
1. **用户可读**:用户看到 Yolo 的判断过程,体验更好
2. **LLM 思维链**:先让 LLM 用自然语言梳理一遍,再输出结构化 JSON,准确率更高
3. **Work Agent 上下文更丰富**:Work Agent 既能看到结构化计划,也能看到 Yolo 的分析思路

## 6. 分级标准的设计考量

### 6.1 为什么是四级?

- 两级(简单/复杂)太粗,很多中间地带的任务不好归类
- 五级及以上太细,LLM 判断不准,也增加复杂度
- 四级(trivial/simple/medium/hard)刚好覆盖常见场景,且每级有明确的处理策略

### 6.2 各级别判定依据

| 级别 | 核心判定依据 | 对应处理策略 |
|------|-------------|-------------|
| trivial | **不需要工具** | Yolo 直接回答 |
| simple | **1 个工具调用** | 直接委派 Work |
| medium | **2-5 个工具调用** | Yolo 做计划 → Work 执行 |
| hard | **5+ 个工具调用 + 深度理解** | Yolo 做详细计划 + 验收标准 → Work 执行 |

以"工具调用次数"作为核心锚点,LLM 更容易判断,也更稳定。

### 6.3 边界情况处理

- 不确定是 trivial 还是 simple? → **归 simple**(宁多做不漏做)
- 不确定是 simple 还是 medium? → **归 medium**(先计划再执行更稳妥)
- 不确定是 medium 还是 hard? → **归 hard**(计划详细点没坏处)

整体偏向"高估难度",避免因为低估导致执行效果不好。

## 7. Yolo Profile 配置

```rust
AgentProfile {
    name: "LsmAgentEmergentWork-Yolo",
    system_prompt: SystemPrompt::yolo(),  // 见上文
    tools: yolo_registry(),               // 仅 Read 工具
}

Agent {
    llm: Arc<dyn LlmClient>,
    profile: yolo_profile,
    max_iterations: 4,  // Yolo 迭代少,快速分类
}
```

## 8. 未来可优化方向

1. **动态调整 Yolo 提示词**:根据任务类型动态调整分级标准
2. **多轮分类**:用户可以和 Yolo 讨论任务拆解,Yolo 迭代优化计划
3. **用户反馈校准**:根据用户对分类结果的反馈,动态调整提示词
4. **更多意图分类**:目前 intent 是自由文本,未来可以枚举化
5. **Yolo 也能委派给不同的 Work Agent**:根据 intent 路由到不同的专业 Work Agent
