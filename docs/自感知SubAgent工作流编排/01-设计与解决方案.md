## 1. 背景与问题

D114/D115 之后,用户已经能用自然语言触发 SubAgent,模型可以用 `batch` 并行启动独立子任务,也可以用 `history` / `resume` 复用历史结论。当前能力仍有三个缺口:

1. **只能表达“独立并行”**:`batch` 中的任务会一次性并行执行,无法表达“先并行调研 → 汇总 → 实现 → 验证”这类跨阶段依赖。
2. **上游结论传递靠父模型手拼**:模型必须等一个 `launch` 返回后,再手动把结论写进下一个 `launch`,额外占用父上下文,也容易漏掉关键约束。
3. **多阶段流程缺少整图状态**:用户无法看到哪一阶段成功、哪一阶段被跳过、依赖失败如何阻断、总预算如何预扣。

中央 `MultiAgentOrchestrator` 已经有 Main-Work 拆解、Kahn 分层、QC 和 SessionContext 收口,不应把这条重量级链路复制到动态子 Agent。本轮增量是把“轻量 DAG 执行器”放进 D114 运行时,让可委派角色在不扩大权限面的情况下表达可复用的小型工作流。

## 2. 目标与非目标

### 2.1 目标

1. **新增 `SubAgent(action="workflow")`**:单工具仍只有一个 `SubAgent`,通过 action 扩展,避免给 LLM 增加新工具名。
2. **声明式小 DAG**:`steps[]` 每步有稳定 `id`、自包含 `task`、`depends_on[]`;执行器做结构校验、拓扑分层和依赖阻断。
3. **同层并行、跨层串行**:无依赖冲突的步骤在同一层并行;所有直接上游成功后才启动下游。
4. **自动产物注入**:上游成功结论以受控摘要追加到下游任务提示词,父模型不需要手动搬运长文本。
5. **治理不旁路**:
   - 工作流总步数不超过 8;
   - 启动前校验会话剩余预算;
   - 复用 `SpawnPolicy` 三重收窄和真实注册表交集;
   - 复用并发信号量、深度限制、超时、取消 token、用量台账;
   - 每个实际执行的步骤仍按 D115 写入 `subagent_run`,`origin="workflow"`。
6. **结构化报告**:返回 DAG 状态、每个步骤状态、`run_id`、上游依赖、产物、错误、耗时、用量和汇总文本,便于父模型整合为最终回答。
7. **失败语义明确**:上游失败/超时/取消时,直接下游标记 `skipped`,不可达下游标记 `blocked`;工作流返回 `partial` / `failed` / `cancelled`,不静默当成成功。

### 2.2 非目标

| 非目标 | 理由 |
| --- | --- |
| 不替代 Main-Work / Plan / QC 中央链路 | 中央链路有项目上下文、阶段化进度和 QC;动态 workflow 只适合模型自主委派的小型 DAG |
| 不做进程级断点续跑 | 子 Agent 运行中的 future 不可序列化;继续沿用 D115 的“结论 resume”语义 |
| 不新增跨进程 A2A 委派 | 协议、权限与审计边界较大,独立轮次处理 |
| 不允许 workflow 内声明 SubAgent 工具 | 委派权只属于当前父策略;步骤工具面会继续剔除 `SubAgent` |
| 不把 workflow 本身落库为独立表 | 每个步骤已有 `subagent_run`;先通过报告聚合 DAG 状态,避免提前固化 schema |

## 3. 用户交互与提示词契约

### 3.1 触发场景

当用户提示词包含以下任一意图,且任务天然分成多阶段时,可委派角色应优先考虑 `workflow`:

- “先并行调研 A/B/C,再汇总成方案”
- “研究 → 实现 → 测试 → 总结”
- “分阶段处理,后面的步骤要使用前面的结果”
- “启动多个 Agent 完成一套工作流”

如果只是互不依赖的并行子任务,继续用 `batch`;单步任务直接执行;需要中央 QC、计划落盘和长会话治理的复杂工程任务仍由中央 Orchestrator 处理。

### 3.2 步骤契约

```json
{
  "action": "workflow",
  "steps": [
    {
      "id": "research-api",
      "task": "调研 src/llm 的请求构造与错误映射,列出关键文件和风险",
      "agent_type": "explore",
      "expected_output": "不超过 40 行的结构化结论"
    },
    {
      "id": "research-ui",
      "task": "调研 src/tui 的任务结果渲染链路",
      "agent_type": "explore"
    },
    {
      "id": "synthesize",
      "task": "合并 API 与 UI 调研结论,提出兼容修改点",
      "depends_on": ["research-api", "research-ui"],
      "agent_type": "plan"
    },
    {
      "id": "review",
      "task": "审查方案是否破坏现有调用方",
      "depends_on": ["synthesize"],
      "agent_type": "code-reviewer"
    }
  ]
}
```

步骤字段:

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `id` | 是 | DAG 节点标识;非空、去重、1..=64 字符 |
| `task` | 是 | 自包含任务;下游执行时自动追加上游结论 |
| `depends_on` | 否 | 直接上游 `id` 数组;默认无依赖 |
| `agent_type` | 否 | 内置或 D115 自定义类型;默认 `general-purpose` |
| `name` / `system_prompt` / `tools` / `expected_output` / `max_iterations` | 否 | 与 `launch` 语义一致,只能收窄能力 |

## 4. 架构设计

```text
SubAgentTool.execute("workflow")
        │ 解析 JSON / 解析自定义类型 / Schema 纠偏
        ▼
subagent_workflow::plan(steps, remaining_budget)
        │ id 去重 / 依赖存在 / 环检测 / Kahn 分层 / 预算校验
        ▼
SubAgentRuntime.run_workflow(...)
        ├─ 第 1 层:runtime.batch([...])  ← 信号量、预算、取消、超时
        ├─ 成功产物摘要注入第 2 层 task
        ├─ 失败上游 → 直接下游 skipped → 间接下游 blocked
        └─ 每个子步骤仍走 run_child → subagent_run(origin="workflow")
        ▼
WorkflowOutcome
        └─ SubAgentTool 统一 JSON 信封 → 父模型汇总
```

### 4.1 计划校验

1. `steps` 必须是 1..=8 个对象;上限与现有 `MAX_BATCH_TASKS` 对齐,且默认会话总预算也是 8,避免一张图抢占整会话。
2. `id` 必须非空且唯一;依赖必须指向已声明节点。
3. Kahn 入度算法检测环;有环返回 `1001`,不启动任何子 Agent。
4. 剩余预算 `< steps.len()` 时返回 `2001`,不部分启动。
5. 自定义类型解析失败返回 `1001` 并列出可用名册;校验期一次性完成,避免第 3 层才发现类型失效。

### 4.2 执行状态机

节点状态:

| 状态 | 含义 |
| --- | --- |
| `ok` | 子 Agent 正常完成 |
| `failed` / `timeout` / `cancelled` | 子 Agent 实际终态 |
| `skipped` | 至少一个直接上游未成功 |
| `blocked` | 更上游失败导致不可达 |

工作流状态:

| 状态 | 判定 |
| --- | --- |
| `completed` | 所有实际执行节点 `ok` |
| `partial` | 有成功也有失败,或存在 `skipped` / `blocked` |
| `failed` | 无一节点成功 |
| `cancelled` | 父任务取消且无成功节点;有部分成功则为 `partial` |

每完成一层,执行器只把直接上游状态为 `ok` 的 `text` 注入下游。单个上游摘要截断 2000 字符,全部上游注入总量截断 6000 字符,避免层级放大撑爆子 Agent 上下文。

### 4.3 能力与治理

- 步骤运行复用 `SubAgentRuntime::batch`,因此自动获得并发信号量、并发等待超时、父取消传播、单 Agent 超时、迭代上限和用量累加。
- `tools` 仍会经过父策略、类型声明、真实注册表交集收窄;请求 `SubAgent` 会被剔除。
- `origin="workflow"` 使 `history` 可以区分工作流步骤;D115 的 `resume` 可继续复用任意步骤结论。
- 工作流报告本身不写新表,避免 schema 提前扩散;后续如需 `/agents workflow` 面板,再增加聚合视图。

## 5. 提示词与可观测性

### 5.1 自感知提示词增量

`self_awareness::prompt_section` 增加一条启动规则:

- 独立并行用 `batch`;
- 有依赖的多阶段任务用 `workflow`;
- `workflow` 每步必须自包含,依赖只传 `id`,不要求父模型复制长结论;
- 必须在最终回答里整合成功产物,并如实说明失败/跳过阶段。

### 5.2 工具描述与错误信封

`SubAgent` 工具描述补充 workflow 语义;JSON Schema 新增 `steps`。错误继续使用统一信封:

| code | 场景 |
| --- | --- |
| `0` | 工作流执行完成;`status` 可能是 `completed` / `partial` |
| `1001` | 缺 `steps`、步数越界、id 冲突、依赖缺失、DAG 环、未知类型 |
| `2001` | 剩余预算不足以执行整张图 |
| `2002` | 当前深度禁止委派 |
| `4002` | 工作流被取消 |

`partial` 不使用错误 code,因为父模型需要继续汇总已完成部分并解释未完成部分。

## 7. 测试与验收

1. `cargo test`:覆盖 DAG 校验、拓扑分层、上游结论注入、失败阻断、预算预检、自定义类型、工具 Schema、提示词规则。
2. `bash testReport/run_e2e.sh`:确认现有 114/115 轮子 Agent 用例不回归。
3. 手工验证:
   - 环形依赖返回 `1001`,不消耗预算;
   - 四节点三阶段 DAG 按层执行,下游任务文本包含上游摘要;
   - 一个上游失败时直接下游 `skipped`,间接下游 `blocked`;
   - `history` 能看到 `origin="workflow"` 的步骤记录。
4. `./rebuild_restart_app.sh`:发布构建成功,根目录 `laew` 更新。

## 8. 兼容性与回滚

- 不改既有 `launch` / `batch` / `resume` 参数;旧提示词和旧工具调用行为不变。
- `LAEW_SELF_SPAWN=off`、深度为 0 或策略 Disabled 时,`workflow` 与旧动态委派一致返回不可用,提示词零注入。
- 不引入新 crate、不改数据库 schema;回滚只需移除 workflow action 与新模块。
