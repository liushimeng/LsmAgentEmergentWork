## 1. 背景与目标

第 100 轮已经交付了 HITL 闭环 + 窗口可视化的最小可用集,初始 reason 集为
`captcha / sms / qr_login / login / manual_verify / custom`(6 个)。

实测覆盖盲区与需求补充(以业务诉求为驱动):

1. **实名认证/人脸核身** —— 金融/政务/医疗/支付场景的入口必过项;
   原方案只能退化到 `manual_verify` 兜底,默认文案与 TUI 标签都不精准。
2. **二次验证 / 2FA / TOTP / 邮箱验证码** —— 企业 SaaS/账号安全场景,
   原本同属于 `captcha` 语义但推荐中"图形/滑块验证码"标签对用户误导,
   并且动态码是"人工直接输入数字"与图形验证码"人工拖动"交互不同。
3. **第三方 OAuth / SSO 授权** —— GitHub / Google / 微信开放平台等;
   原本同会被 `login` 关键词部分命中,但 "授权" 与 "账密登录" 在 Agent
   工作流上是不同事件(授权后跳回原站继续 vs 账密登录后重导航)。

目标:在不改 HITL 架构与 UI 引擎的前提下,以**增量 reason + 增量 blockers
关键词**补齐这三类高频场景,并以常量集中管理 + 可机械回归的方式保证:
LLM 工具面 / TUI 展示 / 阻断检测三处不漂移。

## 2. reason 总览

```
captcha | sms | qr_login | login | real_name | two_factor | oauth | manual_verify | custom
```

| reason | TUI 标签 | 默认说明 | Agent 后续动作 |
| --- | --- | --- | --- |
| `captcha` | 图形/滑块验证码 | 页面出现验证码/滑块,Agent 无法自动完成 | 人工在窗口完成验证 → inspect 验证页面 |
| `sms` | 短信验证码 | 页面要求短信验证码,Agent 无法获取 | 人工在 TUI 输入数字 → input_text 填入 |
| `qr_login` | 扫码登录 | 页面要求扫码登录 | 人工扫码 → inspect 验证页面 |
| `login` | 账密登录 | 页面要求账号密码登录 | 人工在窗口登录(不要发密码给 Agent) |
| `real_name` | 实名认证/人脸核身 | 页面要求实名认证/上传身份证/人脸核身 | 人工在窗口刷脸/上传证件 → inspect 验证 |
| `two_factor` | 二次验证/2FA | 页面要求 2FA / TOTP / 邮箱验证码 | 人工在 TUI 输入动态码 → input_text 填入 |
| `oauth` | 第三方授权 | 页面跳到 GitHub/微信/Google/SSO 授权 | 人工在窗口授权 → inspect 验证页面 |
| `manual_verify` | 人工核验 | 页面流程需要人工核验/确认 | 人工在窗口完成 → inspect 验证 |
| `custom` | 人工介入 | Agent 无法继续当前流程,需要人工处理 | 兜底 reason,完全自定义文案/选项 |

## 3. 设计决策

### 3.1 为何不拆成三个独立工具

考虑过 `request_human_captcha` / `request_human_real_name` / `request_human_oauth`
三个独立工具,否决:

- **Schema token 成本**:三套描述重复严重,且 schema 重复 LLM 吃 cache 命中率反而下降;
- **代码路径同构**:三个工具本质共享 `HumanAssistHub::request()`,只是文案/标签不同;
- **生态对齐**:atomcode / claudecode 等外部 Agent 的同类能力也是"单工具 + 限定
  enum",不是独立工具(参考 `docs/Agent源码调研/专题/专题-第八轮-...md` §8)。

最终选择:**1 个 control_action + 9 个合法 reason**,LLM 用
`reason=<kind>` 区分语义,TUI 侧根据 reason 切换标签与默认文案,
后台调度仍走 `HumanAssistHub` 单例。

### 3.2 为何 `real_name` / `two_factor` / `oauth` 不合并到 `manual_verify`

`manual_verify` 是**兜底**,代表"我不知道这是什么场景,只能交给人工"。
三个新场景是**已知分类**:

- `real_name` —— 人工动作为"刷脸/上传身份证",交互区是手机/摄像头,
  仅在 headed 模式下可视;
- `two_factor` —— 人工动作为"查看手机 Authenticator / 邮箱输入动态码",
  动态码可走自由文本回复(TUI 直接输入数字),与图形验证码交互完全不同;
- `oauth` —— 人工动作为"在第三方站点击授权/同意",Agent 需 `bring_to_front`
  后人工才能看到授权页。

三个明确语义有利于:

1. **系统提示词能写出精准的作业规范**(例如 `two_factor` 推荐 `input_text`
   而不是 `mouse_click` 后 `inspect`);
2. **TUI 展示标签**("实名认证/人脸核身" vs "人工核验")帮助人工一眼识别该做什么;
3. **错误码与业务分类对齐** —— 未来可以按 kind 做遥测统计,
  例如 "本月 real_name 拦截 12 次",发现某些站点可以接入官方 API 后绕过。

### 3.3 为何 `inspect(info=blockers).available_reasons` 公开合法 reason

不公开的话,LLM 只能从工具 description 反查或死记硬背:

- description 每次变动都可能造成 prompt cache 失效;
- 死记硬背会随 reason 增多而退化。

开放该字段的好处:

- LLM 拿到 blockers 后可直接复用该列表构造 `request_human.reason`,
  schema-valid guarantee,无项可"猜/漏/乱";
- 新增 reason 时只需修改常量 + 该表的自动跟随,LLM 零额外动作。

成本:仅增加 9 个字符串的 context(几 token),可忽略。

### 3.4 顺序遵循"推荐使用顺序"而非"字母序"

```rust
pub const HUMAN_ASSIST_ALLOWED_REASONS: &[&str] = &[
    "captcha", "sms", "qr_login", "login",
    "real_name", "two_factor", "oauth",
    "manual_verify", "custom",
];
```

从高频 / 业务重要 到 兜底,LLM 在 "不确定" 时可以默认按顺序选。
手工保证(`human_assist_allowed_reasons_covers_extensions` 单测断言索引 4/5/6
必须是 `real_name` / `two_factor` / `oauth`)。

## 4. blockers 检测的扩展

在原 4 类关键词表上追加 3 类:

| kind | 关键词样本 | 备注 |
| --- | --- | --- |
| `real_name` | 实名认证 / 实名验证 / 身份认证 / 人脸核身 / 人脸识别 / 上传身份证 / kyc | 中文+英文双语 |
| `two_factor` | 两步验证 / 双重验证 / 二次验证 / 动态口令 / 安全令牌 / google authenticator / 2fa / 2-step / 邮箱验证码 / 邮件验证码 / totp | TOTP / 邮箱验证码 / 动态口令三类合并 |
| `oauth` | 微信授权 / 支付宝授权 / github 授权 / 使用 github / 使用 google 续使用 / 授权登录 / 第三方登录 / sso 登录 / oauth / 应用授权 | "使用 X" / "continue with X" 中英双语引导语 |

设计要点:

- **每种 kind 最多返回 1 条**(原设计保持):避免堆研刷屏;
- **中文+英文双语关键词**(原设计仅中文/英文二选一):兼顾国内/跨境业务;
- **`to_lowercase` 后模糊匹配**(原设计):"GitHub" / "github" / "GITHUB" 都应命中;
- **不会误报**:"使用 github" 是动作而非描述,区别于文本中提到 GitHub。
  设计接受低误报率作为代价,高于"有但漏报"。

## 5. 交互流程

### 5.1 Agent 标准链

```
inspect(info=blockers)  识别到 1+ blocker,取第一个 kind 作为"建议 reason"
                         ↓
control(request_human,  人人介入请求
  reason=<kind>,        (kind 为 blockers 第一个命中或 available_reasons 选一个)
  message=<补充说明>,
  options=[...])
                         ↓
TUI 交互(进度协程 250ms 轮询)  打印蓝色边框块
                         ↓
人工输入选项编号 / 自由文本 / q(取消)
                         ↓
oneshot 回填 → envelope
  code=0 + human_response  继续任务(input_text / inspect 验证)
  code=4001                 超时 / 非 TUI 交互(-p 模式),如实上报
  code=4002                 人工取消,终止该路径
```

### 5.2 TUI 交互细节

交互流程未变(参考 `02-人工介入与窗口可视化方案.md` §5),仅 label / message
根据 reason 不同。例:

```
  ┌─ 🔐 人工介入请求 ────────────────────────────────
  │ 类型: 实名认证/人脸核身   页面: https://xxx/kyc
  │ 说明: 页面要求实名认证/上传身份证/人脸核身,Agent 无法代为核验。
  │       请人工在浏览器窗口完成验证(刷脸/上传证件)后回到终端继续。
  │ 选项:
  │   1. 我已完成人工操作,继续
  │   2. 取消任务
  └──────────────────────────────────────────────
  请输入选项编号或直接输入内容(回车=1,q=取消):
```

### 5.3 额外引导

- `real_name`:可视化场景必须 `open(mode=headed)` 让人工看到页面;
  几乎所有实名/人脸流程都是 摄像头/上传控件 在页面。
- `two_factor`:人工拿到动态码后直接在 TUI 自由文本回复,
  Agent 拿 `human_response` 走 `input_text` 填入验证码输入框。
- `oauth`:人工在第三方页点击"授权/Agree"后跳回原站,Agent `inspect`
  检查 URL 是否回到预期域名。

## 6. 错误码与边界

| code | 含义 | 推荐后续动作 |
| --- | --- | --- |
| 0 | 人工已响应 | 拿 `human_response` 继续(`sms` / `two_factor` 走 `input_text`;其他 走 `inspect` 验证) |
| 1001 | 参数错误(含非法 reason) | `data.allowed` 会列出全部合法 reason,LLM 挑一个重试 |
| 4001 | 超时 / 非交互模式 | 如实告知用户"请在 laew TUI 交互模式(-p / TUI)下重试",不要伪造 |
| 4002 | 人工取消 | 汇总已完成部分,不要继续重试该路径 |

非法 reason 错误响应增加 `data.allowed`(全部 9 个),便于 LLM 不查文档修复:

```json
{
  "code": 1001,
  "message": "非法 reason(允许 captcha/sms/qr_login/login/real_name/two_factor/oauth/manual_verify/custom)",
  "data": {
    "reason": "fingerprint",
    "allowed": ["captcha","sms","qr_login","login","real_name","two_factor","oauth","manual_verify","custom"]
  }
}
```

## 7. 与现有 4 个 reason 的兼容

- 原 6 个 reason 的默认文案、TUI 标签、错误码全部保持;
- `inspect(info=blockers)` 原有 4 类关键词不变(向后兼容);
- `control_action=request_human` schema 未变,新增 reason 仅为 enum 扩展;
- 旧版 plugin / 已缓存的会话上下文不会报错(示例 9 个可选 reason);
- 仅 `manual_verify` / `custom` 作为兜底,任何未覆盖的场景仍可走 `custom` + 自定义 message。
