> 适用平台:全平台(crossp)
> 实现:`src/agent/safety/web_evidence.rs`(判定)+ `src/agent/tool_exec.rs::check_web_evidence`(闸门)
> + `src/agent/system_prompt/web_evidence.rs`(提示词段)
> 关联:`02-人工介入与窗口可视化方案.md`(HITL)、`01-设计与解决方案.md` §17(任务锚点)

## 1. 问题

2026-10-08 实测(`llaew_20261008_124929.log`,「云智眼预发布环境」网页任务):

```text
iter=0 MCP_Web_Use open → code=2001 net::ERR_CONNECTION_RESET
iter=1 Bash  curl -s -o /dev/null -w "HTTP:%{http_code}" …/login
iter=2 Bash  ping -c 2 -t 3 172.27.173.6 ; curl …
iter=3 Bash  nc -z -w 5 172.27.173.6 20518 ; curl -v …
iter=4 Bash  curl -sk https://…
iter=1 Bash  netstat -rn -f inet | grep 172.27 ; ifconfig
…
（统计：tool=Bash × 28,tool=MCP_Web_Use × 8）
```

`MCP_Web_Use(action=open)` 失败后,Agent 自行「降级」成 `curl / ping / nc / netstat /
traceroute` 反复探同一台主机,烧掉大半迭代预算,既没登录也没产出任何结论。

这与既有两条纪律同源且互相印证:

- `MCP_WEB_USE_PROMPT_SECTION` 第 10 条「反伪造红线」:禁止用 Bash 手写本应由
  MCP_Web_Use 产出的截图/抓取证据 —— QC 会对账执行轨迹;
- 任务锚点 L3(第 128 轮):`MCP_Web_Use` 显式 URL 动作越界返回 6001 —— 管的是
  「去哪个站点」,本方案管的是「用哪个工具」。

**核心论据**:Bash 抓来的网页内容,Quality-Check 无法与浏览器执行轨迹对账,
与伪造同质。「用错工具」和「编内容」一样不可核验。

## 2. 为什么不是「只改提示词」

只写提示词不够:模型在 `open` 连续失败、迭代预算吃紧时最容易绕过规则(实测正是
如此)。但无条件硬拦也不行 —— 开发任务里 `curl http://localhost:8080/health`
调试自己的服务是正当且高频的,一刀切会把 laew 变成不能干活的工具。

故取**窄口径**:只在「拿 Bash 去顶替 MCP_Web_Use 探任务目标站点」这一种错路上拦截。

## 3. 判定(五条件全中才拦)

| # | 条件 | 理由 |
| --- | --- | --- |
| 1 | `LAEW_WEB_EVIDENCE` 未关(默认开) | 与 `LAEW_TARGET_ANCHOR` 同构的回退开关 |
| 2 | 工具调用是 `Bash` | 其它工具不涉及 |
| 3 | 当前 Agent 工具面**含** `MCP_Web_Use` | 不含就没有替代路径,拦了等于死路(必经 fail-open) |
| 4 | 命令命中网络取证模式 | 见 §3.1 |
| 5 | 命令里的 host **落在任务锚点域内** | 见 §3.2 |

任一不满足即放行。**锚点为空 = 开放任务,永不拦截** —— 与
`check_open_against_anchor` 的 fail-open 哲学一致:防漂移机制自身绝不能成为新的失败面。

### 3.1 网络取证程序

`curl` `wget` `nc` `ncat` `netcat` `telnet` `ping` `ping6` `traceroute` `traceroute6`
`tracepath` `arp` `nmap` `http` `https` `httpie` `httping` `dig` `nslookup` `host`
`openssl`

只认**命令位**上的 token:首个 token,或前置分隔符(`|` `;` `&` `(` 换行)之后的 token。
所以 `echo 'run curl later'`、`cat notes/curl.md` 不会误判。

**刻意不含** `python` / `node` 等通用解释器 —— 它们既能跑本地脚本也能发网络请求,
按名字拦会误伤大量正常开发任务。漏网的 `sh -c "curl …"` 按 fail-open 放行:
提示词层(§4)负责劝阻,硬闸门只兜最高频的主路。

### 3.2 host 抽取

双通道,与任务锚点口径对齐但更全:

1. 复用 `target_anchor::extract_hosts_from_text` —— `http(s)://` 完整 URL + 带 TLD
   白名单的裸域名;
2. **额外补 IP 字面量通道**(`web_evidence::ip_literals`)——
   `nc -z 10.255.159.58 20122`、`ping 172.27.173.6` 这类内网诊断**不带 scheme**,
   裸主机通道因无 TLD 不会命中,而它们恰恰是实测事故里的主力命令。漏掉这一条等于门形同虚设。

比对走 `target_anchor::host_matches_anchor_domain`(可注册域后缀匹配),所以
锚定 `cloud.example.com` 时 `api.cloud.example.com` 同样在门内。

## 4. 提示词侧

`src/agent/system_prompt/web_evidence.rs` 新增第 20 条(仅注入持有 `MCP_Web_Use` 的
SubAgent-Work),要点:

- 任务目标站点的 DOM / 界面文字 / 截图 / 网络证据**只能**来自 MCP_Web_Use;
- **`open` 失败不是「换个工具再来」的信号**:2001/3001 → 如实报告不可达并停止该路径,
  禁止改用 Bash 探同一台主机、反复重试 `open`、换别的站点替代、编造登录成功;
- Bash 的正当用途(本地构建/测试/格式化/Git/文件/进程管理,以及对**非任务目标站点**的
  查询)不受限制;
- 硬闸门会拦,拦了不要重试同一条命令。

同时修正了 `system_prompt/mod.rs` 里三处**自己在鼓励这条错路**的表述:
Main-Work 的「任务前提验证」原本写「先用 Bash / Read / Glob / Grep / MCP_Web_Use
验证任务前提(目标 URL 是否可访问)」,任务前提验证清单原本直接给出
`curl -s -o /dev/null -w "%{http_code}"` 命令模板 —— 现已改为
「目标 URL 的连通性**只能用** `MCP_Web_Use(action=open)` 验证」。

## 5. 拒绝文案

命中后 `exec_tool_call` 直接返回(不进入 `tool.execute()`),`is_error=true`:

```text
[网页取证纪律] 禁止用 Bash 对任务目标站点做网络探测或抓取:命令涉及 172.27.173.6。
命令: curl -s -o /dev/null http://172.27.173.6:20518/login
任务目标站点(172.27.173.6)的一切证据(DOM / 界面文字 / 截图 / 网络请求)只能来自
MCP_Web_Use —— Quality-Check 会与执行轨迹对账,Bash 抓来的内容无法核验。
请改用 MCP_Web_Use:action=open 打开目标站点拿 page_id → action=inspect 读 DOM/文字 →
action=control 做交互。若 open 返回 2001(连接失败)/3001(未装浏览器),
说明目标不可达或环境缺失,**如实报告即可,不要改用 Bash 绕行、不要换站点替代**。
```

同时打 `warn!` 日志(`网页取证纪律:拦截 Bash 对任务目标站点的网络探测` + host +
command),`--debug` / `--info` 日志里可直接对账。
