## 1. 定位与架构

`MCP_Web_Use` 是 SubAgent-Work 的浏览器操控工具,采用**进程内 MCP 风格服务**:LLM 只见
单工具 + action discriminator,协议细节、浏览器生命周期与页面注册表全部封闭在 CDP 驱动层。

```text
SubAgent-Work(LLM 多轮 Agent Loop)
    └── Tool::execute(MCP_Web_Use)
            ├── action 参数校验与结构化 JSON 信封
            ├── open / list / close / control / inspect / sequence
            └── BrowserManager(chromiumoxide CDP)
                    └── Chrome / Edge / Chromium / Brave
```

设计原则来自外部 Agent 源码调研:

1. 单工具 action 分发优于多个细粒工具,可减少 Schema token 并提升协议缓存命中;
2. 浏览器自动化必须形成「探索 → 操作 → 验证」闭环,DOM/Elements 优先,截图只作兜底;
3. page_id 是唯一页面句柄,点击或 `window.open` 派生的新页必须回传新句柄;
4. 所有结果使用统一信封,便于 Agent 按错误码机械恢复,避免崩溃或伪造结果。

## 3. 浏览器生命周期

- 首次 `open` 启动浏览器。**默认 `mode=headed`(可见窗口,第 139 轮)**,使用
  一次性 user-data-dir,不干扰用户日常浏览器;`mode=hidden`/`new_headless` 用于
  静默后台跑;`connect_url` 可接管已开启 `--remote-debugging-port` 的浏览器;
- **缺省模式的唯一真源是 `src/agent/browser_mode.rs::BrowserMode::from_env_or_default()`**,
  优先级:工具参数 `mode` > `LAEW_BROWSER_MODE` > 兼容开关 `LAEW_BROWSER_HEADLESS`
  (仅识别 false 系 = 有头)> 缺省(有 GUI 会话 → `headed`;无 GUI 会话 → `hidden`)。
  GUI 会话探测见 §19.2;
- **启动窗口全模式默认 1920×1080(1080p,第 125 轮)**,小屏笔记本按屏幕工作区
  **自动收边**保证完整可见、页面视口不低于 720p(第 139 轮,详见 §19.4);
  headless 附加 `--hide-scrollbars`(截图不被滚动条蚕食/遮挡);
  内容仍超视口时 open 后自动扩展视口到 ≤2560×1440(2K),详见 §16;
- 浏览器探测顺序:`LAEW_BROWSER_PATH` → Chrome → Edge → Chromium → Brave →
  chromiumoxide 默认检测;未安装时返回 `code=3001` 与安装引导;
- `page_id` 形如 `p_ + 8 位 hex`,对 LLM 不透明;
- 点击链接、中键打开、`window.open`、`new_tab` 后,BrowserManager 通过页面差集 adopt
  新 target,并在响应中返回 `spawned_page_id`;
- 页面注册表跨任务存活,SubAgent 任务入口会注入「已打开的浏览器页面」提示,可复用登录态;
- `close` 幂等;launch 模式最后一个页面关闭后回收浏览器进程、handler 与临时 profile。

## 4. 两种工作模式

### 4.1 单步执行模式(默认)

一次调用一个动作,适合未知页面探索、selector 调整、Console/Network 调试、下载目标确认,
以及支付、删除、确认提交、登出等高风险操作。

```json
{
  "action": "inspect",
  "page_id": "p_ab12cd34",
  "info": "elements",
  "params": {"selector": "textarea", "include_text": true}
}
```

推荐路径:

```text
open → inspect(elements/dom) → control(input/click/wait) → inspect 验证 → close
```

### 4.2 连续执行模式

先在单步模式下探索结构,再把已经明确的动作链交给 `sequence` 一次执行。适合稳定表单、
多页浏览、采集、输入→提交→等待→提取等流程。

```json
{
  "action": "sequence",
  "page_id": "p_ab12cd34",
  "stop_on_error": true,
  "steps": [
    {"action":"control","page_id":"$page_id","control_action":"input_text",
     "params":{"selector":"textarea","text":"你好 laew","use_js":true}},
    {"action":"control","page_id":"$page_id","control_action":"click",
     "params":{"selector":"button[type=submit]"}},
    {"action":"control","page_id":"$page_id","control_action":"wait",
     "params":{"selector":"[class*=result]","timeout_ms":60000}},
    {"action":"inspect","page_id":"$page_id","info":"elements",
     "params":{"selector":"[class*=result]","include_text":true}}
  ]
}
```

规则:

- `steps` 为 1~24 个对象,每项结构与单步调用一致,禁止嵌套 `sequence`;
- `stop_on_error=true`(默认)失败即停止;`false` 可采集全量执行报告;
- 响应逐步返回 `{index,action,code,message,data}`,顶层返回 `completed`、
  `failed_at`、最终 `page_id` 与最近 `spawned_page_id`;
- 两种模式可任意混合、多次调用;
- 不可逆或高风险动作不得进入批处理,必须单步执行并在动作后检查页面状态。

### 4.3 page_id 占位符

连续模式支持递归字符串替换:

| 占位符 | 语义 |
| --- | --- |
| `$page_id` / `${page_id}` | 当前页面 |
| `$spawned_page_id` / `${spawned_page_id}` | 最近派生页面 |

`open` 返回的 `page_id` 成为当前页;响应携带 `spawned_page_id` 时默认自动跟随新页,
保证「点开链接 → 在新页继续操作」。若需留在原页,该步骤可设置
`follow_spawned=false`,此时仅记录 `$spawned_page_id`,不切换当前页。

## 5. 下载管理

### 5.1 调用

```json
{
  "action": "control",
  "page_id": "p_ab12cd34",
  "control_action": "download",
  "params": {
    "url": "https://example.com/report.pdf",
    "save_dir": "downloads/report",
    "filename": "report.pdf",
    "timeout_ms": 120000
  }
}
```

`url` 与 `selector` 二选一:

- `url`:页面内注入一次性隐藏 `<a download>` 触发;
- `selector`:点击页面既有下载链接或按钮,适合前端脚本生成地址。

参数约束:

- `save_dir` 相对路径以工作目录为基准,目录自动创建并 canonicalize;
- `filename` 仅允许文件名,自动 `file_name()` 归一化,禁止路径穿越;
- `timeout_ms` 缺省/0 为 120000,范围 1000~300000。

### 5.2 CDP 链路

```text
Browser.setDownloadBehavior(allowAndName, downloadPath, eventsEnabled=true)
→ 注册 Browser.downloadWillBegin / downloadProgress
→ selector click 或隐藏 anchor 触发
→ 按 guid 过滤 begin/progress
→ 等待 completed
→ 校验文件真实存在
→ filename 存在则安全重命名
→ stat 返回绝对 save_path 与 byte_size
```

成功数据包含 `guid`、`url`、`suggested_filename`、`save_path`、`byte_size`、
`received_bytes`、`total_bytes`、`state`、`elapsed_ms`。不得凭 HTTP 200 或点击成功
推断文件已落盘,必须以 CDP completed 事件和文件存在为准。

## 6. 统一信封与错误恢复

所有 action 返回:

```json
{"code":0,"message":"ok","data":{}}
```

| code | 含义 | Agent 策略 |
| --- | --- | --- |
| 0 | 成功 | 读取 data / page_id |
| 1001 | 参数错误 | 修正 action、必填字段或枚举 |
| 2000 | page_id 失效 | `action=list` 重新同步 |
| 2001 | 浏览器断连或启动失败 | 重新 `open`;无浏览器则报告安装引导 |
| 2002 | 动作失败 | 换 selector / `use_js` / 等待策略;下载失败检查地址与目录 |
| 2003 | 页面崩溃 | 重新打开页面 |
| 3001 | 未检测到浏览器 | 如实告知用户安装 Chrome/Edge/Chromium,不重试 |
| **6001** | **目标站点越界(任务锚点)** | **立即停止该路径,如实报告「目标站点不可达或未指定」并结束本单元;严禁改用其它站点、搜索引擎、缓存或名称相似的替代品 —— 可以失败,不可以乱跑**(第 128 轮,见 §17) |

Agent Loop 已内置浏览器辅助:

- `open` 成功后注入 `next_steps` 四步引导;
- 同 selector 连续失败 ≥2 次注入换姿势提示;
- SubAgent 出口解析真实页面文本,避免只输出「已提取 N 字符」占位;
- System Prompt 强制反伪造:禁止用 Bash/Write 伪造截图、下载文件或网页抓取证据。

## 7. 安全边界

1. 登录凭证只能使用用户明确提供的值,不得编造;
2. 只读可回答的问题优先 `inspect`,不做写操作;
3. 支付、删除、确认提交、登出、批量发送等不可逆动作必须单步执行并二次验证;
4. `eval_js` 与 `dispatch_event` 只用于当前页面任务,不得绕过用户意图修改外部状态;
5. 下载路径和文件名受限,最终文件必须来自受限目录并真实存在;
6. 大 DOM / 截图沿用截断与自动落盘策略,避免 tool_result 撑爆上下文;`eval_js`
   返回值另有**复合值体积闸门**(第 135 轮,数组/对象同样受 20KB 闸门约束,
   详见 §18.1)。
7. **任务锚点(第 128 轮)**:用户原文显式给出的目标站点(`https://x.com` / 域名 / 路径)
   是唯一允许的导航目的地;`open` / `navigate` / `new_tab` 指向锚点外站点会被工具层直接
   阻断(代码 6001),不得以「超时后换其它站」「图方便用类似名称」等理由改派 —— 这种「漂移」
   是 2026-09-24 实测事故(`llaew_20260924_151442.log`)中 Agent 在错误站点判 ✅ 成功的根因。
   实现与判据见 §17;设计依据对齐 `专题/专题-沙箱设计深度分析.md:1973-1994` 的
   `NetworkAcl.allowed_domains` 语义(空白名单 = 不限制,非空 = 严格)。

## 14. 第 99 轮(2026-09-20):验证码 OCR / eval_js 容错 / 页面卫生 / QC verdict 修复

> 背景:云智眼预发布环境登录任务(10.255.159.58:20122)实测三次单元执行累计 550s+
> 未完成登录(迭代黑洞:140KB 验证码 data-url 反复 Bash/Read 解码;`download
> url=about:blank` 挂 120s;eval_js `return` 语句 SyntaxError;QC JSON 缺 `verdict`
> 白耗重试;三次 open 泄漏 3 个页面)。方案全文:`tmpPlan/2026-09-20_01-MCP_Web_Use效率与验证码OCR根治方案.md`。

### 14.1 截图即文字:OCR 能力(A/C)

- **`inspect info=ocr`**(新增第 15 个只读维度)= 截图 + OCR 一步:响应带
  `ocr_text` / `ocr_block_count` / `save_path`;
- `control(screenshot)` 新增 `params.ocr=true`(同上)+ `params.region{x,y,width,height}`
  (OCR 词块过滤,落盘仍为整帧)+ `params.return_base64=true`(显式内联,默认不返回);
- **screenshot 一律落盘**(save_path 指定,否则临时目录),不再内联 base64 ——
  文本模型无法消费图片,base64 内联纯属上下文浪费;
- 实现复用 `agent::window::macos_vision_ocr`(Vision 框架,`ocr_png_file` 新入口);
  图像来自 CDP 截图字节,**不触碰 CGWindow,无需屏幕录制权限**;非 macOS 返回
  结构化 `ocr_error` 引导(如实上报等待人工,禁止猜验证码)。

### 14.2 eval_js 容错与结果净化(B)

- 参数别名:`expression` 之外接受 `function` / `js` / `code`(含 `_b64` 变体);
  缺参错误列出全部合法名(根治 LLM 参数名摸索,实测连续 4 次迭代猜 `function`);
- **`return` / 多语句容错**:首次按原样评估;失败且表达式非函数形态时自动包
  IIFE(`await_promise` 时 async IIFE)重试一次,响应 `wrapped_iife:true`;
- **大结果净化**:`data:` URL 或 >2000 字符字符串自动落盘(临时目录),响应改给
  `result_head`(160 字)+ `result_len` + `saved_to` + 引导 hint —— 根治 140KB
  验证码 data-url 灌爆上下文,及其连锁反应(download 参数超限被截断 → schema 校验失败)。

### 14.3 download 快速失败与 data: 直存(D)

- `data:` URL 直接解码落盘(base64 / 百分号编码载荷),不走 CDP 下载事件
  (Chrome 对 data: 锚点不产生可靠下载事件);响应 `mode:"data_url"`;
- `about:` / `blob:` / `javascript:` 立即结构化报错并给出替代指引 —— 根治
  `download url=about:blank` 白等 120s。

### 14.4 页面卫生(E)

- **open 同 URL 复用**:已存在同 URL 存活页面时默认导航刷新并返回同一 page_id
  (`reused:true`;URL 归一化 = 去尾部 `/` 与 `#fragment`),`reuse:false` 强制新开
  —— 根治「局部重试/重复 open 泄漏页面」(实测 3 次尝试泄漏 3 页);
- **`close page_id="all"`** 一键关闭全部页面并回收浏览器(任务收尾清场)。

### 14.5 QC verdict 语义修复(F,`agent/quality.rs`)

- `repair_quality_json`:反序列化前按信号推断补 `verdict`(`pass` bool →
  `result`/`status`/`conclusion` 字符串关键词 → `issues` 非空 → Fail),无信号
  保持 fail-closed;`source` 缺失用调用方补齐(`serde_json::to_value` 互逆保证);
  `retryable` 缺失按 verdict 推断;
- 三个 QC 提示词(单元/Main-Work/Plan)统一追加 `QC_JSON_SHAPE_HINT`
  (「第一个字段必须是 verdict」+ 完整 JSON 示例),提示词 + 解析端双保险。

## 16. 第 125 轮(2026-09-23):视口基准 1080p 与 2K 自动扩展

> 背景:实测发现 `mode=hidden`(内存无头浏览器)默认视口 1440×900 过窄 ——
> 现代 Web 应用(min-width > 1440 的后台/SaaS/AI 站点)横向被裁,截图显示不全,
> 视口外元素 `Input.dispatchMouseEvent` 坐标落不到目标,**页面显示不全时其他操作
> 也无法进行**。需求:默认最小 1080p(1920×1080),显示不全可自动扩展到 2K
> (2560×1440)。全平台(macOS/Windows/Linux)同一 CDP 机制,行为一致。

### 16.1 三层能力

| 层 | 能力 | 实现 |
| --- | --- | --- |
| **启动基线** | 全模式(hidden/new_headless/headed)默认窗口 **1920×1080**;headless 追加 `--hide-scrollbars`(滚动条不蚕食 innerWidth、不遮挡截图) | `browser.rs::default_window_size()` + launch args |
| **自动扩展** | `open`(新建/复用两路径)导航完成后测量 `innerWidth/Height` vs `scrollWidth/Height`(documentElement/body 双源取大),溢出即 `Emulation.setDeviceMetricsOverride` 撑到 **≤2560×1440**(保持当前 DPR,mobile=false);`auto_expand_viewport=false` 关闭 | `browser.rs::viewport_fit_plan()`(纯决策)+ `BrowserManager::fit_viewport_to_content()`;调用点 `mcp_web_use/mod.rs::run_open` |
| **观测与逃生** | open 回 `data.viewport`(expanded/from/to/content/clamped/hint);`inspect(info=viewport)` 附 `overflow{horizontal,vertical}` + `next_action`;非整页截图溢出时附 `content_overflow` hint(指引 `full_page=true`);`set_viewport` 与 open 窗口参数同区间 clamp(320~7680 / 240~4320,DSF 0.5~4.0) | `mcp_web_use/{control,inspect}.rs` |

### 16.2 关键决策

1. **扩展机制选 `Emulation.setDeviceMetricsOverride` 而非 resize 真实窗口**:
   Playwright/Puppeteer 控制 headless 视口的标准做法;截图与输入坐标都按新视口
   映射(CDP 坐标恒为 CSS 像素,链路内无 DPR 换算 —— 外部调研亦无此类坑记录);
   `Browser.setWindowBounds` 在新版无头下语义不保证,真实窗口留给 headed +
   `set_window`(第 100 轮既有)。
2. **只放大不缩小、上限硬截 2K、容差 2px**:亚像素布局/1px 边框误差不触发;
   内容超 2K 时 `clamped:true` + hint 指回 `full_page=true` / 更大
   `window_width` / `set_viewport` 逃生,不无限撑大拖垮渲染。
3. **纵向一并扩展(≤1440)**:横向溢出是"不可点"根因,纵向溢出是"截图缺区域"
   根因,一次 fit 两个都解;超长页(>1440)保持滚动 + full_page 路径。
4. **覆盖生命周期**:device metrics 覆盖对页面内后续导航持续生效(SPA 站内跳转
   不再回退窄视口),`sync_viewport` / `set_window` 显式清除(第 100 轮既有语义,
   两者响应会撤销自动扩展,文档与 hint 已注明)。
5. **单浏览器复用不冲突**:`window_size` 只在首次 launch 生效(第 100 轮语义不变),
   但 fit 是 per-page 覆盖,复用实例后新开的每个页面各自自适应。
6. **决策函数纯净化**:`viewport_fit_plan(iw,ih,sw,sh,max_w,max_h)` 零 IO 可单测,
   CDP 交互集中在 `fit_viewport_to_content`,失败 fail-open 不阻断 open。

### 16.3 提示词与 LLM 作业规范

SubAgent-Work MCP_Web_Use 第 17 条扩展「视口显示不全对策」:元素在视口外不可点
时先 `inspect(info=viewport)` 看 `overflow.horizontal`,横向溢出必须先扩视口
(重开 open 自动扩 / `set_viewport` 手动)再点击,不得对着看不见的元素反复
click;`clamped=true` 或截图带 `content_overflow` 时按 hint 走 full_page。

### 16.4 验证

- 单测:`viewport_fit_plan` 7 组(无溢出/横向/纵向/截 2K/超大窗口维持/亚像素取整/
  零值退化)、`default_window_is_1080p`、`auto_expand_enabled` 默认开、

### 18.1 eval_js 复合值体积闸门

第 99 轮的 `sanitize_eval_result` 只对 `Value::String` 生效,`Array` / `Object`
直接原样透传:

```rust
let s = match &val { Value::String(s) => s, _ => return val };  // ← 复合值零闸门
```

于是 MCP_Web_Use 成为全工程**唯一没有工具级输出预算的富数据工具**(Bash 工具有
`MAX_OUTPUT_CHARS = 30_000` + `bash_spill.rs`)。实测第一轮 24 次迭代里出现 4 次
8.5KB~19.2KB 的大对象返回,其中一次 17440 B **落盘后 Agent 从未 Read** —— 白烧一轮
迭代加一次 LLM 往返。

第 135 轮把净化逻辑独立到 `eval_sanitize.rs` 并扩展到任意值:

| 返回值形态 | 判据 | 处理 |
| --- | --- | --- |
| `data:` URL 字符串 | 前缀 `data:` | 解码后按 mime 落盘 |
| 长字符串 | 字符数 > 2000 | 落盘,只回 head + 路径 |
| **数组 / 对象** | 序列化**字节**数 > 20000 | 先就地裁剪,仍超限再落盘 |

就地裁剪而不是整块丢弃:数组保留前 50 项(每项只留标量字段),追加
`__skipped__` / `__truncated__` 标注;裁剪后仍超限才落盘,落盘返回**与字符串分支
同一套信封形状**(`result_truncated` / `result_head` / `byte_size` / `saved_to` /
`hint`),模型不必学第二种格式。顺带修掉**同毫秒并发落盘互相覆盖**(文件名加进程内
原子递增序号)。

小结果一字不动,纯向后兼容。

### 18.2 `inspect(info="extract")`:结构化列表 / 表格抽取

**在此之前**,把资讯站点的文章列表变成结构化数据的唯一手段是手写 `eval_js`。
实测 17 次 eval_js 踩了四个坑:猜字段层级(标题全空 → 召回率 14→9 倒退)、大对象直灌、
滚动 / 懒加载试错(17 次迭代 158 秒,最终 0 条被用上)、收口纪律缺失。

`extract` 把「选择器定位 + 字段投影 + 关键词过滤 + 时间窗 + 排序 + 截断」下沉到
工具层一次完成,**在页面内过滤、只回精简字段**:

```json

 "params":{"item_selector":".kr-flow-article-item",
           "fields":{"title":{"selector":"h3 a","required":true},
                     "time":{"selector":"time","attr":"datetime"},
                     "summary":{"selector":".descript","max_chars":300}},
           "filter":{"keywords":["AI","大模型"],"time_field":"time",
                     "since":"2026-10-07 06:00","sort":"time:desc"}}}
```

三个设计要点:

1. **`probe=true` 侦查模式**:只扫页面上重复出现的类名与常见列表选择器,返回
   `likely_item_classes` / `common_selectors`,让模型一次调用就知道该用哪个
   `item_selector`,免去实测里 5~8 轮盲试;
2. **`fields` 缺省不给「默认 title/summary」**,只回通用 `text` + `__url`。给默认
   字段等于又替模型猜了一轮页面结构 —— 正是事故根因;通用投影只回事实,让模型据此
   写 `fields` 再调一次,比猜错字段名浪费一整轮便宜;
3. **时间在页面本地时区解析**:支持中文相对时间(`3小时前` / `刚刚`)、ISO、
   `YYYY-MM-DD HH:mm` 与 Unix 秒。`since` / `until` 的日历分量由**页面内**按本地
   时区换算(开发期用 node DOM 桩实测到:Rust 侧按 UTC 换算会让东八区整整差 8 小时,
   把本该命中的条目全部筛掉)。自诊断字段 `unparsed_time_fields` / `time_range` /
   `truncated` / `scanned` 让模型据下一步动作。

### 18.3 `inspect(info="page_state")`:页面 SSR 注水数据直读

现代资讯站点的列表数据几乎都是 SSR 注水的(`window.__NEXT_DATA__` /
`window.initialState` / `__NUXT__` 等),前端再渲染成 DOM。实测第二轮成功路径正是
`eval_js` 直读 `window.initialState…itemList` —— **一次调用、1.4 秒、零滚动**把整件事
做完。但在此之前模型只能**猜全局变量名**(全仓 `grep __NEXT_DATA__` 零命中,工具
description 也只字未提),猜错就退化成 DOM 遍历,而虚拟滚动 / 懒加载列表页的 DOM 是残缺的。

`page_state` 把「有哪些注水点 → 各是什么结构 → 取哪条路径」变成一次可枚举的调用:
内建 8 个候选 + `probe_window` 一次扫出 window 上所有 `__` 前缀键名 + 一层结构,
顺带提取 JSON-LD。三闸裁剪(`max_bytes` 20000 / `max_depth` 8 /
`max_array_items` 200),**被裁掉的部分显式列进 `dropped_paths`** —— 必须显式告知,
否则模型会误以为「数据就这么多」,在错误假设上继续下游推理。

### 18.4 目标漂移误报根治(`target_drift:div.kr`)

事故第一轮的唯一**强信号**是 `target_drift:div.kr(anchor=36kr.com)`。全会话只有
2 次真实导航且都在 `36kr.com`,**从未访问过 div.kr**。它的唯一来源是一次 `batch`
点击的 CSS 选择器:

```json
{"selector": "div.kr-loading-more-button"}
```

命中链路:`detect_target_drift` 对整段 `args_json` 跑 `extract_hosts_from_text`,
后者的裸主机副通道要求前置分隔符 ∈ `[\s/\\(`\[{<"'，。、;；]` —— JSON 里的 `"`
**正在这个集合内** —— 于是从 `div.kr-loading-more-button` 里截出 `div.kr`,末段 `kr`
又命中 `KNOWN_TLDS`。**CSS 类名不是域名。**

`target_drift` 是强信号,进 `ExecutionTrace::is_failed()` 后被 `quality.rs` 的
`hard_strong_failure` 强制把 QC 的 pass 降级为 Fail —— 一个纯误报把本质上已抓到
数据的单元判死,且单元不可恢复。

第 135 轮双重根治:

1. **裸主机通道拒识标识符续接**:匹配结尾若紧跟 `-` / `_` / `.`,说明后面还有更长
   标识词(CSS 类名 / JS 标识符 / 文件名),丢弃不作为主机。真主机不受影响
   (`example-site.com` 整体匹配,尾字符不是 `-`)。该函数被 `web_evidence.rs` 复用,
   属共性修复;
2. **`detect_target_drift` 收窄到「显式导航目标 URL」**:解析参数 JSON 后按 action
   精确取导航位字段(`open` 的顶层 `url`;`control` 里 `navigate` / `new_tab` /
   `download` 的 `params.url`;`sequence` / `batch` 的 `steps[].params.url`),这些字段
   只走 **scheme 通道**不再走裸主机副通道,并**跳过 `ok == false` 的条目**(被 L3 工具层
   6001 拦下的越界尝试已阻断 + QC 依据①覆盖,不重复计强信号)。

真实漂移防护不削弱:`navigate` / `new_tab` 指向锚点外站点仍会被 6001 直接阻断,
点击派生的落地页由 QC 结合 `final_url` 事后对账。

## 19. 第 139 轮(2026-10-09):浏览器可见模式统一与窗口收边

> 背景:实测(2026-10-09 云智眼预发布环境,macOS `--debug`)发现三件事 ——
> (a) Terminal 里跑 laew 不弹 Chrome 窗口,VS Code 终端里跑弹了,被当成「终端差异」;
> (b) 可见模式下窗口显示不全;
> (c) 人工介入弹窗的输入框不好复制粘贴、其它文案不能选中复制。

### 19.1 根因一:缺省模式是硬编码的,环境开关是死代码

`mcp_web_use::run_open` 原本这样解析模式:

```rust
let requested_mode = match str_arg(&args, "mode") {
    Some("headed") | Some("head") => BrowserMode::Headed,
    Some("new_headless") | Some("old_headless") => BrowserMode::NewHeadless,
    _ => BrowserMode::Hidden,   // ← 硬编码
};
```

**`BrowserMode::from_env_or_default()` 在整条工具链上零调用**(只有单测调它)。
后果是 `LAEW_BROWSER_MODE` / `LAEW_BROWSER_HEADLESS` 形同虚设,「是否弹窗」
完全取决于 LLM 这一轮有没有自己传 `mode=headed` —— 两次实测恰好一次传了一次没传,
看起来像终端差异,实际是**同一份代码同一条路径的随机性**。这类不可复现的现象
最容易被误判成环境问题,根治方式是让缺省值落在代码里、且唯一真源可查。

### 19.2 三层修复

| 层 | 改动 | 位置 |
| --- | --- | --- |
| **决策唯一真源** | 新模块 `src/agent/browser_mode.rs`:`BrowserMode::{DEFAULT=Headed, from_arg, from_mode_env_value, from_legacy_headless_value, resolve(has_gui)}` + `has_gui_session()` | 新增 |
| **接线** | `run_open` 的缺省改为 `BrowserMode::from_env_or_default()`;`BrowserManager` 侧 `pub use` 再导出,外部 `crate::agent::browser::BrowserMode` 路径零改动 | `browser.rs` / `mcp_web_use/mod.rs` |
| **无 GUI 会话兜底** | `has_gui_session()`:`LAEW_FORCE_HEADLESS` / `CI` 非空 / `SSH_CONNECTION`·`SSH_TTY` / Linux 无 `DISPLAY`·`WAYLAND_DISPLAY` / macOS `launchctl managername` 非 `Aqua` → 一律回退 `Hidden` | 同上 |

决策优先级(自上而下):**工具参数 `mode` > `LAEW_BROWSER_MODE` > `LAEW_BROWSER_HEADLESS`
(仅识别 false 系 = 有头)> 缺省(有 GUI 会话 → headed;否则 hidden)**。

> 兼容旧行为:`Hidden` 与 `NewHeadless` 在驱动层本就都调 `new_headless_mode()`,
> 三档枚举实际只有两档;本轮保留三档字符串不变,避免破坏既有响应契约。

### 19.3 根因二:窗口固定 1920×1080,不按屏幕收边

原实现无条件 `--window-size=1920,1080`,两处不足:

1. **不按屏幕裁剪** —— MacBook 逻辑屏常见 1440×900 / 1512×982,1920 宽的窗口放不下,
   右侧与底部被挤出屏幕外,用户看到的就是「显示不全」;
2. **不区分 chrome 高度** —— `--window-size` 设的是**外框**,headed 下标签栏 + 地址栏 +
   书签栏约吃掉 120~145px,页面真实视口只有 ~1920×935。需求要的是「视口至少 720p」,
   而原代码只保证外框尺寸,没有任何一处保证视口尺寸。

### 19.4 收边方案:不自建跨平台屏幕 FFI,问浏览器要

关键洞察:`window.screen.availWidth/availHeight` 就是浏览器算好的**屏幕工作区**
(已扣 Dock / 任务栏),`outerWidth/outerHeight - innerWidth/innerHeight` 就是
**浏览器 chrome 高度**。这两个值天生跨平台、随 DPR 正确换算,比自建 macOS
`NSScreen` / Windows `SystemParametersInfo` / Linux `xrandr` 三套原生 FFI 可靠得多
且维护成本低一个数量级。

新增纯函数(全部可单测):

```
headed_window_plan(cur_w, cur_h, avail_w, avail_h, chrome_h) -> Option<(win_w, win_h)>
```

规则:①`avail ≤ 0`(探测失败)→ `None`,不猜不动;②上限 `cap = avail - 2×8px`,
保证窗口完整落在屏幕内;③窗口高下限 `720 + chrome_h`、宽下限 `1280`,
屏幕给不出时与 `cap` 取交(如实退让,不硬撑出屏外);④目标是**默认 1080p**
clamp 进 `[lo, cap]`,小屏自动降到「屏幕能给的、视口仍 ≥720p」的最大值。

`BrowserManager::fit_headed_window` 在导航完成后实测 → 决策 → 有差异走既有
`Browser.setWindowBounds` → 回读校验;结果回 `data.headed_window`
(`adjusted` / `measured` / `applied`)。fail-open,不影响 open 成功语义。

> **顺序约束**:`fit_headed_window` 必须**早于** `fit_viewport_to_content` ——
> `setWindowBounds` 会清除 `Emulation.setDeviceMetricsOverride`,晚一步会把刚扩好的
> 视口覆盖抹掉。两处调用点(`run_open` 的新建与复用路径)都按此顺序。
