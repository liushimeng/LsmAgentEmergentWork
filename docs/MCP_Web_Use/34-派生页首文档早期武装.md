# 派生页首文档早期武装（第 180 轮）

> 2026-10-18 · 承接 [33-注入面收敛与反检测自证升级](./33-注入面收敛与反检测自证升级.md)
> §六「遗留与下一步」第 1 条（同 32 §九.2）：**派生页（`target=_blank` /
> `window.open` / `control(new_tab)`）的首请求仍可能裸跑**。
>
> **本轮主线**：把「页面自己派生的新标签页」从**导航提交那一刻**起就纳入反检测处置
> —— 此前它们要等到 `adopt_spawned_pages`（触发动作收尾时）才被武装。两档
> （非侵入式 `fidelity` / 侵入式 `hardened`）共同受益，档位语义与既有边界不变。

## 一、问题：派生页有一段「无主」期

laew 自己 `open` 的页面在 178/177/175 轮已闭环：`about:blank` 起页 → UA 去令牌 →
屏幕几何自洽 → 隐身脚本注册 → 真实 URL 只加载一次。但**由页面自己派生**的新标签页
（点击 `<a target=_blank>`、`window.open`、`control(new_tab)` —— new_tab 正是
`window.open` 实现）走的是另一条路：target 由浏览器自己创建，laew 只能在
`adopt_spawned_pages_ex`（触发动作收尾时巡检 `browser.pages()`）之后才能碰它。

源码级核对（chromiumoxide 0.9.1 `handler/target.rs::poll`）确认：handler 对**每一个**
`Target.targetCreated` 都会自动 attach 并跑 init 链（`Runtime.enable` / `Network.enable` /
`Target.setAutoAttach` / 无头档 `setDeviceMetricsOverride(1920,1080)`），但这条 init 链
**不含任何 laew 的反检测处置**。于是在 adopt 之前，派生页读到的环境是：

| 信号 | 无头档读数 | 定级 |
| ---- | ---------- | ---- |
| `screen.*` | `800x600`（init 链的覆盖**不带 screen 字段**，第 175 轮已核）而 `outer=1920` | **`screen_geometry_impossible` 硬判据** |
| `navigator.userAgent`（页面侧） | 带 `HeadlessChrome` 令牌（UA 覆盖还没下发） | 高危令牌 |
| plugins/languages/WebGL 兜底串等 | 保真回填未挂 | 风控加权项 |

其中**屏幕几何这条最重，且是实打实的存量缺陷**：`adopt_spawned_pages_ex` 的收编序列
（enables → UA 清理 → inject_stealth → 高亮 → 管控 → 跟随）**从来没有
`apply_screen_sync_override`** —— 即使 adopt 抢在文档提交之前完成，无头档派生页的
`screen` 仍是 800x600，直到内容超视口触发 2K 扩展才顺带修复。也就是说：**无头档的
每一个派生页都在带着 `outer > screen` 这个物理不可能的硬判据跑**，
`stealth_selfcheck_smoke` 只测了 `open` 直开的页面，一直没覆盖到它。

此外 adopt 的触发面本身有窗口期：`action_may_spawn_page` 只圈定「点击/键盘/导航/表单/
dispatch_event」收尾才巡检，**sequence/batch 在批内不巡检**（第 140 轮提速的取舍），
批内前几步派生的页要等到批结束才被武装；等待类动作期间页面自己开的页同样无主。

## 二、关键机制发现：chromiumoxide 的「提交门」

设计初稿是「watcher 抢 document-start」。真机实验（Windows 11 + Chrome 155，
子页响应分别延迟 400ms / 1500ms）**推翻了这个目标并钉死了物理下限**：

- chromiumoxide 的 `Target::poll` 在 target init 链（`InitializingFrame` →
  `InitializingNetwork` → `InitializingPage` → `InitializingEmulation`）任一环节
  Pending 时**提前 return**，不排空页面句柄的消息队列 —— 也就是说，**通过页面句柄
  发出的一切 CDP 命令都被压在 init 链之后**；
- 而 init 链里有命令（如 `Page.getFrameTree`）要等 provisional 导航**提交**才返回
  —— 实测 watch 侧首条命令（`addScriptToEvaluateOnNewDocument`）的响应**与提交
  同刻到达**（400ms 延迟时 +402ms，1500ms 延迟时 +1546ms，两个数量级都严格对齐）。

结论：**派生页首个文档的 document-start（内联脚本级取样）经 chromiumoxide 通道物理
赶不上**，武装的现实锚点是「提交 + ~5ms」。这不是本实现的缺陷，是通道的属性 ——
真正的 document-start 抢跑需要 `Target.setAutoAttach(waitForDebuggerOnStart=true)`
在 target 启动前暂停导航，而该开关与 chromiumoxide 自身的 attach 状态机互相干扰
（无人调 `Runtime.run` 则新页永不加载，含我们自己的 `open` 流程），需 fork CDP
客户端，与 32 §五 `Runtime.enable` 处置同结论。

提交门对**真实站点**的实际暴露比测试模型小：本地测试服务器整包响应 → 提交即解析
（最坏情况）；真实站点 head 字节随 body 流式到达、风控 SDK 多在自身脚本加载后取样
（又一轮网络往返），多数落在提交 + 数百毫秒之后 —— 正好在武装窗口内。

## 三、方案：事件驱动的「提交即武装」watcher

### 3.1 触发源：`Target.targetCreated` 事件流

chromiumoxide 的 `Browser::event_listener::<EventTargetCreated>()` 订阅浏览器级
target 创建事件（与既有 `EventDownloadWillBegin` 订阅同机制）。浏览器实例建立时
（仅 launch 模式）起一个后台 watcher 任务消费这条流。

**资格过滤**（纯函数，单测锁死）：`type == "page"` 且 **`opener_id` 存在**。
`opener_id` 是「创建该 target 的页面」，`target=_blank` / `window.open`（含
`noopener` —— TargetInfo 的 opener 是创建者而非 `window.opener` JS 关系）都带；
而 laew 自己 `open`/`new_window` 经 `Target.createTarget` 创建的页 **opener 恒空**，
天然被排除 —— 与 `new_page_impl` 的同步武装零重叠零互踩。浏览器初始空页签、
人工 Ctrl+T 也无 opener，同样不碰。

### 3.2 页面句柄与配置：有界锁解析

`Browser` 非 `Clone`（内含 `Child`），watcher 不能自带句柄。设计成：watcher 只持有
事件流；事件到达后经 `BrowserManager::spawn_arm_resolve` 解析 `Page` + 配置快照 ——
**全程有界**（锁等待 ≤1s/次、总预算 3s；锁内 `get_page` ≤2s；attach 完成前的
NotFound 是瞬时失败，静默重试到界）。拿不到就放弃本页，交 adopt 收编兜底
（fail-open，页面自身不受任何影响）。

> 锁纪律的由来：初版实测 watcher 被 adopt **饿死** —— 旧 adopt「全程持锁」把噪声
> 复查的 500ms 等待与逐页武装（含阻塞在 provisional 导航上的 UA 探测，实测 ~1.4s）
> 全压在管理锁上，watcher 的锁等待只能排队。本轮把 **adopt 重构为三段式**
> （快照-武装-登记）：阶段 1 锁内扫描分类 + 期望态快照；阶段 2 **锁外**做全部
> 逐页 CDP（噪声复查/武装）；阶段 3 锁内登记（**target 去重守卫**防并行 adopt
> 重复登记）。与 `list_pages` 已有的「快照-探测-清理三段式」同一纪律，重构后
> watcher 的句柄解析稳定在 ~40ms。

### 3.3 武装序列

拿到句柄后按序（全部命令经提交门在**提交时刻**生效，顺序即落地顺序）：

1. `inject_stealth`（隐身脚本注册 —— 首个文档之后的全部新文档、以及 `run_immediately`
   对当前文档的补跑）；
2. `apply_screen_sync_override`（无头档补 screen 字段，根治 `outer > screen`；
   排在 chromiumoxide init 链之后落地，不会被 init 的无 screen 覆盖回抹）；
3. **无探针 UA 去令牌**（本轮新增通道）：覆盖值来自实例建立时 `Browser.getVersion`
   探得并缓存的浏览器级 UA 字符串（真值，只滤 `HeadlessChrome` 令牌零伪造），
   `Emulation.setUserAgentOverride` 只传字符串（`StringOnly` 语义）—— 不经
   `Runtime.evaluate`，不受 provisional 导航阻塞；**提交后的全部网络请求**
   （子资源/XHR/信标）与页面侧 `navigator.userAgent` 立即干净。品牌表清空副作用由
   ④ 收口（与 `new_page_impl` 首航同语义）。有头档（缓存无令牌）零动作；
4. **落地后补全**（复用 178 轮二段式）：有界后续任务轮询 URL 离开 about:blank
   （≤20s）→ `restore_native_ua` 撤半吊子覆盖 → 重探 → 下发带品牌表的完整覆盖
   （Client Hints 自洽）；顺带重发一次 screen_sync（init 竞态的最后兜底）。
   有头档不起后续任务，零开销；
5. headed 呈现层对齐 adopt：高亮/状态栏、guard 期望态注入与应用、跟随器 —— 派生页
   从提交起即受 locked 管控（人工「可看不可点」不再有空窗）。全部幂等，adopt 后到
   重装一次零风险。

### 3.4 与 adopt 的分工

watcher 只做「提交时刻武装」，**不做注册表记账**：URL 去重、Tab 上限、噪声页清扫、
事件监听挂载、`page_id` 分配仍归 `adopt_spawned_pages_ex`（动作收尾时跑）。watcher
补上了 adopt 序列缺失的 `apply_screen_sync_override`（同一条也补进了 heal 自愈路径
—— 无头档派生/自愈页的硬判据修复不靠单点）。

### 3.5 治理

- **杀开关 `LAEW_WEB_SPAWN_ARM=off/0/false/no/关闭`**：不启动 watcher，回退第 179
  轮行为（adopt 时武装；adopt 的 screen_sync 补丁不受开关影响）。
- **生命周期**：watcher 句柄存 `BrowserInner.spawn_arm`，与 handler 同点
  （purge / 末页回收 / relaunch 回收 / 死句柄清尸）abort；连接断开时事件流自然
  结束，任务自退。
- **connect 模式零注入契约不变**：watcher 只在 launch 模式启动。

### 3.6 两档语义

| 档 | 本轮增强 |
| -- | -------- |
| `fidelity`（非侵入式） | 派生页从提交起即处于「自动化泄漏已移除 + 本机真值已回填 + 几何自洽」环境；无头档 `outer > screen` 硬判据消失（含 adopt/heal 路径修复） |
| `hardened`（侵入式） | 同上；隐身脚本的 `Function.prototype.toString` 原生化对派生页的后续文档同样生效 |

## 四、诚实边界

1. **派生页首请求的 UA 令牌**（33 §六.1 原遗留）：target 一经创建浏览器立即发出
   首个网络请求，watcher 的事件→武装链路（≥5ms）必然晚于请求发出。根治需
   `waitForDebuggerOnStart`（fork CDP 客户端，见 §二）。
2. **派生页首个文档 document-start 的内联取样**（本轮新增的已钉死边界，见 §二）：
   提交门把一切经页面句柄的命令压到提交之后；内联在 `<head>` 解析期取样的脚本
   读到的是原生值。提交之后的一切（子资源请求/XHR/信标/后续文档/SDK 脚本加载后
   的取样）全部在处置之下。冒烟用例的 400ms 整包响应模型是**最坏情况**。
3. **不做 Worker 拦截 / `Runtime.enable` 处置 / Canvas·字体·行为伪造 / 代理池 /
   打码 / 协议逆向**（理由见 26 §三、32 §五）。
4. **watcher 不得持有 inner 锁、全部 CDP 调用有界** —— 违反任何一条都会把「增强」
   变成「挂死放大器」（adopt 的三段式重构正是为了这条纪律）。
5. **资格过滤必须保持 `opener_id.is_some()`**：放宽为「所有新 page target」会让
   watcher 与 `new_page_impl` 的同步武装形成双写竞争（UA 二段式的 restore/覆盖
   交错虽收敛但多付往返），收紧为「opener 是注册表内页面」则漏掉链式派生
   （孙页的 opener 是尚未收编的子页）。
