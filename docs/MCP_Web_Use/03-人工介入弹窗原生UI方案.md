## 1. 背景与目标(第 137 轮重构动因)

第 130 轮引入的弹窗呈现层采用「脚本动态加载」:macOS 用 osascript 跑 JXA(JavaScript)
自绘 NSWindow,Windows 用 PowerShell 跑 WinForms ps1。第 132/133/134 轮针对真机实测
连续修了三类「点了没反应」问题,但 **2026-10-09 实测再次复现同类事故**:

> 弹窗内输入验证码后,点击「⛶ 最大化」按钮后,**取消 / 提交 / 我已完成验证,继续 /
> 取消任务 / 查看原图 / 还原** 等所有按钮全部无响应,只能等 120s 超时自灭。

连续四轮修不干净,说明问题不在某一行代码,而在**脚本层这个载体本身**:

| # | 结构性缺陷 | 表现 |
| --- | --- | --- |
| 1 | **布局契约是两份手工对账的副本**:`contentHeight()`(预算)与 `doLayout()`(排布)在 JS 里各自维护,任何一次改动让两者错位,控件就被推出内容视图(第 134 轮实测 `submit.frame y=-6` 掉出高 300 的 contentView),点击落在被裁边带 | 「按了没反应」 |
| 2 | **最大化路径依赖回读桥接值**:zoom 后用 `win.contentView.frame` 的 JXA 桥接返回值当排版高度,桥接返回 `{origin,size}` 或 `{x,y,w,h}` 因版本而异,且回读时机可能拿到旧值 → 重排必然漂移 | 最大化后全按钮失灵(本轮事故) |
| 3 | **动态语言 + 运行时加载 = 编译器与测试均不可见**:`.laew/human_ui/*.js` 覆盖、`include_str!` 内置正文,单元测试覆盖不到真实 UI 代码路径;每次修复都要真机肉眼回归 | 同类问题反复回归 |
| 4 | **JXA 桥接层自身 quirks**:零参方法必须属性式调用、`registerSubclass` 返回 undefined、NSRect 两种返回形态……都靠踩坑记忆规避 | 修复引入新坑 |

目标:

1. **原生 UI**:macOS 用 Rust FFI 直接调用 AppKit / ObjC runtime;Windows 用 Rust 调用
   Win32 API(`windows` crate,工程既有依赖)。**删除全部 js / ts / ps1 脚本文件**;
2. **布局单一真源**:窗口/控件几何全部由 Rust 纯函数计算,类型检查兜底,最大化/还原
   只用「自己刚设置的值」重排,**永不回读**窗口 frame;
3. **契约不变**:payload/result JSON 协议、四态应答语义、Hub / TUI / 工具信封层零改动
   (弹窗对上层只是「一个会打印结果 JSON 的进程」);
4. **生命周期语义不变**:子进程隔离 + `kill_on_drop`,父任务收口即回收弹窗,不留孤儿窗口。

## 2. 总体架构

```text
SubAgent-Work(LLM)control_action=request_human
        │
        ▼
HumanAssistHub::request()  ←── 全局单例不变(02 §2)
        │ 注册 pending 槽位时同步判定呈现端:
        │   gui_enabled = human_ui::enabled()
        │   ├─ 是 → 槽位标记 via=gui,spawn 弹窗呈现任务 ──┐
        │   └─ 否 → 仅 TUI 轮询(既有路径)                │
        ▼                                                  ▼
oneshot 等待人工回答                            human_ui::present(display)
        ▲                                       (payload 落盘 → spawn 子进程)
        │                                                  │
        │        respond(id, Some/None) ◄──────────────────┤ laew __hitl-dialog <payload.json>
        │        (弹窗应答 / TUI 行读应答 二选一,          │   ├─ macOS: AppKit(FFI)原生窗口
        │         respond 幂等,后到者拿 false)             │   └─ Windows: Win32 原生窗口
        └──────────────────────────────────────────────────┘ stdout 最后一行 JSON = 结果
```

三层职责严格分离(与第 130 轮一致):

| 层 | 模块 | 职责 |
| --- | --- | --- |
| **枢纽层**(不变) | `human_assist.rs` | pending 槽位 / oneshot / 超时 clamp / 四态结局;呈现端只经 `respond` 回填 |
| **呈现层**(本轮重构) | `human_ui/` | 能力探测 + payload 落盘 + **原生弹窗子进程**管理 + 结果解析;失败 fail-open 降级 |
| **呈现层(兜底)** | `tui/dispatch.rs` | 弹窗不可用/弹窗失败时,沿用 TUI 蓝框行读;弹窗接管时仅打印通知行 + 结果事件 |

## 3. 关键决策

1. **原生弹窗放在子进程(`laew __hitl-dialog <payload>`),不留在 Agent 进程内**。
   与既有 `__browser-watchdog` 隐藏子命令同构,理由:
   - **AppKit 要求事件循环在进程主线程**:laew 主线程被 tokio/TUI 占用,而子进程的
     主线程天然空闲,`NSApp.run()` 名正言顺;进程内开线程跑 NSApp 属于未定义行为
     (NSApplication 明确要求主线程);
   - **崩溃隔离**:FFI 层 panic / 窗口系统异常只死弹窗子进程,Agent 主流程照常降级 TUI;
   - **取消语义零成本保留**:`kill_on_drop` 杀子进程 = 窗口立刻消失,与旧 osascript
     时代的回收语义完全一致,不需要跨线程操作 AppKit 对象(那才是真正的线程地狱)。
2. **macOS 用 Rust 手写 objc runtime FFI,零新 crate**:工程既有模式(`window/macos_legacy`
    对 AXUIElement 的手写 FFI)延伸到 libobjc:`objc_msgSend` 按**具体签名**逐个包装
    (touri/tao 同款做法),结构体返回在 x86_64 走 `objc_msgSend_stret`、arm64 统一走
    `objc_msgSend`。不引入 `objc2`/`cocoa` crate,保持依赖面不变。
3. **Windows 用 `windows` crate(Win32 API),工程既有依赖零新增**:`RegisterClassExW` +
    `CreateWindowExW` + 标准控件(BUTTON / EDIT / STATIC)+ 消息循环。
    **WM_SIZE 全量重排** —— 任何最大化/还原/拖拽缩放都重算全部控件坐标,
    这是「最大化后无响应」在 Windows 侧的根治点(旧 ps1 靠 Anchor,布局不重算)。
4. **契约完全不变(§5)**:旧脚本生态的 payload/result JSON、退出码语义原样保留,
    Hub(`human_assist.rs`)、TUI 通知、工具信封(`control.rs`)零改动,回归面最小。
5. **删除脚本动态加载层**:`script.rs` 与 `scripts/{macos_dialog.js,windows_dialog.ps1}`
    删除,`.laew/human_ui/` 两级覆盖与 `LAEW_HUMAN_UI_SCRIPT` 环境变量废止
    (§8 给出迁移口径)。理由:UI 呈现属于工程本体能力,不该是「可被外部文件替换的
    插件」—— 第 130 轮设计把它当灵活性,四轮实测证明它是回归之源:现场跑的 UI 代码
    既不受版本管理约束(用户改了脚本),也不受编译器/测试约束。
6. **弹窗应答与 TUI 行读互斥**(不变):弹窗接管期间 TUI 不读 stdin,`respond` 幂等;
    `/hitl <应答>` 终端应急通道(第 134 轮)原样保留 —— 原生弹窗再出异常仍有逃生门。

## 4. 弹窗 UI 规格(两平台同构)

### 4.1 内容区(自上而下)

| 区块 | 内容 | 说明 |
| --- | --- | --- |
| 标题栏 | `🔐 人工介入 · {kind_label}` | kind_label 与 TUI 蓝框同一映射表(9 reason + custom 兜底) |
| 说明区 | `message` + `页面: {url}` + `页面ID: {page_id}` | macOS:NSTextView(`selectable=true`,NSScrollView 包裹)可拖选可 ⌘C;Windows:ReadOnly 多行 EDIT;url 截断保尾 200 字符 |

### 4.2 应答语义(与 TUI 行读映射表对齐,第 130 轮起不变;第 145 轮起按钮文案显性化)

| 人工动作 | 结果 | 工具信封 |
| --- | --- | --- |
| 输入文本 + 提交/回车/任意选项按钮 | `Answered(原文)`(短信验证码数字即此路径) | `code=0` + `human_response` |
| 点选项按钮 N(输入框空,单选) | `Answered("N. 选项文本")` | `code=0` + `human_response` |
| 勾选项 1/3/… 后点「继续」(多选,输入框空) | `Answered("1. a；3. c")`(全角分号连接,`join_multi_answer` 纯函数编码) | `code=0` + `human_response`(数字前缀形态,`hitl_hint` 归入选项应答分流) |
| 提交但输入框空(无 tag/无勾选) | `Answered("1. " + options[0])` | `code=0`(空回车=选项 1,对齐 TUI;多选空勾选同语义) |
| 点 `[ 取消 ]` / Esc | `Cancelled` | `code=4002` |
| 倒计时归零(弹窗自灭) | `Timeout` | `code=4001` |
| 弹窗进程失败/被杀 | 降级 TUI;无 TUI 则 `Unavailable` | `code=4001` |

> 第 145 轮:主按钮「提交」→「**提交 / 继续**」(宽度 84→96)——**行为零改动**,
> 语义显性化:有输入 = 提交验证码/动态码文本;空输入 = 选项 1(缺省即
> 「我已完成人工操作,继续」)。人工在浏览器窗口完成登录/滑块/扫码后,回弹窗
> 点它就是把控制权交棒给 Agent——「用户和 Agent 交互操作」的收口动作从此可见。
> 工具侧配套:`code=0` 信封的 `next_hint` 按「输码 vs 已完成」分流(自由文本验证码 →
> 立即 `input_text` 填码提交;「N. 选项」形态 → inspect 验证),见 08 文档 §7。
>
> **2026-10-13**:主按钮文案收敛为「**继续**」——验证码专属语义移除(有输入 =
> 把补充说明原样交给 Agent;空输入 = 选项 1 交棒),行为不变。

### 4.3 文本选择与复制(第 139 轮)

> 背景:实测反馈「输入框不好复制粘贴、其它控件的文案不能选中复制」。

**改造前的问题**(`human_ui/` 全目录 grep `NSMenu|copy:|paste:` 零命中):

| 控件 | 改造前 | 问题 |
| --- | --- | --- |
| 输入框 | `NSTextField` + `setEditable:YES`,`setSelectable:` **从未显式设置** | ⌘C/⌘V 全靠 NSTextField 自己在 responder chain 上接住 `copy:`/`paste:`,**没有任何显式支撑**;窗口 `styleMask` 只有 `Titled`,无菜单栏、无右键菜单 |
| 标题 / 时间轴 / 倒计时 | `make_label` 只调 `setEditable:NO`,**从不调 `setSelectable:`** | `NSTextField` 默认 `isSelectable=NO` → 完全不可选中、不可复制 |
| 图片尺寸提示 | `make_label` + **显式 `setSelectable:false`**(`:982`) | 反向锁死 |
| 说明区 | `NSTextView` + `setSelectable:YES`(第 132 轮遗留) | 唯一可复制的区域;但 NSTextView **未设 `setVerticallyResizable`**,长文案滚不动 → 尾部看不全也选不中 |
| Windows 侧 t1/t2/img_hint | `STATIC` 控件 | 天然不可选中 |

**三处改造**:

1. **装主菜单**(`install_main_menu`,macOS):应用菜单 + **编辑菜单**
   (剪切 ⌘X / 复制 ⌘C / 粘贴 ⌘V / 全选 ⌘A)。菜单项用标准 responder action
   (`cut:` / `copy:` / `paste:` / `selectAll:`),系统沿 responder chain 派发给
   first responder —— 输入框(`NSTextField`)与说明区(`NSTextView`)**同时生效**,
   无需各自接线。keyEquivalent 只写单字母,AppKit 默认按 ⌘ 解析。
   必须在建任何控件**之前**安装。
2. **让文本可选中**:统一在 `make_label` 里 `setEditable:NO + setSelectable:YES`
   (标准的「只读可选文本」组合),输入框显式补 `setSelectable:YES`,删掉图片提示
   那句反向的 `setSelectable:false`;NSTextView 补 `setVerticallyResizable:YES`,
   长说明在 NSScrollView 里真能滚。Windows 侧 `STATIC` 无法可选中,靠下面的「📋 复制」补齐。
3. **「📋 复制」一键复制**:`DialogPayload::copy_text()`(macOS/Windows **共用**的纯函数)
   汇总 `【人工介入 · kind_label】+ 说明 + 页面 URL + 页面ID + 提出/截止时刻 + 候选选项`,
   写系统剪贴板(NSClipboard / Win32 `SetClipboardData`),按钮标题短暂变
   「✓ 已复制」后由**既有 1s 定时器**回滚(不额外起定时器)。

   > 为什么必须有一键复制:倒计时行**每秒重绘**,人工拖选过程中就被冲掉;
   > 而且这个弹窗是打断式浮窗,用户多半要把页面 URL / 验证码提示粘到聊天窗口或工单里。

   写入的剪贴板格式为纯文本 `public.utf8-plain-text`(macOS)/
   `CF_UNICODETEXT`(Windows);写入失败(fail-open)只在按钮标题上体现
   「⚠ 复制失败」,不影响弹窗其余功能。

**布局影响**:底部按钮行新增一个按钮,`ZOOM_W` 由 110 收窄到 104、
新增 `COPY_W=92`,`layout_frames` / `content_height` 的单一真源性质不变;
单测锁死「底部四按钮同行对齐 + 互不重叠」。

### 4.4 尺寸与滚动(第 137 轮事故的根治延续;2026-10-13 移除自有最大化按钮)

> 第 137 轮的「最大化/还原」是**验证码图片放大**的配套(图区随窗口放大才读得清
> 九宫格)。验证码功能移除后,说明区本就是 NSScrollView(可滚动),自有「⛶ 最大化」
> 按钮失去存在意义,2026-10-13 整体移除(`toggle_zoom`/`ZOOM_W`/`zoomed`/
> `normal_geo` 全删),底行从七键位收敛为六键位。

| 平台 | 实现 | 为什么不会再坏 |
| --- | --- | --- |
| macOS | 窗口按内容定尺寸(`content_height` 预算 → `setContentSize`),`place_window` 落主屏可见区居中(超高/超宽夹紧);排版高度 = 我们传入的值,**永不回读** `contentView.frame`;窗口 styleMask 仅 `Titled`(无系统缩放/关闭按钮);长说明在 NSScrollView 里滚动阅读 | 布局单一真源:`layout_frames`/`content_height` 同一组常量推导,单测锁死预算对账(第 134 轮事故的根治) |
| Windows | 系统标题栏允许最大化/还原/拖拽缩放(WS_THICKFRAME \| WS_MAXIMIZEBOX 保留);**每次 WM_SIZE 都全量重排**(MoveWindow 全部子控件,坐标由 §6.3 同一套 Rust 纯函数给出) | 布局只依赖「当前客户区尺寸」这一个输入,由窗口系统自己通知(WM_SIZE),不存在两份账本 |

### 4.5 「⏱ +2分钟」延长等待与「提交 / 继续」双语义(第 145 轮)

> 背景:实测(内网站点预发布环境登录)reason=captcha 分档默认 120s,但人工实际要做
> 整条登录链(切子账号 + 账密 + 读码),120s 烧穿 → 弹窗自灭 → QC 单元重试 →
> 36s 后二次弹窗(验证码已刷新)。「⏱ +2分钟」把「我还需要时间」变成弹窗内的
> 一键动作,不再靠超时-重试链硬扛。

| 项 | 行为 |
| --- | --- |
| 点击「⏱ +2分钟」 | 本地 `timeout_ms += 120_000`(倒计时行/时间轴「超时截止」行立即重写;按钮标题追加 `×N` 计数),同时向 stdout 打 **extend 中间行**(见 §5);**进程不退出** |
| 总上限 | 原始 `timeout_ms` + 累计延长 ≤ `MAX_HUMAN_ASSIST_TIMEOUT_MS`(30 分钟);到达上限后点击无效(不累计、不打中间行) |
| 父进程接线 | `human_ui::run_dialog_process` 逐行流式读 stdout:extend 行 → `HumanAssistHub::extend_timeout(id, ms)` 即时推迟 hub 侧截止时刻(仅 id 匹配当前槽位时生效);其余行留存供收口解析 |
| hub 动态截止 | 等待循环每轮按「原始 deadline + 累计延长」重算 remaining;超时臂醒来先非阻塞收一次应答(respond 与截止同时到达的竞态,respond 会清空延长量),再核延长量决定继续等或收口 Timeout |
| 可观测性 | `AssistEvent::GuiExtended{id, added_ms}` 入事件环 → TUI 打「人工已在弹窗延长等待 +120 秒」;到达上限时 `added_ms=0` 打提示行 |
| 布局 | 底行按钮(第 145 轮当时):取消(84)/提交·继续(96)/⏱+2分钟(88) \| 复制(92)/查看原图(110)/最大化(104);窗口宽 560→**680**(2026-10-13 第二轮起查看原图/最大化已移除,现行六键位见 §4.6);两平台单测锁死同行对齐 + 互不重叠 |

### 4.6 「解除屏蔽/恢复屏蔽」互切按钮(2026-10-13,验证码功能移除同轮)

> 背景:天猫/京东双站比价实测(`llaew_20261013_135249.log`)——京东登录弹窗在
> locked 管控下被蒙层挡住,人工的第一体验是「登录界面,不能点击,优化一下」,只能
> 在弹窗输入框打字请 Agent 解锁;第二次 HITL 人工选择取消(4002)。解锁入口必须
> 交到人工手里:弹窗内一键解除屏蔽,随时再恢复,全程不用离开弹窗。

| 项 | 行为 |
| --- | --- |
| 按钮形态 | 单个按钮互切标题:「🔓 解除屏蔽」↔「🔒 恢复屏蔽」;初始标题按 payload `guard_unlocked`(页面实际放行态,`act_request_human` 按 `page_guard_snapshot` 计算) |
| 点击「解除屏蔽」 | stdout 打 **guard 中间行** `{"status":"guard","id":N,"unlock":true}`(进程不退出);父进程 → `HumanAssistHub::guard_toggle_from_ui` → `act_request_human` 安装的 handler 对关联 page_id 应用**整页 open**(`apply_hitl_unlock`,内含导航重放协程,登录提交跳转后维持放行态);按钮标题切「🔒 恢复屏蔽」 |
| 点击「恢复屏蔽」 | guard 中间行 `unlock:false`;handler abort 手动重放协程 + 按**本页解锁前快照**恢复(快照缺失回退全局配置);按钮标题切回 |
| 收口 | 应答/超时/取消后:除既有自动解锁重放外,人工手动解锁的重放协程一并 abort(否则会把已恢复 locked 的页重新顶开);`set_guard_toggle_handler(None)` 双保险清 handler |
| 可观测性 | `AssistEvent::GuiGuardToggled{id, unlock}` → TUI 打「人工已在弹窗解除/恢复页面屏蔽」通知行(不收口请求,弹窗继续接管,与 GuiExtended 同语义) |
| 布局 | 底行(2026-10-13 第二轮起)六键位:取消(84)/继续(96)/⏱+2分钟(88)/管控切换(96) ‖ 复制(92);窗口宽保持 680 |
| 验证码功能移除 | 图片区(NSImageView/STM_SETIMAGE)、「查看原图」「🔍 放大」、`reason=captcha` 自动截图采集链(`captcha_crop` 模块)整链删除;`image_path` 保留(显式透传,TUI 兜底打印);主按钮「提交 / 继续」→「继续」(有输入=补充说明交给 Agent) |

### 4.7 自动弹出(auto-HITL,2026-10-13)与选项多选

**自动弹出**:工具层两处探测点命中时,**不再只回提示载荷等 LLM 再调
request_human(多一轮往返,且有「无视提示继续输入」风险),直接弹人工介入并等待**:

| 触发点 | 位置 | 信封语义 |
| --- | --- | --- |
| T1 输入前置硬闸 | `blocker_probe::challenge_gate` 命中(6002,结构证据) | 弹窗等待人工;应答后**信封码恒 6002**(输入动作仍未执行,不伪造成功),`data.auto_hitl{trigger:"input_gate",status,human_response?}` 回报结果,message 指示重试本动作;取消 → 终止提示;超时/不可用 → 回退原 human_assist 提示载荷 |
| T2 动作收尾探针 | `blocker_probe::probe_alert` **首次命中**(repeat 不弹) | 动作本体已成功(code=0 不变),应答结果并入 `data.auto_hitl{trigger:"blocker_probe",…}`(含 human_response/next_hint),LLM 当轮即见人工答复 |

守卫条件(`hitl_ctl::auto_hitl`,任一不满足回退提示载荷现状):
1. `LAEW_HITL_AUTO` 未关闭(off/0/false/no,缺省开);
2. **不在 sequence/batch 上下文**(mod.rs `IN_SEQUENCE` task_local)—— 批内单步
   150s 预算会截断 300s 分档的人工等待,批内保持「提示载荷 → LLM 以独立
   request_human 步介入」(该步已豁免预算);
3. hub 无 pending(已有人在等应答时不排队叠加、不重复打扰)。

自动路径与 LLM 显式调用共用 `hitl_ctl::request_human_core`(HitlSpec 入参):
解锁判定/页面实际态快照、挑战层滚入视口、guard 互切 handler 安装、焦点租约、
收口恢复全套待遇一致。指纹去重沿用:同一挑战重复命中只回 repeat 事实;LLM 显式
request_human 仍会 `forget_fingerprints`(人工介入 = 页面状态即将改变的新事实)。

**选项多选**:`control(request_human, params.multi_select=true)` → payload
`multi_select` → 弹窗选项渲染为复选框组(单选缺省不变);应答编码
`join_multi_answer` = `1. a；3. c`(全角分号连接),`hitl_hint::is_option_pick_answer`
的数字前缀判定天然兼容(归入选项应答分流,不会被当验证码文本填码)。

## 5. 进程契约(子进程 ↔ Rust,自第 130 轮沿用;第 145 轮扩展中间行;2026-10-13 扩展 guard 中间行)

- 启动:`laew __hitl-dialog <payload.json 路径>`(隐藏子命令,与 `__browser-watchdog`
  同构;测试可用 `LAEW_HITL_DIALOG_EXE` 指向别的可执行文件);
- 输入:命令行参数 = payload JSON 临时文件路径(`human_ui::write_payload` 落盘,
  RAII 守卫清理)。payload 字段:

```json
{
  "id": 3,
  "kind": "sms",
  "kind_label": "短信验证码",
  "message": "页面要求短信验证码……",
  "options": ["我已完成人工操作,继续", "取消任务"],
  "multi_select": false,
  "url": "https://example.com/login",
  "page_id": "p_ab12cd34",
  "image_path": "",
  "guard_unlocked": false,
  "started_at": "2026-10-08 14:32:05",
  "started_at_ms": 1759991525000,
  "timeout_ms": 120000,
  "deadline_at": "2026-10-08 14:34:05"
}
```

> 2026-10-13 新增 `guard_unlocked`:页面当前是否已放行(open/无管控),弹窗
> 「解除屏蔽/恢复屏蔽」互切按钮的初始标题依据(`act_request_human` 按
> `page_guard_snapshot` 页面实际态计算,缺省 false);新增 `multi_select`:选项
> 是否多选(true = 复选框组,点「继续」收集勾选,应答 `1. a；3. c`;缺省 false
> = 按钮组点击即应答)。`image_path` 保留但弹窗不再渲染(验证码图片功能已移除),
> 仅供 TUI 兜底打印路径。

- 输出:stdout **最后一行** JSON(`status` ∈ `answer|cancel|timeout|error`),父进程
  `parse_result` 容错解析(噪声行/多行 JSON 取最后一个合法的):

```json
{"status":"answer","text":"482913"}
{"status":"cancel"}
{"status":"timeout"}
{"status":"error","text":"原因说明"}
```

- **第 145 轮:extend 中间行** —— 「⏱ +2分钟」按钮在弹窗存活期间随时可打
  (进程不退出;Stdout 行缓冲,println! 即时 flush):

```json
{"status":"extend","id":3,"ms":120000}
```

  父进程 stdout 从整体 `.output()` 改为 **piped 逐行流式读**:extend 行即时接线
  `HumanAssistHub::extend_timeout(id, ms)` 推迟 hub 侧截止时刻;其余行留存到进程
  退出后交 `parse_result` 收口解析(extend 行被显式跳过,不会落入「未知弹窗结果」)。
  stderr 并联排空(防子进程写满 pipe 缓冲阻塞),失败路径语义与旧版一致。
  **id 对号入座**:中间行携带 payload 的 `id`,仅当它仍是 hub 当前槽位请求时延长
  生效(弹窗延迟到达的 extend 行不会复活旧请求);同 binary 父子,无版本漂移。

- **2026-10-13:guard 中间行** —— 「解除屏蔽/恢复屏蔽」互切按钮(§4.6)在弹窗
  存活期间随时可打(进程不退出):

```json
{"status":"guard","id":3,"unlock":true}
```

  父进程逐行读 → `HumanAssistHub::guard_toggle_from_ui(id, unlock)`(仅 id 匹配
  当前槽位时执行,同步调用 `act_request_human` 安装的 handler,handler 内部自行
  `tokio::spawn` 落页);`parse_result` 与 extend 行一样显式跳过 guard 中间行。

- 退出码 0 = 正常收口(含 timeout / error JSON);父进程只认 stdout JSON;
- 生命周期:父侧 `tokio::process::Command::kill_on_drop(true)` —— 弹窗 future 被
  drop(槽位被别的通道收口/任务取消)即杀子进程,窗口随之消失。

## 6. macOS 原生实现(`human_ui/macos_dialog.rs`)

### 6.1 objc FFI 底座

- 链接 `libobjc`:`objc_getClass` / `sel_registerName` / `objc_allocateClassPair` /
  `class_addMethod` / `objc_registerClassPair` / `objc_msgSend`(x86_64 结构体返回
  追加 `objc_msgSend_stret`);链接 `AppKit`/`Foundation` 由符号自动解析;
- `objc_msgSend` 按**具体参数形状**包装成类型安全的包装函数(`msg_id` / `msg_id_id` /
  `msg_void_bool` / `msg_id_rect_u64_i64_bool` ……),杜绝裸变参误用 —— 这是
  tauri/tao 等项目验证过的成熟做法;
- ObjC 类 `LaewHitlController`(继承 NSObject)在进程启动时注册,IMP 全部是
  `extern "C" fn(self, _cmd, sender)`,类型串 `v@:@`;通过 `static STATE: Mutex<...>`
  访问窗口/控件/结果(单弹窗进程,UI 线程独占)。

### 6.2 控制器 IMP 与收口

| IMP | 触发 | 语义 |
| --- | --- | --- |
| `submit:` | 选项按钮(tag=i)/ 提交按钮(tag=-1)/ 输入框回车(target/action) | §4.2 映射 → answer |
| `cancel:` | 取消按钮(keyEquivalent `␛`) | → cancel |
| `zoom:` | ⛶ 最大化/还原 | §4.4 重排 |
| `copyInfo:` | 📋 复制(第 139 轮) | 写系统剪贴板 → 标题变「✓ 已复制」,2s 后由 `tick:` 回滚 |
| `openImage:` | 查看原图 | `NSWorkspace.openFile` 系统查看器 |
| `tick:` | NSTimer 1s | 刷新倒计时行;归零 → timeout |
| `focus:` | 0.05s 一次性 timer | 二次 `makeFirstResponder`(防「看着有焦点打不进字」,第 132 轮教训) |
| `windowWillClose:` | 窗口代理 | 兜底 → cancel |

收口函数 `finish(kind, tag)`:幂等守卫 → 读输入框文本 → 映射结果 → invalidate
定时器 → `NSApp.stop(null)` + 投递 `NSApplicationDefined` 空事件唤醒(标准 trick)
→ `NSApp.run()` 返回 → 打印结果 JSON 退出。

### 6.3 布局单一真源(第 134 轮几何的全量移植)

- 常量:`W=560, PAD=16, title_h=22, line_h=18, input_h=28, btn_h=30, gap=8`;
- `struct Layout { msg_h, img_h, ... }` + 两个纯函数:
  `content_height(layout) -> f64`(预算)与 `place_views(content_view_w/h, layout)`
  (排布)—— **place 的消费序列与 content_height 的累加序列逐项对应**,由同一结构体
  参数化,编译期消灭「两份手工账本」(第 134 轮事故一);
- 图区高:`img_h = clamp(text_w * 图高宽比, 60, cap)`,正常 cap=300,最大化
  cap=min(900, 屏高 55%);
- 坐标系注意:AppKit y 轴自底向上,place 自 `y = ch` 起算逐项下移(第 134 轮修正后的
  正确起点,勿回退成 `ch - title_h`)。

### 6.4 选屏与定位(第 134 轮结论延续)

- `pick_screen()`:遍历 `NSScreen.screens`,取 `visibleFrame` 面积最大者
  (多屏副屏在主屏下方时,`[NSWindow center]` 会把窗口丢到副屏 —— 弃用);
- `place_window(w, h)`:`setContentSize(NSMakeSize(...))` + `setFrameOrigin(可见区居中)`
  —— contentRect 语义由 AppKit 处理标题栏,不用 `setFrameDisplay`(frame 坐标差 32px,
  第 134 轮事故二)。

### 6.5 窗口/焦点/激活

- styleMask = `Titled`(无 Closable/Miniaturizable/Resizable:杜绝误关与系统缩放,
  resize 只走自家 ⛶ 按钮);`level = NSFloatingWindowLevel` 视觉置顶,不周期抢焦
  (第 132 轮结论:人工在浏览器操作滑块时不能反复拉焦);
- `setActivationPolicy(Regular)` → `makeKeyAndOrderFront` → `activateIgnoringOtherApps(true)`
  启动激活一次;`makeFirstResponder(input)` + 0.05s 二次断言(IME 可用)。

### 6.6 定时器

`NSTimer::scheduledTimerWithTimeInterval:target:selector:userInfo:repeats:`(1s,
repeats)注册进当前 run loop default mode —— `NSApp.run()` 下正常 fire(第 132 轮
教训:runModal 的 NSModalPanelRunLoopMode 会饿死 default-mode 定时器,故不用 runModal)。

## 7. Windows 原生实现(`human_ui/windows_dialog.rs`)

- 窗口:`RegisterClassExW` + `CreateWindowExW`,样式 `WS_OVERLAPPEDWINDOW`
  (含 THICKFRAME/MAXIMIZEBOX,最大化可用)+ `WS_EX_TOPMOST`;`IsDialogMessageW`
  消息循环(Tab 导航 / Enter=默认按钮 / Esc=IDCANCEL);
- 控件:标题 STATIC(粗体)、说明 READONLY 多行 EDIT(可选中复制)、时间轴 STATIC×2、
  输入 EDIT(ES_AUTOHSCROLL)、选项 BUTTON×N、取消/提交(IDCANCEL/IDOK,
  提交=BS_DEFPUSHBUTTON)、查看原图/⛶ 最大化 BUTTON;字体统一
  `CreateFontW("Microsoft YaHei UI", 9pt)`;
- **WM_SIZE 全量重排**:与 macOS 同一套「布局纯函数 + 消费序列对应」思路,客户区
  尺寸唯一输入,MoveWindow 全部子控件 —— 最大化/还原/拖拽缩放共享一条布局路径;
- 图片:`image` crate(工程既有依赖,从 macos-only 提为全平台)解码 PNG → RGBA
  重采样(宽 ≤528 / 高 ≤300)→ 转 BGRA → `CreateCompatibleBitmap + SetDIBits`
  → `STM_SETIMAGE`;失败降级无图。**不引入 GDI+/WIC**,压低 Win32 面;
- 倒计时:`SetTimer` 1s → `WM_TIMER` 刷新/归零收口;收口 DestroyWindow + PostQuitMessage;
- 置顶:WS_EX_TOPMOST + 创建后 `SetForegroundWindow`;
- **强制可见(第 154 轮)**:`ShowWindow(SW_SHOW)` 后追加
  `SetWindowPos(HWND_TOPMOST, …, SWP_NOMOVE|SWP_NOSIZE|SWP_SHOWWINDOW|SWP_NOACTIVATE)`。
  原因:父进程以 `STARTF_USESHOWWINDOW + SW_HIDE` 启动 laew 时(实测 PowerShell
  `Start-Process -WindowStyle Hidden`,部分 agent harness/调度器同形态),**首次**
  `ShowWindow` 调用会被 STARTUPINFO 的 `wShowWindow` 压制 —— 窗口创建成功但
  `IsWindowVisible=False`(本机探针复现)。`SWP_SHOWWINDOW` 直接置 `WS_VISIBLE`
  样式位、不经首次 ShowWindow 通道,不受启动参数影响。
