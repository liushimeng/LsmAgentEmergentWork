# 14. 窗口铺满 / 置前可见性与弃权如实转达（第 156 轮）

> 实测来源：`llaew_20261012_102053.log`（macOS，Dir07）+ 本机探针复现
> 日期：2026-10-12 ｜ 方案全文：`tmpPlan/2026-10-12_MCP_Web_Use实测缺陷修复方案.md`

本文档记录第 156 轮的四项修复。其中 F2/F3/F4 属浏览器窗口几何与可见性，
F1 属编排层对模型决定的尊重 —— 两者共同指向同一个实测现象：**用户以为
「Agent 根本没启动 Chrome 浏览器」**。

---

## 0. 先澄清一个误诊：浏览器启动链路本来是好的

实测反馈是「macOS 下 Agent 用 MCP_Web_Use 没启动 Chrome」。
本机探针复现证明 headed 模式完全正常：

```
$ laew --info -p "打开 https://www.example.com ，用 MCP_Web_Use 工具，告诉我页面标题"
INFO 工具调用 tool=MCP_Web_Use args={"action":"open","mode":"headed","url":"…"}
INFO 工具结果 is_error=false elapsed_ms=2503 output={"code":0,…,"title":"Example Domain"}
```

原日志里 `MCP_Web_Use` 出现 14 次，**全部位于提示词的工具清单文本内**，
`tool=MCP_Web_Use` 的「工具调用」埋点**零次** —— SubAgent 在 iter=0 直接【拒绝执行】。

按工程原则「任务该不该接完全由模型自行判断，编排器无任何政策性拒绝门」，
**这一层拒绝是设计内的正确行为，本文不改它**。

但用户「看不到浏览器」的**观感**是真问题，源于下面四项。

---

## 1. F1（P0）Main-Work 主动弃权被当成「解析失败」，执行被拒任务 157 秒

### 现象

```
[stage] Main-Work 解析失败,已使用单 WorkFlow 兜底(跳过计划 QC,直接执行 1 个流程) +6.3s
[stage] wf-1.step SubAgent 执行中 … 59.9s
[stage] wf-1.step QC:✅ 通过 +14.2s
[task executed: workflows=1, 总耗时 156.89s]
```

### 根因

Main-Work 的输出**不是解析失败，而是主动弃权**（`summary` 字段）：

> 「不予编排,需回到用户澄清/改题。原因:……故输出 0 个 workflows。
> 可替代的合法方向(请用户任选其一或改写目标后再来,我再重新编排):(A)…(D)」

即 `{"workflows": [], "summary": "不予编排…"}` —— 一个**语义完整、合法**的 JSON 计划。

但 `main_work/parse.rs` 把「解析成功但 workflows 为空」一律转成
`AgentError::WorkflowParse`，`main_work/mod.rs` 的 `unwrap_or_else` 兜底接住后
**构造了一个「执行原任务」的通用 WorkFlow**。后果：

1. Main-Work 说「别做，回去问用户」→ 被无视；
2. SubAgent 在 wf-1 里**又拒绝了一次**（第二道拒绝，本可避免）；
3. 拒绝理由被当成正常产物写成 249 行 Markdown；
4. **156.89s / 12.4 万 input token**，产出为 0；
5. 终态记为 `状态: ✅ 成功`、`[QC] ✅ 通过`、`wf-1 ✅`。

用户看到「✅ 成功」，实际一件事都没做成。

### 设计边界（不可违反）

- **不得**新增政策性拒绝门、关键词检测或 `refuses_task` 类字段 ——
  `safety/refusal.rs::detect_refusal` 已被整体移除，理由是「关键词清单占 token
  且与模型自身判断打架」。本文**不复活它**。
- 本修复做的是**尊重**模型的弃权决定，而非**替模型做**拒绝判断。
- 判据是**结构性**的（零单元 + 非空 `summary`），与措辞无关。

### 实现

| 步骤 | 文件 | 改动 |
|---|---|---|
| 1 | `src/error.rs` | 新增 `AgentError::WorkflowAbstain { summary }` |
| 2 | `main_work/parse.rs` | 新增 `check_zero_unit_plan`：非空 `summary` → `WorkflowAbstain`；空 `summary` → 维持 `WorkflowParse`（真解析失败） |
| 3 | `main_work/mod.rs` | 兜底改前置分流，`WorkflowAbstain` **不进兜底** |
| 4 | `orchestrator/types.rs` | 新增 `enum ExecFailure { Quality(..), Abstain { text, usage } }` + `From<QualityFailure>` |
| 5 | `orchestrator/pipeline.rs` | 新增纯函数 `classify_main_work_error` 做出口分流；调用点把 `Abstain` 收成 `OrchestrationOutcome::DirectAnswer` |

选 `ExecFailure` 而非给 `QualityFailure` 加字段：后者有 15 处字面量构造点，
加字段要全量机械改；独立枚举把改动收敛在 `run_medium` 内，`QualityFailure` 零改动。

预期效果：156.89s / 12.4 万 token / 谎报成功 → 秒级收口 + 如实展示模型的说明与替代方案。

## 2. F2（P1）headed 启动后从不激活窗口

headed 确实拉起了 Chrome（`code:0` + `title` 都拿到了），但项目**不做任何窗口激活**：

- `BrowserManager::bring_page_to_front`（`Page.bringToFront`）**只在 `request_human`
  前被调用一次**，**open 路径从不调用**；
- 全仓无 macOS `activate` / `activateIgnoringOtherApps`（该能力只存在于
  `window/macos_legacy` 与 `human_ui/macos_dialog`，与 Web_Use 无关联）；
- 不设 `--window-position`，不设 `--start-maximized`。

于是 Chrome 落在终端/编辑器之后 —— 用户看到的就是「Agent 没启动浏览器」。

**修复**：open 成功、`fit_headed_window` 之后补一次置前。纯 CDP、跨平台一致、
**零新依赖零平台分支**；**fail-open**（失败只 debug，不改变 `code:0`）；
调尺寸后复置前一次（`setWindowBounds` 可能把窗口压回 z 序底层）。
`data.headed_window` 增 `activated: bool` 供 Agent / QC 对账。

实现落在新子模块 `src/agent/browser_window.rs`（`browser.rs` 改动前已 1964 行，
按「临界文件新增代码优先落到职责子模块」约定拆分）。

## 3. F3（P2）chrome 高度测量拿到实现前默认值，窗口被反向撑高

本机两次探针**确定性复现**：

```json
"measured":{"chrome_height":480.0,"inner":{"height":600.0,"width":800.0},
            "outer":{"height":1080.0,"width":1920.0}, …}
"applied":{"height":1200,"width":1920}
```

`chrome_h = outerHeight - innerHeight`（`browser.rs`）。macOS 上测量发生在窗口
**布局实现之前**：`outer` 已按 `--window-size` 报 1920×1080，`inner` 仍是 Chrome 的
**实现前默认值 800×600**。于是 `chrome = 1080 - 600 = 480`（真值约 **143px**）。

连锁：`floor_h = 720 + 480 = 1200` → `want_h = 1080` 被 clamp 到 `1200`
→ **每次 headed open 都把窗口从 1080 撑到 1200**，正是「窗口尺寸决策」要防的反面。
同一次日志后段 `viewport.content` 实测 `1920×1057`，反证真值 chrome ≈ **143px**，
与 `HEADED_CHROME_FALLBACK_H = 140` 几乎一致。

**修复**：新增纯函数 `plausible_chrome_height(outer_w, outer_h, inner_w, inner_h) -> f64`，
判为不可信即回退 `HEADED_CHROME_FALLBACK_H`：

1. `chrome_h` 落在 `[40, 300]` 之外（负值 = 部分平台 `outer == inner`；过大 = inner 仍是默认值）；
2. `inner` 恰为 `(800, 600)` 且 `outer` 与之不等 —— macOS 上确定性复现的失真特征。

响应中同时回报 `chrome_height_raw`（实测原值）与 `chrome_height_fallback`（是否走了兜底），
供 Agent / QC 判断窗口尺寸决策建立在真值还是估计值之上。

修复后实测：`adjusted:false`，窗口不再被无谓调整。

## 4. F4（P2）大屏不铺满 + connect 模式误改用户窗口

### 4.1 大屏不铺满（用户第 9 点反馈）

本机双屏：

```
U2790B  : 6400×3600 物理, UI Looks like 3200×1800（主屏, DPR 2）
PM1402  : 1920×1080, UI Looks like 1920×1080
```

窗口硬编码 1920×1080，在 3200×1800 主屏上只占 **60% 宽 × 60% 高** —— 这正是
「网页没有铺满 Chrome 窗口」。

第 139 轮的 `headed_window_plan` 目标规则是 `clamp(请求尺寸, lo, cap)`，
即「屏幕给得更多就保持请求尺寸」—— 只覆盖了**小屏方向**，缺**大屏方向**。

**修复**：新增 `fill: bool` 参数。`fill=true`（未显式指定窗口尺寸）时目标取 `cap`
（铺满工作区）；`fill=false`（显式传了 `window` 参数）时保持原行为，只做不溢出收边。
小屏方向行为**完全不变**。

实例侧新增 `BrowserInner.explicit_window` 标志承载该意图。

实测：`fill:true`，窗口调整到 1900×979 铺满 1920×1080 工作区。

### 4.1b 铺满仍有两处漏：只改尺寸不动位置 + 不复核（用户复报「网页没有铺满」）

按 4.1 只下发 `setWindowBounds(width, height)`，`left/top` 显式传 `None`
（「保持 Chrome 已有位置」）。但 Chrome 的初始位置并非工作区原点 —— 实测本机
`applied.left=22, top=31`，此时宽 `avail-16` 的窗口右缘 `22+3184=3206` 已超出
3200 的工作区、底缘同理，**窗口尺寸铺满了、位置却溢出屏外**，用户看到的仍是
「没铺满」。多屏场景更明显：`availLeft/availTop` 非 0（实测副屏
`672,1800`），按原点补边距才不会落到错误的显示器上。

第二处漏是**不复核**：「已下发 setWindowBounds」不等于「真铺满」—— Chrome 会
自行 clamp（实测目标高 1784 实际落 1769，菜单栏在窗口激活后出现又吃掉 82px
工作区），窗口管理器也可能约束尺寸。铺满是给用户的**可见承诺**，必须有回读校验。

**修复**（`browser.rs::fit_headed_window` + `browser_viewport.rs`）：

1. `HEADED_WINDOW_METRICS_JS` 增加 `availLeft/availTop`；
2. `fill=true` 时**同时下发** `left=availLeft+8`、`top=availTop+8`（显式指定尺寸的
   路径仍传 `None`，尊重调用方意图）；
3. 调整后回读真实 `outer*`/`avail*`，算 `fill_ratio = min(outer_w/avail_w,
   outer_h/avail_h)`，低于 `FILL_RATIO_MIN=0.97` 时按回读真值**重试一次**；
4. 响应新增 `fill_ratio` / `fill_verify` / `positioned` 供 Agent 与 QC 对账。

实测：`fill_ratio: 0.98`、`positioned: true`、窗口落在副屏工作区原点。
单测锁死三态：铺满取宽高中较小者、探测失败返 0、**1920×1080 落在 3200×1800 上
判为未铺满**（即本次报障形态）。

### 4.2 connect 模式误改用户窗口（顺带发现）

`fit_headed_window` 在 headed open 路径上被调用，**不区分 connect 模式**。
而 connect 模式（第 142/144 轮「复用已登录浏览器」）接管的是**用户自己的** Chrome ——
调它的窗口尺寸、抢它的前台都是对用户窗口的 intrusive 操作，违反
「connect 模式零注入、不干预用户浏览器」原则（该原则此前只覆盖 guard 蒙层与输入锁定，
窗口几何这一路漏了）。

**修复**：`connect_mode` 时 `fit_headed_window` 整路早退，不调尺寸、不置前，
响应回报 `reason: "connect 模式不干预用户浏览器窗口"`。
