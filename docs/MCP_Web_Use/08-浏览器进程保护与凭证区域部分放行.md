# 08 - 浏览器进程保护与凭证区域部分放行(第 144 轮)

> 唯一最新版。两个需求的联合解决方案:
> 1. **绝不关闭用户已打开的 Chrome**(启动/关闭/调试重启全链路);
> 2. **人工必填区域(账号/密码/验证码)自动成为 partial 部分屏蔽模式的非屏蔽区域**。
>
> 关联文档:[06-复用已登录浏览器会话.md](./06-复用已登录浏览器会话.md)(auto_relaunch 语义更新)、
> [07-页面管控三档模式与人工交互设计.md](./07-页面管控三档模式与人工交互设计.md)(request_human 解锁语义更新)。

## 1. 背景与问题

### 1.1 问题一:auto_relaunch 按进程名杀掉用户浏览器

第 142 轮 `open(reuse_existing=true, auto_relaunch=true)` 的自动重启链路第一步是
`quit_chrome()`(`src/agent/browser_reuse.rs`):

- macOS:`pkill -x "Google Chrome"`(以及 Edge/Chromium/Brave);
- Windows:`taskkill /IM chrome.exe /F`。

两者都**按进程名匹配全部实例** —— 用户日常打开的 Chrome(可能挂着几十个标签页、
未提交的表单)会被一并杀掉。实测影响:

- 用户会话被强断,未保存内容丢失;
- 「让 Agent 复用我的登录态」反而以「关掉我的浏览器」为代价,体验倒挂。

全链路盘点(其余路径均安全,无需改动):

| 路径 | 行为 | 是否影响用户浏览器 |
| ---- | ---- | ---- |
| `BrowserManager::close_page` / `shutdown`(launch 模式) | `browser.close()`/`kill()` 只作用于**自己 spawn 的子进程**(一次性 `laew_browser_*` profile) | 否 |
| connect 模式 close | 只断连 CDP,不关浏览器 | 否 |
| `cleanup_legacy_orphans` | 只杀 `--user-data-dir=<tmp>/laew_browser_*` 的孤儿 | 否 |
| 进程外 watchdog / `cleanup_sync` | 只杀登记的自身 PID | 否 |
| **`relaunch_and_wait` 第 1 步 `quit_chrome`** | **按进程名杀全部 Chromium 系浏览器** | **是(本轮根治)** |

### 1.2 问题二:request_human 提问期间整页放行,权限过大

第 143 轮 `request_human(unlock_page=true)`(默认)把页面**整页切 open**:人工在
等待期间可以操作页面**任何区域**。而 HITL 的真实需求绝大多数是「人工只在凭证输入
区域动手」(填账号/密码/验证码/滑块/短信码),整页放行意味着:

- 人工可能误触页面其余区域(改掉 Agent 正在维护的页面状态);
- 「必须人工输入的信息」与「其余仍由 Agent 管控」没有边界 —— partial 部分屏蔽
  模式的白名单(`allow_selectors` 非屏蔽区域)正是为此设计,却没有被 HITL 链路使用。

## 2. 需求(用户原文归纳)

1. macOS/Windows 上启动/关闭浏览器时,**不要关闭用户已经打开的 Chrome**;复用当前
   已开的浏览器服务。
2. Agent 用 `MCP_Web_Use` 发现网站需要输入账号/密码/验证码等**必须人工输入**的信息时,
   相关区域应是**部分屏蔽模式(partial)的非屏蔽区域**。

## 3. 方案一:浏览器进程保护(不退出用户 Chrome)

### 3.1 原则:进程所有权

laew 只对**自己拥有的浏览器进程**有生杀权:

- launch 模式:自己 spawn 的一次性 profile 实例(已有 watchdog/登记簿治理,不变);
- connect 模式:不拥有进程,close 只断连(第 142 轮已如此);
- 调试重启(auto_relaunch):新启的独立调试 profile 实例归 laew 管;
  **用户日常浏览器进程一律不碰**(删除 `quit_chrome`/`wait_for_chrome_gone`,
  代码库中不再存在任何按进程名杀浏览器的路径)。

### 3.2 auto_relaunch 新流程(三步,无退出步骤)

```
1. 复制默认 profile 登录态关键文件 → ~/.laew/chrome_debug_profile(用户 Chrome
   运行中直接复制,best-effort:单条失败跳过,响应回报 copied/skipped 数);
2. 以 --user-data-dir=<调试profile> --remote-debugging-port=<port> 另启一个
   独立 Chrome 实例(不同 user-data-dir ⇒ 与用户正在运行的 Chrome 并存,
   这是 Chrome 多实例的官方机制;调试实例同样是 headed 可见窗口);
3. 轮询等调试端口就绪(≤15s)→ Browser::connect 接管(复用既有档位一链路)。
```

### 3.3 运行中复制的取舍

旧流程退出 Chrome 后复制,换来「文件锁 + WAL 一致性」;新流程不退出,接受两点
代价并如实回报:

- **登录态可能略旧**:运行中的 Chrome 内存里可能有未刷盘的 Cookie 变更,复制到的
  是磁盘态(差值通常是最近几分钟);
- **单条复制可能失败**(Windows 句柄独占更常见):跳过该条,`data.login_state_copied`
  如实回报;登录态缺位时该网站表现为未登录,Agent 走 `request_human`(人工登录
  先行流)兜底,而不是失败。

复制清单在原 `SECRET_COPIES` 基础上补 `-wal` 变体(`Cookies-wal`/`Login Data-wal`),
降低 WAL 模式下撕裂读的概率(缺失即跳过,零成本)。

### 3.4 接口与响应变化

- `auto_relaunch` 参数语义更新:「复制登录态 → 独立 profile 另启调试实例 → 接管」,
  **不再退出用户浏览器**,因此无需用户「同意关闭浏览器」级别的授权门槛,但保留
  显式 opt-in(默认 false)不变;
- auto_relaunch 成功响应附加:`login_state_copied`(复制条数)/`login_state_skipped`;
- 3002 信封 hint 文案同步(不再出现「自动退出+重启 Chrome」)。

## 4. 方案二:HITL 凭证区域部分放行(partial 白名单挖洞)

### 4.1 解锁档位决策表(request_human,第 144 轮)

`unlock_page=true`(默认)时,提问期间的页面放行按以下顺序决策:

| 优先级 | 条件 | 放行方式 |
| ---- | ---- | ---- |
| 0 | `unlock_page=false` / hidden / connect / 当前已是 open 档 | 不动作(第 143 轮语义不变) |
| 1 | `params.allow_selectors` 显式传入(非空) | **partial + 该白名单挖洞** |
| 2 | 自动探测到凭证区域(见 4.2) | **partial + 探测到的白名单挖洞**(状态条明示「人工输入区已开放…」) |
| 3 | 探测不到凭证区域(如扫码页整页即二维码) | 回退整页 open(第 143 轮行为) |

收口(应答/超时/取消/不可用)后一律按实例期望态恢复(fail-open,既有逻辑)。
响应 `data.page_unlock` 回报 `{applied, mode, allow_selectors, source}`,
`source ∈ explicit|auto|fallback_open|none` 供 LLM/Debug 对账。

杀开关:`LAEW_WEB_HITL_SCOPE=off` 跳过探测,恒走整页 open(回退第 143 轮行为)。

> **第 145 轮补记**:档 2/3 的状态条第三行 note 统一注明收口动作
> 「完成后回弹窗点『提交 / 继续』」(partial 档:「人工输入区已开放(部分锁定),
> 完成后回弹窗点『提交 / 继续』」;open 回退档新增 note:「人工介入中·页面临时开放,
> 完成后回弹窗点『提交 / 继续』」)。管控三档(locked/open/partial)只在 Agent 全面
> 操作时生效;HITL 提问期间是**临时放行态**,人工完成操作后的交棒动作必须在页面上
> 可见 —— 实测反馈:整页 open 回退档只有通用「页面开放」状态条,人工不知道做完
> 要回弹窗点继续。

### 4.2 凭证区域探测(页面内 JS probe)

新模块 `src/agent/tools/mcp_web_use/unlock_zone.rs`,一次 `eval_js` 探测,产出
**主文档 CSS 选择器**列表(partial 白名单直接可用),规则按优先级:

1. **密码框容器**:可见 `input[type=password]` → 就近 `form`(矩形 ≤60% 视口);
   无 form/表单过大 → 沿父链 ≤4 层找 class/id 命中凭证语义关键词的祖先容器;
   再兜底取输入框父节点(保证提交按钮落在放行洞内);
2. **验证码 iframe**:`iframe` 的 `src/id/class/title/name` 命中
   `captcha|verify|recaptcha|geetest|tcaptcha|slider|challenge` 等关键词 → 取
   iframe 元素本身(主文档挖洞覆盖其矩形);
3. **验证码/滑块容器**:`div/section` 命中同组关键词且矩形 ≤40% 视口;
4. **短信/OTP 输入框**:非密码 `input` 的
   `name/id/placeholder/autocomplete/aria-label` 命中
   `otp|one-time|sms|短信|动态码|验证码|code` → 同 1 的容器化规则。

选择器生成:`#id`(CSS.escape)优先 → `tag[name="…"]`(唯一时)→ `tag:nth-of-type`
路径(≤4 层);生成即用 `querySelectorAll` 自验命中;输出去重、≤8 条
(对齐 `MAX_GUARD_SELECTORS`)、单条 ≤150 字符(<160 上限)。
探测不涉及 shadow DOM(穿透不了;探测不到即回退 open,不误伤)。

### 4.3 盾区 JS:子 frame 白名单 fail-open(本轮必改的前置缺陷)

第 143 轮白名单挖洞的实现在**每个 frame** 各自求补集:白名单选择器在子 frame 里
通常**零命中** → `rects` 为空 → 整 frame 加盾。对跨域验证码 iframe(reme reCAPTCHA
复选框、geetest 滑块)这意味着**洞挖了也点不进**(iframe 内部被自家盾罩盖住)——
与本轮「验证码区域必须可人工操作」直接冲突。

修正:`partial + 白名单` 模式下,**子 frame(`window.top !== window`)零命中时不加盾**:

- 主文档的条带分解已经管住了整屏可点区域(iframe 只能出现在主文档某个矩形内,
  该矩形不在洞里时,主文档盾罩(z-index 更高)照拦);
- 子 frame 是白名单语义管不到的粒度,整 frame 加盾只会误伤(黑名单行为**不变**:
  子 frame 命中黑名单元素照样加盾,「跨域 iframe 同样罩得住」的能力保留)。

### 4.4 提问期间的导航重放(多步登录不断链)

人工在放行洞里提交登录后页面往往**导航到下一步**(2FA 页/授权页)。管控 JS 的
新文档按 `new_page` 时烘焙的初始配置重建(= locked),会把人工锁死在半路。本轮
在提问期间 spawn 导航监视协程:

- 订阅 `Page.frameNavigated`,仅主 frame(parent_id 为空)触发;
- 重放临时放行态(partial 挖洞或 open),与 Agent 导航动作收尾的 re-assert 同构;
- 收口时 `abort()`(应答/超时/取消/不可用四种结局都收),再恢复实例期望态。

### 4.5 blockers 联动(发现即给选择器)

`inspect(info=blockers)` 命中人工阻断时,同页面顺带跑一次凭证区域探测:

- `data.credential_zones = [选择器…]` 直接可读;
- 同时注入 `data.human_assist.allow_selectors`,LLM 把它原样传给
  `control(request_human, params.allow_selectors=[…])` 即得精准放行
  (自动档不命中时的人工兜底通道)。

## 5. 安全边界与回退

| 场景 | 行为 |
| ---- | ---- |
| 用户 Chrome 正在运行 + auto_relaunch | 不退出;复制 best-effort;另启独立实例并存 |
| 复制失败/登录态缺失 | 响应回报计数;网站表现为未登录,走 request_human |
| 探测不到凭证区 | 回退整页 open(第 143 轮行为),不阻塞提问 |
| `LAEW_WEB_HITL_SCOPE=off` | HITL 解锁恒整页 open(杀开关) |
| partial 洞外区域(含 iframe 区域) | 主文档条带盾照拦(4.3 修正后语义不变) |
| Agent 自己的输入动作 | 「先隐盾后复盾」让路机制不受影响(临时态也是 partial) |
| 截图/OCR/HITL 附图 | 拍前 `guard_suspend_visuals` 挂起全部视觉(既有),证据链不受盾区污染 |

## 8. 第 145 轮补记:应答 next_hint 分流与交棒显性化

实测(云智眼预发布环境):人工在弹窗**输入验证码文本**(`z7z2`)后,旧 `next_hint`
对 captcha 一律说「人工已完成操作,请 inspect 验证页面状态」——但人工并没有在页面
完成操作,只是报了码;Agent 被误导去 inspect 绕圈而不填码。第 145 轮在
`control.rs` 增加纯函数分流(`hitl_answer_hint` + `is_option_pick_answer`,单测锁死):

| `human_response` 形态 | reason | `next_hint` |
| ---- | ---- | ---- |
| 自由文本(无 `N. ` 前缀) | captcha / sms / two_factor | **立即 `control(input_text)` 填入验证码/动态码输入框并点击提交/登录**,不要仅 inspect 观望 |
| 「N. 选项」形态(弹窗选项按钮 / TUI 数字映射共用) | 任意 | inspect 验证页面当前状态后继续流程 |
| 自由文本 | 其它 reason | 按 `human_response` 内容继续流程 |

配套:弹窗主按钮「提交 → 提交 / 继续」(双语义:交码/交棒)、新增「⏱ +2分钟」
延长等待(总上限 30 分钟,根治人工整链登录超 120s 分档超时)、提问期间两档放行的
状态条 note 注明收口动作 —— 详见 `03-人工介入弹窗原生UI方案.md` §4.5/§14 与
`tmpPlan/2026-10-10_HITL弹窗继续语义与人机交互闭环.md`。
