## 一、复核方法

一台真机（Windows 11 + Chrome 155），四种配置各跑一遍**同一条探针**：

| 配置 | 说明 |
| ---- | ---- |
| `headed` + 缺省档（hardened） | 日常路径（可见窗口） |
| `hidden` + 缺省档 | 无头档（UA 去令牌路径） |
| `headed` + `stealth=off` | 排障对照（裸环境） |
| `hidden` + `stealth=off` | 裸环境 + 无头 |

探针内容：页面侧读数（`navigator.*` / `screen.*` / `window.*`）、`permissions.query`、
`mediaDevices.enumerateDevices`、**blob worker 内读数**、**CDP 附着层四项检测**、
以及**服务端侧实际收到的请求头与请求次数**（本地计数服务器记录 `User-Agent` /
`Sec-CH-UA` / 请求序号）。

> 「服务端读数」是本轮新增的一类判据。前四轮的判据都在**页面侧**，而站点风控有一半
> 在服务端；本轮第一次把「我们发出去的请求长什么样」变成可断言的数据。

## 二、被真机推翻的三条自证判据

### 2.1 `languages_frozen` —— 第 176 轮把方向搞反了

第 176 轮的结论是「原生 WebIDL `sequence<DOMString>` 返回**非 frozen** 数组，
故我们去掉了回填里的 `Object.freeze`」，并据此新增自证项：读到
`Object.isFrozen(navigator.languages) === true` 即告警（判定为我们 freeze 了）。

真机四档读数**全部** `Object.isFrozen(navigator.languages) === true`——**包括
`stealth=off` 的裸环境**：

```
[headed-off]  languages_frozen: true      [hidden-off] languages_frozen: true
[headed-hard] languages_frozen: true      [hidden-hard] languages_frozen: true
```

结论反了：规范里 `NavigatorLanguage.languages` 的类型是 **`FrozenArray<DOMString>`**，
原生**就是冻结的**。于是第 176 轮那条自证在**每一台真实浏览器上恒告警**
（`risk_tier` 从 `ok` 被抬到 `warn`），而回填（去掉 freeze）造的才是异类。

**处置**：① 保真回填改回 `Object.freeze(list)`，与原生同形；② 自证项**反相**——
`languages_not_frozen`（读到 `false` 才告警）；③ 单测 `语言列表回填不得冻结`
改为 `语言列表回填必须冻结`；④ 清掉 `FIDELITY_JS` ③ 里那段方向错误的注释。

### 2.2 `focus_visibility_mismatch` —— 判据与理论相反，且真机常态命中

第 177 轮把「`visibilityState === 'visible'` 却 `document.hasFocus() === false`」
列为**硬判据**（`HARD_CODES`，命中即 `risk_tier=high`），理由是「真机前台页面二者一致」。
真机读数：

| 配置 | `visibility` | `has_focus` |
| ---- | ------------ | ----------- |
| headed（缺省档） | visible | **false** |
| headed（裸环境） | visible | **false** |
| hidden | visible | **true** |

- 无头档反而**有焦点**（该判据在无头下不命中），有头档反而**没有** —— 与理论完全相反；
- `LAEW_WEB_FOCUS=keep`（第 21 轮，缺省）会**主动把键盘焦点还给调用前的应用**，
  所以「有头 + 无焦点」是我们**自己设计出来的常态**；
- 更根本的是：真实用户的 Chrome 窗口被别的窗口挡住（未最小化）时，
  `visibilityState` 同样是 `visible`、`hasFocus()` 同样是 `false` —— 这是
  **普通浏览的常见状态**，不是「无人值守」的证据。

**处置**：从 `suspicious` 与 `HARD_CODES` 中移除，字段保留为**只观测**
（与 `injected_ns_keys` 同档）。这直接闭合了 [31](./31-反检测注入时序与跨档自洽增强.md) §九.1
留下的复核项。

### 2.3 `injected_ns_keys` —— 正则写错，这条自证从来没生效过

```rust
Object.getOwnPropertyNames(window).filter((n) => /^__lz[0-9a-f]{8}/.test(n)).length
```

命名空间实际形态是 `__lzn` + 8 位十六进制（`inject_ns()`），第 5 个字符是 `n`，
**不满足 `[0-9a-f]`** —— 这个 filter 恒为空数组，自证永远报 `0`。
真机实测（用真确正则重测）：

| 配置 | ns 键数 | `getOwnPropertyNames(window)` 总数 |
| ---- | ------- | --------------------------------- |
| headed（缺省档） | **30** | 1264 |
| hidden（缺省档） | **1** | 1239 |
| hidden（裸环境，无注入） | 0 | 1238 |

即：**有头档每页往 `window` 上留 30 个同前缀的全局键**（guard 一族 ~19、
status 一族 ~7、highlight 一族 ~3、`StealthRev` 1）。此前文档写「只能观测不能消除」，
但那时**数字本身就是错的**（恒 0，被当成「几乎没有痕迹」）。

**处置**：① 正则修真（`^__lzn`，按 `inject_ns()` 的真实形态）；② 新增
`injected_ns_symbols`（`Object.getOwnPropertySymbols(window).length`，真机基线 **0**）——
为下一步「把 30 个字符串键收敛成 1 个 symbol 键」提供可度量的基线；
③ 响应 `note` 如实写明「有头档实际 30 个键，收敛方向见 docs §六」。

## 三、首文档盲区：`createTarget(url)` 的那一次裸奔加载（**本轮最高价值**）

### 3.1 实测

`new_page_impl` 用 `browser.new_page(url)` 建页，而 chromiumoxide 的
`create_page` 会**等到该 URL 加载完成才返回**。于是「隐身处置 → 导航」的实际序列是：

```
Target.createTarget(url)   ← ① 真实加载发生在这里(裸环境:无隐身/无 UA 处置/无屏幕几何)
Runtime/Network enable, 隐身注入, UA 去令牌, 屏幕几何   ← ② 处置
page.goto(url)             ← ③ 真实加载**再发生一次**(这次在处置之下)
```

计数服务器实测（`mode=hidden`，缺省档）：

```
[srv] req#1 User-Agent: … HeadlessChrome/155.0.0.0 …     ← 裸奔:UA 令牌原样发出去
[srv] req#2 User-Agent: … Chrome/155.0.0.0 …             ← 处置后
主 URL 请求次数 = 2
```

两个后果：
1. **首个文档全程裸奔** —— 站点风控 SDK 在文档最早期采指纹并上报（第 177 轮
   修的是「脚本注册早于导航」，但注册早于的是 **goto**，`createTarget` 那一次
   排在更前面，第 177 轮的结论对它无效）；
2. **同一个新会话对同一 URL 连续加载两次** —— 本身就是一个异常的导航序列，
   且白付一次完整加载（含所有子资源）。

### 3.2 处置

建页改用 `about:blank`，把「真实加载」收敛成唯一一次：

```
Target.createTarget(about:blank)   ← 空文档,无站点脚本、无请求
Runtime/Network enable, 隐身注入, UA 去令牌, 屏幕几何
page.goto(url)                     ← 唯一一次真实加载,且自始就在处置之下
```

`new_window=true`（多窗口并行）路径同样处理。

### 3.3 `about:blank` 不是安全上下文 —— 为什么这条不伤 UA 去令牌

真机读数：`about:blank` 上 `isSecureContext === false`、`origin === "null"`、
`navigator.userAgentData` **不存在**（Client Hints 只在安全上下文暴露）。于是
「在 about:blank 上做 UA 去令牌探测」会读不到品牌表 —— 这正是 `apply_ua_destealth`
此前必须在真实页面上跑的原因。

但同一次实测把这条顾虑**否掉了**：无头档下 `createTarget` 那次请求的
`Sec-CH-UA` 是 `"Google Chrome";v="155", "Chromium";v="155", "Not(A:Brand";v="24"`
—— **品牌表里根本没有 `HeadlessChrome`**，令牌只出现在 **UA 字符串**里：

```
[srv] req#1 sec-ch-ua: "Google Chrome";v="155", "Chromium";v="155", "Not(A:Brand";v="24"
[srv] req#1 User-Agent: … HeadlessChrome/155.0.0.0 …      ← 令牌只在这一处
```

而 `navigator.userAgent`（**在 about:blank 上可读**）就够生成清理计划了。
所以 about:blank 预载**不损失** UA 去令牌能力：唯一一次真实请求发出时，
UA 字符串已经是干净的。品牌表过滤逻辑保留为防御（真机从未触发
`brands_filtered`，因为 Chrome 的品牌表本就不含自动化令牌）。

### 3.4 但「只清 UA 字符串」会把品牌表清空 —— 二段式补全（**本轮自造、自测、自修的一条**）

上一条只说对了一半。改完 about:blank 预载后，既有冒烟
`stealth_headless_ua_destealth_smoke` **立刻失败**：`navigator.userAgentData.brands`
变成空的。根因是 `Emulation.setUserAgentOverride` 的语义 —— **不带
`userAgentMetadata` 时，页面侧的 Client Hints 品牌表会被清空**（不是「保持不变」）。
于是我们只是把一种不自洽（UA 说 Chrome、品牌表说 Headless）换成了另一种
（UA 说 Chrome、品牌表说空），后者更显眼：Chrome 155 永远会发 `Sec-CH-UA`。

处置 = **二段式**（`browser_ns::UaSweep` 把结果从 `bool` 细化为三态）：

| 阶段 | 时机 | 动作 | 判据 |
| ---- | ---- | ---- | ---- |
| 一 | goto **之前**（页面是 about:blank） | 只清 UA 字符串 → `UaSweep::StringOnly` | 唯一一次真实请求的 `User-Agent` 不含 `Headless` |
| 二 | goto **之后**（真实文档 = 安全上下文） | `restore_native_ua()` 撤掉半吊子覆盖 → 页面重新报出**原生** UA 与品牌表 → 再探一次 → 下发**完整**覆盖 | 页面侧 `userAgentData.brands` 含 `Chromium`/`Google Chrome` 且不含 `Headless` |

二段式第二段的窗口很短（页面脚本早在 document-start 就读到了干净的 UA 字符串），
且**有头档不可达**（第一段本就 `Skipped`，没有令牌要清）。`restore_native_ua` 走
CDP 约定「`userAgent` 传空串即移除覆盖」。

> 这条值得记下来：**它是本轮唯一一条「改出来的缺陷」**，而且是被既有冒烟当场抓住的
> —— 上一条（§3.3）只验证了「UA 字符串干净」这个我关心的维度，而品牌表是同一个
> 机制的另一半。判据不覆盖的维度，改动的破坏性就看不见。

## 四、`pdfViewerEnabled` 与插件回填的一致性

回填分支只在 `navigator.plugins.length === 0` 时触发（本机原生就是 5 条 PDF 插件，
四档实测 `plugins: 5` / `mimeTypes: 2` / `pdf_viewer: true`，**回填路径在本机永不走**，
见 §七的强制触发差分）。但一旦在无插件环境触发，我们会造出「5 个 PDF 插件」，
而 `navigator.pdfViewerEnabled` 在该环境里通常是 `false` —— **5 个 PDF 插件却报
「PDF 查看器不可用」**，是我们自己制造的矛盾（与第 175 轮「形状错误的回填比不回填
更危险」同源）。处置：回填分支同批把 `pdfViewerEnabled` 对齐为 `true`（经 `reg()`
登记身份）；体检侧新增自证 `pdf_viewer_plugin_mismatch`（插件非空却报 `false` 即告警，
对原生环境同样有效）。

## 五、负结论归档（**别再追这三条**）

复核的代价必须留下收益：以下三条流传甚广的「CDP 泄漏」，真机实测**在本项目环境下
不成立**，本轮记录并停止投入。

| 假说 | 真机读数 | 结论 |
| ---- | -------- | ---- |
| `Runtime.enable` 会被 `console.debug(err)` 的 `stack` getter 识破（rebrowser-patches 的 `runtimeEnableLeak`，业界评为 critical） | 四条已知检测路径（own getter / 原型 getter / Proxy 原型链 / 普通对象原型 getter）在 Chrome 155 上**全部为 false**（延迟 400ms 读取，排除异步假阴性） | chromiumoxide 确实在每帧初始化时发 `Runtime.enable`，但**该检测在 Chrome 155 已不可复现**（V8 2025-05 的 `getErrorProperty` 补丁覆盖了 own，本机实测原型路径也不触发）。不做处置、不加自证（加了恒 false 只是噪声） |

## 六、注入面收敛（**本轮只度量，未动刀**）

真机基线（§2.3）：有头档每页 **30 个** `__lznXXXXXXXX*` 字符串键，无头档 1 个，
符号键 0 个。30 个同前缀键是**我们自己留的最大一处页面级签名**——比
`webdriver`、WebGL 兜底串这些「别人也有的痕迹」更独有。

收敛方案（下一轮执行，本轮先把数字测准）：

1. 四套注入脚本（guard / status / highlight / stealth）共用**一个**
   `window[Symbol.for('__lznXXXXXXXX')]` 命名空间对象：字符串键 30 → 0，
   符号键 0 → 1（`getOwnPropertyNames` / `Object.keys` / `for…in` / 展开全部不可见）；
2. 实施走**渲染期文本改写**而不是逐行改模板：`browser_ns::render_template` 按
   **窗口全局后缀白名单**（`GuardSet`/`GuardOff`/`Status*`/`AgentHighlight*`/`StealthRev`…）
   把 `window.%NS%<Suffix>` 改写成 `%NS%NS.<Suffix>`；DOM id 后缀
   （`guard_ui__`/`sb_title__`/`agent`/`locked__`）不在白名单内，保持原样；
3. Rust 侧 21 处 `ns_global("X")` 构造的求值表达式同步改为
   `window[Symbol.for('<ns>')].X`（新增 `ns_member_expr(suffix)` 单点收口）；
4. 判据：`injected_ns_keys` 30 → 0 且 `injected_ns_symbols` 0 → 1，由本轮新增的
   两个观测项**直接验收**。

> 之所以不在本轮做：它触及缺省档（headed）的 guard/status/highlight 热路径，
> 而这三者的真机冒烟覆盖不如 stealth 完整。先把「30」这个数字与验收判据钉死，
> 再动刀。

## 七、验证

### 7.1 真机取证服务器（新增能力）

`tests/stealth_reveal_smoke.rs` 的服务器**记录请求头与请求序号**：断言不再只看页面侧
读数，而是直接对账「站点实际收到了什么」。两条断言（`stealth_first_document_single_load_smoke`，
走 hidden 档 —— 只有无头档的 UA 才带令牌，headed 档下这条恒真、测不出东西）：

- **首文档单一加载**：目标 URL 的请求次数 **1**（修复前为 2）；
- **首个请求 UA 干净**：`req#1` 的 `User-Agent` 不含 `Headless`（修复前含），
  且 `Sec-CH-UA` 不含自动化品牌；
- 页面侧复读 `navigator.webdriver` / `userAgent` 同样干净。

### 7.2 插件回填真机差分（**闭合 31 §九.2**）

31 号文遗留：「回填替身的形态只有 Node 垫片背书，没有真机对照」（因为本机原生就有
5 条插件，回填分支永不触发）。本轮把这条补上：`stealth_plugin_backfill_real_machine_diff_smoke`
在真机上**强制触发**回填（先把 `Navigator.prototype.plugins/mimeTypes` 覆写成空数组、
清幂等闸标记、再注入保真档脚本文本），然后把**回填产物**与**同机原生形态**逐字段对账
（24 项：tag / `instanceof` / `constructor` / 中间原型自有键（含符号键与顺序）/
实例自有键 / 迭代器长度与自反 / `namedItem` 与其回指 `p[0]` / `item(0)===p[0]` /
`mimeTypes` 条数 / 元素形态（`Plugin`/`MimeType` 的原型自有键、`constructor`、
是否凭空多出 `mimeTypes`、`enabledPlugin` 指向）/ 插件名列表）。

判据一律以**同一次运行读到的原生读数**为基准（不是硬编码常量），因此它对
「代码按设想工作但设想不符合原生」这类问题同样有效 —— **本轮就靠它查出四处中间原型
缺 own `constructor`**（`Object.create(原型)` 只**继承**该键，
`Object.getOwnPropertyNames(中间原型)` 因此比原生少一项，一行即可看出「这不是原生
原型」），修复后 24 项**逐项相等**（含键序与符号序）。

## 九、遗留与下一步

1. **注入面收敛落地**（§六）：30 → 0 字符串键 + 1 符号键，验收判据已就位
   （`injected_ns_keys` / `injected_ns_symbols`）。
2. **派生页（`target=_blank` / `window.open` / `new_tab`）的首请求仍是裸的**：
   新 target 由浏览器自己创建，我们的隐身脚本只能在收编之后注册（那时文档已加载）。
   收编后重载能补救后续文档，但首请求已发出 —— 且重载本身是异常序列，故不做。
   任务关键站点请优先 `open` 直开目标页，而不是靠页面内点击派生。
3. **`focus_visibility` 只观测**：如需重新利用该信号，必须先设计出「能区分
   *窗口被遮挡* 与 *无人值守*」的判据（当前两者的页面侧读数完全相同）。
4. **`automation_globals` 前缀表**仍是启发式白名单（同 31 §九.4）。
5. **预存在缺陷（非本轮引入）**：`mcp_web_use_multi_window_parallel_smoke` 与
   `mcp_web_use_open_control_inspect_smoke` 在本机**挂死**（>60s 不返回，需强杀）。

   多窗口平铺与 open/control/inspect 长链路各需单独排查。
   本轮的取证冒烟因此**独立成文件**（`tests/stealth_reveal_smoke.rs`，独立进程 + 独立
   `BrowserManager` 单例），不与该用例共用二进制。
