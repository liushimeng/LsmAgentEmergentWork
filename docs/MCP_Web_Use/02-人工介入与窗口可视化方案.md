## 1. 背景与目标

Agent 用 MCP_Web_Use 自动化网页任务时,存在三类无法纯自动闭环的场景:

1. **人工验证阻断**:图形验证码、滑块拼图、短信验证码、扫码登录、人脸核身等,
   Agent 不应也不允许伪造或绕过;
2. **窗口可视化缺失**:默认 `hidden` 模式无窗口,人工想接管时看不到页面;
   可视化任务需要 1080p 窗口、可自由拖动改尺寸且渲染自适应、不缺区域;
3. **浏览器重复打开**:重试/多轮任务误启多个浏览器进程,干扰用户桌面。

本方案在既有单工具 action 架构上叠加**人工 + Agent 协同闭环**,参考外部调研
(`docs/Agent源码调研/专题/专题-第八轮-Tool权限策略引擎与沙箱设计深度对比.md` §8 HITL):

- atomcode `AskUserQuestion`:结构化问题(标题/选项/自由文本)→ 本方案 `request_human`;
- opencode `WorkerPendingPermission`:会话级请求队列防并发弹窗 → 本方案单 pending 槽位;
- claudecode 超时语义(默认 120s/上限 600s)→ 本方案按 reason 分档默认 120s/300s、clamp 10s~1800s(第 118 轮起,详见 §3.1);
- deepseek 4-outcome 审计 → 本方案 answered / timeout / cancelled / unavailable 四态。

## 2. 总体架构

```text
桌面弹窗 UI(human_ui,macOS/Windows;第 130 轮)   Agent(SubAgent-Work LLM Loop)
  │ 动态加载平台脚本 → 弹窗进程                      │ control_action=request_human
  │ 持续置顶 + 时间轴 + 选项/文本应答                │   bring_to_front + HumanAssistHub.request()
  │◄──────────────────────────────┐                │        │ oneshot 挂起等待
TUI(dispatch 阶段进度协程,兜底)    │                │        ▼
  │ 250ms 轮询 poll()               │                │ tool_result 信封
  │ 弹窗接管→只打通知行;弹窗失败→行读 │                │ code=0 answered / 4001 超时 / 4002 人工取消
  │ respond(id, Some/None) ─────────┼────────────────┘
  └ 任务结束后 cancel_pending() 兜底(同时回收弹窗进程)
```

关键决策:

- **进程内全局枢纽 `HumanAssistHub`**(OnceLock 单例)而非把 TUI 句柄传入工具层 ——
  Tool trait 无法感知调用方是否在 TUI 上下文,全局枢纽 + `attach()` 标记把
  「交互式 TUI」与「-p 管道模式」自然区分;
- **单 pending 槽位**:同一时刻最多一个人工请求;后到请求排队(等待前者 respond),
  对齐 opencode 队列语义的简化版,避免终端提示互相踩踏;
- **呈现端双通道,弹窗优先**(第 130 轮,详案 `03`):macOS/Windows 桌面会话自动弹出
  人工介入弹窗(持续置顶/倒计时/时间轴),TUI 退为兜底行读;弹窗应答与 TUI 行读互斥
  (`respond` 幂等),弹窗脚本失败自动降级 TUI,`-p`/管道模式在桌面会话同样可弹;
- **非 TTY(-p / 管道)且无桌面弹窗时 fail-fast**:未 attach 且弹窗不可用时 `request`
  立即返回不可用,工具回 `code=4001`,System Prompt 指引 LLM 终答告知用户改用 TUI 交互模式;
- **超时兜底**:默认按 reason 分档 120s/300s、上限 1800s(clamp);超时同 4001;
  弹窗接管期间 TUI 不读 stdin(根治阻塞读残留);TUI 行读路径仍保留 5s 缓冲清残。

## 3. 工具面新增能力

### 3.1 control_action=request_human(人工介入请求)

```json
{
  "action": "control",
  "page_id": "p_ab12cd34",
  "control_action": "request_human",
  "params": {
    "reason": "captcha",
    "message": "页面出现滑块验证,请人工完成验证后告诉我",
    "options": ["我已完成验证,继续", "跳过此页面", "取消任务"],
    "timeout_ms": 300000,
    "bring_to_front": true
  }
}
```

| 字段 | 说明 |
| --- | --- |
| `reason` | 9 个合法值:captcha(图形/滑块) / sms(短信验证码) / qr_login(扫码登录) / login(账密墙) / **real_name(实名/认证/人脸核身,第 117 轮新增)** / **two_factor(2FA/TOTP/邮箱验证码,第 117 轮新增)** / **oauth(第三方授权/SSO,第 117 轮新增)** / manual_verify(人工核验) / custom(自定义)。决定默认文案与 TUI 标签。完整列表见 `inspect(info=blockers)` 响应字段 `available_reasons`(LLM 拿到后可直接复用,避免死记硬背)。 |
| `message` | 给人看的具体说明(缺省按 reason 生成默认文案) |
| `options` | 1~6 个选项;TUI 渲染编号列表,回车默认选 1 |
| `timeout_ms` | 缺省按 reason 分档:captcha/sms/two_factor 120000(2 分钟),其余 300000(5 分钟);LLM 显式传入时 clamp 10s~1800s |
| `bring_to_front` | 默认 true:先 `Page.bringToFront()` 把浏览器标签页/窗口带到前台,人工可见 |

返回信封:

| code | 语义 | Agent 策略 |
| --- | --- | --- |
| 0 | `data.human_response` 为人工输入(选项文本或自由文本,如短信验证码数字);`data.assist_channel` 标注应答通道(`gui` 弹窗 / `tui` 终端) | 按回答继续任务(填入验证码 / 检查页面状态) |
| 4001 | 无人应答(超时 / 弹窗与 TUI 均不可用) | 如实告知用户「请在 laew 交互模式(桌面弹窗可用)下重试」,不得伪造结果 |
| 4002 | 人工明确取消(弹窗 `[取消]`/Esc/关窗,或 TUI 输入 q/取消) | 终止该浏览器路径,汇总已完成部分向用户报告 |

### 3.2 inspect info=blockers(阻断自动检测)

启发式扫描 `document.body.innerText`(截取前 20k 字符),Rust 侧模式表匹配:

| 模式 | kind |
| --- | --- |
| captcha / 验证码 / 滑块 / 拖动滑块 / puzzle / reCAPTCHA | captcha |
| 短信验证码 / 手机验证码 / 手机验证码 / sms code | sms |
| 扫码 / 二维码 / QR Code 登录 | qr_login |
| 请登录 / 登录后查看 / sign in / 逐梦正常登录 | login |
| 实名认证 / 身份认证 / 人脸核身 / 上传身份证 / kyc(第 117 轮新增) | real_name |
| 两步验证 / 双重验证 / 2FA / TOTP / 邮箱验证码 / google authenticator(第 117 轮新增) | two_factor |
| 微信授权 / github 授权 / 使用 github / continue with / sso 登录(第 117 轮新增) | oauth |

返回 `{blockers:[{kind,snippet}],suggested_action:"request_human"}`,
作为 SubAgent 判定「无法自动跳过 → 请求人工」的确定性依据(LLM 仍可结合上下文覆盖)。

### 3.3 窗口与视口(control_action 扩展)

| control_action | 参数 | 说明 |
| --- | --- | --- |
| `set_window` | `width`/`height`/`left`/`top`/`window_state`(normal/maximized/fullscreen) | CDP `Browser.getWindowForTarget` + `Browser.setWindowBounds` 运行时调整真实窗口;调整后自动清除视口覆盖,保证渲染=窗口、不缺区域 |
| `sync_viewport` | 无 | `Emulation.clearDeviceMetricsOverride` + 回读 innerWidth/innerHeight;人工拖动窗口大小后调用,使视口自适应窗口,消除黑边/缺区域/渲染不全 |
| `set_highlight` | `enabled`(默认 true) | 运行时开关 Agent 高亮蓝框 |

`open` 新参数:

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| `window_width` / `window_height` | **全模式默认 1920×1080(1080p,第 125 轮;hidden 旧默认 1440×900 已废弃)** | 启动时 `--window-size`(clamp 320~7680 / 240~4320);浏览器已存在时仅记录请求值,响应带 hint |
| `auto_expand_viewport` | true(第 125 轮) | 导航完成后若页面内容超出视口(横向被裁/可视高度不足),自动 `Emulation.setDeviceMetricsOverride` 把视口扩展到 ≤2560×1440(2K),结果回 `data.viewport`;根治「hidden 视口太窄页面显示不全、元素不可见不可点」,详见 `01` §16 |
| `highlight` | true(仅 headed 生效) | 注入 Agent 高亮蓝框(见 §4) |

视口观测与逃生(第 125 轮):`inspect(info=viewport)` 附 `overflow{horizontal,
vertical}` + `next_action` 对策;非整页截图溢出时响应附 `content_overflow` hint
(指引 `params.full_page=true`);`control(set_viewport)` 手动指定视口(同区间
clamp);`sync_viewport` / `set_window` 会清除 device metrics 覆盖(撤销自动扩展)。

浏览器生命周期强化(**不重复打开浏览器**):

- BrowserManager 进程内单例 + 单浏览器实例语义保持;`open` 时若浏览器已存在,
  **永远复用同一实例**(同 URL 页面还走既有 reuse 复用),响应新增 `browser_reused:true`
  与实际 `mode`;请求 mode 与现有实例不一致时不新启进程,返回 `mode_hint` 说明;
- 需要从 hidden 切换到 headed 可视化时:Agent 先 `close(page_id="all")` 回收浏览器,
  再以 `mode=headed` 重开;`request_human` 的 System Prompt 指引已包含该路径。

## 4. Agent 高亮蓝框(可视化标识)

人工介入场景下,桌面上可能有多个浏览器窗口,人必须一眼识别「哪个窗口被 Agent 控制」。
headed 模式注入页面级 overlay(`Page.addScriptToEvaluateOnNewDocument` + 立即执行,
派生/adopt 的新标签页同样注入):

- `#__laew_agent_frame__`:fixed inset:0、`box-shadow: inset 0 0 0 3px #1a73e8`
  (Chrome 品牌蓝)、`pointer-events:none`、`z-index:2147483647`、`data-laew-agent="1"`
  —— 页面四周一圈蓝色选中效果,不拦截任何鼠标/键盘事件,渲染与普通浏览器一致;
- `#__laew_agent_badge__`:右上角「LAEW Agent 控制中」小徽标,蓝底白字,
  `pointer-events:none`;
- `elements`/`dom` 提取自动过滤 `[data-laew-agent]` 子树,不污染 Agent 的 DOM 观察;
- 截图/OCR 保留蓝框(人视场景需要;LLM 视觉路径不受影响的优先级低于人工识别)。

## 5. 交互流程(第 130 轮起:弹窗优先,TUI 兜底)

### 5.0 「为什么没弹窗」的排障口径(第 131 轮新增)

用户反馈里最高频的一条是「验证码要人工,但没弹出人工介入 UI」。实测取证结论是
**弹窗机制本身正常**(直接跑平台脚本验证:`osascript -l JavaScript macos_dialog.js`
能正常弹 NSAlert、倒计时、`abortModal` 自超时、退出码 0),真正的成因按概率排序:

| 成因 | 判别方法 | 处理 |
| --- | --- | --- |
| **Agent 压根没走到验证码页**(`MCP_Web_Use open` 返 `2001 ERR_CONNECTION_*`,页面从未加载 → 无 blockers → 无 `request_human`) | `--debug` 日志里 `tool=MCP_Web_Use` 的 `code` 全是 2001 | 属「目标不可达」,按 §5.3 处理;**不要**改用 Bash 探测(见 `docs/MCP_Web_Use/04` 与 `src/agent/safety/web_evidence.rs`) |
| 弹窗被别的窗口盖住 | 桌面能看到浏览器但没看到弹窗 | 弹窗每 3s 自置顶拉焦;仍找不到时看事件行「弹窗启动失败,已降级为终端作答」 |
| `LAEW_HUMAN_UI` 被关 | `code=4001` 的 `data.human_ui_diagnostics.reason_hint` | 去掉该环境变量 |
| 非 macOS/Windows / 解释器缺失 | 同上,`reason_hint` 直接给结论 | 换平台或装解释器 |
| 走了 `-p` 单轮模式且当时无通知行 | **第 131 轮已修**:单轮模式现在会打通知行 | — |

`code=4001` 信封现在固定携带 `data.human_ui_diagnostics`
(`{gui_enabled, platform, reason_hint, env_switch}`),排障时不必再猜。

### 5.1 桌面弹窗(macOS / Windows,详案 `03`)

请求入位时 `human_ui::enabled()` 为真则自动弹出人工介入弹窗:标题/说明/页面/时间轴
(提出时间、已等待、超时剩余、超时截止,1s 动态刷新)+ 选项按钮 + 文本输入 + `[取消]`,
持续置顶拉焦;人工点选/输入/取消后经 `respond` 回填。弹窗接管期间 **TUI 不读 stdin**,
只打印通知行与结果事件;弹窗脚本失败自动降级 5.2 的 TUI 行读。

### 5.1.1 `-p` / `-f` 单轮模式的弹窗可见性(第 131 轮新增)

**修复前的缺口**:`run_one_shot` 全程不碰 `HumanAssistHub`。而
`HumanAssistHub::request()` 的放行条件是 `is_attached() || gui`(`human_assist.rs`),
macOS/Windows 上 `gui=true` → **弹窗照弹**,应答经 oneshot 正常回填、任务正常完成,
但终端一个字都不打印 —— 用户盯着 stdout 只看到「卡住了」,完全不知道有人在等他。

**现状**:`main.rs::run_one_shot` 起一个 250ms 轮询协程(与 TUI `dispatch_prompt`
同款分支):排空 `AssistEvent`、打「已弹出弹窗」通知行;任务收尾 `cancel_pending()` 兜底。
单轮模式**不读 stdin**(弹窗已是唯一应答通道;弹窗不可用时工具侧仍按既有语义返回 4001),
通知行走 **stderr** 以保持 stdout「只含答案与用量」的既有约定。

### 5.2 TUI 行读(兜底;Linux 全程走此路径)

阶段进度协程(`dispatch_prompt` 内)250ms 轮询分支:

```text
┌─ 🔐 人工介入请求 ────────────────────────────────
│ 类型: 图形/滑块验证码   页面: https://xxx/login
│ 说明: 页面出现滑块验证,请人工完成验证后告诉我
│ 选项:
│   1. 我已完成验证,继续
│   2. 取消任务
└──────────────────────────────────────────────
请输入选项编号或直接输入内容(回车=1,q=取消):
```

- 终端此时处于 cooked mode(任务执行期 InputHandler 未占用 stdin),直接行读;
- 映射:空回车 → 选项 1;数字 → 对应选项;`q`/`取消` → respond(None)(→4002);
  其余原文作为自由文本返回(短信验证码数字即走此路径);
- 任务结束(无论成败)调用 `cancel_pending()` 兜底,防挂起请求跨任务泄漏(同时回收弹窗)。

### 5.3 「该请求人工」的下沉到工具返回层(第 131 轮新增)

HITL 长期只写在**系统提示词**里(§7 第 13/16 条),工具响应层从不携带下一步。
实测中模型看到 `ocr_error` 后自由发挥 —— 反复调参 OCR、换 region、猜验证码,
而不是去 `request_human`,把迭代预算烧光。

第 131 轮把「下一步该做什么」下沉到工具返回层:凡判定为「自动路径已走到尽头」的
分支都在响应里附 `next_action` + `human_assist` 载荷:

```json
{
  "ocr_error": "OCR 失败:权限不足",
  "next_action": "request_human",
  "human_assist": {
    "ready": true,
    "reason": "captcha",
    "message": "页面验证码 OCR 不可用(或返回空文本),请人工在弹窗中识别并输入验证码后继续",
    "options": ["我已完成验证,继续", "取消任务"],
    "call": "MCP_Web_Use(action=\"control\", control_action=\"request_human\", params={…})",
    "rule": "严禁伪造/猜测验证码或跳过人工验证;人工应答后用 data.human_response 继续"
  }
}
```

触发点(三条,判定逻辑见 `src/agent/tools/mcp_web_use/mod.rs::ocr_unavailable_hint`):

| 触发点 | 判定 | reason 取值 |
| --- | --- | --- |
| `control(screenshot, params.ocr=true)` | `ocr_error` 存在 **或** `ocr_text` 为空 | `captcha` |
| `inspect(info=ocr)` | 同上(内部复用 screenshot 路径) | `captcha` |
| `inspect(info=blockers)` | `blocked=true`(原只有裸的 `suggested_action` 字符串) | `blockers[0].kind`(非法时回落 `manual_verify`) |

**空 `ocr_text` 与 `ocr_error` 同等对待** —— 验证码区域是噪声图时 OCR 常常返回空串,
模型此时最容易误以为「再调一次参数也许能出来」而反复重试。

## 6. 错误码扩展

| code | 含义 |
| --- | --- |
| 4001 | 人工介入不可用/超时(弹窗与 TUI 均不可用、或无应答)。**第 131 轮**:`Unavailable` 分支附 `data.human_ui_diagnostics`(`gui_enabled` / `platform` / `reason_hint` / `env_switch`)供排障;超时分支附 `assist_channel` |
| 4002 | 人工取消介入(弹窗取消/Esc/关窗,或 TUI q/取消) |
| **6001** | **任务锚点越界(范围约束,第 128 轮)** —— 见 `01` §17。**不属于人工介入**—— 它表示「这件事本身不允许做」,不是「需要人帮忙完成」;不与 4001/4002 互换语义 |
| **6001'** | **网页取证纪律拦截(第 131 轮)** —— Bash 探测/抓取任务目标站点被拒。走 Bash 工具的 `[工具执行失败]` 文本通道(非 MCP_Web_Use 信封),语义是「工具选型错误」,不是「范围越界」也不是「需要人帮忙」。开关 `LAEW_WEB_EVIDENCE=off` 全关,详见 `docs/MCP_Web_Use/04-网页取证纪律.md` |

非法 `reason` 走 1001 参数错误,响应 `data.allowed` 列出全部 9 个合法值,
LLM 不查文档即可自修复。

**澄清门不进 reason 枚举**:`request_human.reason` 是页面阻断类
(captcha / sms / qr_login / login / real_name / two_factor / oauth / manual_verify / custom),
「目标站点不明确」**不是**页面阻断,是任务入口(Yolo / 编排器 L1 澄清门,
`01` §17.1 左侧通路)的职责,发生在任何浏览器动作之前。两者职责互不重叠。

## 7. System Prompt 作业规范(摘录)

第 100 轮基线:打开页面后如遇登录/验证墙,先 `inspect(info=blockers)` 判定;OCR 可读的图形验证码走既有第 13 条自动链;**滑块/短信/扫码/人脸等无法自动完成的,必须 `control_action=request_human`(可视化场景建议先 open mode=headed 让人工看到窗口),严禁伪造或跳过**;`code=0` 用 `human_response` 继续;`4001` 如实报告需 TUI 交互模式;`4002` 终止路径;可视化任务用 `mode=headed` + 1080p,人工拖动窗口后 `sync_viewport` 自适应,蓝框高亮标识 Agent 窗口不要尝试移除;需要窗口切换 hidden→headed 时:close all → headed 重开(登录态丢失需重新处理)。

第 117 轮扩展:除原有 reason(captcha/sms/qr_login/login)外,以下三类场景
必须走对应专用 reason,不要退化到 `manual_verify`:

- **实名/人脸核身** —— `reason=real_name`;可视化场景必开 headed(摄像头/上传
  控件在页面)。
- **2FA / TOTP / 邮箱验证码** —— `reason=two_factor`;人工拿到动态码后直接在 TUI
  自由文本回复,Agent 走 `input_text` 填入。
- **第三方 OAuth / 授权** —— `reason=oauth`;Agent 先 `bring_to_front` 让授权页可见,
  人工点"授权/Agree"后 `inspect` 验证 URL 是否回到预期域名。

合法 reason 列表以 `inspect(info=blockers).available_reasons` 为准,避免硬编码。

## 9. 附录:第 117 轮扩展场景设计依据(并入自原 `03-扩展场景与覆盖增强方案.md`)

> 第 117 轮新增 `real_name / two_factor / oauth` 三类 reason 与对应 blockers 关键词
> (检测模式表见 §3.2,作业规范见 §7,变更摘要见 `01` §15)。本节收录当时的设计取舍,
> 原文档因与本目录 01/02 重复度过高已删除。

### 9.1 为何不拆成三个独立工具

考虑过 `request_human_captcha` / `request_human_real_name` / `request_human_oauth`
三个独立工具,否决:

- **Schema token 成本**:三套描述重复严重,且 schema 重复 LLM 吃 cache 命中率反而下降;
- **代码路径同构**:三类请求本质共享 `HumanAssistHub::request()`,只是文案/标签不同;
- **生态对齐**:atomcode / claudecode 等外部 Agent 的同类能力也是「单工具 + 限定
  enum」,不是独立工具(参考 `docs/Agent源码调研/专题/专题-第八轮-Tool权限策略引擎
  与沙箱设计深度对比.md` §8 HITL)。

最终形态:**1 个 `control_action` + 9 个合法 reason**,LLM 用 `reason=<kind>` 区分
语义,TUI 侧按 reason 切换标签与默认文案,后台调度仍走 `HumanAssistHub` 单例。

### 9.2 为何 `real_name` / `two_factor` / `oauth` 不合并到 `manual_verify`

`manual_verify` 是**兜底**,代表「不知道是什么场景,只能交给人工」;三个新场景是
**已知分类**,人工动作与交互面完全不同:

- `real_name` —— 刷脸/上传身份证,交互区是摄像头/文件控件,仅 headed 可视;
- `two_factor` —— 人工从手机 Authenticator/邮箱取动态码,TUI 自由文本直接回复,
  Agent 走 `input_text` 填入(与图形验证码「人工拖动」是两条路径);
- `oauth` —— 人工在第三方站点点击授权,Agent 需 `bring_to_front` 后人工才可见,
  授权后跳回原站(与账密登录后重导航工作流不同)。

明确语义的收益:提示词可写精准作业规范;TUI 标签帮人工一眼识别该做什么;
未来可按 kind 做业务遥测(如「本月 real_name 拦截 12 次」→ 评估官方 API 绕行)。

### 9.3 为何 `inspect(info=blockers).available_reasons` 公开合法 reason

不公开则 LLM 只能死记 description(reason 增多即退化,且每次改动击穿 prompt cache)。
公开 9 个字符串的代价是几 token,收益是 LLM 拿到 blockers 后可直接复用构造
`request_human.reason`,schema 层面保证无「猜/漏/乱」。

### 9.4 reason 排序与兼容

常量 `HUMAN_ASSIST_ALLOWED_REASONS` 顺序 = **推荐使用顺序**(高频 → 兜底),
LLM 不确定时按序取用;单测 `human_assist_allowed_reasons_covers_extensions`
锁死索引 4/5/6 必为 `real_name/two_factor/oauth`。向后兼容:原 6 个 reason 的
文案/标签/错误码不变,`inspect` 原 4 类关键词不变,schema 仅 enum 扩展,
未覆盖场景仍走 `custom` 兜底。
