## 1. 产物锚定工作目录

### 1.1 事故

`laew` 经 `/opt/homebrew/bin/laew` 软链启动，`current_exe().parent()` = `/opt/homebrew/bin`，
于是 `plans/`、`DebugReport/`、`AuditTrail/`、`BashSpill/`、`logs/laew-tui.log`、
`CrashReport/` 六类产物**全部逃逸**到家brew 的包管理目录 —— 用户在自己启动 laew 的
工作目录里怎么都找不到 Plan 文件。更糟的是 `Read` 工具带「根目录回退」：工作目录
找不到 `plans/x.md` 时会去读 `/opt/homebrew/bin/plans/x.md`，于是 Agent「读到了」而
用户「找不到」，两边对不上账。

### 1.2 方案

新增 crate 根单一真源 `src/artifact_root.rs`：

| API | 语义 |
|---|---|
| `artifact_root()` | 产物根，进程级 `OnceLock` 单点捕获。优先级 `LAEW_ARTIFACT_DIR` > 启动时 `current_dir()` > `current_exe().parent()` |
| `artifact_dir(rel)` | 产物子目录拼接，内部走 `safe_join` |
| `safe_join(root, rel)` | **纯函数，永不返回 root 之外**：`..`、前导 `/`、Windows 盘符分量全部丢弃 |

迁移清单：

| 产物 | 原基准 | 现基准 |
|---|---|---|
| `plans/` | `paths.root_dir` | `artifact_dir("plans")` |
| `DebugReport/` | `paths.root_dir` | `artifact_dir("DebugReport")` |
| `AuditTrail/` | 独立 `current_exe()` 重推导 | `artifact_root()` |
| `BashSpill/` | 独立 `current_exe()` 重推导 | `artifact_root()` |
| `logs/laew-tui.log` | `paths.root_dir` | `artifact_dir("logs")` |
| `CrashReport/` | 独立 `current_exe()` 重推导 | `artifact_root()` |
| `EvalSpill/`（eval_js 大结果） | `std::env::temp_dir()` | `artifact_dir("EvalSpill")` |
| `WebShots/`（截图 / OCR / HITL 附图 / data: 下载） | `std::env::temp_dir()` | `artifact_dir("WebShots")` |

**SQLite `.db` 位置不变**（仍优先 `root_dir`）：接入点配置与会话记忆是跨工作目录的
全局状态，迁移会丢存量。仅当 `root_dir` 不可写时回退 `<产物根>/.laew/`。

**`root_dir` 的职责收窄**：只剩「定位程序自带资源」（如 `__hitl-dialog` 子进程可执行
文件），不再是任何产物的落点。启动横幅 `根目录:` 改名 `程序目录:`，新增 `产物目录:` 行。

**顺带修正的两处误用**：
- `SkillRegistry::load(&paths.root_dir, &paths.work_dir)` 把 `root_dir` 当 home 传，
  用户级 skill 一直在 `/opt/homebrew/bin` 下找 —— 改用真实 `HOME`/`USERPROFILE`；
- `Read` 的根目录回退整段删除，解析口径收敛为「相对路径就是相对工作目录」。

**边界**：产物围栏**不**约束用户在提示词里显式给出的文件路径 —— 实测任务本身就要求读
`/Users/.../AI-Skill` 的绝对路径，禁绝对路径会把正常能力一并打死。

新环境变量：`LAEW_ARTIFACT_DIR`（显式覆盖产物根）。

## 2. 人工核验闭环

### 2.1 挑战子类识别（原来一律叫「验证码」）

第 151 轮之前 `detect_challenge()` 对任何形态一律写死 `"kind": "captcha"`，于是豆包的
**拖拽拼图**被贴上「图形/滑块验证码」标签：弹窗标题错、人工按验证码思路找输入框（根本
没有）、`hitl_answer_hint` 还提示「立即 input_text 填码」，把人引向不存在的动作。

新增 `ChallengeType`（`blocker_probe.rs`）：

| 子类 | 结构/文案判据 | `interaction`（告诉人工怎么操作） | reason |
|---|---|---|---|
| `drag_puzzle` | canvas + 拖拽类词 | 鼠标按住图片拖到指定位置 | `manual_verify` |
| `slider` | 窄长条滑杆元素 + 滑块类词 | 按住滑块一路拖到最右 | `manual_verify` |
| `image_select` | 九宫格 / CSS 背景图网格 ≥4 | 按题面点选符合条件的图片 | `manual_verify` |
| `text_captcha` | 弹层内有可见输入框 + 强验证词 | 读出图片里的字符并在输入框填入 | `captcha` |
| `embedded_captcha` | 验证码尺寸 iframe（主文档读不到内部） | 在页面内嵌的验证框中完成 | `captcha` |
| `unknown` | 过阈但形态不明 | 在浏览器窗口内完成页面上的验证 | `manual_verify` |

只有**真能填码**的形态才叫 `captcha`（会触发自动截图 + 「立即 input_text 填码」的
next_hint）；拖拽/滑块/点选一律 `manual_verify`（「人工核验」）。子类信息同时进
`blocker_alert.challenge_type` / `.interaction` / `.needs_browser_action` 与响应顶层。

### 2.2 探针识别面补强

- **通用模态候选**：原候选集只有语义类名选择器（`modal`/`dialog`/`captcha`…），
  现代前端的 BEM / 哈希类名（`.css-1x2y3z`）一条都命中不了，整层弹窗直接漏检。
  补一条「不看类名、只看几何与层叠」的兜底：凡 `fixed|absolute` + 面积 ≥6% 视口
  的容器都进候选池（上限 600 个），走同一套筛选。
- **滑杆信号**：滑块验证的把手是窄长条（宽 30~120px、高 20~90px）且带渐变/背景图，
  无文案也能认出来。
- **跨域 iframe 元信息**：iframe 内部读不到，但它的 `src`/`title`/`class`/`id`/`name`
  几乎必然带 `captcha`/`geetest`/`verify` 之类标识 —— 拼进弹层文本参与关键词判定，
  这是主文档侧唯一能拿到的强信号（补「拼图整体在 iframe 内、canvas_count=0」的盲区）。
- **挑战层选择器**：探针产出 `selector`，供 HITL 放行白名单与「滚动到验证弹窗」复用。
- **`eval_expression_mutates` 补齐**：`location =` / `window.location` / `self.location` /
  `top.location` / `parent.location` / `pushState` / `replaceState` / `requestSubmit` ——
  原表只认 `location.href`，这几形态与它副作用完全等价却全部漏网。

### 2.3 同指纹告警去重（治「狼来了」）

实测日志里同一个误报在 iter 7/9/11/12/14/15/17 **连续播报 7 次**，每次拖一份
1~2 万 token 的 `human_assist` 载荷，把 `next_action=request_human` 训练成了噪声。

`blocker_probe` 引入进程内指纹表 `page_id → (指纹, 次数)`，指纹 =
`(kind, matched, snippet 前 40 字)`（**不含按钮文案与时间戳** —— 弹窗每轮渲染都在变，
纳入指纹则去重形同虚设）。

- 首次命中：完整 `blocker_alert + human_assist + next_action`；
- 同指纹再次命中：**只回事实** `blocker_alert{repeat:true, repeat_count:n}`，
  不再重复长载荷；
- 硬闸 6002 **不走**本表 —— 拦截语义要持续生效，去重只针对播报；
- 清除点：`request_human` 发起时（人工介入是新事实）、`close`。

### 2.4 HITL 期间挂起 Agent 输入（新错误码 4003）

提问期间页面按 `unlock_page` 切到 partial/open 供人工操作，但**提问尚未结束**，
Agent 的下一个 `batch` / `sequence` 步骤里的输入类动作照常执行，其收尾的
「先解后锁」把页面**重新锁回 locked**（CDP `Input.setIgnoreInputEvents(true)`）——
人工正在拖的拼图被锁在半路。

这不是「Agent 不听话」，而是**两条并行的所有权没有仲裁**。新增
`src/agent/tools/mcp_web_use/hitl_guard.rs`：

- 覆盖面与 6002 硬闸**完全一致**（20 个输入类动作 + 可变更 `eval_js`），
  共用同一判定函数，避免口径漂移；
- 观察类（`screenshot`/`inspect`/只读 `eval_js`）与 `request_human` 本身**不拦**；
- `params.force=true` 逃生口；
- 拒收返回 **4003**，归 4xxx「人工介入」段（4001 超时 / 4002 取消 / **4003 进行中**）。

### 2.5 挑战弹层纳入 HITL 放行白名单

`CREDENTIAL_ZONE_PROBE_JS` 增第 ⑤ 类 `challenge-overlay`：与 blocker_probe 的弹层
选取同构（高 z-index + 固定/绝对定位 + 面积 ≥，上限放宽到 60% 视口），**不看类名**。

对应两条实测：豆包拖拽拼图弹层类名不含 captcha/verify，①②③④ 全部探测不到 →
回退整页 open（碰巧能拖）；而一旦页面恰好有个含 zone 关键词的容器命中 ④，就会走
partial 挖洞，盾罩把整块挑战弹层罩住 —— 人工看得见却拖不动。**挑战弹层内部的每一个
像素都是人工必操作区**，整层放行是唯一正确解。

### 2.6 提问前把挑战滚进视野

`act_request_human` 在 `bring_to_front` 之后、截图之前，若探针产出
`challenge_selector` 则先 `scrollIntoView({block:'center'})`。验证弹窗落在下半屏或
视口之外时，那张自动附图截到的是空白区域；页面又被 locked 档拦着滚轮，人工自己
也滚不过去。响应附 `data.challenge_scrolled` 对账。

## 3. HITL 弹窗不再外呼系统默认应用（新标签页根因）

macOS 的「查看原图」调 `NSWorkspace.openFile:`、Windows 调 `ShellExecuteW("open")`，
把验证码 PNG 交给**系统默认应用**。用户的 `.png` 默认处理器是浏览器时，每点一次就
新开一个标签/窗口；而验证码截图原写系统临时目录，被清理后浏览器只剩空白 ——
实测表现为「HITL 成功后冒出一堆空的、乱码的验证码标签页」，且弹窗反复弹出时点一次
冒一批。

流程中途唤起外部应用本就属于交叉操作，与第 141~143 轮「人工只读、Agent 独占」的
管控语义冲突。现改为：

- macOS：「🔍 放大」在**当前弹窗内**把图切到 1:1（`NSImageScalesProportionallyUpOrDown`），
  可来回切换；`⛶ 最大化` 看全图；
- Windows：`SS_BITMAP` 是静态位图控件无缩放能力，改为**把图片绝对路径复制到剪贴板**
  （按钮反馈「✓ 路径已复制」，由既有 1s tick 回滚）；
- 两者都**零外部进程、零标签页**。需要另存/用看图工具打开的用户走既有「📋 复制」
  拿路径自行打开 —— 那是**用户主动**行为。

## 4. 幽灵标签页回收

`adopt_spawned_pages()` 原先对「浏览器里有、注册表里没有」的 target **一律收编**，
而收编 ≠ 关闭 —— 页面自己开的 `about:blank`、风控脚本 `window.open('')` 的空窗、
下载导航残留全部滞留在前台，越积越多。

新增 `src/agent/browser_noise.rs`（纯函数 + 单测）：

- `is_noise_url`：`about:blank` / `about:newtab` / `chrome://newtab` /
  `chrome://new-tab-page` / `chrome://search-local-ntp` / `chrome://downloads` /
  `edge://newtab` / `brave://newtab` / `devtools://`；**不认任何真实站点**；
- `is_noise_page`：噪声 URL **且标题为空** —— 标题非空即豁免。

接线（`browser.rs`）：

1. 噪声页**不 adopt，直接 `page.close()`**，记 `tracing::info!`；
2. 关闭前先 `sleep(250ms)` 复查一次 URL —— `target=_blank` 刚打开的窗口 URL 短暂
   就是 `about:blank`，不给导航时间会把真页面误杀；
3. **connect 模式（`open(reuse_existing=true)`）完全不收编**：此时
   `browser.pages()` 返回的是**用户浏览器里的全部标签页**，照旧逻辑会把用户的私人
   标签页一次性收编并注入管控脚本，`spawned_page_id` 还会指向用户的私人页面。

顺带修正 `action_may_spawn_page`：`eval_js` 原被无条件圈进浏览器级巡检，与其上方
注释「eval_js(纯读)不会开新页」自相矛盾 —— 既白付一次 `Target.getTargets` 往返，
又会在只读 eval 附近恰好有页面自己开新标签时，塞进一个与本次动作无关的
`spawned_page_id`（实测日志 iter=5 的思考里就有这一句困惑）。改为**按表达式判定**：
只读 eval 不巡检，可变更 eval 才巡检。

## 5. 页面可视性（Agent 看得到、人工看不到）

### 5.1 事故

Agent 用 `eval_js` 读 DOM 拿到豆包第 N 轮的完整回答，**用户/人工在浏览器窗口里只看得到
第一屏**。两道原因叠加：

1. 视口在 `open` 时按当时内容高度定过一次，多轮对话把消息栈越堆越高，之后再没适配；
2. locked 档的 L1 是 CDP `Input.setIgnoreInputEvents(true)`，**浏览器级一刀切，连滚轮
   一起拦**（第 141 轮实测：真实输入与 CDP 合成输入一视同仁）——「人工自己滚一下」
   这条路在默认档位下根本不存在。

### 5.2 方案

**明确不做**：不放宽 locked 档的输入拦截。CDP 是一刀切的，为了滚轮破掉防交叉操作的
安全语义不划算。

改用「让页面自己停在最新」，新增 `src/agent/browser_follow.rs`：

- `AUTO_FOLLOW_JS`：页面内跟随器，每 1.2s 检查一次，**仅当用户本来就在底部**
  （`scrollHeight - scrollTop - clientHeight ≤ 96`）才吸底 —— 人工往上翻历史时绝不会被
  强行拽回，这是敢默认开启的唯一理由。滚动容器取「视口内面积最大且确实可滚动」的
  元素，退化到 `document.scrollingElement`（AI 聊天站几乎都是内层 div 滚动，
  直接 `window.scrollTo` 什么都不会发生）。
- 注入通道与 guard 同款：`addScriptToEvaluateOnNewDocument` + 导航后按实例期望态
  re-assert（`BrowserInner.auto_follow`，默认开；connect 模式恒 false）。
- 新增控制动作 `control(auto_follow, params={enabled?|scroll_to_bottom?})`；
- 新增观察维度 `inspect(info=visibility)`，回答「人工此刻能看到多少」：
  `scroller` / `scrollable` / `at_bottom` / `below_fold_px` / `hidden_ratio`，
  并给出**Agent 可立即执行**的处置（`scroll_to` / `auto_follow`）—— 而不是一句
  「建议用户滚动」，locked 档下用户滚不了，那句话等于把问题原样退回给用户。

### 5.3 与 HITL 的合流

三条路径共同保证人工看得到：`auto_follow` 让页面停在最新 + `visibility` 让 Agent
知道自己造成了落差 + HITL 提问期间页面已解锁，人工可自由滚动。
