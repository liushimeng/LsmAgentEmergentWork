## 1. 背景与目标

### 1.1 动机

Main-Work 是 laew 多 Agent 架构的**流程编排层**:接收 medium/hard 任务,拆出
WorkFlow 列表委派给 SubAgent-Work 执行。其拆解质量直接决定下游成败 —— 拆得太粗,
SubAgent 单轮 16 次迭代跑不满任务;拆得太细,跨单元丢失真实上下文(尤其是自绘 UI
连续操作的真实焦点)。

Main-Work 当前形态有两处不足:

1. **工具面过窄**:只持 `Bash / Read / Glob / Grep / TodoWrite / SubAgent`,
   缺 **`MCP_Web_Use`** —— 但编排层经常需要先确认目标网站结构再决定怎么拆,
   实测复盘(第 119 轮 / 109 轮 / 100 轮)多次出现「Main-Work 凭想象拆了一堆,
   SubAgent-Work 第一轮 MCP_Web_Use open 才发现 URL 错 / 登录态失效 / 页面
   早已改版,直接退化成无效流程」的场景;
2. **「裸循环」ReAct 缺位**:对标 SubAgent-Work 在第 120 轮完成 ReAct 化后,
   Main-Work 的提示词里**一个 ReAct 字都没有**,循环体只是机械的
   `complete → tool_calls → execute → tool_result → loop`,Thought 不显式、
   Observation 不归纳、原地打转不自知。

Yolo(入口层)已在第 119 轮完成 ReAct 化、SubAgent-Work(执行层)已在第 120 轮完成
ReAct 化 + 工具连续工作模式,**Main-Work(流程编排层)是唯一裸循环的层级** —— 本轮
把这块拼图补齐,使三档链路(简单档 SubAgent、中档 Main-Work → SubAgent、高档 Plan →
Main-Work → SubAgent)的每一级都具备 ReAct + 连续工作模式能力。

### 1.2 设计目标

| 目标 | 说明 |
|------|------|
| **工具面扩展** | Main-Work 持 Bash / Read / Glob / Grep / TodoWrite / SubAgent / **MCP_Web_Use(新增)** |
| **ReAct 显式化** | Main-Work 提示词补 Thought→Action→Observation 节奏;运行时用 hint 强制「先推理再动手」 |
| **信息收集自主决策** | 编排前可按需用 MCP_Web_Use 探查网页结构 / 登录态 / 入口 URL,基于真实页面状态拆解 |
| **复用 SubAgent-Work 的循环守卫** | `LoopGuard` 双阈值止损 + 角色化 runtime hint + 通用收口预告 复用第 120 轮基础设施 |
| **编排精度提升** | acceptance 可锚定 MCP_Web_Use 真实探查的页面状态(URL 准确 / 控件真实存在),而非凭想象 |
| **零回归 + 可回退** | `LAEW_REACT_GUARD=off` / `LAEW_PARALLEL_TOOLS=off` 即可回退到第 120 轮之前行为 |

### 1.3 本轮不做

| 项 | 原因 |
|----|------|
| Main-Work 也加 `MCP_Window_Use` | 桌面窗口操控归 SubAgent-Work 专用(平台门控 + 单一焦点守卫假设);编排层仅做流程级判断 |
| Main-Work 也加 `Write / Edit` | 流程层只编排不落源代码;`Write` 仍是 SubAgent-Work 专用 |
| Main-Work 加结构化 emit 通道 | QC 已有 emit 通道,Main-Work 终答是 JSON 已是约定;无需强制 emit |
| Bash 改为可写 | Main-Work Bash 仅限只读侦察(对齐 Yolo Bash 限制);有写需求委派 SubAgent |
| Goal round-driver 状态机 | 见 SubAgent 第 120 轮`方案 §1.4`,属独立立项 |

### 2.1 核心矛盾

**Main-Work 的拆解目前是「盲拆」**:LLM 拿到 Yolo 摘要 + 用户原始 prompt + 可选
`retry_hint` 后,**第一轮就直接出 JSON**,完全没机会用工具验证任务前提(目标网站 URL
是否可访问 / 入口路由是否需要登录 / 项目根目录是否真有目标文件 / 桌面应用是否安装)。
**真实失败模式**(汇总自 2026-09-15 ~ 2026-09-22 实测复盘):

| 失败形态 | 根因 | 频次 |
|---------|------|------|
| 拆出 6 个 SubAgent 单元,首个 `open` 失败(`ERR_CONNECTION_TIMED_OUT` / `404`) | Main-Work 凭想象拆,未探测目标 | 多次 |
| 拆了「发送 10 条微信消息」,首单元 `chat_send` 找不到焦点 | 桌面应用是否启动 / 窗口列表未知 | 多次 |
| 拆了「删除某个项目的某文件」,SubAgent 找不到 `projects/<name>/` 路径 | 目录结构未探查 | 偶发 |
| 拆解里 acceptance 写了「页面出现某文本」,但 SubAgent `wait_for_text` 永远不等到(页面没这文本) | Main-Work 凭想象写验收 | 多次 |

把 `MCP_Web_Use` 与 `Bash` 暴露给 Main-Work 是补齐「编排前信息收集」的关键路径。

## 3. 方案设计

### 3.1 R1 — Main-Work 工具集扩展:`MCP_Web_Use`

`tools/mod.rs::main_work_registry` 在 `Bash / Read / Glob / Grep / TodoWrite / SubAgent`
基础上追加 `MCP_Web_Use`:

```rust
pub fn main_work_registry() -> ToolRegistry {
    register_subagent(
        ToolRegistry::new()
            .register(Arc::new(bash::BashTool))
            .register(Arc::new(read::ReadTool))
            .register(Arc::new(glob::GlobTool))
            .register(Arc::new(grep::GrepTool))
            .register(Arc::new(todo::TodoWriteTool::shared()))
            .register(Arc::new(mcp_web_use::McpWebUseTool)),  // ← 新增
    )
}
```

**为什么是 `MCP_Web_Use` 而非 `MCP_Window_Use`**:

| 维度 | MCP_Web_Use | MCP_Window_Use |
|------|-------------|-----------------|
| 平台 | 全平台(CDP 三平台一致) | 仅 macOS / Windows |
| 用途 | 编排前探查网页 URL / 入口 / 登录态 | 桌面窗口操控执行 |
| 单一焦点 | 否(只读探查) | 是(单一前台焦点) |
| Main-Work 用法 | inspect / screenshot 观察类 action | 不适用(SubAgent 独享) |
| 对 SubAgent 影响 | 编排精度提升后,SubAgent 任务质量提升 | 无变化 |

`MCP_Web_Use` 全平台可用(第 89 轮落地),无需平台门控,Main-WorkRunner 跨平台
(Windows / macOS / Linux)行为一致。

### 3.2 R2 — Main-Work 系统提示词 ReAct 化

#### 3.2.1 `MAIN_WORK_BASE_PROMPT` 新增「编排循环(ReAct 模式)」

插在「## 核心职责」之后,「## 输入格式」之前:

```text
## 编排循环(ReAct 模式)

你是靠「反馈 → 执行 → 再反馈 → 再执行」逐轮推进的编排 Agent,不是脚本播放器。
每一轮严格按三段走:

- **Thought(推理)**:先用 1~3 句写出 —— 我已经确认了什么?还缺什么?
  下一步做哪一件事最省(能一次拿到最多新信息)?
- **Action(行动)**:发起工具调用。无依赖的只读调用**一次性并发发出**
  (Read / Glob / Grep 可同批多条);有依赖或有副作用的才分轮。
- **Observation(观察)**:读完工具结果,显式判断「这一步是否让任务向前推进了」。
  推进了 → 继续下一步;没推进 → **立即换路径**,不要用相同参数再试一次。

硬性约束:
- **任务前提验证**:拿到用户 prompt 第一轮不要直接出 JSON,先用 Bash / Read / Glob /
  Grep / MCP_Web_Use 验证任务前提(目标 URL 是否可访问 / 目标文件是否存在 /
  目标应用是否安装 / 目标网页入口与登录态)。前提不成立 → 输出空 workflows,
  让上层叙述失败 + 排查建议,不要硬拆。
- 禁止无 Thought 的盲调;禁止不读 Observation 就发下一批调用。
- 同一工具 + 同一参数 + 同一结果**连续出现 2 次**,系统判定为无进展并警告;
  出现 3 次进入止损宽限轮;第 4 次直接终止本单元。需要等待外部状态变化时,用带
  wait / timeout 的调用(如 MCP_Web_Use sequence 的 wait 步骤),不要靠反复轮询。
- 迭代预算过半时系统会提示进度;收到【收口提示】后**立即停止新动作**,基于已有
  Observation 输出最终 JSON。
- 已知充分、accept 可执行时即刻收口,不为「看起来更完整」而继续探查。

**先 TaskFocus、再拆解**(2026-09-23 真实复盘最佳实践):

- 第一轮:**TaskFocus** 阶段,目标是让模型知道「我已经在拆哪一步了」。先用
  TodoWrite 把整份编排计划列出(顶层 todo list),每完成一步 update 标记。
- 第二轮~倒数第二轮:**Verify + Decompose** 阶段,基于 todo 顺序逐项验证
  (Bash / Read / MCP_Web_Use 探查) + 拆解。
- 最后一轮:**Emit** 阶段,基于 todo 进度输出最终 JSON。
```

#### 3.2.2 `main_work_tools_hint()` 重写

```text
工具调用规范:
- 使用 Bash 执行只读类命令(ls / cat / grep / curl / git log 等,禁写盘)。
- 使用 Read 读取文件;使用 Glob / Grep 检索项目结构。
- 使用 MCP_Web_Use(action=open/list/inspect/screenshot,观察类)做网页信息收集。
- 写文件优先用 TodoWrite 列编排清单(顶层 3~6 个 todo),每完成一项 update 标记。
- 不要直接修改源代码(委派给 SubAgent-Work);不要使用 Write 写源代码。

可用工具:
- Bash(command, timeout_ms?, description?): 只读 / 检查类命令。
- Read(file_path, offset?, limit?): 读取文本文件,带行号。
- Glob / Grep: 项目结构与符号检索。
- MCP_Web_Use(action, ...): 网页信息收集(open 拿页面 / inspect 探查 DOM /
  screenshot 视觉验证),只读观察类 action,不要在编排阶段执行写操作。
- TodoWrite(action, ...): 编排清单顶层规划,Step ≥3 时先 create 全量清单。
- SubAgent(action, agent_type?, task?, tasks?, ...): 把相互独立的 WorkFlow 并行
  委派给子 Agent(action=list 先看名册与额度;详见系统提示词「自感知」段)。

## 连续工作模式(一轮做完整批动作)

优先用「一次调用编排多步」的复合能力,把 N 轮压成 1 轮:
- MCP_Web_Use:action=sequence(≤24 步,批内用 $page_id 占位) / batch /
  explore(一次取多个 inspect 维度,信息收集阶段首选)。
- SubAgent:action=batch(≤8 个独立子任务并行,适合相互独立的 WorkFlow 探查)。
- TodoWrite:编排清单 ≥3 步时先 create 全量,每完成一步 update。

单工具批次规则:
- 同一轮里**无依赖**的只读调用(Read / Glob / Grep / MCP_Web_Use 的只读 action)
  一次全部发出,系统会并发执行(上限 4 条),比逐轮串行省 3~4 倍迭代预算。
- 有副作用的调用(Bash 写盘 / Write)按依赖顺序分轮,不要指望它们与只读调用
  混在一批里并发 —— 它们会被保序串行执行。

## 任务前提验证清单(编排前必查)

- [ ] 目标 URL 是否可访问(`curl -s -o /dev/null -w "%{http_code}" --connect-timeout 5`
      或 `MCP_Web_Use(action=open)` 验证连通性)
- [ ] 目标文件 / 目录是否存在(`Glob` / `ls`)
- [ ] 目标依赖是否已安装(`cat package.json` / `cat Cargo.toml`)
- [ ] 目标应用是否已安装(桌面 GUI 任务,`MCP_Window_Use(action=list)` —
      Main-Work 不持此工具,跳过此步)
```

### 3.3 R3 — `with_max_iterations` 与 `with_explore_budget` 默认值

`MainWorkRunner::new` 当前走 `Agent::new(llm, profile)` 默认 `max_iterations=8`
(对齐 Yolo 第 119 轮改造前的旧值)。本轮同步 SubAgent-Work:

```rust
let agent = Agent::new(llm, AgentProfile::main_work_profile())
    .with_max_iterations(8)         // 编排层:保持 8(8 个 wf 上限足够,
                                   //   编排本身不耗太多迭代)
    .with_explore_budget(2);        // 探索预算 2(第 1~2 轮做 TaskFocus + 前提验证)
```

**为什么 `max_iterations=8`**:编排层的「迭代」是「思考轮」,不是 SubAgent 的「工具
调用轮」。编排本身只决定「拆什么」,真正执行都在 SubAgent 里。8 轮 LLM 思考足够覆盖
TaskFocus(1 轮) + 前提验证(2~3 轮) + 拆解 + emit(1 轮)。

**为什么 `explore_budget=2`**:第 1 轮 TaskFocus + 第 2 轮首批前提验证 = 探索期。
第 3 轮起进入「执行期」(verify + decompose + emit),由 `HintRole::Execute` 角色化
文案告知模型「禁止再开新的只读探查」。

**为什么不像 Yolo 那样设 `explore_budget=0`**:Yolo 关掉是因为它的 explore 提示
文案写死浏览器/桌面语义,而 Yolo 信息收集确实不需要这种文案(Main-Work 也属于
「执行层」,Yolo 属「信息收集层」)。Main-Work 工具面无 `MCP_Window_Use`,
角色化 hint 会按 `trace.tool_call_log` 派生为 `Execute`,文案与 SubAgent-Work
一致(允许 `Read/Glob/Grep/Bash 构建与测试`,禁止再开新只读探查),所以保持默认
`explore_budget=2` 即可。

### 3.4 R4 — runtime hint 角色化(零成本复用)

`AgentProfile::hint_role(trace)` 派生规则不变:

| 步骤 | 派生 |
|------|------|
| 1. emit_tool.is_some() | Main-Work **无** → 跳过 |
| 2. tools.names().is_empty() | Main-Work **非空** → 跳过 |
| 3. trace.tool_call_log 含 MCP_Web_Use / MCP_Window_Use | Main-Work 用过 MCP_Web_Use → `Ui` 角色 |
| 4. 其余 | `Execute` 角色 |

**关键差异**:Main-Work 真的动过 MCP_Web_Use(action=screenshot / sequence 等会调
CDP),`hint_role` 派生为 `Ui` —— 与 SubAgent-Work 拿到「click/wait」文案语义一致。
仅用 Bash/Read/Glob/Grep 的 Main-Work 派生为 `Execute` —— 与 SubAgent-Work 代码
类单元文案一致。

**Main-Work 也启用 `runtime hints` 拼装**(沿用 `build_runtime_hints_with`),三类 hint
自动送达:
- **ReAct 进度**(过半预算):与 SubAgent-Work 一致文案;
- **Thought nudge**(连续 2 轮仅 tool_use 无文本):与 SubAgent-Work 一致文案;
- **通用收口预告**(`iter + 2 == max_iterations`):Main-Work 无 emit,走「无 emit
  角色」的「基于已有 Observation 输出最终 JSON」文案。

### 3.5 R5 — LoopGuard 接入

Main-WorkRunner 启用 `LoopGuard`(默认),与 SubAgent-Work 共用同一份进展键 + 双阈值:

```rust
let mut loop_guard = LoopGuard::new();
for each tool_result in completion.tool_calls {
    let tool_record = ToolCallRecord { tool: name, params: stable_json(args), result_summary: digest(output) };
    let verdict = loop_guard.observe(&tool_record);
    match verdict {
        LoopVerdict::Progress => { /* 继续 */ }
        LoopVerdict::Nudge => { /* 把 nudge 注入 system 末尾 */ }
        LoopVerdict::Grace => { /* 宽限轮:再走一轮 */ }
        LoopVerdict::Abort => { /* 提前终止,失败回流 */ }
    }
}
```

**总开关**:`LAEW_REACT_GUARD=off|0|false|no` → Main-WorkRunner 不启用 LoopGuard
(对齐 SubAgent-Work),回退到第 120 轮之前「纯计数器」行为。

### 3.6 R6 — `parallel_safe` 默认行为

Main-WorkRunner 走 `agent_loop.rs::run_session_body`,本轮未改分批并发执行路径
(已在第 120 轮完成),但 Main-Work 启用 `MCP_Web_Use` 后:

| 工具 | parallel_safe | Main-Work 用法 |
|------|---------------|---------------|
| `Read` | true | 同 SubAgent,同批并发 |

# §B 章 · BashTool 只读模式(Round 124 新增,2026-09-23)

> **本轮动机**:第 122 轮(Main-Work ReAct 化 + MCP_Web_Use)让 Main-Work 持 Bash 工具做
> 「编排前信息收集」。但 `pub struct BashTool;` 是空结构体,**Main-Work 提示词写"只读 /
> 禁写盘",代码层零强制** —— LLM 误用 `echo x > f` / `tee` / `sed -i` / `mv` /
> `rm` / `chmod` 等写命令,可能把流程编排层退化成可写执行层,污染"Main-Work 不落源代码"
> 的架构约束。本轮补齐**代码层只读 + 提示词硬性条款 + env 旁路回退 + 测试矩阵**四位一体。

## §B.1 范围与目标

| 项 | 范围 |
|---|------|
| **改造对象** | `BashTool`(原 `pub struct BashTool;`) |
| **新增结构** | `BashMode { ReadWrite, ReadOnly }` 枚举 |
| **新增拦截** | `permissions::check_bash_readonly`(正向白名单 + 反向拦截 + env 旁路) |
| **替换装配** | `main_work_registry()` 用 `BashTool::readonly()`;其他角色保持 `BashTool::new()` |
| **零回归** | SubAgent-Work / 顶层 Bash / MCP_Window_Use 降级路径仍 ReadWrite |
| **回退开关** | `LAEW_BASH_READONLY=off` 完全跳过拦截 |

## §B.2 BashMode 设计

**文件**:`src/agent/tools/bash.rs:220-269`

```rust
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum BashMode { ReadWrite, ReadOnly }

pub struct BashTool { mode: BashMode }

impl BashTool {
    pub const fn new() -> Self { Self { mode: BashMode::ReadWrite } }
    pub const fn readonly() -> Self { Self { mode: BashMode::ReadOnly } }
    pub const fn mode(&self) -> BashMode { self.mode }
}
impl Default for BashTool { fn default() -> Self { Self::new() } }
```

## §B.3 `permissions::check_bash_readonly` 算法

**文件**:`src/agent/permissions/readonly.rs`(新建,与 `dangerous.rs` / `sensitive.rs` 平级)

**拦截流水线**(7 个独立检查器串联,任一命中即返回 `PermissionDenied`):

1. **环境旁路**:`LAEW_BASH_READONLY=off|0|false|no` → 直接 `Ok(())`
2. **pipe-to-shell 拦截**:`curl | bash` / `wget | sh` / `... | python` 等
3. **重定向拦截**:`>` / `>>` / `<>` / `<<<`(quoted 已被 `strip_quoted_strings` 抹除)
4. **写命令名拦截**:`mv` / `rm` / `tee` / `dd` / `chmod` / `chown` / `touch` / `mkdir` / `ln` /
   `install` / `patch` / `ed` / `truncate` / `fdisk` / `mkfs` 等
5. **写盘标志拦截**:`sed -i` / `awk -i` / `perl -i` / `curl -o` / `kill -9` / `tar -x*` /
   `git checkout` / `git reset` 等
6. **包管理器安装拦截**:`apt install` / `pip install` / `npm install` / `cargo install` /
   `brew install` / `systemctl start` 等

7. **直接写磁盘设备**:`> /dev/sda` / `> /dev/nvme*` 等(冗余防护,与 `dangerous.rs` 重叠,
   单独复刻以便拦截文案差异化)

**正向放行**(`check_bash_readonly` 返回 `Ok(())` 的命令):`ls` / `cat` / `grep` / `git log` /
`git diff` / `git status` / `curl -sI` / `find`(无 `-exec` / `-delete`)/ `head` / `tail` /
`wc` / `md5sum` / `stat` / `df` / `du` / `ps` / `tar -tf` / `pip list` 等。**正向白名单
是"软保障"** —— 主拦截靠反向 blacklist),完整 cover 用。

**辅助函数复用**:从 `dangerous.rs` 暴露 `pub(super)`:`strip_shell_comments` /
`strip_quoted_strings` / `split_shell_segments` / `unwrap_wrappers` —— readonly 模式检测
流水线与危险命令拦截共用同一套字符串处理(quoted 抹除 + 连接符切分 + wrapper 剥除)。
