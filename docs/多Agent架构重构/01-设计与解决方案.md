# 多 Agent 架构重构 — 设计与解决方案

> 关联需求:Agent 架构重新梳理 / 拆分 LsmAgentEmergentWork-Work 对象 / 任务三档难度分级 / Quality-Check / SessionContext / Agent-Context + Agent-Memory。
> 关联模块:`src/agent/`(完全重构)、`src/session.rs`(扩展)、`src/tui/`、`src/main.rs`、`src/config/`、`src/agent/context.rs`(新增)、`src/agent/memory.rs`(新增)、`src/agent/quality.rs`(新增)、`src/agent/orchestrator.rs`(新增)、`src/agent/plan.rs`(新增)、`src/agent/session_context.rs`(新增)。

## 1. 背景与现状

### 1.1 现有问题

旧双 Agent 架构(Yolo + Work)在以下场景遇到瓶颈:

1. **Work Agent 身兼多职**:既要做简单问答、又要拆解复杂工程,单 Agent 难以胜任多档难度任务。
2. **缺乏质量门控**:执行层完成单元任务后,没有独立的质量校验;错误容易层层放大。
3. **没有独立 Plan 单元**:复杂任务应该先有独立方案/计划/决策文档,而不是 Yolo 输出结构化文本就立即执行。
4. **上下文管理单一**:只有主 Session 一份上下文,所有 Agent 共用,大型任务上下文容易膨胀。
5. **记忆缺失**:任务执行过程没有结果沉淀,失败原因、经验教训不能复用。
6. **多轮关联性弱**:用户在同一 Session 内连续追问时,缺少上下文衔接与历史检索。
7. **失败回流机制缺失**:任务失败时,缺少逐层回退到入口层让 Yolo 重新评估的能力。

### 1.2 目标

| 目标 | 说明 |
|------|------|
| 多 Agent 拆分 | Yolo / Plan / Main-Work / SubAgent-Work / Quality-Check / SessionContext 六大角色独立 |
| 三档难度分级 | 简单(simple) / 中等(medium) / 高等(hard),三档对应不同 Agent 组合 |
| 质量门控 | 每个执行单元完成后必须经 Quality-Check 通过才能继续 |
| 失败回流 | Quality-Check 不过逐层回退到 Yolo 重新评估 |
| 上下文分层 | 每个 Agent 拥有独立的 `Agent-Context`(实时对话)+ `Agent-Memory`(经验沉淀) |
| Session 总览 | `SessionContext` 串联多次任务输入,提供连续性 |
| 计划文档化 | 高等难度先由 Plan Agent 生成 Markdown 方案后再委派 Main-Work |

## 2. 新架构总体设计

### 2.1 Agent 角色矩阵

| Agent 名 | 类型 | 角色定位 | 工具集 | 触发条件 |
|---------|------|---------|--------|---------|
| `LsmAgentEmergentWork-Yolo` | 入口层 | 任务识别 / 目的-目标-意图 三步分析 / 难度分级 / 失败回流与用户建议 | Read | 每次用户输入首站 |
| `LsmAgentEmergentWork-Plan` | 规划层 | 制定 Markdown 方案与工作计划,产出结构化 Plan 文档 | Read / Write(仅写计划文档) | hard 难度任务 |
| `LsmAgentEmergentWork-Main-Work` | 流程层 | WorkFlow 编排,拆解出多个 SubFlow,决定分支与循环 | Bash / Read | medium / hard 任务 |
| `LsmAgentEmergentWork-SubAgent-Work` | 执行层 | 单流程处理单元,多轮对话+循环工具调用完成单一子任务 | Bash / Read / Write | Main-Work 调度 / 简单任务直接调度 |
| `LsmAgentEmergentWork-Quality-Check` | 质检层 | 校验 SubAgent / Main-Work / Plan 单元输出是否通过 | Read(可选) | 每个执行单元完成后 |
| `LsmAgentEmergentWork-SessionContext` | 会话层 | 串联多次任务输入,提供 Session 级总览 | 工具可选(默认无) | 多轮对话关联 |

### 2.2 任务三档难度与 Agent 路由

| 档位 | 名称 | 触发 Agent 链路 | 特征 |
|------|------|----------------|------|
| **简单** | simple | `Yolo → SubAgent-Work → Quality-Check → SessionContext` | 单步操作,1 个 SubAgent 单元即可完成 |
| **中等** | medium | `Yolo → Main-Work → (SubAgent-Work → Quality-Check)+ → SessionContext` | 多步流程,可分支可循环,每个流程处理单元委派 SubAgent-Work |
| **高等** | hard | `Yolo → Plan → Main-Work → (SubAgent-Work → Quality-Check)+ → SessionContext` | 先出 Markdown 方案 → 拆出多个 WorkFlow → 委派 Main-Work → Main-Work 再委派 SubAgent-Work |

## 3. Yolo 重设计

### 3.1 输入与输出

**输入**:用户提示词 + SessionMemory(历史任务摘要)+ Agent-Memory(Yolo 自己的经验)。

**输出**(JSON 代码块):

```json
{
  "task_level": "simple | medium | hard",
  "purpose": "用户目的(为什么问)",
  "goal_summary": "核心目标",
  "intent": "code_change | info_query | chat | file_operation | config | debug | plan_needed",
  "agent_role": "subagent | main | plan",
  "decomposition_plan": ["步骤 1", "步骤 2"],
  "direct_answer": null,
  "user_suggestion_if_fail": ""
}
```

| 新增字段 | 说明 |
|---------|------|
| `agent_role` | 委派给谁:simple→subagent;medium→main;hard→plan |
| `user_suggestion_if_fail` | 给用户的备选建议(失败时使用,默认空) |

### 3.2 三档分级标准

| 档位 | 判定 | agent_role |
|------|------|-----------|
| **simple** | 1 个工具调用即可完成,无分支 | subagent |
| **medium** | 2-10 个工具调用,有清晰步骤与少量分支 | main |
| **hard** | 多模块综合改动,需要先有书面方案再实施 | plan |

**移除 trivial 档**:原 trivial 直接由 Yolo 用 `direct_answer` 回答,但这与"Yolo 只做分类不做执行"的定位冲突。新架构 Yolo 也保留直接回答能力,但仍输出 JSON(`task_level: simple` + `direct_answer` 内容),由 Orchestrator 判定是否跳过执行层。

### 3.3 失败回流与用户建议

Yolo 收到失败回流时,行为:
1. 读取 `failure_reason`(来自 Quality-Check 或下游 Agent 的失败摘要)。
2. 结合 SessionMemory,判断重试可行性:
   - **可重试**:重新生成 classification,以 `decomposition_plan` 修订版再次调度。
   - **不可重试**:通过 SessionContext 给用户输出"建议修改任务目标 / 提供更多信息 / 改用其他工具"的 `user_suggestion`。
3. 把决策结果(重试 / 给建议)写回 SessionMemory。

## 4. Plan Agent 设计(hard 档专用)

### 4.1 定位

Plan 是**规划层 Agent**,为 hard 任务产出一份**结构化 Markdown 方案**,落盘到 `plans/{session_id}-{seq}.md`。

### 4.2 工具集

| 工具 | 用途 |
|------|------|
| Read | 读取现有代码 / 文档 / 配置 |
| Write | 仅允许写入 `plans/` 目录 |

> Plan 不允许直接执行 Bash / 修改源代码,只产出方案文档。

### 4.3 输出格式(Markdown)

```markdown
# 任务方案:{goal_summary}

> 由 LsmAgentEmergentWork-Plan 于 {ts} 生成
> Session: {session_id}
> 来源: Yolo 分类结果

## 一、目标
{详细目标}

## 二、WorkFlow 拆解
### WorkFlow 1:{名称}
- 步骤:
  - [ ] 步骤 a
  - [ ] 步骤 b
- 委派 Agent: SubAgent-Work
- 验收标准: ...

### WorkFlow 2:{名称}
- 步骤:
- 委派 Agent: SubAgent-Work
- 验收标准: ...

## 三、关键决策
- 决策 1: ...
- 决策 2: ...

## 四、风险与缓解
- 风险: ...
- 缓解: ...

## 五、验收总览
- [ ] 所有 WorkFlow 通过 Quality-Check
- [ ] 编译 / 测试通过
- [ ] 与用户复述最终结果
```

### 4.4 与 Orchestrator 的衔接

Plan 输出后,Orchestrator:
1. 把 Plan 文档路径写入 Agent-Memory(Plan 自己)。
2. 解析 Markdown 提取 WorkFlow 列表。
3. 顺序委派给 Main-Work,每个 WorkFlow 一个 SubFlow。
4. Main-Work 进一步拆 SubFlow → SubAgent-Work。
5. 全部 WorkFlow 通过 Quality-Check → 汇总到 SessionContext。

## 5. Main-Work Agent 设计(medium/hard 档)

### 5.1 定位

Main-Work 是**流程层 Agent**,负责把一个任务拆成多个流程处理单元,处理分支与循环。

### 5.2 工具集

| 工具 | 用途 |
|------|------|
| Bash | 执行 shell 命令 |
| Read | 读取文件 |

> Main-Work 不直接写代码,只编排流程;写代码委派给 SubAgent-Work。

### 5.3 WorkFlow 模型

```rust
pub struct WorkFlow {
    pub id: String,                 // wf-1, wf-2, ...
    pub name: String,
    pub steps: Vec<SubFlow>,
    pub branches: Vec<Branch>,      // 条件分支(基于 step 输出)
    pub loops: Vec<Loop>,           // 循环(基于条件)
    pub depends_on: Vec<String>,    // 依赖其它 WorkFlow id
    pub acceptance: Vec<String>,    // 验收标准
}

pub struct SubFlow {
    pub id: String,
    pub description: String,
    pub delegate_to: AgentRole::SubAgentWork,
    pub expected_output: String,
}
```

Main-Work 通过结构化输出(类似 Yolo 的 JSON,但格式不同)告诉 Orchestrator:
- 有多少个 WorkFlow
- 每个 WorkFlow 的步骤 / 分支 / 循环
- 每个 SubFlow 委派给哪个 SubAgent-Work

### 5.4 执行循环

Orchestrator 调度 Main-Work 时:
1. 把当前 Plan 文档(若存在)+ 用户原始需求 + 已完成 WorkFlow 结果 传给 Main-Work。
2. Main-Work 输出结构化 WorkFlow JSON。
3. Orchestrator 解析 JSON,按拓扑顺序执行 WorkFlow。
4. 每个 WorkFlow 执行后,调用 Quality-Check。
5. Quality-Check 通过 → 写 Agent-Memory 并进入下一个 WorkFlow。
6. Quality-Check 不过 → 回流到 Main-Work,Main-Work 决定重试 / 调整 / 放弃。
7. 全部 WorkFlow 完成 → 进入 SessionContext。

## 6. SubAgent-Work Agent 设计(simple 档 + 所有 SubFlow)

### 6.1 定位

SubAgent-Work 是**执行层最小单元**,继承原 Work Agent 的工具调用循环,但只负责"一个流程处理单元"的工作。

### 6.2 工具集

| 工具 | 用途 |
|------|------|
| Bash | 执行 shell 命令 |
| Read | 读取文件 |
| Write | 写文件 |

### 6.3 调用方式

```rust
pub async fn run_unit(
    &self,
    subflow: &SubFlow,
    inputs: AgentContextInputs, // 输入: 任务描述、依赖产物
) -> Result<UnitOutcome> {
    // 1) 构造独立 Agent-Context(只含本单元相关消息)
    // 2) run_session 循环
    // 3) 收集输出 + 用量
    // 4) 写 Agent-Memory
    // 5) 返回 UnitOutcome
}
```

每个 SubAgent-Work 实例用完即弃,**不持有跨单元对话**——跨单元连续性靠 Orchestrator 注入 inputs。

## 7. Quality-Check Agent 设计

### 7.1 定位

Quality-Check 是**质检层**,对每个执行单元的输入与输出做质量校验。

### 7.2 工具集

默认无工具(纯 LLM 判定);可选 Read 用于读源代码辅助判断。

### 7.3 校验对象

| 来源 | 校验什么 | 通过标准 |
|------|---------|---------|
| SubAgent-Work | 单元输出是否满足 expected_output | LLM 判断 + 可选命令行验证 |
| Main-Work | WorkFlow 结构是否合理 / 依赖是否完整 | LLM 判断 |
| Plan | Markdown 方案是否完备 / WorkFlow 是否覆盖目标 | LLM 判断 |

### 7.4 输出

```json
{
  "verdict": "pass | fail",
  "issues": ["问题描述 1", "问题描述 2"],
  "suggestion": "改进建议",
  "retryable": true | false
}
```

- **verdict=pass** → 单元写入 Agent-Memory,进入下一步。
- **verdict=fail + retryable=true** → 回流到执行单元重试。
- **verdict=fail + retryable=false** → 升级到上一层(Main→Plan→Yolo)。

### 7.5 升级规则

| 失败来源 | 升级目标 |
|---------|---------|
| SubAgent-Work | Main-Work(简单任务无 Main-Work,直接升级到 Yolo) |
| Main-Work | Plan(hard)或 Yolo(medium) |
| Plan | Yolo |

## 8. SessionContext Agent 设计

### 8.1 定位

SessionContext 是**会话层**,串联同一 Session 内的多次任务输入,提供:
- 本次任务的输入 / 输出 / 用量 / 关键事件摘要
- 历史任务摘要(供 Yolo 多轮关联使用)
- 失败回流时给用户的备选建议展示

### 8.2 工具集

默认无工具(纯文本生成)。

### 8.3 SessionMemory 表(SQLite)

```sql
CREATE TABLE IF NOT EXISTS session_memory (
    id           INTEGER PRIMARY KEY AUTOINCREMENT,
    session_id   TEXT NOT NULL,
    seq          INTEGER NOT NULL,         -- 同一 session 内自增序号
    role         TEXT NOT NULL,            -- yolo / plan / main / sub / quality / session / user
    event_type   TEXT NOT NULL,            -- input / output / failure / suggestion / summary
    content      TEXT NOT NULL,            -- Markdown 或 JSON 序列化
    usage_input  INTEGER NOT NULL DEFAULT 0,
    usage_output INTEGER NOT NULL DEFAULT 0,
    created_at   TEXT NOT NULL DEFAULT (datetime('now','localtime')),
    UNIQUE(session_id, seq)
);
```

### 8.4 工作流

每次用户输入完成后,无论成功或失败:
1. Orchestrator 收集本次任务的:
   - 用户原始 prompt
   - Yolo 分类结果
   - Plan 文档路径(若有)
   - WorkFlow 执行结果
   - Quality-Check 报告
   - 累计 token 用量
2. 调用 SessionContext 生成 Markdown 摘要。
3. 写入 session_memory 表(seq 自增)。
4. Yolo 下一轮处理时,把最近 N 条摘要作为上下文注入(默认 N=3,可在配置调整)。

## 9. Agent-Context 与 Agent-Memory 详细设计

### 9.1 Agent-Context(实时)

```rust
pub struct AgentContext {
    pub agent_role: AgentRole,
    pub session_id: String,
    pub unit_id: String,                  // 当前执行单元 id
    pub messages: Vec<ChatMessage>,       // 当前单元的实时消息流
    pub state: HashMap<String, Value>,    // 任务状态(中间结果)
    pub iteration: usize,
    pub created_at: String,
}
```

**特征**:
- 内存态,生命周期 = 当前单元执行时长。
- 仅含与当前单元相关的消息(不继承主 Session 全部历史)。
- 由 Orchestrator 在调用前构造,调用结束后丢弃。

### 9.2 Agent-Memory(经验)

```rust
pub struct AgentMemory {
    pub agent_role: AgentRole,
    pub session_id: String,
    pub entries: Vec<MemoryEntry>,       // 来自 session_memory(role 匹配)
}
```

```sql
CREATE TABLE IF NOT EXISTS agent_memory (
    id           INTEGER PRIMARY KEY AUTOINCREMENT,
    session_id   TEXT NOT NULL,
    agent_role   TEXT NOT NULL,
    input_summary  TEXT NOT NULL,
    output_summary TEXT NOT NULL,
    error_summary  TEXT,                  -- null 表示成功
    artifacts    TEXT,                   -- JSON 序列化的产物引用
    created_at   TEXT NOT NULL DEFAULT (datetime('now','localtime'))
);
```

**特征**:
- 持久化到 SQLite,跨单元 / 跨 Session 共享(可选按 session 过滤)。
- 单元完成后由 Orchestrator 自动写入。
- 下次同类 Agent 处理前,最近 M 条作为背景知识提示。

### 9.3 对比

| 维度 | Agent-Context | Agent-Memory |
|------|--------------|--------------|
| 生命周期 | 单次单元执行 | 持久化(SQLite) |
| 内容 | 实时消息流 / 工具调用 / 中间状态 | 输入摘要 / 输出摘要 / 错误 / 产物 |
| 体量 | 可能很大(每次 LLM 请求都带) | 小(每次单元只写 1 条) |
| 用途 | 让 LLM 完成当前单元 | 让 LLM 借鉴历史经验 |
| 类比 | RAM | 磁盘 |

## 10. Orchestrator 编排器

### 10.1 核心数据结构

```rust
pub struct MultiAgentOrchestrator {
    yolo: Agent,
    plan: Agent,
    main_work: Agent,
    sub_agent: Agent,
    quality: Agent,
    session_context: Agent,

pub enum OrchestrationOutcome {
    DirectAnswer { text: String, classification: TaskClassification, usage: Usage },
    Executed { result: TaskResult, total_usage: Usage },
    Failed { classification: TaskClassification, suggestion: String, usage: Usage },
}

    pub goal: String,
    pub plan_doc: Option<PathBuf>,
```

### 10.2 编排主循环

```rust
pub async fn handle(&self, req: OrchestrationRequest) -> Result<OrchestrationOutcome> {
    // 0) 项目上下文首次注入
    inject_once(req.session, work_dir);

    // 1) Yolo 入口
    let classification = self.run_yolo(&req).await?;
    write_session_memory(yolo, classification, ...);

    // 2) 失败回流计数(防止无限循环)
    let mut retry_count = 0;
    loop {
        let result = match classification.task_level {
            Simple => self.run_simple(&classification, &req).await?,
            Medium => self.run_medium(&classification, &req).await?,
            Hard   => self.run_hard(&classification, &req).await?,
        };

        match result {
            Ok(executed) => {
                // 3) SessionContext 收口
                let summary = self.run_session_context(&executed, &req).await?;
                return Ok(Executed { result: executed, total_usage });
            }
            Err(failure) => {
                retry_count += 1;
                if retry_count > MAX_RETRY {
                    return Ok(Failed { ..., suggestion: failure.suggestion });
                }
                // 4) 失败回流
                let new_classification = self.run_yolo_with_failure(&failure, &req).await?;
                classification = new_classification;
            }
        }
    }
}
```

### 10.3 简单档路径

```rust
async fn run_simple(&self, c: &Classification, req: &Req) -> Result<TaskResult> {
    let sub_outcome = self.sub_agent.run_unit(c, inputs).await?;
    let qc = self.quality.check_subagent(&c, &sub_outcome).await?;
    if qc.verdict == pass {
        Ok(TaskResult::single(sub_outcome))
    } else {
        Err(QualityFail { source: SubAgent, ... })
    }
}
```

### 10.4 中等档路径

```rust
async fn run_medium(&self, c: &Classification, req: &Req) -> Result<TaskResult> {
    // 1) Main-Work 输出 WorkFlow JSON
    let workflow = self.main_work.plan_workflows(c, inputs).await?;
    // 2) 顺序执行 WorkFlow
    let mut results = [];
    for wf in workflow.flows {
        let sub = self.sub_agent.run_unit(wf, ...).await?;
        let qc = self.quality.check_subagent(&wf, &sub).await?;
        if qc.fail {
            // 回流 Main-Work 调整
            return Err(QualityFail { source: MainWork, ... });
        }
        results.push(sub);
    }
    Ok(TaskResult::workflow(results))
}
```

## 11. 与旧架构的兼容性

### 11.1 命名映射

| 旧名 | 新名 | 备注 |
|------|------|------|
| `LsmAgentEmergentWork-Work` | `LsmAgentEmergentWork-SubAgent-Work`(简单档)/ `LsmAgentEmergentWork-Main-Work`(中档)/ `LsmAgentEmergentWork-Plan`(高档) | 拆分而非替换 |
| `LsmAgentEmergentWork-Yolo` | `LsmAgentEmergentWork-Yolo` | 保留并扩展(三档 + agent_role + 失败回流) |
| `TaskLevel::Trivial` | 删除(并入 Simple,通过 direct_answer 字段表达) | - |
| `TaskLevel::Simple/Medium/Hard` | `TaskLevel::Simple/Medium/Hard` | 保留,语义微调 |

### 11.2 行为变更

| 行为 | 旧 | 新 |
|------|-----|-----|
| Yolo 解析失败降级 | simple 直接委派 Work | simple 直接委派 SubAgent-Work,失败回流 |
| Work Agent 名称 | `LsmAgentEmergentWork-Work` | 由 Orchestrator 按档位动态选择对应 Agent 名 |
| Plan 文档 | 无 | hard 档自动落盘 `plans/{session_id}-{seq}.md` |
| 质量门控 | 无 | 每个单元必经 Quality-Check |
| SessionMemory | 无 | 自动写入 session_memory 表,下次 Yolo 自动注入 |
| 失败回流 | 无 | 失败逐层回退到 Yolo,Yolo 决定重试或给用户建议 |

### 11.3 CLI 兼容

- `-p` / `-f` 单轮模式:走 Orchestrator 全部流程,输出最终结果 + SessionContext 摘要。
- TUI 模式:显示每个阶段(Yolo/Plan/Main/Sub/Quality/SessionContext)的状态指示。
- `provider` 子命令:不变。

## 12. 风险与缓解

| 风险 | 影响 | 缓解 |
|------|------|------|
| Agent 多导致延迟增加 | 多次 LLM 调用 | SubAgent-Work 可批量发起工具调用,Quality-Check 与 SessionContext 可选跳过 |
| Plan 文档生成失败 | hard 任务卡住 | Plan 失败视为可重试,3 次后降级为 medium(Yolo 决策) |
| SessionMemory 表膨胀 | 长期使用后占用大 | 定期归档;只保留最近 N 条摘要供 Yolo 注入 |
| Agent-Memory 与 Agent-Context 混淆 | 实现 bug | 类型严格区分;Agent-Context 不可序列化,Agent-Memory 强类型持久化 |
| Quality-Check 误判 | 通过 / 不通过翻转 | 可配置 `quality_strictness`(loose/normal/strict);失败有明确 issues 描述 |
| 失败回流无限循环 | 任务卡死 | `MAX_RETRY=3` 上限,达到后输出建议 |
| 重构影响范围大 | 破坏既有功能 | 旧 `Work Agent` 通过 SubAgent-Work 兼容;旧测试用例需要更新 Yolo JSON 字段 |
