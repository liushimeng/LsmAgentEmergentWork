## 一、为什么需要 TODO 任务清单

### 1.1 当前痛点

laew 多 Agent 架构中，SubAgent-Work / Main-Work 在执行多步任务时：

1. **进度不透明**：用户只在 Orchestrator 收到最终结果时才知道完成情况，中途「Agent 是不是卡了？」无法判定。
2. **失败难定位**：长任务失败时，LLM 输出的「最后一句话」不足以让用户判断「卡在哪一步」。
3. **规划丢失**：Main-Work 输出的 Workflow 列表只在那一刻存在，SubAgent 内部「我接下来该做什么？」需要 LLM 重新从上下文推理。
4. **重置无恢复**：任务重置后（如 `/clear`），之前规划的 todo 全部丢失。

### 1.2 知识库对标

第十九轮深挖合集第二十轮候选 5 明确点名：

> **TODO 任务清单系统**（deepseek `tool-todo/` projection/invariant + opencode todo.ts）— 真实未覆盖

- **deepseek `tool-todo/` projection 模型**：内部维护「任务清单投影」，每次工具调用返回当前清单渲染版，附带不变量校验。
- **opencode `todo.ts`**：`Todo` interface `{content, status, priority}` + `TodoWrite` 单工具 `merge`/`replace` action。
- **atomcode review / 等**：也广泛使用 todo 系统做任务清单跟踪。

### 1.3 laew 现状（修复前）

- **零 TODO 工具**：7 个工具体系（Bash/Read/Write/Edit/Glob/Grep/MCP_Window_Use/MCP_Web_Use）+ 2 个 emit 通道（submit_task_classification/submit_quality_report）都是**操作型/输出型**，缺**任务规划型**。
- **零进度展示**：TUI 横幅只有 session 元信息（device_id / session_id / model / workspace），不显示当前 SubAgent 的任务清单。
- **零跨 Agent 共享**：Yolo 分类后产生的「分解步骤」只在那一刻存在，下游 SubAgent 看不到。

---

## 二、本次实现的核心目标

1. **新增 TodoWrite 工具**：单工具 + `action` 枚举分发（create/update/read/clear），对齐 MCP_Window_Use / MCP_Web_Use 风格。
2. **进程内 todo state**：跨 SubAgent 调用保持（同一 session 内可见）。
3. **TUI 进度显示**：banner 新增 `📋 Tasks: [✓]3 [→]1 [ ]2` 一行（仅在有 todo 时显示）。
4. **零侵入集成**：不修改 main_work/topology、不引入新 crate、不破坏现有 7 工具向后兼容。
5. **重置语义**：`/clear` / `/new` 时自动重置 todo_state，避免看到旧会话的列表。

/// TODO 状态枚举(对外暴露的合法值)。

#[serde(rename_all = "snake_case")]
pub enum TodoStatus {
    #[default]
    Pending,
    InProgress,    // 全列表最多 1 项
    Completed,
    Cancelled,
}

    pub id: u32,
    pub content: String,

    #[serde(default, skip_serializing_if = "Option::is_none")]
    pub priority: Option<TodoPriority>,
    pub created_at: String,

}

### 3.4 TodoWrite 工具设计

**工具名**：`TodoWrite`（与 deepseek `tool-todo/` 同名）

**JSON Schema**：
```json
{
  "type": "object",
  "properties": {
    "action": {
      "type": "string",
      "enum": ["create", "update", "read", "clear"],
      "description": "操作类型"
    },
    "todos": {
      "type": "array",
      "items": {
        "type": "object",
        "properties": {
          "id": { "type": "integer", "minimum": 1 },
          "content": { "type": "string", "minLength": 1 },
          "status": { "type": "string", "enum": ["pending","in_progress","completed","cancelled"] },
          "priority": { "type": "string", "enum": ["high","medium","low"] }
        },
        "required": ["content", "status"]
      }
    }
  },
  "required": ["action"]
}
```

**action 语义**：

| action | 行为 | todos 字段 |
|--------|------|-----------|
| `create` | 清空现有 + 全量替换 | 必填 |
| `update` | 按 id 增量更新 | 必填 |
| `read` | 仅返回当前清单 | 省略 |
| `clear` | 清空 | 省略 |

**不变量校验**：
- 最多 1 个 `in_progress` 项（其余降级回 pending + warning）
- ID 单调递增；`update` 时 id 不存在则报错；`clear` 后 id 从 1 重新开始
- status/priority 字符串兼容别名（`done` ↔ `completed`、`canceled` ↔ `cancelled`、`in-progress` ↔ `in_progress`）
- 单次 create/update 最多 50 条（防 LLM 一次性塞入过多）

**返回值示例**：
```
Todo list created with 5 items:
Todo list: 5 items
✓ [1] 读取 Cargo.toml (high)
→ [2] 解析依赖图 (high)
○ [3] 生成补丁 (medium)
○ [4] 运行 cargo test (medium)
○ [5] 提交变更 (low)
```

## 四、实现要点

### 4.1 为什么不引入新 crate

- TodoWrite schema 仅 1 个 string + 4 个 enum + 1 个 array，serde_json 直接序列化足够。
- 状态机 + Mutex 已有先例（`OfflineQueue`、`ConnectivityTracker`）可直接参考。
- 自研能控制 less surface，**零新增依赖**。

### 4.2 为什么 action dispatch 而非多工具

- 减少 LLM tool 选择成本（1 个工具而非 3-4 个）
- 对齐 MCP_Window_Use / MCP_Web_Use 单工具多 action 模式
- 减少 tool def 体积（schema 仅 1 份）

### 4.3 为什么是 in_progress 单项

- 真实工作状态：「当前只做一件事」
- 多 in_progress 通常是 LLM 推理失误，需约束
- 帮助 TUI summary 产生「进行中 1 项」标识

不变量校验：当 create/update 时发现 N 个 in_progress，**保留第一个为 in_progress，其余降级 pending**，并在返回值附 warning。
让 LLM 在下一次 read 时能立即看到错误 + 自动校正（而非破坏状态）。

### 4.4 为什么 TodoWriteTool 既支持 new() 也支持 shared()

- `TodoWriteTool::new(arc)`：显式绑定某个 TodoState，便于 TUI 会话级隔离与单元测试。
- `TodoWriteTool::shared()`：默认回退到全局 TodoState，适合 `builtin_registry` / `main_work_registry` 直接注册（按调用放模式挂在全局）。

测试中全部使用 `new(fresh_state)` 避免并行污染全局，生产代码注册使用 `shared()` 走全局。

### 4.5 时间格式化陷阱

Cargo.toml 主依赖未启用 `time::macros` feature（仅 build-dependencies 启用）。手动格式化：

```rust
fn now_readable() -> String {
    use time::OffsetDateTime;
    let dt = OffsetDateTime::now_local().unwrap_or_else(|_| OffsetDateTime::now_utc());
    format!(
        "{:04}-{:02}-{:02} {:02}:{:02}:{:02}",
        dt.year(),
        u8::from(dt.month()),
        dt.day(),
        dt.hour(),
        dt.minute(),
        dt.second()
    )
}
```

格式 `YYYY-MM-DD HH:MM:SS`，本地时区优先，失败回退 UTC。
