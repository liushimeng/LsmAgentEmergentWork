## 1. 背景与目标

### 1.1 什么是 ReAct

「反馈 → 执行 → 再反馈 → 再执行」的多轮循环模式,标准名称是 **ReAct**
(Reasoning + Acting,推理 + 行动)。核心是 **Thought→Action→Observation 闭环**:
每轮先推理判断下一步动作,执行工具/操作后获取外部结果作为反馈,再基于新信息
重新推理、调整动作,循环迭代直到任务完成。

ReAct 是 Agent 最基础主流的工作范式;同类还有 Plan-and-Execute(先定计划再执行)
等变体。laew 的多 Agent 架构本身就是「Plan(Plan Agent)→ Execute(Main-Work 拆解
→ SubAgent-Work 执行)」的 Plan-and-Execute 外层 + **SubAgent-Work 内部 ReAct** 的
混合体:外层已有规划,内层必须靠实时反馈逐轮推进。

### 1.2 动机

第 119 轮已完成 **入口层 Yolo** 的 ReAct 化(信息收集型工具面 + 延迟强制 emit),
但**执行层 SubAgent-Work 仍是"裸循环"**:

- 提示词里**一个 ReAct 字都没有**(对比 Yolo 提示词有完整的「信息收集(ReAct 模式)」节);
- 循环体只是机械的 `complete → tool_calls → execute → tool_result → loop`,
  Thought 不显式、Observation 不归纳、无进展不自知;
- 提示词承诺「并行无依赖的工具调用一次性发出」,但运行时**全部串行执行** —— 承诺与实现不符;
- 迭代预算耗尽前**无任何预警**(收口预告只给 Yolo);
- 重复动作检测只覆盖「连续相同**失败**」,不覆盖「连续相同**成功**但结果一字不变」的原地打转。

后果(实测复盘常见模式):SubAgent 在 16 轮预算里反复 `Read` 同一个文件、反复
`inspect` 同一个页面、反复跑同一条失败命令的变体,把预算烧光后被
`MaxIterationsExceeded` 硬杀,QC 拿到的是「跑满上限 + 零产物」。

### 1.3 本轮目标

| 目标 | 说明 |
|------|------|
| **ReAct 显式化** | SubAgent-Work 提示词补 Thought→Action→Observation 节奏规范;运行时用 hint 强制「先推理再动手」 |
| **Observation 进展可判定** | 引入「进展键 = 工具 + 参数 + **结果摘要**」三元组,精确区分「轮询等待(有进展)」与「原地打转(无进展)」 |
| **无进展止损** | doom_loop 双阈值(软提醒 nudge / 硬止损 abort),对齐 AtomCode `ToolLoopPolicy` + OpenCode `doom_loop` + DeepSeek `repeat-tool-reminder` |
| **工具连续工作模式** | 同批只读工具**真并发**执行(`parallel_safe` 参数感知分类 + Semaphore 限流 + 保序回填),对齐 Claude Code `partitionToolCalls` / AtomCode Phase ② EXECUTE |
| **预算自感知** | 迭代进度 hint + **通用收口预告**(无 emit 角色也生效),不再让单元闷头跑满 16 轮 |
| **hint 角色化** | `explore_budget` 耗尽文案按角色分叉(浏览器 / 通用执行 / 信息收集),根治「代码任务被提示去 click」的语义误导 |
| **零回归 + 可回退** | 每项新机制都有环境变量开关;`parallel_safe` 默认 `false` 使未覆写工具行为逐字不变 |

### 1.4 本轮不做(留后续)

| 项 | 原因 |
|----|------|
| Goal round-driver 状态机(DeepSeek `maxGoalRounds`) | laew 的续航由外层 Orchestrator 拓扑 + 单元级重试承担,SubAgent 内部再加目标状态机与现有 WorkFlow 语义重叠,需独立立项 |
| Bash 失败级联取消兄弟(Claude Code `sibling_abort`) | laew `BashTool` 每次调用是独立子进程、**无持久 shell 状态**,不存在 Claude Code 假设的「隐式依赖链」;级联取消只会误伤合法的多命令批 |

### 2.1 核心矛盾

`agent_loop.rs` 的循环是**协议无关的机械闭环**,它保证了「不会跑飞」(5 类短路保护),
但没有保证「每一轮都在推进」。ReAct 的关键不在循环结构(结构早已是 ReAct 形状),
而在三件事:

1. **Thought 必须显式**——不写推理就动手的调用是盲调,盲调是原地打转的根源;
2. **Observation 必须被判定为「有进展 / 无进展」**——这是循环能不能自我纠偏的唯一信号;
3. **预算必须被模型看见**——看不见预算的模型不会主动收口。

本轮就是补这三件事,外加把「连续工作模式」的执行侧(并发)真正落地。

## 3. 方案设计

### 3.1 R1 — `Tool::parallel_safe(args)`:参数感知的并行安全分类

`Tool` trait 新增带默认实现的方法(知识库:`专题-工具调用深度分析.md` §laew 缺口
「parallel_safe 工具并行分类(P1)」,AtomCode `parallel_safe(args)`):

```rust
/// 本次调用能否与同批其它调用**并发执行**(第 120 轮「工具连续工作模式」)。
///
/// 默认 `false` = 保序串行,与第 119 轮之前行为**逐字一致**(零回归基线)。
/// 仅「纯只读、无副作用、无跨调用共享状态」的工具覆写为 `true`。
/// 参数感知:同一工具可按 `args` 决定(例:`MCP_Web_Use` 的只读 `inspect`
/// 理论可并发,但浏览器是单一前台资源,本轮一律 `false`)。
fn parallel_safe(&self, _args: &Value) -> bool {
    false
}
```

分类结果:

| 工具 | `parallel_safe` | 理由 |
|------|-----------------|------|
| `Read` | **true** | 纯读文件,无副作用、无共享状态 |
| `Glob` | **true** | 纯路径匹配 |
| `Grep` | **true** | 纯内容检索 |
| `Bash` | false | 子进程副作用;命令间可能有隐式顺序(建目录→写文件→编译) |
| `Write` / `Edit` | false | 落盘写;同批并发写同一文件会互相覆盖 |
| `TodoWrite` | false | 进程内共享 `Mutex<TodoState>`,并发无收益且乱序 |
| `SubAgent` | false | 内部已自带 `buffer_unordered` 并发(≤8),外层再并发会放大会话级预算 |
| `MCP_Web_Use` | false | 浏览器单一实例 + 单前台 Tab,物理上不可并发 |
| `MCP_Window_Use` | false | 桌面单一前台焦点(第 88 轮焦点守卫的前提就是「独占前台」) |
| `submit_*`(emit) | false | 命中即短路终止,不参与批次 |

### 3.2 R2 — agent_loop 分批并发执行(连续工作模式的执行侧)

采用 Claude Code `partitionToolCalls` 语义:**连续的 parallel_safe 段合并为一批并发**,
其余保序串行。

```
tool_calls:  [Read, Grep, Read, Bash, Read, Glob]
分批结果  :  [ Read, Grep, Read ](并发批,size=3) [ Bash ](串行) [ Read, Glob ](并发批,size=2)
```

执行流程:

1. **预扫描**:定位 emit 短路点 `emit_index`(命中 emit 后的调用一律忽略,不进批);
   在 `0..emit_index` 范围内切出「长度 ≥ 2 的连续 parallel_safe 段」。
2. **并发执行**:每段用 `futures::future::join_all` 并发跑,受
   `tokio::sync::Semaphore(LAEW_MAX_PARALLEL_TOOLS)` 限流(默认 **4**,对齐 AtomCode
   `ATOMCODE_MAX_PARALLEL_TOOLS=4`;Claude Code 用 10,laew 单元预算小、取更保守值)。
3. **结果缓存**:`HashMap<usize /*call index*/, ToolExec>`,主循环按 index 取用;
   取不到(串行段)则走原有单条执行路径。
4. **后处理与回填严格保持原顺序**:浏览器失败学习 / trace 记录 / `tool_call_log` /
   `context.push(tool_result)` 全部仍在主循环里**按 tool_calls 原序**执行 ——
   并发只改「执行时序」,不改「上下文时序」,因此 assistant `tool_use` ↔ `tool_result`
   配对顺序、Anthropic/OpenAI wire 顺序、`recent_tool_history` 叙事顺序**全部不变**。
5. **取消**:每个并发 future 内部仍是 `tokio::select! { biased; cancel => …, exec => … }`;
   任一条命中取消 → 整批放弃 → `backfill_cancelled_tool_results` + `Err(Cancelled)`
   (与现有语义一致)。

为承载 3/4 两步,把原 L504-L568 的「单条执行」逻辑抽成 `Agent::exec_tool_call`
辅助函数,返回统一的 `ToolExec { output, is_error, error_summary, elapsed_ms, cancelled }`;
并发批与串行路径共用同一函数,**行为逐字等价**(纯机械抽取,不改判定分支)。

`ExecutionTrace` 新增 `parallel_tool_batches: usize` 与 `parallel_tool_calls: usize`
两个计数字段(`serde(default)` 兼容旧 trace),供 TUI / Debug Report / QC 对账
「这批是并发跑的,省了多少轮」。

总开关:`LAEW_PARALLEL_TOOLS=off|0|false|no` → 强制全串行(等同第 119 轮行为)。

### 3.3 R3 — `LoopGuard`:无进展检测(doom_loop)+ 双阈值止损

新增职责子模块 `src/agent/loop_guard.rs`。

#### 3.3.1 进展键(与外部工程的关键差异)

```rust
/// 一次工具调用的「进展指纹」。
/// key = 工具名 # stable_json_string(args) # digest(is_error, output)
```

**Observation 摘要进入指纹**是本轮的核心设计决策:

| 工程 | 重复判定键 | 缺陷 |
|------|-----------|------|
| OpenCode `doom_loop` | 工具名 + 输入 hash | 轮询等待(同一 `inspect` 等页面变化)会被误判为死循环 |
| DeepSeek `repeat-tool-reminder` | 工具名 + `canonicalize(arguments)` | 同上 |
| AtomCode `ToolLoopPolicy` | 工具调用签名 | 同上 |
| **laew `LoopGuard`(本轮)** | 工具名 + 参数稳定 JSON + **结果摘要** | 「同动作 + 同结果」才算无进展;轮询期间结果在变 → 判为**有进展**,零误伤 |

`digest` 取 `is_error` 标志 + 输出前 256 字符 + 输出字节长度。参数序列化直接复用
既有 `runtime_hints::stable_json_string`(对象 key 递归排序),正是 DeepSeek
`canonicalize = deep key-sort JSON` 的等价实现 —— 「LLM 调换参数顺序」不会误判为新动作。

#### 3.3.2 双阈值与宽限轮

| 阈值 | 值 | 行为 |
|------|----|----|
| `NUDGE_AT` | **2** | 第 2 次完全相同(动作+结果)→ 注入软提醒到 system 后缀,**不终止**循环 |
| `ABORT_AT` | **3** | 第 3 次 → 首次命中先用**宽限轮**(对齐第 25 轮 F9 设计:nudge 必须真的送达 LLM 才有意义),第二次命中才硬止损 |

laew 单元预算只有 16 轮,阈值必须比 AtomCode(3 nudge / 6 stop)、DeepSeek([3,5,8])
更紧,否则提醒还没生效预算就烧完了。

软提醒文案(经 runtime hints 注入):

```text
【无进展警告】你已连续 N 次发起完全相同的工具调用并得到完全相同的结果
(<tool> <args 摘要>)。重复同一动作不会产生新信息。请立即改变策略:
(1) 换工具或换参数(不同路径 / 不同 selector / 不同命令);
(2) 若目标是等待外部状态变化,改用带 wait/timeout 的调用而非反复轮询;
(3) 若已确认无法推进,直接收口并如实说明卡点。
```

硬止损行为:

- `trace.early_terminated = true`,`early_terminate_reason = "doom_loop_no_progress tool=<name> repeats=<n>"`;
- 失败信号打 `doom_loop`(`collect_failure_signals` 新增分支),QC / Yolo 回流可见;
- **已有工具产出** → 优雅收尾(`finalize_logged` 返回累计文本 + 兜底叙事摘要),交 QC 判定;
- **全程零产出** → `Err(AgentError::RepeatedToolFailure { … })`,走既有失败回流;
- 兜底文本包含最近工具调用叙事摘要(复用 `recent_tool_history`),让用户/QC 看到「它到底在打什么转」。

总开关:`LAEW_REACT_GUARD=off|0|false|no` → nudge 与止损均不生效(等同第 119 轮行为)。

#### 3.3.3 与既有三计数器的关系(互补,不重叠)

| 机制 | 触发条件 | 覆盖场景 |
|------|---------|---------|
| `REPEATED_FAILURE_THRESHOLD=3` | 连续相同 **(工具,参数)** 且**失败** | 幻觉路径反复 Read 不存在文件 |
| `NO_TEXT_CONVERGE_THRESHOLD=8` | 连续 8 轮「仅 tool_use 无文本」 | 不停探查从不收敛 |
| `NO_TOOL_USE_THRESHOLD=3` | 连续 3 轮无 tool_use | 空跑 / 引导失效 |
| **`LoopGuard`(本轮新增)** | 连续相同 **(工具,参数,结果)** | **成功但一字不变的原地打转**(前三者全部漏掉) |

### 3.4 R4 — runtime hints 角色化 + ReAct 进度/收口 hint

#### 3.4.1 角色化 `HintRole`

```rust
/// runtime hint 的角色分叉(第 120 轮:根治 D5「代码任务被提示去 click」)。
pub(crate) enum HintRole {
    /// 浏览器 / 桌面操控执行层(持 MCP_Web_Use / MCP_Window_Use)
    Ui,
    /// 通用执行层(代码 / 文件 / 命令类单元)
    Execute,
    /// 入口层信息收集(Yolo)
    Gather,
    /// 判定层(QC / Debug / Compact / SessionContext),不注入执行期文案
    Judge,
}
```

由 `AgentProfile` 派生(工具面含 `MCP_Web_Use`/`MCP_Window_Use` → `Ui`;
`emit_tool.is_some() && defer_emit_force` → `Gather`;`spawn_policy == Disabled`
且无写工具 → `Judge`;其余 → `Execute`)。

`explore_budget` 耗尽文案按角色分叉:

| 角色 | 文案要点 |
|------|---------|
| `Ui` | 现有文案原样保留(inspect/screenshot/eval_js → input_text/click/wait + 人工介入) |
| `Execute` | 「已进入执行期。剩余迭代专注**落地改动与验证**(Write/Edit/Bash 构建与测试),禁止再开新的只读探查(Read/Glob/Grep),除非用于验证刚做的改动。」 |
| `Gather` | 「信息收集预算已耗尽。请立即基于已收集的信息收口提交,不再开启新的探查。」 |
| `Judge` | 不注入(判定层无探索/执行阶段之分) |

#### 3.4.2 三类新 hint

| hint | 触发条件 | 文案要点 |
|------|---------|---------|
| **ReAct 进度** | `trace.iterations * 2 >= trace.max_iterations`(预算过半) | 「【进度】第 k/N 轮迭代,已调用工具 X 次(成功 Y / 失败 Z)。若已达成 expected_output 请**立即收口**输出终答。」 |
| **Thought nudge** | 连续 **2** 轮「仅 tool_use 无文本」(把 D7 的 8 轮前移到 2 轮,**只提醒不终止**) | 「连续 N 轮未输出推理文本。ReAct 要求每轮先用 1~3 句写出 Thought(已知什么 / 还缺什么 / 下一步做什么最省)再发起工具调用;请本轮补上。」 |
| **通用收口预告** | `iter + 2 == max_iterations` | 有 `emit_tool` → 原 Yolo 文案(强制提交 emit);无 `emit_tool` → 「【收口提示】迭代预算即将耗尽(下一轮为最终轮)。请立即停止新动作,基于已有 Observation 输出最终结果:完成情况 + 实际产出与 expected_output 的对应关系 + 关键工具调用;未完成部分如实说明。」 |

#### 3.4.3 函数签名演进

`build_runtime_hints(trace, consecutive_failures)` 保留为**薄封装**(现有单测零改动),
新增 `build_runtime_hints_with(&RuntimeHintCtx)`:

```rust
pub(crate) struct RuntimeHintCtx<'a> {
    pub trace: &'a ExecutionTrace,
    pub consecutive_failures: usize,
    pub role: HintRole,
    /// LoopGuard 软提醒(§3.3.2)
    pub loop_nudge: Option<&'a str>,
    /// 连续「仅 tool_use 无文本」轮数(§3.4.2 Thought nudge)
    pub silent_rounds: usize,
    /// 收口预告(§3.4.2),由调用方按 emit_tool 有无选文案
    pub deadline: Option<&'a str>,
}
```

全部 hint 仍拼在 system **末尾**(`<<<LAEW:RUNTIME_HINTS>>>` 标记包裹),
不破坏 `cache_control` 缓存前缀(第七轮 PromptCaching 专题约束)。

### 3.5 R5 — SubAgent-Work 系统提示词 ReAct 化

#### 3.5.1 `SUB_AGENT_BASE_PROMPT` 新增「执行循环(ReAct 模式)」节

插在「## 输入格式」与「## 输出格式」之间:

```text
## 执行循环(ReAct 模式)

你是靠「反馈 → 执行 → 再反馈 → 再执行」逐轮推进的执行单元,不是脚本播放器。
每一轮严格按三段走:

- **Thought(推理)**:先用 1~3 句写出 —— 现在已经确认了什么?还缺什么?
  下一步做哪一件事最省(能一次拿到最多新信息)?
- **Action(行动)**:发起工具调用。无依赖的只读调用**一次性并发发出**
  (Read/Glob/Grep 可同批多个);有依赖的才分轮。
- **Observation(观察)**:读完工具结果,显式判断「这一步是否让任务向前推进了」。
  推进了 → 继续下一步;没推进 → **立即换路径**,不要用相同参数再试一次。

硬性约束:
- 禁止无 Thought 的盲调;禁止不读 Observation 就发下一批调用。
- 同一工具 + 同一参数 + 同一结果**连续出现 2 次**,系统会判定为无进展并警告;
  出现 3 次直接止损终止本单元。需要等待外部状态变化时,用带 wait/timeout 的
  调用(如 `MCP_Web_Use` sequence 的 wait 步骤),不要靠反复轮询消耗预算。
- 迭代预算过半时系统会提示进度;收到收口提示后**立即停止新动作**,基于已有
  Observation 输出终答。
- 达成 expected_output 即刻收口,不为「看起来更完整」而继续探索。
```

#### 3.5.2 `sub_agent_tools_hint()` 新增「连续工作模式」节

```text
## 连续工作模式(一轮做完整批动作)

优先用「一次调用编排多步」的复合能力,把 N 轮压成 1 轮:
- `MCP_Web_Use`:`action=sequence`(≤24 步,批内用 `$page_id` 占位)/ `batch` /
  `explore`(一次取多个 inspect 维度)。
- `MCP_Window_Use`:`action=input_batch`(≤40 步鼠标+键盘+控件树混排)/
  `sequence`(≤100 步,含 assert_text / wait_for_text 断言)。
- `SubAgent`:`action=batch`(≤8 个独立子任务并行)/ `workflow`(≤8 步 DAG)。
- `TodoWrite`:单元 ≥3 步时先 `create` 全量清单,每完成一步 `update` 标记 ——
  这既是进度自证,也是你下一轮 Thought 的依据。

单工具批次规则:
- 同一轮里**无依赖**的只读调用(Read/Glob/Grep)一次全部发出,系统会并发执行
  (上限 4 条),比逐轮串行省 3~4 倍迭代预算。
- 有副作用的调用(Bash/Write/Edit)按依赖顺序分轮,不要与只读调用混在同一批里
  指望并发 —— 它们会被保序串行执行。
```

#### 3.5.3 协议 tail 改写

`SUB_AGENT_ANTHROPIC_TAIL` / `SUB_AGENT_OPENAI_TAIL`:
「尽可能并行调用无依赖的工具。」→
「按 ReAct 三段推进(Thought→Action→Observation);无依赖的只读工具调用一次性并发发出,有副作用的调用保序分轮。」

| 环境变量 | 取值 | 行为 |
|---------|------|------|

### 3.7 安全边界(纵深防御)

| 层 | 约束 |
|----|------|
| 工具分类层 | `parallel_safe` 默认 `false`;有副作用工具(Bash/Write/Edit)永不并发 |
| 资源层 | `Semaphore(4)` 限流,防「LLM 一次发 20 个 Read」打爆文件句柄 |
| 上下文层 | 并发只改执行时序,`tool_result` 回填**严格按原序** —— 协议配对/orphan 修复语义零变化 |
| 取消层 | 每个并发 future 内 `select! biased` 竞争 cancel token;命中即整批放弃 + backfill |
| 循环层 | `LoopGuard` 硬止损 + 既有三计数器 + `max_iterations` 四重上界 |
| 回退层 | 三个环境变量开关,任一异常可即时降级到第 119 轮行为 |
