# 双浏览器工具架构(MCP_Web_Chrome_Use × MCP_Web_LsmAgentBrowser_Use)设计与解决方案

> 状态:Phase 1(本设计文档 + 文档/代码改名 + 历史资产找回)已落地;Phase 2(Chrome 基础框架)已落地;后续阶段见文末「分阶段路线图」的状态表。

## 1. 背景与问题

历史沿革(两个时代):

1. **Chrome/CDP 时代**(至 2026-10-20 提交 `49d1891f` 之前):`MCP_Web_Use` 工具底层用 Chromium 子进程 + CDP(chromiumoxide 0.9)驱动,配套反检测注入、指纹一致化、HITL 人工介入、站点熔断等一整套生产能力,知识库沉淀在 `docs/MCP_Web_Use/`(38 篇)。
2. **LsmAgentBrowser 时代**(`49d1891f` 起):`MCP_Web_Use` 工具名不变,底层换成进程内自研内核(无 Chrome、无 CDP),知识库沉淀在 `docs/自定义浏览器和V8引擎/`(22 篇)。Chrome/CDP 实现与文档在替换提交中被整体删除。

问题:

- 一个工具名下先后承载过两套完全不同的实现,知识库与代码考古困难;
- Chrome/CDP 方案在**真实浏览器兼容性与人工交互**(headed 窗口、验证码交给人工、登录态复用)上有不可替代的价值;
- LsmAgentBrowser 内核在**反-反爬**(无浏览器指纹面、进程内可控)上有独特价值;
- 两者本应**并存**:日常 80-90% 的读站/操作走 Chrome(默认优先),对 Chrome 风控敏感的站点才启动 LsmAgentBrowser 内核。

## 2. 目标与非目标

**目标**

1. 工具名按底层方案拆开重命名,全库(代码、注释、文档、提示词)不再出现旧名 `MCP_Web_Use`。
2. 从 git 历史(`49d1891f` 前后)完整找回 Chrome/CDP 时代的知识库文档(38+1 篇)与全部实现源码(47 个文件),零丢失。
3. 同一 Agent 工具面同时持有两个工具;**默认优先 `MCP_Web_Chrome_Use`**(支持人工交互),`MCP_Web_LsmAgentBrowser_Use` 定位为反-反爬专用内核,仅在 Chrome 被风控/抹除/验证墙拦死时启用。
4. 两个工具的对外契约(信封 `{code,message,data}`、page_id 生命周期、错误码语义)保持一致,降低 Agent 心智负担。

**非目标**

- 不在本阶段把 Chrome/CDP 时代的全部高级能力(隐身注入、指纹一致化、站点熔断、HITL 弹窗闭环等)一次性移植完毕——按第 9 节分阶段路线图推进,历史实现已完整归档可对照移植。
- 不改变 LsmAgentBrowser 内核的任何行为,仅重命名。

## 4. 双工具定位与使用场景

### 4.1 定位对比

| 维度 | `MCP_Web_Chrome_Use`(默认优先) | `MCP_Web_LsmAgentBrowser_Use`(反爬专用) |
|------|--------------------------------|------------------------------------------|
| 底层 | Chromium 子进程 + CDP(chromiumoxide 0.9) | 进程内自研内核(无外部浏览器进程) |
| 覆盖目标 | 日常 80-90% 的打开/读取/点击/输入/截图/人工交互 | 对 Chrome 风控敏感的站点(打标/抹除/滑块/指纹检测) |
| 人工交互 | headed 窗口,验证码/登录可交人工(后续阶段恢复 HITL 闭环) | `control(request_human)` 桥接 HITL |
| JS 兼容性 | 真 Chromium,全兼容 | Boa(阶段一/二),复杂站点可能 boot 失败 |
| 渲染 | 真浏览器渲染(canvas/WebGL 可用) | 软件渲染,canvas/WebGL 未实现 |
| 资源占用 | 高(独立浏览器进程) | 低(进程内) |
| 指纹面 | 有(靠反检测注入压低,后续阶段移植) | 几乎无(天然利于反-反爬) |

### 4.2 选用决策(写入 Agent 系统提示词)

1. **默认**:任何网页任务先尝试 `MCP_Web_Chrome_Use`。
2. **切换到 LsmAgentBrowser 的信号**(满足其一):
   - Chrome 返回风控特征:验证码/滑块反复出现、页面被抹除、登录态被清、`code` 提示访问被拒;
   - 目标站点历史上对 Chromium 指纹强检测(如招聘类风控站点,见 `docs/MCP_Web_Chrome_Use/` 反检测系列);
   - 任务明确要求"避免被检测"。
3. **切回 Chrome 的信号**:LsmAgentBrowser 页面 boot 失败(canvas 类应用)、JS 兼容不足。
4. 两个工具共享同一套信封与 page_id 约定,跨工具切换不丢任务上下文(各自维护独立的页面注册表)。

## 5. 工具契约

### 5.1 共同约定

- 响应一律为 JSON 信封:`{"code": int, "message": str, "data": {...}}`;`code=0` 成功,非 0 为错误码(沿用既有错误码体系,如 `6001` 任务锚点越界、`2002` 等待超时)。
- `page_id` 生命周期:`open` 获取 → 后续 action 复用 → `close` 销毁;派生页经 `spawned_page_id` 回传。
- 任务锚点 L3 阻断:显式 URL 动作越界一律返 `code=6001`,两工具一致(`crate::agent::safety::check_open_against_target_anchor`)。
- 网页取证纪律:两工具产出均为有效网页证据;Bash 网络命令顶替的硬闸门对两工具名同时放行(`src/agent/safety/web_evidence.rs`)。

### 5.2 `MCP_Web_Chrome_Use` action 集(基础框架)

| action | 说明 | 状态 |
|--------|------|------|
| `open` | 打开 URL(按需拉起 Chrome 子进程),返 `page_id` + 标题/URL + `tool_hint` | ✅ 已实现 |
| `list` | 列出存活页面 | ✅ 已实现 |
| `close` | 关闭指定页或 `page_id="all"` | ✅ 已实现 |
| `control` | `control_action`: `navigate` / `click` / `type`(= `input_text`) / `eval_js` / `screenshot` / `scroll` / `wait`(ms 或 selector 就绪判定) / `back` / `forward` / `reload` | ✅ 已实现(基础集) |
| `inspect` | `info`: `url` / `title` / `text` / `html` / `screenshot`(支持 `params.save_path` 落盘) | ✅ 已实现(基础集) |

> 2026-10-23 实测补齐(见 `docs/MCP_Web_Chrome_Use/41-双浏览器工具实测结论与百度地图场景对比.md`):
> 截图 `params.save_path` 落盘(信封只回 `{path,bytes,width,height}`,防 base64 撑爆上下文)、
> `input_text` 别名、`wait(selector)` 就绪判定、跨工具 page_id 诊断文案。

### 5.3 `MCP_Web_LsmAgentBrowser_Use` action 集

保持不变(8 个 action:`open`/`list`/`close`/`control`/`inspect`/`sequence`/`batch`/`explore`;`control_action` 48 个写操作;`inspect` 23 个观察维度),详见 `docs/MCP_Web_LsmAgentBrowser_Use/03-MCP_Web_LsmAgentBrowser_Use兼容层设计.md`。

## 6. 代码架构

```
src/agent/
  chrome_browser/                 # Chrome/CDP 驱动(新增,基础框架)
    mod.rs                        # ChromeManager 单例:子进程拉起/回收、页面注册表、模式判定
    page.rs                       # ChromePage:导航/eval/截图/点击/输入/滚动(基于 chromiumoxide Page)
    tests.rs                      # 单元测试
  tools/
    mcp_chrome_use/
      mod.rs                      # McpChromeUseTool + action 分发 + 信封 + 6001 锚点守卫
      tests.rs                    # 工具名单测、schema 形状、参数解析
    mcp_web_lsm_browser_use/      # 原 mcp_web_use,仅重命名,逻辑零改动
  browser/                        # LsmAgentBrowser 内核,目录不变
```

- 依赖:`Cargo.toml` 恢复 `chromiumoxide = "0.9"`(`futures = "0.3"` 已存在)。
- 模式:`LAEW_CHROME_MODE` = `headed` / `hidden`;未设置时按交互性自动判定(stdin/stdout 均 TTY → headed,否则 hidden),与 `LAEW_BROWSER_MODE` 语义对齐。
- 进程回收:进程退出时关闭 Chrome 子进程(挂接既有 graceful shutdown 通道)。

## 7. Agent 工具面与提示词变更

- 所有原本注册 `MCP_Web_Use` 的注册表位点(`builtin_registry` 全平台、yolo、plan、main_work、sub_agent_work 等)**同时注册两个工具**;工具描述中写明第 4.2 节的选用决策(Chrome 默认优先)。
- `src/agent/profile.rs` 的 UI 类 hint 判定(`trace.tool_call_log` 出现浏览器工具)对两个工具名同时生效。
- `src/agent/system_prompt/web_traversal.rs` 网页遍历提示词:双工具并列描述 + 选用决策。
- 环境变量开关:`LAEW_CHROME_USE=off` 可整体关闭 Chrome 工具(回退单内核行为)。

## 8. 安全与合规

- 任务锚点、网页取证纪律、SSRF 私网拦截对两工具同等生效。
- Chrome 工具额外注意:headed 模式下人工可见浏览器窗口,弹窗/HITL 能力属后续阶段;基础框架的 `eval_js` 仅限页面上下文执行,与 Lsm 版 `LAEW_WEB_EVAL_TIMEOUT_MS` 类似的执行预算由 CDP 调用自身超时兜底。
