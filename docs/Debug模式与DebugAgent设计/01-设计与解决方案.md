# Debug 模式与 Debug Agent —— 设计与解决方案

> 版本: v1.0(2026-09-08,最新唯一版本,历史记录已合并删除)
> 状态: 已实现
> 关联代码: `src/agent/debug.rs` / `src/agent/profile.rs` / `src/agent/system_prompt/mod.rs` / `src/main.rs` / `src/tui/mod.rs`

## 1. 需求概述

新增调试模式 `laew -debug`(等价 `--debug`),用于:

1. 以调试模式运行,采集各 Agent 的**输入/输出、性能(耗时/token)、质量(QC 结论)、错误**等详细信息。
2. 新增第 7 个 Agent:**`LsmAgentEmergentWork-Debug`**,专门做任务评估、质量报告、问题报告的生成(对采集到的 trace 做 LLM 评估)。
3. 调试文档输出到 **根目录(laew 所在目录)`DebugReport/`** 下的 `*.md`,文件名含**日期 + 时间 + 随机数**。
4. 使用说明写入 `CLAUDE.md` / `AGENTS.md`(只保留最新一份记录)。
5. `DebugReport/` 加入 `.gitignore`。

## 2. 借鉴来源(已使用,防重复引用)

本设计参考了 `docs/Agent源码调研/` 中以下已调研成果(**已在本轮使用,后续轮次勿重复引用**):

| 来源 | 借鉴点 | 落实到本设计 |

## 3. 总体架构

```
laew -debug [-p "任务" | -f prompt.md | TUI]
        │
        ▼
DebugLlmClient(装饰器,包住真实 LlmClient)
        │  每次 complete():记录 agent 名/输入摘要/输出摘要/耗时/usage/错误
        ▼
MultiAgentOrchestrator(OrchestratorConfig.debug = Some(collector))
        │  额外记录:Yolo 分类结果 / 每次 QC 结论 / 任务终态
        ▼
DebugCollector(内存事件列表,Mutex 保护)
        │  任务结束后
        ▼
finalize_report():
  1) 渲染「原始 trace」Markdown(统计总览 + 逐事件明细)
  2) 调用 Debug Agent(LsmAgentEmergentWork-Debug)对 trace 做评估
     → 产出「任务评估 / 质量报告 / 问题报告」章节
  3) 合并写入 DebugReport/debug_report_{YYYYMMDD}_{HHMMSS}_{rand6}.md
```

### 3.1 关键设计决策

- **LLM 层装饰器采集**:`DebugLlmClient` 实现 `LlmClient` trait 包装真实客户端,
  在 `complete()` 前后打点。Agent 名称从系统提示词中识别(各 profile 的提示词均含自身名称,
  由既有单测保证)。此设计对 6 大 Runner 零侵入。
- **编排层事件补充**:Yolo 分类、QC 结论、任务终态无法从 LLM 层观察到,
  由 `MultiAgentOrchestrator::handle()` 通过 `OrchestratorConfig.debug` 可选注入采集。
- **报告生成时机**:`-p`/`-f` 单轮模式任务结束后生成一次;TUI 模式每完成一个用户任务生成一份。
- **Debug Agent 无工具**:只做文本评估(同 SessionContext),避免调试行为反过来修改系统状态。
- **脱敏**:trace 写入文件前对 `Bearer <token>`、`sk-...`、`api_key=...` 等形状做正则替换。

## 4. 模块设计

### 4.1 `src/agent/debug.rs`(新增)

```rust
/// 调试事件(强类型)
pub enum DebugEvent {
    /// 一次 LLM 调用(任意 Agent)
    LlmCall {
        agent: String,          // 从系统提示词识别的 Agent 名
        seq: usize,             // 全局序号
        started_at: String,     // 可读时间
        duration_ms: u128,      // 耗时
        input_summary: String,  // 输入摘要(最后一条 user 消息,截断)
        message_count: usize,
        tool_count: usize,
        output_summary: String, // 输出摘要(文本+工具调用,截断)
        usage: Usage,
        stop_reason: Option<String>,
        error: Option<String>,  // 调用失败时的错误
    },
    /// Yolo 分类结果
    Classification { level, goal, intent, purpose },
    /// 一次 QC 结论
    QualityCheck { source, verdict, issues, suggestion },
    /// 任务终态
    TaskEnd { outcome: String, total_usage: Usage, total_duration_ms: u128 },
}

pub struct DebugCollector { /* Mutex<Vec<DebugEvent>> + session_id + started_at */ }

/// 装饰器:包住真实 LlmClient,采集每次 complete()
pub struct DebugLlmClient { inner: Arc<dyn LlmClient>, collector: Arc<DebugCollector> }

/// Debug Agent Runner:对 trace 做 LLM 评估
pub struct DebugRunner { agent: Agent }

/// 生成并落盘报告,返回文件路径
pub async fn finalize_report(collector, llm, report_dir, meta) -> Result<PathBuf>
```

### 4.2 Agent Profile(第 7 个 Agent)

- 名称常量:`DEBUG_AGENT_NAME = "LsmAgentEmergentWork-Debug"`。
- `AgentProfile::debug_profile()`:系统提示词 `SystemPrompt::debug()`,工具集为空(复用 `session_context_registry()` 的空注册表模式,新增 `debug_registry()`)。
- 系统提示词职责:输入 trace Markdown → 输出固定四章节 Markdown:
  1. **任务评估**(目标达成度、档位选择合理性)
  2. **质量报告**(各 Agent 输出质量、QC 通过率)
  3. **问题报告**(错误/重试/超时/异常模式,按 P0/P1/P2 分级)
  4. **优化建议**(可落地的改进项)

### 4.3 CLI 与报告文件

- clap 新增 `--debug` flag;`main()` 入口把字面量 `-debug` 归一化为 `--debug`(兼容用户习惯写法)。
- 报告目录:`Paths::detect().root_dir.join("DebugReport")`,不存在则创建。
- 文件名:`debug_report_{YYYYMMDD}_{HHMMSS}_{6位随机十六进制}.md`。

### 4.4 报告文件结构

```markdown
# laew Debug 报告
- 生成时间 / Session ID / 运行模式(-p / -f / TUI)/ 当前模型
## 一、统计总览          (LLM 调用次数、总耗时、token 汇总、错误数、QC 通过率)
## 二、Debug Agent 评估   (LsmAgentEmergentWork-Debug 产出:任务评估/质量报告/问题报告/优化建议)
## 三、原始 Trace 附录    (逐事件明细:每次 LLM 调用输入输出摘要、分类、QC、终态)
```
