### 1.2 核心失败根因(8 项)

| # | 根因 | 严重度 | 说明 |
|---|------|--------|------|
| **R1** | 系统提示词 Unicode 转义泄漏 | P0 | `src/agent/system_prompt/mod.rs:1053` 与 `:1072` 两处字面遗留 `\u70b9` `\70 70\u70b9` —— LLM 看到的是 `70 70\u70b9 click_point 递\u4f20` 的乱码,不是中文「点」「传」,严重污染降级指令语义 |
| **R2** | MCP_WINDOW_USE_PROMPT_SECTION 过长冗余 | P0 | 历经 18 轮迭代堆积 ~280 行/120+ 条规则;LLM 在长 prompt 下注意力分散,执行决策反而劣化;Plan 生成需 122.8s(超出 60s 等待阈值 → 用户体感「卡死」) |
| **R3** | Main-Work 仍生成 6 个 WorkFlow | P0 | 即使第 101 轮已加「2~3 个 wf 不要 6」规则,LLM 仍拆解为 6(开场 → 控件解析 → 联系人切换 → 聊天循环 → 日志 → 报告);长 prompt 让 LLM「看不全」规则 |
| **R4** | Plan 与 Main-Work 系统提示词重复堆砌 | P1 | 同一规则在 SubAgent-Work(Main-Work 编排者)+ Main-Work + Plan 三处重复出现;同一关键词(微信/控件树/MCP_Window_Use)被四个层级 prompt 各自强化,实际权重被稀释 |
| **R5** | Chat-loop 焦点守卫失败后无用户交互 | P1 | 「连续 3 轮前台守卫失败」自动止损中止,不再重试也不再询问用户;若用户在 30s 内未回到窗口,任务彻底失败 |
| **R6** | osascript_exec 无 cancel token 检查 | P1 | `std::thread::sleep(50ms)` + `try_wait` 轮询,在 cancel 触发时不能即时退出;长 chat_loop + 多次 Ctrl-C 后 zsh suspend 而非 exit |
| **R7** | TUI 工具调用明细冗长 | P2 | `print_tool_call` 输出 8 行明细,数据量大时刷屏;用户希望「调用的简介信息,数据量大时只给核心信息」 |
| **R8** | Main-Work 解析 Plan 失败兜底未走 self_drawn 路线 | P1 | Plan → JSON 解析失败 → 兜底生成单 wf「默认流程」时,delegate_to 仍是 SubAgent(无 explore/chat_loop 引导);LLM 兜底路径仍走 inspect 失败循环 |

## 三、修改点详解

### M1: Unicode 转义漏洞修复(P0)

**文件**:`src/agent/system_prompt/mod.rs`
**位置**:L1053 与 L1072

**问题**:`(c) chat_loop 默认 visual_no_input:一定要 ocr 取入框 70 70\u70b9 click_point 递\u4f20;` 与 `立即止损换路线,不要第 3 次。\70 70\u70b9 click_point 递\u4f20;` —— `\u70b9` 应是「点」的中文(汉字「点」unicode U+70B9),但 raw 字符串 `r#"..."#` 不做 unicode 转义,LLM 看到的就是字面 `\u70b9`。

**修改**:
```rust
// 替换为:
(c) chat_loop 默认 visual_no_input:一定要 ocr 取入框(右下)坐标 click_point 传给 chat_loop;

// 删除重复的尾巴
...不要第 3 次。
```

### M2: MCP_WINDOW_USE_PROMPT_SECTION 精简(P0)

**文件**:`src/agent/system_prompt/mod.rs`
**位置**:MCP_WINDOW_USE_PROMPT_SECTION 常量(整段替换)

**精简原则**(用户诉求):
- 删除历史规则(轮次标注 §N 只保留第 102 轮总章);
- 删除与 SubAgent 模板/Main-Work 模板/PlanRunner 重复的规则;
- 删除已被 M2/M3 修复覆盖的旧规则(inspect-失败-换 max_depth 等);
- 保留 8 条核心规则:
  1. capability_probe 必调 + 路线决策
  2. 启动用 bundle_id/中文别名
  3. chat_send / chat_loop 复合 action(微信聊天首选)
  4. explore + run_sequence 双模式(连续工作模式)
  5. Doom Loop 防护
  6. 自绘 UI 降级唯一路径(第 101 轮总章)
  7. 长时等待红线
  8. Windows 平台专属

**预估行数**:280 → 90 行,4800 → 1800 字,token 占用减半。

### M3: Main-Work self_drawn 任务模板强化(P0)

**文件**:`src/agent/main_work/mod.rs`
**位置**:Main-Work 系统提示词中编排范式 JSON 块前 5 行

**修改**:把 self_drawn 任务「2~3 个 wf」模板移到编排示例前,作为首个例子:

```markdown
【重要:编排范式(请严格按示例结构输出,例 1 是自绘 UI 任务的高频场景)】
例 1(自绘 UI 微信/钉钉/飞书/QQ,★最重要★)——
当任务涉及「微信」「钉钉」「飞书」「QQ」「桌面聊天」等自绘 UI 应用时,
**禁止**生成「控件结构深度解析」「控件路径映射表」「AX 路径枚举」等 wf 单元
(自绘 UI 控件树为空,这些任务不可能完成,浪费迭代预算)。
**正确模板**(2~3 个 wf,不要 6 个):
  wf-1:打开/激活目标应用 + explore 快照(explore 一次拿全)
  wf-2:执行核心任务(chat_loop 多轮聊天 / run_sequence 批量操作)
  wf-3(可选):生成报告(读取 chat_log 落盘 Markdown)
wf-2 的 acceptance 锚定 chat_log_path 文件中的 [SEND]/[RECV] 行数。

例 2(常规 GUI 任务,如 VSCode/Notion)——
...  (其余示例,精简为 1~2 个)

【JSON 输出格式】{...}
```

### M4: Plan 系统提示词不重复 MCP 规则(P1)

**文件**:`src/agent/plan.rs` 与 `src/agent/profile.rs`
**位置**:`main_work_profile()` / `plan_profile()` 工厂函数

**修改**:Plan 与 Main-Work 的系统提示词不再嵌入 MCP_WINDOW_USE_PROMPT_SECTION 完整副本;只引用一句:
```
> 桌面窗口操控任务的编排规范请参考 SubAgent-Work 模板的 MCP_Window_Use 章节;
> 你的工作是把用户目标拆解为 WorkFlow 列表,具体执行规则由 SubAgent 在执行时加载。
```

### M5: Chat-loop 焦点守卫失败 → TUI 询问用户(P1)

**文件**:`src/agent/tools/mcp_window_use/chat.rs` + `src/agent/human_assist.rs`
**位置**:`run_chat_loop` 中 `focus_aborted = true` 时

**修改**:当连续 3 轮焦点守卫失败,除 focus_aborted=true 外,通过 `HumanAssistHub` 向 TUI 发起询问:
```
[人工介入] chat_loop 检测到窗口连续 3 次未前台(用户可能正操作其他窗口)。
请选择:
  [1] 继续重试(再尝试一次)
  [2] 暂停等待(我会停在原地直到你说继续)
  [3] 立即中止 chat_loop(已发 N 条,已落盘到 chat_log)
```

**实现**:复用现有 HITL 机制(human_assist.rs);TUI 内弹出选择菜单,oneshot 回填决定;非 TUI 模式 fail-fast 沿用旧行为。

### M6: osascript_exec + run_blocking 加 cancel token 检查(P1)

**文件**:`src/agent/tools/mcp_window_use/chat.rs` + `src/agent/tools/mcp_window_use/mod.rs`
**位置**:`osascript_exec` 与 `run_blocking`

**修改**:`osascript_exec` 的 50ms sleep 间隔替换为 tokio yield,并加 cancel token 注入(经调用方传入,默认 None 兼容旧调用);`run_blocking` spawn_blocking 内部主循环也加 cancel 检查。

### M7: TUI 工具调用摘要精简(P2)

**文件**:`src/tui/format.rs`
**位置**:`print_tool_call` 函数

**修改**:MCP_Window_Use 工具的明细默认 4 行(原 8 行);工具调用参数 `<=` 仅前 60 字符(原 100);Bash `<=` 30 字符(原 40);Read/Write path `<=` 50 字符。

### M8: Main-Work 解析失败兜底走 self_drawn 路径(P1)

**文件**:`src/agent/main_work/mod.rs`
**位置**:`plan_workflows` 兜底分支

**修改**:Plan 解析失败时,若原 prompt 含自绘 UI 关键词(微信/钉钉/飞书/QQ),兜底 WorkFlow 直接使用 self_drawn 模板(2 wf:explore + chat_loop),而非退化「单 wf 默认流程」。

## 六、风险评估

| 风险 | 影响 | 缓解 |
|------|------|------|
| 精简提示词后旧场景覆盖不全 | 中 | 保留 8 条核心规则覆盖 95% 场景;边缘场景由 SubAgent 自主决策 |
