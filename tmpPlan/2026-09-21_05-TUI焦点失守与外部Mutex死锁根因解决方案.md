# TUI 焦点失守与外部 Mutex 死锁根因解决方案

**日期**: 2026-09-21
**轮次**: 第 104 轮
**问题来源**: 长任务/失败任务后 TUI 无法继续输入,Ctrl-C 显式 `^C`、Ctrl-D 也不退出;debug 日志最后停留在 `persist_chat_history: lock acquired`。

---

## 一、问题全景分析

### 1.1 复现场景

测试输入: `Explain rust ownership in detail`（mock LLM 故意返回连接拒绝,模拟真实失败任务）。
复现路径:
```
tmux send-keys -l "Explain rust ownership in detail"
tmux send-keys Enter
# 任务失败(网络错),任务流程结束 → 屏幕显示 >> 与提示行
tmux send-keys C-c
# 期望:程序退出(raw 模式下 Ctrl-C 被 InputHandler 拦截为空 buffer → Exit)
# 实际:屏幕显示 `^C`,Ctrl-D 不退出,焦点仍在 >> 但 raw mode 已失守
```

### 1.2 关键症状

1. **`>>` 仍在屏底**:说明 `enter_pinned` 执行过(滚动区/分隔线/提示行/快捷键 hint 都在)
2. **`^C` 显式回显**:raw mode 已经丢失(否则 Ctrl-C 被拦截为键事件而非 `^C` 回显)
3. **进程未退出**:Tokio signal handler 已被 abort,默认 SIGINT 处理应终止进程,但仍存活
4. **任务后无法回到 `read_line`**:debug 日志显示 `[DEBUG-DP] persist_chat_history: lock acquired` 后即停止

### 1.3 死锁根因 - 完备溯源

通过 macOS `sample <pid>` 取栈调用文件,关键路径:

```
persist_chat_history + 780
  current_model_name + 56      ← 关键！在持锁期间再调 current_model_name
    Mutex::lock + 12            ← std::sync::Mutex<Db> 第二次 lock
      _pthread_mutex_firstfit_lock_wait
        __psynch_mutexwait        ← 内核态 mutex 阻塞
```

具体调用链:

```rust
// src/tui/dispatch.rs::persist_chat_history
pub(crate) fn persist_chat_history(&self) {
    ...
    let lock_result = self.db.lock();      // ← 第一次拿 outer Mutex<Db>(成功)
    match lock_result {
        Ok(_guard) => {
            ...
            let model_name = self.current_model_name();  // ← 关键 bug!
            //     └── fn current_model_name(&self) -> Option<String> {
            //             self.db.lock().expect("db").get_active_or_env()...
            //                              ↑ 第二次锁 outer Mutex(死锁!)
            ...
            _guard.save_chat_snapshot(..., model_name.as_deref(), ...);
        }
        ...
    }
}
```

**核心矛盾**:`std::sync::Mutex<Db>` 是**非可重入**(non-reentrant)。同一线程在持锁状态下再次 `lock()` 会无限阻塞等待(连 busy_timeout 都不生效,因为 std Mutex 是 OS-level mutex)。

而 `current_model_name` 是仅需读 `provider.model_name` 字段,与 persist 写 `chat_sessions/chat_turns` 表没有共享状态。但因为都通过 outer Mutex 串行,被强行绑在一起。

### 1.4 影响

- **焦点失守**:任务失败 → dispatch_prompt 同步调 persist_chat_history → 死锁 → main loop 卡在 dispatch_prompt → 不再调 read_line → TUI 不接收输入
- **raw mode 丢失**:read_line 的 disable_raw_mode 在 read_line 函数返回时调用;死锁让 read_line 不被触发 → 屏幕仍是 TUI 布局,但 raw mode 在上一次 read_line 退出时已关闭(Submitted 后)。新读行的 enable_raw_mode 因死锁未到达。
- **Ctrl-C `^C`**:用户按下 Ctrl-C → 终端处于 cooked mode(tty ICANON+ECHO+ISIG)→ 触发 `^C` 回显 + SIGINT；tokio::signal handler 已被 abort,sig_task 不再响应 SIGINT；SIGINT 默认动作是终止进程，但因为我们处在某个 hold 状态？？

实际验证:在 macOS 上 SIGINT 不会立刻终止 Rust 进程(因为我们没安装 signal handler 时是默认 SIG_DFL,但 Rust runtime 会包装)。让我看到 SIGINT 后状态:

更精确:**SIGINT 触发了 `_pthread_mutex_firstfit_lock_wait` 内核态等待的内核 timer 唤醒**;主线程被锁在 mutex 等待,SIGINT 唤醒但 mutex 持有方是同一线程(自死锁),所以没意义。但**未持有 mutex 的子线程**(tokio-rt-worker)可以响应 SIGINT,但 `sig_task` 已被 abort,无 handler；SIGINT 默认 action 是 terminate,但因 Rust main thread 持有 tokio runtime 的某些锁??实际不会终止,需 kill -9 才能退出。

### 1.5 关联信号点

排查过程中通过详细的 `eprintln!` 探针 + tokio select poll trace,确认:
- ❌ read_line 调用正常(Enter → Submitted → read_line 返回 OK)
- ✅ main loop 调用 handle_user_input OK
- ✅ dispatch_prompt 进入
- ✅ orchestrator handle_cancellable_with_progress 完成(任务失败 Err)
- ✅ stage_printer 正常退出(stage_rx None)
- ❌ persist_chat_history 拿到 outer Mutex 后,调 current_model_name 时死锁

## 二、解决方案

### 2.1 核心修复:打破 outer Mutex 的同事务再入

**改动**:`src/tui/dispatch.rs::persist_chat_history` 在拿锁**之前**先算好所有需要从 outer Mutex 读出的标量(仅 `model_name` 一项),再一次性进入锁区域完成写库。

```rust
pub(crate) fn persist_chat_history(&self) {
    if self.transcript.is_empty() { return; }

    // 准备标量(在锁外),避免持锁后调 current_model_name() 二次拿 outer Mutex 死锁
    let turns: Vec<...> = ...;            // transcript 是 &self 只读,可在外组装
    let title = ...;                       // 同上
    let work_dir = ...;
    let model_name = self.current_model_name();  // ← 关键:锁外求值!

    let guard = match self.db.lock() {
        Ok(g) => g,
        Err(p) => {
            tracing::warn!(error = ?p, "会话持久化:outer db mutex 中毒,本轮跳过");
            return;
        }
    };
    if let Err(e) = guard.save_chat_snapshot(
        &self.session.id, &self.session.created_at, &work_dir,
        model_name.as_deref(), &title, &turns,
    ) {
        tracing::warn!(session_id = %self.session.id, error = %e, "会话持久化失败(不影响当前对话)");
    }
}
```

**为什么 work_dir / turns / title 可以在锁外算?**
- `self.transcript` 是 `Vec<TranscriptEntry>`,只在 TuiSession 内被 push/读取,**本任务内其他代码路径不持有 &mut**
- `self.paths.work_dir` 是 `PathBuf` 不可变引用
- `self.session.id`/`self.session.created_at` 是 String 不可变
- `current_model_name` 短暂取 outer Mutex(很快释放)
- 所以锁外预处理是安全的

**为什么不在 outer Mutex 内做?**
- `current_model_name` 必须锁 outer Mutex,因为内部调 `get_active_or_env`,而 `get_active_or_env` 又是 `self.conn.lock()`(这是 inner Mutex,而不是 outer Mutex)
- 等等:`prompt 看一下实际路径

```rust
pub(crate) fn current_model_name(&self) -> Option<String> {
    self.db
        .lock()        // ← outer Mutex<Db>
        .expect("db")
        .get_active_or_env()  // ← &Db 方法,内部还有 self.conn.lock() = inner Mutex
        ...
}
```

是的,`current_model_name` 也拿 outer Mutex,所以**任何 outer Mutex 持有方调它都会死锁**。

### 2.2 复用 current_model_name 路径:增加无锁版本

为了未来代码不再踩坑,增加 `current_model_name_via_arc_db` 用 `Arc<Db>`(orchestrator 那份)查询,避免 outer Mutex:

但这要求把 `Arc<Db>` 缓存到 TuiSession 字段。本次最小修复只动 persist_chat_history,避免爆炸面。

### 2.3 TUI 焦点失守防线加固

即使 persist_chat_history 修了,任何未来再入 outer Mutex 的 bug 仍会死锁导致焦点失守。增加:

1. **`db_lock_timeout` 持续配置**:为 outer Mutex 引入 try_lock_with_timeout(基于 tokio::sync::Mutex 包装 outer,持有期必须 < 0.1s)。但改动面较大,本次仅在 persist_chat_history 改成 try_lock + warn 日志。
2. **`persist_chat_history` 用 try_lock**:outer Mutex 争用立即返回 + warn,绝不阻塞主循环。

### 2.4 panic 安全网:read_line 内部 panic 不炸 raw mode

```rust
// src/tui/input.rs::read_line
let result = std::panic::catch_unwind(std::panic::AssertUnwindSafe(|| {
    self.read_line_inner(prompt, engine)
}));
let result = match result {
    Ok(r) => r,
    Err(panic_payload) => {
        // 不要炸 raw mode,而是返回 IO 错误让主循环清理
        let _ = terminal::disable_raw_mode();
        return Err(std::io::Error::new(
            std::io::ErrorKind::Other,
            format!("read_line_inner panicked: {:?}", panic_payload),
        ));
    }
};
// 然后照旧 disable_raw_mode
```

确保即使 read_line_inner 内部 panic(任何未来的 bug),raw mode 也会被关掉、main loop 也能从 Err(e) 分支清理终端。

### 2.5 主循环错误路径加 terminal 兜底

`src/tui/mod.rs` 在 `Err(e)` 分支已经有 `teardown_pinned()` + `terminal::disable_raw_mode()`,已经是 OK。本次确认无新改动即可。

### 2.6 SIGINT 双重保险

```rust
// src/tui/dispatch.rs::sig_task
let sig_task = tokio::spawn(async move {
    if tokio::signal::ctrl_c().await.is_err() { return; }
    sig_cancel.cancel();
    tokio::time::sleep(Duration::from_millis(300)).await;
    std::process::exit(130);
});
```

本次确保 sig_task.abort() 后 tokio::signal::ctrl_c() 句柄正确释放。验证:tokio 0.x 的 signal handler 在 Future drop 时自动反注册。
